# Lute 0.45 — stage meaning follows the lowered record, background barks, no concurrent presentations: decisions

Owner decision, 2026-10-15, after 0.44.0 (`81f660fe`). Scope set by the owner:

1. Stage bookkeeping keyed on the **lowered IR record kind** — shape 2
   ("the record kind is the meaning") of
   [`2026-08-10-staging-tag-dispatch.md`](2026-08-10-staging-tag-dispatch.md).
2. The "background bark during a conversation" host pattern, without
   concurrent presentations.
3. Concurrent presentations removed from the candidate list.

Evidence base: v0.44.0 plus two read-only inventories (stage dispatch;
runtime queries and barks) summarized below with file references. The owner
asked for conservative choices where judgement is needed; each is recorded
with its reason.

## Release shape

0.45.0 is a minor release. Every visible axis reads `0.45.0`; the contract
schemas move to the `0.45` line and `bindingsVersion` becomes `"0.45"`. The
**language** axis earns it: the compiled output of a document that uses a
plugin directive lowered to `bg` or `actor` can change (§1). No IR, Event,
snapshot or bindings **shape** changes; no new input kind; no new runtime
query; no new CLI surface.

## Findings

### Stage dispatch (v0.44.0)

- The reducer `lute_check::inject::lower_node` dispatches on the AST tag:
  `::actor` → `lower_actor`, `bg` → `stage_bookkeeping_bg`, `::clear` →
  `stage_clear`, `music` → bookkeeping (`inject.rs:262-273`);
  `exit_is_written_next` does the same (`inject.rs:710-725`). It receives AST
  nodes, the lookahead and the resolved domains, not the capability snapshot,
  so a plugin directive's `lower: { record, fields }` is invisible to it.
- Its two callers are the checker fold (`check/injections.rs`,
  `check/pipeline.rs:741-760`) and the compiler walk
  (`lute-compile/src/stage.rs:208-272`). The compiler walk also uses the
  `::actor` tag for the entry-emotion lookahead (`stage.rs:92,165,1020`) and
  for placement (an actor's injections follow the authored record, every
  other node's precede it, `stage.rs:238-272`).
- `lute-compile` lowers a plugin `record:` directive by kind and fields
  (`lower.rs:405-433`, `lower_record` `541-690`); the IR record is identical
  to the core one. The runtime stage (`lute-runtime/src/stage.rs:72-143`), the
  TypeScript runtime and the player already act on the record kind only; an
  `actor` record leaves the stage exactly when `exit: true`.
- Builtin hooks (`lower: { kind: builtin, name: actorStage | clearStage }`)
  are retagged to the core tag before both walks
  (`builtin_lowering.rs`, `lute-compile/src/lib.rs:516-520`,
  `lute-trace/src/pipeline.rs:200-204`), so they already behave like
  `::actor` / `::clear`. Only declarative `record:` lowering is affected.
- `lute-trace` marks a staging step as an exit from the tag (`::clear`, or
  `::actor` whose `action` is a declared exit; `trace/driver_records.rs:286-300`);
  a plugin `actor` record with `exit: true` is not marked.
- Corpus: one project lowers plugin directives to staging records —
  `docs/examples/typed-projection` (`game.presentation`: `backdrop` → `bg`,
  `portrait` → `actor`). Its only scene shows one character with an authored
  anchor and emotion, then an emotional line; no later scene change.
  Reproduction at v0.44.0 (0.44 decision note §3): a plugin `bg` after an
  on-stage character gets no `stage-bookkeeping` hide and a later plain line
  gets a spurious `auto-pose-reset`.

### Queries and barks (v0.44.0)

- Read-only queries take the state immutably and do not look at the await:
  `Runtime::candidates/view/evaluate/def/gate` (`runtime.rs:835-942`), the
  wasm wrappers (`lute-runtime-wasm/src/lib.rs:137-209`), TS `Program`
  (`packages/runtime/src/Program.ts:198-291`). `Session` locks only
  `send`/`restore` (`Session.ts:87-145`); a query during a running input sees
  the last committed state. So all five answer at `idle`, `awaitChoice`,
  `awaitBridge` and `ended`, and change nothing. Tests cover `view`/`gate` at
  `awaitChoice` only (`packages/runtime/test/Session.test.ts:71-89`).
- `step` refuses any input other than the matching answer while a choice or
  bridge is pending (`E-RUNTIME-BUSY`, `runtime.rs:800-831`); the player's
  `send` refuses outside `idle`/`ended` (`DirectorBusy`). A bark cannot be
  *raised* during a conversation, by design.
- A lore bark is an `<entry category="bark" on=…>` — a beat
  (`docs/runtime/lore-entries.md`). `candidates(occasion, target?)` returns
  `Candidate { id, kind: "entry", document, verdict, read, … }` in selection
  order. The artifact holds the entry head (`kind: "entry"`, `id`, `body`
  position) and, from `body` to the next head, its body records; a line record
  carries `speaker`, `text`, `lineId`, `voiceKey`, optional `texts` (locales)
  and optional `placeholders` (`{{…}}` the runtime substitutes). The index
  maps `document` → artifact and `cast` → display names. So a host can read a
  selected bark's lines from the bundle alone **when the body is static**: line
  records only, none with `placeholders`. A body with `match`, `jump`,
  placeholders, or writes (`set`/`assert`/`retract`; bark bodies may write —
  `docs/examples/games/drowned-crown/lore/quill.lute`) needs the runtime.
- Showing a bark this way records nothing: no `entry.<id>.read`, no `once`
  spending, no writes.

## Decisions

### 1. Stage meaning follows the lowered record kind

| Decision | Why |
|---|---|
| The stage reducer classifies each directive by the **staging record it lowers to** — core directives by their own lowering, a plugin directive by its `lower: { record, fields }` — and dispatches on that record kind: `bg` → scene change (auto-hide, clear `dirty`, record departures), `actor` → `lower_actor`, `music` → bookkeeping. `::clear` and builtin hooks are unchanged (they are already core tags when the walk runs). The same classification drives `exit_is_written_next`, the compiler walk's entry-emotion lookahead and injection placement. | Owner decision (shape 2). One rule: the checker's stage model treats a record the way the runtime will apply it. |
| **Applied to `actor` too**, reading the record's resolved fields: `character`, `anchor`, `action` (pose), `emotion`. A record leaves the stage exactly when its `exit` field is `true` — for core `::actor` that is today's rule (lowering sets `exit` from the action domain's `exits:`); for a plugin record it is the bound `exit` field. Bound `posReset`/`preload` fields do not change the reducer's view — the runtime stage ignores them too, so the checker follows the runtime (a later plain line may still get an injected pose reset). | The inventory shows a plugin `actor` today gets no entrance, exit or dirty bookkeeping, while the runtime stage treats it as a full actor record. Keying on `exit` (not the action domain) keeps the checker's stage equal to the runtime's for every record; for core records the two rules coincide, so core output is unchanged. |
| `::clear` keeps its own rule: it lowers to injected hides only, so there is no record to key on; builtin `clearStage` is already `::clear` when the walk runs. | Spec review: routing `::clear` through "no staging record" would break core byte-identity. |
| A declarative `actor` lowering must bind `character` to a required attribute or a literal; otherwise `E-LOWER-RECORD-FIELD` at assembly. | Spec review: `lower_record` fills an unbound/unauthored `character` with `""`, which the runtime stages as an actor named `""` while no stage rule can follow it. An actor record without a character is a plugin defect; refusing it is the conservative fix. The only corpus plugin (`game.presentation.portrait`) binds a required attribute. |
| Not applied to `cg`, `video`, `camera`, `sequence`, `sfx`, `vfx`: the reducer has no rule for them today, and none is added. `music` keeps its bookkeeping-only arm (it never clears the stage). The `semantics:` flags still do not drive dispatch (dsl 0.9.0 §7 stands for flags; the key is the closed record kind). | Same reducer coverage as before; the 0.9.0 objection was to `mutatesScene`, which `music` shares. The record kind has no such ambiguity. |
| `lute-trace` marks an `actor` record with `exit: true` as an exit, whatever directive produced it (with `::clear` unchanged). | Same principle where trace reads stage presence. Core records: `exit: true` iff the action is a declared exit — identical output. |
| Field resolution (`fromAttr` / literal → record field) has **one implementation**, shared by `lower_record` and the reducer's view; no second mapping. | A second mapping would drift from what the artifact contains. |
| **Output principle**: authored records keep their relative order; only injected records may appear or disappear, at the place the rule emits them (hides before the scene change, a pose reset before its line, an entrance's anchor/preload after it). Positions after an injection renumber, as for every injection. Diagnostics follow (`W-STAGE-ABSENT` after a plugin scene change, as after `::bg`). | Owner principle. |
| A project that uses only core directives compiles, checks, traces and plays **byte-identically**; CLI snapshot differences are allowed only for projects that use plugin directives lowered to `bg`/`actor` (corpus: `docs/examples/typed-projection`), and every difference is classified in the plan's progress log. | Owner acceptance criterion; the first half is the proof that the rule only changes plugin paths. |
| **D6 clean cutover**: no compatibility flag, no per-plugin opt-out. | Owner decision. A plugin that wants a background change without a scene change is asking for a different record; none exists today and none is added. |
| §11.5 of the base spec ("implicit staging … is implementation-defined") is amended: injected staging remains a toolchain rule, but it MUST treat a staging record by its kind and fields, whichever directive produced it. Recorded in the 0.45.0 spec and `spec/current.md`. | The staging note warned that shape 2 turns this into a cross-plugin contract; the sentence must say so. |
| Docs: the 0.44 workaround paragraph in website `plugins/manifests.md` (EN/KO, llms mirror) is replaced by the new rule; language docs that describe the scene-change hide and pose reset say it applies to any directive lowered to `bg`/`actor`. The staging-tag-dispatch note gets a second addendum (implemented in 0.45). | Owner instruction. |

### 2. Background barks during a conversation

| Decision | Why |
|---|---|
| **No contract change.** The pattern works today: while the story waits at `awaitChoice` or `awaitBridge`, the host may call `candidates(occasion, target?)` (and `evaluate`, `def`, `gate`, `view`) on the current state; they never change it. For a selected bark entry whose body is static (line records only, no `placeholders`), the host reads text (`texts[locale]` else `text`), speaker (display name from `index.cast`), `voiceKey` and `lineId` from the bundle and shows it in its own UI, outside the presentation. Such a showing records nothing (no read flag, no `once` spending, no writes). A bark that must record — first read, `once`, authored writes, or a dynamic body — is raised as its occasion after the story is back at `idle`. | Owner question answered "yes, within limits"; the limits are exactly what the IR can express without stepping. Conservative: no new query. |
| Pinned by tests: runtime TS tests run every query at `awaitChoice`, `awaitBridge` and `ended`, and during an input still running (the last committed state), and assert the snapshot is unchanged; a fixture with bark entries (static, with a placeholder, with a `::set`) checks that the documented reading of the bundle yields text, speaker, `voiceKey` and `lineId` for the static bark and identifies the other two as needing a raise; after the conversation, raising the occasion applies the writing bark. A player test runs `program.candidates` while the director shows a choice and asserts nothing changed. | "Documented and pinned" (owner). The tests check behaviour and IR invariants the pattern relies on. |
| Documented in `docs/runtime/event-contract.md` (queries at every await), website `tooling/runtime-contract.md` EN/KO and `player/custom-hosts.md` EN/KO (the pattern, a TypeScript example, the state-changing bark after `idle`). | Where hosts read about queries and `send`. |
| **Not done, recorded as a candidate**: a read-only runtime query that resolves a beat's lines (placeholders, `match`, locales) without stepping. | It would be a contract extension; no host has needed dynamic barks during a wait yet. The static case covers ambient barks. |

### 3. Concurrent presentations: not needed

| Decision | Why |
|---|---|
| Concurrent presentations are **removed from the candidate list**, not deferred. | A multi-speaker conversation is one scene (one presentation, many speakers). Ambient lines are lore barks raised by occasion. A background line during a conversation is §2's host pattern, which needs no second presentation. Nothing left requires two open presentations, and the single-presentation rule keeps replay, saves and the event contract simple. |
| Recorded in `docs/design/runtime-player.md` (where R1–R3 deferred them) and here. | Owner instruction. |
