# Lute 0.43 — agent-facing CLI contract: decisions

Owner decision, 2026-10-14. Scope approved by the owner after the 0.42.1
review: replace `serde_yaml` with `yaml_serde`, a JSON error envelope, a
`lute schema` command, one common JSON envelope across the CLI's reports, and
local-only, opt-out telemetry. Evidence: the owner-provided research report
[`docs/deep-research-report.md`](../../deep-research-report.md) (AI-agent CLI
design; committed with this note as its basis), a blessed.rs comparison, and
three inventories taken at `89ff8caa` (0.42.1): every JSON surface of the
CLI, the diagnostics registry/exit/doctor/test-spawn survey, and a trial
`yaml_serde` migration in a separate worktree.

The owner asked for conservative choices where judgement is needed; each such
choice is recorded below with its reason.

## Release shape

0.43.0 is a minor release: every visible axis reads `0.43.0`, the contract
schemas move to the `0.43` line (`schemas/lute-{ir,events,snapshot,player-bindings}-0.43.schema.json`),
and `bindingsVersion` becomes `"0.43"`. Language, IR, Event and bindings
**shapes** do not change: the schema bodies move only by their stamps, and the
generated TypeScript only by its header. The toolchain (CLI) earns the
release.

## Decisions

### 1. `serde_yaml` → `yaml_serde`

| Decision | Why |
|---|---|
| Replace the deprecated `serde_yaml 0.9.34+deprecated` with `yaml_serde 0.10.7` (the YAML organization's maintained fork) everywhere, including comments and docs that name the crate. No alias crate rename (`serde_yaml = { package = "yaml_serde" }`) — paths read `yaml_serde::`. | Clean cutover. The trial built clean, passed 4200/4200 tests and left all 6132 CLI snapshot outputs byte-identical. It also drops `unsafe-libyaml` (RUSTSEC-2023-0075, RUSTSEC-2024-0449) for `libyaml-rs`. MSRV 1.82 is below the workspace's 1.85. |
| `lute-runtime` is untouched (it does not depend on YAML). | Its wasm dependency set is fixed. |

### 2. Command identity

| Decision | Why |
|---|---|
| A command's id is its clap subcommand path as typed, space-separated: `check`, `check-project`, `scenario reach`, `loc report`, `catalog refresh`. The same id is used in the JSON envelope, the error envelope, `lute schema` and telemetry. Flags never change the id; `scenario`'s bare graph view is `scenario`. | One canonical name an agent can paste back (`lute schema scenario reach`); no second naming scheme (the report's "canonical surface only once" rule). A flag-dependent variant (e.g. `context --target`) is told apart by `schemaVersion`, which already names those shapes. |

### 3. Common JSON envelope

| Decision | Why |
|---|---|
| Every **report** a command prints in JSON mode is one JSON object whose first keys are `command` (the id), `schemaVersion` and `ok`, followed by the report's own fields at the top level (a flat envelope, not `{data, meta}`). | Uniform header for every report with the least churn: existing payload keys stay where consumers read them. A `data` wrapper would move every field of every report for no information gain. |
| `ok` is `true` exactly when the process exits `0`. | One rule an agent can rely on without per-command knowledge; it matches `check`'s existing `ok`. |
| `schemaVersion` names the payload shape as `<release>.<name>`, the convention 0.36.0 started (`0.36.0.diff`, `0.36.0.patch`, `0.36.0.context`, `0.36.0.position`). Those four keep their values (their payloads do not change). Every other report's value is `0.43.0.<id with spaces as dashes>`, e.g. `0.43.0.check`, `0.43.0.scenario-reach`. | Reuse the existing convention instead of inventing a second one; unchanged payloads keep their version. |
| A report that today is a top-level JSON array becomes an object: `constraints` rows under `constraints`, a `trace` refusal's diagnostics under `diagnostics`, `compile --json`'s refusal diagnostics under `diagnostics`. | An envelope needs an object; the key names the existing content. |
| **Not enveloped** (artifacts and engine contracts, unchanged): `compile`'s execution IR and `compile --all`'s output directory, `compile-stream`'s NDJSON, `run --json` (the reference transcript pinned by the conformance corpus), `play --events` (Event contract), `loc export` rows, and `version --json` (`{toolchain, language, ir}`). | They are consumed by engines, the conformance corpus or the playground as documents of their own; wrapping them would change contracts the release does not mean to change. |
| Pretty vs compact printing stays as each command has it. | Not part of the requested contract; avoids incidental churn. |

### 4. JSON error envelope

| Decision | Why |
|---|---|
| A command in JSON mode that fails before producing its report — usage error, unreadable/unwritable path, malformed input file — prints to **stdout** `{"command", "schemaVersion": "0.43.0.error", "ok": false, "error": {"code", "message", …}}` and keeps its exit code (`2`). The human message stays on stderr as today. | stdout is the agent contract; keeping stderr unchanged removes nothing a human relies on. Exit codes are an existing documented contract (0/1/2, trace/play 3). |
| JSON mode is: `--json` given; `--format json` (or `=json`) given; or the command is `schema`. Before clap succeeds it is detected from argv (tokens before `--`). | Usage errors happen before parsing; argv scanning is the only way to honour the caller's request. `loc export`'s implicit default format does not count — only an explicit request switches stderr-only errors to JSON. |
| Streams keep their own protocol: `compile-stream` and `play --events` never emit an error envelope (they already report rejections in-stream; other failures stay on stderr). | An object in the middle of an NDJSON stream would break the stream contract. |
| `patch` keeps the refusal objects it prints today (`0.36.0.patch` with its own `code`, e.g. `E-PATCH-EDIT`), enveloped like any report; the error envelope covers `patch` only where it prints no JSON today. `compile`'s gate refusal (exit 1) is the `compile` report; its rejected flag combinations (exit 2) are `E-CLI-USAGE`. | Spec review: `patch`'s refusals are an existing versioned contract with codes of their own; replacing them would break it for no gain. |
| Error codes are registered diagnostics (so `lute --explain` and the diagnostics reference cover them): `E-CLI-USAGE` (the invocation is invalid: unknown or missing argument, invalid value), `E-CLI-IO` (a path cannot be read or written), `E-CLI-INPUT` (an input file is not valid for the command: malformed JSON/YAML, wrong kind or version). | Three classes cover every exit-2 path found; each is actionable differently (fix the command line / the path / the file). Reusing the registry avoids a second code space. |
| `error` carries `code` and `message` always; `path` when a file is at fault; `argument` (e.g. `--deny-warning`) and `hint` (clap's most similar suggestion, e.g. `--deny-warnings`) for usage errors when clap provides them. No `retryable`, `request_id` or `retry_after_ms`. | A local, deterministic toolchain has no transient failures or requests; fields that are always `false`/absent would be noise the report itself warns against. |

### 5. `lute schema`

| Decision | Why |
|---|---|
| `lute schema [COMMAND]...` always prints JSON (the enveloped report, id `schema`, `0.43.0.schema`). With no path it lists the top-level commands (id, one-sentence summary, whether it has subcommands); with a path it describes that command: summary, arguments and options (name, long/short, required, repeatable, takes value, value name, possible values, default, one-line help), subcommands, and its JSON output (`flag`, `kind`: `report`/`artifact`/`stream`/`none`, `schemaVersion`). An unknown path is `E-CLI-USAGE`. | Progressive narrowing (the report's `schema`, `schema issue`, `schema issue update`) keeps each answer small. The clap command tree is the single source of arguments; the output kind/version come from the same table the envelope uses, so they cannot drift. |
| Hidden arguments and clap's generated `--help`/`--version` are omitted. | Not part of the agent contract. |
| No JSON Schema documents for each report in this release. | Each report would need a hand-maintained schema; out of scope, recorded for later. |

### 6. Local telemetry

| Decision | Why |
|---|---|
| On by default, opt-out; **local file only — no network code exists**. Each CLI invocation appends one JSON line to `telemetry.jsonl` in Lute's state directory. | Owner decision (local storage, opt-out). |
| Record: `{"v":1,"ts":<unix ms>,"lute":"<toolchain>","command":<id or null>,"json":<bool>,"exit":<code>,"durationMs":<ms>}`. Nothing else — no arguments, flag values, paths, file contents, output or environment. | The report's "canonical command, latency, exit class" minimum; anything more risks recording project data. `command` is `null` when argv names no known command. |
| Opt-out: `LUTE_TELEMETRY` set to `0`, `false`, `off` or `no` (any case), or `DO_NOT_TRACK` set to anything but empty/`0`. | Matches the conventions the report cites (`GH_TELEMETRY`, `DO_NOT_TRACK`). |
| State directory: `$XDG_STATE_HOME/lute` when it is an absolute path, else `$HOME/.local/state/lute` (Linux and macOS); `%LOCALAPPDATA%\lute` on Windows. No home → no telemetry. | std-only, no new dependency; XDG state is the right class for logs. |
| Records are best-effort: one append-mode write per line, rotation by rename, no lock. Under concurrency a record can land in the rotated file or be lost. | Spec review raised the rotation race; a lock could stall a command for telemetry, which is the worse failure. |
| The file is rotated once it reaches 1 MiB (renamed to `telemetry.jsonl.1`, replacing the previous one). Every failure (no directory, read-only disk) is silent and never changes output or exit code. Nothing is printed about telemetry during a command. | Bounded disk use; telemetry must not affect the command or pollute stdout/stderr. |
| `lute doctor` reports whether telemetry is on and the file path. No dedicated `telemetry` command. | Discoverable where setup is already reported; the file is plain JSONL for anyone who wants to read it. |
| The repository's own tooling opts out: `.cargo/config.toml` `[env]` sets `LUTE_TELEMETRY=0` for every cargo-run process (tests spawn the binary), CI workflows set it, and `scripts/cli-snapshot.py`, `scripts/check-doc-snippets.py` and the conformance scripts set it. Telemetry's own tests point the state directory at a temp dir. | Tests and generators must not write to the developer's home or depend on its state. |

## Out of scope (recorded)

Field projection (`--fields`), an `--agent` profile, batch patch input,
per-report JSON Schema documents, exit-code reclassification, remote
telemetry, and the deferred runtime items (C ABI, concurrent presentations).
