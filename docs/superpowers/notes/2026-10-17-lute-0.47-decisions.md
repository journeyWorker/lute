# Lute 0.47 — Brinewake round 2: decisions

Inputs: issues #118–#129 (label `dogfood`), filed in **Brinewake dogfood round 2**
(2026-10-17): the round-1 game (`The Last Bell at Brinewake`, a PixiJS town + player-web VN
life sim) moved to Lute 0.46.0 and grown with the features round 1 skipped — a festival hub
with `<return>`, a bridge minigame whose answer carries writes, rewards, timeline/CG bell
cinematics, a second play-through (`user.*`, `prev.run`), a Korean slice, and the AI edit loop
(`lute context` → `lute patch` → `lute diff`). Evidence (browser transcripts, screenshots,
patch files, friction logs) is on the owner's external SSD,
`/Volumes/External/work/brinewake-dogfood-2026-10-17/`; each issue body quotes what the release
needs. Round 2 also verified 0.46 in practice: #103–#107 and #111 hold; **#112 did not**
(→ #118).

Triage by the orchestrator for the owner (2026-10-17). Same rule as 0.46: develop what a real
host or author hit and cannot reasonably work around; one spelling per concept; D13 (the
runtime owns no presentation). Clean cutover (D6).

**Testing rule added by this release** (from #118, where a unit test mocked a plain string and
the feature never worked): every player / player-web behaviour this release touches is
tested against a **real runtime output** (a compiled fixture project through
`@lute-lang/runtime`, or the player-web browser/e2e suite), not a hand-written mock of a view
or record. Where an existing test of a touched feature mocks runtime data, replace it.

## Develop in 0.47

| Issue | Decision |
|---|---|
| #118 (bug, major) | `ui.ended` selects its screen from the real `view().state` entry (compare the entry's value, typed as the declared domain), with an e2e/browser test per screen in the player-web suite (the demo gets a multi-ending case) — the mocked-string test is replaced. |
| #122 (bug, major) | player-web shows translated dialogue: the line cue, backlog and every text surface read the line's `texts[locale]` (falling back to source) for the current `settings.locale`; choice labels and prompts likewise. Settings offers every locale the loaded bundle carries (source locale + compiled locales), not only the current one. Browser test: switch to `ko` mid-run and on a new game, named line + choice + prompt in Korean. |
| #121 (major) | A second play-through survives a page reload. The player persists the **lineage** (the runtime snapshot at the last `ended`, which holds `user.*`, user-tier facts and `prev.run`) in its profile store; New game after a reload restores that lineage and sends `newRun`. Rule clarified: `begin` on a session restored at `ended` sends `newRun` (it never re-presents `started`). `profileVersion` follows the release; older profiles keep read marks/settings and start with no lineage. Browser test: finish run 1, reload, New game → a `prev.run`-gated line and a `user.*` value from run 1. Documented in the player docs as the cross-run model. |
| #128 | Stale translations are diagnosed: `loc import` stores the source text hash per entry in the locale bundle, and `compile --locales` reports `W-L10N-STALE` (deniable) for an entry whose current source differs; the message names the lineId and says to re-export. `lute loc` docs EN/KO. |
| #125 (part) | Branch and hub `prompt=` text is localizable like choice labels: a stable lineId, exported by `lute loc export`, merged by `loc import` / `compile --locales`, read by the player (#122). **Not developed:** per-document locale scoping for partial slices — a shipping game translates fully; `W-L10N-MISSING` stays project-wide. |
| #127 | player-web draws `::cg` above the stage actors and below the dialogue/UI layers (an event illustration covers the stage). Document the layer order on the player-web page. Browser screenshot test. |
| #129 (bug) | No discard-progress confirm for `toTitle` when the flow is `ended`; the in-game menu keeps it. Browser test on the ended screen's button. |
| #120 | Bindings `ui.title.text` names the game on the title screen; when absent, the title shows the project's display name if the project declares one, else no heading (never the literal "Lute"). Bindings schema + checker + generated TS + player-web. |
| #119 | `bindingsVersion` follows the same rule as `luteVersion` (0.41.1 #76): `lute fix` raises a stale `bindingsVersion` to the toolchain line, and `check-project` warns (`W-BINDINGS-VERSION-STALE`) when it is older; a bindings file using a section newer than its declared line is an error naming the line it needs. |
| #123 (bug) | `lute patch` applies several edits in one file correctly (edits resolved against the original tree and applied in descending offset order, or re-resolved after each) and the written file passes `lute fmt --check` before `accepted` is reported. Regression test with two `replaceNode` edits in one file. |
| #124 | The `lute patch` request shape (`base`, `targets`, `edits`, `preserve`, node-key kinds) is documented on the website ai-harness page (EN/KO), and `lute schema patch` describes the request input as well as the output. |
| #126 | `lute diff git:<rev> <path>` materialises only the compared subtree (`git archive <rev> -- <path>`); special files outside it are irrelevant. Regression test with a symlink outside the compared project. |
| docs | The 0.46 tutorial's leftover "0.45 pattern" wording (round-2 note, not filed) is corrected; the tutorial gains the second-play-through and localization steps once #121/#122 land. |
