# Lute 0.44 — player hosting docs, terminal writes, staging-note closure: decisions

Owner decision, 2026-10-15, after a dogfood that moved lute-town (a Phaser
game) from Lute 0.41 to 0.43. Inputs: GitHub issues #94–#97 and the open items
of [`2026-08-10-staging-tag-dispatch.md`](2026-08-10-staging-tag-dispatch.md).
Evidence base: `5b223cde` (v0.43.0) plus two read-only inventories (player
hosting facts; terminal-write behaviour) and reproductions run on that tree
(below). The owner asked for conservative choices where judgement is needed;
each is recorded with its reason.

## Release shape

0.44.0 is a minor release. Every visible axis reads `0.44.0`; the contract
schemas move to the `0.44` line and `bindingsVersion` becomes `"0.44"` (the
alignment policy). No IR, Event, snapshot or bindings shape changes; no new
input kind; no new CLI surface. The toolchain earns the release with one
runtime message change (#97); the rest is documentation.

## Decisions

### 1. Player hosting documentation (#94, #95, #96)

| Decision | Why |
|---|---|
| Document three host recipes, in the same words, in `packages/player/README.md`, `docs/player/architecture.md` (a new "Hosting recipes" section) and the website `player/custom-hosts.md` EN and KO: (a) composing `Director.make` directly — `bundle` is required, `host.plugin` reaches the default cue factory, `cueFactory` is a wrapper of that default (or a pre-composed `Cues.make`); (b) `LutePlayer.make` with an external runtime session — build the runtime `Session.layer` over `BundleSource.value(bundle)` (or `.directory`/`.url`), `LuteRuntime` and an `InputLog`, then give `LutePlayer.make` the **same** `BundleSource` and a `KeyValueStore` (`Stores.memory` for tests/ephemeral, a persistent one — `BrowserKeyValueStore.layerLocalStorage` in browsers, the host's own on Bun/Node — for saves); (c) a table contrasting runtime `Contract.Snapshot` with player `SaveRuntime`, and the checkpoint/restore pattern (`handle.snapshot` → store → `handle.restore`; a fresh player starts from `save.snapshot` then restores the `SaveRuntime`). | The three issues are documentation gaps: the APIs are correct and typed, but the composition had to be read from published source. Keeping one text in three places matches how the repo already mirrors player docs. |
| The fresh-player restore pattern is pinned by a player test that runs the documented sequence (external session, memory store, snapshot, new player, restore). | It is the one recipe no test exercised; a doc that promises it should not be able to drift. |
| Stale prose found on the way is corrected (custom-hosts says saves are `"0.41"`; they follow the release line). | Docs must state the current format. |

### 2. Host writes that accompany an ending (#97)

| Decision | Why |
|---|---|
| **No contract change**: no new input, no writes on `ended`, no terminal input. The rule is documented: once the runtime answers `ended`, it accepts only `newRun` or an `outsideRun` raise, so a host write that belongs to the ending MUST ride as `writes` on the input that causes the terminal transition (`raiseOccasion`, `advanceClock`, `bridgeResult` or `hostWrite`). `choose`, `timeout` and `worldEvent` carry no writes; an ending they cause records its metadata in the story (a `::set` in the branch) or in a `hostWrite` sent before them. `newRun`'s writes seed the next run (where the ended run's values read as `prev.run.*`), never the ended one. | Owner instruction (conservative). The behaviour is consistent and already deterministic; the gap is that nothing says so. Spec review added `worldEvent` and the `newRun` distinction. |
| The refusal of a `hostWrite` at `ended` keeps `E-RUNTIME-BUSY` and its class, and its message names the rule: `the runtime has ended; only newRun or an outsideRun raise is accepted — a write that belongs to the ending rides as \`writes\` on the input that ends the run`. Other inputs at `ended` keep today's message. | The message is where the host meets the rule. The code is unchanged, so no consumer branches on anything new; messages are not pinned by the event contract (it documents codes). |
| Where documented: `docs/runtime/event-contract.md` (normative), website `tooling/runtime-contract.md` EN/KO, and player `custom-hosts.md` EN/KO (`send` at `ended`). | Each is where a host reads about `ended`. |

### 3. The staging-tag-dispatch note's open items

Reproduced on `5b223cde` (scratch projects under `/tmp/stage044`, not added to
the corpus): a core `::bg` scene versus a plugin `::place` with
`lower: { record: bg, fields: { location: { fromAttr: location } } }`.

| Finding at 0.43 | Evidence |
|---|---|
| `lower:`'s closed grammar **is already enforced** (since 0.24.0, `RawLowering` with `deny_unknown_fields` and explicit checks): an unknown key is `E-PLUGIN-KEY` naming the key; `kind: record`, a mix of the two shapes, an unregistered builtin hook, and `record` without `fields` are each `E-PLUGIN-PARSE` with a specific message. Covered by `crates/lute-manifest/src/schema/tests.rs` and `tests/loader.rs`. | Five CLI cases run against the scratch plugin. |
| Scene-change auto-hide still diverges: `::bg` injects the `stage-bookkeeping` exit for a character left on stage; the plugin `bg` record injects nothing, so the runtime stage keeps the character in the new scene. | Artifact diff of the two scenes. |
| Pose reset still diverges in the other direction: after a stateful line and a plugin scene change, a plain line gets an `auto-pose-reset` for a character `::bg` would have auto-hidden. | Provenance of the injected records. |
| `W-STAGE-ABSENT` no longer diverges: it fires for both forms (the note's 0.10 asymmetry is gone). | `check-project` on both projects. |

| Decision | Why |
|---|---|
| `lower:` grammar: nothing to implement; recorded as closed (0.24.0) with its tests. | Already enforced and tested. |
| Dispatch gap: **no behaviour change in 0.44**. Fixing it — treating any directive that lowers to a `bg` record as a scene change in the stage reducer — changes the compiled artifact (added exits, removed pose resets) of currently clean documents that use such plugins: a language-axis semantics change that needs its own spec delta (the note's §11.5 discussion). It is the first **0.45 candidate**, with the shape "the lowered record kind, not the source tag, drives the stage reducer" and the cost named above. 0.44 documents the current behaviour where plugin authors read about lowering (website `plugins/manifests.md` EN/KO): stage hygiene keys on the core `::bg` and `::clear`; a plugin directive lowered to `bg` changes the background only, so exit characters (or `::clear`) explicitly before a plugin scene change. | Owner instruction: conservative; a large contract change is documented and deferred. |
| The note's status becomes `Superseded`, with an addendum pointing here: its `lower:` item shipped in 0.24.0 and its dispatch item is carried by this note as a 0.45 candidate. | Its open work now lives here; leaving it `Draft` misreports it. |

### 4. TypeScript test spawns and telemetry

Found during the final gate: `packages/runtime/test/support.ts` and
`packages/player-web/scripts/demo.ts` spawn `lute` without
`LUTE_TELEMETRY=0`, so a local `bun run test` appended records to the
developer's telemetry file, against 0.43.0's statement that the repository's
tests, scripts and CI run with it off (CI was unaffected: it sets the
variable). **Decision:** fix it in 0.44 (two spawn sites set
`LUTE_TELEMETRY=0`), record it under CHANGELOG "Fixed". It is a defect in a
shipped statement, not new scope.
