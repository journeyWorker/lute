# Lute 0.50 — authoring extensibility: decisions

Decided by the orchestrator under the owner's delegation, 2026-10-25. The owner delegated every
design choice for 0.50. The orchestrator adopted every "recommended option" of the options
document [`docs/design/0.50-extensibility-options.md`](../../design/0.50-extensibility-options.md)
and took that document's defaults for its three "for you to confirm" items. While the normative
spec [`docs/proposals/scenario-dsl/0.50.0.md`](../../proposals/scenario-dsl/0.50.0.md) was written,
some details of the recommendations did not hold against the code at `f34f141f` (v0.49.0). The
decisions below record what the spec does instead, with the evidence. The release order is the
triage note's (owner, 2026-10-25): 0.49.1 is the Rust coding-rules sweep, and 0.50 is this release.

Implementation plan:
[`docs/superpowers/plans/2026-10-26-lute-0.50.0-extensibility.md`](../plans/2026-10-26-lute-0.50.0-extensibility.md).

One name may have two types on disjoint surfaces. ## Where the spec departs from the options document

Each item was found while specifying, against `f34f141f`.

1. **#169: reward-kind attributes cannot be pattern arguments.** The options document admits
   `@<attr>` from the kind's own `attrs:` (`@rarity`). A `<reward>` closes its attributes over
   `REWARD_ATTRS = id, kind, target, amount, when, outcome`
   (`crates/lute-check/src/logic_attrs.rs:72`, `check_reward_attrs` at `:418`). Checked with
   `@lute-lang/lute@0.49.0`: `<reward kind="BADGE" target="mira" rarity="rare"/>` on a kind
   declaring `attrs: [{ name: rarity, type: string }]` is `E-UNKNOWN-ATTR` ("`<reward>` has no
   attribute `rarity`"). No authored value can bind `@rarity`. **Instead:** a reward kind's fact
   effects read only `@target` and constants, and any other `@name` is `E-PLUGIN-PARSE` at load.
   That kind `attrs:` are declared but cannot be authored is a separate pre-existing gap. It is
   listed under "Out of scope" in the spec, not fixed here.
2. **#169: an unknown or ineligible `accepts` quest is `E-ACCEPT-TARGET`, not
   `E-CONN-UNKNOWN-NODE`.** `::accept`'s project check already reports all three faults (unknown
   id with did-you-mean, a quest with `start`, an auto-activating child) as `E-ACCEPT-TARGET`
   (`crates/lute-check/src/accept.rs:287-324`). One code per fault: a reward accept is judged by the
   same rule.
3. **#169: effect records name their grant with a `grant` object, not `effectOf`.** `effectOf` is
   a directive tag, and every renderer prints it as `(effect of ::<tag>)`
   (`crates/lute-cli/src/play/human.rs:251-255`; `lute-trace/src/report.rs:102-112`). A reward kind is
   not a directive. **Instead:** `{ "grant": { "quest", "instance", "index", "objective"?, "kind" } }`,
   which is the grant record's own identity, rendered `(effect of reward <KIND>)`.
4. **#164: no choice-await pass-through.** The options document passes `stamps` on the
   `awaitChoice` menu. `MenuAwait`/`MenuOptionAwait` carry only the address, verdicts and
   `once`/`exit` (`crates/lute-runtime/src/runtime.rs:297-320`). The player reads option `text`,
   `texts` and the prompt from the IR command at `menu.document`/`menu.position`
   (`packages/player/src/cues/index.ts:447-469`). `MenuAwait` is also part of the runtime
   `Snapshot` (`runtime.rs:337-343`, `deny_unknown_fields`), so adding a field would change the
   save shape. **Instead:** stamps stay in the IR, and the player's `ChoiceView` reads them from
   the same command it reads text from. The event and snapshot shapes do not change.
5. **#162: no IR `hostTokens` environment entry and no player substitution change.** The runtime
   keeps every reserved-token marker verbatim (`crates/lute-runtime/src/machine/format.rs:19-27`).
   `packages/player`, `packages/player-web` and `packages/runtime` contain no `userName` code
   (grep, 0 hits outside generated text), so there is no hard-coded table to generalize. The
   placeholder `{ kind: "reserved", token }` already names the token, and `capabilitySnapshot`
   pins the declaration. `celEnv` is the CEL environment (`schemas/lute-ir-0.49.schema.json`
   `$defs/celEnv`, `additionalProperties: false`), and a host token is never a CEL variable.
   The proposed "omitted when only `userName` is declared" rule was also asymmetric. **Instead:**
   no IR field. The core `userName` entry is excluded from the hash fold, so every artifact of a
   project that declares no token stays byte-identical.
6. **#163: duplicates reuse the existing duplicate codes; surface resolution gets its own code.**
   The options document adds `E-PLUGIN-STAMP-CONFLICT` for two entries with the same name on
   overlapping surfaces. That is the fault the existing duplicate codes already name: within a
   package `E-PLUGIN-DUP-ID` (`loader.rs:265`), across plugins `E-PLUGIN-DUP-ACROSS`
   (`assemble.rs:100`). **Instead:** overlap keeps those codes, with the surfaces named in the
   message. Directive tags of other plugins are known only at assembly, so an `on:` name that
   resolves to no surface cannot be a load error. It is the new assembly code
   `E-PLUGIN-STAMP-SURFACE`.
7. **#163: no LSP stamp completion.** The options document lists "`lute-lsp` completion
   (surface-filtered stamps)". The LSP has no stamp completion today (no `stamp_attrs` reader in
   `crates/lute-lsp/src`). Adding one would widen scope. The LSP gets every stamp diagnostic
   through `lute-check` unchanged.
8. **#166b: unknown-code validation uses the checker's code table.** `lute-manifest` cannot see the
   CLI registry. The check uses `lute_check::evidence::classification` (`evidence.rs:600`), which the
   registry test keeps in step. It runs from the CLI manifest pass and from the LSP, which both link
   `lute-check`. The lint glob matcher (`crates/lute-lint/src/glob.rs`) moves to
   `lute-manifest` so that both the project levels and lint `ignore:` use one matcher.

## Not developed

| Item | Reason |
|---|---|
| #166a line flag `stages: speaker`; frontmatter `staging: implicit` | D4: the `actor` record (core or plugin-lowered) composes, and under D13 the runtime needs that record anyway. It would be a second spelling of "show a character". Recipe and hint instead. |
| #170 A — core scene call with return | Components already compose the return case. A runtime presentation stack and cross-document effect summaries would add no expressiveness. |
| #170 B — core `::raise` executed by the runtime | D13 gives raising occasions to the host. |
| #159 — host-owned flow effect (`effects.flow`) | The host would own narrative flow (D13), and the runtime cannot resume at a label. |
| #163 B — `extends:` export | A second declaration site beside `stampAttrs`. |
| #163 C — per-tag `attrs:` for logic tags | It makes `<choice>` look co-owned (`lower:`/`effects:`/`bridge:` would need refusal) and leaves `required:` silently ignored. |
| #169 B — top-level `asserts:`/`retracts:`/`accepts:` keys on a kind | A second spelling of `effects.asserts`. |
| #169 C — compile-time desugaring into handler records | Records nobody authored, a fact decoupled from the host's grant, and no source for `fmt` or source maps. |
| #172 B — lints over the IR | It loses the LSP path and authored spans. |
| #172/#177 C — manifest type `enumBy: { attr, cases }` | Within one directive only, and a second predicate mechanism. It stays the extension point if `check`-time enforcement is ever needed. |
| #176 `map` / `record` attribute values | Each case has a better existing or planned route (options §9). |
