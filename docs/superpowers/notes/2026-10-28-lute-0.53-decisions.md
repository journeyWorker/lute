# Lute 0.53 — dogfood round 3: decisions

The owner decided the scope on 2026-10-28: all eight issues of dogfood round 3
(#224–#231, label `dogfood`) ship in 0.53.0, all as core work, and the
`lute lint` cost (#228) is the headline. The owner fixed the defaults listed
under each issue below. Where the evidence contradicted a default, this note
records the evidence and the change (section "Decisions changed from the
owner's defaults"). Everything else was decided by the orchestrator under the
owner's delegation, with the rule 0.52 applied: **conservative** — the smallest
surface, one spelling per concept, static analysis kept sound, refuse rather
than guess, and the runtime and the checker agree.

The normative contract is
[`docs/proposals/scenario-dsl/0.53.0.md`](../../proposals/scenario-dsl/0.53.0.md);
the implementation plan is
[`docs/superpowers/plans/2026-10-28-lute-0.53.0-dogfood-r3.md`](../plans/2026-10-28-lute-0.53.0-dogfood-r3.md).
Code facts are cited at `596d19c5` (v0.52.0, `main`). Every reproduction and
measurement was run on a debug build of `596d19c5` (`lute toolchain 0.52.0`,
`CARGO_PROFILE_DEV_DEBUG=line-tables-only`), on the owner's machine (10
cores), with `LUTE_TELEMETRY=0`.

Two more facts set the bounds of the new gate:

- The lint engine alone (no manifest, so no input assembly: 400 scene files
  copied to a directory without `lute.project.yaml`) costs 0.03 s CPU for 400
  documents with the default rules — about 0.1 ms per document.
- Assembling a document through a **shared** `InputCache` costs about
  0.13–0.20 ms (the `tag --check` row: `lute tag` already shares one cache,
  `rewrite.rs:205-208`).

private copy is alive at once (the RSS growth). On top of that
`project_for_root` (`lint.rs:203-236`) builds a full checked `ProjectModel`
(`build_single_root`, which runs `check` on every document and the project
passes) and keeps only `model.manifest()`. The document is also parsed twice

## Decisions changed from the owner's defaults

1. **#228: lint builds no `ProjectModel`.** The owner asked for "the same
   `ProjectModel`/memo `check` uses; one build per root". The data `check`
   shares across documents is the input layer underneath the model:
   `ProjectModel::build_impl` itself assembles every document through one
   `InputCache` (`project.rs:172-193`), and the model adds per-document
   **check results** (`check_parsed`, `fold_env`, reconcile). Lint reads
   none of them: `lute_lint::lint` takes `(path, doc, text)` and the display
   name pass reads the snapshot, imports, components and meta. Building the
   model would make lint cost at least a whole `check --project`, against
   #228's expected result ("a lint run with every rule off costs almost
   nothing beyond parsing"). So lint builds the input layer once per root
   (one `InputCache` per run), which is what is shared, and nothing else.
   One build per root holds.
2. **#227 (a): `accept="external"` with `start` stays refused.** The owner's
   default was to allow it as "the host may grant it once `start` holds",
   unless the reason for refusing it still holds. It does:
   - `start` is an activation **trigger**, not a gate. The runtime activates
     a quest when its `start` decides true, without any accept
     (`machine/quest.rs:256-273`, `:459-479`); `quest-lifecycle.md`
     §Activation: "A quest that carries a `start` predicate needs no accept".
     Reading `start` as a gate only when `accept="external"` is present gives
     one attribute two meanings.
   - The IR cannot carry the difference safely. An engine that implements
     0.52 auto-activates any quest with `start`; the gated reading would
     need a new semantic id (D5) and changes in the runtime lifecycle, the
     checker (`E-ACCEPT-TARGET`'s guarantee "an engine never sees an
     `accept` for a quest with a `start` predicate", `quest-lifecycle.md`),
     `E-TRACE-ACCEPT`, `lute play`'s accept rule and reachability.
   - D4: a new meaning needs composition to fail first, and it does not.
     `follows=` already states a quest's prerequisites for analysis and the
     host: probed on v0.52.0, `<quest id="letter" accept="external"
     follows="completed('intro')">` checks clean, `scenario reach --node
     quest:letter` is `Reachable` with `follows: completed("intro")`, and
     the artifact's `prereqEdges` carries `{"node":"letter","follows":
     "completed('intro')"}`, which the host reads. The same holds for a
     reward-accepted quest (`gated`, `follows="active('intro')"`).
   - What `follows=` cannot hold (a state read such as a level) is not
     visible to connectivity analysis in `start` either: only
     `visited(…)`, `entry.X.everRead` and `quest.Y.state == …` conjuncts
     anchor (`graph_assembly.rs:466-473`). So `follows=` keeps exactly the
     part analysis reads.

   The conservative spelling is `follows=`; no language change. The refusal
   messages (`E-ATTR-TYPE` on the pair, `E-QUEST-START-SELF`,
   `E-ACCEPT-TARGET` for an accepted quest with `start`) name it, and the
   docs give the recipe (#230).
3. **#231: no "no `::end` inside" condition.** The owner's rule allowed a
   loop across sections "when no `::end` and no entry other than the head
   lies inside". Probed on v0.52.0: a one-section loop with `::end` in one
   option (`loopend.lute`) checks clean; the region walks already end a
   path at `::end` (it contributes no back edge). A second condition for
   cross-section loops only would be a second rule for one construct. "No
   entry other than the head" is `E-JUMP-INTO-LOOP`, which already applies
   at any distance. So the rule is: the top-level sections are one loop
   scope; every existing rule applies unchanged.

## #231: what a section is at runtime (code evidence)

- The runtime never reads sections: `crates/lute-runtime/src` has no
  reference to `section` or `sections`. A scene runs as one range
  `0..len` (0.52.0 decision note item 2); `loop_table`
  (`machine/mod.rs:383-494`) validates loops over record indices only.
- `position` is build-local execution order, never identity, a save key or
  an entry (`execution-model.md` §Addressing). The `sections` table is
  descriptive; a section `id` "is identity metadata only and is never a jump
  target" (same page).
- A save resumes from a `Snapshot` (`runtime.rs:350-362`): the pending
  `Await`, the world and a continuation; nothing names a section. The player
  has no section reference (`packages/player/src`). `lute trace` uses the
  table only to print headings (`trace/driver_core.rs:16-31`).
- The checker already treats the top-level sections as one range for jumps
  (`BodyRange::TopLevel`, `next_labels.rs:283-293`): forward jumps between
  sections are legal.

The section bound in 0.51 (dsl 0.51.0 §3.2, "a beat or a section") has no
stated reason. It follows from how the flow walks were written: each walk
visits a section's body as its own node list (`fact_must.rs:775-777`) and
takes the loop region as `rest[..region_len(rest, head)]`
(`loop_walk.rs:204-208`, called at `defassign.rs:626`, `fact_must.rs:1057`,
`inject.rs:647`, `cast/presence/walk.rs:319`), so a region could not leave
the head's section. That is an implementation limit, not a meaning, and 0.53
lifts it.

## Where the spec departs from or extends the issues' suggestions

Each item takes the conservative option.

1. **#224: one predicate, three call sites.** Besides `fix.rs:403`, the
   checker reads the rename table at `directives.rs:384` (an omitted
   attribute's `default:` is judged only when the attribute is absent) and
   `:413` (a required attribute written under its old name). Both treat a
   stamp named `action` on `::cg` as the renamed `display`, so the declared
   `default:` of `display` is not judged when a stamp `action` is written.
   All three use `renamed_attr(tag, key, snapshot)`.
2. **#224: a document whose capability snapshot does not resolve** (a
   missing plugin, a bad manifest) gets no attribute rename: `lute fix`
   cannot know whether the key is a stamp. It says so on stderr
   ("kept … — the capability snapshot did not resolve; run `lute check`").
   Every other migration still runs.
3. **#224: the rule list.** The report names rules, not edits: `lute fix`
   prints, per changed file, the count per rule
   (`applied 3 fix(es): renamed-attr 3`); `--json` carries
   `rules: [{rule, fixes}]` and `kept: [{line, column, rule, reason}]` per
   file, under `schemaVersion` `0.53.0.fix`. A per-edit list would make the
   human output scale with the document; the rule names answer "which
   migration will run". No new flag: `--check` is the dry run (cli-grammar).
4. **#225: no scope for `node` rules.** `node` rules have no `scope` key
   (it is refused on every target but `pair`, 0.51.0 §6.1), and
   `node.preceding` resets per section by definition (0.50.0 §8.1).
   Widening `preceding` to the document would make a row's lookups cost
   O(document) where they cost O(section). The issue asks only for `pair`.
5. **#226: `map` too.** The walk recurses into `map` keys and values as
   well as `list` and `record`, because `collect_domain_names`
   (`project_check/domains.rs:128-145`) already does: what is counted as a
   read and what is checked come from the same walk.
6. **#227 (b): `accept="external"` is an anchor source, not "unanchored".**
   Dropping the accept anchor of an external quest would also drop its
   `[accept]` edge, which `impact` (#210) and envelopes (#209) read. The
   anchor keeps its edge and gains the host as an always-routable source.
7. **#227: accept edges that close a cycle stay undrawn.** The cycle path
   of `E-QUEST-START-CYCLE` is rendered from anchors (0.49.0 §6.1), so
   drawing such edges is not needed for the diagnostic, and it would change
   `lute scenario` output. Deadlocked quests are already printed on the
   "part of a start cycle" line instead of a layer.
8. **#227: the in-script accept deadlock is an error.** 0.49.0 §14 left
   accept deadlocks out because "the engine may accept a quest outside any
   `::accept`". dsl 0.25.0 §5 (D-C) settles who may: `accept="external"` is
   "the only non-content source". A non-external accept-driven quest whose
   accept sources all wait on it can therefore never start under the
   declared routes: the same verdict as a `start` cycle, with the same fix
   in the message (`accept="external"`).
9. **#229: one site.** The parser's #139 finder looks at the plain text
   before a marker; `{{{run.a}}` has none (the marker starts at the first
   `{{`). The checker's interpolation-grammar site (`interp_grammar_diag`,
   `check/interp.rs:210-265`) sees every marker of every grammar, so the
   rule lives there: an expression that begins with `{` is never a valid
   form, so only the code and message of an existing error change.
10. **#230: historical CHANGELOG entries stay.** 0.52.0 §11 does not rewrite
    historical records. The issue allows "one note in the docs that they
    link to"; the 0.53 CHANGELOG and `docs/versioning.md` link the new
    section, and `lute fix --help` names every migration.
11. **#231: one loop scope, the same as the range.** "Sections inside a
    beat, entry or quest" do not exist: `##` sections are a document's top
    level (`doc.sections`), and a heading in a quest or lore document is
    `E-GRAMMAR-NOT-ADMITTED` (probed on v0.52.0); beats, entries and quests
    are their own bodies and keep their loop rule. So the rule needs no
    document-kind test.
