# Lute `0.10.0` — design decisions

**Status:** decisions recorded, spec to follow.
**Theme:** *the toolchain says what it knows.*
**Source:** the Anseo drive test — [findings](../notes/2026-07-31-anseo-drive-test-findings.md) (111 entries) and [backlog](../notes/2026-07-31-lute-0.9.0-improvement-backlog.md) (38 issues).
**Scope call (release owner):** 0.10.0 takes the 24 `TOOL` and 2 `DOCS` issues. The 12 `DESIGN` issues — 4, 5, 7, 8, 9, 13, 14, 16, 19, 27, 28, 29 — are deferred, because each requires deciding what the language should *say* before anything can be built.

## Why this is a theme and not a backlog drain

Every release in this repo has stated one idea. `0.9.0` was *vocabulary ownership*. `0.8.0` was *the adoption release*, and it has the same shape as this one: a real assessment against real content, producing a list, producing a spec.

The unifying finding of the drive test was not a missing capability:

> The toolchain computes more than it will tell you, and occasionally tells you the opposite.

Every issue in scope is an instance. The checker holds the declared type and does not apply it to `::set` (#1). The parser holds the per-tag attribute table and does not close it (#6). The reachability pass proves a gate dead and reports it at two different severities depending on which construct it is on (#12, #13). The localization walk has the component's lines and drops their ids (#3). The test harness knows a selection is ineligible and passes anyway (#2). The producibility analysis exists and one branch of it is unwired (#12).

That is the release: **make every diagnostic the toolchain already had the information to emit.**

## Axes

`0.10.0` on all three, per [`docs/versioning.md`](../../versioning.md)'s alignment rule, which has no exceptions.

- **Language** — breaking, pre-1.0 allowance. Six issues change what a document is allowed to be.
- **Toolchain** — the bulk of the work.
- **IR** — moves for a real reason this time, not only alignment: issue #36 renames a field.

## Decisions

The scope call left nine sub-decisions open. Each is settled here so no task stalls on it.

### D-A · `#15` splits; only the rendering half ships

`--values` (report the reachable value set at a node) depends on a revisit policy, and revisit policy is deferred issue #7. Without it there is no answer to whether the reachable set is finite.

**Ship** the writer and fact rendering — the envelope reporting what the checker computed rather than what was declared. **Defer** `--values` to the release that takes #7.

*Rationale:* the issue's own Shape line says "a design decision". Shipping half is honest; shipping a `--values` whose meaning is undefined is not.

### D-B · `#2` splits; the soundness half ships

**Ship (a)** closed-key validation of `*.test.yaml` — an unknown key at any level is an error, and a test with zero expectations is an error. **Ship (d)** auto-pick reporting: when no supplied selection survives, say so rather than silently choosing the first eligible arm.

**Defer (b)(c)** — new expectation kinds for endings, quest lifecycle, and facts. The backlog makes those depend on #19's artifact-backed harness, which is deferred.

*Rationale:* (a) and (d) close the false green — a mis-keyed `choose:` currently passes while running the arm it excludes, and a test with no assertions reports PASS. That is a soundness hole in the tool a work's correctness is defended with. (b)(c) are new features and can wait.

### D-C · `#20` — `lute run` refuses an ineligible selection

Hard refusal, matching `lute trace`. No opt-in flag to replay the ineligible arm.

*Rationale:* the defect is that two tools disagree about the same question. A flag to keep the old behaviour re-creates the divergence under a different name. If replaying an impossible state is ever wanted, it is a separate, named capability with its own design.

### D-D · `#30` — `compile` aligns to `check`

`compile` validates nested manifests, as `check-project` already does. Not the reverse.

*Rationale:* `check` is the stricter side and the more useful one. A manifest the checker rejects must not compile silently. Relaxing `check` to match `compile` would delete a real gate to resolve a disagreement.

### D-E · `#31` — scaffold rot is an error, behind a checker pass

Stale scaffolded artifacts — a mock naming a deleted scene, a README naming a deleted file — are errors, surfaced by a checker pass that runs under `check-project`.

**This reddens `docs/examples/anseo/mocks/playthrough.yaml`, and that is correct.** That mock names `scenes/opening.lute`, deleted in the drive test's first task, and an undeclared `run.greeted`; it has been green for the entire exercise. Finding T1.9 exists precisely because nothing said so. Fixing the mock is one edit, and the corpus must not ship the defect the release is fixing.

*Rationale:* a warning here would leave the finding's own complaint intact — that the toolchain is quiet about rot it can see.

### D-F · `#34` is a language change and goes in the spec

`defaults:` in `lute.project.yaml`, supplying frontmatter every document would otherwise retype, is new manifest grammar with inheritance and override semantics. It changes which documents are accepted.

Keep it, spec it normatively. The named-scalar-predicate half stays out, as the issue itself says.

### D-G · `#12` — contradictory objectives are literal-vs-literal only

The dead-`start=` half is already concrete. For the contradictory-objective half, the supported domain is **scalar comparisons between a declared path and a literal, where two required objectives on the same path cannot both hold**. New code: `E-OBJECTIVE-CONTRADICTION`.

*Rationale:* that is exactly what the finding demonstrated. General range analysis over arbitrary CEL is a different feature with a different cost, and inventing it here would stall the release.

### D-H · `#26` — integer milliseconds, not epsilon

Timeline offsets and durations resolve to integer milliseconds internally. Authors keep writing seconds as decimals; the parser converts.

*Rationale:* epsilon comparison on floats is a bug factory and would replace one false positive with an unpredictable class of them. Milliseconds are authorable, exactly comparable, and the spec already speaks in fractions of a second. This also fixes the boundary hand-off (`0.8 + 0.4` then `1.2`) that the corpus currently works around.

### D-I · `#36` moves the IR axis on its own merit

`provenance.reason` is renamed so it no longer collides with `end.reason` in the same document. IR `0.10.0`, schema `schemas/lute-ir-0.10.schema.json`.

*Rationale:* alignment would have moved the number anyway, but this is a genuine artifact-shape change and the changelog must say so rather than repeating `0.9.0`'s "shape-identical" note.

### D-J · `#6` — attribute closure is a checker rule emitting `E-UNKNOWN-ATTR`

Raised mid-spec: there is no per-tag attribute validator to extend, and the one enforcement that exists is in the wrong layer under an overloaded code. `E-LOGIC-CONTENT` has four emission sites in `crates/lute-syntax/src/parser/blocks.rs`; three are body-shape rules about children (`:178`, `:309`, `:378`) and only `:425` is about attributes — `"<otherwise> takes no attributes"`.

The three attribute surfaces today use three models: content lines a fixed const (`content_line.rs:25`, closed, `E-UNKNOWN-ATTR`); directives the capability schema (`directives.rs:74`, open by design, because plugins contribute attrs); logic tags nothing.

**Decision.** Attribute closure for all six logic constructs is a **checker** rule with a fixed per-tag table, modelled on `content_line.rs` — logic tags are core grammar and, unlike directives, are not plugin-extensible. It emits **`E-UNKNOWN-ATTR`**, the code the other two surfaces already use, because #6's point is that the surface becomes uniform and a bespoke code would defeat it. `<otherwise>` moves into the table as the empty set and the parser's attribute arm is deleted; its three body-shape siblings stay in the parser, where they belong.

## Consequences to plan around

- **The corpus goes red before it goes green.** #31 reddens the Anseo mock by design; #1, #6, #12, #26 were checked against the corpus and redden nothing. Every red must be fixed by correcting the content, never by weakening the check.
- **The drive test is repeatable.** Anseo exists as an instrument. After 0.10.0, re-running its probes measures what the release actually bought — several backlog issues carry a `Verify` section that inverts directly into an acceptance check. That measurement is a release deliverable, not an afterthought.
- **`lute test` is now in CI** (both workflows, added at the end of the drive test), so a regression in the harness fixes is caught.
- **`W-INJECT-CONFLICT` disappears entirely** when #37 lands. Corrected during spec writing, twice over: it is **four** occurrences across `docs/examples`, not the two this document first claimed — `anseo/scenes/bridge.lute`, `anseo/scenes/spine-b.lute`, `bianca-s01ep02.lute`, and `idola-project/date-minigame.lute`; only the first two are documented as deliberate. And it is a **removal, not a narrowing** (spec decision D-U): auto-anchor-on-show is the code's only emission condition and it fires *only* when the explicit anchor equals the declared default, so "stop warning when they agree" deletes the rule. Anseo's README entries and their finding cross-references must be updated in the same change, and `0.9.0` Appendix A's widening row for this code becomes moot.

## Not in this release

The 12 deferred issues, and why they are not merely "later":

Six are `LANGUAGE-GAP`s — route history (#8), choice-driven routing (#7), negative conditions (#9), ending sets and polarity (#14), simultaneous speech (#29), and the IR track field (#27) that one of them needs. Two more are the component-semantics pair (#4 `{{string}}`, #5 no denotation). The rest are #13, #16, #19, #28.

These want a spec cycle of their own, the way `0.9.0` got one. Deciding six language questions at once under release pressure is how a language acquires six unrelated answers.
