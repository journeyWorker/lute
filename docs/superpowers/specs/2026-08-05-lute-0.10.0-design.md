# Lute `0.10.0` — design decisions

**Status:** decisions recorded, spec to follow.
**Theme:** *the toolchain says what it knows.*
**Source:** the Anseo drive test — [findings](../notes/2026-07-31-anseo-drive-test-findings.md) (111 entries) and [backlog](../notes/2026-07-31-lute-0.9.0-improvement-backlog.md) (38 issues).
**Scope call (release owner):** 0.10.0 takes the 24 `TOOL` and 2 `DOCS` issues. The 12 `DESIGN` issues — 4, 5, 7, 8, 9, 13, 14, 16, 19, 27, 28, 29 — are deferred, because each requires deciding what the language should *say* before anything can be built.

## Why this is a theme and not a backlog drain

Every release in this repo has stated one idea. `0.9.0` was *vocabulary ownership*. `0.8.0` was *the adoption release*, and it has the same shape as this one: a real assessment against real content, producing a list, producing a spec.

The unifying finding of the drive test was not a missing capability:

> The toolchain computes more than it will tell you, and occasionally tells you the opposite.

Every issue in scope is an instance. The checker holds the declared type and does not apply it to `::set` (#1). The parser holds the per-tag attribute table and does not close it (#6). The reachability pass proves a gate dead and reports it at two different severities depending on which construct it is on (#12, #13). The localization walk has the component's lines and drops their ids (#3). The test harness knows a selection is ineligible and passes anyway (#2). The producibility analysis exists and one branch of it is unwired (#12).

That is the release: **make every diagnostic the toolchain already had the information to emit.**

## Axes

`0.10.0` on all three, per [`docs/versioning.md`](../../versioning.md)'s alignment rule, which has no exceptions.

- **Language** — breaking, pre-1.0 allowance. Six issues change what a document is allowed to be.
- **Toolchain** — the bulk of the work.
- **IR** — moves for a real reason this time, not only alignment: issue #36 renames a field.

## Decisions

The scope call left nine sub-decisions open. Each is settled here so no task stalls on it.

### D-A · `#15` splits; only the rendering half ships

`--values` (report the reachable value set at a node) depends on a revisit policy, and revisit policy is deferred issue #7. Without it there is no answer to whether the reachable set is finite.

**Ship** the writer and fact rendering — the envelope reporting what the checker computed rather than what was declared. **Defer** `--values` to the release that takes #7.

*Rationale:* the issue's own Shape line says "a design decision". Shipping half is honest; shipping a `--values` whose meaning is undefined is not.

### D-B · `#2` splits; the soundness half ships

**Ship (a)** closed-key validation of `*.test.yaml` — an unknown key at any level is an error, and a test with zero expectations is an error. **Ship (d)** auto-pick reporting: when no supplied selection survives, say so rather than silently choosing the first eligible arm.

**Defer (b)(c)** — new expectation kinds for endings, quest lifecycle, and facts. The backlog makes those depend on #19's artifact-backed harness, which is deferred.

*Rationale:* (a) and (d) close the false green — a mis-keyed `choose:` currently passes while running the arm it excludes, and a test with no assertions reports PASS. That is a soundness hole in the tool a work's correctness is defended with. (b)(c) are new features and can wait.

### D-C · `#20` — `lute run` refuses an ineligible selection

Hard refusal, matching `lute trace`. No opt-in flag to replay the ineligible arm.

*Rationale:* the defect is that two tools disagree about the same question. A flag to keep the old behaviour re-creates the divergence under a different name. If replaying an impossible state is ever wanted, it is a separate, named capability with its own design.

### D-D · `#30` — `compile` aligns to `check`

`compile` validates nested manifests, as `check-project` already does. Not the reverse.

*Rationale:* `check` is the stricter side and the more useful one. A manifest the checker rejects must not compile silently. Relaxing `check` to match `compile` would delete a real gate to resolve a disagreement.

### D-E · `#31` — scaffold rot is an error, behind a checker pass

Stale scaffolded artifacts — a mock naming a deleted scene, a README naming a deleted file — are errors, surfaced by a checker pass that runs under `check-project`.

**This reddens `docs/examples/anseo/mocks/playthrough.yaml`, and that is correct.** That mock names `scenes/opening.lute`, deleted in the drive test's first task, and an undeclared `run.greeted`; it has been green for the entire exercise. Finding T1.9 exists precisely because nothing said so. Fixing the mock is one edit, and the corpus must not ship the defect the release is fixing.

*Rationale:* a warning here would leave the finding's own complaint intact — that the toolchain is quiet about rot it can see.

### D-F · `#34` is a language change and goes in the spec

`defaults:` in `lute.project.yaml`, supplying frontmatter every document would otherwise retype, is new manifest grammar with inheritance and override semantics. It changes which documents are accepted.

Keep it, spec it normatively. The named-scalar-predicate half stays out, as the issue itself says.

### D-G · `#12` — contradictory objectives are literal-vs-literal only

The dead-`start=` half is already concrete. For the contradictory-objective half, the supported domain is **scalar comparisons between a declared path and a literal, where two required objectives on the same path cannot both hold**. New code: `E-OBJECTIVE-CONTRADICTION`.

*Rationale:* that is exactly what the finding demonstrated. General range analysis over arbitrary CEL is a different feature with a different cost, and inventing it here would stall the release.

### D-H · `#26` — integer milliseconds, not epsilon

Timeline offsets and durations resolve to integer milliseconds internally. Authors keep writing seconds as decimals; the parser converts.

*Rationale:* epsilon comparison on floats is a bug factory and would replace one false positive with an unpredictable class of them. Milliseconds are authorable, exactly comparable, and the spec already speaks in fractions of a second. This also fixes the boundary hand-off (`0.8 + 0.4` then `1.2`) that the corpus currently works around.

### D-I · `#36` moves the IR axis on its own merit

`provenance.reason` is renamed so it no longer collides with `end.reason` in the same document. IR `0.10.0`, schema `schemas/lute-ir-0.10.schema.json`.

*Rationale:* alignment would have moved the number anyway, but this is a genuine artifact-shape change and the changelog must say so rather than repeating `0.9.0`'s "shape-identical" note.

### D-J · `#6` — attribute closure is a checker rule emitting `E-UNKNOWN-ATTR`

Raised mid-spec: there is no per-tag attribute validator to extend, and the one enforcement that exists is in the wrong layer under an overloaded code. `E-LOGIC-CONTENT` has four emission sites in `crates/lute-syntax/src/parser/blocks.rs`; three are body-shape rules about children (`:178`, `:309`, `:378`) and only `:425` is about attributes — `"<otherwise> takes no attributes"`.

The three attribute surfaces today use three models: content lines a fixed const (`content_line.rs:25`, closed, `E-UNKNOWN-ATTR`); directives the capability schema (`directives.rs:74`, open by design, because plugins contribute attrs); logic tags nothing.

**Decision.** Attribute closure for all six logic constructs is a **checker** rule with a fixed per-tag table, modelled on `content_line.rs` — logic tags are core grammar and, unlike directives, are not plugin-extensible. It emits **`E-UNKNOWN-ATTR`**, the code the other two surfaces already use, because #6's point is that the surface becomes uniform and a bespoke code would defeat it. `<otherwise>` moves into the table as the empty set and the parser's attribute arm is deleted; its three body-shape siblings stay in the parser, where they belong.

### D-Y · `#34` — a path resolves relative to the file that contains it

Raised by spec review: authored `uses:`/`extends:` resolve against the *document*'s parent (`main.rs:877-879`, `schema_import.rs:161-190,654-670`), so a manifest-supplied default had no specified base at all.

**Decision.** A `uses:`/`extends:` written in `lute.project.yaml`'s `defaults:` resolves against the **manifest**. One written in a document resolves against the **document**, unchanged.

*Rationale:* documents sit at varying depths — `scenes/`, `quests/`, nested roots — so a document-relative default is correct only while every consumer shares a depth, which is the exact fragility `#34` exists to remove; a default that breaks when a file moves into a subdirectory is worse than the boilerplate it replaces. An author reading `../vocabulary.schema.yaml` in the manifest cannot resolve it against a document that does not exist yet. And `pluginsDir`/`catalogDir` in that same file are already manifest-relative. The same key resolving against different bases by origin is stated plainly, not apologised for: it is a shorter rule than any alternative, and document-relative defaults have no defensible spelling.

**Three constraints recorded with it,** all measured against the code rather than assumed:

- `RawProject` carries no `deny_unknown_fields`, so `defaults:` is *silently ignored* by every pre-`0.10.0` binary. The upgrade experience is therefore silence followed by every document failing on the required key the block was hoisting — the spec must describe that, because it is what an author will actually hit.
- `ResolveDiag` has no span, so `E-DEFAULTS-KEY` anchors at the manifest and names the offending key in its message. Spanned YAML parsing is **not** in scope for one diagnostic; the limitation is documented, not engineered around.
- `defaultProfile`'s `unwrap_or` is two rules wearing one (an empty profile overrides; null collapses to the fallback), so `defaults:` states its own override rule directly per D-P — whole-value replacement per key, and a key present with an empty or null value is a *present* key that overrides. No inheritance of accidental semantics.

Also noted: the core frontmatter legal set is exactly 25 keys and the spec's table accounts for all of them, but `mode` is legal and **inert**. A defaultable key nothing reads is a trap; it is either excluded from the defaultable set or documented as inert at both sites.


### D-Z · `#34` — pre-resolve manifest paths at load; do not thread provenance

Spec review carried D-Y past "the spec is silent" to "the resolver cannot express it": after `defaults:` flattens into `Vec<String>`, `resolve_imports`/`resolve_components` receive exactly one `base_dir` — the document's parent — so there is no seam through which a manifest-relative path could survive.

**Decision.** `load_project` canonicalises every path inside `defaults:` against the manifest directory **at load time**. The resolvers keep their single `base_dir` and are not touched.

*Rationale:* the alternative — provenance-carrying refs — means a `Vec<(String, PathBuf)>` or a new type flowing through the whole import DAG and every call site in both the CLI and the LSP, the crate whose test suite exists precisely to catch those two diverging, to serve a case that only arises at depth 0. That is a permanent widening of a hot interface for a narrow need. Pre-resolution confines the change to the loader, and by the time a document inherits a default the base question is already answered and cannot be re-asked wrongly.

**Two constraints:**

- Canonicalisation is I/O and can fail. Precedent exists — `resolve_edges` already canonicalises and reports `E-USES-NOT-FOUND` — but a bad path in `defaults:` fails **once, at the manifest, naming the defaults key**, never once per inheriting document.
- **A canonical path is absolute and machine-specific and must never reach a serialised surface** — not the capability snapshot, not `capabilityVersion`, not a stamp, not a compiled artifact, not `lute context --json`. An absolute path in the stamp means two developers on one commit compute different versions and the drift guard fires on nothing. Pre-resolve for resolution only; anything that renders or hashes keeps the authored string.

  **Verified not currently live, and retained prophylactically.** `capability_version` takes only `&CapabilitySnapshot` and hashes plugin ids/versions/options plus assembled directives, enums, providers, state shapes, templates, asset kinds, bridges, defs, plugin frontmatter, events, stamp attrs and domains (`lute-manifest/src/snapshot.rs:135-273`). `ProjectConfig` is not `Serialize` and holds graph/dirs/identity only (`project.rs:26-50`); compile copies just `input.snapshot.version` into the artifact (`lute-compile/src/lib.rs:238-240`). No authored or canonical manifest path is hashed or rendered today. Profiles and plugins do affect the snapshot semantically, which is intended. The constraint stands anyway: adding resolved defaults to snapshot or context serialisation later is exactly how machine-specific drift would be introduced.

Also settled with it: the spec's entry-span promise is **removed**. Manifest-level spanless `ResolveDiag` naming the offending key is the achievable contract and is enough.


### D-AA · `#37` — the information is dropped, and the spec says so

Spec review found §12.3's mitigation describes a surface that does not exist. `injected: false` appears nowhere in the codebase; every `Provenance` construction is `injected: true`. The doc comment at `inject.rs:107-108` — *"`injected == false` marks a command the author wrote that a rule would have injected"* — is **design intent that was never implemented**.

I checked whether to build it instead, and it is not the small change it looks like. `inject_cmd` (`lute-compile/src/stage.rs:224`) turns **every** `InjectedCommand` into a separate `sprite` record in the artifact. Emitting an `injected: false` record from the conflict arm would put a spurious anchor command in the compiled output beside the author's own — an IR consequence D-I does not sanction, requiring the compile layer to filter on a field no consumer reads today.

**Decision.** Delete the bullet. `W-INJECT-CONFLICT` is removed and the information it carried is **dropped**, stated plainly. The removal is still right — a code whose only trigger is agreement with the default is what this release exists to stop shipping — but it is a straight loss, not a migration to another surface, and a spec that claims otherwise sends the next reader looking for something they will not find.

Two follow-ons: Appendix B records that `Provenance.injected` becomes **constant-`true`** in the IR (field retained; removing it is an IR break for a future cycle), and `inject.rs:107-108`'s doc comment is corrected in the same change, because it is what misled the spec author.

### D-AB · `#31` — mock diagnostics anchor at the mock, not at the offending key

§8 required every mock diagnostic to anchor at the offending key's own line and column. Review found three layers in the way: `parse_mock_yaml` deserializes into `serde_yaml::Value`, which retains no positions (`mock.rs:166`); every mock entry carries a hardcoded all-zeros `synthetic_span()` (`mock.rs:71-79`); and `Diagnostic` has **no file field** at all (`lute-core-span/src/lib.rs:113-141`), so fixing the first two yields a correct position in the wrong file. `facts`/`choose`/`events`/`accepts` have no span slot to fill either.

**Decision.** Retreat exactly as D-Z retreated. The diagnostic anchors at the mock file and **names the offending key in its message**; spanned YAML parsing is not in scope, and the limitation is documented rather than engineered around. This spec already made that call one section earlier for `E-DEFAULTS-KEY`; making the opposite call here for five codes, budgeting nothing, was the inconsistency.

### D-AC · `#31` — the subject key is `file:`, it is REQUIRED, and it is mock-relative

Review argued against D-R and won. The subject concept already exists in the same parser under a different name: `*.test.yaml` goes through the same `parse_mock_yaml` and carries a **required** `file:` (`testcmd.rs:161-169`), used by all 34 corpus tests. Because the grammar is open, `file:` is already legal in a `mocks/*.yaml` and does nothing. D-R's `for:` would have been a second spelling of one concept, in one format family, read by one function — **with a different base directory** (`for:` project-root-relative, `file:` test-file-relative). That is the divergence D-D exists to close, being created deliberately one section later.

**Decision.** The key is **`file:`**, resolved **relative to the mock that contains it** — identical to `*.test.yaml` and to D-Y's rule for documents. It is **required**, which also disposes of the third Critical: review found the no-subject branch was specified against machinery that does not exist (`validate` is document-scoped by signature, `mock.rs:712`; there is no union `FoldedEnv`), and that this unimplementable branch was carrying the release's headline red. A mock with no `file:` is `E-MOCK-SUBJECT`. The author adds it, the schema becomes knowable, and `run.greeted` is then caught as undeclared. Two reds, both real, no union machinery.

`lute trace <doc> --mock m.yaml` supplies the subject on the command line and that wins; a `file:` that disagrees with it is the error. One key, one meaning, one base rule.

### D-AD · `#18` — `W-EXIT-INERT` keeps its discharge path in the spec text

Review's sharpest structural objection: §12.3 removes a warning for having no expressible remedy while §11.2 adds one with the same property, in the same document, and the spec does not notice. `W-EXIT-INERT` fires on a content-line `action=` whose value is in the resolved domain's `exits:`, and a writer who wants that value as a genuine pose has no `--allow`, no in-source acknowledgement, and `--deny-warnings` in CI.

**Decision.** The warning stands — if a project declares `go-under` an exit, `go-under` **means** exit there, and a pose sharing that name is ambiguous by construction. But the discharge must be **stated, not implied**: write the two-event form, or stop declaring that member an exit. §11.2 must say this in as many words, and the message must name the remedy. A warning whose remedy exists but is undocumented is `W-UNPROVEN-RELATIONAL` again by a different route.


### D-AE · `#36` — the renamed field is `Provenance.explanation`

Found while writing the implementation plan: **D-I** and Appendix B both say `provenance.reason` is renamed and neither says *to what*. A plan cannot carry that; the first implementer would have picked a name and every golden in the repo would have been written against a guess.

**Decision.** `Provenance.reason` → **`Provenance.explanation`**, in the Rust struct, the serialized key, and every golden together.

The name follows from what #36 is actually about. The collision is not cosmetic: `end.reason` is an **opaque author token a host dispatches on**, and this field is **human-readable English the compiler wrote**. Two contracts with nothing in common under one key. `explanation` cannot be read as a dispatch key, and it sits correctly beside its sibling: `{ injected: true, by: "auto-pose-reset", explanation: "…" }`. `why` is too terse for an IR field and `rationale` invites the same "is this a token?" question the rename exists to end.


## Consequences to plan around

- **The corpus goes red before it goes green.** #31 reddens the Anseo mock by design; #1, #6, #12, #26 were checked against the corpus and redden nothing. Every red must be fixed by correcting the content, never by weakening the check.
- **The drive test is repeatable.** Anseo exists as an instrument. After 0.10.0, re-running its probes measures what the release actually bought — several backlog issues carry a `Verify` section that inverts directly into an acceptance check. That measurement is a release deliverable, not an afterthought.
- **`lute test` is now in CI** (both workflows, added at the end of the drive test), so a regression in the harness fixes is caught.
- **`W-INJECT-CONFLICT` disappears entirely** when #37 lands. Corrected during spec writing, twice over: it is **four** occurrences across `docs/examples`, not the two this document first claimed — `anseo/scenes/bridge.lute`, `anseo/scenes/spine-b.lute`, `bianca-s01ep02.lute`, and `idola-project/date-minigame.lute`; only the first two are documented as deliberate. And it is a **removal, not a narrowing** (spec decision D-U): auto-anchor-on-show is the code's only emission condition and it fires *only* when the explicit anchor equals the declared default, so "stop warning when they agree" deletes the rule. Anseo's README entries and their finding cross-references must be updated in the same change, and `0.9.0` Appendix A's widening row for this code becomes moot.

## Not in this release

The 12 deferred issues, and why they are not merely "later":

Six are `LANGUAGE-GAP`s — route history (#8), choice-driven routing (#7), negative conditions (#9), ending sets and polarity (#14), simultaneous speech (#29), and the IR track field (#27) that one of them needs. Two more are the component-semantics pair (#4 `{{string}}`, #5 no denotation). The rest are #13, #16, #19, #28.

These want a spec cycle of their own, the way `0.9.0` got one. Deciding six language questions at once under release pressure is how a language acquires six unrelated answers.
