# Lute 0.10.0 — Foundation (IR delta) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land the `0.10.0` IR delta — rename `Provenance.reason` to `Provenance.explanation`, advance `LUTE_IR_VERSION`, and publish `schemas/lute-ir-0.10.schema.json` — before any other `0.10.0` work, so every later task records its goldens against the final artifact shape exactly once.

**Architecture:** One field rename that crosses three crates and every artifact golden in the repo, plus the version constant and schema file that must move with it. Nothing here changes behaviour: no diagnostic is added, no document changes meaning. It is pure shape, sequenced first because it is the only `0.10.0` change that touches goldens every other task also writes.

**Tech Stack:** Rust workspace (`lute-check`, `lute-compile`, `lute-cli`), `insta` snapshot tests, JSON Schema draft 2020-12.

## Global Constraints

These apply to **every** `0.10.0` plan, not only this one.

- **Language version** `0.10.0`; **IR version** `0.10.0`; toolchain version `0.10.0`. `docs/versioning.md`'s alignment rule has no exceptions.
- **`LUTE_LANG_VERSION` is NOT bumped in this plan.** It moves in the Release phase together with the corpus restamp, because bumping it fires the pre-existing `W-LUTE-VERSION-STALE` on every `luteVersion: "0.9.0"` document in `docs/examples`. That is a different golden surface from this one and is not a prerequisite for anything.
- **Every new diagnostic code MUST be added to `DENIABLE_CODES`** (`crates/lute-cli/src/main.rs:505-558`, a hand-maintained **sorted** const, 177 entries today) **in the same task that first emits it**. Anything outside the list is a clap usage error, exit 2. The guard is `every_check_emitted_code_is_deniable`, a `#[cfg(test)]` unit test **inside `crates/lute-cli/src/main.rs` (`:3997`)** — *not* in `crates/lute-cli/tests/deny.rs`, which exists and contains no such test. `main.rs:500`'s own doc comment misdirects to `tests/deny.rs` and has already misled two independent readers; the task that widens the guard's scan set fixes that comment too.
- **No new crates.** Every `0.10.0` change lands in an existing one.
- The normative spec is `docs/proposals/scenario-dsl/0.10.0.md`. The owner's binding decisions are `docs/superpowers/specs/2026-08-05-lute-0.10.0-design.md` (**D-A**…**D-J**, **D-Y**…**D-AE**). Where they differ, the design record wins and the spec is wrong — report it rather than following it.
- Never weaken a check to make a corpus file green. Every red in `docs/examples` is fixed by correcting the content, per §13.

### Task 1: Rename `Provenance.reason` to `Provenance.explanation`

Backlog **#36**, spec Appendix B, decision **D-I** with the name settled by **D-AE**.

The collision this closes is not cosmetic. `grep -n '"reason"'` on a compiled `bridge.lute` returns two hits with nothing in common: `end.reason` is an **opaque author token a host dispatches on**, and `provenance.reason` is **human-readable English the compiler wrote**. `explanation` cannot be read as a dispatch key.

**Files:**
- Modify: `crates/lute-check/src/inject.rs` (the `Provenance` struct at `:109-117`, its doc comment at `:105-108`, and the four construction sites at `:248`, `:300`, `:324`, `:352`)
- Modify: every construction and assertion site the rename reaches — find them, do not assume this list is complete
- Test: `crates/lute-compile/tests/ir_golden.rs`, `crates/lute-compile/tests/inject.rs`, `crates/lute-check/tests/snapshots/golden__branch_ok_resolved.snap`

**Interfaces:**
- Produces: `lute_check::Provenance { pub injected: bool, pub by: String, pub explanation: String }`, re-exported at the `lute_check` root and consumed by `lute_compile::stage::inject_cmd`. **Every later `0.10.0` task that writes an artifact golden depends on this name.** There is no `reason` field on `Provenance` after this task.

- [ ] **Step 4: Rename the field and correct the doc comment**

The `injected` comment is corrected in the same edit because it is **unimplemented intent** — it describes a `false` case that no code has ever constructed, and it is what misled the `0.10.0` spec author into claiming a surface that does not exist (**D-AA**):

```rust
/// Provenance stamp on every injected command (arch doc §5): *which* named rule
/// inserted it and *why*. Surfaced in the resolved/injection view so injection
/// is visible, not silent magic.
#[derive(Clone, Debug, PartialEq, Eq, serde::Serialize)]
pub struct Provenance {
    /// Always `true`. The field is retained for IR compatibility, but with
    /// `W-INJECT-CONFLICT` removed in 0.10.0 (§12.3, D-AA) nothing constructs a
    /// `false`, and a consumer MUST NOT read a `true` as distinguishing
    /// anything. Removing it is an IR break, deferred to a future cycle.
    pub injected: bool,
    /// The named rule responsible (e.g. `"auto-anchor-on-show"`).
    pub by: String,
    /// Human-readable justification, surfaced in the LSP injection view.
    /// Named `explanation`, not `reason`: `end.reason` is an opaque author
    /// token a host dispatches on, and these two share no contract (#36, D-AE).
    pub explanation: String,
}
```
