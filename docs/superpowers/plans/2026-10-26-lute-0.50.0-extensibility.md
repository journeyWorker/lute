## Working rules

- **One Rust owner at a time**, in the main checkout, in the order below. TS and
  docs slices run in worktrees, and the orchestrator merges them.
- **Coding rules.** Every Rust slice reads `docs/design/rust-coding-rules.md`
  first. New types (`StampSurface`, `StampAttrs`, `HostTokenDecl`,
  `RewardEffects`, `GrantEffect`, `DiagnosticLevels`, `SeverityPolicy`) are
  newtypes or enums, not strings. Error types are typed, and no `unwrap()` is
  added outside tests. No `pub(super)`. A module with children is `foo/mod.rs`.
  There is no HIR/Fold: §5.4's analyses read a table and do not synthesize
  nodes.
- **Reviewer pass per slice**, against its spec sections, before the next
  dependent slice starts. The reviewer reads the whole diff and the slice's
  delta list. Findings are fixed first.
- **Regression test per change**, failing on the base (`$SNAP/lute-0.49.1`, or
  the change reverted). The slice records how it showed the failure.
- **Snapshot compare after every slice:**
  `python3 scripts/cli-snapshot.py target/debug/lute "$SNAP/<slice>" --compare "$SNAP/base" --strict`.
  Every changed, added or removed output is listed in `$SNAP/<slice>/deltas.txt`
  with its spec §14 class. An unclassified delta is a defect in that slice.
- `cargo fmt --all` before each Rust commit. **`cargo clean` only by the
  orchestrator, between slices.** **Never** `--release`, `cargo doc` or
  `include!`. No `#[allow]` (use `#[expect(…, reason)]`), no new `catch_unwind`,
  no `unsafe`.
- Never hand-edit generated output. Bless registry pages with
  `LUTE_BLESS_DIAGNOSTICS=1` and review the diff. Regenerate contracts with
  `lute-contract-schema` and `bun run contract:gen`.
- Historical records are never rewritten.
- **Out-of-scope bugs:** `gh issue create --label bug` with evidence,
  immediately, plus a line in the log. Do not fix them here. Known one: spec §15
  (reward kind `attrs:` cannot be authored). S3 files it.
- **Commit per slice** (`feat(0.50): <slice> - …`; `docs(0.50):`,
  `test(0.50):`) and per milestone. Log after each. The tree is clean at
  handoff.
- **Budget rule.** If a slice cannot reach a green RG in its session:
  - commit the work as one WIP commit on `feat/0.50-<slice>-wip`, and leave
    `feat/0.50` unchanged;
  - log what is done, what fails (exact errors) and the next step.

  The next session resumes from the WIP branch. Never land a red slice on
  `feat/0.50`.

## Order and rationale

```text
bootstrap ─ S1 ─ S2 ─ S3 ─ S4 ─ S5 ─ S6 ─ S7 ─ S8 ─┬─ merge ─ K ─ snapshot classification ─ Z ─ final gate ─ release
                 S2t (player ChoiceView, after S2) ─┤
     D1 (docs from spec; example + transcripts after S8) ┘
```

- **S1 first.** It changes the type of `CapabilitySnapshot.stamp_attrs`, which
  every later slice compiles against, and it owns the assembly rules that S2's
  logic-tag surfaces need.
- **S3 before S4.** S4's IR and runtime fields carry what S3's manifest and
  checker resolve.
- **S5, S6 and S7 are independent.** They run in this order because of the one
  Rust owner. S7 lands after S2 so that node rows see element stamps in
  tests.
- **S8 is last of Rust**, because it changes the corpus-visible
  `W-STAGE-ABSENT` text. D1's transcripts are then rerun once on the final
  binary.

### S1 detail

1. `stamps.rs`: `StampSurface` (with `parse(&str, &CapabilitySnapshot) -> Result<StampSurface, SurfaceError>`
   and `Display`), `StampAttrDecl`, `StampAttrs` with the §3.3 API. Its
   `Debug`/hash helper prints the 0.49 form for unscoped entries.
2. Loader: parse the entry (its own struct, because serde cannot combine
   `flatten` with `deny_unknown_fields`). Load faults (§3.2 table). Overlap
   within the package.
3. Assembly: resolve surfaces, shadowing, then overlap across plugins. Each
   refusal drops the entry, and its siblings land.
4. Migrate every `stamp_attrs` reader (spec §3.4 and §3.7 lists). The compiler
   tells you about each one.
5. Checker: resolution order, the `E-UNKNOWN-ATTR` scoped message, `required`
   on lines and directives (logic tags in S2).
6. Tests: §3.8 items 1–3 and 5, the hash-stability test, the exhaustive core-directive
   classification (every core directive not in `UNSTAMPED_DIRECTIVES` is a
   valid `on:` surface, and every one in it draws `E-PLUGIN-STAMP-SURFACE`).
