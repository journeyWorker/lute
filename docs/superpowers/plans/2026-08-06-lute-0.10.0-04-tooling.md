# Lute 0.10.0 — Tooling, Harness & Docs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Land every `0.10.0` item the language spec deliberately excludes — eleven of §2.3's thirteen `TOOL` issues plus the two `DOCS` issues — as twelve independent, individually-committable tasks that make the toolchain say what it already knows.

**Architecture:** Nothing here changes what a document is allowed to be. Every task is CLI behaviour, diagnostic plumbing, harness soundness, report rendering, or prose. That independence is the useful property: no task in this plan consumes a symbol produced by another, and none consumes anything from plans 01, 02 or 03. The order below is therefore chosen by **cost** and by **shared file** — see *Why this order* — so a reviewer gates the cheap self-contained diagnostics first and the three tasks that all rewrite `crates/lute-cli/src/testcmd.rs` land in sequence rather than in parallel conflict.

**Tech Stack:** Rust workspace (`lute-check`, `lute-trace`, `lute-compile`, `lute-cli`), `serde_yaml`/`serde_json`, `insta` snapshot tests, Astro/Starlight docs under `packages/website`, `scripts/check-doc-snippets.py` as the docs gate.

## Global Constraints

These apply to **every** `0.10.0` plan, not only this one.

- **Language version** `0.10.0`; **IR version** `0.10.0`; toolchain version `0.10.0`. `docs/versioning.md`'s alignment rule has no exceptions.
- **`LUTE_LANG_VERSION` is NOT bumped by any task in these plans.** It moves in the Release phase with the corpus restamp, because bumping it fires the pre-existing `W-LUTE-VERSION-STALE` on every `luteVersion: "0.9.0"` document in `docs/examples`.
- **Every new diagnostic code MUST be added to `DENIABLE_CODES`** (`crates/lute-cli/src/main.rs:505-558`, a hand-maintained **sorted** const, 177 entries today) **in the same task that first emits it**. Anything outside the list is a clap usage error, exit 2. The guard is `every_check_emitted_code_is_deniable`, a `#[cfg(test)]` unit test **inside `crates/lute-cli/src/main.rs` (`:3997`)** — *not* in `crates/lute-cli/tests/deny.rs`, which exists and contains no such test.
- **No new crates.**
- Never weaken a check to make a corpus file green. Every red in `docs/examples` is fixed by correcting the content, per spec §13.

/// One `E-TEST-KEY` line for an unrecognised key, with the same
/// edit-distance did-you-mean four checker codes already use (dsl 0.5.0
/// §2.2). `where_` names the level so a top-level typo and an `expect:`-level
/// typo are distinguishable.
fn unknown_key_line(where_: &str, key: &str, allowed: &[&str]) -> String {
    let sugg = allowed
        .iter()
        .map(|k| (*k, levenshtein(key, k)))
        .filter(|&(_, d)| d > 0 && d <= 2)
        .min_by_key(|&(_, d)| d)
        .map(|(k, _)| format!(" — did you mean `{k}`?"))
        .unwrap_or_default();
    format!(
        "error [E-TEST-KEY] unknown {where_} key `{key}` in a `*.test.yaml`{sugg} (legal: {})",
        allowed.join(", ")
    )
}

/// Edit distance, local to this crate. `lute-check`'s `cel_paths::levenshtein`
/// is `pub(crate)` to THAT crate and is not reachable here; duplicating eight
/// lines is cheaper and safer than widening a checker internal for a CLI
/// message.
fn levenshtein(a: &str, b: &str) -> usize {
    let b_chars: Vec<char> = b.chars().collect();
    let mut prev: Vec<usize> = (0..=b_chars.len()).collect();
    let mut cur = vec![0usize; b_chars.len() + 1];
    for (i, ca) in a.chars().enumerate() {
        cur[0] = i + 1;
        for (j, &cb) in b_chars.iter().enumerate() {
            let cost = usize::from(ca != cb);
            cur[j + 1] = (prev[j] + cost).min(prev[j + 1] + 1).min(cur[j] + 1);
        }
        std::mem::swap(&mut prev, &mut cur);
    }
    prev[b_chars.len()]
}

/// `kind:`, no frontmatter envelope, no body. The whole file IS the
/// frontmatter, wrapped in a synthetic `Meta` and fed through
/// `MetaKind::Schema` — byte-for-byte the lift `schema_import::read_and_parse`
/// performs on the same file kind when it is reached through `uses:`, so the
/// two surfaces cannot disagree about whether a schema is valid (#21, T3.9).
fn run_check_schema_yaml(file: &Path, policy: &DenyPolicy) -> ExitCode {
    let text = match std::fs::read_to_string(file) {
        Ok(t) => t,
        Err(e) => {

        raw_yaml: text,

        ExitCode::from(1)
    } else {

        ExitCode::SUCCESS
    }
}
