**How it was measured.** The lints are passed on the command line, so no
file is edited. `CLIPPY_CONF_DIR` points at a scratch `clippy.toml` that holds

### What in the note is outdated after 0.49

These findings now live in the note itself, under "Amendments (2026-10-25)".
In short:

1. Lints are enabled per slice, and only once they are at zero.
2. `allow` → `expect` is done by hand.
3. A cast whose value comes from input keeps `as` and gets an
   `#[expect(…, reason)]`.
4. The explicit list of 31 `Result<_, String>` functions above replaces the
   note's counts.
5. `CliError` and `ExpectError` are in scope.
6. 0.49 missed the rules in two places: the `IncludeError` gap, and the
   `redundant_imports` growth (re-measured after S1).
7. `clippy.toml` and `check-visibility.py` join the CI trigger paths.

One more point is not a rules change. The workspace's `rust-version = "1.85"`
is not the lint toolchain: the lints are checked on 1.96.1 only. The other CI
jobs use `stable` without `-D warnings`, so a lint that a later stable
renames only warns there.

## Working rules

- **One Rust owner at a time**, in the main checkout, in the order below.
  Every slice touches many crates, so slices run strictly one after
  another. The plan has no parallel worktree slices.
- **Behaviour-preserving.** Spec §3 lists the rules. The proof is **0
  snapshot deltas** after every slice. A delta is a defect in that slice; it
  is never classified or accepted.
- **Lints are enabled per slice**, and only once their count is zero (note
  amendment 1, spec A.4). A slice adds its lints to `[workspace.lints]` in
  the same commit that brings them to zero. At no point is a lint listed
  with a nonzero count.
- **Measurement never shares a build with implementation** (review F1).
  Counts come only from `bash "$SNAP/count/measure.sh" <label>`, which sets
  `CARGO_TARGET_DIR` and `CLIPPY_CONF_DIR` per command. Everything else
  (`cargo clippy --fix`, hand fixes, RG) runs with neither variable set, so
  it builds into `target/` and, from S2b, reads the repository
  `clippy.toml`.
- **Reviewer pass per slice**, against spec §3 and note §1–§5, before the next
  slice starts. The reviewer reads the whole diff. A reviewer of a
  `cargo clippy --fix` commit checks that it contains only machine output:
  rerun the same command on the parent and compare.
- **Each slice is its own commit** (`refactor(0.49.1): <slice> - …`;
  `ci(0.49.1):` or `test(0.49.1):` for workflow-only or tooling-only changes),
  and on its own it passes the full RG with 0
  snapshot deltas. A slice MAY be several commits if each one passes RG.
- **Formatting-only commits go into `.git-blame-ignore-revs`**: rustfmt-only
  commits, and the machine-only `cargo clippy --fix` + `cargo fmt` commit of
  S1, which carries no hand edit. Z appends their SHAs with a one-line
  comment each, as the 0.42.1 entry does. The SHAs survive because the PR is
  merged with a merge commit.
- `cargo fmt --all` before each Rust commit. **`cargo clean` only by the
  orchestrator, between slices.** **Never** `--release`, `cargo doc` or
  `include!`.
- No `#[allow]` (use `#[expect(lint, reason = "…")]`), no new
  `catch_unwind`, no `unsafe`.
- Never hand-edit generated output. Registry text does not change in 0.49.1,
  so `LUTE_BLESS_DIAGNOSTICS` is never needed. If the `codes` test asks for
  it, that is a defect.
- Out-of-scope bugs found while sweeping: `gh issue create --label bug` with
  evidence, immediately, plus a line in the log. **Do not fix them here**:
  a fix is a behaviour change.
- **Commit per slice and per milestone; log after each.** The tree is clean
  at handoff.
- **Budget rule.** If a slice cannot reach a green RG in its session:
  - commit the work as one WIP commit on `feat/0.49.1-<slice>-wip`, and
    leave `feat/0.49.1` unchanged;
  - log what is done, what fails (exact errors) and the next step.

  The next session resumes from the WIP branch. Never land a red slice on
  `feat/0.49.1`.

## Order and rationale

```text
bootstrap ─ S1 ─ S2a ─ S2b ─ S2c ─ S3 ─ S4 ─ S5a ─ S5b ─ S5c ─ Z ─ final gate ─ release
```

- **S1 goes first.** It does two things:
  - Its first commit is the strict snapshot compare (review F2), so every
    later slice is proven with it and the proof covers the command set.
  - Its autofix changes the `redundant_imports` set, so every later count is
    taken after it.
- **The lint slices (S2) come before the moves (S3) and the visibility
  rewrite (S4)**, so the per-site anchors in the tables stay valid while
  those slices work.
- **S4 comes before S5**, because typed errors may need types that S4 makes
  `pub(crate)`.
- **Z comes last.** Until Z the binary still reads `0.49.0`. After Z it
  reads `0.49.1`, which the existing normalizer (`0\.(?:48|49)(?:\.\d+)?`)
  already maps, so `cli-snapshot.py` needs no normalizer change.
