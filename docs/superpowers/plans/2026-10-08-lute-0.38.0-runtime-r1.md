# Lute 0.38.0 — runtime R1: implementation plan

- **Spec:** `docs/proposals/scenario-dsl/0.38.0.md`
- **Direction:** ADR D13; brief `docs/design/runtime-player.md` (owner answers 2026-10-08)
- **Base:** branch `feat/0.38`, release 0.37.0 (`681f06f6`) + brief commit `7da78c1f`
- **Cutover:** no re-exports, aliases or compatibility paths for moved symbols; `Session`, `Driver::choose/bridge/forced` and the executor's CEL parse path are gone at the end
- **Scope:** `lute-trace` → `lute-runtime` split, `expr` evaluator, resumable walk and step API, bundle loading, snapshot, `lute play --events`, session conformance, schemas, docs, version stamps

All Rust slices are strictly sequential: S0 → S1 → S2 → S3 → S4a → S4b → S5 →
S6 → S7. One owner edits Rust at a time. A slice owns every downstream caller
its change breaks (`lute-trace`, `lute-runtime`, `lute-cli`, `lute-bench`,
`lute-wasm`, `lute-check`, `lute-compile`, tests); no slice starts on a broken
workspace. Each slice ends with a reviewer pass before the next starts.

## Acceptance every Rust slice runs before yielding

```sh
RUSTFLAGS="-D warnings" cargo check --workspace --all-targets
cargo nextest run --workspace
cargo build -q -p lute-cli && /tmp/lute-baseline/compare.sh
```

`compare.sh` captures every surface of spec §10.4 (all
`docs/examples/**/*.play.yaml` in human and `--json`; `lute test`, `lute
beats`, `lute calendar` per game and for `docs/examples`; `lute trace` human
and `--json` for every game scene/quest and standalone example; `lute run`
human and `--json` over every conformance replay fixture) with the head
binary and diffs it against the v0.37.0 baseline captured in G0, with
`0.38.0` normalized to `0.37.0`. It MUST print `byte-identical`.
`cargo test -p lute-cli --test conformance` (in nextest) additionally pins
`expected.json`.

No `include!` stitching, `--release` builds or `cargo doc` in slices.
Workers never run `cargo clean`; the orchestrator does, between slices.

## G0 — baseline (orchestrator, done)

`/tmp/lute-baseline/lute` is the v0.37.0 binary; `/tmp/lute-baseline/out`
its captured outputs, recorded by `capture.sh` inside a `v0.37.0` worktree
(`/tmp/lute-baseline/wt`) so sources and artifacts are 0.37's; `compare.sh`
captures the head and diffs.

## S0 — version stamps 0.38.0

- Stamp every visible axis 0.38.0 the way 0.37.0 did (`docs/versioning.md`
  alignment; 0.37 plan's stamp list): Cargo workspace/crate versions,
  `LUTE_LANG_VERSION`, `LUTE_IR_VERSION`, npm packages, editors, website
  stamps, `luteVersion:` in `docs/examples/**` and `conformance/**`.

- Regenerate `conformance/*/artifact.json` / `expected.json` with
  `conformance/regenerate.sh`; the only diff is the stamp.
- Acceptance as above; `compare.sh` identical after normalization.

## S1 — `expr` evaluator; the executor stops parsing CEL (spec §13)

Owner: `crates/lute-trace/src/exec/**` (still in `lute-trace`).

1. New `exec/expr.rs`: an evaluator over the `exprNode` JSON
   (`crates/lute-compile/src/expr.rs:42-70`; schema `$defs/exprNode`) with
   the result type today's `Store::eval_expr` returns — values, typed errors,
   three-valued unknowns with read capture — and the same host functions
   (`holds`, `count`, `countDistinct`, `validAt`, `now`, `visited`),
   short-circuit / absorption rules, int/double rules, `in`, `has`, index.
2. Every evaluation site passes the slot's `expr` instead of `cel`:
   `Machine::eval_atoms` / `judge` (`machine/mod.rs:385-452`), set values
   (`machine/commands.rs:145-176`), menu guards and match tests
   (`machine/menu.rs`), placeholders (`machine/format.rs:72-76`), seam gates
   and terminal (`exec/seam.rs`), eligibility `when` / `spentBy`, quest and
   objective slots, rule-body guards (`store.rs` closure).
3. **Parity gate (temporary, removed before the slice ends):** evaluate both
   ways and panic on any difference in value, error or unknown/read set; run
   the full acceptance, `conformance/harness/run.sh`, and `lute test` on
   every game under it. Record the run in the slice report. Then delete the
   CEL path: `Store::parse`, the thread-local cache, `cel-parser` and every
   `lute_cel` parse/eval use under `exec/`.
4. Exit: `grep -rn "parse_slot\|cel_parser\|CelArena" crates/lute-trace/src/exec`
   is empty. `lute_cel` path-formatting helpers may remain until S3.

## S2 — `lute-runtime` crate (pure move)

1. Create `crates/lute-runtime` (workspace member; same edition/lints as
   `lute-trace`). Move `exec/{machine,session,store.rs,driver.rs,seam.rs,
   cadence.rs,expr.rs}` and what they need from the `lute-trace` root
   (`Value`, `EffectiveState`, `Read`, `datalog`, `clock`, `value`) into it.
   `exec/record.rs` (transcript rendering, needles) and
   `exec/session/producers.rs` (refusal hints) stay in `lute-trace`, as do
   `trace/`, `mock`, `report`. Before moving, list every `crate::exec::record`
   / `producers` / `mock` / `report` / `trace` import inside the moving
   modules (e.g. `exec/session/lifecycle.rs:11-12` uses `record::str_of`);
   each such helper that is runtime logic moves into `lute-runtime`, each
   that is report logic is lifted out to the caller. `lute-runtime` never
   depends on `lute-trace`.
2. `lute-trace` depends on `lute-runtime`. Update every consumer path
   (`lute-cli`: `play/`, `testcmd/`, `runner.rs`, `differential.rs`,
   `mockcheck.rs`, `explain.rs`, `cmd_context.rs`, `calendar/`;
   `lute-bench`; `lute-wasm`). No `pub use` re-exports left behind.
3. Behavior unchanged; acceptance as above. `lute-runtime` may still depend
   on `lute-check`, `lute-compile`, `lute-cel`, `lute-syntax` at the end of
   S2; S3 removes them.

## S3 — dependency cut and bundle loading (spec §4, §14)

1. Move the runtime semantics `lute-runtime` uses from `lute-check`
   (inventory: `selection_order`, `reorder`, `beat_target_restricts`,
   `BeatOnce::parse`, `parse_prereq` / `atoms` / `PrereqFormula`,
   `gates::{target_member, persistent_reads}`, `E_OCCASION_GATE`,
   `cel_paths::{prev_run_path, is_prev_path}`,
   `target_writes::{indexed_family, member_path}`,
   `templates::{top_level_and, unparen}`, `is_reserved_entry_read`,
   `OCCASION_TARGET`, `OCCASION_PAYLOAD`, `chapters::PROVENANCE`,
   `BUILTIN_LIFECYCLE_EVENTS`, `RelVocab`, `StateSchema`, `AdvanceSpec`)
   into `lute-runtime`; `lute-check` imports them from there. A helper an
   authoring crate below `lute-check` also needs (`lute_syntax::ast::
   {format_number, format_text}`, `lute_cel::path::bracket_spelling_of`)
   moves to the lowest crate both sides may depend on (`lute-manifest`),
   never duplicated.
2. Runtime-side `Deserialize` types for `project.index.json`; the writer
   stays in `lute-compile` (`index.rs`).
3. Index additions (spec §4.2): `occasions`, `worldEvents`,
   `bridgeResults`, `cast`, `stateDomains`, in
   `schemas/lute-ir-0.38.schema.json`. `build_index` takes the four snapshot
   unions as a new argument; one collector in `lute-cli` (lifted out of
   `play/project.rs:176-219`) computes them from the source model for both
   `crates/lute-cli/src/compile_all.rs` and the play bundle. `stateDomains`
   comes from the typed artifacts inside `build_index`. A test compiles
   a game with `compile --all` and with the play path and asserts the two
   bundles are byte-identical.
4. `Runtime::load(Bundle)` replaces `ExecProject::assemble`: input is
   artifact JSON by relative path plus the index JSON. `lute play` /
   `lute test` / `lute beats` / `lute calendar` / `lute-bench` build the
   bundle in memory (serialize what `compile --all` writes) and load it.
   CLI report data (`authored`, `needles`, `chapter_afters`, `producers`)
   moves to a CLI-side struct beside the runtime.
5. CI: a `test.yml` step comparing `cargo tree -p lute-runtime -e normal
   --depth 1` to the allowed set (`serde`, `serde_json`, `lute-manifest`,
   `lute-core-span`), and `cargo check -p lute-runtime --target
   wasm32-unknown-unknown`.

## S4a — frame-stack walk behind the existing Driver

1. Replace recursive `run_range` nesting (hub option bodies
   `machine/menu.rs:708-712`, quest / handler segments `machine/quest.rs`,
   entry / bundle-beat bodies `machine/entry.rs`) with an explicit frame
   stack (spec §8.1). A frame holds what today's locals hold.
2. `choose` and `bridge` sites suspend: the machine returns
   `Suspended { menu | bridge call }` with its frames intact and resumes on
   `resume(answer)`. A thin loop calls the existing `Driver::choose` /
   `bridge` and resumes, so every consumer is unchanged in this slice.
3. Acceptance as above (byte identity is the proof the refactor preserved
   control flow); add unit tests that suspend inside a nested hub body and a
   quest segment and resume to the same transcript as an uninterrupted run.

## S4b — `Runtime` / `State` / `step` (spec §3, §5, §6, §7.1)

1. Public API of spec §3: `Runtime`, `Seed`, `State`, `Input`, `Output`,
   `Event`, `Await`, `Rejected`, `begin`, `step`, queries of §6.4.
   `State` uses `Arc` copy-on-write for world maps (spec §3.2).
2. Split `World` (spec §7.1): `choose`, `choice_cursor`, `bridges`, `step`,
   `decisions`, `eval_observer` move into the `lute play` driver in
   `lute-cli`; `derive` becomes a `Seed` option.
3. `Session` is removed; its operations become inputs
   (`raiseOccasion` ← `occasion` + `bind_payload`, `advanceClock` ←
   `advance`, `hostWrite` ← `engine`, `worldEvent` ← `event`, `newRun`).
   Rejections and halts of spec §5.3 / §6.3; `E-RUNTIME-*` codes in
   `crates/lute-cli/src/codes/registry.rs`.
4. The `Driver` trait shrinks to the policy seam of spec §8 item 5 (`unknown`,
   `observe`, `is_preview`, `premise_hint`), statically dispatched. `lute
   trace`, document `lute test` and `lute run` answer awaits in a loop with
   their existing rules (`TraceDriver` auto-pick / mocks; `RunDriver`
   scripted choices, top bridge queue, spent→skip); outputs unchanged.
5. `lute play` (`crates/lute-cli/src/play/`) drives `step`: script steps →
   inputs, awaits answered from `choose` / `bridges` with the moved
   `ScriptedChoices` / `BridgeQueues` rules, report from events + queries.
   Halt messages identical to v0.37.0 (`walk.rs` `outcome_halt`).
6. Acceptance as above.
