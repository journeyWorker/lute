# Lute 0.53.0 — implementation plan and progress log

* **Spec:** [`docs/proposals/scenario-dsl/0.53.0.md`](../../proposals/scenario-dsl/0.53.0.md). Every § below refers to it.
* **Decisions:** [`docs/superpowers/notes/2026-10-28-lute-0.53-decisions.md`](../notes/2026-10-28-lute-0.53-decisions.md) (Accepted; owner decisions of 2026-10-28, the rest by the orchestrator under the owner's delegation). It holds the per-command audit with its measurements.
* **Issues:** #224, #225, #226, #227, #228, #229, #230, #231 (label `dogfood`, round 3), plus the audit and review issues that bootstrap step 7 filed, #232–#237 (spec §16, issue map). After the release the tracker is **empty** (owner): every one of them is closed, and an issue found during implementation is either folded in (same class) or, only if it is provably a different class, recorded out of scope by the orchestrator with the owner's approval.

Every new line of Rust follows them. CLI changes follow [`docs/design/cli-grammar.md`](../../design/cli-grammar.md) (0.53 adds no flag to `lute`; `vocab-grid.py` gains `--tier`). Performance work follows `skill://rust-dev-guide/reference/performance.md` S1–S7: build shared data once (S1), per-item overlay (S2), a cache returns the shared value (S5), measure first, and gates check growth, not absolute numbers.
* **Base:** `main` at **v0.52.0** (`596d19c5`, tag `v0.52.0`). Implementation branch `feat/0.53`, created from `docs/0.53-design` (the base plus these three documents and the ADR D14 amendment, no code change). The spec's anchors (Appendix A) were located on `596d19c5`.
* **Snapshot/temp dir:** `SNAP=$HOME/lute-053-snap` (internal disk; the owner's standing instruction for 0.49–0.53: work locally). Remote sandbox: `/workspace/lute-053-snap`.

that produced it. Update the progress log after every milestone.

## Owner's disk and build rules (verbatim intent, binding on every slice)

- `export CARGO_PROFILE_DEV_DEBUG=line-tables-only` in every shell that builds.
- **One target dir:** the repository's `target/`. Never export or pass
  `CARGO_TARGET_DIR`, never `CLIPPY_CONF_DIR`. **No build worktrees:** every
  slice — Rust, TypeScript and docs — runs in the main checkout, one at a time.
- **Keep only the baseline and the latest CLI snapshot:** `$SNAP/base` and
  `$SNAP/latest`. Before each compare, `rm -rf "$SNAP/latest"`. The per-slice
  delta classification is a small text file `$SNAP/deltas/<slice>.txt` and a
  summary in the log.
- `export TMPDIR="$SNAP/tmp"`; Bun, Cargo-installed tools' and Playwright
  caches under `$SNAP/cache`. `vocab-grid.py` and the measurement scripts
  write their projects under `$TMPDIR`.
- **`cargo clean` is the orchestrator's alone, between phases** (below).
  Slices never run `cargo clean`, `--release` or `cargo doc`.
- **Disk guard:** `df -h "$HOME"` at bootstrap and before every slice; below
  **40 GB** free, stop and hand the decision to the orchestrator. Never move
  work to another volume unasked.
- **Cleanup** at the end: `rm -rf "$SNAP"`; `cargo clean` by the orchestrator.
  Anything worth keeping goes into the progress log first.

## Working rules

- **One Rust owner at a time**, in the main checkout, in the order below. TS
  and docs slices also run in the main checkout, never concurrently with a
  Rust slice (no worktrees).
- **Coding rules.** Every Rust slice reads `docs/design/rust-coding-rules.md`
  first. New types (`FixRule`, `FixKept`, `FrontmatterPath`, `Region`,
  `PairScope::Document`, the accept anchor's host source) are enums or
  newtypes, not strings. Errors are typed; no `unwrap()` outside tests; no
  `pub(super)`; a module with children is `foo/mod.rs`. No HIR, no Fold, no
  synthesized AST nodes.
- **Measure first (performance slices L1, L2, F).** Each records the
  `vocab-grid.py grid` table of its tiers before and after, with the load
  average, in the log. A cost claim without a measurement is not accepted.
- **Reviewer pass per slice**, against its spec sections, before the next
  slice starts. The reviewer reads the whole diff and the slice's delta list.
  Findings are fixed first; the fix and the reviewer's verdict are logged.
- **Regression test per change, failing before.** Each test fails on the base
  (`$SNAP/lute-0.52.0`, or the change reverted) — for §3, the `vocab-grid.py`
  tier on `$SNAP/lute-0.52.0` and the one-build unit test with the old call.
  The slice records how it showed the failure.
- **Strict snapshot compare after every slice** against the v0.52.0
  baseline (captured in L0), with the accepted-delta file:
  `rm -rf "$SNAP/latest" && python3 scripts/cli-snapshot.py target/debug/lute "$SNAP/latest" --compare "$SNAP/base" --strict --accept "$SNAP/deltas/accepted.txt"`.
  Every changed, added or removed output is first reviewed and classified:
  the slice appends one line per difference to the cumulative
  `$SNAP/deltas/accepted.txt`, pinning the reviewed bytes:
  `<class> <changed|added|removed> <command label> <stream/file> <sha256 of the normalized head output>`
  (`<stream/file>` is `stdout`, `stderr`, `exit-code` or the artifact path
  under `artifacts/`; `removed` entries hash the baseline output; `#`
  comments allowed). It cites the spec §15 class and keeps its own list in
  `$SNAP/deltas/<slice>.txt`. Exit 0: every difference is listed and its
  bytes still match; exit 1: an unlisted difference or a byte change after
  approval — a defect in that slice until fixed or re-reviewed; exit 2: a
  comparator error, never a delta. Never ignore exit status 1.
- `cargo fmt --all` before each Rust commit. Never `--release`, `cargo doc`,
  `cargo clean` or `include!`. No `#[allow]` (use `#[expect(…, reason)]`), no
  new `catch_unwind`, no `unsafe`.
- Never hand-edit generated output. Bless registry pages with
  `LUTE_BLESS_DIAGNOSTICS=1` and review the diff. Regenerate contracts with
  `lute-contract-schema` and `bun run contract:gen`. Re-bless insta snapshots
  (`cargo insta`) only for a classified delta, and review each.
- Historical records are never rewritten (spec §10).
- **Out-of-scope bugs:** `gh issue create --label bug` with evidence at once,
  plus a log line; do not fix them here. An issue of a class this release
  already fixes (a per-document rebuild, a model built for a manifest field,
  a per-document copy of project data) is **folded in** by the orchestrator:
  the slice that owns the file fixes it and the log says so. Known out of
  scope: spec §16.
- **Commit and push after each green slice** (`feat(0.53): <slice> - …`,
  `test(0.53):`, `docs(0.53):`, `perf(0.53):` for §3), then
  `git push origin feat/0.53`. Log after each. The tree is clean at handoff.
- **Budget rule.** If a slice cannot reach a green RG in its session: commit
  the work as one WIP commit on `feat/0.53-<slice>-wip` (pushed), leave
  `feat/0.53` unchanged, and log what is done, what fails (exact errors) and
  the next step. Never land a red slice on `feat/0.53`.
- **Owner questions** go to the orchestrator with a default; the slice keeps
  going on the default.

## Phases, order and rationale

```text
bootstrap ─┬─ Phase A: L0 ─ L1 ─ L2 ─ L3 ─────────────── cargo clean (orchestrator)
           ├─ Phase B: F ─ P ─ M ─ B ─────────────────── cargo clean (orchestrator)
           ├─ Phase C: Q ─ J ─────────────────────────── cargo clean (orchestrator)
           └─ Phase D: D1 ─ K ─ snapshot classification ─ Z ─ final gate ─ release
```

- **Lint and the model work first** (owner). **L0** extends the CLI
  snapshot to the commands §3 changes and captures the v0.52.0 baseline of
  them, and adds the `vocab-grid.py` tiers' CPU and memory items (failing on
  the base: the evidence). Every later slice is then compared on those
  commands too.
- **L1 before L2:** L1 changes `BuiltInput` (every caller), establishes the
  "one cache per run" pattern, the `InputCache` build counters and the
  `LUTE_STATS=input-cache` line the gate's counter items read; L2 applies the
  pattern to the remaining commands.
- **L3 after L2:** the LSP cache reuses L1's counters and adds the input
  recording (`InputCache::inputs()`) and fingerprints; it is the last §3
  slice, so every tier is on from L3.
- **F after L3:** F changes `rewrite.rs` (`run_fix`) and reads the model
  through the `ModelMemo` pattern; it also owns `renames.rs` and the
  `directives.rs` call sites. F carries `lute fix --help` for #230.
- **P, M, B** are independent and small; sequenced only by the one-owner
  rule.
- **Q before J:** both touch `lute-check`; Q is connectivity only, J is the
  label pass, every flow walk and the compiler's stage walk (the largest
  language change), so it goes last with the most context.
- **D1** documents the landed behaviour (transcripts rerun on
  `target/debug/lute`), then **K** (llms), then **Z**.
