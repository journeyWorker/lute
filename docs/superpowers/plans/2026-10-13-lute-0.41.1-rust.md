# Lute 0.41.1 — Rust-only patch implementation plan

* **Spec:** [`docs/proposals/scenario-dsl/0.41.1.md`](../../proposals/scenario-dsl/0.41.1.md), including its issue map, decisions, CLI identity list, and Appendix B evidence.
* **Decision note:** [`docs/superpowers/notes/2026-10-13-lute-0.41.1-decisions.md`](../notes/2026-10-13-lute-0.41.1-decisions.md).
* **Base:** `39bcfa7a` (released 0.41.0); work on `feat/0.41.1`.
* **Cutover:** Rust-only. Do not modify TypeScript source/tests, generated TypeScript, JSON schema bodies, or repositories outside Lute.

## Session bootstrap

The remote Rust server MUST have:

* Rust stable and pinned Rust `1.96.1` with clippy; `wasm32-unknown-unknown` target;
* `cargo-nextest`;
* `python3`;
* `jq` (used by `conformance/regenerate.sh`);
* `gh` authenticated for this repository, with push access;
* git credentials/push access.

Bun and Node are **not required locally**. TypeScript packages, the website
build, and tree-sitter harnesses are verified by PR CI. Bootstrap is fail-fast:
either clone the repository or enter an existing clone and fetch it, then verify
the remote branch and credentials before doing any build:

```sh
set -euo pipefail
if [ -d .git ]; then
  git fetch origin
elif [ -d lute/.git ]; then
  cd lute
  git fetch origin
else
  git clone git@github.com:journeyWorker/lute.git
  cd lute
fi
git rev-parse --verify origin/feat/0.41.1
git switch feat/0.41.1
git pull --ff-only
command -v jq
jq --version
gh auth status
git push --dry-run origin feat/0.41.1
git status --short --branch
cargo build -q -p lute-cli
```

Do not use `cargo clean` while anything is building. Only the orchestrator MAY
run `cargo clean`, and only between slices when it has confirmed no build is
running. Never use `--release`, `cargo doc`, or `include!`.

## Working rules

* One Rust owner at a time. Rust slices are strictly sequential: R1 → R2 → R3 → D → Z.
* Every slice ends with a reviewer-agent pass over its diff against the spec; all findings are fixed before the next slice starts.
* Every behavior change has a regression test that fails on `39bcfa7a` before the fix.
* Each slice commits its completed work on `feat/0.41.1`; no slice leaves a dirty handoff.
* Each slice updates the documentation of its surface, in both English and Korean website pages. Package README work is included in D.
* Generated TypeScript and schema files are protected files. Do not regenerate them; verify they are byte-identical. The only generated-data operation in Z is the stamp-only conformance regeneration explicitly listed below.
* Keep all temporary build/snapshot directories outside paths the orchestrator cleans. The snapshot directory is `~/lute-0411-snap/`, not `/tmp`.

## Baseline and snapshot discipline (G0)

From the 0.41.0 merge base, capture the CLI corpus before any slice:

```sh
cargo build -q -p lute-cli
mkdir -p ~/lute-0411-snap
python3 scripts/cli-snapshot.py target/debug/lute ~/lute-0411-snap/base
cp target/debug/lute ~/lute-0411-snap/lute-0.41.0
```

The orchestrator records `git diff --exit-code -- schemas/ packages/runtime/src/generated packages/player/src/bindings/schema.ts`
and the protected-file hashes. Each slice runs:

```sh
python3 scripts/cli-snapshot.py target/debug/lute ~/lute-0411-snap/<slice> \
  --compare ~/lute-0411-snap/base
```

A snapshot difference is allowed only when listed in that slice's acceptance
block and in spec §7. An unexplained line, JSON key, artifact, exit code, or
ordering change blocks the slice.
