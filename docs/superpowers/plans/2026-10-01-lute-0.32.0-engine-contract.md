# Lute 0.32.0 — engine contract: implementation plan

- **Spec:** `docs/proposals/scenario-dsl/0.32.0.md`
- **Direction:** `docs/design/architecture-direction.md` D1, D3, D11, D12, §5 phase 1
- **Base:** `57af7e6` (0.31.0). Clean cutover (D6): no legacy modes, every
  consumer migrated in the release.

## Slices and order

```
S0 naming + StateEntry.owner + schema file ──┬─ S1 runtime contract ───────────┐
                                             ├─ S2 CEL core ──┬─ S3b corpus ───┼─ S4 conformance + CI ─ S5 docs + release
                                             └─ S3a lute fix ─┘   migration    │
```

- **S0** runs alone first: it touches every crate (rename) and owns
  `ir.rs` / `schemas/` for its edits.
- **S1 ∥ S2 ∥ S3a** then run in parallel on disjoint files:
  S1 = `lute-trace/src/exec/`, `lute-cli/src/runner.rs`; S2 = everything CEL
  plus `ir.rs` slot types and `schemas/`; S3a = `lute fix` code in
  `lute-cli` (not `runner.rs`).
- **S3b** starts when S2 and S3a land. **S4** starts when S1, S2, S3b land and
  is the **only** slice that regenerates conformance artifacts and
  transcripts. **S5** last.
- Every slice runs its own acceptance once at its end, never mid-flight.

## S0 — naming, owner carry, schema file

1. Rename the Rust type `Artifact` → `ExecutionIr` (LSP rename across the
   workspace); CLI help and messages say "execution IR".
2. `StateEntry.owner: Option<Owner>`, serialized `"owner": "engine"`,
   carried from `StateDecl.owner` (`lute-check/src/meta.rs`).
3. `schemas/lute-ir-0.31.schema.json` → `lute-ir-0.32.schema.json` with the
   `owner` property; schema references updated.

Acceptance: `cargo test --workspace` green (no behavior change besides the
additive `owner` key; conformance fixtures without engine-owned state are
byte-identical); a unit test shows `owner` emitted for an `owner: engine`
slot and absent otherwise.

## S1 — runtime contract

Files: `crates/lute-trace/src/exec/` (`quest.rs`, `cadence.rs`, `mod.rs`,
`machine/build.rs`), `crates/lute-trace/src/{report.rs, trace.rs}` (grant
rendering), `crates/lute-cli/src/runner.rs`, `crates/lute-cli/src/play/human.rs`.

1. Per-quest save-wide instance counter: 1 on first activation, +1 on every
   re-instantiation (`newRun` reset, `rearm`, season reset —
   `cadence.rs:486-507` and siblings). Persisted in the save/carry beside
   `quest_status`.
2. Grant events gain `instance` and `index` (owner-relative reward position,
   document order).
3. `lute run` refuses, before executing, an IR whose commands write an
   `owner: engine` path or assert/retract a `reserved` relation:
   `E-RUN-OWNED-WRITE`, exit 1.

Acceptance: unit tests for each re-instantiation path, persistence across a
save/resume, and identical keys for a replayed transition; `lute run` on a
hand-built owned-write IR exits 1 with the code. Conformance fixtures that
grant are expected to differ (new keys) — S4 re-records them.

## S2 — CEL core

Files: `crates/lute-manifest/src/types.rs` (`Type::Int`, `Literal::Int`, plugin
attribute and bridge result types), `crates/lute-cel/`,
`crates/lute-check/src/{cel_resolve.rs, cel_types.rs, set_type.rs, meta.rs,
ctx.rs}`, `crates/lute-compile/src/{expr.rs, ir.rs slot types, lower.rs,
stage.rs}`, `crates/lute-trace/src/eval.rs`, `crates/lute-lint/src/{eval.rs,
rules.rs}`, `crates/lute-lsp/src/` (features, hover, completion),
`crates/lute-cli/src/cmd_context.rs`, `schemas/lute-ir-0.32.schema.json`,
`schemas/lute.plugin.json` (TypeDef `int`) and `schemas/lute.schema.json`
(state/shape `int`), with schema fixtures for both.

1. Types: `int` and `double` replace `number` everywhere a type is declared
   (state, shapes, def results, plugin attributes, bridge results); typed
   literals; defaults validated; `type: int` is `E-STATE-DECL`.
2. Profile (spec §1.1): admit list-form host calls, `has` / `in`, `int()` /
   `double()`; reject Prolog patterns, `isSet`, `uint`, out-of-range ints,
   computed relation names. Port `pattern_terms` rules to the list form
   (`E-FACT-QUERY`); keep `E-DATALOG-GUARD-FACT`, `E-VALIDAT-DERIVED`;
   may/must fact analysis (0.20.0) reads the list form.
3. Typing (spec §1.2): operands typed from declarations, never `dyn`; CEL
   overload rules plus the mixed-numeric comparison ban (`E-CEL-TYPE`).
4. Compile: every slot emits `{cel, expr, authored?}`; full-profile `expr`
   with typed literals, `index`, `call`; rule-body guards gain `expr`;
   `celEnv` collected from roots and functions actually used.
5. Evaluator (`lute-trace`): `int` / `double` values, CEL overload semantics,
   list-form host calls, `has` / `in`, spec §4 error policy for `run` /
   `play`; three-valued preview kept for `trace`.
6. Lint: evaluator and custom-rule value conversion (`rules.rs:899-1022`) use
   typed numbers.
7. LSP: `Type::Int` / `Literal::Int` in displays (`features/mod.rs:704-725`),
   host-function completion and hover with the list form, relation-name and
   argument completion inside the string/list positions.
8. `lute context`: CEL surface lists host-function signatures and the numeric
   rules.
9. Unit-test literals inside the crates S2 owns are updated in S2.

Acceptance: `cargo test -p lute-manifest -p lute-cel -p lute-check
-p lute-compile -p lute-trace -p lute-lint -p lute-lsp` green, with a test per
new/extended diagnostic of spec §9 and a test that every slot of a compiled
fixture document carries `expr`. CLI integration tests and examples are out of
S2's gate (S3b).

## S3a — `lute fix` rules

Files: `lute fix` implementation in `crates/lute-cli/src/` (not `runner.rs`).

1. Rules for spec §1.3 rows 1–7, operating on the parsed CEL tree (the 0.31
   forms parse as standard CEL syntax), rewriting only the slot's byte range;
   comments and everything else byte-exact.
2. Unit tests per rule, including bound `occasion.target`, quoted names, bool
   arguments, `countDistinct` column mapping, and `isSet` over a quoted key.

Acceptance: `cargo test -p lute-cli` for the new fix tests (other CLI
integration tests may still be red until S3b).

## S3b — corpus migration

1. Run `lute fix` over `docs/examples/**`, `conformance/*/source.lute`,
   documentation `.lute` fences, website pages.
2. Numeric retyping per spec "Compatibility and migration" across every
   numeric declaration (≈120 under `docs/examples/games`, including
   `ember-road` dice `margin`, `check.yaml` `dc`, `state/shapes.yaml`),
   driven by `lute check-project` until clean. Record every declaration
   retyped to `double` (not `int`) and why in the CHANGELOG draft.
3. Rust integration-test literals (`crates/lute-cli/tests/`, others not
   owned by S2) updated.
4. Conformance `source.lute` / `schema.yaml` migrated; artifacts and
   transcripts are **not** re-recorded here.

Acceptance: every project under `docs/examples` checks clean;
`scripts/check-doc-snippets.py` passes; `cargo test --workspace` green except
`tests/conformance.rs` (stale recordings, owned by S4).

## S4 — conformance and CEL equivalence CI

1. Re-record every existing fixture.
2. New fixtures (spec §8): every uncovered command kind, `grant-instance`,
   `grant-replay`, `invalid/owned-write`, `cel-*`. README inventory updated.
3. `lute run --dump-conditions <file>`: JSONL with typed value encoding.
4. `conformance/harness/js/`: `@bufbuild/cel` registering `celEnv` + host
   functions over dumped facts; an `expr` walker; grant-key assertions for
   `grant-replay`.
5. `conformance/harness/go/`: `cel-go`, same comparison.
6. CI job: replay conformance + differential corpora with the dump, run both
   harnesses, fail on any mismatch.

Acceptance: `cargo test --workspace` fully green; the CI job green; a
deliberately wrong result in a scratch run makes each harness fail (verified
once locally, not committed).

1. `docs/runtime/cel-and-facts.md` rewritten for spec §1–§4;
   `execution-model.md` (slot object, `celEnv`, error policy, terminology),
   `state-lifecycle.md` (`int`, `owner` in IR), `quest-lifecycle.md`

2. Website reference pages (CEL, state types, reserved names, diagnostics),
   `llms` docs, VS Code extension grammar/snippets if they reference the old

3. CHANGELOG 0.32.0 with breaking classes (syntax / semantic / IR) and the

4. Version stamps: `LUTE_IR_VERSION` and the language/toolchain constants

   the corpus. Until then the schema file is already `0.32` while compiled
   output still stamps `0.31.0` — intentional, so conformance live-stamp
   checks stay meaningful until S4 re-records; S5 moves every stamp at once.
   `docs/design/runtime-unification.md` status → Implemented.

Acceptance: docs CI (`.github/workflows/docs.yml`) green; `lute version`
prints 0.32.0 on all axes.

## Review gates and build hygiene

- Spec + this plan: reviewer pass before S0.
- **Every slice** gets a reviewer pass on its diff after it lands; findings
  are fixed before a dependent slice starts.
- Before release: reviewer pass on the full diff; smoke run of the CEL
  equivalence job and `lute play` over two dogfood games.
- `cargo clean` between slices (only when no slice is building) so
  `target/debug` stays small; slices build only what their acceptance needs
  (no `--release`, no `cargo doc`).
