# Lute 0.36.0 — identity, migration, and performance: implementation plan
- **Status:** Draft

- **Spec:** `docs/proposals/scenario-dsl/0.36.0.md`
- **Direction:** `docs/design/architecture-direction.md` D6, D8, D11, §5 phase 5
- **Base:** 0.35.0 on the project model, semantic diff, patch loop, and CI perf/test changes already present at HEAD
- **Cutover:** clean identity/source/IR/CLI cutover; no ordinal component identity, legacy rename inference, compatibility alias, or disabled benchmark gate
- **Deliverables:** explicit identity metadata and stable component instance keys; `lute tag` corpus migration; authored rename ledger in manifest/IR/index; `renamed` semantic diff; diagnostic registry and EN/KO pages; CHANGELOG class enforcement; A/B benchmark job; bounded property tests; normalized documentation statuses and current-rules handbook table
- **Build hygiene:** every Rust command uses `CARGO_PROFILE_DEV_DEBUG=line-tables-only CARGO_INCREMENTAL=0`; use scoped `-p` checks during slices; use `cargo nextest` for the full suite; **never run `cargo clean` mid-flight**

The current boundaries are already visible: component scopes are stamped in
`crates/lute-compile/src/normalize.rs:35-50`, line identity is allocated in
`crates/lute-compile/src/address.rs:284-327`, the graph key is a
`NodeKind` plus string (`crates/lute-model/src/graph.rs:60-76`), and patch
preserve currently computes component fingerprints and
`componentAmbiguous` (`crates/lute-model/src/patch.rs:566-635`). The slices
below preserve those crate boundaries and publish interfaces before consumers.
Every slice has disjoint file ownership. A reviewer signs the gate at the end
of each slice before the next dependent wave changes shared behavior.

## Contract published before Wave 1

The integration owner first publishes a small contract-only change. It may add
new types/serialization declarations but does not migrate the corpus or alter
runtime behavior.

1. **Identity record** in `lute-model`/`lute-compile`: an identity source enum,
   stable/fallback status, canonical component scope, and the table row kind.
   `addr` is not representable as a stable identity. The API returns the
   complete component scope and line joins without recomputing an ordinal.
2. **Component key contract:** source spelling is `instance="token"`, token
   regex `[A-Za-z][A-Za-z0-9_-]{0,63}`, scope spelling is
   `{component}#{instance}`, and the immediate-owner uniqueness rule is
   explicit. A missing key is a warning-bearing positional fallback only.
3. **Rename contract:** manifest `identity.renames` maps canonical `NodeKey`
   strings to canonical `NodeKey` strings. The resolved DTO is
   `IdentityRename { from, to }`, sorted by `from`, with validation outcomes
   for stale sources, missing destinations, duplicates, chains, and cycles.
4. **Public wire additions:** `ExecutionIr.identityRenames`,
   `ProjectIndex.identityRenames`, and diff kind `renamed`. Component
   fingerprints remain internal; they MUST use the explicit instance key and
   never an ordinal. Empty optional collections omit from JSON exactly as
   existing IR/index fields do.
5. **Diagnostics contract:** reserve these codes and exact grade ownership:
   `E-COMPONENT-INSTANCE-INVALID`, `E-COMPONENT-INSTANCE-DUPLICATE`,
   `W-COMPONENT-INSTANCE-UNTAGGED`, `W-LINE-CODE-UNTAGGED`,
   `E-RENAME-LEDGER`, `E-RENAME-LEDGER-STALE`,
   `E-RENAME-LEDGER-CYCLE`. The registry is the source for `--explain` and
   generated English/Korean pages.
6. **Benchmark JSON:** schema `0.36.0.bench`; samples identify tier, project,
   phase, base/head label, runner, sample number, iteration count, elapsed
   milliseconds, per-iteration time, exit status, and test count. Missing or
   failed samples are errors, never zero.
7. **Docs invariant:** current-release CHANGELOG class headings are
   `Syntax`, `Semantics`, `IR`, `Plugin`, `CLI`, `Diagnostics`, and `Identity`;
   the consistency checker validates all seven.

The owner records the contract in review before Wave 1. Consumers MUST use
these types rather than add local parsing or identity conventions.

## S1 — identity core and stable component scopes

**Files owned:**

- `crates/lute-compile/src/normalize.rs`
- `crates/lute-compile/src/address.rs`
- `crates/lute-compile/src/source_map.rs`
- `crates/lute-compile/src/lower.rs`
- `crates/lute-compile/src/ir.rs` for component identity payload fields (the
  ledger field is part of this one-time public struct contract)
- `crates/lute-model/src/graph.rs` only for identity metadata and expanded-line
  key construction
- `crates/lute-model/src/identity.rs` (new)
- `crates/lute-compile/src/tests/component_identity.rs` (focused identity
  tests)
- `crates/lute-model/src/identity_tests.rs` (focused identity tests)

**Do not edit:** `lute-cli/src/{cli,main,codes}.rs`, manifest loaders, patch
request parsing, LSP feature files, docs, or corpus fixtures.

**Change:**

1. Parse the reserved `instance` attr on `::use` without passing it as a
   component parameter. Validate the token and immediate-owner uniqueness.
2. Replace ordinal scope creation in `normalize::expand_use` with an explicit
   `{component}#{instance}` segment. Keep the positional ordinal only in a
   warning-bearing fallback object; no stable API returns it as identity.
3. Preserve complete nested scope paths in source markers/source maps and carry
   the explicit key through lower/address/IR joins. `addr` remains unchanged
   and positional.
4. Keep authored line codes unchanged; mark compiler allocation of an uncoded
   line as a warning-bearing fallback. Do not implement source writes here.
5. Make graph expanded-line keys and identity metadata use the same component
   scope. Ensure format-only and sibling insertion comparisons do not use spans
   or command ordinals.
6. Update component identity tests for explicit keys, nested keys, duplicate
   keys, mutually exclusive duplicate keys, earlier insertion, and fallback
   warning metadata.

**Interface to S6/S7:** S6 calls the identity allocator in source order and
writes its chosen token; S7 consumes the stable scope, line joins, and graph
metadata. No consumer may count uses itself.

**Acceptance commands:**

```sh

CARGO_PROFILE_DEV_DEBUG=line-tables-only CARGO_INCREMENTAL=0 cargo test -p lute-model identity
CARGO_PROFILE_DEV_DEBUG=line-tables-only CARGO_INCREMENTAL=0 cargo test -p lute-compile address
```

Also run a throwaway binary smoke against a temporary copy: compile a host
with two explicit uses, insert a new first use, and compare emitted line IDs,
voice keys, graph keys, and source-map scopes. The before/after output must
prove explicit identities are unchanged and the fallback emits the warning.

**Review gate:** compiler/model reviewer checks that every producer and
consumer of `{component}#{n}` is removed or intentionally confined to the
warning-bearing fallback. Review the identity table against source map,
address, graph, and IR output; reject any `addr` or source span used as stable
identity.

## S3 — bounded property-test harness

**Files owned:**

- `crates/lute-syntax/Cargo.toml` and syntax property-test modules
- `crates/lute-syntax/src/format.rs` only for test-facing hooks, not formatter
  semantics
- `crates/lute-compile/Cargo.toml` and IR property-test modules
- `crates/lute-check/Cargo.toml` and parser property-test modules
- new bounded generators under each owning crate's `tests/` or `src/` test
  module

**Do not edit:** formatter production rules, IR field definitions, parser
production code, CLI registry, docs, or CI workflow.

**Change:**

1. Add proptest or equivalent as scoped dev dependencies, with deterministic
   seed `0x0360_2026_10_05`, a fixed 4 KiB maximum input, and fixed case
   limits (formatter 256, parser 256, IR 128).
2. Assert formatter idempotence for generated valid/invalid source where the
   formatter contract permits a result; include corpus samples.
3. Generate valid execution IR values plus corpus artifacts, serialize and
   deserialize, and compare semantic values rather than incidental JSON order.
4. Feed arbitrary bytes/strings to the parser under `catch_unwind`; a panic is
   a property failure, parser errors are accepted values. Persist minimized
   input plus seed as a replay artifact and rerun that seed before reporting.
5. Keep the complete property suite under approximately 30 seconds in CI and
   deterministic under nextest; a case-count or duration breach fails review.

**Interface:** S1/S2 production serde and parse APIs remain unchanged. S11
uses the same property modules; no duplicate fuzz harness is introduced.

**Acceptance commands:**

**Do not edit:** compiler/model production algorithms, CLI command dispatch,

**Change:**

1. Add `crates/lute-bench` as a workspace member with `publish = false` and a

   `monster-league` large.
2. Measure cold load, project resolution, analysis (including forced graph),

**Review gate:** performance reviewer checks in-process phase boundaries,

## S8 — CI A/B benchmark job

**Files owned:**

- new `.github/workflows/benchmarks.yml`
- new `scripts/bench-ab.py` (interleaving driver; merges per-sample JSON)
- no benchmark harness source changes; send schema issues to S4
- First run: when the merge base has no `crates/lute-bench`, run head only,
  upload its report, and pass with a notice (true for the 0.36 PR itself).

**Change:**

1. Run only after S6 has migrated the corpus. Use one pinned
   `ubuntu-latest` runner family for the whole job, one locked toolchain, and
   one `CARGO_TARGET_DIR` shared by both revisions. Create a temporary git
   worktree at the PR merge base, build only the benchmark crate with
   `cargo build --release -p lute-bench`, and copy
   `target/release/lute-bench` aside as `lute-bench-base`. Check out the PR
   revision in the main workspace, reuse the same target directory, build
   `cargo build --release -p lute-bench`, and copy it as `lute-bench-head`.
   Never run `cargo clean`; dependency artifacts are reused from the locked
   target directory.
2. Each binary runs against **its own revision's** tier inputs: the base
   binary with `--root <base-worktree>` (the merge-base corpus it can read),
   the head binary with `--root .`. A PR that edits a tier's content therefore
   measures code plus content; the comparator prints which tiers' inputs
   differ between the two roots (by project revision sha) so a content-driven
   regression is visible and goes through the step-4 exception.
3. Interleaving is done by a driver, not by either binary:
   `scripts/bench-ab.py --base lute-bench-base --base-root <worktree> --head
   lute-bench-head --head-root . --samples 7 --out <dir>` loops over every
   tier × phase and, for each of the seven rounds, runs
   `<bin> --root <root> --tier <t> --phase <p> --samples 1 --json -` for base
   then head (swapping the order on odd rounds), each in-process sample looping
   until 200 ms. It merges the per-sample JSON into `base.json` / `head.json`
   and uploads both plus the comparator output.
4. Fail when `head_median / base_median > 1.10` for any tier/phase. Treat
   missing samples, cancelled runs, runner mismatch, malformed JSON, or a
   failed phase as failures.
5. Allow a deliberate regression only when the PR has
   `performance-approved`, owner review, a note naming tier/phase, and reports
   retained. The job still records the failing comparison.
6. Keep this job separate from correctness nextest/docs gates. Expected
   duration is under 10 minutes; CI records actual duration and retains all
   reports as artifacts. This job's comparator result is the release gate.

**Acceptance commands:**

```sh
CARGO_PROFILE_DEV_DEBUG=line-tables-only CARGO_INCREMENTAL=0 cargo build --release -p lute-bench
CARGO_PROFILE_DEV_DEBUG=line-tables-only CARGO_INCREMENTAL=0 cargo run --release -p lute-bench -- --root . --tier tiny --phase all --samples 1 --json /tmp/lute-036-tiny.json
python3 scripts/bench-ab.py --base target/release/lute-bench --base-root . --head target/release/lute-bench --head-root . --samples 3 --out /tmp/lute-036-ab
python3 scripts/compare-bench.py /tmp/lute-036-ab/base.json /tmp/lute-036-ab/head.json
```

Local proof must include one passing and one deliberate failing ratio fixture.
CI proof is the post-S6 pull-request job with reports retained.

**Review gate:** CI reviewer checks merge-base worktree selection, same target
directory/dependency reuse, `--release -p lute-bench` commands, same-runner
in-process A/B ordering, 200-ms iteration loops, artifact retention, ratio
enforcement, expected duration, and exception auditability.
