# Lute 0.10.0 — Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the `0.10.0` release — realign the language and toolchain versions onto the IR number the foundation plan already moved, restamp the corpus, write the changelog that says what each axis actually bought, re-run the Anseo drive test as a *measurement* of the release rather than a formality, and pass every gate.

**Architecture:** Four tasks, strictly ordered. The version realignment must precede the changelog (the changelog quotes the numbers) and both must precede the drive-test re-run (which measures the shipped state). The re-run is not a test pass — it is the release's own acceptance evidence, because the 38-issue backlog `0.10.0` was scoped from came out of the previous run, and spec §13 makes specific predictions this run either confirms or refutes.

**Tech Stack:** Rust workspace, `cargo insta`, the three `scripts/check-*.py` gates, GitHub Actions (`test.yml`, `docs.yml`).

## Why this plan exists separately

The seam review found that **no plan owned the version realignment its own global constraints required**. Every one of plans 00–04 says "`LUTE_LANG_VERSION` is not bumped here; it moves in the Release phase" — and there was no Release phase document. This is it.

## Global Constraints

- **Language `0.10.0`, IR `0.10.0`, toolchain `0.10.0`.** [`docs/versioning.md`](../../versioning.md)'s alignment rule has no exceptions. IR is **already** at `0.10.0` (foundation plan Task 2); this plan moves the other two onto it.
- **`env -u CI cargo insta test` / `env -u CI cargo insta accept`.** `CI=1` is set in this environment and insta reads it as "never write pending snapshots": assertions fail, no `.snap.new` appears, and a bare `cargo insta accept` reports "no snapshots to review" and **exits 0**. A step that looks like it succeeded will have changed nothing.
- **Never `git add -A`, never `git commit -am`.** `scripts/smoke-sprites.ts` is untracked in this worktree and belongs to another agent's in-flight work. Stage explicit paths.
- **Runs last.** Every task in plans 00–04 lands before Task 1 here. Bumping the language version earlier fires `W-LUTE-VERSION-STALE` across the corpus and churns goldens that other tasks are still rewriting.
- Never weaken a check to make a corpus file green.

- [ ] **Step 2: Move the preamble's three stale claims**

`CHANGELOG.md`'s header states the current language and IR numbers in prose. Update **"Language — currently `0.9.0`"** and **"IR — … (currently `0.9.0`)"** to `0.10.0`.

Then replace the alignment paragraph. The existing one explains `0.9.0`'s situation and explicitly says **"IR `0.9.0` is shape-identical to IR `0.8.0`"** — that sentence is about the previous release and must not be carried forward, because `0.10.0` is the opposite case:

```markdown
Every release holds all three axes **aligned** at one visible number, so a
release presents one number and nobody has to reconcile three. Alignment is a
presentation guarantee, not a claim that every axis changed substantively — this
changelog is where you learn which ones did. `0.10.0` is the first release in a
while where **all three earned it**: the language restricts what a document may
be (six changes), the toolchain is the bulk of the work (twenty-four), and the
IR shape genuinely changes for the first time since `0.8.0` (one field rename).
See [`docs/versioning.md`](docs/versioning.md) for the full policy and the axes
table.
```

- [ ] **Step 3: Write the `0.10.0` section**

Rename `## [Unreleased]` to `## [0.10.0] — 2026-08-XX` (use the real date) and add the release's entries above the pre-existing ones, under Keep-a-Changelog headings (`### Added`, `### Changed`, `### Fixed`, `### Removed`).

The content rule, which is the whole point of this step: **`0.10.0`'s theme is "the toolchain says what it knows" — every entry is a case where the tool already had the information and did not use it.** Write each entry as *what an author now sees that they did not before*, not as an implementation note. Source them from spec §§3–12 and the backlog's 38 issues; the spec's §13 subsections are already written from the author's side and are the best raw material.

Entries that must appear because they are breaking or removing:

- **Removed** — `W-INJECT-CONFLICT`. Say plainly that the information it carried is **dropped**, not migrated (**D-AA**); an earlier draft of the spec claimed otherwise and no such surface exists.
- **Changed (breaking, IR)** — `provenance.reason` → `provenance.explanation`. Name the collision it closes: `end.reason` is an opaque author token a host dispatches on, and these two shared a key with nothing else in common. An engine gated on IR `0.9` must widen to `0.10`; the rename is the only edit it needs.
- **Changed (breaking, mocks)** — `mocks/*.yaml` requires `file:`, resolved relative to the mock.
- **Changed (breaking, documents)** — §§3, 4, 5 can redden a document that checks clean today.
- **Added** — `defaults:` in `lute.project.yaml`, and the eleven new diagnostic codes.

### Task 3: Re-run the Anseo drive test as a measurement

**Files:**
- Create: `docs/superpowers/notes/2026-08-XX-anseo-drive-test-0.10.0.md`
- Modify: nothing else. **If this task wants to change code, it has found a defect — file it, do not fix it here.**

**Interfaces:**
- Consumes: the whole shipped release.
- Produces: the release's acceptance evidence.

This is not a formality and it is not a test pass. `docs/examples/anseo/` exists as an **instrument**: the eleven-scene example was built to drive-test the language, the previous run produced the 111-finding log and the 38-issue backlog `0.10.0` was scoped from, and spec §13 makes specific, falsifiable predictions about what this release changes. Re-running measures what the release actually bought.

- [ ] **Step 1: Establish the shipped baseline**

```bash
cd /Users/journey/Workspace/lute && cargo build -q -p lute-cli
./target/debug/lute check-project docs/examples/anseo; echo "rc=$?"
./target/debug/lute check-project docs/examples; echo "rc=$?"
./target/debug/lute test docs/examples 2>&1 | tail -3
```

The numbers to beat, measured at `b03c3af` before this release: `ok: docs/examples/anseo (18 file(s), 13 project-wide warning(s))`; `ok: docs/examples (47 file(s), 18 project-wide warning(s))`; `34 passed, 0 failed`.

- [ ] **Step 2: Check each §13 prediction, one at a time**

Spec §13 has seven subsections, each stating what reddens and what does not. For **each**, run the probe it implies and record confirmed / refuted with the command and the output. §13.5 is the one with deliberate reds — the three `mocks/*.yaml` — and §13.6's acceptance test is concrete: `docs/examples/anseo/scenes/spine-a.lute` should now carry `duration="0.4"` and be green, where before the release `0.4` produced `E-CLIP-OVERLAP` at `:38:5` and `0.35` was the workaround.

Do not accept "no output" as confirmation of a prediction about a warning. Prove the warning *can* fire by constructing the failing case in `/tmp`, then prove the corpus does not trigger it.

- [ ] **Step 3: Re-run the previous log's own probes**

`docs/superpowers/notes/2026-07-31-anseo-drive-test-findings.md` holds 111 entries with verbatim commands. Take every entry whose verdict was `TOOL-DEFECT`, `DOC-WRONG`, `SPEC-WRONG` or `LANGUAGE-GAP` and re-run its probe. For each: does it still reproduce? An issue `0.10.0` claimed to fix and which still reproduces is the most valuable finding this task can produce, and it is the reason the task exists.

- [ ] **Step 4: Write the findings log**

Create `docs/superpowers/notes/2026-08-XX-anseo-drive-test-0.10.0.md`. Reuse the previous log's verdict vocabulary — `LANGUAGE-GAP`, `ERGONOMIC`, `DOC-GAP`, `DOC-WRONG`, `AUTHOR-ERROR`, `TOOL-DEFECT`, `SPEC-WRONG` — and its rule that exactly one verdict applies per entry. Open with a table: each of the 38 backlog issues, whether `0.10.0` claimed it, and whether the re-run confirms it.

State the headline honestly, whichever way it falls. "Twenty-four of twenty-six confirmed, two still reproduce" is a better release note than a claim of completeness that the next run refutes.

- [ ] **Step 5: Commit**

```bash
git add docs/superpowers/notes/2026-08-XX-anseo-drive-test-0.10.0.md
git commit -m "docs: re-run the Anseo drive test against 0.10.0

The example is the instrument; this is the measurement. Records which of the
38 backlog issues the release actually closed and which still reproduce."
```
