# Lute 0.35.0 — AI edit loop: implementation plan

- **Spec:** `docs/proposals/scenario-dsl/0.35.0.md`
- **Direction:** `docs/design/architecture-direction.md` D2, D6, D8, D10, D11, §5 phase 4
- **Base:** 0.35.0 on the implemented 0.34 project model (`crates/lute-model`)
- **Cutover:** clean source/toolchain/analysis cutover; no legacy formatter, patch alias, dual resolver, or compatibility mode
- **Deliverables:** lossless syntax/formatter, shared revision/diff/patch/context APIs, LSP formatting and position query, 12 edit-task conformance suite, formatted corpus, AI-harness page, docs and all 0.35 stamps

The substrate is already separated as syntax AST, project model, graph, and
impact: `lute-syntax` owns parse/AST modules (`crates/lute-syntax/src/lib.rs:25-36`),
`ProjectModel` owns per-root assembly/check/compile/index
(`crates/lute-model/src/project.rs:81-240`), and `lute-model` exports graph and
impact types (`crates/lute-model/src/lib.rs:39-44`). The slices below preserve
those boundaries. Every slice has disjoint file ownership; shared interfaces
are published before dependent implementation begins.

## Contract published before Wave 1

The integration owner publishes these interfaces in a small contract change
before parallel slices edit consumers:

1. **Revision API** in `lute-model`: `FileRevision`, `ProjectRevision`, sorted
   input manifest, `project_revision`, and `ProjectModel::revisions() ->
   &ProjectRevision`; paths are root-relative UTF-8 `/` paths and all digests
   are lowercase SHA-256.
2. **Formatter API** in `lute-syntax`: lossless `SourceStream`, source
   concatenation invariant, `FormatOptions`, and fallible `format_source`
   with unchanged AST parse behavior.
3. **Diff API** in `lute-model`: `SemanticDiff`, `SemanticChange`, stable
   JSON/human projections, and `diff_models(before, after)`. Node matching is
   by `NodeKey`; spans and `addr` are excluded from semantic equality.
4. **Resolver API** in new lower-level `crates/lute-resolve`: byte-offset cursor,
   expected type, visible symbols, imports, and source span. It depends on
   `lute-syntax`, `lute-check`, and `lute-model` only; both `lute-lsp` and
   `lute-cli` depend on it, never the reverse. Verify this dependency graph
   against both Cargo manifests before coding.
5. **Patch contracts**: operation/preserve JSON schemas, refusal codes, and
   atomic staged-build protocol. S4 implements against the published diff,
   revision, formatter, and resolver APIs rather than inventing local copies.

The contract includes schema versions, deterministic ordering, error ownership,
exit codes, and examples. A reviewer signs it before Wave 1 coding starts.

### Exact interface contract

```rust
// Shared imports: std::{collections::BTreeMap, path::{Path, PathBuf}};
// lute_core_span::{Diagnostic, Span}; serde_json::Value;
// lute_model::{NodeKey, ProjectModel}; lute_syntax::ast::Document;
// lute_check::schema_import::SchemaImports; lute_manifest::{snapshot::CapabilitySnapshot, types::Type};

// lute-syntax: spans index the borrowed source; concatenation is exact.
pub enum TokenKind { Structure, Attribute, Cel, Prose, Yaml, Comment, Whitespace }
pub struct SourceToken { pub kind: TokenKind, pub span: Span }
pub struct SourceStream<'a> { pub source: &'a str, pub tokens: Vec<SourceToken> }
pub struct FormatOptions { pub regions: Vec<Span> } // empty means full document
pub struct FormatResult { pub text: String, pub changed: bool }
pub enum FormatError { InvalidSource(Vec<Diagnostic>), Preservation { span: Span, reason: String } }
pub fn source_stream(source: &str) -> SourceStream<'_>;
pub fn format_source(source: &str, options: &FormatOptions) -> Result<FormatResult, FormatError>;

// lute-model: hash the supplied exact input closure, sorted by canonical path.
pub struct FileRevision { pub path: PathBuf, pub sha256: String }
pub struct ProjectRevision { pub sha256: String, pub files: BTreeMap<PathBuf, FileRevision> }
pub enum RevisionError { InvalidPath(PathBuf), Io { path: PathBuf, message: String } }
pub fn project_revision(root: &Path, inputs: &[(PathBuf, Vec<u8>)]) -> Result<ProjectRevision, RevisionError>;
pub struct SourceLocation { pub file: PathBuf, pub span: Span }
pub enum ChangeKind { Added, Removed, Moved, Field(String), ConditionUnparsable }
pub struct SemanticChange { pub kind: ChangeKind, pub node: NodeKey, pub before: Option<Value>, pub after: Option<Value>, pub locations: Vec<SourceLocation> }
pub struct SemanticDiff { pub before: ProjectRevision, pub after: ProjectRevision, pub changes: Vec<SemanticChange> }
pub enum DiffError { Revision(RevisionError), IncompleteModel(Vec<Diagnostic>) }
pub fn diff_models(before: &ProjectModel, after: &ProjectModel) -> Result<SemanticDiff, DiffError>;

// lute-resolve: protocol-neutral results, no LSP types.
pub struct PositionQuery<'a> { pub document: &'a Document, pub source: &'a str, pub byte_offset: usize }
pub struct Cursor { pub kind: String, pub span: Span }
pub struct Symbol { pub name: String, pub kind: String, pub ty: Option<Type>, pub declaration: Option<SourceLocation> }
pub struct Resolution { pub cursor: Option<Cursor>, pub expected_type: Option<Type>, pub visible_symbols: Vec<Symbol> }
pub enum ResolveError { OutOfBounds, Unresolved(String), Invalid(String) }
pub fn resolve_position(query: PositionQuery<'_>, imports: &SchemaImports, snapshot: &CapabilitySnapshot) -> Result<Resolution, ResolveError>;

// lute-model: serialized request matches §5; application reports all violations.
pub struct PatchBase { pub project: String, pub files: BTreeMap<PathBuf, String> }
pub enum PatchEdit { ReplaceNode{node:NodeKey,text:String}, InsertBefore{node:NodeKey,text:String}, InsertAfter{node:NodeKey,text:String}, ReplaceAttr{node:NodeKey,attr:String,value:String}, RemoveNode{node:NodeKey}, CreateFile{path:PathBuf,text:String}, MoveFile{from:PathBuf,to:PathBuf}, ReplaceText{file:PathBuf,rev:String,span:Span,text:String} }
pub enum Preserve { Ids(Vec<NodeKey>), LineIds, VoiceKeys, ChoiceEffects(Vec<NodeKey>), Rewards(Vec<NodeKey>), HostContracts, Conditions(Vec<NodeKey>), Reachability(Vec<NodeKey>), Constraints }
pub struct PatchRequest { pub base: PatchBase, pub targets: Vec<NodeKey>, pub edits: Vec<PatchEdit>, pub preserve: Vec<Preserve> }
pub enum PatchRefusal { Stale { expected: String, actual: String }, Target { node: NodeKey, reason: String }, Edit { index: usize, reason: String }, Check(Vec<Diagnostic>), Preserve(Vec<SemanticChange>), Io { path: PathBuf, message: String } }
pub struct PatchReport { pub before: ProjectRevision, pub after: ProjectRevision, pub diff: SemanticDiff, pub writes: Vec<PathBuf> }
impl ProjectModel { pub fn revisions(&self) -> &ProjectRevision; }
pub fn apply_patch(root: &Path, patch: PatchRequest, dry_run: bool) -> Result<PatchReport, PatchRefusal>;
```

These are the normative signatures/fields, not compilable implementations.
Request/result DTOs derive serde traits with the proposal's tagged operation/
preserve spelling. Inputs are borrowed except the owned patch request; source
byte spans remain authoritative. Revision maps use `BTreeMap` path ordering;
diff changes sort by canonical node, change kind, file, and span; resolver
symbols sort by kind/name/declaration path; patch writes sort by path.

Dependency proof: existing CLI dependencies have no LSP edge
(`crates/lute-cli/Cargo.toml:11-26`); LSP already depends on model/check/syntax
(`crates/lute-lsp/Cargo.toml:15-29`); model has no CLI/LSP dependency
(`crates/lute-model/Cargo.toml:7-17`). Adding
`{lute-cli,lute-lsp} → lute-resolve → {lute-model,lute-check,lute-syntax}`
therefore introduces no cycle. The resolver MUST NOT depend on either consumer;
the Integrator owns dependency manifest wiring.

## Integrator — command wiring and registry (short pre-wave/between-wave role)

**Files owned:** `crates/lute-cli/src/{cli.rs,main.rs,codes.rs}` and the
diagnostics pages generated from `codes.rs`. At Integration Gate 1 only, the
Integrator also owns the one-time formatted-corpus and line-sensitive
golden/conformance snapshot changes; S5 owns task fixtures and report files
created afterward.

The integrator runs as a short pre-Wave-1 step, adding `fmt`, `diff`, and
`patch` command stubs, registry entries, and `lute-resolve` dependency wiring.
Slices own only their `cmd_*.rs` files and focused tests; they send dispatch
and help lines to the integrator rather than editing shared dispatch files.
Between waves, the integrator applies those lines and resolves registry/doc
page updates. This prevents concurrent edits to the CLI command enum,
`main.rs`, or diagnostic registry.

**Acceptance:** command stubs parse and return the documented not-yet-landed
error before their slices land; after each wave, dispatch, `--help`, and
`--explain` show the landed command/codes. Stubs are removed or fully wired
before S5.

## Slices and order

```
Wave 1 (parallel)
  S1 lossless syntax + fmt + LSP formatting ───────┐
  S2 revisions + semantic diff ────────────────────┼─> Integration Gate 1
  S3 resolver extraction + context ────────────────┘       │
                                                          v
Wave 1.5: corpus fmt → model → diff_models (empty) → golden regeneration
                                                          │
                                                          v
Wave 2: S4 atomic patch ────────────────────────────────> Integration Gate 2
                                                          │
Wave 3: S5 12 tasks + REPORT.json + docs/stamps/release
```

Wave 1.5 is a separate integration step immediately after S1 and S2: format
the corpus, run `lute fmt --check`, safely materialize/check any Git fixtures,
rebuild models, run `diff_models` against pre-format snapshots, and require an
empty semantic diff. Regenerate line-sensitive goldens/conformance fixtures
once at this gate. Only then author the 12 tasks on the formatted corpus and
freeze `REPORT.json`.

- **Wave 1:** S1, S2, and S3 have disjoint ownership and begin after the
  contract review. They MUST NOT edit integrator-owned CLI files.
- **Wave 2:** S4 starts only after Integration Gate 1 and after S1/S2
  formatter/revision/diff APIs are reviewed; it consumes S3's target/resolution
  contract.
- **Wave 3:** S5 starts after S4's refusal/preserve behavior is stable; it owns
  task fixtures/report, final corpus/doc/stamp changes, and release snapshots.
- Each slice runs scoped proof only. The workspace-wide suite runs once after
  all slices land, followed by actual CLI smoke scenarios and docs checks.

## S1 — lossless syntax, `lute fmt`, and LSP formatting

**Files owned:**

- `crates/lute-syntax/src/trivia.rs` (new) and lossless stream exports in
  `crates/lute-syntax/src/lib.rs`;
- formatter implementation/tests in `crates/lute-syntax/src/format.rs` (new);
- CLI `crates/lute-cli/src/cmd_fmt.rs` (new) and its focused tests;
- LSP formatting handler/capability in `crates/lute-lsp/src/backend.rs` and
  its focused tests;
- the integrator owns `cli.rs`, `main.rs`, `codes.rs`, and dispatch/help lines;
- no edits to `lute-model`, patch/diff commands, or task fixtures.

**Change:**

1. Add `SourceStream` over original bytes. Preserve every byte as token or
   trivia, map structural tokens to AST spans, and leave the authoritative AST
   parser unchanged. Add round-trip and arbitrary-input no-panic property
   tests.
2. Implement canonical body layout: LF, trailing-whitespace removal, one final
   newline, one blank-line run, two-space nested indentation, matching closing
   delimiters, single attribute spaces, 0.32 quote form, and consistent
   directive spacing. Preserve attribute order, comments, CEL, and prose.
3. Treat frontmatter and project/schema/plugin YAML as opaque except trailing
   whitespace/final newline. Add a regression corpus for YAML comments, flow
   maps, duplicate-looking text, and multiline scalars.
4. Add `lute fmt [--check] <path…>` with sorted recursive selection, no-write
   check mode, exit 0/1/2 behavior, and write-only-if-changed behavior.
5. Add `textDocument/formatting` using the same formatter function. Advertise
   only full-document formatting; do not add a second range printer.
6. Send the command enum/dispatch/help changes to the Integrator; format the
   dogfood corpus only at Integration Gate 1.

**Acceptance:**

- `concat(SourceStream::tokens(x)) == x` for valid and fuzz-generated input.
- `fmt(fmt(x)) == fmt(x)`; all comment payloads survive; prose/CEL payloads are
  byte-identical; YAML changes are limited to trailing whitespace/final newline.
- LSP formatting returns the same edit as CLI formatting.
- Scoped proof: `cargo test -p lute-syntax <formatter tests>` and focused
  `cargo test -p lute-lsp <formatting tests>` only, with compact cargo env.

**Review gate:** a formatter/source-preservation reviewer checks the corpus
fixtures and property boundaries before Integration Gate 1 touches any source
file.

## S2 — revisions and semantic diff

**Files owned:**

- `crates/lute-model/src/revision.rs` (new), `diff.rs` (new), and model
  revision accessors in `project.rs`/`lib.rs`;
- `crates/lute-cli/src/cmd_diff.rs` (new) and focused diff tests;
- the integrator owns `cli.rs`, `main.rs`, `codes.rs`, and dispatch/help lines;
- no edits to syntax/formatter files, context/resolver files, or patch files.

**Change:**

1. Compute file SHA-256 from exact bytes and capture every input file actually
   read by the model (sources, manifest, schemas, plugins, imports). Normalize
   paths root-relative with `/`; sort `(path, fileRevision)` pairs; hash a
   length-delimited encoding to obtain project revision.
2. Keep revision data on the model snapshot, not in `InputCache` keys. Current
   cache keys are capability/profile/plugin inputs and omit source bytes
   (`crates/lute-model/src/cache.rs:14-31`), so revision capture must be
   explicit.
3. Materialize `git:<rev>` with `git archive` in a private temporary directory,
   admitting only regular files/directories; reject symlinks/submodules,
   absolute paths, and archive entries containing `..`; verify every extracted
   input remains below the temp root, hash the extracted file set before model
   construction, and delete the directory after comparison.
4. Match by `NodeKey`. Compare exact-profile canonical CEL ASTs (whitespace and
   parentheses normalized, literal kind preserved; unparsable conditions emit
   `conditionUnparsable` with no text fallback), effects, writes/asserts/
   retracts, grants/rewards, line text/IDs/voices/speakers, choices, every
   scheduling input (`once`, `on`, `priority`, `share`, `spentBy`, `after`,
   `until`/`by`, duration/advance/clock consumption, cadence, season),
   reachability/constraints, host contracts, required semantics, and vocabulary.
   Ignore spans and `addr`; classify path changes as moves when identity
   survives. Match rewards by authored owner-local content, refusing identical
   ambiguities.
5. Produce stable JSON/human output with before/after revisions, change kind,
   node, before/after values, and file:line locations. Empty output is the
   formatter semantic-preservation proof.
6. Add model-level unit tests for additions/removals/moves, line identity,
   reward/grant changes and ambiguity, scheduling changes, host contract
   changes, constraint verdict changes, pure formatting, and deterministic sort.

**Acceptance:**

- A byte-only trailing whitespace/final-newline change yields an empty diff.
- A changed guard/effect/line/choice/reward/scheduling/required semantic yields
  exactly one appropriate semantic change with both locations.
- A path move with unchanged `meta.id`/line identity is `moved`, not removed plus
  added; an ID change is removed plus added.
- File/project revisions are stable under filesystem traversal order and are
  printed by diff.
- Scoped proof: `cargo test -p lute-model <revision/diff tests>` and a smoke
  `lute diff` on one directory pair.

**Review gate:** a semantic-model reviewer checks that no span, `addr`, or
formatter-only value leaks into semantic equality.

- no edits to `lute-model/src/diff.rs`, syntax formatter, patch modules, or task

**Change:**

1. Extract cursor resolution, import precedence, visible-symbol candidates, and

   shots, quests, lore, beats, directives, CEL, set paths, interpolations, and
   speaker positions (`crates/lute-lsp/src/features/mod.rs:167-202`); preserve

2. Make LSP hover/completion/definition/references and CLI position queries use
   the crate. Preserve imported-state-wins and inline-defs-win precedence
   (`crates/lute-lsp/src/features/mod.rs:64-85`).
3. Add CLI `lute context <dir> --target <nodeKey> [--json]` while retaining the
   existing whole-file `lute context <file>` surface. Add `--max-items` and
   deterministic sort/truncation.
4. Build the target report from `ProjectModel::graph()` and `impact::query`,
   then attach declared reads/writes/queries/asserts, source excerpt, direct
   references both directions, and related scripts. Enumerate every
   `*.play.yaml`/`*.test.yaml`, follow loader includes, classify exact typed
   step/expectation ID or lineId matches as static, and classify visits from
   `--run` play/test execution as witnessed. Put unresolved includes, dynamic
   raises, unrun scripts, and non-observable derived nodes in `notIncluded`
   with counts/reasons. Add neighborhood vocabulary, revisions, and remaining
   `notIncluded` exclusions/counts.
5. Add `--at <file>:<line>:<col>` returning `expectedType` and
   `visibleSymbols`; use one-based CLI coordinates and the existing `TextIndex`
   conversion at the LSP boundary.
6. Close target coverage required by edit tasks: where `NodeKind` exists but the
   graph does not yet emit authored choice/option nodes, add deterministic
   choice keys in the model graph slice without changing execution IR.

**Acceptance:**

- Existing LSP completion/hover/nav tests pass unchanged in meaning after
  resolver extraction; CLI and LSP return the same symbols/type for a shared
  cursor fixture.
- Context target JSON is deterministic, size bounded, revision-stamped, and
  includes both incoming/outgoing references, impact evidence, related scripts,
  relevant vocabulary, and explicit exclusions.
- Unknown and ambiguous targets refuse deterministically; truncation counts are
  present in `notIncluded`.
- Scoped proof: focused `cargo test -p lute-lsp` resolver tests, focused
  `cargo test -p lute-cli` context tests, and one `lute context --target` plus
  one `--at` smoke invocation.

**Review gate:** resolver reviewer verifies there is exactly one cursor/type
resolution implementation and no CLI-only symbol precedence.

## S4 — atomic patch and preserve enforcement

**Files owned (starts after S1 + S2 review):**

- `crates/lute-model/src/patch.rs` (new), patch staging/preserve helpers, and
  exports in `lib.rs`;
- `crates/lute-cli/src/cmd_patch.rs` (new) and focused patch tests;
- the integrator owns `cli.rs`, `main.rs`, `codes.rs`, and dispatch/help lines;
- no edits to formatter, diff, resolver, context, conformance, or corpus files.

**Change:**

1. Parse `{base, targets, edits, preserve}` with strict schema validation.
   Resolve `kind:key` against the model; reject unknown/ambiguous targets and
   project/dependency-only nodes without source anchors. Schema state
   declarations expose YAML spans and are editable through `replaceText`.
2. Implement node-span operations (`replaceNode`, `insertBefore`,
   `insertAfter`, `replaceAttr`, `removeNode`), file operations (`createFile`,
   `moveFile`), and exact-revision `replaceText`.
3. Check each operation is inside its target node and detect overlapping edits
   before mutating staged text. For moves, preserve bytes/identity and update
   references only through explicit patch edits.
4. Stage all source bytes in memory; format touched regions using S1; rebuild
   the complete ProjectModel from the stage; run check-project rules; run S2's
   before/after semantic diff; enforce every preserve item.
5. On any refusal discard the stage and emit one stable code plus full details.
   On success write all files as one commit-like operation; `--dry-run` stops
   before write and reports proposed files/revisions/diff.
6. Add refusal tests for stale project/file revisions, unknown/ambiguous or
   source-anchor-less targets, out-of-target and overlapping edits, new check
   errors, unparsable conditions, reward ambiguity, preserve violations, move
   identity, and escape-hatch revision mismatch.
7. For repeated component uses without authored instance keys, fingerprint
   component name, authored argument bindings, enclosing node key, and authored
   stable child IDs. Preserve existing scopes when inserting before them; refuse
   identical/ambiguous fingerprints with `E-PATCH-PRESERVE` rather than guess.

**Acceptance:**

- A successful multi-file patch writes all intended files; injected failure at
  any pre-write stage leaves every original byte unchanged.
- `E-PATCH-STALE`, `E-PATCH-TARGET`, `E-PATCH-EDIT`, `E-PATCH-CHECK`, and
  `E-PATCH-PRESERVE` have exact exit 2 and stable JSON payloads.
- Preserve checks catch changed IDs/line IDs/voice keys, choice effects,
  rewards, host contracts, conditions, reachability, and worsened constraints.
- `moveFile` is a move in diff, retains `meta.id`/line identity, and either
  updates references or refuses/flags them.
- Scoped proof: focused patch tests plus one dry-run and one successful smoke
  invocation against a temporary copy of a dogfood game.

**Review gate:** patch reviewer checks atomicity, stale handling, target scope,
semantic diff reuse, and no source writes before preserve completion.

## Review gates and build hygiene

- Spec and the published interface contract receive a reviewer pass before
  Wave 1. No dependent slice starts after a failed gate.
- Each slice gets a focused reviewer pass after landing. S2 and S4 receive a
  semantic-model/provenance review; S1 receives a source-preservation review;
  S3 receives a resolver-single-source review.
- Do not run workspace-wide builds/tests or formatters while siblings are
  editing. Use compact scoped proof only:
  `CARGO_PROFILE_DEV_DEBUG=line-tables-only CARGO_INCREMENTAL=0` and
  `cargo test -p <package> <focused test>`.
- Never use `--release`, `cargo doc`, or `cargo clean` mid-flight. Preserve
  incremental artifacts. A clean environment, if required for the final gate,
  happens only after all slices land and no sibling is active.
- The final integration gate runs the full suite once, then actual smoke
  commands: `lute fmt --check`, representative `lute context --target` and
  `--at`, `lute diff` directory and `git:<rev>` sides, `lute patch --dry-run`,
  one successful patch, one refusal per error class, and the edit-task report.
