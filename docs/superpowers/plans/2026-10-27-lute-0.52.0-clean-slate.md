- `export CARGO_PROFILE_DEV_DEBUG=line-tables-only` in every shell that builds.
- **One target dir:** the repository's `target/`. Never export or pass
  `CARGO_TARGET_DIR`, never `CLIPPY_CONF_DIR`. **No build worktrees:** every
  slice — Rust, TypeScript and docs — runs in the main checkout, one at a time.

  `$SNAP/latest`. Before each compare, `rm -rf "$SNAP/latest"`. The per-slice

  Anything worth keeping goes into the progress log first.

## Working rules

- **One Rust owner at a time**, in the main checkout, in the order below. TS
  and docs slices also run in the main checkout, never concurrently with a
  Rust slice (no worktrees).
- **Coding rules.** Every Rust slice reads `docs/design/rust-coding-rules.md`
  first. New types (`HubLeave`, `RangeEnd`, `MenuText`, `RewardAttrFault`,
  `BodyRange`) are newtypes or enums, not strings. Errors are typed; no
  `unwrap()` outside tests; no `pub(super)`; a module with children is
  `foo/mod.rs`. No HIR, no Fold, no synthesized AST nodes.
- **Reviewer pass per slice**, against its spec sections, before the next
  slice starts. The reviewer reads the whole diff and the slice's delta list.
  Findings are fixed first; the fix and the reviewer's verdict are logged.
- **Regression test per change, failing before.** Each test fails on the base
  (`$SNAP/lute-0.51.0`, or the change reverted, or — for a fixed point — the
  iteration disabled; for #198 the clippy evidence of spec §9). The slice
  records how it showed the failure.
- **Strict snapshot compare after every slice** against the v0.51.0
  baseline:
  `rm -rf "$SNAP/latest" && python3 scripts/cli-snapshot.py target/debug/lute "$SNAP/latest" --compare "$SNAP/base" --strict`.
  Every changed, added or removed output goes into `$SNAP/deltas/<slice>.txt`
  with its spec §15 class. An unclassified delta is a defect in that slice.
- `cargo fmt --all` before each Rust commit. Never `--release`, `cargo doc`,
  `cargo clean` or `include!`. No `#[allow]` (use `#[expect(…, reason)]`), no
  new `catch_unwind`, no `unsafe`.
- Never hand-edit generated output. Bless registry pages with
  `LUTE_BLESS_DIAGNOSTICS=1` and review the diff. Regenerate contracts with
  `lute-contract-schema` and `bun run contract:gen`. Re-bless insta snapshots
  (`cargo insta`) only for a classified delta, and review each.
- Historical records are never rewritten (spec §11).
- **Out-of-scope bugs:** `gh issue create --label bug` with evidence at once,
  plus a log line; do not fix them here. Known: spec §16.
- **Commit and push after each green slice** (`feat(0.52): <slice> - …`,
  `test(0.52):`, `docs(0.52):`), then `git push origin feat/0.52`. Log after
  each. The tree is clean at handoff.
- **Budget rule.** If a slice cannot reach a green RG in its session: commit
  the work as one WIP commit on `feat/0.52-<slice>-wip` (pushed), leave
  `feat/0.52` unchanged, and log what is done, what fails (exact errors) and
  the next step. Never land a red slice on `feat/0.52`.

## Phases, order and rationale

```text
bootstrap ─┬─ Phase A: S1 ─ S2 ─ S3 ─ S4 ──────────────── cargo clean (orchestrator)
           ├─ Phase B: S5 ─ St ─ S6 ──────────────────── cargo clean (orchestrator)
           ├─ Phase C: S7 ─ S8 ───────────────────────── cargo clean (orchestrator)
           └─ Phase D: D1 ─ K ─ snapshot classification ─ Z ─ final gate ─ release
```

- **S1 first:** the smallest language change (lexer and inline parser), with
  no dependency; every later slice's tests may write `\{{`.
- **S2 before S3:** with quest top-level content refused, every label is in a
  body, which simplifies S3's range-body rule; S2 also removes the 0.51 R4
  cause S3 would otherwise have to keep.
- **S3 before S4:** S4's hub fixed point must route S3's leaving jumps as
  forward jumps (not back edges).
- **S5 then St:** S5 changes the event shape and the generated TypeScript; St
  makes the player read it and must follow at once so the TS gates are green.
- **S6, S7, S8** are independent; they are sequenced only by the one-owner
  rule. S7 and S8 are small.
- **D1** documents the landed behaviour (transcripts rerun on
  `target/debug/lute`), then **K** (llms), then **Z**.

### S1 detail

1. The finder walks an inline node list exactly as `inline_plain_text`
   joins it (`ast.rs:151-164`) and reports the first marker whose preceding
   decoded literal run ends in an odd number of `{`. `IrText` is not changed:
   the check is what makes its output unambiguous.
2. The label-grammar predicate is one function in `lute-check`: given the
   owning node and attribute (and, for a directive, the snapshot's `text`
   attributes), it says whether the value takes the label grammar. S5 reuses
   it for prompts' interpolation scans.
3. Grep and log every caller of `parse_inline_text` and `parse_inline_nodes`,
   to show that the check reaches lines, translations and spliced component
   lines: `git grep -n -E 'parse_inline_text|parse_inline_nodes' -- crates`.

### S3 detail

1. In the label pass, record for each site the chain of range bodies
   (0.51's body chains, `BodyKind`); `BodyRange` names the range body.
   Compute `leaves` and `E-JUMP-INTO-BODY` in the same pass after
   collection.
2. `leaves` reaches lowering the way 0.51's `LoopTable` does (stored beside
   `next_targets` on the check result); lowering writes it on the `jump`.
3. The runtime's `RangeEnd` replaces the bare `return` paths of `run_range`;
   every caller (`entry.rs:81,167`, `menu.rs:717,733`, `quest.rs:1169`, the
   top-level `run`) is updated; only `do_hub` acts on `Leave`.
4. Conformance: start from `conformance/session/hub-once/project` with the
   issue's `hub.lute` and script; the `run` fixture compiles the same scene.
   Regenerate with `conformance/regenerate.sh`; both harnesses register it.

### S4 detail

1. The hub head is `StageFlow::hub(entry, hub) -> StageState` in
   `inject.rs`, built on `head_fixpoint` with the `StageHead` lattice. The
   probe walk of one iteration folds each non-exit option body from the
   current head with `fold_injections` (emission off, fresh pending map),
   joins the exits, then folds the `<return>` body from that join.
2. The compiler's `walk_hub` calls it before emitting, then emits every
   option from the head as today. The checker's fold calls it in place of
   the parallel-arms treatment for `Node::Hub`.
3. Order: the shared function and its unit tests; the checker fold; the
   compiler; the agreement test; the bench axis. Commit per step.

### S5 detail

1. Checker first (prompts in the label grammar), then `ProjectDoc` (a
   mechanical change across callers; build the workspace after it), then
   #212's scan, then the IR, then the runtime.
2. The runtime's shared helper renders a text and its translations exactly
   as `rec_line` renders a line's (`commands.rs:95`); `rec_line` itself calls
   it, so there is one rendering path.
3. Regenerate: `cargo run -q -p lute-runtime --features json-schema --bin lute-contract-schema`,
   then `(cd packages/runtime && bun run contract:gen)`, then
   `conformance/regenerate.sh`; review every regenerated hunk (only the new
   menu fields may appear) and commit.

### S6 detail

1. Manifest: the reward-kind attribute rules mirror `validate_directive`'s
   (`DuplicateAttr`, `AttrDefaultType`, `structured_attr`) plus the reserved
   names; reported at load like `validate_reward_effects`.
