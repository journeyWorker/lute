# Runtime and player — working brief for ADR D13

Authority: `docs/design/architecture-direction.md` D13 (and D1, D6, D11). This
brief carries what the owner decided while D13 was being discussed
(2026-10-07), the code facts the work starts from, and the questions the first
spec must settle. Read it before writing the D13 phase-1 spec. Where this brief
and D13 disagree, D13 wins and this brief is corrected.

## 1. Decided (owner-approved)

**Layers.** Runtime (IR execution) → Player (what a person sees) → Host (the
game). Only the runtime reads the execution IR; player and host consume the
runtime's events and send it inputs. Static project metadata (index, state
declarations) may be read by the host directly — it is a list, not execution
meaning.

**What belongs in the runtime** — anything that meets one of:
1. it changes story outcome or state;
2. it must survive save/load or rollback;
3. it must be identical on every platform.

Everything that depends on the device, wall-clock time or I/O, or is purely
visual, stays outside; its *result* enters as an input.

**Runtime shape.**
- Rust crate `lute-runtime`, split out of `lute-trace`; no checker, no CEL
  parser (evaluates the IR `expr`); `lute play` / `lute test` run on it.
- Pure core: `step(state, input) -> (state', output)`. No I/O, clock,
  randomness, threads, globals. Effects (bridge/plugin calls, grants) are
  returned as data with a request id; the host executes them and feeds the
  result back as an input. An input log replays exactly.
- Stage state lives in the runtime: background, who is on stage (character,
  anchor, emotion, costume), current music. Transient visuals do not (fade
  progress, shake in flight, typewriter position).
- Time: in-game time (clock day/slot, deadlines) and progression order are the
  runtime's; wall-clock time never is. Timing *rules* that change outcomes
  (a timed choice's default) are runtime rules, triggered by a `Timeout` /
  `TimeElapsed` input.
- Grants carry an instance key in every product shape; the host settles
  (packaged game: client; live service: server after replaying the input log).
- Distribution: wasm (browser, Node server verification) and C ABI / FFI
  (Unity, Flutter, Godot). The game-facing binding is a new crate, separate
  from the playground's `lute-wasm` (which carries checker + compiler).
- Porting stays possible: the conformance corpus, generated by the canonical
  CLI, is the contract an independent runtime must pass.

**Player.**
- `player-core` (presenter-agnostic): progression statechart (advance, auto,
  skip / read-skip, backlog, choice, timed choice, menus), cue scheduler
  (interprets `timing.wait/duration/delay/at/timeline` and `barrier`; waits on
  presenter completion), bindings (project semantic vocabulary → concrete
  assets: `emotion`, `framing`/`move`/`transition`, `textStyle`, `cgLayout`,
  `sequence`).
- Presenter interface, minimal: `apply(cue) -> completion` and
  `restore(stageState)`. Lute builds one 2D web reference presenter; hosts
  build 3D / engine presenters (Unity Timeline + Cinemachine, Godot) against
  the event contract.
- Stack: TypeScript, XState **v6 alpha pinned to an exact version** (no `^`),
  `@xstate/effect` pinned alongside; Effect at the edges (wasm shell, ports).
- Saves are a Lute-owned format: runtime snapshot + player settings. Never a
  serialized XState snapshot.

**Repository.** Runtime, bindings and `packages/player` live in this repository
until the event contract stabilizes; games live in their own repositories. CI
path filters keep player-only PRs off the Rust jobs. The event contract gets
its own version axis (`docs/versioning.md`).

## 2. Code facts at v0.37.0

- Executor: `crates/lute-trace/src/exec` — `machine/` (command walk, store,
  datalog, cadence), `session/` (occasions, beats, quests, eligibility, world
  carry), `store.rs`, `driver.rs`, `seam.rs`. About 9.7k lines in
  `machine/` + `session/`.
- **Control is inverted relative to D13.** The `Machine` calls a `Driver`
  synchronously mid-walk: `choose(menu)`, `forced(...)`, `bridge(call)`,
  `unknown(site)`, `emit(rec)` (`exec/driver.rs`). D13's step function needs a
  resumable walk that suspends at a choice / bridge / input point and resumes
  on the next input. This is the core refactor.
- `lute-trace` depends on `lute-check`, `lute-compile`, `lute-cel`,
  `lute-syntax`, `lute-manifest` (`crates/lute-trace/Cargo.toml`). Preview-only
  machinery (three-valued unknowns, `unknown()` / `observe()` /
  `premise_hint()`, mocks) belongs to `trace`, not the runtime.
- The machine reads the artifact as `serde_json::Value`
  (`Store::of_artifact`); typed IR structs live in `crates/lute-compile/src/ir.rs`.
  Decide whether the runtime parses into typed structs from a small shared IR
  types crate or keeps JSON.
- Users of `lute-trace`: `lute-cli`, `lute-bench`, `lute-wasm`.
- Performance history: 0.36.4–0.36.6 removed per-evaluation state cloning and
  datalog recomputation; `lute-bench` has `play-assembly` / `play-replay`
  phases with a CI A/B gate. Keep the gate green through the split.
- Contract docs the event contract builds on: `docs/runtime/execution-model.md`
  (dispatch by `family`/`kind`, positions, timing, segments),
  `timeline-semantics.md`, `bridge-protocol.md`, `quest-lifecycle.md`,
  `beats-and-occasions.md`, `state-lifecycle.md`. IR schema:
  `schemas/lute-ir-0.37.schema.json`. Conformance: `conformance/README.md`.

## 3. Draft event contract (to be specified, not final)

| Input (host/player → runtime) | Output (runtime → player/host) |
|---|---|
| `Advance` | events: `Line` (plain text + `segments`, `voiceKey`, role), `Stage` (bg/actor/music/sfx/vfx/camera/cg/video/sequence, with resolved timing), `Grant` (instance key), `QuestChanged`, `StateChanged` |
| `Choose { option }` | await: `AwaitAdvance`, `AwaitChoice { options, timeout? }`, `AwaitBridge { requestId, call }`, `AwaitOccasion`, `Ended { reason }` |
| `RaiseOccasion { name, target? }` | |
| `BridgeResult { requestId, value }` | |
| `Timeout` / `TimeElapsed` | |
| `Load { snapshot }` | |

## 4. Open — settle in the phase-1 spec

1. Suspension granularity: does the runtime stop after every line
   (`AwaitAdvance`) or emit runs of non-blocking records until the next input
   point and let player-core pace them?
2. Snapshot granularity for rollback (per input? per line?) and snapshot cost
   (copy-on-write discipline; no deep clones — see the 0.36.4 lesson).
3. Cross-run data — read history (keyed by `lineId`), gallery, endings: Lute
   `user.*` state owned by the runtime, or a player/host profile?
4. Non-blocking dialogue (barks, walk-and-talk): may occasions interleave with
   an open conversation? This is runtime meaning, not presentation.
5. Typed IR vs JSON inside the runtime; where the IR types crate lives.
6. Which `lute-trace` parts move (walk, store, datalog, session) and which stay
   preview-only; how `lute trace` keeps its three-valued preview on top of the
   runtime.
7. Event contract version axis name and how `lute play --json` relates to it
   (same stream, or a projection).
8. Order-dependent semantics: where `BTreeMap` iteration order is de facto
   meaning (quest updates, rule application) — pin it in the spec and
   conformance so an independent runtime can match.

## 5. Suggested order

1. **R1 (0.38):** spec the event contract + resumable step API; split
   `lute-runtime` out of `lute-trace`; `lute play` / `lute test` on it;
   conformance gains session-level cases (occasions, quests, beat selection,
   clock, timed choice, save/load replay). Byte-identical CLI output vs 0.37
   except deliberate contract changes.
2. **R2:** game-facing bindings (wasm + C ABI) and a thin TS shell
   (`packages/runtime`, Effect) with a replay test from a recorded input log.
3. **R3:** `packages/player` — player-core statecharts, cue scheduler,
   bindings, 2D web reference presenter; driven by recorded runtime outputs.

Work the way 0.32–0.37 were run: spec + plan under
`docs/proposals/scenario-dsl/` and `docs/superpowers/plans/`, reviewer pass per
slice, one Rust owner at a time, `cargo clean` only by the orchestrator between
slices.
