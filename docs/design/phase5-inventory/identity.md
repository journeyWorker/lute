# Phase 5 inventory - identity

## summary

Identity inventory for 0.35.0/CI head: authored ids are generally stable under sibling insertion and formatting, but file moves and parent renames have mixed behavior; untagged line codes are positional/back-filled and component instance `{component}#{n}` is explicitly ordinal, so inserting an earlier use renumbers later component identities. `addr` is always build-local. `lute diff` compares canonical NodeKeys and reports path changes as `moved`, but does not infer parent/file rename when the key itself changes; changed keys become removed/added.

## architecture

Source AST/frontmatter -> lute-check validation/folding -> normalize component expansion -> lower/stage -> address.rs final addr and line identity -> ExecutionIr/ProjectIndex. Separately ProjectModel builds SemanticGraph with canonical NodeKey keys and diff compares before/after model values by NodeKey. Runtime sessions persist selected canonical ids in World/Carry. LSP is source-span/cursor based and does not consume addr, lineId/voiceKey, or a component fingerprint table.

## Scope and normative baseline

The requested phase-5 baseline is explicit: D6 requires clean cutovers with corpus migration and no compatibility shims (`docs/design/architecture-direction.md:158-165`); D8 keeps existing identity roles—`meta.id`, per-speaker `code` to `lineId`/`voiceKey`, author-declared ids for the listed DSL constructs, and `addr` as build-local position (`docs/design/architecture-direction.md:187-203`); D11 requires conformance/property hygiene (`docs/design/architecture-direction.md:243-255`). Phase 5’s exit is “identity source documented per node kind, stable component instance keys,” with inserting a component use renumbering nothing and benchmark regressions failing CI (`docs/design/architecture-direction.md:350-366`).

## Identity mechanics that affect every row

* `addr` is regenerated on every compile, is `"{shot}-{(index+1)*100}"`, and is a position rather than identity (`docs/runtime/execution-model.md:130-140`). `address.rs` sizes address fields over the whole artifact and assigns/resolves them in the final pass (`crates/lute-compile/src/address.rs:54-81`; `crates/lute-compile/src/address.rs:84-109`). Therefore `addr` changes under insertion, deletion, reordering and often formatting only if formatting changes parsing/order; it is never a save/localization key.
* Default content joins are `{prefix}.{speaker}_{code}` for `lineId` and `{prefix}.{speaker}-{code}` for `voiceKey`; prefix is normally `meta.id` (`docs/runtime/execution-model.md:130-140`). `identity:` may re-template both, and consumers must treat them as opaque (`docs/runtime/execution-model.md:136-140`). `LineCmd.code` is compiler-internal and skipped from serialization; `line_id` and optional `voice_key` are serialized (`crates/lute-compile/src/ir.rs:953-984`).
* `address.rs` performs a two-pass identity allocation per identity scope: first maximum authored numeric code per `(component scope, speaker)`, then final emission-order allocation of missing codes by +10 (`crates/lute-compile/src/address.rs:284-327`). Existing authored codes do not renumber when a sibling line is inserted; an untagged line gets a newly computed code and can shift if earlier untagged lines are inserted.
* `lute tag` persists codes into source. It refuses to rewrite structurally broken documents, leaves already-tagged documents byte-identical, and assigns missing codes through `lute_check::tag_document` (`crates/lute-cli/src/rewrite.rs:125-129`; `crates/lute-check/src/tag.rs:23-32`). Its per-scope allocator uses highest existing numeric code plus ten (`crates/lute-check/src/tag.rs:102-132`). `--force` rewrites every code in document order and is refused by `codesLocked`, because code changes sever localization/voice joins (`crates/lute-cli/src/rewrite.rs:131-135,152-158`; `crates/lute-check/src/tag.rs:198-208`).
* Component expansion is normalized before lowering. Each use gets a sentinel scope `{component}#{n}`, where `n` is the 1-based use ordinal of that component among the host’s uses of the same component; nested uses append their own segments (`crates/lute-compile/src/normalize.rs:35-50`). The scope is carried into `Source.scope` and used by `address.rs` to mint `{prefix}.{component}#{n}.speaker_code` identities (`crates/lute-compile/src/ir.rs:749-755`; `crates/lute-compile/src/address.rs:288-295`). This ordinal is not stable under insertion of an earlier same-component use; this is the explicit phase-5 gap (`docs/design/architecture-direction.md:196-203`).
* Component untagged line codes are back-filled from the component body in source order before match folding, using the same max-authored-plus-ten policy as `lute tag`; this makes literal and `@def` argument forms use the same code for the same component source line (`crates/lute-compile/src/normalize.rs:82-121`). This fixes call-site argument/fold dependence but does not fix ordinal scope renumbering.
* Choices and hubs do not use line-code allocation for option labels. `address.rs` emits structural option line IDs `{prefix}.{branchOrHubId}.{optionId}` and explicitly does not template them (`crates/lute-compile/src/address.rs:253-263,333-345`; `crates/lute-compile/src/ir.rs:1190-1275`).
* Locale text/labels are joined by `lineId`, never `addr` (`crates/lute-compile/src/locale.rs:1-18`).

## `{component}#{n}` production and consumption map

1. **Produced by normalization:** `expand_use` stamps the begin sentinel with the component name and 1-based same-component ordinal in host document order; nested uses are relative to the enclosing component expansion (`crates/lute-compile/src/normalize.rs:35-50`).
2. **Carried through source provenance:** `Source.scope` stores the dot-joined enclosing segments, but `scope` is skipped from wire serialization because the resulting line identity already carries it (`crates/lute-compile/src/ir.rs:749-755`).
3. **Consumed by stage/source mapping:** the stage walker’s expansion stack and source map preserve the scope for records; `source_map.rs` documents that the scope is the identity scope (`crates/lute-compile/src/source_map.rs:89-92`).
4. **Consumed by address identity:** `assign_identity_scope` reads `LineCmd` source scope and prefixes component lines with `{prefix}.{scope}` before applying the line template (`crates/lute-compile/src/address.rs:288-327`).
5. **Consumed indirectly by lineId/voiceKey:** the emitted IDs therefore contain `component#ordinal`; locale import/export joins by the resulting lineId, and voice collision checks compare resulting voiceKey values (`crates/lute-compile/src/locale.rs:1-18`; `crates/lute-compile/src/index.rs:623-646`).
6. **Consumed by model graph:** component-expanded lines are graph `Line` nodes keyed by their final `line_id`, anchored to the host use span rather than component source span (`crates/lute-model/src/graph.rs:403-425`).
7. **Consumed by LSP:** inspected LSP features operate on parsed AST spans/cursor constructs and source-local branch/state/def references; no `component_fingerprints`, `{component}#{n}`, IR `addr`, lineId or voiceKey consumer was found in `crates/lute-lsp/src` (the feature contract is cursor/span based: `crates/lute-lsp/src/features/nav.rs:30-45`; component/param completion is vocabulary only: `crates/lute-lsp/src/features/completion.rs:147-214`).
8. **Patch/fingerprint status:** `PatchRequest` preserves `NodeKey`s, line IDs, and voice keys as separate preserve categories (`crates/lute-model/src/patch.rs:140-184`), but the inspected `patch.rs` contains no `component_fingerprints` field or producer/consumer. This is a gap, not evidence of a hidden stable fingerprint mechanism.

## Uncoded line behavior and `lute tag`

`lower.rs` carries authored `code` or the internal component `__code` into `LineCmd.code` (`crates/lute-compile/src/lower.rs:49-57`). For a normal untagged line, `address.rs` scans authored numeric codes, then assigns the next +10 code in final command order; it never writes that code back to source (`crates/lute-compile/src/address.rs:299-327`). Thus insertion before an untagged line can change its computed lineId/voiceKey, and a component’s host lines do not determine component-body codes because component back-fill occurs before match folding (`crates/lute-compile/src/normalize.rs:90-121`).

`lute tag` runs the persistent equivalent over source, by speaker and identity scope, and inserts `code="0010"`, `0020`, etc. into untagged lines (`crates/lute-check/src/tag.rs:102-132`; CLI wrapper `crates/lute-cli/src/rewrite.rs:125-129`). Once tagged, later sibling insertion leaves existing codes unchanged; force-retag is the deliberate exception and is guarded by `codesLocked` (`crates/lute-check/src/tag.rs:198-208`).

## `NodeKey`, graph and checker identity construction

`NodeKey` is only `(NodeKind, key: String)` with canonical `kind:key` serialization (`crates/lute-model/src/graph.rs:60-76`). Current graph kinds are Project, Document, Scene, Beat, Shot, Line, Choice, Quest, Objective, Reward, Entry, Occasion, Relation, State, Def, Component, Expanded, Fact, Clock and Engine (`crates/lute-model/src/graph.rs:9-58`). There are no dedicated Branch, Hub, Mark, Match, Arm, Track, Enum, Entity, Chapter, Event, Param or Use node kinds.

Construction details: documents use authored folded id or fallback relative path (`crates/lute-model/src/graph.rs:177-186`); scenes use document id (`crates/lute-model/src/graph.rs:197-200`); shots use document id plus heading (`crates/lute-model/src/graph.rs:242-254`); quests use q.id (`crates/lute-model/src/graph.rs:246-248,267-268`); objectives use `q.id.o.id` (`crates/lute-model/src/graph.rs:280-282`); rewards use declaration ordinals (`crates/lute-model/src/graph.rs:302-304,327-329`); entries use e.id and bundle beats use `doc_id.beat_id` (`crates/lute-model/src/graph.rs:342-357`); lines use final emitted lineId (`crates/lute-model/src/graph.rs:403-425`); choices use document + branch/hub id + option id (`crates/lute-model/src/graph.rs:716-757`); state, relation, fact, def, component and occasion keys use their authored/path/name spelling (`crates/lute-model/src/graph.rs:481-550,652-680`).

The checker is the source of declaration validity and uniqueness: component-cycle/param checks, branch/choice duplicate checks and id validation happen before compilation; compilation explicitly relies on checker-proven invariants (`crates/lute-compile/src/lib.rs:436-440`). It does not create a second universal identity store; many constructs remain source spans/order only.

## `lute diff` move/rename behavior

`revision.rs` hashes exact input bytes together with normalized project-relative paths and sorts those path/hash pairs into the project digest (`crates/lute-model/src/revision.rs:50-89`). Therefore pure formatting changes alter revision hashes even when semantic changes are empty; file moves also alter revision hashes because paths are included.

`diff.rs` strips `addr`, `span`, `body`, CEL authored spelling and other positional fields before semantic comparison (`crates/lute-model/src/diff.rs:101-119`). It indexes serialized command fields by `id`, `lineId` and `key` (`crates/lute-model/src/diff.rs:140-166`), then compares before/after model values by canonical NodeKey. A same-key node with changed semantic payload gets a field category; same-key node whose source file changes gets `Moved` (`crates/lute-model/src/diff.rs:453-490`; move branch `crates/lute-model/src/diff.rs:524-548`).

Consequences:

* Moving a file while retaining the same semantic NodeKey is classified `moved` (unless the model’s source lookup fails or the key is a path fallback).
* Renaming a document/parent id that is embedded in a child key produces a new key; the old key is `Removed` and the new key `Added`, not a first-class rename. This follows the key-union comparison (`crates/lute-model/src/diff.rs:500-523`) and the graph key constructions above.
* Renaming a parent whose child key is not parent-qualified can leave child keys unchanged but produce field/path effects elsewhere; there is no generalized parent-rename inference.
* Reformatting generally produces no semantic changes because spans/addrs/CEL source spelling are stripped, but the revision hashes still change (`crates/lute-model/src/diff.rs:101-119`; `crates/lute-model/src/revision.rs:50-89`).
* Reward ordinals are inherently ambiguous; `reward_ambiguities` suppresses/marks some duplicate semantic values rather than providing stable author identities (`crates/lute-model/src/diff.rs:411-440,524-542`).

## Runtime/save keys and breakage surface

The engine/session state is not a single serialized save schema in this repository, but the `World`/`Carry` structures show the keys that a save/resume implementation must preserve: persistent state map (`run.*`, `user.*`, `app.*`, `quest.*`, `entry.*`), facts, quest statuses/instances, visited scene ids, run/user spending sets, clock spend records, accepts, failed objectives and bridge queues (`crates/lute-trace/src/exec/session/world.rs:28-58`; `crates/lute-trace/src/exec/mod.rs:163-177`; `crates/lute-trace/src/exec/session/walk.rs:118-147`).

Specific identity-sensitive persisted/engine-observable keys:

* Quest id: `quest.<id>.state`, `quest.<id>.failedBy`, `quest.<id>.objectives.<oid>.done/failed`, `quest_instances[id]`, accepted quest ids and failed-objective tuples (`crates/lute-trace/src/exec/session/cadence.rs:486-506`; `crates/lute-trace/src/exec/session/quest.rs:267-275`; `crates/lute-trace/src/exec/mod.rs:297-308`).
* Entry id: `entry.<id>.read` and `entry.<id>.everRead`; user-tier `everRead` survives `newRun`, while run-tier read resets (`crates/lute-trace/src/exec/session/resolve.rs:240-252`; `crates/lute-trace/src/exec/session/step.rs:383-385`).
* Scene/beat id: `visited` is a set of canonical presented scene/bundle-beat ids (`crates/lute-trace/src/exec/session/world.rs:40-42`; `crates/lute-trace/src/exec/session/present.rs:187-190`).
* Hub/option ids: `scene.visited.<hub>.<option>` records once options (`crates/lute-trace/src/exec/machine/menu.rs:699-739`).
* Once/share/cadence ids: `spent_run`, `spent_user`, clock positions and `share_spent_by` use beat/share ids (`crates/lute-trace/src/exec/session/world.rs:43-58`; `crates/lute-trace/src/exec/session/present.rs:134-141`).
* `lineId`/`voiceKey`: runtime transcripts and localization/voice systems consume them, but the inspected session World does not put them into persistent state; changing them breaks content joins/assets rather than the core state map (`crates/lute-trace/src/exec/mod.rs:95-96`; `crates/lute-compile/src/locale.rs:1-18`).
* Marks/addrs: marks and `addr` are control-flow/build-local and are not shown as save keys; changing them can alter replay/control targets but does not directly rename a persistent save slot (`docs/runtime/execution-model.md:130-170`).

## Gaps and risks

1. **Stable component instance key is not implemented.** `{component}#{n}` is ordinal and later instances renumber when a prior use is inserted (`crates/lute-compile/src/normalize.rs:35-50`; `docs/design/architecture-direction.md:196-203`).
2. **No `component_fingerprints` producer/consumer was found** in the inspected patch/model/LSP paths; patch preserves lineIds/voiceKeys but has no component-instance fingerprint category (`crates/lute-model/src/patch.rs:140-184`).
3. **No universal identity for many authorable constructs.** Branch/hub/mark/match/arm/timeline/track/param/enum/entity/chapter/event lack dedicated graph NodeKinds; several are positional or represented only as fields/spans (`crates/lute-model/src/graph.rs:9-58`).
4. **Generated fallback identities remain edit-sensitive:** shot headings and fallback document paths, ordinal rewards, untagged line codes, and document-qualified bundle beats (`crates/lute-model/src/graph.rs:177-186,242-254,302-329,356-357`; `crates/lute-compile/src/address.rs:299-327`).
5. **Rename classification is not migration-aware.** `lute diff` reports same-key file changes as `moved`, but key-changing parent/document renames as removed+added; no explicit rename relation or save migration is produced (`crates/lute-model/src/diff.rs:500-548`).
6. **Revision hashes are path/byte hashes, not semantic identity.** Formatting and file moves change project revisions even when semantic diff is empty or only `Moved` (`crates/lute-model/src/revision.rs:50-89`; `crates/lute-model/src/diff.rs:101-119`).
7. **LSP is not an identity-preservation surface.** It resolves source-local declarations/references and UTF-16 spans, with no observed IR/component fingerprint or save-key awareness (`crates/lute-lsp/src/features/nav.rs:30-45`).
8. **Persistence is distributed and implicit.** Quest, entry, visited, once/share, facts and state keys are spread across World/Carry/session code rather than represented as a single versioned save contract (`crates/lute-trace/src/exec/session/world.rs:28-58`; `crates/lute-trace/src/exec/session/walk.rs:118-147`).
9. **No benchmark gate evidence was found in the inspected identity/model/compiler paths.** D11 states the hygiene requirement, but this inventory found no identity-specific benchmark gate implementation to cite beyond the directive (`docs/design/architecture-direction.md:243-255`).
