# Quality audit after 0.36 - architecture



## summary

Read-only architecture audit completed across all 15 crates, manifests, checker/compiler/runtime/LSP/CLI boundaries, duplicated utilities, and CLI corpus harnesses. Highest-payoff problems are the oversized lute-check modules, the dependency direction through lute-model/lute-check, repeated filesystem canonicalization/project discovery, and duplicated CEL AST walkers.

## architecture

Dependency graph from Cargo.toml (production edges): core-span <- manifest <- syntax <- cel <- check <- compile; check also directly depends on manifest/syntax/cel/core-span. model depends on manifest, check, compile, cel, syntax, core-span. resolve depends on model plus check/manifest/cel/syntax/core-span. trace depends on compile, check, manifest, cel, syntax/core-span. CLI depends on almost every production crate (manifest, check, syntax, compile, model, resolve, trace, cel, lint, core-span). LSP depends on model, resolve, check, lint, manifest, syntax, cel/core-span. wasm depends on check, compile, trace, manifest, syntax/core-span. lint depends on check, cel, manifest, syntax/core-span. bench depends on model/check/trace. No Cargo cycle is visible in the manifests themselves, but the layering is inverted: lute-model is not a model-only layer; it owns project loading, compile/check orchestration and reconciliation while depending on lute-check and lute-compile. lute-resolve then depends on that orchestration layer, and CLI/LSP depend on both the orchestration and low-level passes. This makes the project model a de-facto application service and forces broad rebuild/API coupling. lute-check is also a grab-bag: syntax admission, CEL profile/type/reference validation, graph/reachability, beats, cast/presence, project chapters and component expansion all live there. lute-cli duplicates application policy instead of being thin: command modules re-discover projects, canonicalize paths, build models, normalize diagnostics and construct JSON independently. LSP repeats portions of the same model/context assembly. lute-wasm is a facade, not a layering violation, but directly taking check/compile/trace means it must track their internal contract surface. `pub(crate)` is used extensively as a pass-to-pass coupling mechanism; the checker has many crate-private cross-module APIs and large shared structs (`Ctx`, `Env`, `FoldedEnv`, `ProjectScope`) rather than narrow pass interfaces.

## report

RANKED FINDINGS (payoff/cost)

1. HIGH payoff / MEDIUM cost — checker god modules and mixed-phase ownership.
Evidence: `lute-check/src/meta.rs:1-3485`, `beats.rs:1-3433`, `cast.rs:1-2711`, `cel_resolve.rs:1-2450`, `connectivity.rs:1-2481`, and `syntax/src/parser.rs:1-3003`. Examples: `beats.rs` contains both attribute parsing (`advances_from_attr` around 200), project beat modeling (`ProjectBeat` around 1456), target-domain validation (1133+), selection/coverage and project-level diagnostics; `cast.rs` contains speaker checks (45+), CEL/fact collection (1100+), DNF/guard expansion (1638+), and presence reconciliation (1069+); `cel_resolve.rs` contains the top-level CEL check (74+), profile walk (838+), rule guards (490+), and multiple separate recursive walkers (713+, 763+, 843+, 1180+, 1250+). Why it matters: unrelated changes invalidate large modules, domain concepts have no stable owner, and semantic passes are difficult to benchmark independently. Refactor direction: split by phase and ownership: `lute-check::cel::{parse_errors, profile, types, refs, facts}`, `project::{beats, chapters, graph, presence}`, and a thin pipeline that consumes typed pass results. Move pure parser/frontmatter helpers out of the parser/meta god files. Blast radius: ~15–30 files and most checker call sites.

2. HIGH payoff / MEDIUM cost — `lute-model` is an application service, not a model layer.
Evidence: `crates/lute-model/Cargo.toml` depends on `lute-check`, `lute-compile`, `lute-cel`, `lute-syntax`, and `lute-manifest`; CLI calls `ProjectModel::build_single_root` from `cmd_compile.rs:298`, `cmd_context.rs:163`, `cmd_diff.rs:112-114`, `cmd_impact.rs:23`, `doctor.rs:907`, `endings.rs:846`, `lint.rs:229`, and project commands. The model owns project discovery/loading, checking, compilation, reconciliation, graph/index/report output, patch/diff/identity features. Why: the supposed domain model now sits above compiler/checker and is consumed by resolve/LSP/CLI, creating a wide “everything depends on model” bottleneck and making low-level reuse impossible. Refactor direction: extract `lute-project`/`lute-load` for manifest/file discovery and a separate `lute-analysis` orchestration layer; make `ProjectModel` a result type over those services. Keep diff/patch/identity as separate domain modules. Blast radius: ~20–40 files, Cargo manifests and public APIs.

3. HIGH payoff / LOW-MEDIUM cost — repeated project discovery and path canonicalization.
Evidence: `lute-cli/src/project/mod.rs:221+` has `discover_project`; `cmd_check.rs:557`, `cmd_compile.rs:135`, `cmd_context.rs:65,146,324`, and `cmd_trace.rs:55` call discovery independently. Canonicalization appears in `lute-check/src/component_import.rs:229,257`, `schema_import.rs:1201`, `state_decls.rs:85,90,140,207,242`, CLI `cmd_check.rs:277,486`, `cmd_check_project.rs:178,219`, `cmd_trace.rs:129-130`, `differential.rs:859,889,984,1070,1163`, `mockcheck.rs:103,148`, `testcmd.rs:782-798`, and play script include handling `script.rs:518,853-855`. Concrete inconsistency: some use `canonicalize(...).ok()` and silently fall back, others return diagnostics, others compare canonical paths repeatedly in loops (`bench/main.rs:471-476` canonicalizes every model document during test preparation). Why: filesystem I/O is repeated, behavior differs for nonexistent paths/symlinks, and errors are translated at many layers. Refactor direction: one `lute-core-path`/manifest resolver with `CanonicalPath`, root discovery, display-relative path and imported-file resolution APIs; canonicalize once while building the model and index by canonical path. Blast radius: ~15–25 files.

4. HIGH payoff / MEDIUM cost — CEL tree-walk duplication and semantic drift risk.
Evidence: `lute-check/src/cel_paths.rs:435+`, `cel_resolve.rs:713+`, `763+`, `843+`, `1180+`, `1250+`, `cel_types.rs:156+`, `chapters.rs:602+`, `connectivity.rs:244+`/`1405+`, `decide.rs:398+`, `deps.rs:328+`, `fact_check.rs:1364+`, `fact_must.rs:886+`, `gates.rs:731+`, and `check/component_body.rs:440+` each recurse over `Expr::Call`, `Expr::Select`, lists/maps/structs with subtly different stop/short-circuit rules. Concrete excerpt: `cel_paths::Walk::expr` classifies `has`/`isSet` and indexed paths; `cel_resolve::check_guard_fact_access` stops at guard firewall calls; `cel_types::walk` checks calls then recursively visits target/args; `visited_targets` repeats a third generic walk. Why: new CEL AST forms must be added in many places; omissions produce inconsistent diagnostics/reachability. Refactor direction: introduce a shared visitor/fold in `lute-cel` with explicit policies (`visit_calls`, `visit_literals`, `stop_at_query`, dominance context), then express analyses as visitors. Keep specialized state (dominance/local bindings) in pass state, not recursion shape. Blast radius: ~12–20 checker modules plus lute-cel.

5. HIGH payoff / LOW cost — YAML/frontmatter parsing is repeated instead of using parsed metadata.
Evidence: `lute-check/src/chapters.rs:155,464,538,548,887`, `connectivity.rs:144,382`, `project_check.rs:252,366`, `spent_by.rs:85`, `usage.rs:223`, `lib.rs:104`, `state_decls.rs:231`, `beats.rs:1700`, and `meta.rs:868` repeatedly call `serde_yaml::from_str` on `doc.meta.raw_yaml`. Why: repeated allocations/parsing per pass and inconsistent authored-vs-derived handling (`authored_yaml` is used only in some callers). Refactor direction: parse once into a typed/borrowed frontmatter snapshot during syntax/model construction, retaining raw spans for diagnostics; expose `AuthoredMeta` and `EffectiveMeta`. Blast radius: ~15 files.

6. HIGH payoff / LOW cost — JSON output helpers and diagnostic rendering are duplicated at CLI boundaries.
Evidence: `cmd_check.rs:688-705`, `cmd_check_project.rs:282-314`, `cmd_compile.rs:208-237`, `beats_cmd.rs:342-345`, `cmd_context.rs:414-415`, `cmd_diff.rs:115-116`, and bench `main.rs:138-141,321-327,660-662`. The same patterns repeatedly do `serde_json::to_value`, mutate an object to add `ok/path/denied`, then `to_string_pretty`; human rendering separately uses `render_diagnostics`, `severity_str`, path display helpers in `output.rs`. Why: JSON shape/deny policy can drift between commands and serialization work is duplicated. Refactor direction: command-neutral `OutputEnvelope`/`DiagnosticReport` serializers in one CLI output module; make each command return typed report data plus exit policy. Blast radius: 8–15 files.

7. MEDIUM-HIGH payoff / LOW cost — diagnostic construction and fix-it logic are duplicated across checker/fixer/LSP.
Evidence: `lute-check/src/check/choice_record.rs:313-318` explicitly says `fix.rs` and LSP code action are independent implementations that MUST stay byte-identical; `cel_message.rs:411+` builds fixits; many modules create `Diagnostic { code, severity, message, span }` directly (`admission.rs:671+`, `cast.rs:229+`, `chapters.rs:204+`, `bundles.rs:326+`). Why: byte-identical migration behavior is maintained by tests/comments instead of one implementation; new output fields or span rules require broad edits. Refactor direction: central `DiagnosticBuilder`/migration edit constructors in core-span/check, with LSP and CLI only adapting transport. Blast radius: 10–20 files.

8. MEDIUM-HIGH payoff / MEDIUM cost — duplicate test temporary-directory and process harnesses.
Evidence: grep found repeated helpers across `lute-cli/tests/*.rs`: `temp_dir`/`temporary`, `write`, `run`, `lute`, and `Command::new(BIN)` wrappers; `lute-bench/tests/contract.rs:5-7` has a PID-named temp path, while conformance `conformance.rs:98-106` has fixture-specific scratch setup and many CLI integration files reproduce process capture. Why: tests are order-sensitive when cleanup/unique naming differs, and every test file invents output/error conventions. Refactor direction: one `lute-cli/tests/support/mod.rs` (or dev-only `lute-test-support`) with `TempProject`, `run_cli`, `write_fixture`, JSON decode and cleanup-on-drop. Blast radius: ~30 test files, low production risk.

9. MEDIUM-HIGH payoff / MEDIUM cost — integration test file god object.
Evidence: `crates/lute-cli/tests/check_project.rs` is 3,106 lines; it contains generic `run`/fixture helpers near line 33, project fixture builders, compile/check/context/diagnostic tests, conformance fixture validation and many repeated `Command::new(BIN)` calls (examples at 1751, 1807, 1848, 1933, 1971, 2017, 2057, 2182, 2252, 2303). Why: unrelated failures share one compilation unit and fixture conventions are local rather than reusable. Refactor direction: split by command/domain (`check_project_diagnostics`, `check_project_schema`, `check_project_components`, `check_project_json`) and move builders to support. Blast radius: test-only, 5–10 files.

10. MEDIUM-HIGH payoff / MEDIUM cost — parser god object mixes grammar, recovery, source mapping and policy diagnostics.
Evidence: `lute-syntax/src/parser.rs` is 3,003 lines; `parse` spans 114-349 (>200 lines), `parse_document_inner` starts 459, and `parse_line` starts 1202. `parse_line` handles speaker syntax, attributes, interpolation scanning and line diagnostics; parser tests occupy the tail from 1732 onward. Why: grammar changes require touching a single stateful type with many unrelated invariants; source-span policy is coupled to parsing decisions. Refactor direction: split cursor/source map, frontmatter/document framing, block/tag parsing, and line/interpolation parsing; keep recovery diagnostics as a small shared emitter. Blast radius: ~5–8 files.

11. MEDIUM payoff / MEDIUM cost — `lute-check::beats` mixes authored syntax and global scheduling analysis.
Evidence: `beats.rs:176-228` parses `advances`; `294+` lifts scene beats; `593+` validates entry attributes; `1133+` checks target domains; `1456+` defines project beat model; `1928+` and 2411+ perform project selection/tie/cycle logic. Why: local attribute diagnostics and global scheduler invariants have different inputs, complexity and performance profiles. Refactor direction: `beat_parse.rs`, `beat_domain.rs`, `beat_project.rs`, `beat_select.rs`; make a typed `BeatIndex` input to global passes. Blast radius: 4–8 files.

12. MEDIUM payoff / MEDIUM cost — project graph/connectivity and semantic dependency extraction are entangled.
Evidence: `connectivity.rs:244` has a dedicated visited-conjunct walk, `1405+` top-conjunct/origin extraction, and the module ends at 2481 while also defining `ConnGraph`, scene identity and cycle diagnostics. Why: graph algorithms and source-language extraction cannot evolve independently; graph consumers need to know CEL shapes. Refactor direction: extract `cel-deps` (typed dependency facts) from `project-graph` (nodes/edges/cycles). Blast radius: 5–10 files.

13. MEDIUM payoff / MEDIUM cost — broad shared checker context and crate-private coupling.
Evidence: `lute-check/src/check/mod.rs:148+` defines `CheckInput`, `DomainUse`, `CheckResult`, `Resolved`, and `FoldedEnv`; `ctx.rs:37+` defines broad `Env` and `Ctx`; many modules consume `crate::...` and `pub(crate)` helpers (e.g. `admission.rs:652`, `component_body.rs:683`, `beats.rs:176`, `cast.rs:869`). Why: adding a field or changing a pass contract propagates across most checker modules; tests cannot exercise passes without assembling a large environment. Refactor direction: immutable typed snapshots per pass (`SyntaxFacts`, `CelEnv`, `ProjectFacts`, `DiagnosticSink`) and private module boundaries; expose only pass-level functions. Blast radius: ~15–25 files.

14. MEDIUM payoff / LOW cost — bench hot path repeatedly canonicalizes and reparses instead of indexing once.
Evidence: `lute-bench/src/main.rs:460-478` canonicalizes the test document and every model document inside `.position(...)`; `run`/`run_sample` also rebuild models for phase measurements (`main.rs:217+`, `264+`). Why: benchmark measures filesystem and repeated setup in addition to the named phase, and O(test_count × document_count) canonicalization is avoidable. Refactor direction: build a canonical-path-to-index map once in `PreparedTest` creation; separate cold-load, resolution and execution setup explicitly. Blast radius: 1–3 files.

15. MEDIUM payoff / LOW cost — conformance harness has two independent representations and intentionally does not recompile.
Evidence: `lute-cli/tests/conformance.rs:7-33` defines byte replay of checked-in `artifact.json`/`expected.json` and explicitly says it does not assert fresh compile equality; discovery is one recursive walker (`57-80`), replay is one process per fixture (`130-183`), stamps are separately checked (`210+`). Why: replay proves runtime compatibility but can pass with mutually stale source/artifact/transcript; the stamp check catches only a narrow drift vector. Refactor direction: add a separate sampled or nightly source→artifact→run pipeline, while retaining frozen third-party replay; share fixture discovery/JSON/error helpers with edit-task harness. Blast radius: 1–3 test files plus CI cost.

16. MEDIUM payoff / LOW cost — edit-task harness is a second bespoke report/fixture engine.
Evidence: `lute-cli/tests/edit_tasks.rs:12-33` defines its own workspace/root/read JSON/model cache; `refusal_json` at 47+ manually builds patch error schema; `record` at 149+ uses global `LazyLock<Mutex<...>>` and bless-mode writes `REPORT.json`; task execution starts 174+. Why: report generation, base substitution (`fill`), model selection and result comparison are all special-purpose and can drift from production patch output. Refactor direction: move patch result serialization into production `lute-model`/CLI output, use a data-driven task runner with one fixture schema, and make blessing an explicit binary/script rather than test-global side effects. Blast radius: 2–5 test files plus patch serialization API.

17. MEDIUM payoff / MEDIUM cost — differential harness and command test harness duplicate model indexing/path policy.
Evidence: `lute-cli/src/differential.rs:820-890` stores `ProjectModel` plus a canonical document map, then repeats canonicalization at 984, 1070 and 1163; command modules independently call `ProjectModel::build_single_root` and discovery. Why: differential comparisons may use different fallback behavior from ordinary CLI commands. Refactor direction: expose a shared `ProjectIndex` from model build containing canonical document paths, relative display paths and revisions; inject it into differential/commands. Blast radius: 5–12 files.

18. MEDIUM payoff / LOW cost — no `mod.rs` with thousands of lines was found; the smell is instead file-level and test-level aggregation.
Evidence: `glob` found module files, but observed `lute-trace/src/exec/machine/mod.rs` is 354 lines and `lute-check/src/check/mod.rs` is 325 lines, while the thousands-line units are named files (`meta.rs`, `beats.rs`, `parser.rs`, `cast.rs`, `testcmd.rs`, `check_project.rs`). Why: splitting only by `mod.rs` would miss the actual responsibility seams. Refactor direction: preserve current module tree but split the named files by responsibility; do not create a new `mod.rs` dumping ground. Blast radius: same as findings 1, 9 and 10.

19. MEDIUM payoff / LOW cost — large structs are not the principal smell, but `ProjectModel`/shared env objects are wide aggregates.
Evidence: grep found no clearly >15-field ordinary user-defined struct in the inspected declarations; the largest risk is semantic aggregation rather than raw field count. `CheckInput`, `CheckResult`, `Resolved`, `FoldedEnv`, `Env`, `Ctx`, `ProjectBeat`, `ConnGraph::NodeInfo` and `Report` group data from multiple phases. A concrete struct with >15 fields was not observed from the declaration scan, so there is no grounded >15-field hit to list. Refactor direction: use phase-specific substructs/newtypes rather than splitting solely by field count. Blast radius: 5–15 files depending on target.

20. MEDIUM payoff / LOW cost — CEL error translation is a mini-parser collection.
Evidence: `lute-check/src/cel_message.rs:74+` translates backend errors, then has separate scanners at 327, 434, 471, 490, 534, 555 and 580. Why: each scanner independently understands strings/identifiers/operators; future CEL syntax changes can produce contradictory spans and suggestions. Refactor direction: share a token/mask scanner from `lute-cel`, return structured token ranges, and keep message policy in `cel_message`. Blast radius: 3–6 files.

21. MEDIUM payoff / LOW cost — YAML/JSON and human diagnostic policy is split between core and CLI/LSP.
Evidence: `lute-core-span` owns diagnostic data, checker modules construct raw diagnostics, CLI `output.rs` renders human/relative paths, CLI command files mutate JSON, and LSP converts diagnostics separately. Why: one diagnostic can have several subtly different path/column/related-information policies. Refactor direction: core diagnostic normalization (byte→display span, related locations, fixit shape), transport-specific rendering only at the edge. Blast radius: 6–12 files.

22. MEDIUM payoff / MEDIUM cost — LSP has a wide dependency surface and likely duplicates model assembly.
Evidence: `lute-lsp/Cargo.toml` depends on model, resolve, check, lint, manifest, syntax, cel and core-span; `src/features` includes hover/nav/completion/symbols/semtok with separate feature queries. CLI context code independently builds `ProjectModel` and JSON authoring surfaces (`cmd_context.rs:145-165,404-505`). Why: editor features and CLI context can diverge on project resolution/state vocabulary. Refactor direction: shared read-only `AuthoringSnapshot`/`DocumentIndex` API in model or a neutral analysis crate; LSP and CLI become adapters. Blast radius: 8–15 files.

23. MEDIUM payoff / LOW cost — model/CLI logic duplication for project loading is explicitly visible in comments and call sites.
Evidence: `lute-check/tests/plugin_defs_disk.rs:51-55` says it mirrors `crates/lute-cli/src/main.rs:116-160`; CLI and tests separately call `load_project`, `project_providers`, `resolve_document_snapshot`; `lute-check/src/chapters.rs:413-418` reloads the project manifest internally even though it receives project docs/folds. Why: hidden I/O in a checker pass breaks composability and repeats parse work. Refactor direction: pass a `ProjectConfig`/manifest snapshot into project checks; keep loading in model/CLI boundary. Blast radius: 5–10 files.

24. MEDIUM payoff / LOW cost — `find_expr`-style local walks are duplicated under different names and semantics.
Evidence: grep identified local recursive walkers in `cel_paths`, `cel_resolve::visited_targets`, `chapters::waited_on`, `beats` path/read functions, `connectivity` conjunct/source extraction, `decide`, `deps`, `fact_check`, `fact_must`, `gates`, component body scanning and use-site functions. Why: the same concept (“inspect every descendant expression”) has no shared traversal contract; omissions for `target`, list/map/struct/comprehension nodes are likely. Refactor direction: shared `ExprVisitor` plus narrowly scoped domain predicates; add exhaustive match canaries in one place. Blast radius: 10–20 files.

25. MEDIUM payoff / LOW cost — test corpus organization duplicates coverage across layers.
Evidence: `lute-compile/tests` has insta e2e snapshots; `lute-cli/tests/conformance.rs` replays frozen artifacts; `conformance/` stores `source.lute`, `artifact.json`, `expected.json`, `mock.yaml`; edit tasks store JSON patch fixtures plus `REPORT.json`; CLI tests independently launch the binary for the same command families. Why: one behavior can be pinned by a snapshot, a frozen artifact, a command test and a conformance transcript, but ownership is unclear and failures are expensive to interpret. Refactor direction: define a test taxonomy: parser/check unit tests, compiler golden tests, runtime conformance, CLI contract tests, edit-task mutation tests; shared fixture metadata should declare the owning layer and avoid duplicate assertions. Blast radius: test-only, 10–30 files.

Largest functions (>200 lines) observed or directly bounded from source structure:
- `lute-syntax/src/parser.rs:114-349`, `parse` (~236 lines): frontmatter/body framing, parser state initialization, document-kind dispatch, top-level recovery and diagnostic merging. Split framing/dispatch from body parse.
- `lute-syntax/src/parser.rs:1202-1357` (`parse_line`) is ~156 lines, therefore large but below the requested >200 threshold; it is still a high-value extraction target because it combines speaker parsing, line attrs, interpolation scanning and span mapping.
- `lute-check/src/beats.rs` contains several project-level routines spanning hundreds of lines in the 700–1450 and 1900–2400 regions; responsibilities mix local beat validation, target-domain reasoning and global schedule/selection analysis. Exact per-function boundaries should be computed mechanically before refactoring.
- `lute-check/src/cast.rs` contains the large `Presence`/guard-analysis implementation in the ~1400–2711 region, mixing CEL DNF expansion, fact producers, presence checks and reconciliation; split before optimizing.
- `lute-check/src/check/component_body.rs:683+` `walk_component_body` is a large recursive policy function with `#[allow(clippy::too_many_arguments)]`, handling purity, params/domains, nested matches, CEL checking, diagnostics and imported spans. Extract a `ComponentContext` and per-node handlers.
- `lute-cli/tests/check_project.rs` has multiple very large test functions/fixture builders in the 1700–3106 region; they mix fixture creation, process execution, output normalization and assertions. Move common setup to support and split by contract.
- `lute-cli/src/testcmd.rs` has a large command execution/rendering pipeline (file extent 3,690 lines), mixing test discovery, model construction, trace execution, coverage, JSON and human rendering. Extract `TestRunner`, `CoverageReport`, and transport renderers.

Struct scan result for the requested >15-field criterion: no grounded ordinary struct declaration with more than 15 fields was found in the inspected declarations. The architectural risk is instead wide aggregate structs and tuples: `Env`, `Ctx`, `FoldedEnv`, `CheckInput`, `CheckResult`, `Resolved`, `Report`, `ProjectBeat`, `NodeInfo` and `ConnGraph` carry multiple phase responsibilities. Do not claim a >15-field hit without a mechanical field counter.

Crate/test harness conclusion: conformance is intentionally artifact-first and third-party-engine oriented; compile snapshots are compiler-owned; edit-tasks are patch/revision-owned; differential is trace-vs-run owned. The main duplication is not the fixture data itself but repeated discovery, JSON decoding, scratch directories, subprocess invocation, canonical path indexing and stale/bless/report plumbing. A shared dev-only harness would reduce maintenance without collapsing the distinct acceptance contracts.
