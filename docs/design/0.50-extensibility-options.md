# Lute 0.50 / 0.51 — authoring extensibility: options and recommendations

Decision input for the orchestrator (owner delegated every design choice for 0.50 on 2026-10-25).
Inputs: issues #159 #162 #163 #164 #165 #166 #169 #170 #172 #176 (authoring half) #177, each with
a 0.48.1 reproduction written from a large real port; the triage note
[`2026-10-23-lute-0.49-dogfood-triage.md`](../superpowers/notes/2026-10-23-lute-0.49-dogfood-triage.md)
("0.51" table, which the owner's 2026-10-25 renumbering moves to 0.50); the ADR
[`architecture-direction.md`](./architecture-direction.md); the shipped 0.49.0 surface
(spec [`0.49.0.md`](../proposals/scenario-dsl/0.49.0.md), website docs). Code facts are cited at
`main` = v0.49.0 `f34f141f`. Examples use neutral names (`acme.stage`, `mira`, `theo`).

Each section gives the problem, two or three options with sketches, cost, interactions and a
recommendation. §12 groups the items into **0.50** and **0.51**; §13 is the summary table.

## 0. Criteria and shared findings

Every recommendation is judged by, in order:

1. **Composition first (D4).** An existing construct composed, then a module extension, then a
   new module. A new core keyword must show the first three fail.
2. **One spelling per concept.** No second declaration site for something that already has one.
3. **Static analysis stays sound.** No edge the analyses cannot see; no `proven` through a hidden
   edge; termination stays provable (the "total" claim on the landing page).
4. **D13.** The runtime owns IR execution, state, facts, quests, occasion selection and stage
   state; the host owns raising occasions, plugins, settlement; nobody but the player owns
   presentation. A design that puts narrative control flow in the host, or presentation in the
   runtime, is rejected.
5. **D5 / D6.** A meaning-changing IR field gets a semantic id in `requiredSemantics`
   (`crates/lute-compile/src/semantics.rs` `REGISTRY`); an additive descriptive field does not.
   Clean cutover; the corpus migrates in the same change.
6. **Smallest surface; cost.** Crates touched, contract change, engine/player impact.

Findings that several sections rely on:

- **Effects already exist as a declared vocabulary.** A directive's `effects:` declares `writes`,
  `asserts`, `retracts` (`lute-manifest/src/schema/directives.rs` `DirectiveEffects`); the
  compiled `plugin` record carries resolved `asserts`/`retracts`; the runtime applies them
  (`lute-runtime/src/machine/plugin.rs:319`); every fact analysis reads them as `::assert`s. A
  reward kind has only `target`, `attrs`, `credits` (`schema/vocabulary.rs` `RewardKindBody`),
  and the runtime already applies `credits` at the grant (`machine/quest.rs:1022`). Grants fire
  before the lifecycle handler body of the same transition (`docs/runtime/quest-lifecycle.md`
  "Order within one owner"). → #169 and #170 extend this one vocabulary.
- **The host can only raise occasions.** `lute_runtime::Input` has `raiseOccasion`, `choose`,
  `bridgeResult`, `advanceClock`, `hostWrite`, `worldEvent`, `newRun` (`runtime.rs:97`); there is
  no "present scene X" input, and D13 lists "raising occasions" as a host duty. → #170.
- **`<choice>`/`<hub>` records already carry a stamp.** `Command::stamp_mut` returns `Some` for
  `Choice` and `Hub` (`lute-compile/src/ir.rs:2129`), so a `stamps` object is already legal on
  those records in the 0.49 IR schema; `ChoiceOption`/`HubOption` have none. The refusal is in the
  checker: logic tags have closed constant attribute tables (`lute-check/src/logic_attrs.rs`, decision
  D-J "logic tags are not plugin-extensible"). → #164.
- **Stamp declarations are keyed by name only** (`CapabilitySnapshot.stamp_attrs:
  BTreeMap<String, AttrDecl>`, `lute-manifest/src/snapshot.rs:59`), and the directive checker
  consults them as a fallback after the directive's own attributes (`lute-check/src/directives.rs:255`).
  `required:` on a stamp is parsed and never read. → #163.
- **Lints read the AST, not the IR.** `lute-lint` computes six metric tables from
  `lute_syntax::ast::Document` (`metrics.rs`), runs in the LSP without `lute-compile`, and its CEL
  fragment supports `&&`/`||`/`!`/ternary, `in`, indexing, `size()` and scalar operators
  (`eval.rs:171`) — no string member functions. Lints never touch `capabilitySnapshot`. → #172, #177.
- **`userName` is hard-coded in the parser** (`lute-syntax/src/ast.rs:736` →
  `InterpKind::Reserved`); the IR placeholder `{ kind: "reserved", token }` is already generic, and
  the runtime keeps a reserved token verbatim for the host/player (`machine/format.rs:21`). → #162.
- **Choice `text=` is already a localized attribute**: lineId, `texts`, placeholders
  (`ChoiceOption`), exported by `lute loc export`, merged by `--locale-bundle`, checked by
  `W-L10N-MISSING`/`STALE` (`lute-compile/src/locale.rs`). Line `code` is back-filled at compile
  and persisted by `lute tag`. → #165.

## 1. #163 + #164 — attributes on named core surfaces (one mechanism)

### Problem

A plugin can add attributes to core surfaces only through `stampAttrs`, which are cross-cutting:
every directive and every content line takes every stamp. So `voiceAssetId` is accepted on `::bg`,
`::sfx`, `::end`; `required: true` on a stamp loads and is never enforced; and one name cannot have
two types on two surfaces (#163). The logic elements `<branch>`, `<hub>`, `<choice>` take no
plugin attribute at all — `E-UNKNOWN-ATTR` even for a stamp the docs call "admissible on every
directive" — so a host-side option id or menu type is split into companion passthrough directives
(`::interaction` before the branch, `::option` first in each arm) that hosts must re-join (#164).
The triage asks for one mechanism for both.

### Options

**A. Scope a stamp with `on:` (recommended).** The existing `stampAttrs` entry gains an optional
`on:` list of surfaces. Absent `on:` keeps today's cross-cutting meaning. The surface vocabulary is
closed: `line`, `branch`, `hub`, `choice`, and any directive tag in the resolved snapshot that has a
stamp carrier (core staging/control directives and plugin directives; `jump`/`label`/`clear` are
`UNSTAMPED_DIRECTIVES` and refused).

```yaml
# plugins/acme.stage/stampattrs/columns.yaml
stampAttrs:
  - { name: voiceAssetId, type: { providerRef: voice }, required: true, on: [line] }
  - { name: assetName,    type: string, on: [bg, actor] }
  - { name: menuType,     type: { enum: [plain, timed, minigame] }, on: [branch, hub] }
  - { name: optionKey,    type: string, required: true, on: [choice] }
  - { name: cue,          type: string }                     # cross-cutting, as today
```

```lute
<branch id="route" prompt="Which way?" menuType="plain">
  <choice id="goLeft" text="Left" optionKey="L1">
    @mira{voiceAssetId="VO.mira.0010"}: Left it is.
  </choice>
</branch>
```

- **Load rules** (`E-PLUGIN-PARSE` at the entry): an unknown surface (did-you-mean); `on: []`;
  `jump`/`label`/`clear`; `required: true` without `on:` ("a stamp required on every record is not
  a column — name its surfaces with `on:`"). Assembly (`E-PLUGIN-STAMP-CONFLICT`, new): two
  entries with the same name whose surface sets overlap (a cross-cutting entry overlaps every
  set); disjoint sets may give one name two types, which is what #163 asks.
- **Check rules.** Resolution order stays strict: the surface's own declarations, then the stamp
  entries whose `on:` contains the surface (or have none), then `E-UNKNOWN-ATTR`. A stamp used
  outside its `on:` is `E-UNKNOWN-ATTR`: `` `voiceAssetId` is a stamp for `line` only (`acme.stage`); `::bg` does not take it ``.
  A missing `required` stamp is `E-MISSING-ATTR` at the surface's head (the code a missing declared
  directive attribute already draws, `directives.rs:372`). Logic tags: `close()` in
  `logic_attrs.rs` consults the snapshot for `branch`/`hub`/`choice` before its constant table, so
  core keys still win and a stamp named like one (`id`, `text`, `when`, `into`, `once`, `exit`,
  `prompt`, `timeout`, `default`) is refused at assembly like the existing core-stamp reservation
  (`E-PLUGIN-RESERVED-STAMP-ATTR`, the reserved list extended per surface).
- **IR.** `choice`/`hub` records already carry `stamps`. `ChoiceOption` and `HubOption` gain an
  optional `stamps` object (omitted when empty). Additive; descriptive (the runtime does not act on
  stamps), so no semantic id.
- **Event contract.** The choice/hub await the runtime emits passes the record's `stamps` and each
  option's `stamps` through to the player and host, beside and never merged into other fields
  (the 0.49 rule for plugin events). Additive.
- **`capabilitySnapshot`**: `on:` is printed only when set (the hand-written `Debug` pattern used
  for `credits`/`forbidden`), so manifests without it keep their stamp.

**B. A second export `extends:` keyed by surface** (the issue's sketch: `extends: { bg: [...],
line: [...] }`). Same check behaviour, but it is a second declaration site for "a plugin attribute
on a core surface" beside `stampAttrs`, and a cross-cutting attribute would still live in the other
file. Rejected: two spellings for one concept.

**C. Open the logic tags to plain directive-style `attrs:` declared per tag** (a plugin "extends
directive `choice`" block, `DirectiveDecl`-shaped). Gives per-surface typing but makes
`<choice>` look like a directive the plugin co-owns (`lower:`, `effects:`, `bridge:` would all be
meaningless there and need refusal), and still leaves `required:` on `stampAttrs` silently ignored.
Rejected.

### Cost (A)

- Crates: `lute-manifest` (schema `on:`, snapshot index `name → [(surfaces, decl)]`, assembly
  conflict check, reserved names per surface), `lute-check` (`directives.rs` fallback,
  `content_line.rs`, `logic_attrs.rs` for three tags, required check), `lute-compile` (populate
  option stamps; branch/hub stamps through the existing `Stamp`), `lute-runtime` (pass option
  stamps in the choice await), `packages/player` (port types), schemas `lute-ir`/`lute-events`,
  `lute-lsp` completion (surface-filtered stamps), docs.
- Contract change: **yes, additive** — IR `ChoiceOption.stamps`/`HubOption.stamps`, event
  pass-through, plugin manifest key `on:`. No semantic id.
- Analysis: none (stamps are inert to every analysis). D14: the surface index is built once in
  the snapshot, not per document.
- Breaking (D6): a manifest with `required: true` on a cross-cutting stamp now fails to load
  (it was a silent no-op). The corpus has none to migrate unless the port's plugin is in it.

### Interactions

- #177: with stamps on `<branch>`/`<choice>`, the repro's marker/option pair collapses into
  attributes of one element and its parent, which a node lint can relate (§8).
- #165: a localizable value is not a stamp (§3); `type: text` is refused on stamps.
- #172: node rows expose authored attributes, stamps included.
- #166: a line-scoped sprite stamp is now typed per surface, but it still does not stage (§4).

### Recommendation

**A** — `on:` on `stampAttrs`, `required` enforced on scoped stamps and refused on cross-cutting
ones, surfaces `line` / directive tags / `branch` / `hub` / `choice`. One declaration site, one
resolution order, IR change additive. Size **M**. **0.50**, first slice of the release
(other items read its surface index).

## 2. #162 — project-declared host interpolation tokens

### Problem

Line text may interpolate a declared state path, a def, or the one reserved host token
`{{userName}}`; any other `{{token}}` is `E-CEL-PROFILE`. Engines that substitute other render-time
host values (a nickname, a platform label, a currency name) cannot declare them; the escape
`\{{token}}` means "never substitute", so the token never reaches the player.

### Options

**A. A `hostTokens` plugin export; `lute.core` declares `userName` (recommended).**

```yaml
# plugins/acme.stage/hosttokens/tokens.yaml
hostTokens:
  playerName: { type: string }
  platform:   { type: { enum: [ios, android, web] } }
```

- The parser stops special-casing `userName`: a single bare identifier interpolation becomes an
  unresolved token, and the checker classifies it against the snapshot's `hostTokens` (an
  identifier can never be a state path, which always has a tier root, so nothing is ambiguous).
  An undeclared one stays `E-CEL-PROFILE`, its hint listing the declared tokens.
- Types `string | int | { enum }` drive modifier typing exactly as `userName` does today
  (`:capitalize` on text, `:ordinal` on `int`, `E-REF-TYPE` otherwise).
- Load errors: a token named like a tier or a reserved root (`run`, `user`, `scene`, `app`,
  `season`, `occasion`, `quest`, `entry`, `clock`, `prev`) or not an identifier; a duplicate across
  plugins (the existing cross-plugin duplicate rule).
- IR: placeholders keep `{ kind: "reserved", token }`. The artifact's environment declaration
  (D12) gains `hostTokens: [{ name, type }]`, omitted when only `userName` is declared — so
  existing artifacts are byte-identical. `capabilitySnapshot` folds the export.
- Lint counts a token as one word (already true for any interpolation).

**B. Project schema `hostTokens:`** (the issue's sketch). Same mechanics, but a host token is a
promise about what the *engine* substitutes — capability, like occasions and events, which are
plugin-only. A schema-level declaration lets a project promise substitution the engine pack does
not perform, and the snapshot hash would not move. Rejected.

**C. Keep one token; document `owner: engine` state paths** (`{{app.playerName}}`, the issue's
workaround). Works and is checked, but puts render-only values into runtime state and saves (the
host must `hostWrite` them, a save carries a stale nickname). Kept as the recipe for values a
condition must also read; not the answer for render-only values.

### Cost (A)

`lute-manifest` (export, snapshot), `lute-syntax` (drop the literal), `lute-check`
(`check/interp.rs`, `defassign.rs`, `deps.rs`, `quest_refs.rs` already ignore reserved),
`lute-compile` (env declaration), `lute-lsp` completion, player (substitution table keyed by token,
not a hard-coded `userName`), docs. Contract change: **yes, additive** (`hostTokens` env entry,
manifest export). Analysis impact: none. Size **S**. **0.50**.

## 3. #165 — localizable text in plugin directive attributes

### Problem

A passthrough directive can carry player-visible text (a banner, a toast, a title card), but its
attributes are plain strings: no `lineId`, absent from `lute loc export`, not merged by
`--locale-bundle`, invisible to `W-L10N-MISSING`/`W-L10N-STALE`. Ports carry per-language copies
as stamps (`textKo`, `textEn`) that nothing checks.

### Options

**A. Attribute type `text` (recommended).** A directive attribute (not a stamp) may be typed
`text`. Its value takes the inline grammar of `<choice text=…>` (interpolation, modifiers,
`\{{`), the exact path a choice label already takes.

```yaml
directives:
  - name: banner
    attrs:
      - { name: text, required: true, type: text }
```

```lute
::banner{code="0010" text="Welcome to the hall, {{playerName}}"}
```

- **Identity (D8).** A directive with a `text` attribute takes the core `code=` attribute the way a
  content line does: absent, it is back-filled deterministically at compile, and `lute tag`
  persists it. `lineId` = `{prefix}.{tag}_{code}.{attr}` (the line template's prefix, so project
  `identity:` templates apply). Position is never identity.
- **IR (additive).** The `plugin` record keeps `fields.text` as the source-language string
  (unchanged for hosts that ignore localization) and gains `lineIds: { <attr>: lineId }`,
  `texts: { <attr>: { <locale>: text } }` and `placeholders: { <attr>: [...] }`, each omitted when
  empty. Descriptive; no semantic id (the player picks the locale text as it does for options).
- **Tooling.** `loc export` rows `kind: "directive"` with `tag` and `attr`; `loc import` /
  `--locale-bundle` merge by lineId; `W-L10N-MISSING`/`STALE` and `E-L10N-MODIFIERS` apply
  unchanged; `E-DUP-VOICEKEY`-style duplicate lineId check covers them.
- **Load rules.** `text` on a stamp, on a bridge-call attribute, or with a `default:` is
  `E-PLUGIN-PARSE` (a stamp has no identity of its own; a default would be untranslatable source).
  A `lower: { record }` directive cannot bind a `text` attribute (`E-LOWER-RECORD-FIELD`): staging
  records carry no localized text.

**B. Composition: write player-visible text as a content line** (`@system{textStyle="banner"}:
Welcome…`, plugin bits as line stamps). Fully localized today, zero core change, and D13-clean
(presentation of `textStyle` is the player's). It fails for a directive that carries two texts
(title + subtitle) or text plus non-line semantics (a host panel with an asset and a result key),
and it makes the dialogue backlog show host UI captions. Kept as the documented recipe for
single-caption banners; not sufficient alone.

**C. A per-attribute `localize: true` flag on `type: string`.** Same mechanics as A under a flag
instead of a type. A type is the better carrier: it also selects the inline grammar and the
placeholder typing; a flag on `string` would make `string` mean two grammars.

### Cost (A)

`lute-manifest` (type), `lute-check` (inline grammar on the attribute, `code` admission on such
directives), `lute-compile` (`address.rs` lineIds, `locale.rs` merge, `lower.rs`), `lute-cli`
(`loc.rs` export/import, `tag`), runtime (pass `texts` through on the plugin event), player (locale
selection), schemas, docs. Contract change: **yes, additive**. Analysis: none. Size **M**. **0.51**
(isolated, safe, but not blocking; keeps 0.50 balanced).

## 4. #166 — a line that stages its speaker; per-project warning levels

Two separate questions.

### 4a. A content line staging its speaker

**Problem.** Some sources show the speaker's sprite from the dialogue row itself. Ported, a row
after a declared exit draws `W-STAGE-ABSENT` ("stages someone who is not present") in very large
numbers.

**Options.**

- **A. Port with the existing spelling (recommended).** The importer emits a staging record
  before a row that shows a speaker who is off stage: `::actor{character="mira"}`, or a plugin
  directive lowered to `actor` that carries the sprite id (`lower: { record: actor, fields: … }`,
  stage meaning follows the lowered kind since 0.45). The importer has the data (it knows the row
  shows a sprite). This is also what the runtime needs: under D13 the runtime owns who is on
  stage, and the player shows a sprite because an `actor` record says so.
- **B. A stamp flag `stages: speaker`** (`{ name: assetId, type: string, on: [line], stages:
  speaker }`). The checker would treat the line as an implicit re-entrance. To keep the runtime's
  stage state in step, the compiler must then inject an `actor` show before the line (the
  first-line implicit-entrance injection, extended to "currently off stage"). Cost: stage model in
  `lute-check` and `lute-compile/src/stage.rs`, a new injected-record provenance, conformance; and a
  second spelling of "show this character" beside `::actor`.
- **C. Frontmatter `staging: implicit`** (every off-stage speaker re-enters on their line). A
  per-document dialect of the stage model; the same injection cost as B, applied blindly, and it
  silences the hand-authored case too.

**Recommendation: A; B and C not developed** (D4: composition works; one spelling for "show a
character"). Deliverable: a recipe in the migration guide (EN + KO) and the `W-STAGE-ABSENT` hint
naming the plugin-lowered `actor` form. Size **S** (docs).

### 4b. Silencing or re-levelling a `W-` code per project

**Problem.** `lute check` only promotes (`--deny`, `--deny-warnings`); `lute.lint.yaml` configures
`L-*` rules and refuses `W-*` ids (`E-LINT-CONFIG`). A port cannot keep a warning for its
hand-authored scenes while muting it on imported ones.

**Options.**

- **A. `diagnostics:` in `lute.project.yaml` (recommended).** The project contract already lives
  there (`constraints:`, #186's decision); this is the check-side analogue of lint `rules:`.

  ```yaml
  diagnostics:
    W-DISPLAY-NAME-DUP: error
    W-STAGE-ABSENT: { level: off, paths: ["scenes/imported/**"] }
  ```

  Levels `off | info | warn | error`; `paths:` optional project-relative globs (the lint `ignore`
  glob syntax). Only `W-*` codes: an `E-*` (an error is a contract violation, never optional) or
  an `L-*` (configured in `lute.lint.yaml`) is a manifest diagnostic naming the right place.
  Applies to `check`, `check --project`, `lint`'s `W-` findings, `compile` diagnostics, the LSP.
  CLI `--deny CODE` naming a code still promotes it (explicit beats config); `--deny-warnings`
  does not resurrect an `off` code. Every summary line counts suppressed findings
  (`… 0 warning(s), 212 suppressed by lute.project.yaml diagnostics`) and `--json` lists them by
  code, so silencing stays visible (D9: nothing is hidden without saying so).
- **B. Allow `W-*` ids in `lute.lint.yaml` `rules:`.** One file for levels, but it couples `check`
  to the lint config and makes the lint file a second home for checker contracts. Rejected.
- **C. Inline suppression comments** (`<!-- lute-allow W-STAGE-ABSENT -->`). Per-site precision,
  but a port would emit thousands, and a second channel of silence spread through content.
  Not now; revisit if `paths:` proves too coarse.

**Cost (A):** `lute-manifest` (project key, validation), `lute-cli` (one severity pass in the shared
diagnostic sink used by every command's envelope), `lute-lsp` (same pass), docs. Contract: CLI JSON
envelope gains a `suppressed` count (additive). Size **S**. **0.50**.

## 5. #169 — reward kinds that assert / retract facts and accept quests

### Problem

Some rewards mean a fact ("unlocking a character" means the player knows them) or accept a quest
(a reward whose meaning is "offer quest X"). `rewardKinds` can only `credits:` a state path, so
content gated on a reward-produced fact is a false `E-QUEST-UNREACHABLE` ("no producer"), the
workaround (`reserved: true` relation) blinds `lute scenario knowledge`; and an accept-driven quest
taken up by a reward is a false `W-QUEST-NEVER-ACCEPTED` with no `[accept]` edge in the scenario
graph. The faithful spelling (`::accept` / `::assert` in `<on event="questComplete">`) shows the
analyses already handle the meaning; only a reward *kind* (data tables) cannot say it.

### Options

**A. `effects:` on reward kinds, the directive vocabulary (recommended).**

```yaml
rewardKinds:
  BADGE:       { target: { entity: person, required: true }, effects: { asserts: ["met(@target)"] } }
  OFFER_QUEST: { target: { required: true },                 effects: { accepts: ["@target"] } }
```

- Keys: `asserts`, `retracts` (the `FactEffect` grammar, shared code), and `accepts` (a list of
  quest ids or `@target` / `@<attr>`). `writes` is **not** admitted on reward kinds: `credits:`
  already is the reward's state write, and two spellings for it would collide
  (`W-REWARD-DOUBLE-CREDIT` exists for exactly that). Pattern arguments: `@target`, the kind's own
  `attrs:` (`@rarity`), members, `true`/`false`, `_` in `retracts`. An unknown `@name` or `_` in
  `asserts` is `E-PLUGIN-PARSE`, as on directives.
- **Meaning.** At the grant instant (objective grant, quest `complete` grant, `outcome="failed"`
  grant; only when the reward's `when` holds), after `credits`, the runtime applies retracts, then
  asserts, then accepts. Grants precede the transition's handler body (quest-lifecycle "Order
  within one owner"), so a `questComplete` handler reads the fact.
- **Checks.** The relation, arity and argument kinds are judged per `<reward>` as for a directive
  call; `accepts` resolves its id against the project's quests (`E-CONN-UNKNOWN-NODE`, did-you-mean)
  and must name an accept-driven quest (`E-ACCEPT-TARGET`, the `::accept` rule). An `@target` left
  empty by a reward without `target=` contributes nothing (the directive rule).
- **Analyses.** Each effect is read as if written in the owner's grant point: an `::assert` /
  `::retract` / `::accept` in the corresponding `<on event="questComplete">` (or objective body,
  or `questFailed` for `outcome="failed"`). So the fact analysis (may/must), `E-QUEST-UNREACHABLE`,
  `W-RELATION-UNREAD`, `E-FACT-EXCLUSIVE`, `lute scenario knowledge`, `lute lore`, the `[accept]`
  edge (`quest(first) -> quest(second) [accept]`) and `W-QUEST-NEVER-ACCEPTED` all follow without a
  second model. Knowledge output names the producer: `met(mira) — produced by reward BADGE of quest firstVisit`.
- **IR.** `RewardEntry` gains resolved `retracts`, `asserts` (`{ relation, args }`, as on the
  plugin record) and `accepts` (quest ids), each omitted when empty. This changes meaning: an
  engine that ignores them loses facts and quest activations. New semantic id
  **`lute.quest.rewardEffects/1`** (module `quest`), collected only by artifacts that use one.
- `capabilitySnapshot`: printed only when set.

**B. Top-level `asserts:` / `retracts:` / `accepts:` keys on the kind** (the issue's sketch).
Same mechanics, but a second spelling of directive `effects.asserts`. Rejected.

**C. Desugar at compile: the compiler appends `::assert`/`::accept` records to the quest's handler.**
No new IR field, but the artifact would contain records nobody authored, the host's grant event
and the fact change would be decoupled (a host that settles the grant late still sees the fact),
and `lute fmt`/source maps would have no source for them. Rejected.

### Cost (A)

`lute-manifest` (`RewardKindBody.effects`, shared `FactEffect` parsing), `lute-check` (per-reward
judging; feed the reward effects into the fact producer set, accept edges, connectivity),
`lute-compile` (`RewardEntry`, semantics), `lute-runtime` (`machine/quest.rs` grant path through
the one assert/retract/accept path), `lute-trace`/`play` transcript (`assert met(mira)  (effect of
reward BADGE)`), schemas, conformance (one grant fixture per effect kind), docs. Contract change:
**yes** (IR fields + semantic id). Analysis: makes reward producers visible; soundness improves
(no more `reserved` workaround). Size **M**. **0.50**.

### Interactions

#170 adds `raises` to the same `effects:` vocabulary on both carriers. #181/#182 (0.49 start
cycles) — a reward `accepts` closing a cycle of accept-driven quests is drawn by the same cycle
detector, since it is an `[accept]` edge.

## 6. #170 — a scene that leads to another scene

### Problem

A scene cannot present another scene. Ports model "play this scene now" (a sequence step, a quest
reward that plays a cut-scene) as a passthrough `::playScene{scene=…}`; the scenario graph then
sees no edge, the callee is a root, and `reach`/`impact` cannot answer across it. The only edge an
author can draw is a hand-copied `after: visited("…")` in the callee.

### Options

**A. A core call with return, `::present{scene="chapter2"}`.** The runtime suspends the caller,
presents the callee, resumes. Needs a presentation stack in the runtime and its snapshot (save
format), a recursion ban (`E-CALL-CYCLE` over the call graph), callee-effect summaries in the
caller's flow analyses (definite assignment, stage state, facts after the call), and a rule for a
callee with `on:`/`after:` (selection bypassed). The return case is already composed by
**components** (`::use{component=…}` splices reusable content inline with its own instance
identity, D8). D4: composition covers the call-with-return; rejected.

**B. A core `::raise{occasion target}` the runtime executes.** Content raises an occasion; the
runtime queues it after the current presentation. Contradicts D13, which gives raising occasions
to the host; it would also need a queue in the runtime snapshot and a semantic id. Rejected.

**C. A declared `raises` effect, host-executed (recommended).** A directive's (and, with #169, a
reward kind's) `effects:` may declare the occasion the host raises in answer to it — the same
"declare what the host does" contract as `effects.asserts`:

```yaml
# plugins/acme.stage/occasions/o.yaml
occasions:
  cutscene: { select: first, target: { prefix: scene, entity: cutsceneId }, raisedBy: declared }
# plugins/acme.stage/directives/d.yaml
directives:
  - name: playScene
    attrs:
      - { name: scene, required: true, type: { entity: cutsceneId } }
    effects:
      raises: [{ occasion: cutscene, target: "@scene" }]
```

```lute
--- # scenes/chapter2.lute
kind: scene
id: chapter2
on: cutscene
target: scene.chapter2
---
```

- **Meaning (contract).** After the presentation that ran the call ends, the host raises the named
  occasion for the target. Lute does not execute it (no runtime change); the compiled `plugin`
  record (and `RewardEntry`) carries the resolved `raises: [{ occasion, target }]` so the host does
  not re-derive it. Descriptive for the runtime → additive, no semantic id.
- **`raisedBy: declared`** (new occasion key, optional): the host raises this occasion only where
  a declared `raises` says so. Without it the occasion stays an entry the host may raise any time
  (today's meaning), and a `raises` edge is an anchor only. With it, a beat/scene answering the
  occasion is reachable only through its raisers, `reach`/`impact` route through the edge, and an
  occasion no effect raises is `W-OCCASION-NEVER-RAISED` (the analogue of
  `W-QUEST-NEVER-ACCEPTED`, with the same three remedies). This is the occasion-side counterpart of
  `accept="external"` vs accept-driven quests.
- **Checks.** `occasion` must be declared (`E-PLUGIN-PARSE` at load); the target is checked per
  call against the occasion's domain (`E-BEAT-ATTR` wording, did-you-mean); a target with no
  answering scene/beat is `E-CONN-UNKNOWN-NODE` at the call.
- **Graph.** `lute scenario` draws `scene(intro) -> scene(chapter2) [raises]`; `--json`
  `kinds: ["raises"]`; dot solid. Reach treats a `raisedBy: declared` occasion's answerers as
  anchored by their raisers (the accept-anchor machinery).

### Cost (C)

`lute-manifest` (effects key `raises`, occasion `raisedBy`), `lute-check`/connectivity (edge kind,
anchors, reach, new warning), `lute-compile` (resolved `raises` on plugin record / `RewardEntry`),
`lute-cli` (`scenario`, `impact`, `reach` text/json/dot), schemas, docs. Runtime/player: none.
Contract change: **yes, additive** (IR descriptive field, manifest keys). Size **M**. **0.51**
(after #169, which introduces the shared reward `effects:`; and it changes `reach`, which wants its
own regression set).

## 7. #159 — retry loops

### Problem

`::jump` is forward-only (`E-JUMP-BACKWARD`) so the walk stays a DAG and every scenario provably
terminates. That leaves "retry" without a spelling: attempt, a result says fail, go back. `<hub>`
covers player menus (the repro's "Again? yes/no" is a hub with a `<return>` and an `exit` choice);
it does not cover a loop decided by a `<match>` over a bridge result or a rejoin to an earlier
point. The port's workaround — an opaque passthrough `::goto` — hides the edge, so everything only
reachable through it is false `W-CODE-AFTER-JUMP`/`END`.

### Composition check (D4)

- Hub: player-menu loops only; every iteration presents a menu.
- Re-raising the scene's occasion from the host: restarts the whole scene and needs host flow.
- Copying the retried stretch N times (unrolling by hand): expressible, unmaintainable.
- A plugin flow effect (`effects.flow: backToLabel`): the host cannot resume the runtime at a
  label (labels compile to no record; `Input` has no such entry), and it would make the host own
  narrative flow (D13). Rejected.

Composition fails for non-menu loops, so a language change is justified.

### Options

**A. A bounded backward `::jump` (recommended).** `::jump` may target an earlier `::label` when it
carries `max`, the number of times it may be taken; after that it falls through.

```lute
::label{name="attempt"}
::minigame{level="2"}                       # blocking bridge, writes run.won
<match subject="run.won">
  <when is="false">
    @mira: Again!
    ::jump{to="attempt" max="2"}
  </when>
</match>
@theo: That's enough for today.
```

- **Rules.** A backward jump without `max` stays `E-JUMP-BACKWARD`, the hint naming `max` and
  `<hub>`. `max` on a forward jump is `E-JUMP-MAX-FORWARD` (it means nothing). `max` is a literal
  int 1..=99. Well-nestedness, so the loop is always reducible: the target label must sit in the
  jump's own body or an enclosing one (`E-JUMP-LOOP-SCOPE`); a forward jump from outside the loop
  region `[label, jump]` into it is `E-JUMP-INTO-LOOP`; two regions may nest but not cross
  (`E-JUMP-LOOP-CROSS`).
- **Counter.** Per presentation, per jump; reset whenever control reaches its label other than by
  that jump (so an inner loop restarts its budget on each outer iteration). Total work is bounded
  by the product of the `max` values, so termination stays provable without player cooperation —
  stronger than a hub.
- **Analyses.** A label targeted by a backward jump is a loop head: its state is the join of the
  entry state and the state at each back edge; the walker iterates the region to a fixpoint before
  reporting (the lattices are finite: stage state, definite assignment, `into` writes; verdicts
  built on constant knowledge become *possible* at the head). Content after a bounded jump is
  reachable (exhaustion), so no `W-CODE-AFTER-JUMP`. `lute trace` unrolls up to `max` and reports
  *Bounded* (D9). The scenario graph is unaffected (intra-scene).
- **IR / runtime.** The `jump` record gains `max` (and its target position is earlier). Meaning-
  changing — an older runtime would loop forever or never loop — so new semantic id
  **`lute.core.boundedJump/1`**. The runtime keeps the counters in session state, so the snapshot
  (save) format gains them (`snapshotVersion` bump). Player: none.

**B. A structured block `<retry max="2"> … ::again … </retry>`.** Same semantics with an explicit
region, so nesting is syntactic rather than checked. Two new core words (an element and a
directive) where A needs one attribute on an existing directive; importers translating backward
`next` pointers must compute regions first, which A's scope rules check for them. Kept as the
fallback if A's scope rules prove confusing in review.

**C. Docs-only recipe + a label "entry point" marker** (issue option 3). Silences
`W-CODE-AFTER-*` but still hides the edge, so reachability remains unsound. Rejected.

### Cost (A)

`lute-check` (jump rules, loop-head fixpoint in the flow walks: `defassign.rs`, stage fork/join,
`decide.rs`, code-after), `lute-compile` (emitter backward bind, stage injection at the head with
the same fixpoint, `jump.max`, semantics), `lute-runtime` (counters, snapshot), `lute-trace`
(bounded unrolling), conformance (loop, nested loop, exhaustion, save/restore mid-loop), schemas,
docs, the Ink/Yarn guide (`-> knot` back-diverts now have a spelling). Contract change: **yes**
(IR field + semantic id + snapshot). Size **L**. **0.51** (touches every flow analysis and the save
format; the riskiest item).

## 8. #172 + #177 — declarative predicates (lints over nodes)

### #172 problem

Plugin and `custom:` lints assert over six core-computed metric tables (`line`, `section`, `scene`,
`speaker`, `group`, `project`). Structural policies of imported content sets have no home: "a
`::signal{value="puzzle"}` must be followed by a `<branch>`", "the first node of a section is a
`::bg`", "a label name starts with a prefix that depends on the scene kind", "`begin`/`end` pairs
balance, with only some kinds inside". `target: directive` and `scene.firstDirective` are load or
evaluation errors.

### #177 problem

An attribute's legal values can depend on another attribute — of the same directive (`mode`
selects legal `speed`s) or of a neighbouring one (a marker `::interaction{kind}` decides which
`::option{value}`s the following choices may use). Each attribute is typed against one closed
domain, so the declared domain is the union, and invalid combinations pass.

### Options

**A. A `node` lint target over the AST walk, plus a `pair` target (recommended).** Lints stay
declarative, ground, AST-based, outside `capabilitySnapshot`; no plugin code in the checker.

`target: node` binds one row per body node in document order (lines, directives incl. `::label`/
`::jump`/`::use`, and the elements `branch`, `hub`, `choice`, `match`, `when`, `otherwise`,
`return`, `quest`, `objective`, `on`, `reward`), plus the existing `scene` row:

| field | meaning |
|---|---|
| `node.kind` | `line`, `directive`, or the element name |
| `node.tag` | directive tag, element name, `""` for a line |
| `node.speaker` | speaker of a line, `""` otherwise |
| `node.attrs` | authored attributes as a string map (stamps included; `BoolTrue` is `"true"`) |
| `node.index`, `node.first`, `node.last`, `node.depth` | position in its body |
| `node.prev`, `node.next` | `{ kind, tag, attrs }` of the sibling; all-empty at a body edge |
| `node.parent` | `{ kind, tag, attrs }` of the enclosing element; `kind: "section"` at top level |
| `node.preceding` | map tag → `{ attrs }` of the nearest earlier node with that tag in the same section, on the path to this node (enclosing bodies included, sibling arms excluded) |
| `node.section` | `{ index, title, id }` |

The lint CEL fragment gains the standard string members `startsWith`, `endsWith`, `contains`
(no regex, no macros). Message interpolation and anchoring work as for `line` rows (the node's
span).

```yaml
lints:
  - id: signal-needs-menu
    target: node
    when: 'node.tag == "signal" && node.attrs["value"] == "puzzle" && node.next.kind != "branch"'
    level: warn
    message: "a puzzle ::signal must be followed by a <branch>"
  - id: section-opens-with-bg
    target: node
    when: 'node.first && node.parent.kind == "section" && node.tag != "bg"'
    level: warn
    message: "section {node.section.title} opens with {node.tag}"
  - id: beat-label-prefix
    target: node
    when: 'node.tag == "label" && scene.kind == "beat" && !node.attrs["name"].startsWith("b_")'
    level: error
    message: "a beat's labels start with b_"
  - id: option-fits-interaction          # #177, the repro's marker/option pair
    target: node
    when: >-
      node.tag == "option" && "interaction" in node.preceding &&
      !(node.attrs["value"] in options.cases[node.preceding["interaction"].attrs["kind"]])
    level: error
    message: "option {node.attrs.value} does not belong to this interaction"
    options: { cases: { greet: [wave, bow], gift: [accept, decline] } }
```

With #164, the same rule over element stamps reads `node.kind == "choice"` and
`node.parent.attrs["kind"]`. A same-directive dependency is `node.attrs` against `node.attrs`.

`target: pair` covers balance, which no single-row predicate can:

```yaml
  - id: group-balanced
    target: pair
    open:   'node.tag == "group" && node.attrs["mode"] == "begin"'
    close:  'node.tag == "group" && node.attrs["mode"] == "end"'
    inside: 'node.kind == "line" || node.tag in ["actor", "sfx"]'   # optional
    scope: body                                                       # body (default) | section
    level: error
    message: "::group begin/end"
```

It reports an unclosed `open`, a `close` without an `open`, a nested `open`, and an inside node
that fails `inside`, each at the offending node. Linear, ground, deterministic.

**B. `target: record` over the compiled IR** (the issue's sketch). Sees expanded components and
lowered records, but needs a compile per lint run, loses the LSP path (lute-lint does not link
`lute-compile`), and reports on records without authored spans. Rejected.

**C. For #177, a manifest type `enumBy: { attr, cases }`.** A checker-native domain (error in
`check`, LSP completion), but only within one directive: it cannot reach the marker/option case the
issue is about, and it is a second predicate mechanism beside lints. Rejected in favour of A; if a
same-element dependency later needs `check`-time enforcement, `enumBy` is the extension point.

### Cost (A)

`lute-lint` only (`metrics.rs` node rows built in the one walk, `eval.rs` string members, `model.rs`
targets, `config.rs` validation, pair evaluator), `lute-manifest/src/lint.rs` (`LintTarget::{Node,
Pair}`, `open`/`close`/`inside`/`scope` keys), `lute-lsp` (evaluates `node`/`pair` like other
in-document targets), docs (`tooling/linting`, the "core change, not a YAML extension" paragraph
rewritten). Contract change: **none** (lints are excluded from the snapshot and the IR). Analysis
impact: none. Rows are borrowed views over the AST, not copies (D14 S1; `preceding` is a persistent
per-section map). Size **M** (node + `preceding` + strings), **S** for `pair`.

### Recommendation

**A.** `node` target with `preceding`/`parent`/`prev`/`next` and string members in **0.50** (it
also closes #177 with no new type); `pair` target in **0.51** (independent, small, after `node`
proves the row model).

## 9. #176 (authoring) — values for `list` / `map` / `record` attributes

### Problem

Since 0.49 a directive attribute or stamp typed `list`/`map`/`record` is refused at plugin load
(`E-PLUGIN-INVALID-DIRECTIVE`), because no `.lute` spelling could satisfy it. The port's structured
columns (a per-language map of voice ids, a list of option labels) are JSON strings the checker
cannot see into.

### Options

**A. JSON array values for `list` attributes; `map`/`record` stay refused (recommended).**
`tags=["a", "b"]` — a JSON array literal after `=`, elements quoted strings, numbers or bools,
each checked against the element type (enum/entity/provider/asset members with did-you-mean, per
element span). Compiles to a JSON array in `fields`/`stamps`. No `@ref` elements (a list attribute
is static data, the reward-target rule). Only `{ list: <scalar> }` is admitted at load; nested
lists, `map`, `record` keep the 0.49 refusal with a message naming the route:
- `record` → one attribute per field (now typed per surface with `on:`, §1);
- per-language `map` → a `text` attribute (§3) or the `voiceKey` join;
- other `map` → keyed attributes, or a provider id the host resolves.

**B. JSON for all three** (`voices={"ja": "VO.1"}`). One grammar, but a map literal is
almost always one of the routes above in disguise, and objects in attribute position are the
hardest case for tree-sitter, `lute fmt` and LSP positions.

**C. Delimited strings declared in the manifest** (`{ list: …, sep: "," }`, `tags="a,b"`).
No syntax change, but every plugin picks its own separator and escaping — no single spelling.
Rejected.

### Cost (A)

`lute-syntax` (attribute value `AttrValue::List`), tree-sitter grammar + highlights, `lute fmt`
(canonical `["a", "b"]`), `lute-lsp` (per-element completion/diagnostics), `lute-check`
(`literal_of` for lists, element typing), `lute-compile` (`attr_json_typed`), `lute-manifest`
(admit `list` of scalar), component params (a list argument passes through `::use` unchanged, or
`E-TEMPLATE` until supported — decide in the spec), docs. Contract: IR values may be arrays (the
schema types `fields` values as any JSON already; `stamps` likewise). Size **M**. **0.51**
(syntax-wide, and its demand drops once §1 and §3 land — verify on the port before starting).
