# Phase 2 inventory — time

> Draft research input for the 0.33 spec (ADR phase 2). Generated by a read-only scout on 2026-10-02 against the 0.32.0 working tree; verify citations before relying on them.

## Summary

1. Clock/calendar semantics are engine-owned; schema declares day/slot/order/week/raise and IR carries `clock` verbatim.
2. `advance`/beat `advances` move time, settle quests, and raise declared clock occasions at explicit stops.
3. Derived `clock.index`, weekday/label, and `clock.ended` are read-only engine paths; clock writes do not raise occasions.
4. Occasions are capability vocabulary; beats/entries/bundles provide candidates selected by priority and project index order.
5. `raisedWhen` gates are engine gates and checker assumptions; terminal suppresses ordinary occasions, with outside-run exceptions.
6. Beat eligibility combines after/when/spentBy/once/target; sequence/also presentation settles quests between presentations.
7. Cadence includes run/user/day/slot/week/season spends, shared `share`, and latch-like spentBy behavior.
8. State tiers are scene/run/user/app/quest plus season; prev.run and prev.season are read-only prior-window mirrors.
9. `newRun`, rearm, and season opening reset scoped lifecycle state while preserving quest instance counters.
10. `by` deadlines settle every lifecycle instant; `until` is raise-bound and checked after done, with explicit judge-before/after ordering.

## Proposed architecture

Proposed owner is a single `time` module for clock/calendar/schedule/cadence, gates/terminal/season transitions, and occasion timing; it must publish explicit ordering edges to `quest-lifecycle` (deadline/settle), `beat-selection` (eligibility/presentation), and `state` (tier resets and prior-window snapshots). Engine-visible semantics should be negotiated independently for clock advances, occasion raises/gates, cadence spends, season resets, terminal/outside-run behavior, and prior-state/new-run transitions.

## Existing ordering rules between modules

1. **Clock movement → quest settle → clock occasion raise.** An advance moves the clock, settles quests, and raises the declared occasion at the stopping position; day-end/day-start are explicit intermediate stops (`docs/proposals/scenario-dsl/0.24.0.md:41-60`).
2. **Clock raise gate → beat eligibility.** `raisedWhen` is conjoined into every beat and a false gate suppresses/refuses the occasion (`docs/proposals/scenario-dsl/0.27.0.md:75-83`).
3. **Raise → one eligibility snapshot → selection → presentation.** Eligibility is decided once at raise; sequence/also do not requalify later beats within the same raise (`docs/runtime/beats-and-occasions.md:249-363`).
4. **Selection order is priority descending, then project index/source order.** The runtime contract states deterministic selection and ordering (`docs/runtime/beats-and-occasions.md:249-298`).
5. **Presentation → quest settle before next presentation.** Every presented beat is followed by a quest settle, including sequence and also lists (`docs/runtime/beats-and-occasions.md:349-363`).
6. **`judge: before` moves objective judging before beat presentation; default `after` judges after.** Lifecycle handlers for the occasion and transitions still run after beats (`docs/runtime/beats-and-occasions.md:53-62`).
7. **Within objective judgment, `done` precedes `by`/`until` failure.** `by` is every settle; `until` is only matching raise; same-step done wins tie (`docs/proposals/scenario-dsl/0.24.0.md:106-115`).
8. **Quest fail precedes derived completion.** An activated quest whose `fail` holds fails even if objectives would otherwise complete (`docs/runtime/quest-lifecycle.md:150-180`).
9. **Run reset precedes first new-run evaluation.** `newRun` resets run-tier values/facts/quests, applies queued acceptances, then settles lifecycle (`docs/runtime/quest-lifecycle.md:173-180`).
10. **Season false→true edge precedes season-window evaluation.** State/cadence/season-tier quests reset and previous values are captured when a season opens (`docs/proposals/scenario-dsl/0.27.0.md:101-116`).
11. **Terminal check precedes ordinary occasion raises.** Terminal suppresses ordinary occasions; outside-run occasions are the explicit exception (`docs/proposals/scenario-dsl/0.27.0.md:84-88`; `docs/proposals/scenario-dsl/0.28.0.md:80-88`).
12. **Beat `advances` occurs after presentation, then recursively invokes clock movement.** The source of truth is the beat declaration, and the movement follows the same settle/raise cascade as explicit advance (`docs/proposals/scenario-dsl/0.31.0.md:29-38`).
13. **Entry first-read writes read flags around body execution.** Entry presentation runs body against live state and first-read sets `entry.read`/`everRead`; subsequent once checks use those flags (`docs/runtime/beats-and-occasions.md:349-363`; `docs/runtime/lore-entries.md:49-66`).
14. **Shared spend is atomic across all beats sharing a key.** Presenting one member spends every member for its common cadence (`docs/runtime/beats-and-occasions.md:249-298`).

## Gaps and ambiguities requiring 0.33 clarification

- **Clock raise vs terminal timing:** The docs establish terminal-before-ordinary-raise, but do not fully state whether terminal is re-evaluated between each `dayEnd`, `dayStart`, final slot raise, and nested beat `advances`; this matters if an intermediate presentation makes terminal true (`docs/proposals/scenario-dsl/0.27.0.md:84-88`; `docs/proposals/scenario-dsl/0.24.0.md:41-60`).
- **Gate and target binding order:** `raisedWhen` may read `occasion.target`, but the exact host phase that binds target/payload relative to gate evaluation is implied, not explicitly sequenced for all target forms (`docs/proposals/scenario-dsl/0.27.0.md:75-83`; `docs/proposals/scenario-dsl/0.27.0.md:58-73`).
- **Quest settle vs engine writes at intermediate stops:** `advance` says attached engine writes land after each day stop and before final settle/slot raise, while the general settle-before-raise rule leaves ambiguous whether writes occur before or after the intermediate day-end settle (`docs/proposals/scenario-dsl/0.24.0.md:56-69`).
- **Beat presentation vs `advances` exact point:** 0.31 says clock movement occurs when beat is presented and follows advance semantics, but does not explicitly say whether movement is after the whole body (including `::end`) or at presentation admission (`docs/proposals/scenario-dsl/0.31.0.md:9-38`).
- **Finite endpoint ordering:** 0.27 says the last `dayEnd` is raised and clock stops, but does not specify whether the final endpoint's `clock.ended` becomes true before or after that raise's gate/beat eligibility and quest settle (`docs/proposals/scenario-dsl/0.27.0.md:84-94`).
- **First-run prior mirrors:** `prev.run.*` has no prior snapshot before the first run, but the exact runtime value/`has()` behavior is only described as “no default” in checker folding (`crates/lute-check/src/fold.rs:321-340`), not fully stated in the engine contract.
- **Season opening initialization:** `live` false→true is the trigger, but initial season state when a save starts with `live=true` is not explicitly distinguished from an opening edge (`docs/proposals/scenario-dsl/0.27.0.md:101-116`).
- **Overlapping season reset order:** seasons “overlap freely,” yet no order is specified if two seasons open in the same settle and their conditions/state writes interact (`docs/proposals/scenario-dsl/0.27.0.md:101-116`).
- **Rearm observation at load:** rearm's first observation is baseline, but save-load initialization and whether a persisted previous rearm truth is required are not specified (`docs/runtime/quest-lifecycle.md:215-235`).
- **`spentBy` latch storage:** the docs say the condition holds and the beat is spent for its once period even if it turns false, but do not specify whether the latch is a presentation record, dedicated engine bit, or reconstructed from history (`docs/proposals/scenario-dsl/0.27.0.md:101-118`).
- **Entry once and run reset sequencing:** entry `read`/`everRead` flags are set by first read, while run reset semantics are stated for run-tier quests and run state; the exact reset event/order for `entry.*.read` is documented informally rather than in the state lifecycle reset list (`docs/runtime/lore-entries.md:60-66`; `docs/runtime/state-lifecycle.md:58-66`).
- **Calendar bounded semantics:** calendar evaluates a bounded grid but the evidence vocabulary and treatment of unknown conditions across cells are not fully unified with the architecture proposal's Bounded/Witnessed model (`docs/proposals/scenario-dsl/0.23.0.md:13-30`; `docs/design/architecture-direction.md:209-220`).
- **Schedule ownership boundary:** `when` conditions and `after` prerequisites are authored on beats/quests while the engine owns actual raise times; no single contract states whether a future schedule/raise registry belongs to the time module or beat-selection (`docs/runtime/beats-and-occasions.md:15-18`; `docs/runtime/quest-lifecycle.md:3-8`).
