# Phase 2 inventory — quest

> Draft research input for the 0.33 spec (ADR phase 2). Generated by a read-only scout on 2026-10-02 against the 0.32.0 working tree; verify citations before relying on them.

## Summary

1. Quest semantics are declaration-driven: the engine derives lifecycle from `quest`/`on` records, not command flow.
2. Core lifecycle is `unset → active → complete|failed`; `fail` is evaluated before derived completion.
3. Objective completion is monotone; `visibleWhen` only controls presentation and never gates `done`.
4. `on`/`target` objectives judge `done` at matching raises; `by` is continuous, while `until` is raise-local.
5. Required objective deadline failure propagates to quest failure; optional objective failure closes only that objective.
6. Subquests synthesize `done = quest.child.state == 'complete'`; parent activation/cascade remains engine-derived.
7. `complete="any"` supersedes other active child alternatives; ordinary terminal cascades use `failedBy=cascade`.
8. `run`, `season:<name>`, and false→true `rearm` reset instance scratch; instance counters must survive resets.
9. Rewards are declaration data, ordered per owner, granted before lifecycle handlers, and need `(quest,instance,objective,index)` identity.
10. Proposed owner is `quest.lifecycle`; split schedule/clock ownership only for reset observations, with explicit lifecycle ordering dependencies.

## Proposed architecture

Proposed owner: one official `quest.lifecycle` module owns quest declarations, objective state, activation/failure/completion, subquest edges, accepts, handlers, and rewards. `clock.schedule` owns clock positions, season live transitions, and reset triggers; it must invoke `quest.lifecycle` at each crossed position. `staging/occasion` owns occasion raising/presentation and calls lifecycle objective judgment. `state/knowledge` supplies CEL reads/facts but does not derive quest transitions. Lowering remains declaration data (`QuestCmd`, `ObjectiveEntry`, `OnCmd`, `AcceptCmd`) plus addressed body segments; the engine owns all reserved quest writes and reward settlement.

## Existing ordering rules (with citations)

1. Cadence observation (season opening/rearm) precedes quest fixpoint; lifecycle may re-observe after a pass changes quest state (`crates/lute-trace/src/exec/session/lifecycle.rs:21-44`; `crates/lute-trace/src/exec/cadence.rs:18-24`).
2. Within lifecycle fixpoint: referenced-child activation → continuous objective done → `by` deadlines → fail determination → derived completion → child cascade (`crates/lute-trace/src/exec/machine/quest.rs:430-610`).
3. `fail`/required deadline failure precedes derived completion; `complete="any"` suppresses single-alternative failure until all required alternatives fail (`crates/lute-trace/src/exec/machine/quest.rs:535-610`; `docs/runtime/quest-lifecycle.md:45-70`).
4. Occasion raise filters active quests and target-compatible objectives; `done` is judged before `until`, with deferred `by` handled after the raise (`crates/lute-trace/src/exec/machine/quest.rs:720-783`; `crates/lute-trace/src/exec/session/step.rs:164-180`).
5. World handlers for an occasion run before occasion objective judgment; lifecycle handlers run after grants and state transition (`docs/runtime/quest-lifecycle.md:630-645`; `crates/lute-trace/src/exec/machine/quest.rs:580-610`).
6. Objective grants precede objective body execution and quest-level grants; quest-level grants precede `questComplete`/`questFailed` handlers (`crates/lute-trace/src/exec/machine/quest.rs:700-720`; `docs/runtime/quest-lifecycle.md:560-610`).
7. A terminal parent recursively cascades active children; `complete="any"` uses `superseded` for still-active alternatives, otherwise `cascade` (`crates/lute-trace/src/exec/machine/quest.rs:600-610,860-903`; `docs/runtime/quest-lifecycle.md:535-560`).
8. Every clock position crossed by an advance is a quest settlement point, even when no clock occasion is raised (`crates/lute-trace/src/exec/session/advance.rs:145-150`; `docs/runtime/state-lifecycle.md:210-245`).
9. New-run reset clears run-tier quest scratch, then queued next-run accepts and lifecycle settlement occur (`crates/lute-trace/src/exec/session/step.rs:378-385`; `docs/runtime/quest-lifecycle.md:190-235`).
10. Project-level quest documents are advanced in path order and repeated to a fixpoint so cross-document quest state can gate another quest (`crates/lute-trace/src/exec/session/lifecycle.rs:21-44`; `crates/lute-trace/src/exec/project.rs:46-55`).

## Gaps / ambiguities to resolve in 0.33

- **Semantic-id granularity:** D5 requires one versioned ID per engine-visible behavior, but no registry exists yet. Decide whether lifecycle, objective occasions, deadlines, subquests, reset tiers, handler dispatch, rewards, and grant identity are separate IDs or one `lute.quest.lifecycle` family (`docs/design/architecture-direction.md:136-153`).
- **Grant identity is specified but IR/runtime implementation is not fully aligned:** 0.32.0 requires `instance` and owner-relative `index`, while the current `RewardRec` parser/executor must be audited for emission and persistence (`docs/proposals/scenario-dsl/0.32.0.md:207-228`; `crates/lute-trace/src/exec/machine/quest.rs:1-100`).
- **Quest-instance persistence/reset API:** lifecycle docs require save-wide counters, but the exact engine save schema and behavior when a quest is seeded terminal/active are not a single module contract (`docs/runtime/quest-lifecycle.md:10-35`; `crates/lute-trace/src/exec/world.rs:317-405`).
- **Cross-document ordering:** path order plus fixpoint is implementation behavior, but the normative contract does not clearly say whether path order is observable or only convergence is normative (`crates/lute-trace/src/exec/session/lifecycle.rs:21-44`).
- **Chapter ordering versus quest settlement:** chapters select scene beats and quests settle after presentations, but the exact point at which chapter chain eligibility observes quest transitions is distributed across staging/session docs (`crates/lute-check/src/chapters.rs:11-15`; `crates/lute-trace/src/exec/session/step.rs:164-180`).
- **Season live edge cases:** season-tier reset is specified on false→true opening, but simultaneous season opening, rearm, clock raise, and quest deadline tie precedence should be a single normative phase table (`crates/lute-trace/src/exec/cadence.rs:15-24`; `docs/runtime/quest-lifecycle.md:235-290`).
- **Accept timing under nested handler/body transitions:** accepts queue for the next lifecycle settle, but exact ordering when an accept body writes state and also triggers a terminal parent in the same fixpoint should be stated independently of the current implementation (`crates/lute-trace/src/exec/world.rs:55-60`; `crates/lute-trace/src/exec/machine/quest.rs:420-470`).
- **Reward `when` snapshot wording:** docs say triggering transition snapshot, while grants can be emitted after objective state writes; 0.33 should define whether `when` sees pre-transition state, post-objective write, or a per-transition snapshot (`docs/runtime/quest-lifecycle.md:595-610`).
- **Optional subquest semantics:** optional child failure does not fail parent, but activation/cascade and whether its rewards count toward parent completion are scattered across the subquest section and implementation (`docs/runtime/quest-lifecycle.md:500-560`).
- **`follows` and chapters are graph metadata, not gates:** this is documented, but authors may expect chapter order to activate quests; the 0.33 contract should explicitly distinguish selection order, quest activation, and lifecycle settle (`docs/runtime/quest-lifecycle.md:640-645`; `crates/lute-compile/src/ir.rs:186-189`).
