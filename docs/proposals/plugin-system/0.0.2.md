# Lute Plugin System — 0.0.2

- **Version:** 0.0.2
- **Status:** Draft (delta on [`0.0.1`](0.0.1.md))
- **Date:** 2026-07-27
- **Companion:** [`scenario-dsl/0.8.0.md`](../scenario-dsl/0.8.0.md)
- **Scope:** implements Appendix C1, C2 and C4 of 0.0.1; implements the
  declarative `lower: { record, fields }` form 0.0.1 §8 specified but shipped
  dead; adds one new export kind, `stampAttrs`. No change to activation
  ordering, snapshot composition, provider resolution, or the data↔code
  boundary.

0.0.1 remains the base specification. Everything not restated here is unchanged.

## 1. Motivation

0.0.1 Appendix C listed four MUSTs as "spec'd but unimplemented." Three of them
share one failure mode: **the manifest is trusted without being checked.** A
plugin could declare an option and pass it a value of the wrong type; declare a
frontmatter key and have any value accepted; declare an attribute named `wait`
and shadow the core stamp. That is precisely the "declaration accepted,
validation absent" hole that makes a schema decorative, and it is the same hole
an adopting project is trying to *escape* by moving off ad-hoc validators.

The fourth item, `lower: { record }`, is worse than unimplemented: it parses.
`Lowering::Record` deserializes cleanly and is then never matched anywhere in
`lute-compile`, so every plugin directive — declarative or not — lowers to
`kind: "plugin"`. A manifest author gets no error and no effect.

`stampAttrs` is the one genuinely new surface, and it comes from a measured
gap: engines carry per-record metadata that is orthogonal to the record kind
(analytics tags, bonus hooks, experiment buckets). 0.0.1 could declare
attributes only per-directive, so such a key had to be redeclared on every
directive — or, in practice, smuggled through an untyped field.

## 2. §5.1 — Option validation (closes C1)

Activation MUST validate every supplied plugin option against the owning
`plugin.yaml` `options:` declaration, **after** the merge described in
0.0.1 §11.1 and before the snapshot is assembled.

- An option name not declared by the plugin is **`E-PLUGIN-OPTION-UNKNOWN`**:

  > plugin `<id>` has no option `<name>` (declared: a, b, c)

- A value that fails its declared type is **`E-PLUGIN-OPTION-TYPE`**:

  > option `<id>.<name>` expects `<type>`, got `<literal>`

Type checking uses the §7 manifest type system through the single shared
predicate `type_accepts(&Type, &Literal)`. Both diagnostics travel the same
resolution channel as load errors and unresolved `depends`, so the CLI, the
checker, and the LSP observe them identically — the no-divergence guarantee of
0.0.1 §13 extends to activation.

Defaults are unaffected: an undeclared-but-defaulted option is simply absent
from the merge and takes its declared default.

## 3. §6.8 — Frontmatter value validation (closes C2)

A plugin's `frontmatter/*.yaml` export declares `{ key, schema }` pairs, and the
checker already admits those keys past `E-META-UNKNOWN-KEY`. It MUST now also
validate their **values** against the declared `schema`.

A value that violates its declared type is **`E-FRONTMATTER-SCHEMA`**, reported
at the frontmatter key's span:

> frontmatter key `<key>` expects `<type>` (declared by an active plugin),
> got `<found>`

A value that cannot be represented as a manifest `Literal` at all is the same
error — never a panic, never a silent pass.

Core keys (the universal set, the scene-only set, and the component-only set)
keep their existing bespoke handling and are **not** routed through this check.

## 4. §14.1 — `stampAttrs`: cross-cutting attributes (new)

### The problem

0.0.1 attributes are per-directive. The core `Stamp` — flattened into every
stamped record — has exactly seven reserved keys: `wait`, `duration`, `delay`,
`at`, `timeline`, `provenance`, `source`. A host that tags *every* record with,
say, an analytics id had no declaration site: it would have to add the attribute
to every directive it ships, and could still never put it on a content line.

### The export

A plugin MAY export `stampattrs/*.yaml`:

```yaml
stampAttrs:
  - { name: bonusId,    type: string }
  - { name: bonusScore, type: number }
```

Entries are ordinary `AttrDecl`s (`name`, `required`, `type`, `default`) and are
folded into the capability snapshot with the same duplicate handling as every
other map (0.0.1 §11.3, first owner wins, collision diagnosed). **`stampAttrs`
participates in `capabilityVersion`**: a changed cross-cutting vocabulary is a
changed capability surface, and an engine must be able to refuse a mismatch.

### Admission

A declared stamp attribute is admissible on **every** directive and on **content
lines** (`@speaker{…}: text`), in addition to that directive's own attributes.
Key resolution order:

1. the directive's own `AttrDecl`s (or the content-line attribute set) — wins;
2. the snapshot's `stampAttrs`;
3. otherwise `E-UNKNOWN-ATTR`, unchanged.

Value typing goes through the existing attribute-type path
(`E-ATTR-TYPE` / `E-BAD-ENUM`) with no new rules.

### Lowering

An authored stamp attribute is typed by its `AttrDecl` and lands in the record's
stamp, flattened alongside the reserved keys. An **unauthored** stamp attribute
is *not* injected even when it declares a `default` — absent means absent, so a
project that authors none produces a byte-identical artifact.

### Reserved-name rejection (also closes C4)

Assembly MUST reject any attribute — `stampAttrs` **or** ordinary
per-directive — whose name collides with a reserved stamp key. This is
**`E-PLUGIN-RESERVED-STAMP-ATTR`**, a dedicated assembly-time error and not an
`E-UNKNOWN-ATTR` fallthrough:

> plugin `<id>` declares reserved stamp attribute `<name>`;
> `at`/`duration`/`delay`/`wait`/`timeline`/`provenance`/`source` are owned by
> the core stamp (plugin §14)

C4 asked for exactly this over the timing subset (`at`, `duration`, `delay`,
`wait`); 0.0.2 widens it to all seven, since `timeline`, `provenance` and
`source` are equally core-owned.

### Boundary check

`stampAttrs` adds **vocabulary**, not behavior: fixed syntax, attribute-local
validation, a finite attrs→record mapping, no new control flow, no
cross-sibling reasoning, no AST-shape change, no new ordering model. It passes
all seven data↔code tests of 0.0.1 §12 and is therefore correctly a plugin
surface.

## 5. §8 — Declarative lowering, implemented

0.0.1 §8 offered two lowering forms:

```yaml
lower: { record: <name>, fields: { … } }     # finite attrs → one record
lower: { kind: builtin, name: <hook> }       # a named core hook
```

Only the second was ever wired. This section makes the first real and pins its
narrow scope.

### `record`

`record` names one of the **non-control-flow core command kinds**:

```
background · music · sfx · vfx · sprite · camera · cut · video
```

Anything else — including `line`, `set`, `assert`, `retract`, `choice`,
`match`, `hub`, `jump`, `barrier`, `end`, `quest`, `on`, `plugin` — is
**`E-LOWER-RECORD-UNKNOWN`** at assembly time:

> directive `::<name>` lowers to unknown record `<record>`; declarative
> lowering targets the staging kinds (background, music, sfx, vfx, sprite,
> camera, cut, video)

The exclusion is not arbitrary. Control-flow kinds carry addresses resolved by
the compiler's own passes; content kinds carry identity (`lineId`/`voiceKey`)
derived from authored `code`. Neither is a finite attrs→fields mapping, so
neither is data — 0.0.1 §12 rule (4) and rule (6).

### `fields`

`fields` maps a target field of that record kind to either a `fromAttr`
reference or a literal:

```yaml
directives:
  - name: backdrop
    attrs:
      - { name: img, required: true, type: { assetKind: BG } }
    lower:
      record: background
      fields:
        assetId: { fromAttr: img }
```

An unknown target field for that record kind, or a `fromAttr` naming an
attribute the directive does not declare, is **`E-LOWER-RECORD-FIELD`** at
assembly time.

### Timing

**Validate at assembly, lower at compile.** A declaration that fails validation
never reaches lowering. At compile time the directive emits the named core
command — carrying the same resolved `stamp` it would have carried as a plugin
record — instead of `Command::Other`. An optional source attribute that was not
authored leaves its target field absent.

### Why this matters for adoption

An engine with a large closed command vocabulary currently needs a hand-written
adapter that switches on the plugin `tag` — and, in the field, a hand-copied
whitelist of supported kinds kept in sync by comment. Declarative lowering moves
that mapping into the manifest, where the checker, the LSP, and the compiler all
already read it.
