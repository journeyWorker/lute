# Lute Plugin System — 0.0.6

- **Version:** 0.0.6
- **Status:** Draft (delta on [`0.0.1`](0.0.1.md), after
  [`0.0.2`](0.0.2.md), [`0.0.3`](0.0.3.md), [`0.0.4`](0.0.4.md), and
  [`0.0.5`](0.0.5.md); shipped with Lute `0.17.0`)
- **Date:** 2026-09-14
- **Companion:** no grammar or IR-shape change. This is an author-time
  capability-admission and toolchain contract.
- **Scope:** generic project/host permission ceilings over already-declared Lute
  capabilities. It does not add a plugin export, source-authored authority, a
  runtime sandbox, an AI service, a product plugin, or reward execution.

0.0.1 remains the base specification, as amended by 0.0.2 through 0.0.5.
Everything not restated here is unchanged.

## 1. Outcome and trust boundary

A project or host MAY restrict which capabilities authored source can use.
Permissions are a **ceiling** over a normally resolved capability snapshot, not
an activation mechanism. They MUST NOT add a directive, activate a plugin,
widen a state schema, or make an otherwise-invalid document valid.

Permission policy is trusted configuration. It is accepted only from
`lute.project.yaml` and from an independently selected host permission profile.
It MUST NOT be accepted from `.lute` frontmatter, component source, plugin
manifests, plugin exports, or inline plugin activation. A source-authored
`profile:` selects capabilities but is not an authorization boundary.

The compiler rejects forbidden authored effects before producing an artifact.
This is admission control, not isolation: Lute does not execute the artifact,
contain the engine, mediate runtime bridge calls, or protect host secrets.

## 2. Project configuration

`lute.project.yaml` gains an optional project-root `permissions` object and an
optional `permissions` object inside each profile:

The published JSON Schema for the complete project file, including this strict
shape, is [`schemas/lute.project.json`](../../../schemas/lute.project.json).

```yaml
defaultProfile: authored
permissions:
  bridges: [dialogue/respond, minigame/play]
profiles:
  authored:
    plugins: {}
  generated:
    plugins: {}
    permissions:
      directives: [camera, auto, bg, music, sfx, end, set, use]
      stateWrites: [scene.*]
      factWrites: []
      bridges: []
      rewards: false
      quests: false
```

The closed shape is:

| Field | Type | Meaning |
| --- | --- | --- |
| `directives` | optional set of strings | Exact directive names without `::`, or the sole wildcard `*`. Includes parser-special-cased `set`, `assert`, `retract`, and `use`. |
| `stateWrites` | optional set of strings | Exact state paths, `*`, or a suffix-descendant pattern such as `scene.dialogue.*`. |
| `factWrites` | optional set of strings | Exact relation names or `*`. |
| `bridges` | optional set of strings | Exact `service/operation` pairs or `*`. |
| `rewards` | optional boolean | `false` denies declarative rewards; `true` adds no restriction. |
| `quests` | optional boolean | `false` denies quest declarations; `true` adds no restriction. |

An **absent field** imposes no additional restriction. An explicitly empty
list denies every member of that category. `true` is similarly unrestricted,
while `false` denies. Explicit `null`, an unknown field, a non-list/non-boolean
value, or a malformed pattern is a configuration error; it MUST NOT fall back
to unrestricted behavior.

List values are mathematical sets. Implementations MUST normalize ordering and
duplicates for deterministic serialization and hashing.

### 2.1 Pattern grammar

A directive or relation spelling is exact. `*` MAY appear only as the complete
entry. A directive is authored without its `::` sigil.

A state-write entry is one of:

- `*`;
- an exact dot path with non-empty segments; or
- an exact path followed by `.*`.

`scene.dialogue.*` admits descendants such as `scene.dialogue.line`, but does
not admit the root `scene.dialogue`, `scene.dialogueOther.line`, an empty
segment, an interior wildcard, a partial-segment wildcard, whitespace, or a
regular expression.

A bridge entry is `*` or one exact `service/operation` pair. A dotted or
otherwise ambiguous join is invalid. Unknown well-formed names in a nonempty
allowlist grant nothing; they do not become configuration errors merely because
no active capability currently declares them.

## 3. Resolution is conjunctive

The effective permission policy retains each applicable set as a separate
layer. The layers are, in order:

1. the project-root `permissions` ceiling, exactly once;
2. the reserved `global` profile's permissions, when present;
3. every ancestor in the selected profile's `extends` chain, parent first;
4. the selected profile's permissions; and
5. any trusted host-selected permission profile, resolved as its own
   project/global/ancestor/profile ceiling and applied additionally.

Within one list field, matching is OR: any entry may admit the capability.
Across layers, admission is AND: every layer that restricts the field must
admit it. Missing fields do not participate. A child profile, inline plugin
activation, or later host restriction MUST NOT widen an earlier denial.
Implementations MUST retain conjunctive layers rather than computing an
unsound textual wildcard intersection.

Existing language rules still apply. Permission to write `app.*`, for example,
does not override the language's read-only rule.

### 3.1 Shared manifest API

`lute_manifest::permissions` exposes:

```text
PermissionSet {
  directives: Option<BTreeSet<String>>,
  state_writes: Option<BTreeSet<String>>,
  fact_writes: Option<BTreeSet<String>>,
  bridges: Option<BTreeSet<String>>,
  rewards: Option<bool>,
  quests: Option<bool>
}
Permissions { layers: Vec<PermissionSet> }

Permissions::is_unrestricted() -> bool
Permissions::allows_directive(&str) -> bool
Permissions::allows_state_write(&str) -> bool
Permissions::allows_fact_write(&str) -> bool
Permissions::allows_bridge(service: &str, operation: &str) -> bool
Permissions::allows_rewards() -> bool
Permissions::allows_quests() -> bool
Permissions::restrict(&Permissions)
```

Both types are cloneable, debuggable, defaultable, equality-comparable, and
serializable with camel-case wire names. `PermissionSet` deserialization is
strict as specified in §2. `ProjectConfig` adds root
`permissions: PermissionSet` and
`profile_permissions: BTreeMap<String, PermissionSet>` while the existing
`Profile` type remains unchanged.

`project::resolve_permissions(&ProjectConfig, selected: &str)` reuses the
existing inheritance chain, returns resolver errors, and applies global exactly
once. Ordinary document snapshot resolution attaches the result.
`CapabilitySnapshot` carries `permissions: Permissions` and
`restrict_permissions(&Permissions)`, which intersects and restamps the
snapshot.

## 4. Host pinning

`check`, `compile`, `compile --all`, `compile-stream`, and `context` accept:

```text
--permission-profile NAME
```

The named profile is a trusted **additional ceiling** after ordinary document
profile/plugin resolution. It does not activate that profile's plugins, replace
the source's selected profile, or rewrite source. The project and profile must
exist; lookup and malformed-policy failures are ordinary resolver errors.

Thus source containing `profile: authored` cannot widen a host invocation pinned
with `--permission-profile generated`. `compile --all` applies the same host
ceiling independently to every document and MUST write no denied artifact.
`compile-stream` freezes the ceiling with all other resolved inputs and applies
it to both the initial template and every appended unit. There is no mid-stream
permission switch.

Rust hosts perform the same operation with:

```rust
snapshot.restrict_permissions(&host_permissions);
```

The operation intersects and restamps the snapshot. Hosts MUST consume resolver
diagnostics rather than proceeding with a partially resolved policy.

## 5. Capability identity

The effective permission layers are part of the capability snapshot and
`capabilityVersion` **only when restrictive**. An unrestricted policy is
normalized away. Therefore every policy-free existing snapshot and artifact
hash remains byte-for-byte unchanged.

Equivalent set ordering and duplicate spellings produce the same identity.
Different effective restrictive ceilings produce different identities. A
`capabilityVersion` is compatibility metadata, not proof of authorization: a
host MUST NOT accept an arbitrary externally supplied artifact hash as evidence
that trusted policy was applied.

No new artifact field is added. Existing `capabilityVersion` carries the
identity of the effective authoring surface.

## 6. Static enforcement

The checker runs one shared permission pass after ordinary resolution. It MUST
inspect authored source even in branches currently proven unreachable; policy
admits source, not an optimizer's selected execution path. An unrestricted
policy takes a fast path with no behavioral or hashing change.

The pass rejects, at the authored span:

- every forbidden directive, including specialized `::set`, `::assert`,
  `::retract`, and `::use` nodes;
- explicit state assignments, choice `into` writes, implicit choice-selection
  and hub-visit writes;
- plugin-declared `effects.writes`, resolved through invocation attributes, and
  plugin state-shape defaults or initialization;
- root/imported state defaults and seed facts (initial values are writes);
- plugin bridges independently of directive admission or declared state writes;
- every quest declaration and lifecycle/objective initialization;
- every quest/objective reward declaration, including one behind a dead guard;
- nested branch, match, hub, objective, `on`, and timeline bodies; and
- transitive invoked component bodies under the caller's policy.

A state declaration without a default remains legal read-only external context.
Builtin quest lifecycle slots are governed by `quests`, not ordinary authored
`stateWrites`; explicit quest scratch defaults still require state-write
permission. If a plugin effect's state path cannot be resolved under a
restrictive policy, checking fails closed in addition to preserving ordinary
shape/type diagnostics.

An imported component does not gain authority from its own `profile:`. Its
invoked body inherits the caller's policy. Diagnostics should preserve the
component body's related location or clearly attribute an invocation-anchored
error; an uninvoked component is not reported as executed merely because it was
imported.

`compile_with_check` MUST re-run this shared, cheap permission pass against its
input before lowering. A caller-supplied successful `CheckResult` created under
a different policy is not trusted. This gate does not re-run or reject the
project-reconciled definite-assignment analyses supplied by the ordinary
compile path. Streaming compilation inherits the same gate.

## 7. Diagnostics and tooling

Forbidden source produces non-suppressible errors through the normal diagnostic
pipeline:

| Code | Denied category |
| --- | --- |
| `E-PERMISSION-DIRECTIVE` | directive |
| `E-PERMISSION-STATE` | scalar state write or initialization |
| `E-PERMISSION-FACT` | fact/seed-fact write |
| `E-PERMISSION-BRIDGE` | bridge service/operation |
| `E-PERMISSION-REWARD` | declarative reward |
| `E-PERMISSION-QUEST` | quest declaration |

Malformed project policy keeps loader/resolver diagnostics and explicitly names
the permission context. Host-profile lookup failures use the same resolver
channel.

`lute context --json` includes the effective permission layers and filters the
directive, bridge, reward, and quest authoring surface. Read-only external state
remains visible. Because plugin write paths may depend on invocation attributes,
context does not claim to enumerate every permitted write. Text context calls
the policy a restriction and explicitly says it is not runtime sandboxing.

The LSP uses the same resolver and checker. It publishes the same permission
diagnostics and filters prohibited directive/bridge completions; it MUST NOT
implement a second authorization algorithm.

## 8. Non-goals

This delta does not:

- make an AI call or add model-specific syntax;
- add a product-specific plugin or vocabulary;
- sandbox an engine, plugin implementation, process, network, filesystem, or
  secret;
- implement reward settlement, inventory, currency, or range rolling;
- let source or plugins author their own authorization policy;
- switch permission policy in the middle of a continuation stream; or
- alter the language grammar or compiled IR shape.

## Appendix A — Compatibility

A project with no `permissions` fields behaves and hashes exactly as before.
Adding an absent profile `permissions` object is equivalent to omission. Adding
an explicit empty list is intentionally not equivalent: it denies that entire
category.
