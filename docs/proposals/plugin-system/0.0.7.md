# Lute Plugin System — 0.0.7

- **Version:** 0.0.7
- **Status:** Draft (delta on [`0.0.1`](0.0.1.md), after [`0.0.2`](0.0.2.md), [`0.0.3`](0.0.3.md), [`0.0.4`](0.0.4.md), [`0.0.5`](0.0.5.md), and [`0.0.6`](0.0.6.md); shipped with Lute `0.17.2`)
- **Date:** 2026-09-18
- **Scope:** preserve the owning plugin id on passthrough plugin IR records. No grammar change, no new source-authored capability, and no runtime execution semantics.

Everything not restated here is unchanged from 0.0.1 through 0.0.6.

## 1. Owner metadata

When a resolved plugin directive does not use declarative record lowering or a core builtin lowering hook, the compiler emits the existing plugin record:

```json
{
  "kind": "plugin",
  "addr": "001-0400",
  "plugin": "game.presentation",
  "tag": "host-panel",
  "fields": {}
}
```

`plugin` is the resolved owning plugin package id. It is not an authored attribute and cannot be overridden by source. `tag` remains the authored directive name. Together they identify the extension operation as `(plugin, tag)`.

The owner is resolved during capability assembly from the directive declaration's active plugin package. Core directives are owned by `lute.core`, but the compiler omits `plugin` from core and unresolved passthrough records. An older artifact may also omit the field.

## 2. Record classification

Owner metadata does not change command classification:

- A directive with `lower: { record: ... }` still emits the targeted core staging record, such as `background` or `sprite`.
- A directive with a named core builtin lowering hook still emits the builtin's defined core records.
- A host-owned directive without either lowering form emits `kind: "plugin"` with typed `fields`, optional `effects`, and optional `plugin` owner metadata.

Plugin ids MUST NOT become dynamic values of the IR `kind` field. `kind` remains a stable schema discriminator; `plugin` and `tag` provide extension routing identity.

## 3. Compatibility

The field is additive. Consumers MUST ignore unknown fields on a known `plugin` record and MAY use `plugin` for dispatch and diagnostics. Consumers that support older artifacts MUST treat an absent owner as an older or unresolved record and retain their existing manifest-based fallback.

The `capabilityVersion` calculation is unchanged by this delta. Plugin ids and versions are already part of the resolved capability identity; the owner map is a resolved index over that same active plugin set.

## 4. Conformance

A conforming implementation MUST:

1. preserve the resolved plugin id for an active plugin directive;
2. omit `plugin` for core and unresolved directives;
3. preserve `tag`, typed `fields`, and declared `effects` exactly as before;
4. lower declarative presentation directives to their declared core record kinds; and
5. accept older plugin records that do not contain `plugin`.
