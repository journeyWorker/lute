# Lute Plugin System — 0.0.3

- **Version:** 0.0.3
- **Status:** Draft (delta on [`0.0.1`](0.0.1.md), after [`0.0.2`](0.0.2.md))
- **Date:** 2026-07-30
- **Companion:** [`scenario-dsl/0.9.0.md`](../scenario-dsl/0.9.0.md)
- **Scope:** three changes, all to §6.10 / §8.1. `lute.core` exports an **empty**
  `enums`; an `enums` entry MAY use the long form carrying member semantics; and
  the closed `semantics` vocabulary drops two flags that had no consumer,
  **twelve → ten**. No change to activation ordering, snapshot composition,
  provider resolution, export kinds, or the data↔code boundary.

0.0.1 remains the base specification, as amended by 0.0.2. Everything not
restated here is unchanged.

## 1. Motivation

Two of the three changes remove things that were never true.

§6.10 documented `lute.core` as shipping "the language's base domains"
(`emotion`, `mood`, `volume`, `anchor`, `vfxType`, `musicAction`) and said "a
plugin MAY add further domains." In practice a plugin could not *add* any of
those six, nor could a project schema: the merged-map machinery drop-and-reports
a duplicate name, so every route to a project's own `emotion` failed. A closed
vocabulary in the one plugin nothing can influence is not a base — it is a
ceiling. dsl 0.9.0 removes it, and this delta records the consequence for the
plugin surface.

§8.1's closed flag set advertised `isStateful` and `cancelsPrevious`. **Zero
flags in that vocabulary are consumed** by the checker or the compiler today —
they are declarative — but those two are attached to no shipped directive and
have no honest consumer even in principle. A closed vocabulary must not
advertise names that do nothing.

The third change is additive: dsl 0.9.0 needs a domain declaration to carry
member-level semantics, and the `enums` export is one of the two places a
declaration can live.

## 2. §6.10 — `enums/*.yaml`, long form (amends 0.0.1 §6.10)

An `enums` entry's value MAY be either

```yaml
enums:
  # (a) shorthand — a bare sequence IS `{ members: [...] }`
  emotion: [neutral, surprised, delighted, shy, content, angry, sad]

  # (b) long form
  anchor:
    members: [left, center, right]
    default: center
  action:
    members: [fade-in-up, sway, lean, fade-out, hide]
    exits:   [fade-out, hide]
```

The shorthand is exactly the 0.0.1 form, so **every existing `enums/*.yaml`
keeps parsing byte-for-byte**. The long form's keys are:

| key | Req. | Rule |
| --- | ---- | ---- |
| `members` | MUST | the ordered list of member idents, as in the shorthand |
| `default` | MAY | the member that applies when the bound attribute is absent; MUST be one of `members` |
| `exits` | MAY | the members that exit their character; every entry MUST be one of `members` |

Slot-specific obligations, enforced at assembly with the **same validator** the
project-schema route uses (one rule set, two doors):

- A declaration named `action` **MUST** supply `exits:`; a declaration named
  `anchor` **MUST** supply `default:`. Omission is `E-ENUM-MISSING-SEMANTICS` —
  an error, never a fallback.
- For every other name, `exits:`/`default:` are meaningless and rejected with
  `E-ENUM-UNEXPECTED-SEMANTICS`, so a typo cannot hide in an ignored key.
- `E-ENUM-DEFAULT-NOT-MEMBER` / `E-ENUM-EXITS-NOT-MEMBER` for a value outside
  `members`.

An **open** (registry-style) domain has no static member list, so all four rules
are vacuous for it.

Unchanged from 0.0.1: an enum name MUST be unique across the resolved closure
(a duplicate is `E-DOMAIN-DUP`, no silent shadow), the merged domains populate
the capability snapshot's `enums`, and they therefore contribute to
`capabilityVersion` — a changed vocabulary is a changed capability surface.

### Which route surfaces where

The two declaration routes are equivalent for checking and deliberately
different for *reporting*, because they describe different things:

| route | surfaces on | reaches the compiled artifact's `enums` array |
| ----- | ----------- | --------------------------------------------- |
| plugin `enums` export | the capability snapshot — `lute context --json`'s `enums`, and `capabilityVersion` | no |
| project schema `enums:` | `lute context --json`'s `projectEnums` | yes |

A plugin-exported vocabulary is part of the capability surface an engine or
vendor ships; a project-declared one is project data that travels with the
compiled document. Declaring the same slot through **both** in one project root
is `E-DOMAIN-DUP`: pick one route per slot.
`docs/examples/showcase/plugins/showcase.pack/enums/` demonstrates the plugin
route; `docs/examples/base.schema.yaml` demonstrates the project-schema route.

## 3. §6.10 — `lute.core` exports an empty `enums` (amends 0.0.1 §6.10)

`lute.core`'s `enums.yaml` is `enums: {}`. It ships **no members for any
vocabulary**, so `load_core_snapshot().enums` and `.domains` are both empty,
pinned by a test.

The seven slot *names* still exist, as the declared types of core directive and
content-line attributes (`{ domain: emotion }`, and so on — dsl 0.9.0 §2). The
core therefore still owns which slots exist and which of them carry member
semantics; it owns none of the members.

Consequences for a plugin author:

- Exporting `enums: { emotion: [...] }` from your own capability plugin now
  **works**. It used to fail whole-project resolution with
  `E-PLUGIN-DUP-ACROSS` + `E-DOMAIN-DUP`, taking `lute context` down with it.
- If your plugin's directives bind one of the seven slots, either export the
  vocabulary or document that consuming projects must declare it — otherwise the
  first author to use your directive gets `E-DOMAIN-UNKNOWN`.

## 4. §8.1 — the closed `semantics` vocabulary: twelve flags → ten

`isStateful` and `cancelsPrevious` are **removed**. Declaring either is now
`E-PLUGIN-INVALID-DIRECTIVE` (the pre-existing unknown-flag error; no new code).

The surviving **ten**, unchanged in meaning and still declarative:

```
writes.sceneState   writes.characterState   reads.onStage
mayExitCharacter    usesAnchor              isExit
mutatesScene        requiresAnchor          bridgeCall
terminatesWalk
```

`terminatesWalk` arrived in dsl 0.8.0 with `::end` and is declared by
`lute.core`'s `::end` and by nothing else; it is counted here because 0.0.1
§8.1's enumeration predates it. The set was eleven in 0.0.1, twelve with
`terminatesWalk`, and is ten now.

The set remains **owned by the core**: a plugin MUST NOT invent flag names.
Flags declare *which* core behaviour a directive participates in; the core owns
*how*.

**Breaking only in principle.** No shipped plugin — in this repository or in the
examples — declares either removed flag, so the practical migration surface is
empty. If a third-party manifest declares one, delete the flag: it had no effect
in any released version.

Wiring the surviving flags to drive reducer dispatch remains a **non-goal**
(dsl 0.9.0 §7). `mutatesScene` is declared on both `::bg` and `::music`, so
branching on it would make `::music` clear the stage; the reducer keeps matching
on the directive tag.

## Appendix A — Diagnostic codes

No new codes. The four `enums` member-semantics errors are shared with dsl 0.9.0
and are emitted at assembly time when a **plugin** declaration violates them:

| code | severity | § |
| ---- | -------- | - |
| `E-ENUM-MISSING-SEMANTICS` | error | §2 |
| `E-ENUM-UNEXPECTED-SEMANTICS` | error | §2 |
| `E-ENUM-DEFAULT-NOT-MEMBER` | error | §2 |
| `E-ENUM-EXITS-NOT-MEMBER` | error | §2 |

Reused: `E-PLUGIN-INVALID-DIRECTIVE` (§4, a removed `semantics` flag),
`E-DOMAIN-UNKNOWN` (a slot no source declares), `E-DOMAIN-DUP` (unchanged; it
simply stops firing for the seven core slot names, which the core no longer
declares).

## Appendix C — Open items carried forward

Unchanged from 0.0.1 Appendix B and 0.0.2 Appendix C: option merge strategies
beyond override/deep-merge/replace; cross-project provider-snapshot id
canonicalization; plugin kinds other than `capability`.

Added by this delta: a plugin cannot yet declare that one of the seven slots is
**required** by its directives, so "activate my plugin and you must declare
`vfxType`" is documentation rather than a diagnostic. Deferred until a real
plugin needs it.
