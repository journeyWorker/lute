# Lute Plugin System — 0.0.4

- **Version:** 0.0.4
- **Status:** Draft (delta on [`0.0.1`](0.0.1.md), after [`0.0.2`](0.0.2.md) and [`0.0.3`](0.0.3.md))
- **Date:** 2026-08-26
- **Scope:** adds the declarative `lints` export kind for advisory content rules. It does not change activation ordering, capability resolution, grammar, lowering, or artifact identity.

0.0.1 remains the base specification, as amended by 0.0.2 and 0.0.3. Everything
not restated here is unchanged.

## 1. Motivation

A plugin can already declare the vocabulary a project authors and the capabilities
its compiler consumes. It cannot declare a project-quality assertion over that
content without putting a bespoke rule in the core. That makes ordinary editorial
policy—such as a coverage threshold for a plugin-defined attribute—needlessly
expensive to distribute.

Lints are deliberately a different surface from capabilities. A capability changes
what an author may write or how an artifact is understood; a lint reports an
advisory finding over content already understood by the core. A changed lint rule
MUST NOT change a compiled artifact or its capability identity.

## 2. §6.11 — `lints/*.yaml` (new export kind)

A plugin MAY export `lints/*.yaml`. Each file contains a YAML list of rule
objects:

```yaml
- id: variant-coverage
  target: speaker
  when: 'speaker.lines >= 10 && speaker.attrShare["variant"] < options.minShare'
  level: warn
  message: "speaker has {speaker.lines} dialogue lines"
  options:
    minShare: 0.5
```

| key | Required | Rule |
| --- | --- | --- |
| `id` | MUST | The plugin-local rule id. |
| `target` | MUST | One of `line`, `shot`, `scene`, `speaker`, `group`, or `project`. |
| `when` | MUST | A lint CEL assertion evaluated against the target's core-computed metric row. A rule fires when it evaluates `true`. |
| `level` | MAY | Default finding level: `off`, `hint`, `info`, `warn`, or `error`. It MAY be overridden by `lute.lint.yaml`. |
| `message` | MUST | A diagnostic message template, with metric/options-path interpolation. |
| `options` | MAY | Default option map, deep-merged with project overrides. |

The loader MUST retain plugin rule ids in their authored, raw form. A consuming
lint engine namespaces every active plugin rule as `<plugin-id>/<id>` for
configuration, diagnostic-code derivation, and collision-free identification. For
example, `variant-coverage` exported by `my-plugin` is
`my-plugin/variant-coverage`.

A malformed plugin lint-rule YAML entry is `E-LINT-RULE`, reported during plugin
load; the malformed entry is skipped. This diagnostic is distinct from
`E-LINT-CONFIG` (a project's lint configuration) and `E-LINT-EXPR` (an expression
that cannot be evaluated).

In this revision, the lint engine resolves ONE rule set per project root: the
**default profile's** plugin activation supplies the active plugin rules for
every document under that root (and for `project`-target rules). Narrowing
activation to each document's own resolved profile is a named future
refinement, not current behavior — a document selecting a profile that
activates extra plugins still lints under the default profile's rule set.

## 3. Capability snapshot and artifact identity

`lints` is an advisory export, not a capability export. It MUST be excluded from
the capability snapshot and from the `capabilityVersion` hash. Adding, removing,
or changing a lint rule therefore leaves the snapshot and compiled artifact
identity unchanged.

This exclusion is intentional, not an omission: engines may choose different
editorial policies without accepting different grammar, declarations, lowering, or
runtime semantics. Capability exports remain subject to the existing snapshot and
versioning rules.

## 4. Data↔code boundary check

A plugin lint is data precisely when it is a CEL assertion over the metric tables
computed by the core. It can select a row, inspect the published fields, compare
against declared options, and format those facts into its message; it does not add
a traversal, a fact, or an evaluation primitive.

Anything that needs a new metric is a core change. New metrics require the core to
define their AST traversal, scope, ordering, calculation, and stable semantics for
every consumer. Putting that request in plugin YAML would make the data declare
an algorithm, crossing the existing data↔code boundary. Likewise, executable lint
plugins, CEL macros, and stateful or non-ground evaluation are out of scope.

This export passes the boundary check: its input tables, target vocabulary, CEL
fragment, diagnostic transport, and rule evaluation are all fixed by the core;
the plugin supplies only a finite assertion, default options, and message.

## Appendix A — Diagnostic codes

| code | severity | § |
| ---- | -------- | - |
| `E-LINT-RULE` | error | §2 |

The lint engine also uses `E-LINT-CONFIG` for semantic project-config errors and
`E-LINT-EXPR` for a rule whose expression cannot be evaluated; those codes are
owned by the lint-system contract rather than by plugin loading.
