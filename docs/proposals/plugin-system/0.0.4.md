# Lute Plugin System — 0.0.4

- **Version:** 0.0.4
- **Status:** Draft (delta on [`0.0.1`](0.0.1.md), after [`0.0.2`](0.0.2.md), [`0.0.3`](0.0.3.md))
- **Date:** 2026-08-12
- **Companion:** none — no grammar or static-semantics change. This is an IR
  (artifact-shape) delta; see *irVersion* under §3.
- **Scope:** one change, entirely inside `lute-compile`. A plugin-owned
  top-level frontmatter key that passes the checker's §6.8 schema validation
  now reaches the COMPILED artifact, in a new `meta.plugin` object. No change
  to §6.8's declaration shape, to `E-FRONTMATTER-SCHEMA`'s validation rule, to
  activation ordering, snapshot composition, or the data↔code boundary.

0.0.1 remains the base specification, as amended by 0.0.2 and 0.0.3. Everything
not restated here is unchanged.

## 1. Motivation

§6.8 (0.0.1) let a plugin declare a top-level frontmatter key with a schema,
and 0.0.2 §3 made the checker enforce that schema (`E-FRONTMATTER-SCHEMA`). Both
stop at validation. `lute-compile`'s `SceneMeta`/`QuestMeta` (`crates/lute-compile/src/ir.rs`)
are closed structs — `character`/`season`/`episode`/`episodeId`/`title` for a
scene, `title`/`contentLang` for a quest — and `artifact_meta`/`quest_meta`
(`crates/lute-compile/src/lib.rs`) never read a plugin-owned key out of the raw
frontmatter mapping at all. A document author writes `cast: { ana: { costume:
school } }`, the checker proves it well-typed against the plugin's declared
schema, and `lute compile` **discards it** — the value the checker just spent a
validation pass on evaporates at the one step that turns a checked document
into something a runtime reads.

This is the same failure mode 0.0.2's motivation named for options and
timing attrs: **the manifest is trusted and checked, and the checked value is
then thrown away.** The concrete driver is a consuming project (adoption case,
per `docs/versioning.md`'s "consuming engines gate parsing on it") that wants
to author card-staging layout data — a `cardstages:` key, nested
record/map/list shapes — as scene frontmatter and read it back from the
compiled artifact at runtime, exactly the way `state:` defaults and `entities:`
already round-trip through `meta`/`state`/`entities`. Nothing about `cardstages`
is special: **any** plugin-owned key hits the identical wall, and the fix
belongs at the general boundary, not behind one plugin's name.

## 2. §4.1/§6.8 — `meta.plugin`: validated frontmatter reaches the artifact (amends IR shape)

`SceneMeta` and `QuestMeta` each gain one new field:

```rust
/// key -> already-validated value, JSON.
#[serde(skip_serializing_if = "BTreeMap::is_empty")]
pub plugin: BTreeMap<String, serde_json::Value>,
```

Wire example (scene), using the plugin-system 0.0.1 Appendix A `cast` shape:

```json
{
  "kind": "scene",
  "lute": "0.10.1",
  "irVersion": "0.10.1",
  "capabilityVersion": "…",
  "meta": {
    "character": "bianca",
    "season": 1,
    "episode": 2,
    "episodeId": "s01ep02",
    "plugin": {
      "cast": { "ana": { "costume": "school", "sealed": false, "maskAs": "???" } }
    }
  }
}
```

**Membership rule (normative).** A key `k` with authored value `v` (the raw
YAML the document's `---` block parsed to) is admitted into `meta.plugin` iff
**both**:

1. `k` is present in the resolved capability snapshot's `frontmatter` map
   (`CapabilitySnapshot.frontmatter: BTreeMap<String, Type>`) — by
   construction of snapshot resolution (§11), a key present there is declared
   by an **active** plugin. A core key, an unknown key, or a key an inactive
   plugin would have declared is never a candidate.
2. `Literal::from_yaml(v)` produces a `Literal` and `type_accepts(ty, &lit)`
   holds for `ty = snapshot.frontmatter[k]` — the **exact same predicate**
   0.0.2 §3 gates `E-FRONTMATTER-SCHEMA` on (`crates/lute-check/src/meta.rs`).

Value conversion is `Literal` → `serde_json::Value` via `lute-compile`'s
existing `literal_json` (the same function every `state:` `default:` and
`::set{}` literal already serializes through) — **no independent YAML→JSON
path is introduced.** `Literal::Map` is a `BTreeMap`, so nested record/map
values are already key-sorted before `literal_json` ever runs; the top-level
fold into `meta.plugin` uses a `BTreeMap` too. **Deterministic serialization
is MUST, not incidental**: two compiles of the same document produce
byte-identical `meta.plugin` JSON, at every nesting depth, with no dependence
on YAML mapping order.

**Never a second validation pass, in spirit.** `lute-compile::compile`
(`= compile_with_check(input, check(input), _)`) only reaches artifact
construction past the D6 check gate on the SAME snapshot the checker validated
against, so in the ordinary path rule 2 above already holds for every
candidate key before `lute-compile` ever looks at it — the checker would have
refused the document otherwise, and `compile` would have returned `Err`. The
re-check inside `lute-compile` is **defense in depth**, not a second source of
truth: it exists because `compile_with_check`'s caller-supplied-`CheckResult`
seam (the project-aware CLI gate, `compile_with_check`'s own doc comment) lets
a caller assert `ok: true` without `lute-compile` itself having derived it. A
key the checker would reject — wrong type, or no active plugin owner — MUST
NOT reach `meta.plugin` regardless of which gate produced the `CheckResult`;
`lute-compile` re-derives ownership from `snapshot.frontmatter` and re-runs
`type_accepts` itself rather than trusting the caller's `ok`.

**Absent means absent, not `{}`.** `plugin` carries `skip_serializing_if =
"BTreeMap::is_empty"`, mirroring `title`/`domain`/`default` elsewhere in the
envelope: a document that authors no plugin-owned key produces the exact same
bytes it produced before this delta. This is why the change needs **no**
migration for `lute.core`-only documents — every fixture and golden in the
existing corpus declares no plugin frontmatter and is therefore untouched.

**Scene AND quest, same rule.** §6.1's frontmatter validation does not
distinguish document kind (a plugin-owned key is legal frontmatter on either),
so both `SceneMeta.plugin` and `QuestMeta.plugin` exist and are populated by
the same `plugin_frontmatter` helper.

### Boundary check (0.0.1 §12)

This is pure **passthrough of already-checked data** — no new control flow,
no lowering decision, no cross-sibling reasoning, no inference. The compiler
does not decide *whether* a value is admissible (the checker already decided
that); it copies a value from one typed representation (`Literal`, checker-
validated) to another (`serde_json::Value`) through a conversion that already
exists for a different field. It is not a new golden-test surface in the
directive sense (§12's golden-test gate is about directive *behavior*); the
existing round-trip tests (this delta's §4) are the equivalent discipline for
a data-shape addition.

## 3. irVersion

`meta.plugin` is a **real, additive change to the compiled artifact schema** —
per `docs/versioning.md`, that is unconditionally an **IR** axis change ("Change
the compiled artifact's shape → IR, and toolchain"). It does **not** change
`capabilityVersion`: the declared key/schema pairs the plugin exports were
already part of the capability snapshot and its version hash (0.0.1 §6.8) —
only whether the compiler *acts* on that already-hashed declaration changed.

This delta deliberately does **not** bump `LUTE_IR_VERSION` (staying `0.10.1`)
or touch `schemas/lute-ir-0.10.schema.json`. Both are release-cut actions this
repository performs together with re-aligning `LUTE_LANG_VERSION` and the
toolchain `CARGO_PKG_VERSION` (`docs/versioning.md` "Alignment": *"every
release re-aligns every visible axis number to that release's number"*), which
this delta is not — it ships no language change (no companion `scenario-dsl`
spec; §0 above says so explicitly) and no toolchain release. Bumping `irVersion`
alone here would either desynchronize the three axes (breaking the alignment
invariant, and the `lang_and_ir_version_stamps` test that pins it) or force an
unrelated language/toolchain version bump to manufacture agreement. Precedent:
`0.10.1` shows the reverse case working (all three axes moved though only the
toolchain substantively did); this delta is the mirror — the shape genuinely
moves, but the version number waits for a real release to carry it, exactly as
`0.8.0`'s `end`-command IR addition and `0.10.0`'s `provenance.explanation`
rename were both landed as part of a numbered release, never as a bare
mid-cycle constant bump.

**Consequence, stated plainly:** as of this delta, `lute compile` emits
`meta.plugin` under the `irVersion: "0.10.1"` stamp, while
`schemas/lute-ir-0.10.schema.json`'s `sceneMeta`/`questMeta` still declare
`"additionalProperties": false` and would reject that field under strict
schema validation. This is intentional and temporary: the code ships now (an
`oshiz`-style consumer with a permissive JSON parser reads `meta.plugin`
today), and the schema catches up to what shipped — the same order 0.8.0 and
0.10.0's shape changes landed in — at the next coordinated release, which also
bumps `LUTE_IR_VERSION` and (per the `major.minor` gate,
`docs/runtime/execution-model.md`) requires nothing else from an existing
engine: `meta.plugin` is purely additive, so an engine still on the *next*
`irVersion` gate that simply ignores an unknown envelope key already round-trips
unaffected.

## Appendix C — Open items carried forward

Unchanged from 0.0.1 Appendix B / 0.0.2 Appendix C / 0.0.3 Appendix C: option
merge strategies beyond override/deep-merge/replace; cross-project
provider-snapshot id canonicalization; plugin kinds other than `capability`; a
plugin declaring a required slot.

Added by this delta:

- `schemas/lute-ir-0.10.schema.json`'s `sceneMeta`/`questMeta` definitions need
  a `plugin` property (and, per the file's own precedent, possibly a renamed
  schema file) at the next IR-axis release — deferred deliberately (§3), not
  forgotten.
- A plugin cannot yet declare a frontmatter key **required** (present in every
  document, or every document under a profile) — today an author simply omits
  it and the key is absent from `meta.plugin`, same as any other optional
  field. No plugin has asked for this; filed for the same reason as the
  required-slot item above.
