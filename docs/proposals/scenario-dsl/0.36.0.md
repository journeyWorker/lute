# Scenario DSL 0.36.0

Phase 5 of `docs/design/architecture-direction.md` (§5): identity is
explicit and reviewable, authored renames are migration data rather than
remove/add guesses, and performance is a measured CI contract. This is a
clean cutover under D6. The dogfood corpus is migrated in this release; no
legacy identity mode, compatibility alias, or ordinal component identity
remains after the cutover.

The authoritative inputs remain `.lute` documents and project declarations
(D2). The project semantic model remains internal (D3). The execution IR and
project index are public, versioned engine inputs. `addr` remains a build-local
position and is never a save, localization, patch, or identity key.

The current implementation facts that this specification closes are recorded
in the phase-5 inventories. In particular, normalization currently stamps
component scopes as `{component}#{n}` (`crates/lute-compile/src/normalize.rs:35-50`),
line code allocation and `lute tag` are separate source/back-fill paths
(`crates/lute-compile/src/address.rs:284-327`; `crates/lute-check/src/tag.rs:23-32`),
`NodeKey` is a `(NodeKind, key)` pair (`crates/lute-model/src/graph.rs:60-76`),
and the current diff compares the key union (`crates/lute-model/src/diff.rs:500-548`).
The release makes the identity and migration contracts below the only valid
interpretation.

## 1. Identity contract

### 1.1 One identity vocabulary

Lute has no second identity store and adds no universal `nodeId`. A canonical
identity is one of:

1. an authored key declared by the construct or project declaration;
2. the canonical document key from `meta.id`;
3. a per-speaker `code`, which is rendered into `lineId` and `voiceKey`;
4. a component instance key declared on `::use`;
5. a compiler-generated fallback explicitly marked as unstable and diagnosed;
   or
6. `addr`, but only as a build-local position for execution ordering and
   control-flow target resolution.

`NodeKey` continues to serialize as `kind:key`; the key is opaque to callers
except where a language rule below defines its source. Patch targets, semantic
diff, LSP identity metadata, source maps, and save migration all consume this
same vocabulary. A caller MUST NOT derive identity from byte spans, command
array position, formatted text, or `addr`.

### 1.2 Normative identity table

resume, localization/voice join, or durable engine record; an emitted field

source of the identity is unchanged; `N` means it changes; `conditional`
identifies the prerequisite.

The source of truth for current save-shaped keys is the runtime session state:
quest, entry, visited, once/share, facts, state, accepts, and bridge queues
(`crates/lute-trace/src/exec/session/world.rs:28-58`; `crates/lute-trace/src/exec/mod.rs:163-177`).
`lineId` and `voiceKey` are durable content joins, not entries in that state
map (`crates/lute-compile/src/locale.rs:1-18`).

### 1.3 `addr` and generated fallbacks

`addr` is assigned after lowering and is regenerated when command order changes
(`crates/lute-compile/src/address.rs:84-109`). It MAY appear in execution
traces, source maps, and jump targets, but MUST NOT appear as a `NodeKey`,
localization key, patch target, save key, fingerprint, or rename-ledger key.

A fallback identity is valid only when all of the following hold:

- the construct has no author-declarable key in the current source grammar;
- the fallback is deterministic within its owner;
- its output carries a warning naming the construct and the command to make it
  explicit; and
- `check-project --deny-warnings` rejects the project until the dogfood corpus
  has been tagged.

A warning-bearing fallback is never silently promoted to a stable identity.

## 2. Stable component instance keys

### 2.1 Source spelling and scope

A component invocation MAY declare an instance key with the reserved `instance`
attribute:

```lute
::use{component="hearthFire" instance="opening" flare="high"}
```

`instance` is not passed as a component parameter. It is an identity
attribute. Its value MUST be a non-empty ASCII token matching
`[A-Za-z][A-Za-z0-9_-]{0,63}`. The canonical scope segment is
`{component}#{instance}`; the segment remains readable in existing line-id
shapes but the suffix is now an authored key, never an ordinal. Thus the
example produces a component scope containing `hearthFire#opening`, not
`hearthFire#1`.

Uniqueness is checked in the immediate expansion owner: two uses of the same
component name with the same `instance` in one host body are an error even if
conditional branches are mutually exclusive. Nested uses have a separate
immediate owner scope and are made globally unambiguous by their complete
scope path. A key may be reused for a different component name or in a
separate host scope. The same rule applies to component definitions imported
through a diamond: the host use site, not the import path, owns uniqueness.

The full component scope is used consistently by:

- normalized `Source.scope` and source-map provenance;
- `lineId` and `voiceKey` for expanded lines;
- expanded-line `NodeKey` and graph ownership;
- semantic diff matching and `componentAmbiguous` reporting;
- patch `component_fingerprints` and preserve checks;
- LSP node identity and references; and
- documentation examples and generated index data.

No consumer may reconstruct an instance by counting sibling uses.

### 2.2 Untagged fallback and `lute tag`

A missing `instance` uses the old positional ordinal as an untagged
fallback; the fallback is always marked non-stable (`stable: false`) in
model/diff output. An explicit key never moves when an earlier use is
inserted.

Stability is **required per project**, not per file: a project opts in with

```yaml
identity:
  requireStable: true
```

in `lute.project.yaml`. Under that flag every document the project checks
emits `W-COMPONENT-INSTANCE-UNTAGGED` for each `::use` without `instance` and
`W-LINE-CODE-UNTAGGED` for each content line without a per-speaker `code`.
Without the flag (the default, and always for standalone files and snippets)
neither warning is emitted: a draft or a tutorial is not noise, and its ids
are still reported as non-stable wherever identity is surfaced. A project
publishes content joins or saves ⇒ it sets the flag, and `check-project
--deny-warnings` then keeps it fully tagged.

`lute tag` becomes the single corpus migration command for both identity axes:

1. parse/check the project and refuse to rewrite structurally broken inputs;
2. preserve every authored line `code` and `instance` byte-for-byte;
3. allocate missing line codes per existing speaker/scope policy;
4. allocate missing component instances in source order, using the smallest
   available decimal-free token `use-001`, `use-002`, … within each owner and
   component; and
5. write only changed source files, with a second run being a no-op.

The generated `use-001` spelling is deliberately explicit and is treated as
an authored key after writing. A project MAY replace it with a domain-specific
key later; that edit is a rename of expanded identities and MUST be represented
in the rename ledger when published save/content joins are affected.

Uncoded lines get the same treatment. Every dogfood game under
`docs/examples/games/*` sets `identity.requireStable: true`; the release
migration runs `lute tag` over every dogfood project, then
`check-project --deny-warnings`, so no release game retains either warning.

`lute tag --force` retains its existing meaning of force-retagging line codes
and MUST NOT rewrite an explicit component `instance`. It is refused when
`codesLocked` is present, as today (`crates/lute-check/src/tag.rs:198-208`),
and remains the only operation that can deliberately sever published line
joins. Normal `lute tag` may add missing line codes and missing instance keys
under `codesLocked`; it MUST NOT change an existing code/key. There is no
`--force-instances` mode in 0.36. A user who wants to rename an instance edits
source and supplies a ledger entry; positional renumbering is never a repair.

### 2.3 Diagnostics

0.36 adds these stable registry entries to
`crates/lute-cli/src/codes.rs`; the English and Korean diagnostic pages MUST
contain one matching section for each code, in registry order:

| Code | Grade | Raised when |
|---|---|---|
| `E-COMPONENT-INSTANCE-INVALID` | error | `instance` is empty, exceeds 64 characters, uses a non-ASCII token, or appears more than once as an identity attribute on one `::use`. |
| `E-COMPONENT-INSTANCE-DUPLICATE` | error | the same component and instance key occur twice in one immediate expansion owner. |
| `W-COMPONENT-INSTANCE-UNTAGGED` | warning | `identity.requireStable` is set and a `::use` has no explicit `instance` (positional fallback). |
| `W-LINE-CODE-UNTAGGED` | warning | `identity.requireStable` is set and a content line has no explicit per-speaker `code` (compiler allocation). |
| `E-RENAME-LEDGER` | error | a rename entry is malformed, has an unknown kind/key, duplicates a source or destination, or is not a canonical key mapping. |
| `E-RENAME-LEDGER-STALE` | error | a ledger source key is still present, or its destination key is absent after project resolution. |
| `E-RENAME-LEDGER-CYCLE` | error | rename entries form a chain, self-loop, or cycle. |

The error diagnostics point to the declaration in `lute.project.yaml` or the
use site. Warnings point to the missing attribute and include the exact
`lute tag` command. JSON carries `identity` (`source`, `computed`, `stable`)
and, for component diagnostics, `component`, `instance`, and `scope` fields.
`lute --explain` and both reference pages are normative projections of the
registry, not separately authored message contracts.

## 3. Rename ledger and save migration

### 3.1 Manifest schema

The project manifest gains this exact optional block:

```yaml
identity:
  requireStable: true            # optional, default false (§2.2)
  renames:
    "quest:oldName": "quest:newName"
    "line:old.scene.narrator_0010": "line:new.scene.narrator_0010"
```

`identity.renames` is a YAML mapping from one old canonical `NodeKey` string
to one new canonical `NodeKey` string. Keys are opaque strings after
`kind:` parsing and are serialized in lexical order. A mapping value is not a
wildcard, path, regular expression, or sequence.

The checker resolves the project before validating the ledger and requires:

- every `from` key is absent from the new graph;
- every `to` key is present in the new graph;
- each source and destination occurs at most once;
- no source is also a destination (this forbids chains); and
- no mapping is a self-loop or cycle.

A ledger is an authored migration declaration, not a suggestion. File moves
with an unchanged canonical key remain `moved` and do not require a ledger.
The checker does not have a before-state and therefore does not infer a
rename or reject a missing mapping. Instead, `lute diff` marks an unmapped
removed-plus-added pair whose old node is a save-shaped kind with
`unmappedIdentity: true` in JSON (and the equivalent human review marker).
This is a review signal, not a checker error.

### 3.2 Diff, IR, and project index

`lute diff` adds `renamed` as a first-class change kind. A rename includes
`from`, `to`, both source locations when present, and the ledger declaration
location. It MUST NOT also emit a removed and added pair for the same mapped
identity. An unmapped key change remains removed plus added; when the old
identity is save-shaped, the JSON change carries `unmappedIdentity: true`.

The execution IR and project index expose the resolved, sorted ledger using
this exact camel-case field and value shape:

```json
{
  "identityRenames": [
    { "from": "quest:oldName", "to": "quest:newName" }
  ]
}
```

`ExecutionIr.identityRenames` is the ledger relevant to that artifact;
`ProjectIndex.identityRenames` is the project union. An empty list is omitted
from JSON. Both structures carry the same `irVersion`/schema contract as the
existing public fields (`ExecutionIr` begins with version/capability fields at
`crates/lute-compile/src/ir.rs:16-31`; `ProjectIndex` carries the corresponding
project fields at `crates/lute-compile/src/index.rs:177-183`). The compiler
registers `lute.identity.renames/1` in the 0.33 semantic-id registry when that
registry is the authority for artifact behavior, adds it to
`requiredSemantics` whenever `identityRenames` is non-empty, and includes it in
the project union. If the registry implementation is not yet split out, the
0.36 registry change creates it before the field is emitted; no engine may
silently ignore this meaning-bearing field.

An engine that supports the semantic id MUST apply all ledger entries before
reading save state, atomically and in deterministic `from` order. It migrates
all matching durable locations (quest/objective/entry/visited/once/share/state,
base facts, and any engine-owned key explicitly declared by the engine), keeps
a migration report, and refuses partial application. Lute does not own the
save format or settlement of engine-owned state; it owns the ledger contract
and conformance fixtures.
Before mutating a save, the engine MUST detect a destination collision: if a
save already contains durable state under a `to` key, migration MUST refuse
the entire ledger before changing any key unless the existing destination
value is equal to the value that would be moved there. Equal values MAY be
coalesced deterministically; unequal or differently typed values are a hard
failure. The engine MUST report the colliding `from`/`to` keys and leave the
original save byte-identical.

### 3.3 Diff and patch interaction

`NodeKey` matching first applies the validated ledger, then compares the
mapped nodes. `preserve: {"ids": [...]}` treats a mapped old key and its new
key as the same identity. `lineIds`, `voiceKeys`, and component instance
preserves still compare the emitted joins. A missing or ambiguous component
fingerprint is a refusal, not a best-effort match.

Patch preserve and diff fingerprinting remain internal implementation details.
Where an internal component fingerprint is used, it MUST contain the
component name, explicit instance key, complete enclosing scope, and
source-origin key, never an ordinal or byte offset. An ambiguous fingerprint
is a refusal, not a best-effort match. The existing internal
`componentAmbiguous` finding (`crates/lute-model/src/patch.rs:566-635`) is
updated to use the explicit instance key; neither `component_fingerprints` nor
`componentAmbiguous` is a public patch request/report field.

## 4. Breaking changes and migration policy

### 4.1 0.36 CHANGELOG contract

The `0.36.0` release section in `CHANGELOG.md` MUST contain a `Breaking`
section with exactly these class headings, even when one class says “None”:

- `#### Syntax`
- `#### Semantics`
- `#### IR`
- `#### Plugin`
- `#### CLI`
- `#### Diagnostics`
- `#### Identity`

From 0.36 onward, every breaking item is listed under exactly one primary
class; cross-cutting items may link to the related class but are not duplicated.
`lute fix` or a one-shot codemod MUST ship in the same release for every
syntax break. The class headings are a documentation invariant enforced by
`scripts/check-docs-consistency.py` for the current release; the checker also
rejects a current release section that omits the heading or uses a different
spelling.

0.36 remains under D6: no legacy loader, alias, dual identity mode, or
compatibility switch is accepted. The corpus migration, `lute tag` output,
ledger entries, docs, and tests land together. CLI and diagnostic JSON changes
are breaking classes even when the source grammar is unchanged. Plugin names,
capability snapshots, and external operation keys are Plugin breaks.

### 4.2 After D6 ends

D6 ends at the first external consumer, as stated by the architecture
direction (`docs/design/architecture-direction.md:158-166`). At that point
new releases enter an explicitly announced deprecation window for source and
CLI contracts: the old form may be accepted for the window, `lute fix` remains
the prescribed migration, and the CHANGELOG names the first and last release
of the window. Execution-IR meanings do not become silently optional: D5
required-semantics negotiation and capability matrices refuse unsupported
artifacts before playback. No external-consumer exception is applied to
0.36; D6 clean cutover is still in force for this release.

## 5. Benchmark gates

### 5.1 Corpus and phases

The benchmark tiers are fixed and are not selected by size heuristics:

| Tier | Project |
|---|---|
| tiny | `docs/examples/games/ledger` |
| medium | `docs/examples/games/drowned-crown` |
| large | `docs/examples/games/monster-league` |

The harness measures these phases separately for every tier, using library
calls inside one benchmark process rather than spawning `lute` subprocesses:

1. **cold load** — a fresh `ProjectModel`/input cache discovers and reads the
   project for each measured iteration;
2. **project resolution** — `ProjectModel` construction, including model
   build/fold/reconcile inputs but not deferred graph work;
3. **analysis** — checker/project reconciliation and graph-backed analysis;
   the harness forces `ProjectModel::graph()` in this phase;
4. **serialization** — execution IR and project index serialization; and
5. **playback** — the existing `lute test` playback semantics through the
   library test runner, not a CLI process.

The graph is lazy (`ProjectModel::graph()` at
`crates/lute-model/src/project.rs:298-301`), so the harness MUST force it in
analysis and MUST NOT hide it in resolution. Serialization MUST measure
`serde_json` IR and index output, not file copying. Every phase is a
repeatable in-process closure over the fixed project.

### 5.2 Harness and JSON

Add the fixed, non-publishable workspace crate `crates/lute-bench`
(`publish = false`). It accepts `--root <checkout>` (tier projects resolve
under it), `--tier tiny|medium|large|all`, `--phase <name>|all`, `--samples
<n>`, and `--json <path>|-`. For each sample it loops the phase closure until at least
**200 ms** elapsed, records the iteration count, and reports per-iteration
time. It emits one deterministic JSON document:

```json
{
  "schemaVersion": "0.36.0.bench",
  "commit": "…",
  "runner": {"os":"linux","arch":"aarch64","cpu":"…"},
  "binary": {"label":"base|head","profile":"release"},
  "samples": [
    {
      "tier":"medium", "project":"drowned-crown", "phase":"analysis",
      "sample":0, "iterations":128, "elapsedMs":256.4,
      "perIterationUs":2003.1, "exit":"ok"
    }
  ]
}
```

The report records test count and an error instead of a sample when a phase
fails. It never reports a missing sample as zero. JSON keys, sample order,
phase names, and iteration accounting are stable.

### 5.3 Same-runner A/B gate

Performance is a separate CI job and the release gate. It checks out the pull
request merge base in a temporary git worktree, builds only `-p lute-bench`
with `--release`, copies the resulting benchmark binary aside, then builds
the pull-request revision with `--release` in the same `CARGO_TARGET_DIR` and
copies that binary aside. Each binary runs against its own revision's tier
inputs (`--root` = the merge-base worktree for base, the PR checkout for
head), and the comparator reports which tiers' project revisions differ so a
content-driven change is visible. A driver (`scripts/bench-ab.py`) alternates
single-sample invocations of the two binaries on the same runner. When the
merge base has no `crates/lute-bench` (the 0.36 PR itself) the job runs the
head binary only, uploads its report, and passes with that notice. Both
builds reuse locked dependency artifacts, the same toolchain and the same
build hygiene; no `cargo clean` is run.

For each tier and phase, the harness executes seven samples per side in an
interleaved order `base/head/base/head/...`; each sample independently loops
until 200 ms. It compares medians of per-iteration times. A cell fails when
`head_median / base_median > 1.10`, with no absolute floor. A missing sample,
malformed JSON, cancelled job, or runner mismatch fails the gate. No aggregate
average may hide a large-tier regression.

The expected job duration is **under 10 minutes** on the pinned
`ubuntu-latest` runner, including two `-p lute-bench --release` builds and
all 3 × 5 × 14 in-process sample cells; CI records actual duration and keeps
reports as artifacts. A deliberate regression is accepted only with an
explicit `performance-approved` pull-request label, a CHANGELOG/plan note
naming the affected tier and phase, retained before/after JSON, and review by
an owner of the affected crate. The A/B job still runs and publishes the
failed comparison; the label is an auditable exception, not a disabled job or
a new threshold.

## 6. D11 property and documentation hygiene

### 6.1 Bounded property tests

0.36 adds bounded property tests (proptest or an equivalent deterministic
property runner) with one fixed seed (recorded in the test module and in any
failure report), fixed case/input limits, and a CI budget of **under 30
seconds for the complete property suite**:

- formatter idempotence: `fmt(fmt(x)) == fmt(x)` for generated source and
  corpus samples;
- execution IR serialize/deserialize round trip: valid generated IR and
  corpus artifacts serialize, deserialize, and compare semantically; and
- parser totality: arbitrary byte/string input up to 4 KiB never panics, with
  parser errors returned as values.

The generator uses deterministic RNG configuration (seed `0x0360_2026_10_05`)
and bounded case counts. A failing case persists its minimized input and seed
as a local replay artifact; CI reruns that seed before reporting failure.
These are behavior properties, not snapshots of incidental error wording. The
existing formatter invariants in the 0.35 proposal
(`docs/proposals/scenario-dsl/0.35.0.md:96-111`) remain required.

### 6.2 Status markers and handbook

Every document under `docs/proposals`, `docs/design`, and `docs/superpowers`
MUST begin with one controlled status: `Draft`, `Accepted`, `Implemented`,
`Superseded`, or `Rejected`. Historical documents are not rewritten to claim
current behavior; their status records their historical state. In particular,
`docs/design/runtime-unification.md` is marked `Implemented` because its
`Machine` landed, replacing the stale “design for wave 2” marker. The docs
consistency script checks status vocabulary and the current-release CHANGELOG
class headings.

The current-rules handbook is updated in the same release. Its identity page
(or, until a dedicated page exists, `docs/handbook/core.md`) reproduces the
normative identity table from §1.2, including the persistence column and the
four stability axes. The handbook states that `addr` is positional, explicit
component `instance` keys are required, and untagged lines/uses are warning
bearing until `lute tag` runs. Release proposals remain the historical reason
for a rule; the handbook is the current rule.

## 7. Acceptance and conformance

The release is complete only when all of the following are true:

1. inserting a component use before any existing use leaves all explicit
   instance-scoped line IDs, voice keys, NodeKeys, diff matches, patch
   preserves, LSP identity metadata, and index entries unchanged;
2. every dogfood project is `lute tag`ged and passes
   `check-project --deny-warnings`;
3. duplicate/invalid instance keys and all ledger failure modes produce the
   registered codes in CLI JSON, human output, `--explain`, English docs, and
   Korean docs;
4. a parent/document rename with a ledger is one `renamed` diff and produces
   an IR/index ledger usable by a save migrator; a missing/stale/cyclic ledger
   fails before compilation;
5. every 0.36 syntax break has a same-release `lute fix` rule and every
   breaking class is present in the CHANGELOG;
6. the A/B benchmark job runs all three fixed tiers and all phases in-process,
   rejects a median ratio over `1.10` for any tier/phase, and retains its JSON
   report;
7. the three bounded property tests pass; and
8. the complete existing suite and dogfood scenario tests pass after the
   corpus cutover.

Conformance fixtures MUST include: inserting an earlier component use;
explicit and generated instance keys; duplicate keys in mutually exclusive
branches; nested components; `codesLocked` with normal and force tag; each
rename-ledger validation failure; a quest/line/state rename migration; a save
with unequal destination state that proves the engine refuses the whole
migration before mutation; a pure file move; an unmapped save-shaped
removed/added pair carrying `unmappedIdentity: true`; a formatter-only change;
and a deliberate benchmark comparison fixture. Runtime conformance compares
declared observables, not rendering.

| Decision | Chosen rule | Rejected alternative | Reason |
|---|---|---|---|
| component key spelling | `instance="token"`, scope `{component}#{instance}` | keep ordinal `{component}#{n}` | preserves readable scope while making the suffix authored and stable |
| key uniqueness | same component + key in one immediate expansion owner | project-global key namespace | permits reusable components without accidental cross-document coupling |
| missing instance | warning-bearing positional fallback, then `lute tag` | silently accept ordinal forever | clean cutover and `--deny-warnings` make identity debt visible |
| force retag | `--force` changes line codes only; never instance keys | force-renumber all identities | line joins are already guarded by `codesLocked`; instance keys need intentional source edits |
| rename representation | manifest mapping `identity.renames` | inferred delete/add or hidden alias table | authored, checkable, engine-visible save migration |
| diff result | `renamed` | removed + added | preserves user intent and lets engines migrate saves |
