# Scenario DSL 0.34.0

Phase 3 of `docs/design/architecture-direction.md` (§5): one project semantic
model, a dependency graph and impact query, author constraints, and explicit
evidence on analyses. This is a clean cutover under D6; the model is an
internal read-only query surface, while source and execution IR retain their
roles under D2/D3. All language, IR, and toolchain axes are `0.34.0`.

## 1. Project model

### 1.1 One model and its ownership

The new `lute-model` library crate owns project loading and the per-invocation
input cache moved from `lute-cli`'s `input.rs`, `input_cache.rs`, and
`project/mod.rs`. It owns root resolution, per-document check/fold, project
reconciliation, compilation of clean non-component documents with their
`SourceMap`s, and the `ProjectIndex`. This consolidates the currently split
`CheckInput`/`Document`/`FoldedEnv`, `ByRoot`, compiled-artifact, and
`ProjectIndex` shapes (inventory: `docs/design/phase3-inventory/project-model.md:70-72,98-104`).

`ProjectModel` is built per project root. The root is the nearest manifest
ancestor, bounded by the directory supplied to a recursive walk: this is the
rule currently used by single-file discovery and project collection
(`crates/lute-cli/src/cmd_check.rs:548-556`; `crates/lute-cli/src/project/mod.rs:56-77,89-116`).
A walk containing several roots builds one model per root. `play` and `calendar`
use the model of the root at the supplied directory; they do not force the
supplied directory to be one root (the current forced-root divergence is
recorded at `docs/design/phase3-inventory/project-model.md:100-103`).

The model performs, in order: assemble each input (manifest/defaults,
providers, capability snapshot, schema imports, components, identity), parse,
fold and check each document, reconcile the root, compile clean non-component
documents, build the index, then join analyses into the semantic graph. Input
assembly remains the shared operation currently described at
`crates/lute-cli/src/input.rs:99-110,145-232`; component files are not runtime
artifacts, matching the current project compile pass
(`crates/lute-cli/src/play/project.rs:95-100,132-148`).

### 1.2 Consumers

`check-project`, `context`, `scenario`, `beats`, `impact`, `calendar`, `play`,
and `test` build their reports from `ProjectModel`. Single-file `check`,
`trace`, and `compile` use the same input assembly, but do not require a
project-wide query unless their command contract requests one. `run` remains
artifact-only and does not load source, manifests, schemas, or plugins
(`crates/lute-cli/src/runner.rs:78-126`).

The LSP uses the same assembly with `Mode::Author`; it retains document/result
caches but does not gain project-wide semantic-model caching in 0.34. The
current LSP reconstructs `CheckInput` with author mode and resolves manifest,
providers, snapshot, imports, and components per analysis
(`crates/lute-lsp/src/backend.rs:228-285,735-791`; `crates/lute-lsp/src/lint.rs:1-10`).
Phase 5 will measure before changing that policy.

## 2. Semantic graph

The model exposes a deterministic, internal graph. Every node has a stable
kind-specific key, declaration/source span where available, and owning root.
Every edge has `sourceSpan`, a `reason` describing the matched expression,
expansion, ownership, or evaluation rule, and an evidence level when the link
is not a pure syntactic join. Source spans join checker analyses to compiled
identity through `SourceMap`, which maps addresses and construct side tables
(`crates/lute-compile/src/source_map.rs:1-20,80-199`; stable line identities are
allocated in `crates/lute-compile/src/address.rs:253-355`).

### 2.1 Node kinds and keys

| kind | key |
|---|---|
| project/document | root path; document `meta.id` plus canonical path |
| scene/scene beat/shot | document id + authored scene/beat/shot id; shot key is document + source address when no authored id exists |
| line | document id + `lineId` (with `voiceKey` as its content join) |
| choice/option | containing node id + authored choice/option id |
| quest/objective | quest id; objective `quest.objective` |
| reward | owner (`quest` or `quest.objective`) + declaration index |
| lore entry/bundle beat | document id + entry/beat id |
| occasion/occasion gate | occasion name; gate declaration key |
| relation/state path | relation name; canonical dotted CEL path |
| `@def`/component use | definition name; document path + source span/use ordinal |
| component-expanded node | use key + expanded source node key |
| fact pattern | relation + normalized arguments (wildcards preserved) |
| clock/season | declared clock/season id |
| engine boundary | reserved relation or engine-owned state path/event boundary key |

The line key follows the existing distinction between regenerated positional
`addr` and stable `lineId`/`voiceKey` (`crates/lute-compile/src/address.rs:1-3,253-355`).
Rewards are separate graph nodes even though they remain nested in IR owner
records (`crates/lute-compile/src/ir.rs:1404-1418,1506-1530`).

### 2.2 Edge kinds and feeds

| edge | source/reason | model-owned feed |
|---|---|---|
| `reads` | state path, role, enclosing slot, and source span | A model adapter walks each document's folded/expanded AST (reusing `cel_paths` walking logic, made public as needed) and records every authored and expanded state-path read and write. |
| `queries` | fact atom used by `holds`, negated queries, `count`, `countDistinct`, or `validAt` | The same span-bearing walk records every query form, including nested CEL and relation patterns. |
| `writes` | state write or authored effect, with exact command span | The walk records every write, rather than treating `defassign`'s final must-write set as authored provenance. |
| `asserts`/`retracts` | fact pattern written by command/effect, with exact span | A public/model adapter emits all fact write patterns and their source text; the legacy `fact_edges` feed remains unchanged for `scenario --facts`. |
| `derives` | Datalog head <- body, with bindings and full closure | The model records the complete least-fixpoint closure over rule heads and bodies, including variable bindings. |
| `contains` | scene/entry/beat/quest contains line, choice, objective, or reward | Parsed structure and compiler side tables, with reward declarations added to the compiler's `SourceMap` tables (owner, declaration index, and span). |
| `gates` | `when`, `start`, `done`, `visibleWhen`, `by`, `until`, `raisedWhen`, `after`, `visited(x)`, `completed`, or `active` | The model's span-bearing AST walk records each gate and its referenced node. |
| `discloses` | entry `read`/`everRead` reader supplies disclosure dependency | While walking every CEL guard, including negated reads and expanded definitions, the model builds a reverse disclosure index from the entry read to every consuming guard, line, quest, and derived rule. |
| `expands` | `@def`/component use to expanded node, preserving origin | Model-owned expansion records carry use, origin, bindings, and both authored/expanded spans; existing expansion code is made public as needed. |
| `raises` | occasion raises an answering beat/entry | Occasion and ladder declarations are joined by their source spans. |
| `engine` | engine-owned state/reserved relation/event writes a boundary node | Owner/reserved declarations and capability/event snapshot. |

The graph feeds are model-owned adapters, not claims that existing checker
APIs already provide this contract. For each document the model performs its
own span-bearing walk over the folded/expanded AST, recording every state-path
read/write, fact query atom, assert/retract pattern, entry reader, def-use and
component-use/expanded-node provenance, and reward declaration. CEL reads and
queries retain the enclosing slot span plus matched expression text because
`cel-parser` drops sub-expression positions. Commands, writes, and asserts use
their exact command spans. Existing `fact_edges` remains the `scenario
--facts` feed unchanged. SourceMap tables gain a reward side table. Datalog
records full rule closure with variable bindings.

A `SourceMap` is required when a compiled line or reward must be joined to a
checker span; unresolved or engine-owned joins remain explicit boundary nodes.
Datalog impact follows the complete least-fixpoint dependency closure, with no
current depth-four bound.

## 3. Impact query

### 3.1 Command and closure

`lute impact <dir> <target>` accepts human output and `--json`. Targets are:
`state:<path>`, `fact:<rel>(<args>)` (CLI ground-fact notation; `_` is a
wildcard), `relation:<rel>`, `scene:<id>`, `quest:<id>`,
`objective:<quest>.<id>`, `entry:<id>`, `beat:<id>`, `occasion:<name>`,
`def:<name>`, and `component:<name>`.

The result is the transitive reverse-dependency closure over a finite node and
edge set. An item is affected when it depends on the target: its eligibility,
reachability, presented content, rewards, or effects read something in the
target's reverse closure. This is dependency existence, not a claim that
changing the value must flip the item. A conjunct is still a dependency:
`slew(regent)` -> `visited('hub.regentFell')` -> `regentTold` remains `proven`
even though `regentTold` also requires `holds('felled', ['regent'])`.

Traverse with reverse BFS and a visited set; cycles terminate, and cyclic rules
or mutual guards are traversed once. A node's read of its own write is not an
impact edge. For each item, the strongest chain is the chain with highest
evidence rank (`proven` > `witnessed` > `bounded` > `heuristic` > `unknown`);
ties go to fewest edges, then lexicographically smallest node-key sequence.
Output is sorted by group, canonical key, file, and span start. Retain all
chains tied at that selected strength.

Groups are: `lines` (lineId, speaker, file:line), `quests/objectives`,
`rewards`, `disclosures` (entries and bundle beats), `beats/scenes`, and
`downstream` facts/state. Each item carries a target-to-item reason chain;
each link includes edge kind, reason, file, line, and source span.

Pattern overlap unifies target arguments with pattern arguments position by
position. Equal ground values, or `_` on either side, match as `proven`.
A parameter/`@param`, CEL variable, or Datalog rule variable not bound by the
target matches as `heuristic`; differing ground values do not match. Negated
queries, `count`/`countDistinct` relation patterns, and `validAt` are
dependencies like `holds`. `after`/`visited(x)`/`completed`/`active` are
`gates` edges from node `x`. Entry `read`/`everRead` readers are `discloses`
edges.

### 3.2 Evidence and JSON

An impact item's evidence is the weakest link on its strongest chain. A direct
syntactic dependency is `proven`; pattern overlap requiring unbound parameters
or variables is `heuristic`; a chain through an engine boundary (engine-owned
state, reserved relation, or engine-raised occasion) is `unknown`, while the
item remains listed. `witnessed` and `bounded` may appear when the strongest
chain is established by a supplied run or finite analysis scope.

Normative JSON shape:

```json
{
  "target": {"kind": "fact", "relation": "felled", "args": ["regent"]},
  "root": "docs/examples/games/drowned-crown",
  "items": {
    "lines": [{"lineId":"...","speaker":"brann","file":"lore/brann.lute","line":27,
      "evidence":"proven","reasons":[{"edge":"gates","reason":"holds('felled',['regent'])","file":"lore/brann.lute","line":26}]}],
    "quests": [], "objectives": [], "rewards": [], "disclosures": [],
    "beats": [], "downstream": []
  }
}
```

## 4. Evidence levels

### 4.1 Vocabulary and fields

The vocabulary is `proven`, `witnessed`, `bounded`, `heuristic`, and
`unknown`. `Diagnostic` gains optional `evidence` and optional `scope`; a
bounded diagnostic MUST include a non-empty scope. Pure parse, type, and
declaration errors leave evidence absent. Analysis-derived diagnostics always
set it. JSON serializes fields when present.

Human output appends ` [bounded: <scope>]`, ` [heuristic]`, or `[unknown]` as
appropriate; it appends nothing for proven or witnessed. “No path found within
bounds” MUST never be rendered as “no path exists.”

## 5. Constraints

### 5.1 Manifest schema

Constraints are project-level source declarations in `lute.project.yaml`:

```yaml
constraints:
  - id: regent-reachable
    kind: reachable
    node: scene:hub.regentFell
    severity: error
  - id: library-completes
    kind: completable
    quest: libraryKey
  - id: dead-brann-never-speaks
    kind: speaksOnlyWhen
    speaker: brann
    when: "!holds('felled', ['brann'])"
  - id: no-slot-only-progress
    kind: noSingleSlotProgress
    quest: '*'
```

`lute-manifest` MUST add a typed `constraints` field to the raw project
schema. The raw loader MUST retain a YAML span for each declaration and for
each kind-specific field. Each declaration requires unique non-empty `id`, a
closed-set `kind`, its kind-specific fields, and optional `severity`
defaulting to `error`. Unknown keys, unknown kinds, missing fields, bad node
references, and duplicate IDs are `E-CONSTRAINT-DECL` at the offending
field's YAML span (or declaration span when no field exists).

### 5.2 Kinds and checking

* `reachable: <node>` reuses connectivity: `holds`/`violated` are proven;
  unresolved analysis is `unknown`.
* `completable: quest:<id>` is `violated` (proven) when the quest is
  unreachable or a required objective is unsatisfiable. A
  `lute constraints <dir> --run` invocation additionally executes the
  project's `*.play.yaml` and `*.test.yaml` scripts and records a witness
  for each observed `-> complete` transition in the run's quest states.
  A witness record is `{script path, quest id, observed transition}` and comes
  from the play outcome or test trace quest-state transitions. A matching
  record makes the result `holds (witnessed)`, naming the script. Without
  `--run` there are no witnesses; otherwise the result is `unknown`.
* `speaksOnlyWhen` takes `speaker` and CEL `when`. It covers every line whose
  speaker is X, including `{vo}` and `{os}` lines. Use a public,
  parameterized guard-implication decider extracted from `cast.rs` (the same
  proof core used by `W-CAST-ABSENT`) without presence-specific assumptions
  (`present`, `changedOn`, ladder, or `assume`). `W-CAST-ABSENT` is
  re-expressed on top of that core with those assumptions layered on. The
  constraint holds (proven) per line, is violated (proven) when `when` is
  provably false, else is unknown listing the line.
* `noSingleSlotProgress: quest:<id>` or `quest:'*'` uses a refactored
  `clock_positions` result: one deterministic record per objective containing
  objective, quest, declared windows, candidate beats with spans, and verdict.
  Both legacy `W-OBJECTIVE-STRANDED`/`W-SLOT-CONTENTION` diagnostics and this
  constraint verdict are projections of that result. `quest:'*'` means every
  quest with required objectives; each quest's verdict is its worst objective.

  Results are bounded with scope `declared clock windows; no path search`.

Constraint diagnostics use the constraint declaration in `lute.project.yaml`
as the primary span (the retained YAML file span). `related` contains causal
source spans: the unsatisfiable objective, failing line, slot candidates, or
unreachable node as applicable. Each related span has a short reason and
related spans are ordered by file path, then byte offset. Declaration and
causal Lute spans retain their own file and coordinate systems.

`check-project` reports constraint **violations** only (`E-CONSTRAINT-VIOLATED`,
plus `E-CONSTRAINT-DECL` for malformed declarations); `holds` and `unknown`
results are not diagnostics. Every verdict, including `unknown`, appears in
the `lute constraints <dir>` report. There is no `W-CONSTRAINT-UNKNOWN`.
A bounded violation defaults to warning; explicit `severity` controls all other
violations. `E-CONSTRAINT-VIOLATED` carries verdict, evidence, scope when
bounded, and witnesses/counterexamples. `lute constraints <dir>` reports every
constraint, verdict, evidence, scope, witness, and counterexample.

## 6. Genre policy vs contract

The handbook separates genre guidance from execution semantics. “Only
significant actions consume time” is guidance for authors, moved from the 0.31
policy section; the execution contract says **the host advances time**. A
checker MAY report schedule consequences, but it MUST NOT turn genre advice
into an engine obligation.

## 7. Diagnostics

| code | severity | meaning/evidence |
|---|---|---|
| `E-CONSTRAINT-DECL` | error | malformed manifest declaration; source error, no evidence field |
| `E-CONSTRAINT-VIOLATED` | declared (bounded defaults warning) | invariant violation; carries evidence and bounded scope when applicable |
| `W-CONSTRAINT-UNKNOWN` | never emitted | unknown verdicts appear only in the `lute constraints` report |
| `W-OBJECTIVE-STRANDED` | warning | bounded to `declared clock windows; no path search`; no universal wording |
| `W-SLOT-CONTENTION` | warning | bounded to `declared clock windows; no path search`; no universal wording |
| `W-FACT-GUARANTEED` | warning | proven redundant guard (`crates/lute-check/src/fact_check.rs:55-59`) |

## 8. Decisions

| # | Decision | Why |
|---|---|---|
| D-A | `lute-model` owns assembly, reconciliation, compilation, index, and graph. | One authoritative snapshot; current loaders duplicate these passes (`docs/design/phase3-inventory/project-model.md:98-104`). |
| D-B | Build one model per nearest manifest root; remove play/calendar forced-single-root behavior. | Align all commands with the existing nearest-root rule (`project-model.md:100-103`). |
| D-C | Keep LSP project caching out of 0.34. | Current cache is document/result-only; phase 5 measures first (`project-model.md:106-107`). |
| D-D | Graph edges retain engine boundaries instead of dropping uncertain items. | Engine-owned state and occasion events are external to authored producers (`dependencies.md:188-199,212-229`). |
| D-E | Derived impact closure is full Datalog closure, not current depth-four fact-edge traversal. | Depth four is an existing incompleteness (`dependencies.md:154,231`). |
| D-F | Rewards are owner/index nodes and disclosures are explicit edges. | Existing IR nests rewards and fact-must models disclosure without a reverse graph (`dependencies.md:160-174,218-219`). |
| D-G | Unknown constraint verdicts are not diagnostics; `lute constraints` reports them. | An undecided invariant is not a defect in the source; reporting it on every `check-project` run would be noise. |
| D-H | All axes move to 0.34.0 with no compatibility mode. | D6 clean cutover and fixed version decision. |
| D-I | `compile --all <dir>` keeps one artifact set and index for the walked directory (nested manifests still warn), built from one `ProjectModel` over the walk; every other project command uses nearest-root models. | `compile --all`'s output contract is a single index for the directory it was given; changing it is out of phase-3 scope. Its loading still goes through the model (no second loader). |

## 9. Compatibility and migration

This is a breaking source/toolchain/JSON analysis cutover under D6. There is no
second loader, compatibility alias, legacy mode, or fallback. Implementations
move input assembly and cache out of `lute-cli`, migrate every named command to
`ProjectModel`, and remove obsolete loader paths. Human output changes for
bounded and heuristic diagnostics: wording is scoped and receives evidence
suffixes. JSON consumers must accept `evidence` and (for bounded results)
`scope`; command result verdicts gain the same field.

All language, IR, and toolchain stamps move to `0.34.0`; execution IR shape is
unchanged except where the new evidence/report fields are required. Project
manifests gain `constraints`; malformed declarations fail rather than being
ignored. The source corpus, fixtures, snapshots, expected diagnostics, schemas,
handbook, and command documentation migrate in the same release. `run` keeps
its artifact-only contract.
