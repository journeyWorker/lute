# Lute 0.41.1 — Rust-only patch fixes

This is the normative 0.41.1 contract. It is a patch release on the 0.41
contract line. The words **MUST**, **MUST NOT**, **SHOULD**, and **MAY** have
the RFC 2119 meanings. A **spec decision** is collected in Appendix A.

0.41.1 is deliberately Rust-only for implementation. No TypeScript source or
test logic changes are permitted. Markdown documentation, package README
files, the release stamp, and the existing Rust test/conformance fixtures are
permitted. All four 0.41 schema bodies and all generated TypeScript remain
byte-identical.

## 1. Scope and version contract

The versioning rule in `docs/versioning.md` aligns every visible axis on every
release, including a patch release. Therefore the toolchain, language, IR,
Event/snapshot stamps, player packages, and launcher packages read `0.41.1`.
The schema filenames and schema bodies stay on the gated `0.41` line:
`schemas/lute-{ir,events,snapshot,player-bindings}-0.41.schema.json` are not
renamed or regenerated. This is a stamp-only move for consumers of the 0.41
major/minor contracts; the schema files remain byte-identical.

| Axis | 0.41.1 rule |
|---|---|
| Toolchain | Cargo workspace, `lute version`, and all package versions stamp `0.41.1`. |
| Language | `luteVersion` stamps become `0.41.1`; diagnostics and checker semantics in §3 change as specified. |
| IR | `irVersion` stamps become `0.41.1`; IR shape and `lute-ir-0.41.schema.json` body are unchanged. |
| Event/snapshot | Runtime version stamps become `0.41.1`; event/snapshot shape and schema bodies are unchanged. |
| Player bindings | `bindingsVersion` remains `"0.41"`; the bindings schema body and generated bindings TypeScript are unchanged. |
| CLI/play scripts | Rust checker, `lute fix`, bridge-script parsing, and human transcript change as §3–§4 specify. |
| Packages/docs | All seven npm package versions align to `0.41.1`; README and migration links are corrected. |

The release MUST NOT alter the bodies of
`schemas/lute-{ir,events,snapshot,player-bindings}-0.41.schema.json`,
`packages/runtime/src/generated/**`, or
`packages/player/src/bindings/schema.ts`. No issue below may be implemented by
changing a JSON contract shape or TypeScript consumer.

## 3. Rust checker and CLI

### 3.1 `lute fix` never panics on Unicode YAML (#74)

The YAML domain rewrite MUST inspect byte slices as bytes or advance through
`char_indices`; it MUST NOT slice a UTF-8 `&str` at a non-character boundary.
The existing domain-key and `domain:` scalar migrations retain their exact
span-splicing behavior: comments, quoting, key order, whitespace, and all
non-ASCII scalar bytes are preserved. A file containing an unquoted Korean
scalar, an em dash, or any other valid UTF-8 scalar MUST either be migrated or
reported as an ordinary failed input; it MUST never panic and MUST never exit
101.

A second invocation over the result MUST be idempotent. This issue introduces
no diagnostic code and no automatic rewrite of the scalar's value.

### 3.2 `luteVersion` stamp migration (#76)

`lute fix` MUST update an existing language stamp from any older value to the
current `0.41.1` value in:

* `lute.project.yaml`'s `defaults.luteVersion`; and
* a `.lute` document's top-level `luteVersion` frontmatter key.

It MUST NOT add a missing stamp, edit a plugin's unrelated value, or rewrite a
future stamp. The edit is byte-preserving and follows the existing CEL/YAML
span-rewriter rules. Each changed scalar counts as one fix in the existing
`applied N fix(es) in M of K file(s)` summary. A second invocation changes
nothing. This rule is mechanical; it does not alter the meaning of any other
migration and has no new diagnostic code.

After a successful fix, a project whose only stale language stamps were those
rewritten MUST no longer emit `W-LUTE-VERSION-STALE` for those stamps.

### 3.3 `W-DEF-UNUSED` names the host escape (#75)

`W-DEF-UNUSED` remains a warning. For a def declared in a project schema or
plugin export, its exact message becomes:

```
def `<name>` is declared but no `@<name>` reference uses it anywhere in the project (content, other defs, or rule guards); use it, drop it, or mark it `host: true` if the host reads it (for example, `Program.def`)
```

The existing location, code, severity, ordering, and project-wide usage scan
are unchanged. A frontmatter def still rejects `host:` with its existing
`E-DEF-DECL` diagnostic; the new text MUST NOT suggest an invalid frontmatter
escape.

### 3.4 Effective option defaults for `enumFromOption` (#67)

When checking an attr or its declared default whose type is
`{ enumFromOption: <option> }`, the checker MUST resolve the effective value
for every active plugin that declares that option:

1. the selected profile's option value wins;
2. otherwise the plugin manifest's `options[].default` is used;
3. otherwise no option domain is available and the existing best-effort skip
   behavior remains.

The resolved default MUST be the same literal shape the option declaration
accepts (a list yields the member list). An authored or default attr value not
in that list reports the existing `E-BAD-ENUM` error with the existing exact
message:

```
`<got>` is not a valid value for `<key>` of `<owner>` (expected one of: <members>)
```

including the existing did-you-mean suffix when applicable. A valid member,
profile override, and omitted option with no declared default retain current
behavior. No schema or JSON contract changes are made.

### 3.5 Bridge declarations without result writes (#81)

A directive that declares both `layer: bridge` and `bridgeCall` semantics MUST
have at least one `effects.writes` entry whose value is
`{ fromBridgeResult: <result-field> }`. Otherwise `lute check` and
`lute check-project` MUST emit one new error at the directive declaration:

* code: `E-BRIDGE-NO-RESULT-WRITE`;
* severity: `error`;
* exact message:

```
bridge directive `<name>` declares `layer: bridge` but no `effects.writes` reads a bridge result; it will not block — add a `fromBridgeResult` write or remove `layer: bridge`
```

The error prevents compilation. A directive with a result write remains a
blocking bridge under the existing rule; no new declaration key, index field,
Event field, or schema field is introduced. Non-blocking plugin records remain
write-free.

## 4. Play scripts and human transcript

### 4.1 Bridge answer writes (#82)

The existing top-level and per-step `bridges:` surfaces remain in place. Every
queue still maps a tag to an ordered list of answers, consumed in the existing
play-step order. The legacy short form remains valid:

```yaml
bridges:
  battle:
    - { outcome: win, hpFloor: 3 }
steps:
  - occasion: duel
    target: kato
```

A new long form is accepted:

```yaml
bridges:
  battle:
    - fields: { outcome: win, hpFloor: 3 }
      writes:
        state:
          - { path: run.score, value: 1 }
        facts: [pulled(rope)]
        retract: []
        accept: []
steps:
  - occasion: duel
    target: kato
```

`fields` is the answered bridge-result map and MUST contain scalar literals
accepted by the pending bridge. `writes` is exactly the runtime's existing
`WritesInput` shape: optional `state` (`StateWrite` entries with `path` and
exactly the existing `value` or `add` form), `facts`, `retract`, and `accept`
arrays. Unknown keys and malformed values are usage errors at the answer's
source span. The parser MUST convert both forms to the existing Rust
`BridgeAnswer` and send the same `bridgeResult { request, fields, writes? }`
input; runtime validation, ordering, replay, and rejection behavior are
unchanged. This is a play-script authoring surface only and MUST NOT change
`lute-events-0.41` or generated TypeScript.

The same long form is valid under a step's `bridges:` key. Existing bridge
answer consumption, include scopes, repeat behavior, and leftover-answer
errors remain byte-identical.

### 4.2 Beat `advances:` and clock raises in text output (#83)

The JSON/events stream remains unchanged. In the human transcript, an
`advances:` movement nested in a presented beat MUST be shown immediately
after that beat's own `presentationEnd`, before the nested clock raises, using
the existing advance spelling:

```
  ↻ advance <by>: <from> → <to>
```

`<by>`, `<from>`, and `<to>` use the same values and formatting as an
explicit `step N · advance <by>: <from> → <to>` line. Every raise caused by
that movement remains in raise order and uses the existing line:

```
  ↻ <occasion> (clock raise)
```

A closed raise is also visible at its position, with this exact line:

```
  ↻ <occasion> (clock raise — not raised: <why>; the clock moved on without it)
```

The line's `<why>` is the existing closed-seam explanation, not a new
checker/runtime diagnostic. The explicit `advance:` step format and its
existing `note:` lines are unchanged. No clock event, JSON record, or
snapshot field is added.

## 5. Documentation and package surfaces

### 5.1 Migration note (#84)

The 0.41.1 migration note MUST explicitly say that the public
`SessionOptions`/player-session layer option formerly called `castNames` (and
older `castNamesFrom` references) is now `cast`, and that display names come
from `bundle.index.cast`. The English and Korean website pages MUST carry the
same migration instruction.

### 5.2 `@lute-lang/lute` README (#73)

`packages/cli/README.md` MUST be included in the published package. It MUST
cover installation, `lute --help`, the CLI reference, and links to the
versioned CHANGELOG/migration notes. Links MUST work from npm (absolute GitHub
or documentation-site URLs).

### 5.3 `@lute-lang/player` README links (#72)

Every guide link in `packages/player/README.md` MUST be an absolute URL pinned
to the release (`https://github.com/journeyWorker/lute/blob/v0.41.1/...` or an
absolute docs-site URL). No `../../docs/...` or root-relative `/player/...`
link may remain. The README MUST continue to describe the package's existing
peer dependencies; this issue does not change package APIs.

## Appendix A — spec decisions

| § | Decision | Reason |
|---|---|---|
| 1 | Align all visible numbers to 0.41.1 but retain `-0.41` schema filenames and bodies. | `docs/versioning.md` requires alignment; schema files track the major/minor contract. |
| 3.1 | Treat UTF-8 as bytes only for scanning and preserve source spans. | The panic is an implementation boundary error; YAML text must not be reserialized. |
| 3.2 | Update existing project/document stamps, never add absent ones or touch future stamps. | Fix is a migration, not a formatter or project initializer. |
| 3.4 | Profile value wins over a manifest default; no default means the current skip remains. | This is the resolver's existing precedence and avoids inventing a domain. |
| 3.5 | Make a missing bridge result write an error, rather than silently changing blocking behavior. | A declared bridge is an author promise; silent non-blocking execution is unsafe. |
| 4.1 | Long form uses `{fields, writes}` while flat scalar maps remain valid. | It reuses `BridgeAnswer`/`WritesInput` and keeps existing play files byte-identical. |
| 4.2 | Nested movement uses `↻ advance …`; closed raises use the existing reason text in one line. | It is visible in the same indentation/marker vocabulary as current play output without changing events. |
| 5.3 | Pin README links to `v0.41.1`, not `main`. | An npm user must reach docs matching the installed package. |
