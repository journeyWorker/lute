# Lute 0.50.0 — authoring extensibility

This is the normative 0.50.0 contract. The words **MUST**, **MUST NOT**,
**SHOULD** and **MAY** have their RFC 2119 meanings.

The inputs are the dogfood issues #162, #163, #164, #166, #169, #172 and #177
(each with a 0.48.1 reproduction from a large real port). The options and
recommendations are in
[`docs/design/0.50-extensibility-options.md`](../../design/0.50-extensibility-options.md),
and the decisions are in
[`2026-10-25-lute-0.50-decisions.md`](../../superpowers/notes/2026-10-25-lute-0.50-decisions.md).
Where this spec departs from a recommendation, the decision note gives the
evidence, and Appendix B lists every decision.

The release adds authoring surface without new control flow. There is no new
keyword and no new element. There are two new plugin manifest keys
(`stampAttrs[].on`, `rewardKinds.<K>.effects`), one new plugin export
(`hostTokens`), one new project manifest key (`diagnostics:`) and one new lint
target (`node`). The release is a clean cutover (ADR D6). The base is
`origin/main` after v0.49.1. Code anchors are cited at v0.49.0 `f34f141f`;
Appendix A lists how 0.49.1 moves them.

Implementation plan:
[`2026-10-26-lute-0.50.0-extensibility.md`](../../superpowers/plans/2026-10-26-lute-0.50.0-extensibility.md).

## 1. Scope and version contract

This is a minor release. Every public version axis is `0.50.0`: toolchain,
`luteVersion` (`LUTE_LANG_VERSION`), `irVersion`, `eventVersion`,
`snapshotVersion`, and the seven npm packages. The contract schemas move to the
`0.50` line (`schemas/lute-{ir,events,snapshot,player-bindings}-0.50.schema.json`).
`bindingsVersion` and the player save/profile format become `"0.50"`. This follows
the 0.49.0 §1 precedent (and 0.48.0's before it).

| Axis | 0.50.0 contract |
|---|---|
| Language | No syntax change. A plugin stamp may now be written on `<branch>`, `<hub>` and `<choice>` when its `on:` names them (§3). A bare-identifier interpolation `{{name}}` resolves against the declared host tokens (§4). A stamp declared `required` on a surface is enforced there (§3.4). |
| IR | **Additive.** `choice`/`hub` option entries gain an optional `stamps` object, and the `choice`/`hub` record's existing `stamps` carries the element's stamps (§3.5). `RewardEntry` gains optional resolved `retracts`, `asserts` and `accepts` (§5.5). Schema `-0.50`. |
| Semantics (D5) | New semantic id **`lute.quest.rewardEffects/1`**, collected only by an artifact with a reward effect (§5.5). |
| Event / snapshot | **No shape change.** A grant may be followed by `assert`/`retract`/`accept` records that name their grant (§5.6). The `record` payload is untyped in the event schema, so only the record catalogue changes. The schemas are renamed to `-0.50`. |
| Plugin manifests | `stampAttrs[].on` (§3.1); `rewardKinds.<K>.effects` (§5.1); the `hostTokens` export (§4.1). A cross-cutting stamp with `required: true` is refused (§3.2). |
| Project manifest | `diagnostics:` (§6). |
| Lint | `target: node`; the string members `startsWith`, `endsWith`, `contains` (§8). |
| CLI | Severity overlay from `diagnostics:`. Suppressed findings are counted, in text and JSON, only when nonzero (§6.4). No new option and no report-id change. |
| Runtime / player | The runtime applies reward effects at the grant (§5.6). The reference player's `ChoiceView` carries element and option stamps read from the IR (§3.6). |
| `capabilitySnapshot` | Unchanged for every manifest that uses none of the new keys. Each new key folds into the hash only when it is used (§3.3, §4.2, §5.1). |
| Report ids | Unchanged. |

Outside the deltas listed in §14, every output captured by
`scripts/cli-snapshot.py` MUST be byte-identical to 0.49.1 after version-stamp
normalization. Compare with `--strict` (0.49.1).

## 2. Shared rules

- **Regression test first.** Every behaviour change has a regression test that
  fails on the base: the 0.49.1 binary, or the change reverted. The issue
  reproductions are the first tests.
- **Diagnostic shape.** A new code is registered in
  `crates/lute-cli/src/codes/registry.rs` and
  `crates/lute-check/src/evidence.rs`. Registry text is blessed with
  `LUTE_BLESS_DIAGNOSTICS=1`. The generated website page (EN) and its KO
  translation follow. **No hint may recommend a spelling the checker rejects.**
- **No silent drop.** An authored value that the toolchain does not carry into
  the artifact is a diagnostic at the value. A declaration that can never take
  effect is a diagnostic at the declaration (§3.2, §5.1).
- **Byte stability.** A project that uses none of the new keys compiles to
  byte-identical artifacts (`capabilitySnapshot` included) and reports
  byte-identical diagnostics. The only exceptions are the message changes of
  §9.2.
- **Documentation.** Every changed behaviour is documented in the same change:
  website EN + KO, `docs/runtime/*`, and `llms-full.txt`. Historical records are
  never rewritten.
- **New Rust code** follows `docs/design/rust-coding-rules.md` (Accepted, with
  its 2026-10-25 amendments and the 0.49.1 sweep applied): no `pub(super)`, no
  `unwrap()` outside tests, typed errors per failure domain, `foo/mod.rs` for
  modules with children, newtypes where values can be confused (a stamp surface
  is a `StampSurface`, not a `String`), and no HIR/Fold (rules §7). Analyses
  consult the new declarations directly. They do not synthesize AST nodes.

## 3. Plugin attributes on named surfaces (#163, #164)

### 3.1 Manifest: `on:`

A `stampAttrs` entry is the 0.49 `AttrDecl` (`{ name, type, required?, default? }`)
plus one optional key, `on:`, a non-empty list of **surface names**:

```yaml
# plugins/acme.stage/stampattrs/columns.yaml
stampAttrs:
  - { name: voiceAssetId, type: { providerRef: voice }, required: true, on: [line] }
  - { name: assetName,    type: string, on: [bg, actor] }
  - { name: menuType,     type: { enum: [plain, timed, minigame] }, on: [branch, hub] }
  - { name: optionKey,    type: string, required: true, on: [choice] }
  - { name: cue,          type: string }                          # cross-cutting, as in 0.49
```

```lute
<branch id="route" prompt="Which way?" menuType="plain">
  <choice id="goLeft" text="Left" optionKey="L1">
    @mira{voiceAssetId="VO.mira.0010"}: Left it is.
  </choice>
</branch>
```

- **Surface vocabulary** (closed):
  - `line`: every content line (`@speaker{…}: text`), including lines in
    component, quest, objective, `<on>`, entry and beat bodies;
  - `branch`, `hub`: the element of that name;
  - `choice`: every `<choice>`, in a `<branch>` or a `<hub>`;
  - a **directive tag**: a directive of the resolved snapshot
    (`CapabilitySnapshot::directive(tag)` is `Some`) that has a stamp carrier,
    that is, not in `lute_manifest::core::UNSTAMPED_DIRECTIVES` (`jump`,
    `label`, `clear`; 0.49.0 §4.1).
  - The four names `line`, `branch`, `hub` and `choice` always mean the core
    surface. `branch`, `hub` and `choice` are already reserved plugin directive
    names (`E-PLUGIN-RESERVED-NAME`). A plugin directive tagged `line` cannot be
    named in `on:`.
- **Absent `on:`** keeps the 0.49 meaning exactly: the stamp is admissible on
  every directive with a stamp carrier and on every content line. It is **not**
  admissible on `<branch>`, `<hub>` or `<choice>`. The logic tags stay closed
  (D-J) unless a stamp names them.
- `on:` order is not significant. The snapshot stores the set.
- `schemas/lute.plugin.json`: the `stampAttrs` item schema gains
  `on: { type: array, items: { type: string }, minItems: 1, uniqueItems: true }`.

### 3.2 Load and assembly rules

At **load** (per package; code `E-PLUGIN-PARSE`, at the entry):

| Fault | Message shape |
|---|---|
| `on:` is not a list of strings, or is empty | `` stamp attribute `X` has an empty `on:` — list the surfaces it applies to, or omit `on:` for every directive and content line `` |
| a surface repeated in `on:` | `` stamp attribute `X` lists `bg` twice in `on:` `` |
| `required: true` without `on:` | `` stamp attribute `X` is `required: true` but has no `on:`; a stamp required on every record is not a column — name its surfaces with `on: […]` `` |

**Uniqueness within a package.** Two entries may share a name only if both have
`on:` and their surface sets are disjoint. Any overlap (an entry without `on:`
overlaps every entry) is the existing **`E-PLUGIN-DUP-ID`** (`loader.rs:265`),
naming the shared surfaces: `` stampAttr `assetName` is declared twice on the
surface `bg` — give each entry disjoint `on:` surfaces ``. The loader's
`merge_named` key for `stampAttrs` becomes (name, surface set) and the overlap
test replaces plain name equality (`loader.rs:625-634`).

At **assembly** (`assemble.rs:462-495`, once the active snapshot's directives
are known), in this order. A refused entry is dropped and its siblings still
land (the 0.49 precedent):

1. The existing core-stamp reservation (`at`, `duration`, `delay`, `wait`,
   `timeline`, `timing`, `provenance`, `source`) is unchanged:
   `E-PLUGIN-RESERVED-STAMP-ATTR`.
2. Each `on:` name resolves to a `StampSurface`. A name that is none of the
   four core surfaces and no directive of the snapshot is
   **`E-PLUGIN-STAMP-SURFACE`** (new, error): `` stamp attribute `assetName`
  (`acme.stage`) names `bgg` in `on:`, which is not `line`, `branch`, `hub`,
  `choice` or a directive of the resolved profile — did you mean `bg`? ``.
   A directive without a stamp carrier draws the same code:
   `` … names `jump` in `on:`, but `::jump` emits no stamped record (0.49.0 §4.1) ``.
   A plugin that scopes a stamp to another plugin's directive declares that
   plugin in `depends:`, so that the directive is in every profile that
   activates it. The message says so when the tag exists in an installed but
   inactive plugin.
3. **Shadowing.** A scoped entry whose name is an attribute the named surface
   already owns is **`E-PLUGIN-RESERVED-STAMP-ATTR`** (existing code, message
   extended): `` stamp attribute `prompt` (`acme.stage`) is scoped to `branch`,
   but `prompt` is an attribute of `<branch>` itself, so the stamp could never
   be read ``. The surface's own attributes are:
   - a directive: its declaration's `attrs` (plus `when` on `::jump`);
   - `line`: `lute_check::content_line::KNOWN_ATTRS` (which holds `wait`, 0.49.0 §4.2) plus the guard `when`;
   - `branch`: `id`, `prompt`, `timeout`, `default`;
   - `hub`: `id`, `prompt`;
   - `choice`: `id`, `text`, `when`, `into`, `value`, `once`, `exit`, and the
     renamed/removed `label`, `as`, `persist`.

   These core lists move into `lute_manifest::core` (`LINE_ATTRS`,
   `BRANCH_ATTRS`, `HUB_ATTRS`, `BRANCH_CHOICE_ATTRS`, `HUB_CHOICE_ATTRS`,
   `CHOICE_RETIRED_ATTRS`), and `lute-check` (`logic_attrs.rs:58-65,252-262`,
   `content_line.rs:26`) reads them from there. There is one list per surface.
   A cross-cutting entry keeps the 0.49 rule: the surface's own declaration
   wins, and the entry is not refused.
4. **Uniqueness across plugins.** Two plugins' entries with the same name and
   overlapping surfaces are the existing **`E-PLUGIN-DUP-ACROSS`**
   (`assemble.rs:100`), naming both plugins and the shared surfaces. Disjoint
   entries from two plugins are legal.

### 3.3 Snapshot index and `capabilitySnapshot`

- `CapabilitySnapshot.stamp_attrs` (`snapshot.rs:59`, today
  `BTreeMap<String, AttrDecl>`) becomes a `StampAttrs` index in
  `lute-manifest` (new module `stamps.rs`). It holds `StampAttrDecl { decl:
  AttrDecl, on: Option<BTreeSet<StampSurface>>, plugin: String }` grouped by
  name, and is built once per snapshot (D14). Its API replaces every direct map
  access:
  - `get(surface, name) -> Option<&AttrDecl>`: the entry whose `on:` contains
    `surface`; otherwise the cross-cutting entry, if `surface` is `line` or a
    directive (never for `branch`/`hub`/`choice`);
  - `for_surface(surface)`: every admissible declaration, used for listings,
    hints and `required`;
  - `scoped_elsewhere(surface, name)`: the entries of `name` that do **not**
    admit `surface` (for the §3.4 message);
  - `iter()`, `is_empty()`, `names()`.
- `StampSurface` is `Line | Branch | Hub | Choice | Directive(String)`, with a
  `Display` that prints the author's spelling (`content lines`, `::bg`,
  `<branch>`).
- **Hash.** The `stampAttrs` fold (`snapshot.rs:361-366`) prints, per name in
  order and per entry, `name=<AttrDecl Debug>`, and appends `@on=[…]` (sorted
  surface names) only for a scoped entry. A manifest without `on:` therefore
  hashes exactly as in 0.49, and a test pins that.

### 3.4 Check rules

**Resolution** of an attribute `k` on surface `S`. The order is strict, and the
first match wins:

1. `S`'s own attributes: the directive's declaration
   (`directives.rs:223`), the content line's known attributes
   (`content_line.rs`), or the logic tag's table (`logic_attrs.rs`).
2. For a directive, the 0.49 unstamped refusal (`directives.rs:228`,
   `unstamped_attr_message`), then the universal timing keys
   (`directives.rs:241`).
3. `stamp_attrs.get(S, k)`. The value is typed by that declaration through
   `check_attr_value`, as in 0.49 (`E-ATTR-TYPE`, `E-BAD-ENUM`, `@ref` typing).
4. Renamed or removed attribute diagnostics (`renames::attr_diag`).
5. **`E-UNKNOWN-ATTR`**. When `scoped_elsewhere(S, k)` is non-empty, the message
   names where the stamp applies instead of listing `S`'s attributes:
   - `` `::bg` has no attribute `voiceAssetId`: it is a stamp of `acme.stage` for content lines only ``
   - `` `<branch>` has no attribute `optionKey`: it is a stamp of `acme.stage` for `<choice>` only ``
   - otherwise the 0.49 message, extended for a logic tag with the stamps that
     surface admits: `` `<choice>` has no attribute `cue`; its attributes are `id`, `text`, `when`, `into`, `value` and the stamps `optionKey` (`acme.stage`) ``.

**Logic tags (#164).** `check_branch_attrs`, `check_hub_attrs` and
`check_choice_attrs` (`logic_attrs.rs:278,396,595`) take the snapshot. `close()`
(`logic_attrs.rs:656`) admits a key that `stamp_attrs.get(surface, key)` returns
and checks its value as above.

**Reference typing on logic surfaces.** Today a `@ref` attribute value is typed
only when it carries a directive tag: `check_attr_refs`
(`check/walker.rs:639-650`) derives the expected type from
`directive_ref_type(snapshot, tag, key)` only. `check_attr_value` skips a `Ref`
value (`directives.rs:570-586`), and the folded-value validation in
`def_inline.rs` (`attr`, `:247-253`) returns early without a directive. So a
stamp `@ref` on `<branch>`/`<hub>`/`<choice>` would be neither typed nor
validated after folding. 0.50 makes both surface-aware:

- `check_attr_refs` takes the attribute's `StampSurface` (or the directive tag)
  instead of `Option<&str>`. For `branch`, `hub` and `choice` it expects the type
  of `stamp_attrs.get(surface, key)`, so a def of the wrong type is
  **`E-REF-TYPE`**. The call sites `walker.rs:202-206` and `:465-469` pass the
  element's surface.
- `def_inline.rs` validates a folded literal of a logic-surface stamp with the
  same declaration through `check_attr_value`. A folded value outside an enum is
  **`E-BAD-ENUM`**, and a wrong scalar is **`E-ATTR-TYPE`**, exactly as on a
  directive. Lines and directives keep their 0.49 paths, and only the
  declaration lookup becomes `get(surface, name)` (S1).
- Regression cases (failing on 0.49.1, where the attribute is `E-UNKNOWN-ATTR`
  outright, and against a variant with reference typing disabled):
  `<branch menuType=@m>` with `@m` an `int` def → `E-REF-TYPE`;
  `<choice optionKey=@k>` with `@k` a string def → clean;
  `<hub menuType=@m>` with `@m` folding to `"grid"` (not in the enum) →
  `E-BAD-ENUM`.

The D-J module comment is amended: the tables are constant, and the only
plugin extension point is a stamp whose `on:` names the tag.

**Required.** For every declaration in `for_surface(S)` with `required: true`
(only scoped entries can be required, §3.2) that `S` does not author,
**`E-MISSING-ATTR`** (existing code, error) is reported at the surface's head
span (the span `E-MISSING-ATTR` uses for a directive, `directives.rs:371`; a
line's span; the element's opening tag):

- `` `::bg` requires attribute `assetName` (a stamp of `acme.stage`) ``
- `` this content line requires attribute `voiceAssetId` (a stamp of `acme.stage` for content lines) ``
- `` `<choice id="goLeft">` requires attribute `optionKey` (a stamp of `acme.stage`) ``

The rule applies wherever the surface is authored, component bodies included.
A line that `::use` splices in is checked once, in its component. The check
does not look at a declared `default:`, because a stamp is never injected
(0.49 §3.1, "absent means absent").

**Other readers of `stamp_attrs`**, migrated to the surface-aware API:
`def_inline.rs:261` (`S` = the directive), `check/use_site.rs:986` (the
directive), `project_check/domains.rs:30` (`iter()`: every declaration's
domain), and the hint lists at `content_line.rs:161` (`for_surface(Line)`).

### 3.5 IR and lowering

- `lower.rs:760-773` (`plugin_stamps`) takes the `StampSurface` of the record
  it fills and types each value by `get(surface, name)` (`attr_json_typed`).
  `lower.rs:453` (keeping stamps out of a plugin record's `fields`) uses the
  same lookup. A stamp typed differently on two surfaces serializes with each
  surface's type.
- The `choice`/`hub` records already carry `Stamp` (`ir.rs:1271,1324`;
  `stamp_mut`, `ir.rs:2129-2146`). Their `stamps` object now holds the
  `<branch>`/`<hub>` element's stamps.
- `ChoiceOption` and `HubOption` (`ir.rs:1277,1332`) gain
  `stamps: BTreeMap<String, Json>` with
  `#[serde(skip_serializing_if = "BTreeMap::is_empty")]`, serialized last,
  filled from the `<choice>` element's stamps (`stage.rs:423,502`). An option
  without stamps is byte-identical to 0.49.
- An unauthored stamp is never injected (0.49.0 §3.1).
- **Schema** `schemas/lute-ir-0.50.schema.json`: the option definitions of
  `cmdChoice` and `cmdHub` gain `"stamps": { "$ref": "#/$defs/stamps" }`.
- **D5.** Stamps are descriptive (the runtime does not act on them), so there is
  no semantic id. `FIELD_TABLE` already holds `stamps`.

### 3.6 Runtime and player

- **Runtime: no change.** The runtime never reads stamps. The `awaitChoice`
  menu carries the address (`document`, `position`), verdicts and
  `once`/`exit` (`runtime.rs:297-320`), and stays unchanged. No event or
  snapshot shape changes.
- **Player.** `packages/player/src/ports/index.ts` `ChoiceView` gains
  `readonly stamps?: Readonly<Record<string, Json>>`, and each option gains the
  same. `cues/index.ts` `choiceView` (`:447-469`) fills them from the IR
  command at `menu.document`/`menu.position`, the command and options it
  already reads `text`/`texts`/`prompt` from. Each is omitted when absent.
  A presenter receives them through `showChoice`.
- **Hosts** that do not use the reference player read stamps from the IR
  record at the menu's address, as they read option text (documented in
  `tooling/runtime-contract` and `docs/runtime/event-contract.md`).

## 4. Host interpolation tokens (#162)

### 4.1 Manifest

A new plugin export `hostTokens` (`plugin.yaml` `exports: { hostTokens: hosttokens/ }`),
read from `hosttokens/*.yaml`:

```yaml
hostTokens:
  playerName: { type: string }
  rank:       { type: int }
  platform:   { type: { enum: [ios, android, web] } }
```

- The key is the token name. The value is `{ type }`, where `type` is `string`,
  `int` or `{ enum: [members…] }`. Any other type or key is `E-PLUGIN-PARSE`
  (unknown keys `E-PLUGIN-KEY`).
- A token name is an **identifier** (`lute_manifest::ident::is_ident`: an ASCII
  letter or `_`, then letters, digits or `_`). It is not merely a name
  (`is_name` also admits `-` and a leading digit), because a host token is
  written bare inside `{{…}}`. A non-identifier key is `E-PLUGIN-PARSE`:
  `` host token `player-name` is not an identifier (letters, digits and `_`, not starting with a digit) ``.
  Rejection tests: `player-name`, `2ndName`, `-x`, and the empty key. A name that
  is a state root or CEL literal (`scene`, `run`, `user`, `app`, `quest`,
  `entry`, `prev`, `clock`, `occasion`, `season`, `true`, `false`, `null`)
  is **`E-PLUGIN-RESERVED-NAME`** at assembly. The reason is in the message:
  `` `{{run}}` would read as a state root ``.
- **`lute.core` declares `userName: { type: string }`** in a new core asset
  `crates/lute-manifest/assets/lute.core/hosttokens.yaml`, folded by
  `build_core_snapshot` (`core.rs:103`). Redeclaring a token another plugin
  (or `lute.core`) declares is `E-PLUGIN-DUP-ACROSS`.
- `CapabilitySnapshot.host_tokens: BTreeMap<String, HostTokenDecl { ty, plugin }>`.
- **Hash.** The fold adds a `hostTokens` section only when a token not owned by
  `lute.core` exists, and folds only those tokens. The core snapshot hash and
  every artifact of a project that declares no token are unchanged (test).
- The loader's export list, `E-PLUGIN-UNKNOWN-EXPORT` did-you-mean and
  `schemas/lute.plugin.json` gain `hostTokens`.

### 4.2 Parsing and checking

- `lute_syntax::ast::classify_interp` (`ast.rs:734`) stops special-casing
  `userName`. A referent that is an identifier by the same `is_ident` rule (no
  `.`, `[`, `(`, `-`, not `$`, not starting with `@` or a digit) is
  `InterpKind::Reserved`, a host token. `{{player-name}}` and `{{2nd}}` stay
  in the `Path` bucket and keep their 0.49 `E-CEL-PROFILE`. The
  doc comments of `InterpKind::Reserved` and `Placeholder::Reserved`
  (`ir.rs:895`) change from "`userName`" to "a host token". Scanners that
  share the classifier (content lines, `<choice text=…>` labels, prompts)
  follow automatically. A state path always has a tier root and a `.`, so no
  spelling changes bucket except bare identifiers, which were always
  `E-CEL-PROFILE`.
- `check/interp.rs` (`:33-41`): a `Reserved` referent is looked up in
  `snapshot.host_tokens`.
  - **Declared:** its format hint is checked by `check_interp_format` with
    the token's type. A `string` or `enum` token takes text hints, and a number

## 5. Reward effects (#169)

### 5.1 Manifest

`RewardKindBody` (`schema/vocabulary.rs:182`) and `RewardKindDecl` (`:301`)
gain `effects: Option<RewardEffects>`:

```yaml
rewardKinds:
  BADGE:       { target: { entity: person, required: true }, effects: { asserts: ["met(@target)"] } }
  REVOKE:      { target: { entity: person, required: true }, effects: { retracts: ["met(@target)"] } }
  OFFER_QUEST: { target: { required: true }, effects: { accepts: ["@target"] } }
```

- `RewardEffects { asserts: Vec<FactEffect>, retracts: Vec<FactEffect>, accepts: Vec<AcceptEffect> }`,
  `deny_unknown_fields`. `FactEffect` is the directive type
  (`schema/directives.rs:106`, the one parser). Each list is optional, and an
  empty `effects: {}` is `E-PLUGIN-PARSE` ("declares no effect").
- **`writes` is not admitted.** `credits:` is a reward's state write. The key
  is `E-PLUGIN-KEY`, whose message adds `` — a reward's state write is `credits:` ``.
- **Pattern arguments** of `asserts`/`retracts`: members, `true`/`false`,
  `@target`, and `_` (in `retracts` only). **Any other `@name` is
  `E-PLUGIN-PARSE`**: `` reward kind `BADGE` effect `met(@rarity)` reads `@rarity`; a reward kind's effects read only `@target` (a `<reward>` takes no other attribute) ``.
  A reward kind's `attrs:` cannot be authored on `<reward>`
  (`logic_attrs.rs:72,418`). See the decision note, item 1.
- **`accepts`** entries: `@target` or a literal quest id (an identifier).
  Anything else is `E-PLUGIN-PARSE`.
- A kind with `target: { forbidden: true }` whose effects read `@target` is
  `E-PLUGIN-PARSE` (the effect could never bind).
- `RewardKindDecl`'s hand-written `Debug` (`vocabulary.rs:314`) prints
  `effects` only when present, so every existing kind keeps its hash.
- `schemas/lute.plugin.json`: `rewardKinds` values gain `effects`.

### 5.2 Checks per `<reward>`

`match_check/rewards.rs` judges each `<reward>` whose kind declares effects.
`@target` is bound to the reward's quoted `target=` (0.49.0 §3.3: the only form
that reaches the IR).

- **Facts:** each resolved pattern is judged exactly as an `::assert` /
  `::retract` of it: relation declared, arity, argument kinds and members, and
  closed-kind membership. It uses the same codes `directive_facts::check_call`
  (`directive_facts.rs:191`) draws, at the reward's `kind=` span, and each
  message is prefixed `` `<reward kind="BADGE">` asserts `met(mira)` (its kind's `effects`): ``.
  A pattern helper `reward_facts(kind, reward)` mirrors `call_facts`
  (`directive_facts.rs:60`).
- **Accepts** (project-wide, with `check_project_accepts`, `accept.rs:190`):
  each resolved quest id is judged by `::accept`'s rule (`check_target`,
  `accept.rs:287`), which reports **`E-ACCEPT-TARGET`** for an unknown id
  (did-you-mean), for a quest with `start`, and for an auto-activating child.
  The anchor is the reward's `target=` value when the id came from `@target`,
  otherwise `kind=`. The messages name the reward:
  `` `<reward kind="OFFER_QUEST" target="secnd">` accepts quest `secnd` (its kind's `effects.accepts`), but no quest in the project declares that id — did you mean `second`? ``.
- **Unbound `@target`** (no `target=`): the effect is not applied and there is
  no extra diagnostic. This is the directive rule (`lower.rs:483-486`). A
  `required: true` target already reports `E-REWARD-TARGET`.
- `W-REWARD-DOUBLE-CREDIT` is unchanged.

### 5.3 Meaning

At the grant instant, for a reward that is granted (its `outcome` filter
matches the transition and its `when=` holds; `machine/quest.rs:980-998`), in
declaration order, **per reward**:

1. the `grant` record and its `credits` write, as in 0.49;
2. the reward's `retracts`, then `asserts`, through the runtime's one
   assert/retract path (the `::assert`/`::retract` path, including the
   `E-FACT-EXCLUSIVE` runtime check);
3. its `accepts`, through `::accept`'s path (`commands.rs:24-49`): an
   accept-driven quest of the artifact activates on the next lifecycle round,
   and a quest already past `unset` is left alone, with the record saying so.

Then the next reward. As in 0.49 (`docs/runtime/quest-lifecycle.md` "Order
within one owner"), objective grants precede quest grants, and all grants of a
transition precede its lifecycle handler body, so a `questComplete` handler
reads the asserted fact. An effect fires exactly once per grant. Replay and
restore follow the grant's existing instance identity.

### 5.4 Analyses

Every analysis reads a reward effect **as if it were the corresponding
`::assert` / `::retract` / `::accept` written first in the owner's grant
point**:

| Reward | Grant point |
|---|---|
| quest-level, no `outcome` | the quest's completion, before its `questComplete` handlers |
| quest-level, `outcome="failed"` | the quest's failure, before its `questFailed` handlers |
| objective-level | the objective's completion |

A conditional reward (`when=`) is a conditional producer. It contributes to
*may* sets, and to *must* sets only on the route where its guard holds (the
guarded-assert fork/meet below). This adds no new model: it is the 0.49
treatment of an effect in a lifecycle handler. It follows for:

- the relational fact analysis (may/must envelopes; `E-QUEST-UNREACHABLE`,
  `E-ARM-DEAD`, `E-OBJECTIVE-UNSATISFIABLE`, `W-FACT-GUARANTEED`),
  `W-RELATION-UNREAD`, `E-FACT-EXCLUSIVE`, and cast presence (`cast/facts.rs`,
  `cast/presence/walk.rs`);
- the scenario graph: fact edges `quest(first) -> quest(second) [asserted
  fact]` (`fact_edges.rs`), and the accept edge `quest(first) -> quest(second)
  [accept]` (`connectivity/graph_sources.rs`), for reachability and
  connectivity. **Start-cycle detection is unchanged.** `[accept]` anchors,
  a reward accept's included, do not gate a quest's start
  (`connectivity/start_cycles.rs:16-22`, `gates()`: the engine may accept a
  quest outside any `::accept`, and accept deadlocks are out of scope,
  0.49.0 §14). A reward accept therefore never draws `E-QUEST-START-CYCLE` or
  `E-QUEST-START-SELF`;
- `W-QUEST-NEVER-ACCEPTED` (`accept.rs:234`): a reward accept names the
  quest. The message becomes `` … but no `::accept` or reward `accepts` in the project names it … ``;
- `lute scenario knowledge` and `lute lore`: the producer is named
  `` met(mira) — produced by reward BADGE of quest `firstVisit` ``.

**Mechanism.** A new `lute-check` module `reward_effects.rs` resolves, per
project root and once (D14), every reward effect into

```text
GrantEffect {
  quest, objective: Option<ObjectiveId>, point: GrantPoint,   // §5.4 table
  order: (grant_rank, reward_index, effect_index),           // §5.3 order
  kind, reward_span,
  guard: Option<&CelSlot>,                                   // the reward's `when=`
  effect: Fact(FactPattern, Polarity) | Accept(QuestId),
}
```

The guard is carried, so no consumer has to re-find the `<reward>` from the
owner and the span. `grant_rank` puts objective grants before quest grants
(§5.3). Within one reward, `effect_index` orders retracts, then asserts, then
accepts.

**Transfer into the flow analyses.** At each grant point, before the walk of
the body it precedes, the effects of that point are applied to the entry flow
in `order`, with the rules `fact_must.rs` already uses for authored nodes
(`fact_must.rs:903-944`):

| Grant point | Entry flow the effects are applied to |
|---|---|
| quest complete (no `outcome`) | the base of every `<on event="questComplete">` body of the quest (`Node::On`: `body_base`), and the quest-completion state the project analysis propagates along `after:`/`completed(...)` edges |
| quest failed (`outcome="failed"`) | the same for `questFailed` |
| objective | the objective body's entry, after `assume(done)` (`Node::Objective`), and the objective-completion state |

- An **unguarded assert** is `assert(fact, flow)`: Must and May.
- A **guarded assert** (`when=`) forks like a guarded `::assert`:
  `record(when)`, `taken = flow.clone()`, `assume(when, taken)`,
  `assert(fact, taken)`, `meet(flow, taken)`. It is May always, and Must only
  on the route where the guard holds.
- A **retract**, guarded or not, removes what it matches from Must, as a
  guarded `::retract` does, and it is recorded in May for `E-FACT-EXCLUSIVE`.
- An **accept** has no fact effect. It feeds the accept and reachability
  consumers only.

Each consumer above reads that table beside its existing `::assert` /
`::retract` / `::accept` walk (`accept::for_each_accept`,
`directive_facts::collect_call_facts`, the `Node::Assert`/`Node::Retract`
matches). No synthetic AST node is created (rules §7). The implementing slice
greps every consumer of `is_accept`, `accept_quest`, `call_facts`,
`collect_call_facts`, `Node::Assert` and `Node::Retract`, and records each one
that does not consume the table with its reason (for example, intra-scene
definite assignment: rewards are quest-level only).

## 6. Project diagnostic levels (#166b)

### 6.1 Manifest

```yaml
# lute.project.yaml
diagnostics:
  W-DISPLAY-NAME-DUP: error
  W-STAGE-ABSENT: { level: off, paths: ["scenes/imported/**"] }
```

- `diagnostics:` is a map from diagnostic code to either a level or
  `{ level, paths }`. One entry per code.
- **Levels:** `off`, `info`, `warn`, `error`.
- **`paths`** (optional): project-root-relative globs, with the lint `ignore:`
  syntax (`*` within a segment, `**` across segments). When `paths` is given,
  the level applies only to diagnostics of documents whose root-relative path
  matches a glob. Elsewhere the code keeps its native severity.
- `ProjectConfig` (`lute-manifest/src/project.rs:51`) gains
  `diagnostics: DiagnosticLevels` and `diagnostics_diags: Vec<ResolveDiag>`,
  following the `constraints`/`constraint_diags` pattern (`:114-115`).
- **`E-DIAGNOSTICS-CONFIG`** (new, error, a manifest diagnostic). It is reported
  once per manifest by the CLI manifest pass (`manifests.rs:140`, beside
  `defaults_diags`) and by the LSP. The entry is dropped, the rest loads, and the
  manifest is invalid. Faults:

  | Fault | Message shape |
  |---|---|
  | an `E-*` code | `` `E-UNKNOWN-ATTR` is an error: an error is a contract violation and cannot be re-levelled; fix the reported source instead `` |
  | an `L-*` code | `` `L-…` is a lint rule; set its level in `lute.lint.yaml` `rules:` `` |
  | a code the toolchain does not define | `` `W-STAGE-ABSNT` is not a diagnostic code — did you mean `W-STAGE-ABSENT`? `` |
  | a bad level | `` level `silent` is not one of `off`, `info`, `warn`, `error` `` |
  | `paths: []`, a non-string, an absolute path or a `..` segment | `` `paths` takes project-relative globs, e.g. `scenes/imported/**` `` |

  "Defined" means `lute_check::evidence::classification(code).is_some()`
  (`evidence.rs:600`). This shape and code validation is one `lute-check`
  function, shared by the CLI and the LSP. Every `W-*` code in the CLI
  registry MUST be in that table (a test).

### 6.2 Application

One function, `DiagnosticLevels::level_for(code, rel_path) -> Option<Level>`
in `lute-manifest`, is applied at the reporting boundary only:

- **CLI.** `DenyPolicy` (`crates/lute-cli/src/output.rs:17`) becomes
  `SeverityPolicy { deny, deny_warnings, levels: Option<Arc<DiagnosticLevels>>, root }`.
  Every command that builds a `DenyPolicy` today (`cmd_check.rs`,
  `cmd_check_project.rs`, `cmd_compile.rs`, `compile_all.rs`, `lint.rs`,
  `cmd_trace.rs`, `cmd_expr.rs`, `cmd_constraints.rs`, `play/project.rs`,
  `lib.rs`) builds it from the gate options plus the discovered project's
  `diagnostics:`. It is applied in the one place that serializes and prints
  diagnostics (`output.rs`). The order is:
  1. the project level for (`code`, path);
  2. `--deny CODE` naming the code promotes it to error, even when the project
     set it `off` (an explicit command line beats the config);
  3. `--deny-warnings` promotes what is still a warning after step 1. An `off`
     code stays off, and an `info` code stays info.

  Errors are never demoted. Only `W-*` codes are configurable. A diagnostic
  without a document path (a manifest diagnostic) matches only an entry without
  `paths`.
- **LSP.** `backend/diagnostics.rs` (before `publish_diagnostics`, `:128`)
  applies `level_for` with the document's root-relative path. `off` is not
  published, and a relevelled diagnostic is published at its new severity.
- **Never applied to analysis.** Levels change only what is reported and the
  exit status. They never change analyses, artifacts, constraint verdicts, the
  scenario graph, or what a `.play.yaml`/`.test.yaml` expectation observes.
- **Glob matcher.** `crates/lute-lint/src/glob.rs` moves to
  `crates/lute-manifest/src/glob.rs` (pub), and `lute-lint` calls it there. It
  is a clean move: there is no re-export.

### 6.3 Exit status and markers

## 8. Node lints (#172, #177)

### 8.1 Target `node`

`lute_manifest::lint::LintTarget` (`lint.rs:81`) gains `Node` (`target: node`).
It is valid in plugin `lints:` exports and `lute.lint.yaml` `custom:` rules. The
documented target list (`lint.rs:49`) includes it.

**Rows.** One row per node, in document order, over every body the checker
walks:

- section bodies;
- `<quest>` declarations and their bodies (objectives, `<on>` handlers);
- `<reward>` children of a quest or objective, placed at their source position
  among the owner's children;
- top-level `<entry>` and `<beat>` declarations and their bodies;
- `<branch>` choices and choice bodies;
- `<hub>` choices, choice bodies and its `<return>` body;
- `<match>` arms (`<when>`, `<otherwise>`) and their bodies;
- `<timeline>` (one row; track clips are not rows).

| `node.kind` | for |
|---|---|
| `line` | a content line |
| `directive` | every `::tag{…}`: plugin and core directives, `::set`, `::assert`, `::retract`, `::accept`, `::use`, `::label`, `::jump`, `::clear`, `::end` |
| the element name | `branch`, `hub`, `choice`, `return`, `match`, `when`, `otherwise`, `timeline`, `quest`, `objective`, `on`, `reward`, `entry`, `beat` |

**Bindings:** `node`, `scene` (the existing document row) and `options`.

| Field | Meaning |
|---|---|
| `node.kind` | as above |
| `node.tag` | the directive tag or element name; `""` for a line |
| `node.speaker` | a line's speaker; `""` otherwise |
| `node.attrs` | map string → string of every attribute **as authored**: a key is present iff the author wrote it, and its value is the authored value text, unquoted (§8.1 "Authored attributes"). This includes the attributes the parser lifts into fields (`<branch id>`, `<reward kind target amount>`, `::jump{to}`) and stamps. A bare flag is `"true"`, and an `@ref` value is its source text (`@name`). An unauthored attribute is absent even when the IR carries a default (`<reward>` without `amount` has no `amount` key). `::set`/`::assert`/`::retract` have `{}`. |
| `node.index`, `node.first`, `node.last` | 0-based position in its body; first/last in that body |
| `node.depth` | 0 for a section's (or document's) top-level node, +1 per enclosing element |
| `node.prev`, `node.next` | `{ kind, tag, attrs }` of the sibling in the same body; all fields empty at a body edge |
| `node.parent` | `{ kind, tag, attrs }` of the enclosing element. At a section's top level `kind` is `"section"`; at a quest/lore document's top level `kind` is `"document"`. |
| `node.preceding` | map tag → `{ attrs }`: for each tag, the nearest node with that tag among the earlier siblings of this node and of each of its ancestors, together with the ancestors themselves. It does **not** enter the bodies of earlier siblings (another arm is not on this path). It is reset at each section and declaration. Lines are not keyed. It is read through a borrowed scope view (§8.1 "Cost"), not stored per row. |
| `node.section` | `{ index, title, id }` of the enclosing section; `{ 0, "", "" }` outside sections |

- **Anchoring and messages** work as for `line` rows: the diagnostic spans the
  node (`span` of the line, directive or element), and `{node.attrs.value}`
  interpolates.
- **Authored attributes.** The AST keeps typed values for lifted attributes
  (for example `Reward.amount: RewardAmount`, a parsed integer) and drops their
  text. `node.attrs` therefore does not rebuild text from fields. The lint engine
  re-reads the authored head from the source: `LintDocInput.text`
  (`lute-lint/src/engine.rs:31-39`, kept "for future rules") is passed to
  `compute_doc_tables` (`metrics.rs:211`). For each node, the attribute list is
  recovered from its head span with **the parser's own attribute scanner**,
  exposed by `lute-syntax` as
  `pub fn authored_attrs(source: &str, head: Span) -> Vec<AuthoredAttr { key, raw_value, key_span, value_span }>`.
  There is no second attribute grammar. Residual `Attr`s keep their
  `value_span` (`ast.rs:925-930`), and lifted ones are found by the scan. The
  LSP passes the buffer text it already holds. Acceptance:
  `<reward kind="COINS" amount="+005"/>` gives `node.attrs["amount"] == "+005"`
  and not `"5"`; `amount="5"` gives `"5"`; a reward without `amount` has
  `!("amount" in node.attrs)`; `<branch id="route">` has `id`; `@ref` and bare
  flags as in the table; a document with CRLF line ends and multi-byte text
  gives the same values.
- **Missing keys** keep CEL semantics: `node.attrs["x"]` on an absent key is an
  evaluation error (`E-LINT-EXPR`, as today). `&&` short-circuits
  (`eval.rs`, `LOGICAL_AND`), so a rule guards **every** index it takes:
  `"x" in node.attrs && node.attrs["x"] …`, `"t" in node.preceding && "k" in node.preceding["t"].attrs && …`,
  and `key in options.cases && …` before indexing an options map. Every §8.3
  recipe does this.
- **Cost.** Rows are built in the existing metrics walk (`metrics.rs:385-460`)
  in one pass.
  - **`preceding` is never copied on descent.** The walk keeps one mutable
    map `tag → &Node` plus a scope stack of undo logs. Entering a body pushes
    a frame. Visiting a node with tag `t` records the previous entry for `t`
    in the frame and sets `t`. Leaving a body pops the frame and restores its
    entries. A row's `node.preceding` is a borrowed view of that map at the
    row's point. `"t" in node.preceding` and `node.preceding["t"]` are
    O(log T) lookups. The map is materialized only when a rule returns it whole
    (`size(node.preceding)`), and then only for that row.
  - Rules are evaluated during the walk while the view is valid, or (if the
    engine keeps rows) through a persistent shared-history structure. Either
    way there is no per-row or per-descent copy.
  - The evaluator resolves a select/index chain rooted at a binding by
    reference: `Expr::Ident` no longer clones the whole row on every access
    (`eval.rs:115-118`).
  - **Acceptance** (generated documents, one `node` rule reading `preceding`,
    times recorded): node count N ∈ {5 000, 10 000, 20 000} at T = 10 distinct
    tags and depth D = 3, each doubling ≤ 2.3×; T ∈ {10, 100, 1 000} at
    N = 10 000, D = 3, 10→1 000 ≤ 2×; D ∈ {2, 8, 32} at N = 10 000, T = 10,
    2→32 ≤ 2×. A unit test counts map clones during a walk: 0 outside an
    explicit whole-map read.
- The LSP evaluates `node` rules like the other in-document targets.

### 8.2 String members

The lint CEL fragment (`eval.rs:171-268`) gains the standard CEL string
members `s.startsWith(t)`, `s.endsWith(t)` and `s.contains(t)`, member-call
form only, both operands strings. A non-string operand is an evaluation error.
There are no regexes and no macros.

### 8.3 Recipes (#177) and examples

The linting page (EN + KO) and the porting guide gain these rules (each
example is checked by `check-doc-snippets.py`). Every index is guarded (§8.1).
**Policy for an unknown discriminator:** a dependent-value rule excludes a
discriminator it has no case for, and a separate `*-known` rule reports the
discriminator itself. So each violation is reported once, by the rule that
names it.

```yaml
lints:
  - id: signal-needs-menu
    target: node
    when: 'node.tag == "signal" && "value" in node.attrs && node.attrs["value"] == "puzzle" && node.next.kind != "branch"'
    level: warn
    message: "a puzzle ::signal must be followed by a <branch>"
  - id: section-opens-with-bg
    target: node
    when: 'node.first && node.parent.kind == "section" && node.tag != "bg"'
    level: warn
    message: "section {node.section.title} opens with {node.tag}"
  - id: beat-label-prefix
    target: node
    when: 'node.tag == "label" && scene.kind == "beat" && "name" in node.attrs && !node.attrs["name"].startsWith("b_")'
    level: error
    message: "a beat's labels start with b_"
  # #177, same element: `mode` selects the legal `speed`s.
  - id: move-mode-known
    target: node
    when: 'node.tag == "move" && "mode" in node.attrs && !(node.attrs["mode"] in options.speeds)'
    level: error
    message: "unknown move mode {node.attrs.mode}"
    options: { speeds: { walk: [slow, normal], run: [normal, fast] } }
  - id: speed-fits-mode
    target: node
    when: >-
      node.tag == "move" && "speed" in node.attrs && "mode" in node.attrs &&
      node.attrs["mode"] in options.speeds &&
      !(node.attrs["speed"] in options.speeds[node.attrs["mode"]])
    level: error
    message: "speed {node.attrs.speed} is not legal in mode {node.attrs.mode}"
    options: { speeds: { walk: [slow, normal], run: [normal, fast] } }
  # #177, a marker directive before the branch decides the legal option values.
  - id: interaction-kind-known
    target: node
    when: 'node.tag == "interaction" && (!("kind" in node.attrs) || !(node.attrs["kind"] in options.cases))'
    level: error
    message: "::interaction needs a known kind"
    options: { cases: { greet: [wave, bow], gift: [accept, decline] } }
  - id: option-fits-interaction
    target: node
    when: >-
      node.tag == "option" && "value" in node.attrs &&
      "interaction" in node.preceding && "kind" in node.preceding["interaction"].attrs &&
      node.preceding["interaction"].attrs["kind"] in options.cases &&
      !(node.attrs["value"] in options.cases[node.preceding["interaction"].attrs["kind"]])
    level: error
    message: "option {node.attrs.value} does not belong to this interaction"
    options: { cases: { greet: [wave, bow], gift: [accept, decline] } }
  # #177 with #164 stamps: the parent <branch> carries the discriminator.
  - id: menu-type-known
    target: node
    when: 'node.kind == "branch" && "menuType" in node.attrs && !(node.attrs["menuType"] in options.keys)'
    level: error
    message: "unknown menu type {node.attrs.menuType}"
    options: { keys: { plain: [L1, R1], timed: [T1] } }
  - id: choice-fits-menu
    target: node
    when: >-
      node.kind == "choice" && "optionKey" in node.attrs &&
      "menuType" in node.parent.attrs && node.parent.attrs["menuType"] in options.keys &&
      !(node.attrs["optionKey"] in options.keys[node.parent.attrs["menuType"]])
    level: error
    message: "option key {node.attrs.optionKey} is not a {node.parent.attrs.menuType} key"
    options: { keys: { plain: [L1, R1], timed: [T1] } }
```
