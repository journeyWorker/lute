# Lute Scenario DSL — 0.22.0: A reference player that can stand in for the engine

- **Version:** 0.22.0
- **Status:** Draft
- **Date:** 2026-09-25
- **Scope:** the play/test harness model. Three dogfood games (a detective
  mystery, a roguelike hub, a day-clock visual novel) each shipped a fake
  engine inside their content because `lute play` could not write the state
  the engine owns, could not start from a save, could not assert anything,
  and could not vary decisions per step. 0.22.0 closes those gaps, gives run
  boundaries a lifecycle, lets trace and test apply Datalog rules, and gives
  occasion targets a vocabulary. It also carries the two identity changes
  0.21.1 deferred because they alter compiled output.
- **Evidence:** dogfood triage T2-1 … T2-10, T2-12 (partial), T1-9, T1-10,
  T1-15, T3-1, T3-3, T3-4, T3-5, T3-12, T3-14, T3-17.
- **IR:** `voiceKey` default and component `lineId` change (§11); additive
  `QuestMeta.tier`, `EntryCmd.once`; occasion `target` domain in the
  capability snapshot.

## 1. Engine-written state in play

### 1.1 `engine:` steps

A play step MAY write what the engine owns:

```yaml
steps:
  - occasion: runEnd
  - engine:
      state:
        run.outcome: fell
        user.runs: { add: 1 }
      facts: [slew(warden)]
      retract: [holds(ember)]
```

- `state:` values are literals, or `{ add: <number> }` for a numeric delta.
  Paths MUST be declared; values MUST fit the declared type (the trace-mock
  rules, `E-MOCK-*`).
- `facts:` / `retract:` take ground atoms of declared relations and MAY name
  **reserved** relations — the engine is exactly who asserts them.
- An `engine:` step presents nothing and raises no occasion; the quest
  lifecycle settles after it (a state change may complete an objective).
- `newRun` also accepts the long form `newRun: { state: …, facts: … }`, applied
  after the reset — the new run's seed.

### 1.2 `owner: engine`

A state declaration MAY carry `owner: engine`:

```yaml
state:
  run.day:  { type: number, default: 1, owner: engine }
```

Content that writes it (`::set`) is `E-ENGINE-OWNED-WRITE`. Reads are
unrestricted. `owner: engine` paths are written by the engine at runtime and
by `engine:` steps / mocks in the toolchain. Reserved relations already have
this meaning for facts (`reserved: true`).

## 2. Per-step decisions

A step MAY carry its own `choose:` map; for that step's presentation it
replaces the script's top-level `choose:` key by key. The top-level map
remains the default for every step.

```yaml
  - occasion: talk
    target: npc.oskar
    choose: { ask: notYet }
```

## 3. Starting from a save

Top-level script keys seed the playthrough's history before step 1:

| Key | Meaning |
| --- | --- |
| `visited: [scene ids]` | scenes presented in this save (feeds `visited()` and `after: visited(…)`) |
| `presented: { user: [beat ids], run: [beat ids] }` | spent `once: user` / `once: run` beats |
| `quests: { <id>: unset \| active \| complete \| failed }` | quest lifecycle status |
| `entriesRead: { run: [ids], user: [ids] }` | `entry.<id>.read` (run) / `entry.<id>.everRead` (user, §7) |

Unknown ids are usage errors (exit 2). The same keys are accepted by trace
mocks and `*.test.yaml` where meaningful (`visited`, `quests`,
`entriesRead`).

## 4. Assertions in play scripts

A step MAY carry `expect:`:

```yaml
  - occasion: hubVisit
    expect: { winner: hub.welcome, offered: [hub.welcome, hub.idle], notOffered: [hub.trophy] }
```

`winner` names the presented beat (`none` when the occasion passes);
`offered` / `notOffered` constrain the eligible set. A top-level `expect:`
judges the end of the playthrough:
`{ exit, quests, state, facts, notFacts, transcriptContains, transcriptLacks }`.

A failed expectation is reported with the step and the actual value, and
`lute play` exits 1. `lute test` runs every `*.play.yaml` that carries any
`expect:` alongside `*.test.yaml`, and `--coverage` counts every document a
play presented.

## 5. Scenario-test expectations

`*.test.yaml` gains `transcriptLacks: [...]`, `offered: { <choice id>: [opts] }`
(the options actually offered at that choice), and `entry: <id>` /
`entries: [ids]` for a lore file (walks those entries in order).

## 6. Derivation in trace and test

`lute trace`, `lute test` and `lute play` apply the project's seed facts and
Datalog rules (stratified negation) over the mocked/asserted base facts —
`derive: true` is the **default**. A mock MAY still supply a derived atom; it
is then a seed like any other. `derive: false` (mock key, `--no-derive`)
restores the 0.21 behavior, in which an unmocked derived atom is unknown and
a note names each derived read. `lute play --explain <atom>` prints the
derivation tree (or the failing premises) for one atom at the end of the play.

## 7. Run boundaries

- `<quest tier="run">` — the quest's status and objectives reset to `unset`
  at `newRun` (and, in the engine contract, when a run starts). Default
  `tier="user"`: status persists across runs, as today.
- `entry.<id>.everRead` — a reserved **user-tier** bool beside the run-tier
  `entry.<id>.read`, set on first read and never reset by `newRun`.
- Entry beats accept `once="run" | "user"`: an entry whose read flag (resp.
  `everRead`) is set is not eligible. Absent = repeatable, as in 0.21.
- `W-QUEST-HANDLER-DEAD`: an `<on event="questFailed">` on a quest that has
  no `fail` condition and no failing objective.

## 8. Occasion targets as a vocabulary

An occasion's `target` MAY name a domain:

```yaml
occasions:
  talk: { target: { prefix: npc, entity: person } }
```

A target is then `<prefix>.<member>` where `<member>` is a member of the
entity kind (`entities:` in the schema). A beat or objective target outside
it is `E-BEAT-ATTR` with a did-you-mean; a play step target outside it is a
usage error. `target: true` keeps the 0.21 shape-only meaning.

## 9. Firing world events from play

A play step `- event: <name>` fires a declared world event exactly as trace
`events:` does (`<on event>` handlers of active quests run). An
`E-UNKNOWN-EVENT` whose name is a declared occasion says so.

## 10. Passing on an offered list

`pick: none` on a `select: all` occasion closes the list: nothing is presented
or spent; `on=` objectives are still judged.

## 11. Identity

- The default `voiceKey` template becomes `{prefix}.{speaker}-{code}`
  (project-unique). **Breaking** for projects that recorded audio against the
  0.21 keys; pin `identity.voiceKey: "{speaker}-{code}"` to keep them.
- Lines expanded from a component are addressed
  `{prefix}.{component}#{n}.{speaker}_{code}` where `n` is the 1-based `::use`
  ordinal in the host, so two uses never share a `lineId`.

## 12. Staging analysis follows paths

`W-STAGE-ABSENT` forks the stage state at each choice/match arm and joins at
convergence (the fact must-set discipline). A character hidden by `::bg`
auto-hide is recorded as exited, so a later line by them warns.

## 13. Tooling

- `lute init --template beats` / `lute new scene --on <occasion> [--target]`:
  scaffolds use `id:`, respect `defaults:`, and create `plugins/`, `plays/`,
  `tests/`; `lute new` outside a project says so.
- Lint defaults exclude beat scenes, components and lore from linear-VN metrics
  and count only staging directives.
- `lute context` lists defs, reserved relations and tiers, `owner: engine`
  paths, component signatures, built-in directives and all ids.
- `lute doctor` reports active plugins and occasions, and a `lute-lsp`
  version that differs from `lute` (`lute-lsp --version` prints it).
- `W-BEAT-PRIORITY-TIE`: two beats on one occasion/target with equal priority
  whose conditions are not provably exclusive (the winner depends on file
  order). An advisory note for a `once: run` beat whose `when` reads only
  `user.*` state.
- `lute tag` / `lute fix` accept directories (recursive, sorted).
- Play steps MAY carry `label:` (printed in the transcript) and
  `repeat: <n>`.

## 15. Decisions

| # | Decision | Rationale |
| --- | --- | --- |
| **D-A** | engine writes are play steps, not content | the fake-engine scenes the dogfood games shipped are exactly what the contract says content must not be |
| **D-B** | `derive: true` by default | trace/test disagreed with run/play about the same project; the closed-world rules are the language's semantics, not an opt-in |
| **D-C** | quest tier defaults to `user` | changing persistence of existing quests would silently alter every project; roguelike authors opt in |
| **D-D** | no harness-only profile | with `engine:` steps the harness content disappears, so the profile gap that blocked it (0.21.1 made check-project enforce one snapshot) no longer matters |
| **D-E** | voiceKey default changes now, with a pin | a colliding default is a data-loss bug in audio pipelines; a one-line pin preserves old keys |
