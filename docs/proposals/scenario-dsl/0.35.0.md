# Scenario DSL 0.35.0

Phase 4 of `docs/design/architecture-direction.md` (§5): a lossless source
layer and canonical formatter, source/project revisions, task-scoped context,
position queries, semantic diff, and an atomic source patch loop. This is a
clean cutover under D6. The authoritative inputs remain `.lute` and project
declarations (D2), while the project model is an internal, read-only query
surface (D3). All language, IR, and toolchain axes move to `0.35.0`; the IR
shape is unchanged except where a field is required to carry an already
specified contract.

The compiler and model are the AI's oracle. The normative flow is:

`Inspect → Plan → Patch → Check → Replay → Review`.

The structured CLI JSON surfaces below are the primary interface. 0.35 does
not add a chat application, session manager, MCP server, or general agent
harness (D10; `docs/design/architecture-direction.md:225-241`).

## 1. Lossless syntax + `lute fmt`

### 1.1 Lossless layer

`lute-syntax` currently peels frontmatter, blanks body comments while retaining
offsets, and parses structural lines into an AST (`crates/lute-syntax/src/parser.rs:195-232`,
`crates/lute-syntax/src/lex.rs:240-258`). The AST has no comment or blank-line
fields (`crates/lute-syntax/src/ast.rs:1-21`), and tree-sitter's comments and
whitespace are editor extras rather than formatter-owned trivia
(`tree-sitter-lute/grammar.js:24-31`). 0.35 adds a lossless token/line stream
beside that AST; the AST parser and its semantic behavior are unchanged.

For every source byte sequence `x`, the stream has ordered tokens and trivia
whose concatenation is exactly `x`, including line endings, indentation,
comments, blank lines, delimiters, attribute lexemes, opaque content text, and
frontmatter envelope bytes. Every structural token carries an original byte
span and, when applicable, the semantic AST node/attribute identity. A stream
round-trip test MUST assert `concat(tokens(x)) == x` for valid and arbitrary
input. This is source preservation, not a second semantic parser.

Body comments (`//` and `/*…*/`) and blank lines are trivia. Content/prose text
is opaque line text: the formatter MUST never rewrite it. Attribute order and
CEL source text are similarly opaque payloads; the formatter may normalize the
surrounding layout but MUST NOT reorder attributes or rewrite CEL. Existing
attribute storage proves authored order is a `Vec<Attr>` and CEL retains raw
text (`crates/lute-syntax/src/ast.rs:1071-1118`; `docs/design/phase4-inventory/formatter.md:194-199`).

Frontmatter YAML and project/schema/plugin YAML are preserved byte for byte
except trailing whitespace and final-newline normalization. Full YAML
canonicalization is deferred: serde YAML currently provides semantic values
and reconstructed spans, not a lossless CST (`crates/lute-manifest/src/yaml_text.rs:1-47`).
The stream MUST therefore treat YAML as an opaque region for 0.35 formatting;
YAML CST canonicalization is a post-0.35 decision, recorded in §9.

### 1.2 Canonical rules

`lute fmt [--check] <path…>` accepts files or directories. Directory traversal
is recursive, sorted, and includes `.lute` plus project/schema/plugin YAML
inputs. Without `--check`, it writes only changed files. With `--check`, it
writes nothing and exits 1 if any selected file is not canonical; I/O or
formatting failure exits 2. A clean check exits 0. It MUST be deterministic
independent of host platform.

The canonical form is deliberately minimal:

1. LF line endings.
2. No trailing horizontal whitespace.
3. Exactly one final newline for non-empty files (and no extra final newline
   run); empty files remain empty.
4. Runs of blank lines collapse to one blank line, while comment text and
   opaque prose lines remain unchanged.
5. Nested blocks use one canonical indentation unit (two spaces); matching
   closing delimiters align with their opener. Existing zero- and two-space
   corpus forms demonstrate why this must be explicit rather than inferred
   (`docs/examples/carry-ep.lute:9-28`,
   `docs/examples/games/summer-station/scenes/sol/first.lute:20-43`).
6. Attributes have one space between adjacent attributes and consistent spacing
   around directive/attribute delimiters. Attributes remain in authored order.
7. String attributes use `name="value"` according to the 0.32 quote rule:
   double quotes outside, single quotes inside CEL. The formatter escapes only
   the enclosing attribute syntax; it never changes CEL expression text.
8. Comments, comment text, and prose/line text are byte-preserved apart from
   the whitespace rules above. A trailing comment remains attached to its
   original line.

Frontmatter and YAML receive only rules 1–3. The formatter MUST NOT reorder
keys, normalize scalar quote style, wrap flow collections, or move comments in
YAML. Existing source rewrites are span edits rather than serializers, which is
the preservation pattern to reuse (`crates/lute-cli/src/rewrite.rs:210-211,282-319,900-917`).

### 1.3 Invariants and LSP

The formatter has four mandatory invariant tests:

* idempotence: `fmt(fmt(x)) == fmt(x)`;
* semantic preservation: compile before/after and semantic-diff them; the diff
  is empty after ignoring spans and regenerated `addr`;
* comment preservation: the multiset of comment payloads is unchanged;
* parser robustness: a property/fuzz test proves arbitrary input never panics.

The lossless stream gets unit/property tests for source concatenation, line
endings, comments, blank-line runs, nested indentation, attribute spacing,
quote handling, opaque CEL/prose, and YAML byte preservation. The dogfood
corpus is formatted once in the release, and CI runs `lute fmt --check` over
it. This fulfills the formatter and parser properties required by D11
(`docs/design/architecture-direction.md:243-255`).

The LSP uses exactly this formatter core. `textDocument/formatting` returns a
full-document `TextEdit` (and no independent printer); range formatting is not
added in 0.35. The server advertises a formatting provider beside its existing
full-sync and feature capabilities (`crates/lute-lsp/src/backend.rs:691-734`).
Formatting an unsaved document uses the text supplied by the LSP request and
never writes the workspace.

## 2. Revisions

A file revision is the lowercase hexadecimal SHA-256 digest of the exact file
bytes. The project revision is the lowercase hexadecimal SHA-256 digest of a
canonical byte encoding of the sorted `(path, fileRevision)` pairs for every
input file actually read by `ProjectModel`: source documents, manifest,
schemas, plugins, and imports. Paths are normalized to UTF-8 `/`-separated
paths relative to the project root; the encoding includes length-delimited
path and revision fields, so concatenation is unambiguous. A file is included
once under its canonical path. The sorted pair set, not filesystem order,
defines the project digest. Inputs outside the root (e.g. a schema imported
from `../shared/`) are included with their canonical path expressed relative
to the canonical root (`../shared/x.schema.yaml`, lexically normalized), so a
change to an external input changes the project revision; a path with no
relative form (another volume) uses its canonical absolute path prefixed
`abs:`.

The model currently reads source files, assembles inputs, checks, compiles,
and indexes artifacts (`crates/lute-model/src/project.rs:102-142,168-240`),
but `ModelDocument` has no source revision (`crates/lute-model/src/project.rs:59-71`).
0.35 adds a revision snapshot at the model boundary and exposes it through
context, patch, and diff. Revisions are content revisions, not the LSP open
version (`crates/lute-lsp/src/backend.rs:50-51,319-321`) and not the existing
capability snapshot stamp (`crates/lute-cli/src/cmd_context.rs:393-395`).

`context`, `patch`, and `diff` print both `projectRevision` and a deterministic
`files` map of path to file revision. A patch's optional per-file base map is
checked against this map. New files use the empty/nonexistent file convention
specified by the patch schema; moved files retain their bytes and identity.

## 3. Task-scoped context + position queries

### 3.1 Command and target

`lute context <dir> --target <nodeKey> [--json]` builds one `ProjectModel` for
the resolved project root and accepts the canonical `kind:key` syntax already
used by `NodeKey` (`crates/lute-model/src/graph.rs:60-77`). The existing graph
already defines project/document/scene/beat/shot/line/choice/quest/objective/
reward/entry/occasion/relation/state/def/component/expanded/fact/clock/engine
kinds (`crates/lute-model/src/graph.rs:9-57`) and stores source files, spans,
reasons, and evidence on graph edges (`crates/lute-model/src/graph.rs:79-105`).
Unknown or ambiguous keys are an error, not a best-effort guess.

The target object contains:

* `kind`, canonical `key`, `file`, byte/line/column span, and a bounded source
  excerpt from the original file;
* declared `reads`, `writes`, `queries`, and `asserts` with relation/path,
  source span, and reason;
* direct references in both directions, with edge kind, evidence, reason, and
  location;
* affected items from the same reverse impact closure used by `lute impact`
  (the current impact surface already emits evidence, reasons, files, lines,
  spans, line IDs, and speakers: `crates/lute-model/src/impact.rs:102-138`);
* related tests and plays discovered by exact rules: `static` means a script
  step/expectation names the node (scene/beat/entry/quest ID or lineId);
  `witnessed` means `--run` actually executes the script and visits the node.
  Other scripts are not included and appear in `notIncluded` with a count and
  reason;
* relevant vocabulary limited to relations, state paths, defs, and enum
  members used by the target and its direct neighbors;
* `projectRevision` and `files` revisions;
* `notIncluded`, an explicit list of dynamic/retrieval-only relations, engine
  boundaries, and truncations, each with a reason and count.

The graph is a semantic dependency graph, not a source reconstruction layer;
its nodes and edges are deterministic and source-span-bearing
(`crates/lute-model/src/graph.rs:99-119`). Context therefore reads the source
through the revision snapshot and emits excerpts separately from model data.

Related-script discovery enumerates every `*.play.yaml` and `*.test.yaml`
under the model root and follows the existing script loader's includes.
Static references are exact typed step/expectation fields, not arbitrary
substring matches. With `--run`, that discovered set is executed through the
existing play/test machinery; a visit is a recorded node/line presentation,
quest transition, or an expansion's source-origin join. Derived nodes without
a run-observable join remain excluded with a reason/count. Scripts not run,
unresolved includes, dynamic raises, and targets with no observable join are
explicit coverage exclusions; no static relationship is called witnessed.

### 3.2 Bounds and JSON

`--max-items N` applies independently to each bounded collection (references,
impact items, tests/plays, vocabulary, excerpts). Results are sorted by group,
canonical key, relative file, and span start before truncation. Every truncated
collection adds a `notIncluded` record with `kind`, `limit`, `available`, and
`omitted` count. Human output is a projection of the same JSON; it is not a
second query implementation.

Normative top-level shape:

```json
{
  "schemaVersion": "0.35.0.context",
  "projectRevision": "sha256:…",
  "files": {"scenes/sol/first.lute": "sha256:…"},
  "target": {"kind":"choice","key":"sol.first:solHello.coffee", "file":"scenes/sol/first.lute", "span":{"line":21,"column":3}, "excerpt":"<choice …>"},
  "declared": {"reads":[],"writes":["run.aff.sol"],"queries":[],"asserts":[]},
  "references": {"in":[{"node":"scene:sol.first","evidence":"proven"}],"out":[]},
  "affected": [],
  "tests": [], "plays": [],
  "vocabulary": {"relations":[],"state":[],"defs":[],"enums":[]},
  "notIncluded": []
}
```

The example key is illustrative; producers MUST serialize the actual graph key,
not synthesize a new identity. Every output includes an explicit `schemaVersion`
for this JSON surface.

### 3.3 Position queries and shared resolver

`lute context <file> --at <file>:<line>:<col> [--json]` returns
`expectedType` and `visibleSymbols`, plus the resolved cursor kind and source
span. The coordinate is one-based line/column for the CLI; conversion uses the
same UTF-16/byte index rules at the LSP boundary.

The current LSP feature layer resolves a byte cursor into directives,
attributes, CEL, set paths, interpolations, and construct positions
(`crates/lute-lsp/src/features/mod.rs:88-173`), then hover/completion merge
imports with the checker's precedence (`crates/lute-lsp/src/features/mod.rs:64-85`);
expected type is currently threaded into CEL checking in the backend
(`crates/lute-lsp/src/backend.rs:647-650`). 0.35 extracts this resolution and
symbol/type environment into a shared library. LSP hover/completion,
`textDocument/definition`, `textDocument/references`, and the CLI position
query all call that library. No second resolver or CLI-only precedence rule is
permitted. `visibleSymbols` is the deterministic completion candidate set at
the cursor; `expectedType` is the checker-resolved type or `null` where the
position has no type expectation.

## 4. Semantic diff

`lute diff <before> <after> [--json]` accepts a project directory on either
side or `git:<rev>`. A Git side is materialized read-only with `git archive`
into a private temporary directory and deleted after comparison. The extractor
MUST reject symlinks/submodules, absolute paths, and any archive entry
containing `..`; only regular files and directories are admitted. It verifies
every materialized input is a regular file below the temp root and hashes the
extracted file set before model construction. Neither side is modified.

The comparator builds both ProjectModels and matches nodes by canonical NodeKey,
never by `addr` or span. Patchable targets MUST be span-bearing source nodes.
Project/dependency-only state nodes without a source anchor are refused with
`E-PATCH-TARGET` ("no source anchor"); state declarations in schema YAML expose
their retained YAML declaration spans and are editable only through
`replaceText`. Span-only changes are not semantic changes. It reports added,
removed, and moved nodes, where a move is a path change with preserved
identity. For every matched node it compares:

* guards as canonical ASTs under the exact 0.32 Lute CEL profile: the
  `cel-parser` AST normalizes whitespace and parentheses while preserving
  literal kind. If either side is unparsable, the diff contains
  `conditionUnparsable` and any relevant preserve check fails; there is no text
  fallback;
* writes, asserts, retracts, grants, and rewards;
* line text, `lineId`, `voiceKey`, and speaker;
* choice effects and targets;
* `once`, `on`, `priority`, `share`, `spentBy`, `after`, `until`/`by`,
  period/duration/advance/clock-consumption, cadence, and season attributes;
* reachability and constraint verdicts;
* `requiredSemantics`, host/engine paths, and reserved relations;
* relevant vocabulary and declaration changes.

Rewards match by authored content within their owner: owner key, reward kind,
item/amount, and `when`. The graph's ordinal reward key remains display
provenance only. Two identical rewards under one owner are ambiguous and MUST
produce `E-PATCH-PRESERVE` when a preserve claim depends on them.

Each change has `kind`, `node`, `before`, `after`, and `file:line` locations on
both sides when available. The JSON additionally carries both revisions and a
stable `schemaVersion`; human output is a deterministic projection. Empty
means semantically equal, including pure formatter changes.

The comparator is a model-level API in `lute-model/src/diff.rs`, used by both
`cmd_diff.rs` and patch application. It compares the model substrate already
exposed by `ProjectModel` (`crates/lute-model/src/lib.rs:24-44`) and the graph
identity/provenance (`crates/lute-model/src/graph.rs:60-105`), while treating
compiler-local `addr` as positional as required by D8
(`docs/design/architecture-direction.md:187-204`). It is not the existing
trace-vs-compiled-run differential oracle, which compares two executions of one
source (`crates/lute-cli/src/differential.rs:1-54`).

## 5. Patches

### 5.1 Input and edit vocabulary

`lute patch <dir> <patch.json> [--dry-run] [--json]` consumes:

```json
{
  "base": {"project":"sha256:…", "files":{"scenes/sol/first.lute":"sha256:…"}},
  "targets": ["scene:sol.first"],
  "edits": [],
  "preserve": [
    {"ids":["scene:sol.first"]},
    {"choiceEffects":["choice:…"]},
    {"hostContracts":true}
  ]
}
```

The `base.project` revision is required. `base.files` is optional; when present
it is an additional exact assertion for those paths. Edit operations are
anchored to model node spans and are:

* `replaceNode {node, text}`;
* `insertBefore {node, text}` and `insertAfter {node, text}`;
* `replaceAttr {node, attr, value}`;
* `removeNode {node}`;
* `createFile {path, text}`;
* `moveFile {from, to}`;
* `replaceText {file, rev, span, text}`, the escape hatch, which MUST match
  the named file revision exactly.

The JSON schema rejects unknown operation fields, malformed node keys, missing
required fields, overlapping byte ranges, and duplicate edit anchors. `targets`
are a declaration of intended scope, not permission to bypass checks.

### 5.2 Atomic application

Application stages every edit in memory, preserving all untouched source bytes.
It then formats touched regions with the §1 rules, rebuilds `ProjectModel` from
the staged file set, applies `check-project` rules, computes the shared
before/after semantic diff, and enforces `preserve`. Only after every stage
succeeds are all files written. A failure leaves every original file unchanged.
`--dry-run` performs all stages and emits the proposed writes/diff without
writing. A successful application prints before and after project/file
revisions and the semantic diff; `--json` emits only the versioned machine
surface.

A patch exits 0 on success, 1 when a valid patch produces a semantic change
that the caller must review (the change is still reported), 2 on refusal or
I/O. Refusals have one stable code:

| code | refusal |
|---|---|
| `E-PATCH-STALE` | project or asserted file revision differs from `base` |
| `E-PATCH-TARGET` | unknown, ambiguous, or source-anchor-less target |
| `E-PATCH-EDIT` | edit is outside its target node, overlaps another edit, or has an invalid span |
| `E-PATCH-CHECK` | staged model has new check errors; carries diagnostics |
| `E-PATCH-PRESERVE` | semantic diff violates preserve; names every violated item |

A stale or refused patch MUST NOT attempt a partial write. The existing `tag`
and `fix` commands remain their narrow mechanical operations until this clean
cutover; neither is silently reinterpreted as `patch`
(`crates/lute-cli/src/cli.rs:238-268`).

### 5.3 Preserve contract

`preserve` is checked against the semantic diff, never trusted from the AI:

* `ids: [nodeKey…]`: each node still exists with the same key;
* `lineIds` and `voiceKeys`: all existing values in scope are unchanged. A
  line without an authored code gets a positional lineId (`lute-compile`
  `address.rs`), which an insertion before it legitimately shifts, so the diff
  reports it. Run `lute tag` before an edit to give every line a stable code;
  the edit-task bases are tagged;
* `choiceEffects: [nodeKey…]`: writes, asserts, and grants of each choice are
  unchanged;
* `rewards: [nodeKey…]`: reward grants are unchanged. Matching uses authored
  owner/kind/item-or-amount/`when`, never the ordinal display key; identical
  rewards under one owner are ambiguous and fail closed;
* `hostContracts`: `requiredSemantics`, `owner:engine` paths, reserved
  relations, and CEL environment are unchanged;
* `conditions: [nodeKey…]`: guards are unchanged;
* `reachability: [nodeKey…]`: verdict is unchanged;
* `constraints`: no constraint verdict gets worse.

A `moveFile` preserves identity: `meta.id`, line IDs, voice keys, and semantic
NodeKeys remain unchanged; references are updated by the patch or the patch is
refused/flagged by `E-PATCH-PRESERVE`. D8 explicitly says a move or rename is
not delete-plus-create and that `addr` is not identity
(`docs/design/architecture-direction.md:187-204`). The patch engine MUST
report every violated item, not only the first.

Component-expanded identity uses a source-level fingerprint consisting of
component name, authored argument bindings, enclosing node key, and authored
stable child IDs when present. Inserting a new use therefore does not renumber
existing instance scopes. If two uses have identical fingerprints, matching is
ambiguous and MUST refuse with `E-PATCH-PRESERVE` rather than guess. This
closes the D8 ordinal-instance gap for the edit transaction without adding an
IR identity field; permanent authored component-instance keys remain a phase-5
follow-up (`docs/design/architecture-direction.md:196-203`).

## 6. Edit-task suite

The release exit criterion is a checked-in `conformance/edit-tasks/` suite
with one directory for each Appendix A task. Each task contains:

* `task.md`: the English instruction an AI receives plus the Korean report
  task name;
* `base`: a dogfood game reference, or a fixture under
  `conformance/edit-tasks/_games/` where the corpus lacks the construct;
* `patch.json`: a correct reference edit written by the maintainers;
* `expect.json`: required intended changes, forbidden changes, and `preserve`;
* one or more trap patches representing the report's error-to-discover column.

`crates/lute-cli/tests/edit_tasks.rs` and either `scripts/edit-tasks-report` or
`lute patch --report` apply every patch in a temporary copy. The runner records
validity/check result, intended semantic change presence, unintended semantic
diff, preserved-ID changes, and every trap verdict/code. It writes the checked-in
`conformance/edit-tasks/REPORT.json`; the test fails on regressions. The suite
must use the same formatter, model build, diff API, and preserve checker as
normal commands—no task-specific oracle.

The report is an experiment plan, not an existing result; its 12 tasks and
metrics are specified at `reports/lute_report_03_bundle/lute_report_03.md:869-916`.
The release records syntax validity, type/reference validity, intended-change
accuracy, unintended diff, preserved-ID changes, repair count, tokens, tool
calls, elapsed time, and human review time without collapsing them into one
score (`reports/lute_report_03_bundle/lute_report_03.md:910-916`).

## 7. AI harness surface

0.35 publishes one thin adapter page, `docs/handbook/ai-harness.md`, containing
only the versioned JSON contracts for `context`, `patch`, `diff`, and the
position query, exit codes, revision rules, and the inspect/plan/apply/check
sequence. The CLI remains the boundary: TypeScript or another harness invokes
`lute` as a subprocess and consumes JSON. There is no chat UI, session store,
MCP server, or Lute-specific agent protocol, matching D10's interface order
(`docs/design/architecture-direction.md:225-241`). The page is a projection of
this proposal, not a second normative source; if examples differ, this spec
wins.

## 8. Diagnostics table

| code/surface | condition | exit | required payload/action |
|---|---|---:|---|
| `E-FMT` | formatter cannot parse or preserve the requested file | 2 | file and span; no write |
| `E-FMT-CHECK` | `fmt --check` found noncanonical bytes | 1 | file and first differing span |
| `E-CONTEXT-TARGET` | target unknown or ambiguous | 2 | candidate keys and locations |
| `E-CONTEXT-POSITION` | `--at` coordinate invalid or outside source | 2 | file and coordinate |
| `E-PATCH-STALE` | base project/file revision mismatch | 2 | expected/actual revisions |
| `E-PATCH-TARGET` | unknown/ambiguous target or no source anchor | 2 | target, candidates, and anchor reason |
| `E-PATCH-EDIT` | out-of-scope, overlapping, malformed, or escape-hatch mismatch | 2 | operation index and span |
| `E-PATCH-CHECK` | new staged check/project error | 2 | complete diagnostics |
| `E-PATCH-PRESERVE` | preserve violation, including ambiguous reward/component matching | 2 | each item and diff change |
| `E-DIFF-INPUT` | side cannot be read/materialized/built, including unsafe archive entry | 2 | side and model diagnostics |
| `E-DIFF-MODEL` | comparison cannot produce a complete model | 2 | project diagnostics |
| `E-TASK-TRAP` | suite trap did not refuse or flag as expected | test failure | task, trap, expected/actual verdict |

Existing CLI diagnostics are stable code surfaces and `lute --explain` remains
available (`docs/design/architecture-direction.md:320-331`); the new codes are
additive within the 0.35 cutover and are registered in the same registry.

## 10. Compatibility and migration

0.35 is a clean cutover under D6: all language, IR, and toolchain version
stamps move to `0.35.0`; there is no legacy formatter, patch mode, revision
alias, or dual resolver. The execution IR shape remains unchanged unless the
implementation proves an existing field is insufficient; such a change must
be called out as an IR-breaking change before landing. `addr` remains
build-local and is never accepted as an AI identity.

The release formats the complete dogfood corpus and commits the resulting
source layout in the same change. CI then runs `lute fmt --check`, model/diff/
patch/context tests, and the 12-task report. Existing `lute tag` and `lute fix`
behavior is migrated only where the corpus needs it; they remain separate
mechanical commands, not aliases for `patch` (`crates/lute-cli/src/cli.rs:238-268`).
LSP clients that support `textDocument/formatting` receive the canonical
formatter; clients that do not continue using existing diagnostics and code
actions.

The clean cutover is classified as source/toolchain/analysis breaking, not as
an execution-IR semantic change. Patch consumers MUST pin the JSON
`schemaVersion`, send the project revision returned by context, and treat
unknown fields as an error in this pre-1.0 internal surface. A first external
consumer would require a new compatibility policy under D6/D5.
