# Lute Scenario DSL — 0.16.0: Declarative rewards

- **Version:** 0.16.0
- **Status:** Draft
- **Date:** 2026-09-01
- **Scope:** the language axis gains ONE new element — self-closing
  `<reward kind= target= amount= when= on=/>`, legal only as a direct child
  of `<quest>` or `<objective>` — plus the engine rules that grant it and an
  optional plugin vocabulary export (`rewardKinds:`) that makes `kind`/
  `target` statically checkable. Two new diagnostic codes (`E-REWARD-ATTR`,
  `E-REWARD-KIND`); `reward.when` joins the ordinary CEL-slot registry
  (profile, `E-MAYBE-UNSET`, unset-sentinel guards). The tree-sitter grammar
  gains a `reward` production (tags are enumerated), but `capabilityVersion`
  is UNCHANGED for every project that installs no `rewardKinds:`-declaring
  plugin — the stamp tracks the core capability snapshot, and the new
  snapshot section is guarded (empty ⇒ byte-identical hash).
- **IR:** additive-only. `QuestCmd.rewards` and `ObjectiveEntry.rewards`
  (arrays of `RewardEntry`, omitted when empty — a rewardless document is
  byte-identical). `RewardEntry`: `kind`, optional `target`, exactly one of
  `amount` / (`amountMin` + `amountMax`), optional `when` (`CelPair`),
  quest-level `on` (`"complete"` default, omitted, or `"failed"`).
- **Design record:**
  [`docs/superpowers/specs/2026-09-01-lute-reward-design.md`](../../superpowers/specs/2026-09-01-lute-reward-design.md).

## 1. Motivation

Conditions are first-class, statically checked surface; rewards were only
operational — `<on event="questComplete">` bodies carrying plugin `::grant`
directives. Execution is correct (exactly-once, quest-scoped since 0.14.0)
but the artifact carries rewards as commands inside a handler, so nothing
reads "this quest's rewards" as data: no journal preview at accept time, no
balancing extraction, no reward-shaped lint, and a conditional reward is
equally invisible. 0.2.0 §Non-goals deferred reward kinds to a follow-on
that never shipped; the adoption assessment pushed 1,759 `quest_rewards`
rows (16 kinds, negative amounts real) through the handler idiom and rated
the fit high — the missing half is data, not execution. `0.16.0` adds the
data and leaves execution where it has always lived: the engine.

## 2. `<reward/>` — the declaration

```lute
<quest id="anonLook" start="holds(clearedIdolaEvent(npc_anon))">
  <reward kind="EXP_ACCOUNT" amount="80"/>
  <reward kind="ITEM" target="empty_milk_carton" amount="-5"/>
  <reward kind="SHARD" amount="1..5" when="quest.anonLook.objectives.bonus.done"/>
  <reward kind="SHARD" amount="2" on="failed"/>
  <objective id="collect" done="count(ownsItem(empty_milk_carton)) >= 5">
    <reward kind="SHARD" amount="1"/>
  </objective>
</quest>
```

An **element, not a directive**: `::`-forms are commands in flow; elements
are declarations, and `<reward/>` sits beside `<objective/>`. Always
self-closing; a `<reward>` with a body, or one appearing anywhere other than
as a direct child of `<quest>` / `<objective>`, is rejected (the parser's
closed tag dispatch — same treatment any misplaced construct gets). The
one-physical-line tag rule (§2.3) applies.

Attributes (closed set — anything else is `E-UNKNOWN-ATTR` via the per-tag
table, 0.10.0 D-J):

| Attr | Type | Meaning |
| --- | --- | --- |
| `kind` | required, non-empty string | the reward vocabulary key (engine/plugin-owned) |
| `target` | optional string | the rewarded id (item, currency, quest, …) |
| `amount` | optional | integer scalar (negative legal — deductions are real) **or** range literal `N..M` with integer bounds and `N <= M`; default `1` |
| `when` | optional `CelString` | grant condition, evaluated at the grant instant; ordinary CEL slot |
| `on` | quest-level only | `complete` (default) or `failed` — which terminal transition grants it |

Shape violations — empty `kind`, malformed `amount` (non-integer, bad range,
`N > M`), `on=` on an objective-level reward, an `on` value outside the
closed enum — are **`E-REWARD-ATTR`**, anchored at the offending attribute.

`amount="N..M"` is a **declaration of a range, not a roll**: the journal
shows "1–5", the balancer computes expectation, and the roll itself belongs
to the engine (the 0.0.1 dice contract). There is deliberately no drop-chance
slot: display/expected-value contracts for probabilistic grants vary per
game; a game declares one as a plugin attribute on its own vocabulary and
its engine interprets it — the language never reads it.

## 3. Semantics — pure data, the engine grants

Rewards lower to arrays on the owning records and are **never synthesized
into handlers, commands, or predicates** — the exact inverse of 0.14.0's
subquest synthesis, deliberately: `::grant` is plugin vocabulary, and the
core language must not depend on any plugin's directive existing.

Engine rules (normative additions to `docs/runtime/quest-lifecycle.md`):

- **When.** At the `→ complete` transition, grant the quest's `on="complete"`
  rewards; at `→ failed` (including a parent-cascade failure, 0.14.0), its
  `on="failed"` rewards. When an objective first becomes `done`, grant that
  objective's rewards. Each reward is granted **at most once per quest
  instance** (the same monotonicity as objective bodies).
- **`when`.** Evaluated at the grant instant against the same state/fact
  snapshot the transition itself observed; a non-`true` verdict skips the
  reward (once — it is not re-armed).
- **Order.** Within one owner, declaration order. When one step settles
  both an objective and its quest, objective grants precede quest grants;
  all grants precede the corresponding lifecycle handler body, so handler
  narrative can react to what was just granted.
- **Ranges.** The engine resolves `N..M` however it likes (that is the
  simulation's half); the **reference runtime never rolls** — `lute run` /
  `play` / `trace` emit a structured grant event carrying the declared
  shape verbatim (scalar, or the range bounds), keeping reference output
  byte-deterministic. `lute test` can assert grants through the transcript
  today; a first-class expectation key is out of scope (§8).

The `<on questComplete>` + `::grant` idiom remains fully supported for
narrative staging and engine-specific effects; declarative rewards and
handlers coexist. (Double-grant detection across the two is a non-goal —
plugin semantics are opaque to the checker.)

## 4. `rewardKinds:` — optional plugin vocabulary

The language owns the shape; kinds are engine vocabulary. A plugin manifest
MAY export `rewardKinds:` — a map of kind id → declaration: an optional
`target` contract naming a provider domain (the `providerRef` pattern:
resolved against pinned snapshots, Fresh / *catalog-stale* / unknown-id
exactly like directive attrs), and optional extra attr schema for
game-specific slots (`chance=`, `min`/`max` variants, …).

When the resolved capability set declares any reward kinds:

- a `<reward kind>` outside the declared set is **`E-REWARD-KIND`**;
- a `target` present/absent against the kind's contract, or failing its
  provider domain, is **`E-REWARD-KIND`** (stale snapshots degrade to the
  usual *catalog-stale* grade, never a hard error).

No declaration ⇒ shape checks only. `rewardKinds` folds into the capability
snapshot as a guarded, sorted section: a populated vocabulary moves
`capabilityVersion` (it changes what the checker accepts), while the empty
core section hashes byte-identically — no restamp for existing projects.

## 5. IR delta

| Field | Change |
| --- | --- |
| `QuestCmd.rewards` | NEW, `[RewardEntry]`, omitted when empty |
| `ObjectiveEntry.rewards` | NEW, `[RewardEntry]`, omitted when empty |
| `RewardEntry` | NEW: `kind: string`; `target?: string`; exactly one of `amount: int` / `amountMin: int` + `amountMax: int`; `when?: CelPair`; `on?: "failed"` (omitted = complete; never emitted on objective entries) |

`LUTE_LANG_VERSION` / `LUTE_IR_VERSION` → `0.16.0`; schema renames to
`lute-ir-0.16.schema.json` per the release-line rule, gaining `rewardEntry`
and both arrays. Engines gate by IR **MAJOR** (0.13.0) — additive, no cost
to a consumer that ignores the arrays.

## 6. Diagnostics

| Code | Grade | Status |
| --- | --- | --- |
| `E-REWARD-ATTR` | error | new — shape violation (§2) |
| `E-REWARD-KIND` | error | new — vocabulary violation when a plugin declares `rewardKinds:` (§4) |
| `E-UNKNOWN-ATTR` | error | reused — `<reward>` joins the per-tag closure table |
| existing CEL set | — | `reward.when` joins the CEL-slot registry: `E-CEL-PROFILE`, `E-MAYBE-UNSET`, unset-sentinel comparison guards, LSP hover/fill |

## 7. Compatibility

- Every 0.15.x document is a valid 0.16.0 document unchanged; `<reward>` was
  previously a parse error, so no meaning shifted.
- A document declaring no rewards compiles byte-identically plus the version
  strings. Conformance quest fixtures gain reward coverage; the scene
  fixtures are untouched.
- `capabilityVersion` unchanged for every project without a
  `rewardKinds:`-declaring plugin (guarded hash section, §4). The
  tree-sitter grammar gains the `reward` production (tags are enumerated) —
  a grammar regeneration, not a capability restamp (the stamp tracks the
  core snapshot).
- 0.2.0 §6.5's "rewards are `::set`/plugin `::grant`" stance is superseded
  by this section for the *data* half; the operational half it describes
  remains true and supported.

## 8. Decisions

| # | Decision | Rationale |
| --- | --- | --- |
| **D-A** | `<reward>` is an owner FIELD (`Quest.rewards` / `Objective.rewards`), not a body `Node` | it is a declaration, not flow; keeping it out of `Node` spares every exhaustive body-walk in check/compile/trace/LSP/lint from a variant that could never legally reach them |
| **D-B** | pure data; the engine grants; no handler synthesis | synthesizing `::grant` would make core language output depend on a plugin's directive existing — the dependency inversion 0.2.0 §6.5 drew the boundary against |
| **D-C** | `amount` admits `N..M`; the reference runtime never rolls | the range is journal/balancing data (oshiz `{min,max}` rows are real); rolling in the reference runtime would break byte-determinism, and dice belong to the engine (0.0.1) |
| **D-D** | grants precede lifecycle handler bodies; objective grants precede quest grants | handler narrative reacting to a grant is the common case; the reverse order would make "you received X" a lie at the instant it plays |
| **D-E** | `rewardKinds` is a guarded capability-snapshot section | vocabulary that changes what the checker accepts must move `capabilityVersion` when present (plugin contract), while its absence must not restamp every existing project |
| **D-F** | no first-class `lute test` reward expectation in this release | grants are assertable via the transcript today (`transcriptContains`); a closed expect-key extension is its own surface and waits for demand |
| **D-G** | no drop-chance slot | probabilistic-grant display contracts are game-specific; a plugin attr on the game's vocabulary covers it without the language reading probabilities |
