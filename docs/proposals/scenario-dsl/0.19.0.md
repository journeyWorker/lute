# Lute Scenario DSL — 0.19.0: Lore entries (queried content)

- **Version:** 0.19.0
- **Status:** Draft
- **Date:** 2026-09-24
- **Scope:** a third document kind, `kind: lore`, whose top level is a set of
  `<entry>` declarations — content the engine **looks up** (an item
  description, a found note, a place inscription, a codex page, an ambient
  bark) instead of content it **plays** in sequence. Entry bodies select text
  by state with the ordinary `<match>`, and reveal knowledge with the ordinary
  `::assert`. One reserved state path per entry (`entry.<id>.read`), three new
  errors, one new warning, a new artifact kind and command record, and two
  CLI surfaces (`lute trace --entry`, `lute lore`).
- **IR:** additive. New artifact `kind: "lore"` with `LoreMeta`; new command
  record `entry`; `ProjectIndex.entries`. Scene and quest artifacts are
  byte-identical apart from the version strings.

## 1. Motivation

Lute's narrative is a **time axis**: scenes and quests say what happens, in
what order, under which conditions. Much of a game's story is not on that
axis. It sits in **space and objects**: the torn page in the lab, the
inscription on a door, the description of a rusty key that changes after the
fire, the line an NPC mutters when you walk past. The player finds these in
any order, re-reads them, and assembles the story themselves — the
environmental storytelling of *Dark Souls* item descriptions or a codex of
scientist's logs.

Today an author can only fake this with a scene per note, which is wrong in
every dimension: a scene is scheduled (`after:`), sequential, and played once
through; a note is looked up, unordered, and read again. The engine has no
declaration telling it "this text belongs to this item, shows this variant
after the fire, and teaches the player this fact".

0.19.0 adds that declaration. Lute keeps its contract (0.0.1): Lute declares
**what** the text is, **when** it is eligible, and **what reading it
changes**; the engine decides **where** it lives — which item spawns where,
which panel shows the codex, when an NPC barks.

## 2. The lore document

```lute
---
kind: lore
uses: ../world.schema.yaml
title: Ship's records
---

<entry id="scientistLog1" target="item.torn_note_1" category="note" series="scientistLog" order="1" title="Research log, day 3">
  @scientist: Day three. Subject E does not respond to light.
  ::assert{knows(vesna, project_lumen)}
</entry>

<entry id="rustyKey" target="item.rusty_key" category="item">
  <match on="run.labBurned">
    <when is="true">
      @narrator: A scorched key. Someone's name has melted into the grip.
    </when>
    <otherwise>
      @narrator: A rusty key, stamped "Research wing B2".
    </otherwise>
  </match>
</entry>
```

- `kind: lore` accepts the same frontmatter keys as a quest document.
- The body is **one or more** top-level `<entry>` declarations. A `# ` title
  heading, a `## ` shot, a `<quest>`, or content outside an entry is
  `E-GRAMMAR-NOT-ADMITTED`; a lore document with no entry is malformed,
  exactly as a quest document with no `<quest>`.
- The one-physical-line tag rule applies to the `<entry …>` open tag.

### 2.1 The document is the bundle

An author writes a captain's log — pages one through seven — in one sitting,
in one file, and comes back to that file to fix page four or to tell an AI
collaborator "rewrite the last two pages". A quest chain is written the same
way: the chain's quests together, top to bottom. The file is the unit the
author thinks in, so the language names it.

- **`id:`** — a quest or lore document MAY declare a document id, with the
  same shape rules as a scene's `id:` (`E-META-ID`, dsl 0.15.0 §2). It names
  the bundle (`haven.captainsLog`, `haven.mainChain`), becomes the artifact's
  `meta.id`, and is the document's `ProjectIndex` key; without it the key
  stays the first declared quest or entry id. Document ids share one
  project-wide namespace with scene ids (`E-CONN-EPISODE-ID-DUP`, its message
  generalized to "document id"). Optional, so every 0.18 quest document stays
  valid.
- **`series:`** — a lore document MAY declare that all of its entries form
  one series, ordered by **position in the file** (1-based). Reordering the
  pages is moving the entries; inserting a page renumbers the ones after it.
  In such a document an entry carrying its own `series=` or `order=` is
  `E-ENTRY-ATTR`. A series that spans several files still uses the per-entry
  attributes (§3).

```lute
---
kind: lore
id: haven.captainsLog
title: Captain's log
series: captainsLog
uses: ../world.schema.yaml
---

<entry id="captainsLog1" target="item.captains_log" category="note" title="Day 1">
  @captain: We cleared the dock at the third bell.
</entry>

<entry id="captainsLog2" target="item.captains_log" category="note" title="Day 2" when="entry.captainsLog1.read">
  @captain: The manifest is wrong. I have told no one.
</entry>
```

Here `captainsLog1` is `order` 1 and `captainsLog2` is `order` 2 of series
`captainsLog`. The compiled `entry` records and `ProjectIndex.entries` carry
the resolved `series` / `order`, so an engine reads every entry the same way
whichever form the author used.

## 3. `<entry>` attributes

| Attr | Type | Meaning |
| --- | --- | --- |
| `id` | required ident | the entry's identity; unique across the project |
| `target` | optional dotted id | the engine-owned thing the entry is attached to (`item.rusty_key`, `place.lab_b2`, `npc.vesna`) |
| `category` | optional ident | what kind of text it is (`note`, `item`, `place`, `codex`, `bark`, …) — engine vocabulary |
| `title` | optional string | display title; localized like a quest title |
| `series` | optional ident | groups multi-part text (`scientistLog`) |
| `order` | optional non-negative integer | position within `series`; requires `series` |
| `when` | optional `CelString` | eligibility — the entry may be presented only while this holds |

- `id` follows quest-id rules (`Ident`). `target` matches
  `Ident ("." Segment)*` where `Segment ::= [A-Za-z0-9_-]+`. Neither `target`
  nor `category` is checked against a vocabulary in this release: they are
  **shape-only**, the way core `assetId`s are (§8 D-E, D-F).
- Several entries MAY share a `target` (an NPC's barks, an item's variants
  that the author prefers to split rather than `<match>`).
- Shape violations — missing or non-ident `id`, malformed `target`, non-ident
  `category`/`series`, `order` that is not a non-negative integer, `order`
  without `series` — are **`E-ENTRY-ATTR`**, anchored at the attribute.
  Unknown attribute keys are `E-UNKNOWN-ATTR` via the per-tag closure.
- Two entries with the same `id` in one project are **`E-ENTRY-ID-DUP`**
  (per document in `lute check`, project-wide in `check-project`). Two
  entries with the same `(series, order)` are **`E-ENTRY-SERIES-ORDER`**.

## 4. Entry bodies

An entry body admits **content lines, `<match>` (recursively, with the same
admission), `::set`, `::assert`, and `::retract`** — nothing else. `<branch>`,
`<hub>`, `<timeline>`, `<on>`, `<objective>`, and every `::` directive
(staging, plugin, `::use`, `::end`) are `E-GRAMMAR-NOT-ADMITTED`: an entry is
read, not played, so it has no player choice, no staging, and no handlers.

Lines inside entries are ordinary content lines: any speaker (`@narrator`, an
in-world author such as `@scientist`), interpolation, `when=` line guards,
and lineId / voiceKey / code identity. Each entry is its own identity scope —
prefix `{entryId}`, a fresh per-speaker code counter — as each quest is.

**Revealing knowledge is `::assert`.** There is no separate reveal verb:
reading the torn note asserts `knows(vesna, project_lumen)` with the relation
the project already declares, checked by the same arity/domain/tier rules
(0.3.0 §5). Scenes and quests then react through the ordinary
`holds(knows(…))` guard.

## 5. `entry.<id>.read`

Every entry has a reserved, engine-written state path
**`entry.<id>.read: bool`** (default `false`), readable from any CEL slot in
any document kind — a scene line guard, a quest objective, another entry's
`when` (series gating: `when="entry.scientistLog1.read"`), or the entry's own
`<match>`.

- Writing an `entry.*` path is rejected, as writing a `quest.*` path is.
- Like `quest.<id>.state`, the path is admitted even when the entry lives in
  another document; `check-project` warns **`W-ENTRY-REF-UNKNOWN`** when no
  document in the project declares that entry id.
- Lifetime: the path resets with the **run** tier.

## 6. Runtime semantics (engine contract)

Normative text lives in [`docs/runtime/lore-entries.md`](../../runtime/lore-entries.md).

- **Eligibility.** An entry is eligible while `when` is absent or true. The
  engine decides when and where an eligible entry is presented, keyed by
  `target` and `category`. When several eligible entries share a `target`
  and `category`, choosing among them is engine policy; `ProjectIndex.entries`
  order (document order within the project) is the tiebreak Lute provides.
- **Presentation.** Presenting an entry runs its body in document order
  against live state: lines present, `<match>` selects an arm.
- **First-read effects.** `::set`, `::assert`, and `::retract` records apply
  only while `entry.<id>.read` is `false` — that is, on the entry's first
  presentation in a run. After that presentation completes, the engine sets
  `entry.<id>.read` to `true`. Re-reading a note shows its (possibly
  changed) text and changes nothing else.

## 7. IR delta

| Field / record | Change |
| --- | --- |
| `Artifact.kind` | NEW value `"lore"` |
| `Artifact.meta` | NEW `LoreMeta` for lore artifacts: `id?`, `title?`, `series?`, `contentLang?`, `extra?`, `plugin?` |
| `QuestMeta.id` | NEW, optional — the quest document's authored `id:` (§2.1); omitted when not authored, so existing quest artifacts are byte-identical |
| `Command` | NEW record `kind: "entry"`: `addr`, `id`, `target?`, `category?`, `title?`, `titleLineId?`, `series?`, `order?`, `when?: CelPair`, `body: string` (address of the entry's body segment, the `OnCmd.body` convention); `series` / `order` are the RESOLVED values, including those a document-level `series:` supplies |
| `ProjectIndex.entries` | NEW, omitted when empty: one row per entry — `id`, `document`, `target?`, `category?`, `series?`, `order?` (resolved) — in document order |
| `IndexDocument.key` | a quest or lore document with an authored `id:` is keyed by it |

Each `entry` record is followed by its body segment's records, addressed and
terminated exactly as an `<on>` body is. `LUTE_LANG_VERSION` /
`LUTE_IR_VERSION` → `0.19.0`; the schema renames to
`lute-ir-0.19.schema.json` and gains `loreMeta`, `entryCmd`, and the index
rows. Engines gate by IR MAJOR (0.13.0): scene/quest consumers are
unaffected; an engine that does not support lore rejects `kind: "lore"` the
way it rejects any unknown artifact kind.

## 8. Tooling

- **`lute trace <doc> --entry <id> [--mock <m.yaml>]`** presents one entry
  against mocked state and prints the transcript — lines, the arm taken, and
  the effects a first read applies (or skips, when the mock seeds
  `entry.<id>.read: true`). `lute run <artifact> --entry <id>` does the same
  over a compiled artifact. Running a lore artifact without `--entry` is a
  usage error: there is no sequence to play.
- **`lute lore <dir> [--json]`** reports the project's world-narrative map:
  entries grouped by `target` and by `series` (in `order`), and for every
  relation asserted anywhere, which ground facts are revealed by entries,
  which only by scenes/quests, and which by both.
- `lute new lore <name>` scaffolds a lore document. `lute tag`, `lute loc`,
  `lute compile --all`, the LSP (symbols, folding, highlighting, attribute
  completion and hover), and tree-sitter all treat `<entry>` as they treat
  `<quest>`. `lute lint` excludes lore documents from scene metrics and
  counts their lines as translatable content.

## 9. Diagnostics

| Code | Grade | Status |
| --- | --- | --- |
| `E-ENTRY-ATTR` | error | new — `<entry>` attribute shape (§3) |
| `E-ENTRY-ID-DUP` | error | new — duplicate entry id in a document or project (§3) |
| `E-ENTRY-SERIES-ORDER` | error | new — duplicate resolved `(series, order)` (§2.1, §3) |
| `E-META-ID` | error | extended — applies to a quest or lore document's `id:` (§2.1) |
| `E-CONN-EPISODE-ID-DUP` | error | extended — quest and lore document ids join the scene-id namespace; message says "document id" (§2.1) |
| `W-ENTRY-REF-UNKNOWN` | warning | new — `entry.<id>.read` names an id no document declares (`check-project`, §5) |
| `E-GRAMMAR-NOT-ADMITTED` | error | extended — the lore top level and entry bodies (§2, §4) |
| `E-UNKNOWN-KIND` | error | extended — `lore` joins `scene` / `quest` |
| existing CEL / fact / line set | — | entry `when` joins the CEL-slot registry; `::assert` / `::retract` / `::set` and content lines are checked exactly as in scenes |

## 10. Compatibility

- Every 0.18.x document is a valid 0.19.0 document; `kind: lore` was
  previously `E-UNKNOWN-KIND`, `entry.*` paths were undeclared, and `id:` in
  a quest document was `E-META-UNKNOWN-KEY`.
- Scene and quest artifacts are byte-identical apart from the version
  strings. `capabilityVersion` is unchanged: no core vocabulary is added.
- The tree-sitter grammar gains a top-level `entry` production (a
  regeneration, not a capability restamp).

## 11. Decisions

| # | Decision | Rationale |
| --- | --- | --- |
| **D-A** | a new document kind, not a scene feature | looked-up content has no sequence, no schedule, and different identity and runtime rules; mixing it into scenes would make every scene walker special-case unordered blocks |
| **D-B** | reveal is plain `::assert` | the relation layer already models knowledge (0.3.0 §9 epistemic pattern); a separate verb would duplicate arity/domain/tier checking and the runtime contract |
| **D-C** | effects apply on the first read only; text re-presents | matches how found text behaves in games (reading a note twice does not teach twice), keeps `::set x += 1` meaningful, and needs no per-command flag — the engine skips effect records by kind once `read` is set |
| **D-D** | `entry.<id>.read` is a reserved state path, not a relation | it is scalar, per-entry, engine-written, and needed in `<match on>` subjects (relations are guard-only, `E-MATCH-RELATION-SUBJECT`); it mirrors `quest.<id>.state` |
| **D-E** | `target` is shape-only; the attribute is `target`, not `anchor` | an author writes lore before the engine's item catalog exists, and `providerRef` fails closed without one (the `asset-exists` precedent); `anchor` is already a core enum-domain slot name, while `target` matches `<reward target>` |
| **D-F** | `category` is shape-only, no plugin vocabulary yet | the useful categories differ per engine; a guarded `entryCategories:` export (the `rewardKinds` pattern) can follow when a project needs it |
| **D-G** | no directives in entry bodies | staging belongs to the presenting surface (inspect panel, codex, bark bubble), which is the engine's; allowing `::bg` in a note would promise a presentation Lute cannot define |
| **D-H** | choosing among eligible entries is engine policy | salience rules (most specific match, cooldowns, randomness) are game design, not language; Lute supplies eligibility and a stable declaration order |
| **D-I** | knowledge-presumption analysis is deferred to 0.20.0 | warning when a line presumes a fact the player may not know needs a path-sensitive fact envelope (the scalar `envelope.rs` has no fact analogue yet); 0.19.0 ships the data it will read |
| **D-J** | quest and lore documents MAY declare `id:`; it is optional | the file is the unit an author (and an AI collaborator taking instructions) works in — a log collection, a quest chain — so it deserves a name; requiring it would break every 0.18 quest document for a key no language rule reads |
| **D-K** | a document-level `series:` orders entries by file position | authors write a series top to bottom and reorder by moving pages; hand-numbered `order=` on every page is bookkeeping that drifts. Per-entry attributes stay for series spanning files, and mixing the two in one document is an error rather than a precedence rule |
