# Lute Scenario DSL — 0.11.0: No Language Change

- **Version:** 0.11.0
- **Status:** Draft (**alignment-only** revision of 0.10.2)
- **Date:** 2026-08-15
- **Scope:** no grammar production, no static-semantic rule, no IR shape, no
  `decide()` (§5.1 R1–R5) change, no Closure change. Language 0.11.0 is
  **byte-for-byte 0.10.2 (== 0.10.1 == 0.10.0) semantics** for every document.
  The single change on this axis is the version stamp: `LUTE_LANG_VERSION`
  advances from `"0.10.2"` to `"0.11.0"` in the release that aligns the
  toolchain and the IR at the same number. **Unlike `0.10.2`, the IR axis is
  ALSO a no-op this time** — see §2.

## 1. Why this file exists

Same reason as [`0.10.1.md`](0.10.1.md) and [`0.10.2.md`](0.10.2.md), which
set the precedent this file repeats: [`docs/versioning.md`](../../versioning.md)
commits to re-aligning every visible axis number on every release, and
separately commits the language axis's history to this stack. A language
version with no entry here is a hole a reader resolving
`luteVersion: "0.11.0"` cannot see into — nothing distinguishes "this revision
changed nothing" from "the revision was never written down." `0.7.0`,
`0.10.1`, and `0.10.2` each closed that hole for their own release; this is
the fourth.

## 2. What changes on the language axis — nothing; what changes on the IR
   axis — also nothing, but the number still moves

`LUTE_LANG_VERSION` → `"0.11.0"`. Nothing else on this axis. Every diagnostic
code, grammar production, admission rule, vocabulary slot, and `decide()`
result is exactly as `0.10.2` (== `0.10.1` == `0.10.0`) defined it. Historical
citations of the form "dsl 0.10.0 §N" / "dsl 0.10.1 §N" / "dsl 0.10.2 §N"
continue to name the proposal that defined the rule and are **not** rewritten.

**The IR axis is a no-op too — unlike `0.10.2`'s story, not a repeat of it.**
`0.10.1`'s IR advance was shape-identical to `0.10.0`; `0.10.2`'s gained real
content (`meta.plugin`) while staying shape-identical in envelope terms.
`0.11.0` gains **nothing at all**: no field, no shape change, no content
change of any kind. The compiled artifact `0.11.0` produces is byte-identical
in structure to the one `0.10.2` produces.

**And yet the schema file is renamed, which `0.10.1`'s and `0.10.2`'s were
not.** This is the one place `0.11.0`'s story genuinely diverges from both.
`0.10.1` and `0.10.2` each shared `major.minor` `0.10` with the release before
them, so [`docs/versioning.md`](../../versioning.md)'s rule — the schema file
tracks the gated `major.minor`, not the release number — kept
`schemas/lute-ir-0.10.schema.json` exactly as it was through both. `0.11.0`'s
`major.minor` is `0.11`, a real move away from `0.10`, so the same rule now
points the other way: `schemas/lute-ir-0.10.schema.json` is renamed to
[`schemas/lute-ir-0.11.schema.json`](../../../schemas/lute-ir-0.11.schema.json)
(`$id` updated to match; body otherwise byte-identical), exactly the
precedent `0.7.0` set the first time a `major.minor` moved with no shape
change. The runtime contract
([`docs/runtime/execution-model.md`](../../runtime/execution-model.md#version-negotiation))
still gates on `irVersion` **major.minor**, and this is the first release
since `0.10.0` where that component moves — so an engine implementing IR
`0.10` **must widen its gate to `0.11`** before it accepts a `0.11.0`
artifact, even though there is nothing new in that artifact to read once it
does. The widening is the entire migration; nothing is renamed, added, or
removed inside the artifact itself.

## 3. What the release does change

Everything real this release ships is **toolchain**, per
[`docs/versioning.md`](../../versioning.md)'s "which bump when" ("Fix a
checker/compiler/LSP bug, add a CLI flag … → toolchain only"):

- A new `schedule.yaml` project-file layer — a tick clock, `user`/`world`
  lanes, guarded placements with route-space static checks — deliberately
  kept OUTSIDE this stack: no `kind:`, no `luteVersion:` frontmatter, no
  project `uses:` resolution, no capability fold. See
  [`docs/superpowers/specs/2026-08-14-lute-schedule-and-play-design.md`](../../superpowers/specs/2026-08-14-lute-schedule-and-play-design.md)
  §2 for why that is a deliberate scope decision rather than an oversight, and
  [`docs/schedule-and-play.md`](../../schedule-and-play.md) for the authoring
  reference.
- A new `lute play` command that chains a schedule's placements into one
  reviewer-facing transcript across a whole project, plus `lute play
  --coverage` for corpus review-gap reporting.
- Two fixes in the shared reference runner (`crates/lute-cli/src/runner.rs`,
  used by both `lute run` and `lute play`): a compiled `<when is=…>` match arm
  now reads its structured `expr` instead of always falling through to
  `<otherwise>`, and a hub whose scripted decisions run out with an eligible
  option still remaining now halts incomplete instead of silently converging.

None of the three touches this stack. See [`CHANGELOG.md`](../../../CHANGELOG.md)
for the full entries.

## 4. Stale-stamp remedy

Because the language version advances, a document carrying
`luteVersion: "0.10.2"` (or `"0.10.1"`/`"0.10.0"`) now lags `LUTE_LANG_VERSION`
and fires **`W-LUTE-VERSION-STALE`** (dsl 0.6.1 §3) — the stamp is still never
validated against capabilities (D13 stands; the warning is a freshness signal
only). The remedy is mechanical — restamp to `luteVersion: "0.11.0"` — and
because `0.11.0` is byte-for-byte `0.10.2`/`0.10.1`/`0.10.0` semantics, an
already-clean document restamped to `0.11.0` checks clean with no other edit.

## 5. Non-goals

- No grammar, semantic, or IR shape/content change, on any axis this stack
  tracks.
- No new diagnostic code on the language axis and none removed. The release
  does add a whole family of **schedule-file** codes (`E-SCHED-*`/
  `W-SCHED-*`); every one of them fires on `schedule.yaml`, never on a
  `.lute` document, and `schedule.yaml` is deliberately not a doc kind this
  stack governs (§3) — which is why they are a toolchain entry and not a
  language one, exactly as `0.10.1`'s `E-PLUGIN-ASSET-SEGMENT-TYPE` was.
- No change to the axis-independence policy. The axes MAY drift when an axis
  genuinely does not change; this release re-aligns the visible numbers so a
  single release presents a single number, and this file is where a reader
  learns that neither the language nor the IR axis earned its move — only the
  IR's *number* moved, and only because alignment moves every number on every
  release.
