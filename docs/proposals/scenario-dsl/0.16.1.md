# Lute Scenario DSL — prospective 0.16.1 checked continuation tooling

- **Candidate version:** 0.16.1
- **Status:** Draft tooling proposal; not a released-version claim
- **Date:** 2026-09-14
- **Scope:** no grammar, static-semantic, capability, or IR-schema change. The
  proposed toolchain adds a checked continuation compiler and `compile-stream`
  CLI over the existing language and ordinary artifact.

The key words **MUST**, **MUST NOT**, **SHOULD**, and **MAY** are interpreted as
in RFC 2119.

The implementation contract that governs this proposal is
[Streaming continuation compiler](../../superpowers/specs/2026-09-14-streaming-continuation-compiler-design.md).
The operational guide is
[Checked streaming continuations](../../runtime/incremental-continuations.md).

## 1. Outcome and boundary

A host begins with a complete, checked **scene template**: frontmatter, resolved
project inputs, existing authored content, and at least one shot. It then appends
ordinary Lute **shot-body source** to that template's final shot. Each complete
line, directive, or closed outer block is checked and compiled through the
existing whole-document pipeline. Accepted units yield full, ordinary `Artifact`
snapshots before transport EOF.

This adds no streaming-only source language. In particular:

- dialogue remains `@speaker{attributes}: text`, for example
  `@guide: The door is open.`;
- directives, `<branch>`, `<match>`, `<hub>`, `<timeline>`, component use, and
  plugin directives retain their existing grammar and checks;
- body input MUST NOT replace frontmatter or introduce a shot heading, label, or
  quest root; and
- emitted data is ordinary Lute IR, not a JSON AST patch or a new runtime
  instruction set.

The template and its project/capability inputs are host-owned and resolved once.
When the host supplies `--permission-profile NAME` (or restricts the Rust
snapshot directly), the same frozen capability-permission ceiling applies to
the template and every appended unit; see the prospective plugin-system
[`0.0.6`](../plugin-system/0.0.6.md) delta. There is no mid-stream switch.

The compiler validates appended text; it does not make generated text trusted,
execute it, or grant runtime authority. This service is not an LLM client, game
engine, or secure runtime capability sandbox. Host effects, secrets,
persistence, resource authorization, and idempotency remain outside Lute.

## 2. Public Rust API

The public module is `lute_compile::streaming`:

```rust
pub struct ContinuationCompiler { /* private state */ }

impl ContinuationCompiler {
    pub fn new(
        input: CheckInput,
        identity: IdentityTemplates,
    ) -> Result<Self, Vec<Diagnostic>>;

    pub fn artifact(&self) -> &Artifact;
    pub fn push(&mut self, chunk: &str) -> ContinuationCompilation;
    pub fn finish(&mut self) -> ContinuationCompilation;
}

pub struct CompilationUpdate {
    pub sequence: u64,
    pub append_from: usize,
    pub artifact: Artifact,
}

pub struct ContinuationCompilation {
    pub updates: Vec<CompilationUpdate>,
    pub need_more: Option<NeedMoreInput>,
    pub diagnostics: Vec<Diagnostic>,
    pub finished: bool,
}
```

`CheckInput` is already resolved: source URI, capability snapshot, provider
snapshots, imported schemas/components, defaults, and analysis mode are the same
inputs ordinary checking consumes. `IdentityTemplates` is frozen at construction.
The continuation compiler MUST NOT re-resolve mutable project files between
units.

### 2.1 Construction and initial artifact

`ContinuationCompiler::new` MUST check and compile `input` immediately. It MUST
reject a non-scene document, a scene with no shot, or any existing syntax,
semantic, resolution, or compilation error. On success, `artifact()` exposes the
initial ordinary artifact and later appends target only the last existing shot.
The prefix source is immutable for the compiler's lifetime.

Template-service failures use `E-STREAM-TEMPLATE`; ordinary gate diagnostics
remain present and unsuppressed.

### 2.2 `push`

`push(&str)` appends valid UTF-8 text to the current body stream. Transport chunk
boundaries have no syntactic meaning. A chunk MAY end inside a physical line,
quoted attribute, block comment, Unicode scalar sequence already decoded by the
caller, or nested element. `push` MUST process every newly complete top-level
unit in source order and return an update for each accepted unit.

A leaf requires a physical newline. An outer block requires its matching close
and that close's physical-line boundary. `need_more` describes the retained
suffix as `Line`, `QuotedAttribute`, `BlockComment`, or
`NestedBlock { open_tags }`; this is framing state, not an error.

For each complete unit the implementation MUST compile the accumulated template
plus every accepted unit through the existing checker, normalization, component
expansion, lowering, stage-injection, addressing, and artifact assembly. It MUST
NOT implement a second checker or lowering path.

### 2.3 `finish`

`finish` declares transport EOF. EOF MAY replace the final newline for a complete
leaf. It MUST NOT invent `</tag>`, `*/`, a forward target, or any other recovery.
Unclosed syntax is rejected. After successful finalization `finished` is true
and no more source may be appended. A finalization failure is also terminal.
Any later `push` or `finish` returns `E-STREAM-CLOSED` and no update.

EOF and authored `::end` are different. EOF closes the compiler input and, only
on success, permits a `finish` event. `::end{reason="..."}` is an ordinary Lute
command that can terminate runtime execution before EOF; it does not close stdin
or prevent the compiler from validating later source.

## 3. Updates, failure, and diagnostics

`sequence` starts at `1` for the first accepted appended unit and increases once
per update. `append_from` is the previous snapshot's `commands.len()`. It is a
snapshot-diff hint, not a runtime program counter.

A failing unit and all subsequent units in the same call MUST produce no IR.
Updates for earlier accepted units in that call remain valid and MUST still be
returned. Diagnostics for appended source refer to cumulative source coordinates:
the immutable template, accepted units, then the failing unit. Implementations
MUST NOT shift spans by wrapping fragments in a synthetic shot or document.

The service-specific diagnostics are:

| Code | Meaning |
| --- | --- |
| `E-STREAM-TEMPLATE` | Construction input cannot establish a valid scene prefix and initial artifact. |
| `E-STREAM-BODY` | Appended input is outside the admitted final-shot body surface. |
| `E-STREAM-PREFIX-CHANGED` | Recompilation changed an already emitted command or state entry. |
| `E-STREAM-CLOSED` | A caller used the compiler after success or failure made it terminal. |

Existing parser, checker, resolver, and compiler diagnostics MUST remain unchanged
and unsuppressed. A unit requiring a forward target not yet present fails now;
the service MUST NOT guess future source.

## 4. Irreversible-prefix compatibility

Every update is a full `Artifact`, but output already observed by a consumer is
irreversible. Before accepting a candidate artifact, the compiler MUST establish:

1. every prior command is semantically identical after canonicalizing **only**
   typed command addresses and typed control targets to unpadded numeric
   `(shot, index)` pairs; and
2. every existing state-table entry is identical.

Address width can legitimately grow as command counts cross a padding boundary,
for example `001-0900` becoming `001-00900` everywhere. Such formatting-only
widening MUST be accepted. Arbitrary payload strings, line text, ids, state
values, and plugin data MUST NOT be normalized. If a later append renumbers an
implicit line identity, changes stage injection, mutates an earlier command, or
alters an existing state default, the candidate MUST be rejected with
`E-STREAM-PREFIX-CHANGED`.

This rule is why `append_from` indexes commands rather than comparing raw address
strings, and why a consumer rebuilds address lookup from every snapshot.

## 5. Runtime consumer contract

On every update a consumer MUST:

1. replace its immutable program snapshot with `update.artifact`;
2. rebuild the artifact's `addr -> command index` lookup;
3. retain its **numeric command cursor**, state values, facts, selected
   control-flow stack, and host-owned effect/idempotency records;
4. initialize only state slots newly declared by the snapshot; and
5. resume the ordinary choice/match/hub/jump dispatcher from its retained
   execution position.

It MUST NOT reapply existing state defaults or seed facts. `append_from` identifies
the newly appended array region; it MUST NOT cause every command in that slice to
execute. Ordinary control flow selects the actual path.

At the current frontier the runtime waits for another accepted update. It MUST
NOT mark the scene complete merely because the current `commands` array ended.
Completion occurs after successful compiler `finish`, or earlier through an
ordinary authored `end` command. Host side effects remain host-owned and
idempotent across snapshot replacement.

## 6. Cost model

This proposal improves time to first checked output, not total compilation cost.
Each complete unit recompiles the cumulative source with the existing compiler.
For units of sizes $u_1, \ldots, u_n$, work is proportional to compiling prefixes
$u_1$, $u_1+u_2$, through $u_1+\cdots+u_n$. One long unfinished block emits
nothing until its close. Implementations and users MUST NOT describe this as an
asymptotically incremental compiler; large sessions SHOULD be measured before
adoption.

## 7. CLI protocol

```text
lute compile-stream <scene.lute> [--project DIR] [--providers DIR]
```

The CLI resolves the template exactly once using the ordinary project, provider,
component, defaults, and identity helpers, then reads body text from stdin. It
MUST never modify the template. stdout is newline-delimited JSON and MUST flush
after every start/update/error/finish record:

```json
{"kind":"start","sequence":0,"appendFrom":0,"artifact":{}}
{"kind":"update","sequence":1,"appendFrom":0,"artifact":{}}
{"kind":"finish","sequence":1}
```

The artifact values above are abbreviated; on the wire each is a complete
ordinary artifact. On rejection the final record is
`{"kind":"error","diagnostics":[...]}` and no success marker follows.

Exit codes are `0` only after successful EOF finalization, `1` for
syntax/semantic/service rejection, and `2` for invocation, I/O, or malformed
UTF-8. stdin bytes MUST be decoded as valid UTF-8 before calling the Rust `&str`
API. A broken stdout MUST stop input consumption. stderr is reserved for I/O and
invocation failures. The command performs no remote call, publication, runtime
bridge, or user effect.

## 8. Compatibility and non-goals

- Existing `lute_syntax::incremental::IncrementalContinuationParser` remains a
  useful lower-level framing and parser API. It returns lossless body units and
  local syntax diagnostics; it does not check or compile them.
- Existing `lute_syntax::parse`, `lute check`, and `lute compile` behavior is
  unchanged.
- No new Lute grammar, permission, runtime side effect, IR patch type, or engine
  feature is implied.
- No language or IR version advances until an explicit release is cut. If this
  candidate becomes a release, the repository's normal axis-alignment policy
  applies at that time.
