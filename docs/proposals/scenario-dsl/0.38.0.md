# Lute 0.38.0 — runtime R1

This specification is the normative 0.38.0 contract for phase R1 of ADR D13:
a Rust crate `lute-runtime` split out of `lute-trace`, whose core is a pure
resumable step function, and the first version of the runtime **event
contract** — the inputs a host or player sends and the outputs the runtime
returns. `lute play` and play-bearing `lute test` run on it. The authoring
language is unchanged.

The words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Scope and version contract

All visible version axes are `0.38.0` (`docs/versioning.md` alignment rule):
toolchain, language (`luteVersion:`), IR (`irVersion`), CLI/LSP/npm/Cargo
stamps, and the new **event** axis (§9). The schema files are
`schemas/lute-ir-0.38.schema.json`, `schemas/lute-events-0.38.schema.json` and
`schemas/lute-snapshot-0.38.schema.json`.

| Axis | Change in 0.38.0 |
|---|---|
| Language | none — no-op for authors |
| IR | additive: `project.index.json` gains the runtime unions of §4.2; artifacts unchanged |
| Event (new) | first version: inputs §5, outputs §6, snapshot §7 |
| CLI | `lute play --events` (§10.2); every other output byte-identical to 0.37.0 (§10.4) |

Out of scope (later phases, ADR D13 order): game-facing bindings (wasm,
C ABI) and `packages/runtime` (R2); `packages/player`, presenters and saves
with player settings (R3); concurrent presentations; typed IR inside the
runtime; any language-level timed-choice expiry rule.

## 2. Layers and terms

- **Runtime** — `crates/lute-runtime`. Executes the execution IR. The only
  layer that reads it (static project metadata — the index — may also be
  read by a host).
- **Host** — the program driving the runtime: a game, `lute play`, a
  verification server.
- **Bundle** — what the runtime loads (§4).
- **State** — everything the runtime carries between steps (§7).
- **Input point** — a point where the runtime stops and waits for input: an
  open choice, a pending bridge result, idle between presentations, or the
  end of the run (§6.2).
- **Presentation** — one walk of one beat, scene, entry or quest segment that
  an input started, from the input to the next input point.

## 3. The step function

```rust
pub struct Runtime { /* immutable, loaded once from a bundle */ }

impl Runtime {
    pub fn load(bundle: Bundle) -> Result<Runtime, LoadError>;
    pub fn begin(&self, seed: Seed) -> Result<(State, Output), Rejected>;
    pub fn step(&self, state: State, input: Input) -> Result<(State, Output), (State, Rejected)>;
    pub fn snapshot(&self, state: &State) -> Snapshot;      // §7
    pub fn restore(&self, snapshot: Snapshot) -> Result<State, LoadError>;
}
```

1. `step` is a pure function of `(Runtime, State, Input)`. It MUST NOT do
   I/O, read a clock, use randomness, spawn threads, or read or write any
   global. Two calls with equal arguments MUST return equal results on every
   platform.
2. `step` takes `State` by value and returns the successor. A caller that
   wants to keep the predecessor (rollback, verification) clones it first;
   `State::clone` MUST be O(size of the continuation), not O(size of world
   state): persistent maps are shared (`Arc`) and copied on first write.
   No deep clone of world state may occur per evaluation or per step
   (the 0.36.4–0.36.6 rule).
3. A rejected input (§5.3) returns `Err((state, Rejected))` with `state`
   equal to the argument: rejection changes nothing.
4. Effects are data. A plugin call that needs a bridge result returns
   `AwaitBridge` with a request id; the host performs the call and sends
   `BridgeResult`. A grant is an event; the host settles it. The runtime
   never calls out.
5. **Replay.** For a bundle `B`, a seed or snapshot `S0`, and inputs
   `i1…in`, the sequence of outputs is a function of `(B, S0, i1…in)`. The
   pair `(S0, [i1…in])` is the **input log**; replaying it MUST reproduce
   every output byte-identically after JSON serialization (§9.3).
6. The runtime runs a presentation until the next input point and returns
   every event produced on the way in one `Output` (owner answer 1). Pacing
   lines one at a time is the player's job.

## 4. Bundle

### 4.1 Contents

A bundle is exactly the output of `lute compile --all <project> -o <dir>`:
each document's execution IR (`<relative>.json`) plus `project.index.json`.
`Runtime::load` reads only these; it MUST NOT read sources, manifests,
plugins or YAML. The runtime trusts the bundle: the `compile --all` gate
(model, check, capability negotiation, index conflicts) already ran. Load
still MUST reject an `irVersion` whose major.minor is not the runtime's
(`E-RUNTIME-IR-VERSION`) and an unknown command `kind`
(`docs/runtime/execution-model.md` §Version negotiation).

`lute play` builds the same bundle in memory and loads it through the same
`Runtime::load` (no second assembly path). What the CLI reports beyond the
runtime's events — authored directive text, transcript needle vocabulary,
chapter-derived `after:` provenance, fact producers for refusal hints — is
CLI report data computed beside the runtime from the project model; it is
not part of the bundle.

### 4.2 Index additions (IR 0.38.0)

At v0.37.0 `ExecProject::assemble` (`crates/lute-trace/src/exec/session/project.rs`)
needs data the index does not carry; the CLI collects it from each
document's capability snapshot (`crates/lute-cli/src/play/project.rs:176-219`).
0.38.0 adds it to `project.index.json`, each field omitted when empty:

| Field | Shape | Source today |
|---|---|---|
| `occasions` | object: occasion name → `{select, target, judge?, payload?, outsideRun?}` (the `OccasionDecl` wire shape without `description` and `raisedWhen`; the gate stays in `gates`) | `input.snapshot.occasions`, first declaration wins |
| `worldEvents` | sorted array of event names | `input.snapshot.events` keys |
| `bridgeResults` | object: plugin tag → field → `"bool" \| "number" \| "string"` | `BridgeReads::with_result_types` |
| `cast` | object: cast id → display name | `lute_check::cast::declared_cast` |
| `stateDomains` | object: state path → `{kind, members[]}` | in-memory `member_domain` (`ExecProject.state_domains`) |

Union rules are the ones `play/project.rs` applies today (first declaration
in document path order wins). `build_index` gains a third argument carrying
the four snapshot unions (`occasions`, `worldEvents`, `bridgeResults`,
`cast`); one collector in `lute-cli`, moved out of
`assemble_project_from_model`, computes them from the source model and is
called by both `compile --all` and the in-memory bundle of `lute play`, so
the two bundles are byte-identical. `stateDomains` is computed inside
`build_index` from the typed artifacts' `member_domain`. Everything else
`ExecProject` derives (state-table union, quest documents, entries, kinds,
cadence plan, bridge read paths, derive schemas) the runtime derives at load
from artifacts and index, as `assemble` does now.

## 5. Inputs

### 5.1 Input set

The wire form is JSON with a `type` tag. Each input corresponds to one
`lute play` script step action (`crates/lute-cli/src/play/script.rs`
`StepAction`); §5.4 gives the field shapes.

| `type` | Fields | Accepted at | Effect |
|---|---|---|---|
| `raiseOccasion` | `occasion`, `target?`, `payload?`, `pick?`, `writes?` | `idle`; `ended` only for an `outsideRun` occasion | applies `writes`, binds payload, judges the seam and candidates, presents the selected beat(s), settles quests (`Session::occasion`) |
| `choose` | `request`, `option` | `awaitChoice` with that `request` | resumes the walk with the option |
| `bridgeResult` | `request`, `fields` | `awaitBridge` with that `request` | applies result-dependent effects, resumes |
| `advanceClock` | `by`, `writes?`, `pick?` | `idle` | applies `writes`, moves the clock, settles, raises the clock's `raise` occasions (`Session::advance`); `pick` is for that raise |
| `hostWrite` | `writes` | `idle` | engine-owned writes, then settle (`Session::engine`) |
| `worldEvent` | `name` | `idle` | raises a declared world event to quest handlers (`Session::event`) |
| `newRun` | `writes?` | `idle`, `ended` | resets run-tier state and quests, applies queued `nextRun` accepts and `writes`, settles (`Session::new_run`) |

`begin(seed)` is not an input: it builds the initial state from project
defaults plus the seed (the play script's top-level `state`, `facts`, and
save keys `visited`, `presented`, `quests`, `questInstances`, `entriesRead`),
runs the initial settle, and returns the first `Output`. A snapshot (§7) is
the other way to obtain a `State`. The brief's `Load` input is therefore
`restore`, outside the step function: an input log always starts from a
seed or a snapshot.

The brief's dialogue `Advance` input does not exist: the runtime does not
stop per line (§3.6). `Timeout` does not exist in R1: the IR carries a
choice's `timeout` seconds, but expiry semantics are host-owned
(dsl 0.11.1 §3); a host that times out sends `choose` with the option its
policy picks. A language-level expiry rule is a later language change.

### 5.2 Request ids

Every `awaitChoice` and `awaitBridge` carries `request`, an unsigned integer
from a counter in `State`, incremented per await and never reused within a
state lineage. It is part of the snapshot, so a restored state accepts the
same request ids.

### 5.3 Rejections

A rejected input leaves the state unchanged (§3.3). `Rejected` is
`{code, message}`; `message` is the human text `lute play` prints today for
the same refusal. Codes:

| Code | When |
|---|---|
| `E-RUNTIME-BUSY` | any input other than the one the current await accepts (owner answer 4: no interleaved presentations) |
| `E-RUNTIME-REQUEST` | `choose` / `bridgeResult` whose `request` is not the pending one |
| `E-RUNTIME-OPTION` | `choose` naming an option the menu does not have, or whose verdict is not `open` (play's `forced` refusal of `Spent` / `Closed`) |
| `E-RUNTIME-BRIDGE-SHAPE` | `bridgeResult` missing a field content reads, or a value of the wrong type |
| `E-RUNTIME-INPUT` | a malformed input or seed: unknown path, relation, quest, occasion, event or beat; a value that does not resolve to the declared type (§5.4) |
| `E-OCCASION-GATE` (a false `raisedWhen`, or `terminal:` holds), existing pick / write / clock refusals | as `lute play` refuses them today |
| `E-RUNTIME-HALTED` | any input after a `halted` output (§6.3) |

The new `E-RUNTIME-*` codes join the code registry
(`crates/lute-cli/src/codes/registry.rs`) with this section as their spec.

### 5.4 Wire shapes

Values are JSON scalars (`bool`, number, string). A value is resolved
against the declared type of where it lands exactly as `lute play` resolves
the same literal today (`exec/session/resolve.rs`); a value that does not
resolve is rejected (`E-RUNTIME-INPUT`, with play's message). Arrays keep
the order written; the runtime applies them in that order.

```jsonc
// writes — the play `engine:` block
{ "state": [ { "path": "run.storm", "value": "squall" },
             { "path": "run.gold", "add": 5 } ],
  "facts":   [ "met(mira, harbor)" ],      // ground facts, rendered form
  "retract": [ "inParty(elena, _)" ],      // `_` allowed, as in play
  "accept":  [ "findTheKey" ] }            // every key optional

// raiseOccasion
{ "type": "raiseOccasion", "occasion": "talk", "target": "mira",
  "payload": { "gift": "rose" },
  "pick": { "beat": "mira.thanks" },       // or "pass" (play `pick: none`)
  "writes": { … } }

// advanceClock — `by` is play's `advance:` value
{ "type": "advanceClock", "by": "slot" }    // "slot" | "day" | <slots:int>
{ "type": "advanceClock", "by": { "to": { "weekday": "sat", "slot": "dusk" } } }

// choose / bridgeResult / worldEvent / newRun / hostWrite
{ "type": "choose", "request": 3, "option": "talk" }
{ "type": "bridgeResult", "request": 4, "fields": { "won": true, "score": 12 } }
{ "type": "worldEvent", "name": "harborClosed" }
{ "type": "newRun", "writes": { … } }
{ "type": "hostWrite", "writes": { … } }
```

`Seed` is the play script's top level without `choose`, `bridges`,
`steps` and `expect`:

```jsonc
{ "state": [ { "path": "user.endingsSeen", "value": 2 } ],
  "facts": [ "met(mira, harbor)" ],
  "derive": true,                                   // default true
  "save": { "visited": ["prologue"],
            "presented": { "user": ["mira.intro"], "run": [] },
            "quests": { "findTheKey": "active" },
            "questInstances": { "findTheKey": 2 },
            "entriesRead": { "user": [], "run": [] } } }
```

The events schema (§9) is normative for every field; these examples are
not exhaustive.

## 6. Outputs

`Output` is `{events: [Event], await: Await}`.

### 6.1 Events

`events` lists, in execution order, everything the presentation produced:

| `type` | Fields | Meaning |
|---|---|---|
| `record` | `document`, `record` | One execution record exactly as the machine emits it at v0.37.0: the `lute run --json` `commands[]` record shape (pinned by `conformance/*/expected.json`) plus the play-only line `delivery` and menu marker fields `lute run` strips (`crates/lute-cli/src/runner.rs` `RunDriver::emit`). Lines, staging (bg, actor, music, sfx, vfx, camera, cg, video, sequence — with resolved `timing`), sets, asserts, retracts, accepts, grants, entries, choice/hub/match decisions and plugin records are all `record` events. |
| `presentation` | `occasion?`, `target?`, `beat`, `document`, `kind` | A presentation starts. |
| `presentationEnd` | `beat`, `document`, `reason?` | It ends (walk finished or `end` command). |
| `quest` | the `QuestAdvance` fields `lute play --json` prints in `quests[]` | A quest or objective status changed in a settle. |
| `clock` | `from`, `to`, `passed?` | The in-game clock moved. |

A grant is the machine's `grant` record (`quest`, `instance`, `objective?`,
`index`, `reward`, …); `instance` is the settlement key (ADR D1, D13).
Selection diagnostics — candidate lists, eligibility reasons, evidence —
are not events: a host that wants them calls the read-only queries of §6.4.

### 6.2 Await

| `type` | Fields | Accepted inputs |
|---|---|---|
| `awaitChoice` | `request`, `menu`: `{construct: "branch"\|"hub", id, document, position, presentation, prompt?, timeout?, options: [{id, verdict: "open"\|"closed"\|"spent", exit, once}]}` | `choose` |
| `awaitBridge` | `request`, `tag`, `document`, `position`, `fields` (field → declared type) | `bridgeResult` |
| `idle` | — | `raiseOccasion`, `advanceClock`, `hostWrite`, `worldEvent`, `newRun` |
| `ended` | `reason` (`terminal`) | `newRun`, `raiseOccasion` of an `outsideRun` occasion |
| `halted` | `kind`: `incomplete` \| `error`, `message`, `site?` | none |

A verdict `unknown` cannot reach `awaitChoice`: an option whose guard is
undecided halts the walk as `incomplete`, as play halts today.

### 6.3 Halt

`halted` ends a state lineage. `incomplete` is play's exit 3: the walk needed
a value no input can provide (an unseeded state path, an unbound
`occasion.target`, `now()` / `validAt(…)` — which R1 leaves unresolved,
exactly as `lute play` does at v0.37.0). `error` is play's exit 1 for a
failure inside a walk that is not a rejected input (e.g. a write violating
`E-FACT-EXCLUSIVE`). A host restores an earlier snapshot to continue.

### 6.4 Read-only queries

`Runtime` exposes pure queries over `&State`: `candidates(occasion, target)`,
`eligibility(beat, member)`, `clock()`, `terminal()`, `view(with_facts)`.
They are today's `Session` queries (`exec/session/mod.rs:90-136,222-229`).
`lute play` builds its report (candidates, evidence, writes) from them; they
never change state.

## 7. State and snapshot

### 7.1 State

`State` holds exactly:

1. **World** — the persistent and per-run fields of today's `World`
   (`exec/session/world.rs:28-116`): `state` (persistent tiers; `scene.*`
   excluded), base `facts`, `quests`, `questInstances`, `visited`,
   `spentRun`, `spentUser`, `spentAt`, `shareSpentBy`, `accepts`,
   `nextRunAccepts`, `failedObjectives`, `deferBy`, `deferHandlers`,
   `deferredHandlers`, `clockAdvancedByBeat`, `advanceCascadeDepth`,
   `cadence`.
2. **Continuation** — present only at `awaitChoice` / `awaitBridge`: the
   frame stack of the suspended walk (§8) and the pending request.
3. **Request counter** (§5.2) and the current await kind.

Today's `World` fields that are play-script scaffolding leave the runtime and
move to the `lute play` driver: `choose`, `choice_cursor`, `bridges`,
`derive` (becomes a `Seed` option), `step`, `decisions`, `eval_observer`.

### 7.2 Snapshot

`Snapshot` is the JSON serialization of `State`
(`schemas/lute-snapshot-0.38.schema.json`):

```json
{ "snapshotVersion": "0.38.0", "project": "<fingerprint>", "await": "idle",
  "request": 7, "world": { … }, "continuation": { … } }
```

- `project` is a fingerprint of the bundle (`irVersion`,
  `capabilitySnapshot`, and a hash of the index and artifact bytes).
  `restore` MUST reject a snapshot whose fingerprint differs
  (`E-RUNTIME-SNAPSHOT-PROJECT`) or whose `snapshotVersion` major.minor
  differs (`E-RUNTIME-SNAPSHOT-VERSION`). Migrating saves across content
  versions is a later phase.
- Round trip: for every reachable state `s` and input `i`,
  `step(restore(snapshot(s)), i)` MUST equal `step(s, i)`.
- Snapshots are taken at input points only (owner answer 2): a save in the
  middle of a batch of lines is the snapshot at the preceding input point
  plus the player's cursor into that batch (R3).

### 7.3 Cross-run data

State a condition can read is runtime state: endings and gallery unlocks are
authored as `user.*` state and travel in the snapshot (owner answer 3).
Per-`lineId` read history for read-skip is a player profile and never enters
the runtime.

## 8. Resumable walk

At v0.37.0 the `Machine` asks a `Driver` synchronously mid-walk
(`exec/driver.rs:14-42`), and hub option bodies, quest/handler segments and
entry bodies run through recursive `run_range` calls
(`machine/menu.rs:708-712`, `machine/quest.rs`, `machine/entry.rs`), so a
suspended walk's continuation lives on the Rust stack.

1. The walk MUST keep its continuation in an explicit, serializable frame
   stack. A frame records at least: document, program counter, range end,
   and the construct-specific context today held in locals (hub
   presentation index, return target and spent `once` options; quest /
   handler segment context; entry / bundle-beat body context).
2. `Driver::choose` and `Driver::bridge` become suspension points: the walk
   pushes its frames into `State`, returns `awaitChoice` / `awaitBridge`,
   and the next `step` resumes from the top frame. The machine's internal
   resume keeps every answer today's `Pick` / `BridgeReply` can give
   (`AutoFirst`, `HubAutoPass`, `Unscripted`, `Unanswered`), because
   `lute trace` and `lute run` answer with them; the public `choose` input
   is only `Pick::Option`, and the public `bridgeResult` only `Answer`.
3. For the public `choose` input, `Driver::forced` becomes the
   `E-RUNTIME-OPTION` rejection (§5.3).
4. `Driver::emit` becomes appending to `Output.events`.
5. `Driver::forced`, `unknown`, `observe`, `is_preview` and `premise_hint`
   remain as an internal policy seam for `lute trace`, document `lute test`
   and `lute run` (§10.3), which keep their rules (e.g. `lute run` skips a
   spent hub option). The runtime's own policy rejects a non-open pick,
   halts on unknown and ignores observations; it MUST be selected
   statically (no dynamic dispatch on the hot path).

## 9. Event contract versioning and wire rules

### 9.1 The `event` axis

`docs/versioning.md` gains the axis **Event**: the input, output and
snapshot JSON of §§5–7, stamped `eventVersion`, current `0.38.0`, aligned
with every other axis. Pre-1.0 a host gates on exact major.minor.

### 9.2 Stamps

`Output` serialized for the wire is `{eventVersion, events, await}`; a
snapshot carries `snapshotVersion` (equal to `eventVersion`).

### 9.3 Determinism

Serialized JSON MUST be deterministic: object keys in the order the schemas
list them (records keep the key order the machine emits today), no floating
point formatting differences (numbers are formatted as `lute run` formats
them today), and collection order as §11 pins.

## 10. CLI

### 10.1 `lute play`

`lute play` converts each script step to inputs, answers `awaitChoice` from
the script's `choose` lists (the `ScriptedChoices` cursor rules move to the
CLI unchanged) and `awaitBridge` from its `bridges` queues (per-tag FIFO,
step queue before top queue), and builds its report from events and §6.4
queries. When a script has no answer for an await, play reports exactly
what it reports at v0.37.0 for an exhausted choice or an unanswered bridge
and exits 3.

### 10.2 `lute play --events`

Prints the runtime's input/output stream as JSON Lines, one object per
input: `{"input": …, "output": …}`; the first line is
`{"seed": …, "output": …}` for `begin`. Every object carries
`eventVersion`. `--events` and `--json` are mutually exclusive. This stream
is the event contract's reference output and what session conformance pins
(§12).

### 10.3 Other commands

- `lute trace`, document-style `lute test`, `lute run`, `lute beats` and
  `lute calendar` keep their outputs. They use the runtime's machine through
  the internal policy seam (§8 item 5) and the read-only queries (§6.4); the
  machine is one implementation in `lute-runtime`.
- `lute run` stays the artifact-level reference runner: its JSON contract
  and its unknown-continues policy do not change.

### 10.4 Byte identity

Every CLI output except the new `--events` MUST be byte-identical to
v0.37.0, except the version stamps (`0.37.0` → `0.38.0`). Procedure
(`docs/design/runtime-unification.md` §6.3): a baseline binary from the
`v0.37.0` tag; for every `docs/examples/**/*.play.yaml` run `lute play`
human and `--json`; for every game run `lute beats`, `lute test`,
`lute test --json`; for every `docs/examples/**/*.lute` with tests run
`lute trace` human and `--json`; and `lute run --json` on each
conformance artifact; diff with stamps normalized. Any other diff is a
defect, not an allowed change.

## 11. Order-dependent semantics (normative)

An independent runtime MUST reproduce these orders; session conformance pins
them.

1. **Beat selection:** candidates start in index `beats` order, each
   `forKind` expanded in member order, then sorted by priority descending,
   then member / sub-kind / kind precedence, then original index order
   (`session/eligibility.rs:297-366`, `lute_check::beats::selection_order`).
   `first` and `sequence` consume that order; `all` presents in it.
2. **Quest settle:** quest documents in path order, repeated to a fixpoint;
   an earlier document's update is visible to a later one in the same pass
   (`session/lifecycle.rs:20-54,151-193`).
3. **Grants:** a quest's rewards in declaration order
   (`machine/quest.rs:972-1035`).
4. **Menus:** options in document order; hub presentations numbered from 0
   per visit.
5. **Datalog:** rules in IR order within a stratum to a fixpoint; facts as an
   ordered set (lexical order of the rendered fact).
6. **Seasons and cadence:** plan order, season paths in declared order
   (`cadence.rs:83-148,547-563,650-655`).
7. **Accepts and events:** queued accepts and world-event handlers in queue
   and declaration order.
8. **Bridge effects:** in IR effect order.
9. **State maps** are keyed; where their iteration is visible (snapshot
   serialization, `view`) it is lexical by path.

## 12. Conformance

1. **Session cases.** `conformance/session/<case>/` holds `project/`
   (sources, manifests), `inputs.jsonl` (the seed and input log) and
   `expected.jsonl` (the `lute play --events` output). Generated by
   `conformance/regenerate.sh` from a `script.play.yaml`; never hand-edited.
   R1 adds at least: occasion with `first` / `sequence` / `all` selection and
   priority ties; quest settle across two documents; grant with repeatable
   quest instances; clock advance with day/slot raises; hub with `once`
   options and a choice suspended and resumed; bridge await and result; a
   rejected input (`E-RUNTIME-BUSY`); `newRun`; and snapshot/restore in the
   middle of a hub (the case's log restores a snapshot captured at an input
   point and continues).
2. **Replay test.** A Rust test replays every case's log through
   `lute-runtime` directly and compares byte-for-byte; a second test
   snapshots and restores at every input point of every case and of every
   `docs/examples/**/*.play.yaml` run and checks the remaining stream is
   unchanged.
3. **Expressions.** The runtime evaluates `celSlot.expr` and never `cel`
   (§13). `conformance/harness` condition dumps (`--dump-conditions`) keep
   passing in JS (CEL and `expr`) and Go (CEL).

## 13. Expressions without a CEL parser

The compiler already emits `expr` for every CEL slot, including host calls
(`crates/lute-compile/src/expr.rs:371-392`; `celSlot` requires `expr` in the
schema). The executor ignores it and parses `cel` (`exec/store.rs` `Store::eval`
→ `lute_cel::parse_slot`, a thread-local parse cache).

1. `lute-runtime` MUST evaluate `expr` with its own walker over the JSON
   node (`schemas/lute-ir-0.38.schema.json#/$defs/exprNode`) and MUST NOT
   depend on `lute-cel` or `cel-parser`.
2. The walker MUST give the same value, error and unknown result as today's
   evaluator for every slot, including three-valued unknowns with read
   capture (used by the `lute trace` policy), `&&` / `||` error and unknown
   absorption, int/double arithmetic and overflow, `in`, `has`, indexed
   reads, and the six host functions.
3. `docs/runtime/execution-model.md` §Dispatcher loop is corrected: every
   slot carries `expr`; the `evalCel` fallback is removed from the reference
   loop.

## 14. Crate boundary

1. `lute-runtime` depends on `serde`, `serde_json` and `lute-manifest`
   (declaration types: clock, `Type`, occasions, entity kinds) only. It MUST
   NOT depend on `lute-check`, `lute-compile`, `lute-cel`, `lute-syntax` or
   `cel-parser`. A CI step checks `cargo tree -p lute-runtime -e normal`
   against this list.
2. Runtime semantics currently in `lute-check` and used by the executor
   (beat `selection_order` / `reorder`, `BeatOnce` parsing, prerequisite
   formula parsing, gate and target-member helpers, `prev`-run path
   helpers, reserved names) move to `lute-runtime`; `lute-check` imports
   them from there, so each rule has one definition. `lute_syntax`'s number
   and text formatting used by placeholders moves likewise.
3. The runtime reads the index through its own `Deserialize` types; the
   writer stays in `lute-compile`. `lute play` loading the serialized bundle
   (§4.1) is what keeps the two in agreement.
4. `lute-trace` keeps the preview: `TraceDriver`, mocks, `TraceReport`,
   transcript rendering and needles (`exec/record.rs`), producers and
   refusal hints. It depends on `lute-runtime`.
5. Public consumers of `lute_trace::exec::*` (`lute-cli`, `lute-bench`,
   `lute-wasm`) move to the new paths in the same slice that moves the
   symbol; no re-exports or aliases remain.
6. `lute-runtime` stays free of `std::fs`, `std::process`, `std::time`,
   threads and randomness; `cargo check -p lute-runtime --target
   wasm32-unknown-unknown` is part of CI.

## 15. Performance

The `lute-bench` A/B gate (`.github/workflows/benchmarks.yml`, 1.10 ratio)
stays green on every slice. `play-assembly` now includes bundle
serialization and `Runtime::load`; `play-replay` runs through `step`. A
regression above the threshold needs the owner's `performance-approved`.
