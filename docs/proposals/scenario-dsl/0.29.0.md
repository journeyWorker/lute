# Scenario DSL 0.29.0

0.28 left four questions open and one mechanism deferred. 0.29 settles each the
way that leaves the author one rule to remember, and ships the fourteen dogfood
games as checked examples.

## 1. One identifier rule

Every name an author writes — a scene, beat, entry, quest, objective, branch,
hub, choice or mark id; a document id segment; a `share=` key; a season,
relation, def, enum or entity member; a component or template param; an
occasion or event a plugin declares — is an **identifier**: a letter, then
letters, digits or `_`. A dotted id joins identifiers with `.`.

A `-` (or any other character) in a name is an error at the name, under the
slot's existing code, and names the camelCase spelling (`lamp-duty` →
`lampDuty`). 0.28 refused `-` where CEL reads the name and accepted it
elsewhere (`share="nana-report"`, `id: door-notes`); that split is gone.

## 2. Causes print first across files

`lute check-project` prints in the order a fix must follow: `lute.project.yaml`,
then plugins, then schemas, then documents in path order, then project-wide
rows. A consequence whose cause is reported in another file is still dropped
(0.28's one-cause-one-report rule); this orders what remains.

## 3. Only a chain stalls

`W-CHAPTER-STALL` stays specific to `chapters:`. A chain promises the scenes
play in order, so a scene that may never play breaks the promise silently. A
hand-written `after:` is itself the statement "wait for that scene" and never
warns. The stall advice already says: take a gated scene out of the chain and
give it its own `on:` and `after:`.

## 4. `lute new` writes what you asked for

`lute new scene --occasion O` always writes `on: O`. When `O` carries a
`chapters:` chain, it prints how to make the scene a chapter instead (list it
in the chain and drop `on:`).

## 5. Intent is stated where it is meant

There is no generic warning suppression — no allow list, no comment pragma: a
switch that hides a code hides the next real instance too. A warning that can
describe an intended design has a spelling that states the intent:

| Warning | The statement that means "on purpose" |
|---|---|
| `W-TERMINAL-PERSISTENT` | `terminal: { when: "<cond>", persists: true }` (new) |
| `W-SPENT-BY-REVERSIBLE` | write the `once:` period beside `spentBy` |
| `W-CHAPTER-STALL` | take the scene out of the chain; use `after:` |
| `W-TEMPLATE-DOT-PARAM` | write `F[@param]` |
| `W-DISPLAY-NAME-DUP` | `sharedName: true` on the cast entry |
| `W-BEAT-UNRAISED` (run start) | clock `raiseAtStart: true` |

`terminal:` keeps its string form. The long form `{ when, persists }` says the
ending outlives runs on purpose (a roguelike's permanent ending):
`W-TERMINAL-PERSISTENT` is silent, and `lute play` says the game is over for
good instead of offering `newRun`. `persists: true` on a terminal that reads
only run state is `E-META-VALUE` (it cannot persist). The IR carries
`terminalPersists: true` beside `terminal`.

## 6. The dogfood games are examples

The fourteen games written against Lute 0.21–0.28 move into the repo under
`docs/examples/games/<slug>/`, each with a README (genre, premise, what it
shows of the language, how to run it). CI checks each with
`lute check-project --deny-warnings` and runs its tests and plays, so the
examples stay clean as the language moves.

## Compatibility

- A name with `-` that 0.28 accepted (`share=`, document ids, and the other
  non-CEL slots) is now an error; rename it to the camelCase spelling given.
- `check-project` output order changes (causes first).
- `lute new scene --occasion` on a chained occasion writes `on:`.
- Additive: `terminal:` long form, IR `terminalPersists`.
