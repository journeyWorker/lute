# Lute 0.52.0 — clean slate

This is the normative 0.52.0 contract. The words **MUST**, **MUST NOT**,
**SHOULD** and **MAY** have their RFC 2119 meanings.

The release resolves every issue open on 2026-10-27, so that a fresh dogfood
starts from a clean slate: #139, #198, #201, #208, #209, #210, #211, #212,
#213, #214, #216, #217, #218. The decisions are in
[`2026-10-27-lute-0.52-decisions.md`](../../superpowers/notes/2026-10-27-lute-0.52-decisions.md);
where this spec goes beyond an issue's suggested fix, the note gives the
evidence and Appendix B lists every decision. The rule throughout is
conservative: the smallest surface, one spelling per concept, static analysis
kept sound, refuse rather than guess, and the runtime agrees with the checker.

The base is `main` at **v0.51.0** (`52d5420a`). Code anchors are cited at
`52d5420a`; Appendix A lists them by symbol.

Implementation plan:
[`2026-10-27-lute-0.52.0-clean-slate.md`](../../superpowers/plans/2026-10-27-lute-0.52.0-clean-slate.md).

## 2. Shared rules

The 0.51.0 §2 rules apply unchanged: a regression test that fails on the base
for every behaviour change (the issue reproductions first); one diagnostic
shape (registered in `crates/lute-cli/src/codes/registry.rs` and
`crates/lute-check/src/evidence.rs`, blessed with `LUTE_BLESS_DIAGNOSTICS=1`,
website EN + KO); **no hint recommends a spelling the checker rejects**; no
silent drop; byte stability for projects that use none of the changed
constructs (except §15); documentation in the same change; and
`docs/design/rust-coding-rules.md` for new Rust code. In particular:

- **Newtypes and enums, not strings:** `HubLeave` (a `u32` ≥ 1, the
  `jump.leaves` count), `RangeEnd` (how a runtime range ended), `MenuText`
  (a rendered text and its rendered translations), `RewardAttrFault`,
  `BodyRange` (the separately run body a node sits in).
- **One function per rule, shared by checker and compiler.** The hub head
  (§5.4) is one `pub` function in `lute-check` that `lute-compile` calls, as
  0.51's loop head is (`inject.rs:647`). A reward attribute's bound value
  (§7.3) is one function used by the checker, the raise table and lowering.
- **No HIR, no Fold, no synthesized nodes (rules §7).**
- **Counted work.** The hub head fixed point counts its work in 0.51's
  `LoopWalkStats` (heads, probe passes, probe nodes), asserted in CI.
- **Project diagnostic levels (0.50.0 §6).** `W-STAGE-ABSENT`'s new sites can
  be re-levelled like every `W-*` code; simulating commands apply no levels.

## 3. Literal braces in text (#139, #211)

### 3.1 A literal `{` before a marker (#139)

The IR encodes a literal `{{` in line text as `\{{` and doubles a literal
backslash before `{{` (lute 0.47.1 §3, `IrText`, `line_text.rs:103-176`). It
has no encoding for a literal `{` directly before a marker: plain text that
ends in an **odd run of literal `{`** right before a marker encodes to a bare
`{` followed by `{{` (`IrText::flush` escapes `{{` pairs greedily), and every
reader of the IR (the runtime's `markers`, an engine) then opens the marker one
brace early. On v0.51.0, `@narrator: S }}{\{{{{run.a}}} E` checks clean and
renders `S }}{{3} E` instead of `S }}{{{3} E`.

**Rule.** In line text, a `{{…}}` marker whose preceding decoded literal text
ends in an odd run of `{` is **`E-INTERP-BRACE`** (new, error, source layer).
An even run is representable (each pair encodes as `\{{`) and stays legal:
`\{{{{run.a}}` (a literal `{{` then a marker) renders `{{3` today and MUST keep
doing so.

The decoded literal text is what the inline parser builds (`decode_inline_text`
of each text piece, modifiers' text included, joined in order as
`inline_plain_text` joins them, `ast.rs:151-164`): sources such as
`{\{{{{run.a}}`, `\{\{{{run.a}}` and `x{:pause{s=0.5}{{run.a}}` all reach it.
A source `{{{run.a}}` is not this case: the parser opens the marker at the
first `{{` and its inner text `{run.a` is already `E-CEL-PROFILE`.

- **Where.** One function in `lute-syntax` (beside `IrText`) finds the first
  such marker in an inline node list; the inline parser
  (`parser/line.rs:135`, `parse_inline_nodes`) calls it for every line text it
  parses and emits the diagnostic at the marker's span. So:
  - a line in a scene, quest, lore or component body reports at the marker;
  - a component line whose `{{@param}}` splices an argument that ends in an odd
    run of `{` before a marker reports at the `::use` (the component-body
    diagnostic anchoring). The slice confirms which pass builds a spliced
    line's plain text (`normalize.rs:1232-1240`, `bind_line_head` `:1399`)
    and calls the finder there;
  - a translation (`bind_line`, `locale.rs:416-452`) runs `parse_inline_text`,
    so a translation with the sequence is not merged:
    `` E-L10N-MODIFIERS `ko` text for `s.narrator_0010` is not merged: its inline markup does not parse (E-INTERP-BRACE: …) `` (existing wording).
- **Labels are not affected.** An option label, prompt or
  directive `text` value is carried to the IR as written and read by the same
  `{{` rule (`interp_sites`, `line_text.rs:50-92`) in the checker and the
  runtime, so there is no re-encoding and no ambiguity.
- **Message:**
  `` a literal `{` directly before `{{run.a}}` cannot be told apart from the marker in compiled text (lute 0.47.1 §3): put a character between them (`{ {{run.a}}`), or show the brace from a string state path (`{{run.lbrace}}{{run.a}}`, with `run.lbrace` declared `{ type: string, default: "{" }`) ``
  Both spellings check clean and render on v0.51.0 (probed: the second renders
  `S {3 E`). `{{…}}` in the message is the offending marker's source text.
- **A plain `{{` spliced before a marker (#221).** A `::use` argument is
  spliced with its inline punctuation escaped, so an argument ending in `{`
  is written `\{` and fuses with a `{{` right after it into the escaped
  opener `\{{`: the marker is lost from the text while its placeholder stays
  (v0.51.0: `p="{{"` before `{{run.a}}` compiles `S \{{\{{run.a}} E` and
  renders `S {{{{run.a}} E`). The check judges the text the expansion means
  (each spliced argument fenced off, so nothing fuses): an odd run before a
  marker is the rule above; an even run that still fuses — an argument
  ending in a plain `{{`, an opener without its `}}` (dsl 0.26.0 §3.1) — is
  `E-INTERP-BRACE` at the outermost `::use` too, with
  `` a `::use` argument ending in a plain `{{` merges with the `{{run.a}}` spliced after it, and the marker is lost: pass a literal `{{` in an argument as `\\{{` (lute 0.47.1) ``.
  Refused rather than rendered as written: a plain `{{` in an argument is
  not a literal, and rendering it as one would add a second spelling beside
  `\\{{`, which never fuses (it renders `S {{3 E`).

### 3.2 A literal `{{` in a quoted attribute value (#211)

**The label grammar.** These values take the label grammar (`{{…}}`
interpolation with modifiers, read by `interp_sites`): a `<choice text>` of a
`<branch>` or `<hub>`, a `<branch prompt>` and a `<hub prompt>` (from 0.52,
§6.1), and a plugin directive attribute declared `type: text` (0.51.0 §5.2).
From 0.52 an `<objective title>` is plain text, not label grammar (§6.7).

**Rule.** In a quoted attribute value, an odd backslash run directly before
`{{` (`\{{`, `\\\{{`) is accepted by the lexer and stored **verbatim**, as
`decode_value` already keeps `\\`, `\n` and `\t` (`parser/attrs.rs:514-551`).
In a value that takes the label grammar it is a literal `{{` — the line-text
spelling (0.47.1 §3). An even run (`\\{{`) is a literal backslash followed by a
live marker, as in line text. `\{` not followed by `{` stays `E-STRING-ESCAPE`.

- **Lexer** (`scan_attr_list`, `attrs.rs:62`, escape check at `:104-119`):
  `\{` is no longer pushed to `escapes` when the next byte is also `{`.
- **Checker:** in any quoted value that does **not** take the label grammar,
  an odd backslash run before `{{` is `E-STRING-ESCAPE` at the attribute's
  value span. The check reads each node head's authored attributes
  (`authored_attrs`, `attrs.rs:413-461`, which keep escapes undecoded), so
  values the parser lifts into typed fields or CEL slots (`when`, `test`) are
  covered. The value is read by the lexer's own escape pairs, not the label
  scanner: outside the label grammar a value has no markers, so a `\{{`
  after a `{{…}}` or an unterminated `{{` is refused too (review S1-R1). An
  imported component body is judged at each host's `::use` under the host's
  snapshot as well, nested `::use` arguments included, with the body's own
  position related (the component-body anchoring; review S1-R2). Messages:
  - generic: `` `\{{` (a literal `{{`) is defined only in line text and in the values that take the label grammar — `<choice text>`, `prompt` and a plugin `text` attribute; `<attr>` of `<owner>` is not one ``
  - on a `::use` argument the clause ends `…; a `::use` argument passes a literal `{{` as `\\{{` (lute 0.47.1)` (the 0.47.1 spelling, unchanged; probed on v0.51.0).
- **The parser's own message** for an undefined escape changes from
  `only \" \\ \n \t are defined escapes (dsl §4.4)` to
  `` only \" \\ \n \t are defined escapes, and `\{{` for a literal `{{` in a label (dsl §4.4) ``.
- **IR and runtime.** A label's IR `text` holds `\{{`; under the 0.47.1 reading
  rule it is a literal `{{`, and the runtime's rendered menu text (§6.3)
  decodes it. `placeholders` stay 1:1 with the markers (an escaped `{{` is no
  marker, `scan_label_interps`, `ast.rs:837-841`).
- **Tooling.** `lute fmt` and tree-sitter keep the value bytes (no new token);
  the LSP's semantic tokens treat `\{{` in a label as text.

## 4. A quest's top level admits only `<on>` and `<objective>` (#208)

The runtime runs a quest artifact through `run_quest`: its `<on>` handler
bodies and `<objective>` segments only (`machine/mod.rs:836-851`,
`machine/quest.rs:1162-1170`). Anything else directly inside `<quest>` compiles
to records no run reaches. On v0.51.0 a top-level content line, `::set`,
`::label` and `<branch>` check clean and compile.
Content **after the last body** is the one exception that ran: the last body's
segment runs to the end of the quest's commands (`run_segment` stops at the
next segment start, else the end of the stream; `quest_program` collects the
starts, `machine/quest.rs:130-168, 1162-1170`), so a line after the last
`<on>`/`<objective>` played by fallthrough as part of that body. 0.52 refuses
it like all other top-level content (an intentional behaviour change, decided
by the orchestrator): it belongs in the body it ran with.

**Rule.** The admission table's `QuestBody` context (`admits`, `admission.rs:103`;
the arm at `:132-143`) admits `On` and `Objective` only. Every other node kind directly
inside `<quest>` is **`E-GRAMMAR-NOT-ADMITTED`** (existing code, new cause). A
`<reward>` is not a node (it is a quest field) and stays admitted. Nested
bodies are unchanged (`Emittable`).

- **Message** (the node described as `describe` does, `admission.rs:594-608`):
  `` a content line at the top level of `<quest id="q">` never runs — a quest runs only its `<on>` handlers and `<objective>` bodies: move it into the `<on event=…>` or `<objective>` whose moment it belongs to (dsl 0.2.0 §6.7) ``
  `<hub>` and `<timeline>` at the top level keep their current message (they
  are refused anywhere in a quest).
- **`E-JUMP-LOOP-SCOPE` loses a cause.** 0.51's "a loop region spans an
  `<on>`/`<objective>` at a quest's top level" (0.51.0 decision note R4)
  needed a top-level `::label`, which is now refused. The cause, its message
  branch and its registry sentence are removed; its tests expect
  `E-GRAMMAR-NOT-ADMITTED`.
- **Registry summary** of `E-GRAMMAR-NOT-ADMITTED` names the new case ("…,
  anything but `<on>`/`<objective>` at a quest's top level, …").
- **Corpus.** No document under `docs/examples` or `conformance` has quest
  top-level content (scanned at `52d5420a`). The test fixture
  `crates/lute-cli/tests/fixtures/stage-record-045/quests/stage.lute` does; it
  migrates its two lines into an `<objective>` body and keeps its test
  (`stage_record_045.rs:112-137`) asserting the preload.
- **Tests:** each node kind at the top level (line, directive, `::set`,
  `::label`, `::jump`, `<branch>`, `<match>`, `::assert`, `::retract`) is
  refused with the message (failing on v0.51.0); `admission.rs`'s
  `assert_retract_admitted_wherever_set_is` keeps the `<on>`-arm half and its
  top-level half now expects the refusal; the 0.51 R4 loop tests move.

## 5. Hubs: leaving jumps and the hub head (#216, #217)

### 5.1 A jump stays in its range or leaves hubs (`E-JUMP-INTO-BODY`)

A **range body** is a body the runtime runs as its own range: a `<hub>` option
body, a hub `<return>` body, an `<on>` body, an `<objective>` body, a lore
`<entry>` body, a lore `<beat>` body, and a document's top level (all of a
scene's sections together: a scene runs as one range, `machine/mod.rs:847`, so
a forward jump between sections stays legal, as in
`games/monster-league/scenes/mid/helix-tower.lute`). `<choice>`
bodies of a `<branch>` and `<match>` arms are laid out inline and are not range
bodies (the 0.51 `BodyKind::inline` rule, `next_labels.rs:151-167`).

**Rule.** Let `B(J)` be the innermost range body around a `::jump` and `B(L)`
the innermost range body around its `::label`. `B(L)` MUST be `B(J)` or a range
body that encloses `B(J)`, and every range body from `B(J)` outward up to (not
including) `B(L)` MUST be a hub option or `<return>` body. Otherwise the jump
is **`E-JUMP-INTO-BODY`** (new, error, source layer), at the jump. On v0.51.0
each of these checks clean: a jump from one hub option into a sibling option's
body; a jump from before a hub into an option body; a jump from one
`<objective>` body into another.

- **Message** (the entered body named as `BodyKind::leave_message` names it,
  `next_labels.rs:171-203`):
  - hub option: `` `::jump{to="mid"}` enters the body of hub `desk`'s option `take`, which runs only when that option is chosen — jump to a label in the same body, or after the hub ``
  - `<return>`: `` … enters the `<return>` body of hub `desk`, which runs only when an option hands control back — … ``
  - `<objective>`: `` … enters the body of `<objective id="p">`, which runs only when that objective completes — jump to a label in the same body (to end a body early, jump to a label at its end) ``
  - `<on>`: `` … enters the `<on event="e">` handler, which runs only when that event fires — jump to a label in the same body (to end a body early, jump to a label at its end) ``
  - `<beat>`: `` … enters `<beat id="b">`, which runs only when that beat is presented — jump to a label in the same body (to end a body early, jump to a label at its end) ``
    (an `<entry>` and the document's sections take the same hint: the
    migration of an early return through another body, §13)
- The rule runs in the label pass with the body chains 0.51 already records
  (`check_next_labels`, `next_labels.rs:536`), one pass after collection. It
  is independent of `max` (a bounded jump is already confined by
  `E-JUMP-LOOP-SCOPE`).
- **Corpus:** no jump under `docs/examples` or `conformance` is in a hub body
  except `conformance/bounded-jump`'s in-body loop, which stays legal.

### 5.2 IR: `jump.leaves` and `lute.core.hubLeave/1`

A runtime range ends on any transfer out of it (`run_range`,
`machine/mod.rs:945-979`, `:967-969`), and the hub loop then presents again
(`do_hub`, `machine/menu.rs:717-737`). Positions cannot tell a leaving jump
from an ordinary end: a `<branch>` at the end of an option body ends in a
compiled converge jump to the option's `stop`, and a label right after
`</hub>` binds to the hub's converge, which equals `stop` for the last laid-out
non-exit option of a hub without `<return>` (option bodies are laid out
consecutively; only an exit option ends in a jump, `stage.rs:679-693`).

**Rule.** `JumpCmd` (`ir.rs:1394`) gains **`leaves`**: the number of hub option
or `<return>` bodies between the jump and its label's range body (§5.1),
written only when ≥ 1 (`HubLeave`). The label pass computes it; lowering
(`lower.rs:442`) writes it. A bounded jump never carries it (§5.1).

- **Semantic id** `lute.core.hubLeave/1` (module `core`, behaviour "jumps that
  leave a hub"), collected **only** by an artifact with a `jump` that carries
  `leaves` (D5: an engine that ran the 0.51 behaviour would present the hub
  again; it MUST refuse such an artifact). `semantics.rs` `REGISTRY` 17 → 18;
  `FIELD_TABLE` gains `leaves`; `docs/design/modules.md` lists the id.
- **IR schema:** `jump.leaves` (integer ≥ 1). Engine negotiation test beside
  `lute.core.boundedJump/1`.
- No corpus artifact gains `leaves` or the id.

### 5.3 Runtime

- `do_jump` (`machine/mod.rs:1002`) on a jump with `leaves = n` returns a
  `Step::Leave { to, hubs: n }` instead of `Step::Next(to)`.
- `run_range` returns a `RangeEnd`: `Done` (it ran off its end, or a transfer
  left it as today) or `Leave { to, hubs }` (a `Step::Leave` was taken; the
  range ends at once).
- `do_hub`, on `RangeEnd::Leave { to, hubs }` from an option or `<return>`
  range: the hub visit ends (no `<return>` body runs, no re-presentation); with
  `hubs == 1` it returns `Step::Next(to)`; with `hubs > 1` it returns
  `Step::Leave { to, hubs: hubs - 1 }` to the enclosing range. A quest segment
  and the top-level range never receive a `Leave` (the count never exceeds the
  enclosing hubs).
- **Load-time validation** (beside 0.51's `loop_table`, `machine/mod.rs:357`;
  Review052 F1). For a `jump` with `leaves = n`, take the chain of range bodies
  enclosing the jump (innermost first) and the range body enclosing its target.
  Removing **exactly** the `n` innermost bodies of the chain MUST leave the
  target's range body as the innermost remaining one, and each removed body
  MUST be a hub option or `<return>` range. Otherwise the artifact fails to
  load with a message naming the jump's position and the count it expected.
  This rejects an **undercount** (a jump inside two hub options targeting a
  label after both hubs with `leaves: 1` would end only the inner hub and the
  outer hub would present again — #216 recreated), an **overcount**, and a
  target in a **sibling** body. A `jump` carrying both `max` and `leaves` is
  refused at load too (a bounded jump never leaves a hub, §5.1/§5.2; the 0.51
  loader would otherwise accept `max` on a forward jump).
- **Coincident ends** (S3 review P2). For an inner hub in the outer hub's
  last laid-out non-exit option with no outer `<return>`, the end of that
  option and the outer converge are one address, so the target lies in two
  ranges at once and both `leaves: 1` and `leaves: 2` pass the load check.
  They do **not** run alike: `leaves: 1` ends the inner visit, completes the
  outer option and presents the outer hub again (the source label is at the
  end of the outer option); `leaves: 2` ends both visits and continues after
  the outer hub (the label is after `</hub>`). Position cannot tell them
  apart; `leaves` is authoritative and the compiler writes the count of the
  source form (tests pin both forms, through `lute compile` and `lute run`).

### 5.4 The hub head (#217)

A hub presents again after every non-exit option (and after its `<return>`
body), so an option may run after any sequence of options. Both stage walks
fork every option from the hub's **entry** state: the compiler's `walk_hub`
(`stage.rs:611-729`, fork at `:666-677`) and the checker's fold, which treats a
hub's bodies as parallel arms (`check/injections.rs:54-88`). On v0.51.0 the
#217 hub (`send` hides `mira` on a declared exit, `talk` has `@mira: Still
here.`) checks clean, while the same two steps without a hub warn.

**Rule.** The stage state at a hub's options is the **hub head** `H`, the
least fixed point (in the stage lattice's order, as 0.51's loop head) of

```
H₀      = entry
Hₖ₊₁    = entry                 when back(Hₖ) = None
          join(entry, b)        when back(Hₖ) = Some(b)
C(H)    = the join of the completion states of the non-exit option bodies walked
          from H that complete (reach their end) — Option<StageState>: None
          when no non-exit option completes on any route
back(H) = None                       when C(H) = None
          Some(R(c))                 when C(H) = Some(c),
          R = the <return> body walked from c (when the hub has one; else identity),
          and None again if no route completes the <return> body
```

The completion result is an `Option<StageState>` (Review052 F2):
`StageState::join(entry, [])` returns `entry` (`inject.rs:340-343`), so a join
cannot stand for "unreachable". When no non-exit option can complete — a hub
of exit options only, or one whose non-exit options all end in an unguarded
jump, a leaving jump (§5.2) or `::end` — `<return>` is **not** applied and
there is **no** back edge (the runtime's exit options break before `<return>`,
`machine/menu.rs:721-733`). This is the `None`-versus-state distinction
`head_fixpoint` already makes (`loop_walk.rs:245-272`).

The iteration uses the one `StageState::join` (`inject.rs:340`) and 0.51's
`head_fixpoint` and `StageHead` lattice (`inject.rs:647-719`): probe passes
fold the bodies with the checker's fold, emission off, a fresh probe-local
pending map, publishing nothing; the bound is 4 × the characters the entry
and the bodies name, + 2 (0.51's 3, plus one step for a sprite turning
unknown, below), with the same widening to the lattice top. A jump's state
still goes to its label as today.

**`::end` inside a hub body** (orchestrator decision, 2026-10-27). Neither
0.51 stage walk ends a route at `::end`. Inside a hub option or `<return>`
body both walks now do (`StageFlow::ends`, one predicate), so such a body
does not complete: it feeds neither `C(H)` nor, in an exit option, the
converge. Elsewhere `::end` is unchanged: ending stage routes at every `::end`
would change branch and match joins outside hubs (for example
`conformance/end-reason`), which is not in 0.52's scope.

**The join keeps presence (#222, folded into 0.52 by the orchestrator).**
0.51's `StageState::join` carried a character as on stage only when every
side had an identical sprite; a differing emotion, pose or anchor dropped
the character to "maybe on stage" with no `dirty` flag, so a plain line after
the join lost its `auto-pose-reset` although every route needed one. The hub
head joins the entry with the options' completions, so it would have
surfaced this in the corpus (`summer-station/lore/talks.lute`, `radioHub`).
The join now keeps a character on stage when every side has them on stage;
differing sprite attributes merge to an **unknown** sprite
(`SpriteState::unknown`, every attribute `None`), and `dirty` survives when
any side marks it. Presence-driven injections follow presence (the plain
line resets the pose); attribute-driven ones stay conservative: an `::actor`
of a character with an unknown sprite injects what a fresh show does (the
default anchor, the emotion preload), as 0.51 did after dropping them, and
settles the sprite. The same join serves branches, matches, labels, loop
heads and the hub head.

- **Final pass:** every option body is walked once from `H`; the `<return>`
  body is walked from `C(H)` when it is `Some`, and not at all otherwise
  (its nodes are then unreachable, as at runtime), with emission and
  diagnostics on.
- **After the hub:** the state at the hub's converge is `join(H, [H, the exit
  states of the exit options])` — `H` stands for the natural convergence when
  nothing is eligible.
- **One function.** The head lives in `lute-check` (`StageFlow`, `inject.rs`),
  is `pub`, and is called by `fold_injections` and by `lute-compile`'s
  `walk_hub`. The checker/compiler agreement test (0.51's
  `record_stage_labels`, `inject.rs:749-761`) records each hub head as a label
  state keyed `hub:<id>` and asserts both walks bind the same states.
- **Counted work:** a hub head is a head in `LoopWalkStats` (heads, probe
  passes, probe nodes). `lute-bench flow-loops` gains a `hub` shape (options
  R, nesting D) with CI-asserted work, like 0.51's region grid.
- **Other walks** (inventoried, not changed): definite assignment forks every
  option from the entry (`defassign.rs:988-1029`), which is sound because a
  write never un-assigns, so the head's available set equals the entry's;
  `fact_must` already iterates a hub fixed point (`fact_must.rs:1454`). The
  presence walk (`cast/presence/walk.rs:126`) forks options from the entry
  but first kills every state path and fact any hub body writes
  (`kill_writes` over `h.bodies()`), so no guard proven at the entry survives
  into an option a previous round could have falsified: its claims hold for
  every round, and it is unchanged.
- **Corpus:** every corpus delta is listed with its reason in §15 class 6.

## 7. Reward-kind attributes (#201)

A reward kind's `attrs:` (plugin §14, dsl 0.16.0 §4) are loaded and folded into
the capability snapshot but cannot be authored: `<reward>` closes over six keys
(`REWARD_ATTRS`, `logic_attrs.rs:101`), so every declared attribute is
`E-UNKNOWN-ATTR`; and the declarations themselves load unchecked.

### 7.1 Declarations (load)

A reward kind's `attrs:` entries follow the directive attribute declaration
rules. At load, beside the 0.50 reward-effect faults (`loader.rs:757-780`,
`validate_reward_effects`, `validate.rs:792`), each of these is
**`E-PLUGIN-PARSE`** at the entry (a new `ManifestError::RewardAttr { kind,
attr, fault: RewardAttrFault }`):

| Fault | Message |
|---|---|
| a `<reward>` key (`id`, `kind`, `target`, `amount`, `when`, `outcome`) | `` reward kind `BADGE` declares attribute `amount`, which `<reward>` already has (`id`, `kind`, `target`, `amount`, `when`, `outcome`) — give it another name `` |
| declared twice | `` reward kind `BADGE` declares attribute `rarity` more than once — keep one declaration `` |
| `default:` not of the type (`attr_default_accepts`, `validate.rs:596`) | `` reward kind `BADGE` declares attribute `rarity` as `string` with `default: 3`, which is not of type `string` — give a default of the declared type `` |
| `list`, `map` or `record` | `` reward kind `BADGE` declares attribute `tags` as `list<string>`; an attribute value is written as one scalar (string, number, bool, an enum or entity member, a provider or asset id), so no `.lute` value can satisfy a `list`, `map` or `record` (structured attribute values are not supported yet): give each field its own attribute `` |

Types and defaults render as the directive messages render them
(`types::type_str`, the YAML literal). `type: text` on a reward kind attribute
is already refused when the file parses and stays so. No corpus reward kind
declares `attrs` (scanned at
`52d5420a`), so no corpus project changes.

### 7.2 Authoring and checking

On a `<reward>` whose `kind` names a declared kind, the closure is
`REWARD_ATTRS` plus the kind's declared attribute names. Each authored kind
attribute is checked against its declaration by the directive checker's
`check_attr_value` (`directives.rs:731-805`) with the owner rendered
`` <reward kind="BADGE"> `` (so `E-ATTR-TYPE`, `E-BAD-ENUM`, `E-UNKNOWN-ID`,
the entity/provider/asset checks apply with their wording); a `required: true`
attribute that is not authored is `E-MISSING-ATTR`.

- **Values are quoted literals** (a bare flag is `true` for a `bool`). An
  `@ref` value is **`E-REWARD-ATTR`** (existing code, new cause), as an `@ref`
  `target=` is (0.49 #192, `rewards.rs:459-476`):
  `` `<reward rarity=@r>`: a reward's attributes are static data the engine grants against — write a quoted value (`rarity="gold"`) ``
- **`E-UNKNOWN-ATTR`** on a `<reward>` whose kind declares attributes appends
  them: `` `<reward>` has no attribute `rarety`; its attributes are `id`, `kind`, `target`, `amount`, `when`, `outcome`, and kind `BADGE` declares `rarity` `` (with the existing did-you-mean). The message of a kind that declares none, or of an
  unknown kind, is unchanged.
- No snapshot reward kinds (no plugin) keeps today's six-key closure.

### 7.3 Effects read `@<attr>`

Reward-kind `effects` read `@<attr>` where directive effects do:

- **Facts** (`asserts`, `retracts`): `@<attr>` may name `target` or a declared
  attribute of the kind. The load fault becomes
  `` reward kind `BADGE` effect `badge(@rarty)` reads `@rarty`, but the kind declares no such attribute (declared: target, rarity) `` (with did-you-mean).
- **Raise targets** (`effects.raises`, 0.51.0 §4.1): `@<attr>` may name
  `target` or a declared attribute, under the 0.51 assembly typing rule
  (`E-PLUGIN-RAISES`: for a domain occasion `{ prefix, entity }` the attribute
  is typed `{ entity: <entity> }`). The load fault for an undeclared attribute
  reads as the fact one.
- **Accepts** are unchanged: `@target` or one quest id (decision note item 8).
- **Binding** (one function, used by `reward_facts`/`target_facts`,
  `reward_effects.rs:162-221`, the raise table's `reward_raises`,
  `raises.rs:718`, and lowering): the reward's authored value of the
  attribute; else the attribute's `default:`; else **unbound**, and the
  effect that reads it is not applied (0.50's rule for an unbound `@target`).
  `forbidden` targets keep their rule.
- Graph and analyses read the bound effects through the existing paths (fact
  edges, `[raises]` anchors, `E-RAISES-TARGET`), unchanged otherwise.

### 7.4 IR

`RewardEntry` (`ir.rs:1997-2037`) gains **`attrs`**: each authored kind
attribute and each declared `default:` not authored, typed as a `plugin`
record's `fields` are (`attr_json`, `default_json`; `lower.rs:510-525`),
written last and only when non-empty. The bound effects land in the existing

### 7.5 Runtime

The `grant` record's `reward` object (`machine/quest.rs:999-1021`) gains

### 8.2 `lute impact` follows `[accept]` and `[raises]` (#210)

`lute impact` traverses the semantic graph (`lute-model/src/graph.rs`), which
has neither edge. **Rule:** `graph.rs`'s `add_project_dependencies` (`:768`)
adds, for every edge of the root's scenario graph (`RootScenario.graph`,
`lute-model/src/scenario.rs:19`) whose kinds include `Accept` or `Raises`, an
edge from the source node to the dependent node, labelled `accepts` /
`raises`, with the node mapped to its semantic node key (scene, quest, beat)
by one mapping function.

**Evidence (Review052 F4).** The graph keeps only edge kinds, and the raise
anchors keep `RaiseFrom { source, shown }` (`raises.rs:200-231,249-252`), so
neither can tell a static raise from a dynamic one. The graph is not widened.
Instead the model passes the **resolved raise sites** of the project raise
table (`RaiseSite`, each with its `RaiseTarget::{Static, Dynamic}`
provenance) to the impact builder alongside the graph. An `[accept]` edge is
`Proven`. A `[raises]` edge is `Proven` if **any** static raise site backs it
(source node and answering node), else `Heuristic` (every backing site is
dynamic, `occasion.target`). Tests: the #209 project's `impact --node scene:a`
lists `quest:q` via `accepts` (failing on v0.51.0); a static-only, a
dynamic-only and a mixed raise edge (`Proven`, `Heuristic`, `Proven`); JSON
and human output. 0.51.0 §4.5's sentence that impact follows neither is
