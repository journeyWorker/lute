# Scenario DSL 0.32.0

Phase 1 of `docs/design/architecture-direction.md` (§5): everything an engine
needs to implement Lute's execution IR without reading Lute's source. Four
changes, one release, clean cutover (D6): conditions become standard CEL from
source to IR (§1–§4, D12), engine-owned state is visible in the IR (§5, D1),
reward grants carry an idempotency identity (§6, D1), and the compiled output
is named and versioned as the **execution IR** (§7, D3). §8 extends the
conformance corpus; §9 lists diagnostics; §10 records decisions.

## 1. Conditions are standard CEL

Every condition and value slot (guards, `when`, `test`, `<match on>`, `::set`
values, quest `start` / `fail` / `rearm`, objective `done` / `visibleWhen` /
`by` / `until`, reward `when`, entry / beat `when` / `spentBy`, `<on when>`,
gate `raisedWhen`, season `live`, `terminal`, rule-body `cel("…")` guards,
def bodies, timeline durations) holds a **standard CEL** expression
(cel-spec) over the environment of §3, restricted to the profile of §1.1.
An expression that any conforming CEL implementation would parse, type-check
against that environment and evaluate to the same value is valid Lute;
nothing else is.

Two forms inside a CEL slot are Lute's and are expanded at compile time, so
the IR never contains them:

- `@name` — a project `def` reference, replaced by the def's CEL.
- `$` — the `<match on>` subject inside its `<when test>`.

Two authoring forms are not CEL slots and are unchanged by this release:

- `<when is="…">` alternatives — a literal/range shorthand the compiler
  synthesizes into a CEL comparison against the match subject; the arm carries
  the shorthand in semantic IR field `is`, while the slot's `authored` is
  diagnostic-only (§7).
- `{{…}}` interpolation in line text — a rendering form restricted to a
  state path, `@ref` / `@ref(args)` or `userName`; a `@ref` resolves to a def
  whose body is a CEL slot and is emitted as one.

### 1.1 The closed profile

Admitted:

| Form | Notes |
|---|---|
| literals | `int` (`3`, `-7`), `double` (`3.0`, `1.5e2`), `bool`, `string`. No `uint`, bytes, `null`. Integer literals MUST lie within ±2^53 so every JSON reader keeps them exact. |
| lists | list literals; `in` membership. |
| state reads | select (`run.day`) and index (`quest["zero-coke-001"].state`, `user.bond[occasion.target]`). |
| operators | `!`, unary `-`, `&&`, `\|\|`, `==`, `!=`, `<`, `<=`, `>`, `>=`, `+`, `-`, `*`, `/`, `%`, `?:`. |
| presence | the `has()` macro over a select; `"key" in map` for keys that are not identifiers. |
| conversions | `int(x)`, `double(x)`. |
| host functions | `holds`, `count`, `countDistinct`, `validAt`, `now`, `visited` (§2). |

Rejected (`E-CEL-PROFILE`): every other function or macro (comprehensions
`all` / `exists` / `map` / `filter`, `size`, string methods), map and struct
literals, `uint`, bytes, `null`, free identifiers that are not environment
variables.

### 1.2 Numbers: `int` and `double`

The state model's numeric types are CEL's: **`int`** and **`double`**.
`type: number` is removed; every numeric declaration names one of the two,
everywhere a type is declared: state slots, shapes, def results, plugin
directive attributes and bridge result fields. Literals are typed as in CEL.

The checker types every operand from its declaration — never as `dyn`, even
though `celEnv` declares roots as `map(string, dyn)` — and applies these
rules:

- arithmetic requires both operands of the same numeric type; `%` is `int`
  only (CEL overload rules);
- comparison and equality between an `int` and a `double` operand are
  rejected; convert explicitly with `int()` / `double()`. This is a **Lute
  profile restriction**, stricter than CEL: cel-spec defines heterogeneous
  numeric equality and ordering at runtime, and the restriction keeps a
  checked condition from depending on whether an implementation enables it;
- `int / int` truncates toward zero, as CEL does;
- integer overflow and integer division or modulo by zero are evaluation
  errors (§4); `double` arithmetic follows IEEE 754 as in CEL (`1.0 / 0.0`
  is `+inf`, never an error).

A `::set` value must have the target slot's type. A default must be a literal
of the slot's type (`default: 0` for `int`, `default: 0.0` for `double`; an
integral literal default for a `double` slot is `E-STATE-DECL`).

### 1.3 What changes for an author

| 0.31 | 0.32 |
|---|---|
| `holds(inParty(elena, _))` | `holds("inParty", ["elena", "_"])` |
| `count(inParty(_))` | `count("inParty", ["_"])` |
| `holds(owned(occasion.target))` | `holds("owned", [occasion.target])` |
| `countDistinct(sawAt(W, _, _, _), W)` | `countDistinct("sawAt", ["_", "_", "_", "_"], 0)` |
| `validAt(at(hall), t)` | `validAt("at", ["hall"], t)` |
| `isSet(run.tip)` | `has(run.tip)` |
| `isSet(run.visits["lab-b2"])` | `"lab-b2" in run.visits` |
| `day: { type: number }`, `run.day % 2 == 0` | `day: { type: int }`, same text |
| `affection: { type: number }`, `run.affection > 3` | `affection: { type: double }`, `run.affection > 3.0` — or `type: int` |

CEL accepts `'…'` and `"…"` string literals alike. Inside a `.lute` attribute
delimited by `"` — and inside a YAML double-quoted scalar or a rule-body
`cel("…")` — CEL strings use single quotes:
`<choice when="holds('inParty', ['elena', '_'])">`. No backslash escapes are
needed anywhere; `lute fix` and the documentation follow this rule.

## 2. Host functions

Declared in the environment (§3), implemented by the engine over its fact
store and presented-scene set. Their semantics are those of 0.31 (dsl §8,
0.21.0 §7a.1, 0.24 T3-9, `docs/runtime/cel-and-facts.md`); only the calling
convention changes.

| Signature | Meaning |
|---|---|
| `holds(string, list(dyn)) -> bool` | some current fact of the named relation matches the argument list |
| `count(string, list(dyn)) -> int` | number of current facts matching |
| `countDistinct(string, list(dyn), int) -> int` | number of distinct values at the given 0-based position among matching facts; the list element at that position MUST be `"_"` |
| `validAt(string, list(dyn), int) -> bool` | the matching fact was valid at the narrative-time tick. The checker keeps the 0.24 rule: the third argument must be a narrative-time expression (`now()`, a quest's `activatedAt`, or arithmetic on them), never a bare literal (`E-TEMPORAL-ARG`); its CEL type is `int` |
| `now() -> int` | the current narrative-time tick |
| `visited(string) -> bool` | the scene with that `meta.id` has been presented in this save |

Argument lists: one element per relation argument, in order. An element is a
string literal (an entity, enum member or name), a `bool` literal, the
wildcard `"_"`, or `occasion.target`. `"_"` matches anything and is never a
name (identifiers start with a letter, 0.29.0 §1). The checker keeps every
0.31 pattern rule — arity, argument domains, the `countDistinct` column, the
ban on fact calls in rule-body guards (`E-DATALOG-GUARD-FACT`) and
`E-VALIDAT-DERIVED` — now applied to the list form. A relation name is a
string literal; a computed relation name is `E-CEL-PROFILE`.

## 3. Environment declaration

Every execution IR carries `celEnv`, the environment its expressions were
checked against, in CEL type spelling:

```json
{
  "celEnv": {
    "variables": [
      { "name": "run",      "type": "map(string, dyn)" },
      { "name": "user",     "type": "map(string, dyn)" },
      { "name": "occasion", "type": "map(string, dyn)" }
    ],
    "functions": [
      { "name": "holds", "overloads": [ { "params": ["string", "list(dyn)"], "result": "bool" } ] },
      { "name": "count", "overloads": [ { "params": ["string", "list(dyn)"], "result": "int" } ] }
    ]
  }
}
```

`variables` lists exactly the roots the IR's expressions read (state
namespaces `scene`, `run`, `user`, `app`, `quest`, `season`, and engine roots
`entry`, `occasion`, `clock`, `prev` as used). `functions` lists exactly the
host functions they call. Standard operators, `has`, `int()` and `double()`
are not listed; every CEL implementation provides them. An engine registers
these declarations with its CEL library, or ignores them when it walks `expr`.

## 4. Activation and evaluation

**Activation.** An engine evaluates against nested maps built from its state:

- each declared root is present as a map, and every intermediate map on the
  path to a declared slot is present;
- a slot is present iff it has an effective value (write, else seed, else
  default) — so `has(run.tip)` is the 0.31 `isSet(run.tip)`;
- values carry their declared type: `int` as CEL `int`, `double` as `double`,
  `bool`, `string`, enum members as `string`, lists as lists;
- reserved engine paths are always present, with their reserved defaults
  until the engine writes them (dsl 0.5.1 §1.2, 0.24.0 §2): for every quest
  the IR declares, `quest.<id>.state` and `quest.<id>.failedBy` (`"unset"`),
  and for each of its objectives `quest.<id>.objectives.<oid>.done` and
  `.failed` (`false`); for every lore entry, `entry.<id>.read` and
  `entry.<id>.everRead` (`false`).

For a `<match>` whose subject is a bare state path with no effective value, an
arm carrying `is` is definitely not satisfied unless `is` is exactly
`"unset"`; the latter is satisfied. All other arms are evaluated normally.
An evaluation error means the arm is not satisfied.

**Errors.** A condition slot whose evaluation errors (absent key, overflow,
division by zero) is **not satisfied**: an option is not offered, an arm is
not taken, a quest does not start, a reward is not granted. A `::set` value
that errors halts the walk with an error (the engine MUST NOT write a partial
value). CEL's `&&` / `||` already absorb an error when the other operand
decides; nothing else is special-cased.

`lute trace` keeps its three-valued preview (unknown state, unknown time).
That is an authoring tool's view; it is not engine semantics.

## 5. Engine-owned state in the execution IR

`StateEntry` gains `owner: "engine"` for every path declared `owner: engine`
(dsl 0.22.0 §1.2); the key is absent for content-owned paths. Reserved
relations already carry `reserved: true`. Engines MAY refuse an execution IR
whose commands write an engine-owned path or assert / retract a reserved
relation; `lute run` does, with `E-RUN-OWNED-WRITE`, before executing
anything. A checked IR never contains such a write; the refusal guards
hand-built or tampered input.

## 6. Grant identity

Each quest carries an **instance number**: `1` on its first activation in a
save, incremented on every re-instantiation (a `run`-tier reset at `newRun`, a
`rearm`, a `season:<name>`-tier reset at season opening). It is save-wide: no
reset clears it. The engine persists it with quest status.

A grant event (`docs/runtime/quest-lifecycle.md` §Rewards) gains:

```jsonc
{
  "kind": "grant",
  "quest": "<questId>",
  "instance": 3,                 // new
  "objective": "<objectiveId>"?,
  "index": 0,                    // new: position in its owner's rewards, document order
  "reward": { … },
  "onFailed": true?
}
```

`(quest, instance, objective, index)` identifies a grant uniquely within a
save. An engine that settles rewards — locally or through its own server —
deduplicates on it across save / reload, retry and repeatable runs.
The example lists fields, not key order: the `lute run --json` transcript
keeps its stably-sorted keys (`conformance/README.md`).

## 7. Execution IR: naming, versions, stability

The compiled JSON is the **execution IR** in every document, CLI message and
schema title; the Rust type is renamed to match. Its schema file becomes
`schemas/lute-ir-0.32.schema.json`. `docs/architecture.md` opens with the
stability table of D3:

| Surface | Stability |
|---|---|
| execution IR (schema, `irVersion`) | public, versioned |
| CLI commands and their `--json` outputs | public, versioned |
| bridge protocol | public, versioned |
| `lute context` output | public, versioned |
| semantic-model query API | experimental |
| AST, checker and compiler internals | internal |

Each slot's emitted shape is `{ "cel": "<standard CEL>", "expr": <exprNode>,
"authored"?: "<source text when it differs>" }`. `cel` is what a CEL library
evaluates; `expr` is the same expression as JSON for a walker; `authored` is
diagnostic-only and MUST NOT be used to determine match semantics.
For a match arm authored with `is="…"`, the arm additionally carries
`"is": "…"`; `test=` arms omit `is`. On an unset bare-path subject, an `is`
value other than `"unset"` is not satisfied, while `is: "unset"` is satisfied.
Other arms are evaluated normally, and evaluation errors are not satisfied.
Choice / hub option `when` + `expr` and match arm `test` + `expr` become this
object; rule-body guards gain `expr`. `expr` is present on **every** slot.

`exprNode` (full profile):

| shape | meaning |
|---|---|
| `{"int": 3}` / `{"double": 3.5}` / `{"bool": true}` / `{"string": "x"}` | typed literal |
| `{"list": [<node>, …]}` | list literal |
| `{"path": "a.b.c"}` | state read, canonical dotted path (0.30.0 §3) |
| `{"index": <node>, "key": <node>}` | computed index (`user.bond[occasion.target]`) |
| `{"has": "a.b.c"}` | presence |
| `{"op": "!" \| "-", "l": <node>}` | unary |
| `{"op": <sym>, "l": <node>, "r": <node>}` | binary, `<sym>` ∈ `&& \|\| == != < <= > >= + - * / % in` |
| `{"cond": <node>, "then": <node>, "else": <node>}` | ternary |
| `{"call": "<name>", "args": [<node>, …]}` | `int`, `double`, and the host functions of §2 |

## 8. Conformance

The corpus (`conformance/`) gains fixtures for every command kind it does not
yet cover — `background`, `music`, `sfx`, `vfx`, `sprite`, `camera`, `cut`,
`video`, `barrier`, `plugin` (mocked bridge), `accept`, `beat`, `retract` —
plus:

- `grant-instance`: a repeatable quest granting across two runs, showing
  `instance` 1 and 2;
- `grant-replay`: a play script that saves after a grant transition and
  replays the same steps from that save. The transcript emits the identical
  `(quest, instance, objective, index)` key twice; the harness asserts that
  identical transitions produce identical keys and different instances
  produce different keys — the property an engine deduplicates on;
- `owned-write`: a hand-built invalid IR that `lute run` refuses with
  `E-RUN-OWNED-WRITE` (an `invalid/` fixture class);
- `cel-*`: conditions covering every profile form, both numeric types, every
  host function and the error policy.

**Condition equivalence.** `lute run --dump-conditions <file>` writes one
JSON line per condition evaluation during a replay: `cel`, `expr`, the
activation, the facts and visited set it read, and Lute's result. Values in
the activation and the result use the typed encoding of `exprNode` literals,
recursively (`{"int": 3}`, `{"double": 3}`, `{"bool": …}`, `{"string": …}`,
`{"list": [...]}`, `{"map": {...}}`), because a JSON reader cannot tell `3`
from `3.0`. CI replays
the conformance corpus and the differential corpus with the dump enabled, then
re-evaluates every line with:

- `@bufbuild/cel` (Node; harness `conformance/harness/js/`),
- `cel-go` (`cel.dev/cel-go`; harness `conformance/harness/go/`),
- an `expr` walker (JS, in the same harness),

each with the §2 host functions implemented over the dumped facts. Every
result MUST equal Lute's. A mismatch fails CI.

## 9. Diagnostics

| code | severity | |
|---|---|---|
| `E-CEL-PROFILE` | error | extended: Prolog-style fact patterns, `isSet`, `uint`, out-of-range integer literals, computed relation names |
| `E-CEL-TYPE` | error | extended: mixed `int` / `double` arithmetic, comparison or equality; `%` on `double`; `::set` value of the wrong numeric type |
| `E-FACT-QUERY` | error | new name for list-form shape errors: wrong arity, a non-wildcard at the `countDistinct` column, an element outside the admitted forms |
| `E-RUN-OWNED-WRITE` | error (`lute run`) | new: §5 |
| `E-STATE-DECL` | error | extended: `type: number` (removed; use `int` or `double`); a default whose literal type differs from the declared `int` / `double` |

## 10. Decisions

| # | Decision | Why |
|---|---|---|
| D-A | Source conditions are standard CEL; inside a slot only `@def` and `$` remain, expanded at compile time; `is=` and `{{…}}` stay as non-CEL authoring forms | Authors are mostly AI; "write CEL" must be a complete instruction (ADR D12). The four forms are reuse/shorthand with no CEL equivalent, and none reaches the IR as anything but CEL |
| D-B | Fact queries take a relation-name string and an argument list; `"_"` is the wildcard | Ordinary CEL calls every implementation can register; `"_"` can never be a name |
| D-C | `countDistinct` names its column by index | No CEL variables exist to bind; an index is plain data |
| D-D | Presence is `has()` / `in`; `isSet` is removed | Standard CEL; `has()` cannot take an index, so non-identifier keys use `in` |
| D-E | Numeric types are CEL's `int` and `double` everywhere a type is declared; `number` is removed; mixed `int`/`double` operations rejected statically, comparison and equality included — a Lute restriction stricter than cel-spec | "Use CEL types" is a complete instruction for an AI author; no checked condition depends on an implementation's heterogeneous-numeric behavior |
| D-F | Integer literals bounded to ±2^53 | JSON readers in every language keep them exact |
| D-G | Error ⇒ condition not satisfied; error in a `::set` value halts | One deterministic policy; never writes a partial value |
| D-H | Each slot carries `cel` and full-profile `expr`; the engine chooses | ADR D12; CI proves the two agree |
| D-I | Quest instance number, save-wide, plus reward `index` on grants | Idempotent settlement for any engine, packaged or online (ADR D1) |
| D-J | `owner: "engine"` is carried in `StateEntry`; `lute run` refuses owned writes | ADR D1; lets engines and the corpus enforce what the checker already guarantees |
| D-K | Equivalence is proven by re-evaluating dumped condition evaluations | Covers every condition the corpora actually evaluate, with real activations |

## Compatibility and migration

Breaking (D6, clean cutover). Classes: **syntax** (§1.3), **semantic** (`int`,
error policy), **IR** (slot object shape, `exprNode`, `celEnv`, `owner`,
grant fields, schema file).

- `lute fix` rewrites fact patterns, `isSet` and quoted-key presence
  mechanically (§1.3 rows 1–7). The 0.31 forms are syntactically valid CEL
  (`holds(inParty(elena, _))` parses as nested calls), so the rewrite works on
  the parsed CEL tree and does not need the 0.31 checker. It does not retype
  numbers.
- Numeric retyping is reviewed, not mechanical, and covers every numeric
  declaration: state slots, shapes, def results, plugin directive attributes,
  bridge result fields. Every `number` becomes `int` when its default, writes,
  bridge sources and compared literals are all integral, else `double` with
  its integral literals gaining `.0`. A bridge result written into
  a slot must end with the slot's type. `lute check-project` is the oracle: a
  migrated project checks clean.
- Every example, conformance fixture (re-recorded), documentation snippet,
  test string and website page is migrated in the release.
- An engine built against 0.31 must read `cel` / `expr` from the new slot
  object, accept typed literals, register `celEnv`, and read `instance` /
  `index` on grants.
