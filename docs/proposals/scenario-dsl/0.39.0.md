# Lute 0.39.0 — runtime R2

This specification is the normative 0.39.0 contract for phase R2 of ADR D13:
the game-facing **wasm binding** of `lute-runtime` and the TypeScript package
`@lute-lang/runtime`, written in Effect 4 the Effect way, which loads a
compiled bundle, drives the resumable step function and replays a recorded
input log. The event contract keeps its 0.38 wire shape; its schemas become
generated from the Rust types, which are its single definition. The
authoring language and the IR are unchanged.

The words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Scope and version contract

All visible version axes are `0.39.0` (`docs/versioning.md` alignment rule):
toolchain, language, IR, Event, and the npm packages (`@lute-lang/lute`, the
platform packages and the new `@lute-lang/runtime`, released in lockstep).

| Axis | Change in 0.39.0 |
|---|---|
| Language | none — no-op for authors |
| IR | none — stamps only; `schemas/lute-ir-0.39.schema.json` is the 0.38 file renamed |
| Event | wire shapes unchanged; `eventVersion` / `snapshotVersion` `0.39.0`; `schemas/lute-events-0.39.schema.json` and `schemas/lute-snapshot-0.39.schema.json` are **generated** from the Rust types (§3) |
| CLI | every output byte-identical to v0.38.0 except version stamps (§9) |
| npm | new package `@lute-lang/runtime` (§5–§7) |

Out of scope: the C ABI / FFI binding (owner, 2026-10-09: later, not in
0.39); a Node platform layer (Bun is the server-side target, §6.2);
concurrent presentations (R3); `packages/player` (R3); snapshot migration
across content versions; typed IR inside the runtime.

## 2. Layers and terms

- **Runtime** — `crates/lute-runtime`, unchanged in behaviour.
- **Binding** — `crates/lute-runtime-wasm`: a `wasm-bindgen` cdylib over
  `lute-runtime` only. Separate from the playground's `lute-wasm` (checker +
  compiler), per the brief.
- **Contract** — the JSON wire shapes of inputs, outputs, events, awaits,
  rejections, snapshots and the `--events` stream (0.38.0 §5–§7, §10.2).
- **TS runtime** — `packages/runtime` (`@lute-lang/runtime`): Effect services
  over the binding.
- **Host** — the program that embeds the TS runtime (a game, the R3 player,
  a verification server on Bun).

## 3. One contract definition: Rust types, generated schemas

The contract's single definition is the Rust types in `lute-runtime`
(`Input`, `Seed`, `Output`, `Event`, `Await`, `Rejected`, the snapshot) and
`lute-ir` / `lute-manifest` types they embed. Everything else is generated
from them and committed:

1. `schemas/lute-events-0.39.schema.json` and
   `schemas/lute-snapshot-0.39.schema.json` are emitted from the Rust types
   with `schemars` (JSON Schema draft 2020-12). The hand-written 0.38 schema
   files are not carried forward.
2. `packages/runtime/src/generated/Contract.ts` is emitted from those JSON
   Schemas by `packages/runtime/scripts/contract-codegen.ts` as Effect
   `Schema` code (§3.2).
3. CI regenerates both and fails on any difference (`git diff --exit-code`).

### 3.1 Rust side

- `schemars` is an **optional** dependency behind a `json-schema` feature
  of `lute-runtime`, `lute-ir` and `lute-manifest`, off by default. The
  runtime's normal dependency set (0.38.0 §14, CI boundary step) does not
  change; the CI step runs with default features.
- Every contract type derives `JsonSchema` under the feature with the same
  serde attributes it serializes with. Types with hand-written `Serialize` /
  `Deserialize` that the contract reaches (`BeatOnce`, the snapshot's
  `arc_world` field adapter) get hand-written `JsonSchema` impls next to
  their serde impls. The index and `expr` types of `lute-ir` are not part of
  the Event contract (a bundle is the IR's contract) and get no schema here.
- The snapshot becomes a typed struct `Snapshot { snapshot_version, project,
  await_, request, world, continuation }` (today a `json!` literal) with
  `continuation: Option<Continuation>` **omitted when `None`**
  (`skip_serializing_if`), as 0.38 omits the key for an idle, ended or
  halted state; the schema marks it optional. The `--events` stream line
  becomes a typed `StreamLine` enum (`seed`/`output`, `input`/`output`,
  `input`/`rejected`, `seed`/`rejected`). Both live in `lute-runtime`, so
  they have a schema. Their JSON is byte-identical to 0.38 (session
  conformance and the snapshot test pin it, with and without a
  continuation).
- A binary `lute-contract-schema` in `lute-runtime` (feature-gated, `required-features = ["json-schema"]`) writes the two schema files.
- Schema output is deterministic (sorted definitions, stable titles), so
  regeneration is a no-op when nothing changed.

### 3.2 TypeScript side

`contract-codegen.ts` is a Lute-owned emitter (not Effect's best-effort
JSON-Schema translator, which does not accept the contract's `oneOf`
shapes): it reads the generated JSON Schemas, whose shapes are the closed set
`schemars` produces from serde, and emits:

- one exported `Schema` per definition, named as the Rust type;
- `type`-discriminated enums as `Schema.Union([...]).pipe(Schema.toTaggedUnion("type"))`
  with `Schema.Literal` discriminants, so hosts `match` on `type`;
- untagged enums (`PickInput`, `AdvanceBy`) as `Schema.Union` in the Rust
  declaration order (the order serde tries them); adjacently tagged enums
  (`Value`: `kind` / `value`) as tagged structs on `kind`; enums tagged on
  another key (`verdict`, `premise`, §4.1) as `toTaggedUnion(<key>)`;
  string-like enums with custom serde (`BeatOnce`) as their string
  schema with the documented pattern;
- tuples (`Fact = (String, Vec<String>)`, `deferredHandlers` pairs) as
  `Schema.Tuple`, and `uniqueItems` arrays (`BTreeSet`) as
  `Schema.UniqueArray`;
- optional fields as `Schema.optionalKey` (absent, never `undefined`),
  integers as `Schema.Int`, maps as `Schema.Record`, recursion through
  `Schema.suspend`;
- the exported `Type` aliases (`export type Input = typeof Input.Type`).

The emitter fails on any schema shape outside this list, rather than
degrading to `Schema.Json`; only fields the Rust type itself declares as
free JSON (`record`, `commands`, `from`/`to`, payload values) are
`Schema.Json`. Generated code is formatted and carries a do-not-edit header
naming the generator and the source schema.

## 4. Binding — `crates/lute-runtime-wasm`

The binding exposes the 0.38 runtime API over JSON strings and opaque
handles. It holds no host policy.

```ts
// wasm-bindgen surface (generated .d.ts), all strings are contract JSON
export class Program {             // a loaded bundle (Runtime)
  static load(index: string, artifacts: string): LoadResult
  begin(seed: string): StepResult
  step(state: State, input: string): StepResult
  snapshot(state: State): string
  restore(snapshot: string): RestoreResult
  candidates(state: State, occasion: string, target?: string): string
  eligibility(state: State, beat: string, member?: string): string
  clock(state: State): string
  terminal(state: State): boolean
  view(state: State, withFacts: boolean): string
  readonly fingerprint: string
  free(): void
}
export class State { free(): void }  // opaque; cloning is O(1) (Arc world)
export class StepResult { readonly ok: boolean; readonly state?: State; readonly output?: string; readonly rejected?: string }
export class RestoreResult { readonly ok: boolean; readonly state?: State; readonly rejected?: string }
export class LoadResult { readonly ok: boolean; readonly program?: Program; readonly rejected?: string }
```

1. `Program.load` takes `project.index.json` and a JSON object mapping each
   index `artifact` path to its artifact. It never throws: a bundle the
   runtime refuses (`E-RUNTIME-IR-VERSION`, including JSON that is not a
   bundle) is `ok: false` with `rejected` JSON `{ code, message }`.
2. A rejected `step` returns `ok: false`, the **unchanged** state handle and
   `rejected` JSON — the runtime's `(State, Rejected)` (0.38.0 §5.3). A
   rejected `begin` has no state to return (`state` absent).
3. States are immutable values: `step` never invalidates its input handle
   (undo and branching are the host's to keep). Handles are released by
   `free()` and by the JS finalizer (`wasm-bindgen` weak references).
4. A Rust panic is a defect: the published `.wasm` is built with
   `RUSTFLAGS="-C panic=abort"` on the binding's `cargo build` (the
   workspace release profile for native binaries is unchanged); the trap
   reaches the host as an exception, never as a rejection. A test drives a
   deliberately panicking debug-only export and asserts a defect.
5. The crate depends on `lute-runtime`, `serde`, `serde_json` and
   `wasm-bindgen` only, and is checked for `wasm32-unknown-unknown` in CI.
   Every JSON string it returns is canonical (keys sorted, 0.38.0 §9.3).

### 4.1 Query results (new wire shapes)

The read-only queries (0.38.0 §6.4) were Rust-only; the binding returns
their results as JSON, which makes them part of the Event contract from
0.39.0 (in `lute-events-0.39.schema.json`, generated like the rest):

- `Candidate { id, kind, document, priority, verdict, read, also,
  forMember?, rejudged }`;
- `Verdict`: `{ "verdict": "eligible" }` | `{ "verdict": "ineligible",
  "premise": Premise }` | `{ "verdict": "unknown", "why": string }`;
- `Premise`, tagged on `premise`: `spent { once?, reason }`, `after { raw,
  unmet: Atom[], chapters }`, `spentBy { raw }`, `when { raw }`, `gate {
  occasion, raw, reads }`, `terminal { occasion, raw }` — the `premise`
  names are 0.38's `PREMISE_KINDS`; `Atom` is the prerequisite formula's
  leaf (`{visited}` / `{completed}` / `{active}`), `reads` the gate's
  `GuardRead` rows;
- `WorldView { state, facts?, quests, clock? }` with `ClockView`, and
  `ClockAt { day, slot }`.

These Rust types gain `Serialize` / `Deserialize` / `JsonSchema` in
`lute-runtime` (`BeatKind` and `BeatOnce` come from `lute-ir`, `Atom` from
`lute-manifest`); their `Display` texts used by the CLI are unchanged.

## 5. TS runtime — Effect, the Effect way

`packages/runtime` targets **Effect 4** (`effect@4.0.x`, pinned exactly).
It is written as Effect code end to end, not as promise code with Effect
error types:

- dependencies are **services** (`Context.Service`) provided by **Layers**;
  platform differences live only in Layers (§6);
- expected failures are **typed errors** in the error channel
  (`Schema.TaggedError` classes, §5.3); contract violations and binding
  traps are **defects** (`Effect.die`), never typed errors;
- resources (the wasm instance, a loaded program, a session) are **scoped**
  (`Effect.acquireRelease`, `Layer.scoped`) and released on scope close;
- data crossing the boundary is decoded/encoded by the generated `Schema`
  (§3.2), never cast;
- state is held in `SubscriptionRef`, events are published through `PubSub`
  and consumed as `Stream`; step ordering is enforced by a `Semaphore`;
- public operations are `Effect.fn("Lute.<Module>.<name>")` traced
  functions; module imports use `.js` specifiers and the build emits ESM
  plus declarations.

### 5.1 Services

| Service | Shape | Provided by |
|---|---|---|
| `LuteWasm` | the instantiated binding (`Program` constructor) | `LuteWasm.layerFromBytes(bytes)`; the platform `wasm` layers (§6) |
| `BundleSource` | `load: Effect<Bundle, BundleError>` | `BundleSource.directory(path)` (needs `FileSystem`, `Path`), `BundleSource.url(base)` (needs `HttpClient`), `BundleSource.value(bundle)` |
| `LuteRuntime` | `load(bundle): Effect<Program, RuntimeRejection, Scope>` | `LuteRuntime.layer` (needs `LuteWasm`) |
| `Session` | a running playthrough (§5.2) | `Session.layer(options)` (needs `LuteRuntime`, `BundleSource`, `InputLog`) |
| `InputLog` | `reset(start)`, `append(entry)`, `entries` of the recorded `(seed \| snapshot, inputs)` | `InputLog.memory`, `InputLog.keyValueStore(key)` (needs `KeyValueStore`) |

`Program` is a plain value (not a service) wrapping one loaded bundle:

```ts
interface Program {
  readonly fingerprint: string
  readonly begin: (seed: Seed) => Effect.Effect<Step, RuntimeRejection>
  readonly step: (state: RuntimeState, input: Input) => Effect.Effect<Step, RuntimeRejection>
  readonly snapshot: (state: RuntimeState) => Effect.Effect<Snapshot>
  readonly restore: (snapshot: Snapshot) => Effect.Effect<RuntimeState, RuntimeRejection>
  readonly candidates: (state: RuntimeState, occasion: string, target?: string) => Effect.Effect<ReadonlyArray<Candidate>>
  readonly eligibility: (state: RuntimeState, beat: string, member?: string) => Effect.Effect<Option.Option<Candidate>>
  readonly clock: (state: RuntimeState) => Effect.Effect<Option.Option<ClockAt>>
  readonly terminal: (state: RuntimeState) => Effect.Effect<boolean>
  readonly view: (state: RuntimeState, options?: { readonly facts?: boolean }) => Effect.Effect<WorldView>
}
interface Step { readonly state: RuntimeState; readonly output: Output }
```

`RuntimeState` is an opaque branded handle; it is never serialized (the
snapshot is the serialized form).

### 5.2 Session

`Session` is the host-facing driver of one playthrough:

```ts
interface Session {
  readonly fingerprint: string
  readonly started: Output                                         // begin's output; restored: no events, the snapshot's await
  readonly send: (input: Input) => Effect.Effect<Output, RuntimeRejection | InputLogError>
  readonly current: SubscriptionRef.SubscriptionRef<SessionState>   // { state, await }
  readonly events: Stream.Stream<Event>                              // every event of every later output, in order
  readonly awaits: Stream.Stream<Await>                              // each later await
  readonly save: Effect.Effect<Snapshot>
  readonly restore: (snapshot: Snapshot) => Effect.Effect<void, RuntimeRejection | InputLogError>
}
```

1. `send` and `restore` are serialized by a `Semaphore(1)`: two concurrent
   `send`s run in call order; the second sees the first's state.
2. An accepted input is appended to `InputLog` before its events are
   published; a rejected input is neither logged nor applied, and fails
   with its `RuntimeRejection`. `restore` restarts the log at
   `{snapshot}`.
3. `events` and `awaits` are backed by unbounded `PubSub`s; a subscriber
   sees what is published after it subscribed. The output of `begin`
   precedes any subscriber and is `started`. Closing the session's scope
   shuts both down, ending their streams.
4. `Session.layer({ seed })` begins a playthrough; `Session.layer({ snapshot
   })` restores one. The session's scope owns its `Program`.
5. The session adds no game policy: it does not answer awaits, advance
   lines or time anything (R3 player-core does).

### 5.3 Errors

- `RuntimeRejection` is the union of one `Schema.TaggedError` per runtime
  code: `RuntimeBusy` (`E-RUNTIME-BUSY`), `RequestMismatch`
  (`E-RUNTIME-REQUEST`), `OptionUnavailable` (`E-RUNTIME-OPTION`),
  `BridgeShapeMismatch` (`E-RUNTIME-BRIDGE-SHAPE`), `InvalidInput`
  (`E-RUNTIME-INPUT`), `RuntimeHalted` (`E-RUNTIME-HALTED`),
  `IrVersionMismatch` (`E-RUNTIME-IR-VERSION`), `SnapshotProjectMismatch`
  (`E-RUNTIME-SNAPSHOT-PROJECT`), `SnapshotVersionMismatch`
  (`E-RUNTIME-SNAPSHOT-VERSION`), each carrying `code` and `message`. A code
  the TS runtime does not know is a defect (contract drift).
- `BundleError` (`BundleNotFound`, `BundleUnreadable`, `BundleMalformed`,
  each with the `path` it concerns) for `BundleSource`.
- `WasmLoadError` for a binding that cannot be fetched or instantiated.
- `InputLogError` for an input log that cannot be read or written (a
  persistent store's failure); `Session.send` and `restore` carry it.
- Output, snapshot or query JSON that fails the generated `Schema` is a
  defect. `Replay.parseLog` fails with Effect's `SchemaError` on a
  malformed log line (the log is host data, not binding output).

### 5.4 Replay

`Replay.run(program, log): Stream<Output, RuntimeRejection>` drives a
recorded log (`inputs.jsonl` shape: first line `{seed}` or `{snapshot}`,
then `{input}` lines) through `Program` and emits each output. Replaying a
log against the bundle that recorded it reproduces every output; the
conformance test (§8) is this function over the session cases.

## 6. Platforms

### 6.1 Layers

Platform code lives only in the two platform entry points; services and
programs are platform-free. Each entry point exports the same four
layers:

| Layer | Bun (`@lute-lang/runtime/bun`) | Browser (`@lute-lang/runtime/browser`) |
|---|---|---|
| `wasm` | the packaged `.wasm` read with `FileSystem` (`BunServices`) | `wasm(url)`: fetched with `FetchHttpClient` |
| `runtime` | `LuteRuntime.layer` over `wasm` | `runtime(url)` |
| `bundle(where)` | `BundleSource.directory(dir)` over `BunServices` | `BundleSource.url(base)` over `FetchHttpClient` |
| `session(options)` | `Session.layer` over the three above; `log` defaults to `InputLog.memory` | the same; `log: key` keeps the input log in `localStorage` (`inputLog(key)`) |

Both instantiate the binding through `LuteWasm.fromBytes`, so neither uses
a promise API directly.

### 6.2 Package layout

```
@lute-lang/runtime            namespaces Bundle, BundleSource, Contract, Errors, InputLog,
                              LuteRuntime, LuteWasm, Program, Replay, Session
@lute-lang/runtime/bun        wasm, runtime, bundle(dir), session(options)
@lute-lang/runtime/browser    wasm(url), runtime(url), bundle(base), inputLog(key), session(options)
```

`effect`, `@effect/platform-bun` and `@effect/platform-browser` are peer
dependencies pinned to the same exact 4.0.x version (the platform ones
optional). The package ships the `.wasm` and its `wasm-bindgen` JS glue
built in release mode (`wasm-bindgen --target web`, `wasm-opt -O`).

## 7. Distribution

- `@lute-lang/runtime@0.39.0` is published by `.github/workflows/publish.yml`
  in the same lockstep release as the other packages, with provenance.
- The publish workflow builds the binding (`cargo build --release -p
  lute-runtime-wasm --target wasm32-unknown-unknown`, then `wasm-bindgen`
  pinned to the crate's `wasm-bindgen` version) and the package
  (`bun run build`) before `npm publish`.
- Pre-1.0, the TS API follows D6 (clean cutover between minors, no aliases).

## 8. Conformance and tests

Tests use `@effect/vitest` (`it.effect`, `it.layer`) and run **on the Bun
runtime** (`bunx --bun vitest run`).

1. **Replay conformance:** for every `conformance/session/<case>/`, compile
   the case project (`lute compile --all`) to a bundle, load it through
   the Bun `bundle(dir)` and `runtime` layers, replay `inputs.jsonl`
   with `Replay.run`, encode every output with the generated `Schema`, and
   compare its canonical JSON (keys sorted) with `expected.jsonl` byte for
   byte.
2. **Session:** a test per §5.2 rule — serialized `send`, rejected input not
   logged and state unchanged, events/awaits streams in order, save → new
   session restore → same continuation.
3. **Typed rejections:** each runtime code maps to its error class;
   an unknown code dies.
4. **Contract drift:** regenerating schemas and `Contract.ts` is a no-op;
   every line of every session `expected.jsonl` / `inputs.jsonl` decodes
   with the generated `Schema` and re-encodes to the same canonical JSON;
   every snapshot the Rust snapshot test takes validates against the
   generated snapshot schema.
5. **Browser:** one Vitest browser-mode test (Playwright, Chromium) replays
   one session case through the browser `wasm(url)` and
   `BundleSource.url`.
6. Rust: the existing runtime tests stay; target-independent logic of
   `lute-runtime-wasm` (result building, rejection JSON) has native `cargo`
   tests. **Handle semantics** are tested against the built `.wasm` from the
   TS side on Bun (§8.2): a rejected `step` returns a state whose snapshot
   equals the input state's; load and `begin` rejections are values; a
   state handle stays usable after a later `step` from it; `free()` on a
   `Program` makes later use a defect, not undefined behaviour.
7. Contract fixtures: the drift test (§8.4) includes hand-picked lines
   covering every non-trivial shape — `PickInput` (`"pass"` and `{beat}`),
   `AdvanceBy` (`"slot"`, a slot count, `{to: "<slot>"}`, `{to: {weekday,
   slot}}`), `Value` (every `kind`), `World.facts`, `World.deferredHandlers`,
   each `Verdict` / `Premise` of §4.1, and a snapshot with and without
   `continuation`.

## 9. CLI and byte identity

Every CLI output is byte-identical to v0.38.0 except version stamps
(procedure of 0.38.0 §10.4 against a v0.38.0 baseline). `lute play --events`
streams are unchanged except `eventVersion` `0.39.0`; the session
`expected.jsonl` files are regenerated for the stamp only.

## 10. Performance

The `lute-bench` A/B gate stays green. The TS runtime adds a Bun
benchmark (not gated in 0.39): replay of the largest example play through
the binding, reporting per-step latency, so R3 has a baseline.
