# Scenario DSL 0.33.0

Phase 2 of `docs/design/architecture-direction.md` (§5): this release makes
module ownership and engine capability negotiation explicit. Lute still emits
an execution IR; an engine interprets it (D1), and the reference executor is
the semantic oracle and conformance reference, not a Lute VM. This is a clean
cutover before 1.0 (D6). The contract below is deliberately normative and
small: a semantic id names a behavior an engine could plausibly lack, not a
command spelling or a diagnostic.

## 1. Domain modules and evaluation order

A domain module owns its declarations and types, reads and writes, evaluation
point and order, static guarantees, lowering, semantic ids, and conformance
fixtures. The modules are internal and ship in the same binary. A boundary is
valid only when the behavior can be evaluated independently of the neighboring
module; the order below is the explicit cross-module contract.

| module | one-line responsibility | reads / writes and lowering | independent evaluation boundary |
|---|---|---|---|
| **core** | Baseline execution, state tiers, standard CEL, and the wire-level command walk. | Reads typed state, `celEnv`, and engine-owned paths; writes content-owned state through `set`; lowers baseline scene, shot, line, choice, hub, match, jump, branch convergence, and plugin-record wire data. | CEL activation/type/error policy and sequential command traversal are settled before domain events; every engine MUST implement this baseline. |
| **narrative** | Source-facing scene/quest/lore organization, identities, lines, choices, branches, components, and templates. | Reads resolved project ids and state; emits core records and source stamps. It does not add an engine capability: components/templates disappear at compile time. | Expansion and identity allocation finish before execution; the resulting records are core behavior, so narrative has no separate semantic id. |
| **staging** | Presentation directives: background, music, SFX, VFX, sprite, camera, cut, and video. | Reads asset references and timing stamps; requests presentation effects, never semantic state writes. Lowers to the eight staging command kinds. | A presentation record is observed when reached by the walk; selection/lifecycle state is already settled. All presentation obligations are negotiated as one unit. |
| **timeline** | Timeline clip placement and barrier joins. | Reads `Stamp.timeline`, `Stamp.at` and `barrier`; clips start from their placement and a barrier joins them before the walk continues. Lowers timeline placement and `barrier`. Per-command `wait`/`duration`/`delay` belong to the owning command. | Order and joins are observable independently of the presentation payloads on the clips. |
| **quest** | Quest lifecycle, objectives, subquests, accepts, handlers, and reward settlement. | Reads state/facts, occasions, clock positions, and child quest state; writes engine-owned quest/objective status and grant requests. Lowers `quest`, `on`, `accept`, objective/reward declaration fields. | At each settle: activate children, judge objectives/deadlines, fail, complete, cascade, then grant and dispatch lifecycle handlers. Rewards have a separate engine obligation. |
| **time** | Clock positions, cadence spends, seasons, and reset observations. | Reads the declared clock and CEL conditions; writes engine-owned clock/previous-window/cadence state and reset requests. Lowers `clock`, `seasons`, beat cadence fields, and `advances`. | Every crossed clock position is observed before the next lifecycle settle; season false→true and rearm reset observations precede quest evaluation. |
| **occasions** | Occasion gates and beat/entry candidate selection. | Reads `gates`, terminal state, `ProjectIndex.beats`, visited/spent state, targets and priorities; writes presentation selection/spend state. Lowers beat metadata, `gates`, `terminal`, and `outsideRun`. | Gate evaluation precedes candidate selection; selection is priority then project-index order, with target expansion before presentation. |
| **knowledge** | Relation vocabulary, fact deltas and queries, Datalog closure, and temporal fact history. | Reads entity/enum/relation declarations and state; writes fact deltas and derived closure; lowers declarations, `assert`, `retract`, rule data, and CEL fact calls. | A command-ordered fact delta is visible to later commands; closure reaches a stratified least fixpoint before the next condition snapshot. |
| **lore** | Lore entries/beats and first-read disclosure state. | Reads facts, state, target/category/series eligibility; writes ordinary body facts and engine-owned `entry.*.read/everRead`; lowers `entry` and bundle `beat`. | Eligibility precedes body; first-read effects precede read flags. Lore selection is distinct from occasion selection, though entry beats use the occasions module. |

A raise observes clock/cadence changes and quest reset/settle before it is
attempted. For the default (`judge: after`), the order is **candidate selection
and presentation → world handlers → objective judgment → grants and lifecycle
handlers**. For `judge: before`, it is **objective judgment → candidate
selection and presentation → deferred handlers**. This follows
`crates/lute-trace/src/exec/session/step.rs:191-195,330-334`,
`session/lifecycle.rs:101-111,245-257`, and `machine/quest.rs:293-295`.
A command body can assert/retract facts in order; a sibling handler uses the
pre-event snapshot. A timeline barrier pauses the walk but does not reorder a
settle already reached.
`E-SEMANTICS-FIELD` is an internal compiler invariant: use a debug assertion
and the existing internal-error channel, not a registered author diagnostic.

Components and templates are compile-time expansion. Engines never see
`::use`, component parameters, or template definitions and therefore no
semantic id is allocated for them. Plugins remain declarative vocabulary and
typed bridges: their record wire shape is covered by `lute.core/1`, while
plugin behavior and bridge replay remain under the exact `capabilityVersion`
snapshot (D5), not this registry.

## 2. Semantic-id registry

Ids have the form `lute.<module>.<feature>/<major>`, except the baseline
`lute.core/1`. A feature row is one engine-visible behavior; the trigger column
names the exact IR field, command, or value that causes collection. A field in
one row MUST NOT be interpreted through another row.

| id | module / engine-visible behavior | IR feature trigger | spec origin | conformance fixture |
|---|---|---|---|---|

| `lute.staging/1` | Execute presentation requests as a unit, including their asset references and blocking/non-blocking presentation behavior. | Any of `background`, `music`, `sfx`, `vfx`, `sprite`, `camera`, `cut`, `video` and their payload fields. | 0.32.0 §8 command coverage; DSL 0.4–0.8 staging directives. | `staging-all-directives` (add), `staging-video-blocking` (add). |

`lute.core/1` is intentionally broad: it is the minimum engine contract,
not a license to ignore domain declarations. An engine claiming core but not a
required domain id MUST refuse the artifact. Descriptive labels, titles,
source spans, authored text, and plugin-owned fields that do not change
execution are not additional ids.

## 3. Required semantics in the execution IR

The 0.33 execution-IR envelope gains a field immediately after
`capabilityVersion`:

```json
{
  "irVersion": "0.33.0",
  "capabilityVersion": "<exact plugin snapshot>",
  "requiredSemantics": [
    "lute.core/1",
    "lute.knowledge.facts/1",
    "lute.quest.lifecycle/1"
  ]
}
```

`requiredSemantics` is a sorted, duplicate-free array of strings. The compiler
collects it from the lowered IR; authors cannot provide, remove, or reorder
it. A document with executable IR always requires `lute.core/1`; an empty
metadata-only artifact still carries the baseline when it is loadable by an
engine. The project index gains the same `requiredSemantics` field, equal to
the sorted union of all document artifacts, so `check-project`, `play`, and
engines can negotiate before opening a document.

Collection is structural, not text-based:

| lowered feature | collected id |
|---|---|
| Baseline state/CEL/control-flow/scene records or `kind: plugin` | `lute.core/1` |
| Any staging command or staging timing payload | `lute.staging/1` |
| `Stamp.timeline`, `Stamp.at`, or `barrier` | `lute.timeline/1` |
| `quest`/`on`/`accept`, objective lifecycle fields, subquest or engine quest paths | `lute.quest.lifecycle/1` |
| A non-empty quest/objective rewards list or grant-capable reward record | `lute.quest.rewards/1` |
| `clock` or an `advances` value | `lute.time.clock/1` |
| A cadence value (`once`, `share`, `spentBy`) | `lute.time.cadence/1` |
| `seasons`, season tier, or `rearm` | `lute.time.seasons/1` |
| A beat/entry candidate and its selection fields; `prereqEdges.after` | `lute.occasions.selection/1` |
| `gates`, `terminal`, or `outsideRun` | `lute.occasions.gates/1` |
| entities/relations/seeds, `assert`/`retract`, fact CEL calls, or fact metadata (enums count only as relation argument domains; an enum that types state alone is core) | `lute.knowledge.facts/1` |
| `rules`, derived relations, or Datalog body values | `lute.knowledge.rules/1` |
| `validAt`/`now` calls | `lute.knowledge.temporal/1` |
| `entry`/bundle `beat` or lore read state | `lute.lore/1` |
| `prereqEdges.follows` | No semantic id: quest graph metadata is non-semantic. |

The collection pass runs after lowering and before serialization. It follows
references and synthesized fields (for example, a subquest's synthesized
`done` CEL and a scene's resolved beat); it MUST NOT infer ids from an
unresolved source keyword. Plugin records add no semantic id beyond core.
Plugin snapshot handling remains exactly the existing `capabilityVersion`
mechanism: assembly requires the artifact's exact resolved plugin/bridge
snapshot.

## 4. Engine capability matrix

The capability declaration is a YAML file named `lute.engine.yaml`. It belongs
to the engine package or deployment (not the author project), is immutable for
a playback invocation, and is suitable for source control:

```yaml
engine: chat-text-engine
irVersion: "0.33.0"
supportedIds:
  - lute.core/1
  - lute.quest.lifecycle/1
  - lute.quest.rewards/1
  - lute.knowledge.facts/1
  - lute.knowledge.rules/1
  - lute.knowledge.temporal/1
version: "1.4.0"
description: "Text-only chat client: no staging, timeline, or clock"
```

Required fields are `engine` (non-empty display/name key), `irVersion`
(accepted IR version line), and `supportedIds` (unique semantic ids). The
matrix MAY include descriptive `version` and `description`; these do not
participate in negotiation. Unknown fields are ignored. Unknown ids, duplicate
ids, malformed ids, and missing required fields are errors.

`lute run --engine <file>` and `lute play --engine <file>` load the engine
matrix, check the IR exact-minor line, then compare every `requiredSemantics`
entry with `supportedIds`. On a missing id they refuse **before playback**,
with exit code **2** and diagnostic **`E-ENGINE-SEMANTICS`**; no command,
condition, asset, or bridge is executed. An unsupported `irVersion` or
malformed matrix also exits 2 with its own diagnostic.

`lute check --engine <file>` and `lute check-project --engine <file>` perform
author-time negotiation. They report each construct whose lowered feature
requires an id absent from `supportedIds`, with the construct's source span,
semantic id, and engine name. The diagnostic is **`E-CHECK-ENGINE-SEMANTICS`**
(error by default); it is not a playback refusal because no playback occurs.
The project form reports the union and each contributing document/span.

The reference executor's built-in matrix is named `reference` and supports
every id in this registry. Plugin snapshot handling remains the existing exact
`capabilityVersion` check; it is not part of this matrix.


## 5. Versioning and the 0.33 gate

`irVersion` answers how to parse the wire format. `capabilityVersion` is the
exact resolved plugin/bridge snapshot. `requiredSemantics` answers which core
meanings the artifact uses. A build identity answers which exact artifact a
save or test result belongs to. None substitutes for another.

For `0.x` IR, an engine accepts only the exact **major.minor** line. Thus a
0.33 engine accepts `0.33.0`, `0.33.1`, and other `0.33.*` patches, but refuses
`0.32.*` and `0.34.*`; the refusal is the existing exit-2 exact-minor gate,
now performed before semantic negotiation. From 1.0 onward the gate changes
to major-only as specified by `runtime/execution-model.md`.

A semantic id's `/1` is its major meaning line. A module increments to `/2`
only when an engine would need a different evaluation order, state ownership,
observable output, required input, error policy, or lowering—not for a new
optional descriptive field, a new diagnostic, or an additive feature that is
provably ignorable. An id `/2` is collected for artifacts using the changed
behavior; an engine supporting only `/1` refuses those artifacts. The module
keeps `/1` in the registry while old artifacts are still relevant, then marks
it deprecated with a removal release. Before 1.0, D6 permits a clean corpus
cutover, so no compatibility shim or dual lowering is required.

Adding a new id is preferred to silently changing an existing id. A registry
entry MUST include its owning module, behavior, triggers, origin, and fixture
before code claims the id. The reference executor MUST support every current
and non-deprecated id.

## 6. Conformance corpus

The existing corpus is re-recorded for IR 0.33 and gains at least the fixtures
named in §2. The fixture metadata records `requiredSemantics`; a harness check
fails if a fixture exercises a registry trigger without collecting its id.
The corpus covers every command kind, every optional semantic field, every
quest transition and reward grant, every gate/cadence/season edge, all fact
strata and temporal queries, and all staging/timeline behaviors. Invalid
fixtures cover a missing required id, an unsupported IR line, a malformed
matrix, and an owned-state write.

Conformance comparison remains over declared observables: choices offered,
line ids presented, effects requested, quest/knowledge changes, clock and
selection state, and grant identities—not rendering. `lute run`, `play`, and
`check-project` each exercise the negotiation path in the harness.

## 7. Diagnostics

| code | severity | meaning |
|---|---|---|
| `E-ENGINE-MATRIX` | error, exit 2 | Engine YAML is unreadable, malformed, has duplicate/malformed ids, or misses required fields. |
| `E-ENGINE-IR-VERSION` | error, exit 2 | Engine matrix and artifact are outside the pre-1.0 exact-major.minor line. |
| `E-ENGINE-SEMANTICS` | error, exit 2 | Playback engine does not declare one or more artifact `requiredSemantics`; refusal occurs before playback. |
| `E-CHECK-ENGINE-SEMANTICS` | error | Author-time `check`/`check-project` found a construct requiring an id absent from the target engine; includes source span. |
| `E-SEMANTICS-UNKNOWN` | error | Artifact or registry names an id not declared by this IR line. |

## 8. Decisions

| # | Decision | Why |
|---|---|---|
| D-A | Keep nine small internal modules, but make `core` the complete baseline and retain narrative as an ownership module without its own ids. | Narrative records are not independently optional to an engine: every engine must walk scenes, lines, choices, branches, and CEL. Components/templates are erased before execution. |
| D-B | One `lute.staging/1` covers all presentation directives. | A text/chat engine can lack presentation as one capability. Splitting every media command would turn command kinds into ids. Video blocking is still tested by `staging-video-blocking`; it does not have a different state contract. |
| D-C | Keep clock, cadence, and seasons as three time ids. | An engine can implement a clock without cadence spending, or cadence without season windows; each has distinct state and evaluation boundaries. |
| D-G | YAML is the engine matrix format; unsupported semantic ids always refuse. | YAML is reviewable; semantic negotiation cannot silently downgrade required behavior. |
| D-E | Knowledge vocabulary, fact deltas, and CEL fact queries are one facts id; Datalog and temporal history are separate. | Declarations/deltas/query answers share one fact-store obligation. Stratified closure and append-only temporal history have independent algorithms and observables. |
| D-F | Lore read state stays in `lute.lore/1`. | Read flags, first-read disclosure, and entry eligibility form one atomic engine operation; separating them would permit a partial reread implementation. |
| D-H | `requiredSemantics` is compiler-derived in both each artifact and the project index. | Engines cannot be tricked by an author claiming a feature is optional; the project can negotiate before loading all documents. |
| D-I | `lute.core/1` includes plugin record wire handling but plugin meaning remains `capabilityVersion`-negotiated. | There is one plugin representation and no accidental second semantic registry (D5). |
| D-J | 0.33 uses the existing exact-minor pre-1.0 gate. | Semantic negotiation closes the unknown-field hole; it does not change the independent IR parser compatibility rule. |

## 9. Compatibility and migration

This is a breaking IR/toolchain change under D6. The class is **IR and engine
contract**; the source language is unchanged except for any corpus edits
needed to exercise new fixtures. There is no legacy mode, compatibility
window, alias, or runtime fallback.

1. The compiler emits IR 0.33 with sorted `requiredSemantics`; project index
   generation emits the sorted union. Schema and serializers are re-recorded
   in the same change.
2. Every dogfood artifact and conformance fixture is recompiled and
   re-recorded. A fixture that uses a feature listed in the registry but whose
   required id is absent fails the corpus check.
3. Engine integrations add `lute.engine.yaml`, declare the exact 0.33 IR line,
   and list all ids they implement. They must handle refusal before opening a
   playback session and expose source spans for author-time checks.
4. `lute fix`/the release codemod updates committed IR snapshots, project
   indexes, expected diagnostics, and docs snippets. It does not let an author
   hand-edit `requiredSemantics`.
5. A 0.32 engine refuses 0.33 artifacts at the exact-minor gate; a 0.33
   engine refuses a 0.33 artifact whose required id it lacks. The reference
   executor is updated in the same cutover and supports all ids.
6. Plugin manifests and bridge records continue to use the exact
   `capabilityVersion`; no plugin semantic id is invented during migration.

## Appendix B — optional semantic-field mapping

Each optional meaning-changing field in the current IR has one and only one
row below. Descriptive fields (`title`, labels, authored source text) are
listed under their containing behavior so they cannot be mistaken for a new
capability. Fields marked plugin are governed by `capabilityVersion` as well.

| IR owner / optional field(s) | exactly one id | trigger |
|---|---|---|
| `ExecutionIr.entities`, `relations`, `seedFacts` | `lute.knowledge.facts/1` | Relational vocabulary or initial fact store exists. |
