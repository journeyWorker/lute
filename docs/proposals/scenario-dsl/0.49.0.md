# Lute 0.49.0 — correctness, diagnostics and project-model cost

This is the normative 0.49.0 contract. The words **MUST**, **MUST NOT**,
**SHOULD** and **MAY** have their RFC 2119 meanings. Inputs are the 0.49 rows
of the [triage note](../../superpowers/notes/2026-10-23-lute-0.49-dogfood-triage.md)
(issues #155–#188, label `dogfood`), and the owner's decision of 2026-10-23 for
#155/#156: plugin stamps are nested in the IR. Each issue body carries a
reproduction on 0.48.1. There is **no new syntax**. Every item is a bug fix, a
diagnostic, a documentation fix, a cost fix, or (#155/#156) an IR placement
fix. The release is a clean cutover (ADR D6). Where this spec decides
something the triage left open, the decision and its reason are stated where
it applies and are collected in Appendix B.

Release numbering: 0.50 is the behaviour-preserving Rust coding-rules sweep
([`docs/design/rust-coding-rules.md`](../../design/rust-coding-rules.md),
Accepted). Every authoring-extensibility item the triage deferred is 0.51.

## 1. Scope and version contract

This is a minor release. Every public version axis is `0.49.0`: toolchain,
`luteVersion`, `irVersion`, `eventVersion`, `snapshotVersion`, and the seven
npm packages. The contract schemas move to the `0.49` line
(`schemas/lute-{ir,events,snapshot,player-bindings}-0.49.schema.json`).
`bindingsVersion` and the player save/profile format become `"0.49"`.

| Axis | 0.49.0 contract |
|---|---|
| Language | No syntax change. Stricter static semantics: stamps on `::jump`/`::label`/`::clear` (§4.1), entity/provider frontmatter values (§4.3), `start` self-reads and unavoidable start deadlocks (§6.1, §6.2). Looser: blocking bridge result writes are assigned after the call (§5.2), and `'<member>' in <family>` is a presence guard (§5.3). |
| IR | **Shape change:** plugin `stampAttrs` values move from top-level record keys to one nested object `stamps` (§3.1). Content changes: in a `<choice into=…>` arm the synthesized `set` record now comes first (§5.1), and a line may carry `timing.wait` (§4.2). Schema `-0.49`. |
| Event / snapshot | **New optional field `stamps`** (omitted when empty; separate from `attrs`, never merged): on plugin event records (normal and halted), on the bridge await (`Await::Bridge`) and the snapshot/request that carries it (§3.1). Staging records keep their core-field `attrs` whitelist. Every other shape is unchanged. |
| Plugin manifests | `list`/`map`/`record` attribute types are refused (§3.2). Reward targets gain `forbidden: true` (§3.3). Core-stamp name reservation unchanged. |
| CLI | `constraints` report `0.49.0.constraints` (§6.3–§6.5). `constraints` fails on an invalid manifest (§6.5). `lint <DIR>` discovery (§7.4). `asset-exists` attribute selectors (§7.3). |
| Runtime / player | Every reader of plugin stamps reads `stamps` (§3.1). The reference scheduler honours `timing.wait: false` on a line (§4.2). |
| Cost | The project vocabulary is built once per project and shared by every document (§9). |
| Report ids | `0.49.0.constraints` is new. Every other report keeps its id. |

Outside the deltas listed in §13, every output captured by
`scripts/cli-snapshot.py` MUST be byte-identical to 0.48.1 after version-stamp
normalization. The §9 work MUST NOT add a delta of its own.

## 2. Shared rules

- **Regression test first.** Every behaviour change has a regression test
  that fails on the base: the 0.48.1 binary, or the change reverted.
- **Diagnostic shape.** A new code is registered in
  `crates/lute-cli/src/codes/registry.rs` and `crates/lute-check/src/evidence.rs`.
  Registry text is blessed with `LUTE_BLESS_DIAGNOSTICS=1`, and the generated
  website page (EN) and its KO translation follow. **No hint may recommend a
  spelling the checker rejects**, positive or negative (§5.3).
- **No silent drop.** An authored value that the toolchain does not carry into
  the artifact is a diagnostic at the value.
- **Documentation.** Every changed behaviour is documented in the same change:
  website EN + KO and `llms-full.txt`. Historical records are never rewritten.
- **New Rust code** follows `docs/design/rust-coding-rules.md` (Accepted).
  Existing code is not swept; that is 0.50.

## 3. Plugin assembly and the stamp placement

### 3.1 Plugin stamps are nested (#155, #156)

**Boundary at 0.48.1.**
- `Stamp` (`crates/lute-compile/src/ir.rs:433-460`) is flattened into every
  *stamped* command: the commands for which `Command::stamp_mut`
  (`ir.rs:1894-1921`) returns `Some`. `Jump` and `Barrier` have no stamp.
- `TaggedRecord` (`ir.rs:575-581`) writes `kind`/`family` first, then the
  command's own fields, then the flattened stamp.
- `Stamp.extra` (`ir.rs:458-459`, filled by `lower.rs:66,258,735-764`) is
  flattened beside the command's own keys. A plugin stamp named like a key of
  its carrier (`tag`, `speaker`, `text`, `kind`, `assetId` on staging
  commands, `label` on `vfx`, `name` on `sequence`, `id` on `hub`, …)
  therefore writes that key twice.

**0.49.**
- `Stamp.extra` serializes as **one nested object, `stamps`**, on the stamped
  command: `"stamps": { "<attr>": <value>, … }`. The object is omitted when
  empty, so a record with no plugin stamp is byte-identical to 0.48.1.
- It stays last within the stamp, after `timing`, `provenance`, `source`.
- Why the name `stamps`: it is the manifest's own noun (`stampAttrs`), and it
  is not a property of any `$defs/cmd*` record in
  `schemas/lute-ir-0.48.schema.json` (verified: no command or nested record
  has a `stamps` key). It names exactly what it holds.
- Plugin stamp names can no longer collide with a record key. There is **no**
  schema-derived reserved list.
- The core stamp members stay flattened: `timing` (object), `provenance`,
  `source`. So does the authoring reservation of `at`, `duration`, `delay`,
  `wait`, `timeline`, `timing`, `provenance`, `source`:
  `E-PLUGIN-RESERVED-STAMP-ATTR`, unchanged (`assemble.rs:240,341,462`).
  `at`/`duration`/`delay`/`wait`/`timeline` remain authoring keys of the core
  stamp that compile into `timing`. `provenance`/`source`/`timing` remain
  flattened record keys. A plugin stamp named like one of them would be
  ambiguous to the author even though it no longer collides in JSON.
- The JSON value of each entry is unchanged: typed by the declaring plugin's
  `AttrDecl` (`attr_json_typed`).

**Schema.**
- `schemas/lute-ir-0.49.schema.json` gains `$defs/stamps`:
  `{ "type": "object", "additionalProperties": true, "description": "plugin stampAttrs values (plugin §14.1), keyed by attribute name" }`.
- It adds `"stamps": { "$ref": "#/$defs/stamps" }` to every stamped `cmd*`
  def, and drops the "further top-level keys" wording. `cmdJump` is unchanged.

**Consumers migrated in this release (D6).** Every place that writes or
reads plugin stamps today:

**Regression tests** (#155, #156, from the issue repros):
- A passthrough `::signal{value="puzzle" tag="warmup"}` compiles to
  `"tag": "signal"` and `"stamps": {"tag": "warmup"}`.
- Lines with `speaker`/`text`/`kind` stamps keep their own keys and carry the
  stamps under `stamps`.
- Each compiled JSON text is checked for duplicate keys with a strict parser
  (`object_pairs_hook` that fails on a repeat).

### 3.2 Attribute types no value can satisfy (#176)

- A directive attribute or a `stampAttrs` entry whose top-level type is
  `list`, `map` or `record` MUST be refused at plugin load with
  **`E-PLUGIN-INVALID-DIRECTIVE`** (a new `ManifestError` variant,
  `crates/lute-manifest/src/validate.rs:155,268`). The message names the
  attribute:

  > directive `::tagged` declares attribute `tags` as `list<enum[a, b]>`; an attribute value is written as one scalar (string, number, bool, an enum or entity member, a provider or asset id), so no `.lute` value can satisfy a `list`, `map` or `record` — declare it `string` and parse it in the host, or split it into one attribute per field

  For a stamp it reads `stamp attribute `tags``.
- Plugin `options:`, frontmatter keys, state shapes and bridge results keep
  these types, because YAML can write them.
- An authoring spelling for structured attribute values is a **0.51** design
  item.

### 3.3 `target: { forbidden: true }` (#168)

- A reward kind's `target:` admits `forbidden: true`
  (`schema/vocabulary.rs:212`). It is exclusive with `provider`/`entity`/
  `required`. A combination is a `SchemaError::RewardTarget`:
  `a reward kind's `target:` takes `forbidden: true` alone — a kind that takes
  no target cannot also name an id space or require one`.
  `schemas/lute.plugin.json` gains the key.
- A `<reward>` of such a kind with `target=` is **`E-REWARD-TARGET`**, error,
  at `target=`: `<reward kind="COINS"> takes no `target=`: its reward kind
  declares `target: { forbidden: true }` — remove the attribute`.
- `RewardTarget`'s `Debug` prints `forbidden` only when it is set, so existing
  `capabilitySnapshot` hashes are unchanged.

## 4. Directives, lines and frontmatter

### 4.1 Stamps on directives that emit no stamped record (#157)

- `::jump` lowers to an unstamped `jump` record (`ir.rs:1920`).
- `::label` lowers to no record (`lower.rs:385`).
- `::clear` lowers to no record of its own. It may inject one actor exit per
  character on stage, and none on an empty stage (`lower.rs:386-392`,
  `stage.rs:248-269`).
- On 0.48.1, jump and label accept plugin stamps and `wait`/`duration`/`delay`
  and drop them (verified: `::jump{to="x" wait="true"}` checks clean and
  compiles without `wait`). `::clear` already refuses every attribute,
  including timing keys (`directives.rs:231-240,264-269`). It still admits
  plugin stamps through the `stampAttrs` fallback (`directives.rs:249`) and
  drops them.

**0.49.**
- The set of directives with **no stamp carrier** is the constant
  `lute_manifest::core::UNSTAMPED_DIRECTIVES = [JUMP_DIRECTIVE, LABEL_DIRECTIVE, CLEAR_DIRECTIVE]`.
- On these directives a plugin stamp attribute and a core timing key are
  **`E-UNKNOWN-ATTR`**, error, at the attribute. Messages:
  - `::jump`: `` `::jump` does not carry `cue`: it compiles to a `jump` record that has no stamp — put the attribute on the line or directive before it ``
  - `::label`: `` `::label` does not carry `cue`: it compiles to no record — put the attribute on the line or directive after it ``
  - `::clear`: the existing `::clear` message ("it takes no attributes; every character on stage exits with its own exit") now also covers stamp attributes.
- `::clear` does not hand stamps to its injected exits. Reason: whether an exit
  exists depends on stage state, so an empty stage would still drop the value.
  A stamp belongs on the `::actor{exit}` the author writes.
- The check runs before the `universal_timing_decl` and `stampAttrs` fallbacks
  (`directives.rs:235`, `:249`).
- Test (exhaustive, consistent with the set): every core directive that is
  *not* in `UNSTAMPED_DIRECTIVES`, lowered with one plugin stamp, yields a
  record whose `stamps` carries it. For every directive in the set, the
  checker reports `E-UNKNOWN-ATTR`. The lists are taken from
  `lute_manifest::core`'s core directive list, so a new core directive must
  be classified.

### 4.2 `wait` on a content line (#174)

- A content line admits `wait` (bool) through `universal_timing_decl("wait")`.
  `delay`/`duration` on a line stay `E-UNKNOWN-ATTR`.
  The attribute list in `content_line.rs:157` includes `wait`.
- It compiles to the line record's `timing.wait`. Absent stays omitted.
- Meaning: a line always waits for its own advance. `wait` says whether the
  staging cues that follow it, up to the next line, wait for the line.
  `true` or absent means they wait (0.48.1). `false` means they start while
  the line is presented. The next line still waits for the previous one.
- Reference player (`packages/player/src/scheduler/index.ts:107`): a line cue
  with `timing.wait === false` is forked. The scheduler joins it before the
  next `line` cue, before a `presentation` cue (it clears the dialogue window,
  so it is not a staging cue that may overlap the line; orchestrator
  clarification 2026-10-24 after the F2p review), and before the batch
  settles. `timingOf` (`cues/index.ts:54`) already defaults a line to
  `wait: true`.

### 4.3 Reference-typed frontmatter keys (#178)

- A plugin frontmatter key typed `entity`, `domain`, `enumFromOption`,
  `providerRef` or `assetKind`, whose value is a YAML string, is checked in
  `fold_env` by `check_attr_value` (`directives.rs:507`) with owner
  `frontmatter`. Example:
  `` `mirra` is not a member of entity kind `person` (attribute `lead` of `frontmatter`) — did you mean `mira`? `` (`E-BAD-ENUM`).
  It replaces the static `type_accepts` check at `meta/frontmatter.rs:389`.
- A `list` of such a type checks each element. A non-string value stays
  `E-FRONTMATTER-SCHEMA`.
- Span: `meta_key_span(meta, key)`.

## 5. Data flow

### 5.1 `into=` writes before the arm body (#158)

- `<choice into="run.p" [value=…]>` means `::set{run.p = <value>}` placed
  **first** in the arm: `normalize::synth_into` (`normalize.rs:1418`)
  inserts at index 0.
- Definite assignment applies the record write before walking the arm
  (`defassign.rs:671,715`), so a read of `run.p` inside the arm is assigned.
  The test asserting the opposite (`defassign.rs:~1800`) is inverted.
- `E-INTO-*` and "the arm already `::set`s" (`choice_record.rs:123`) are
  unchanged.
- New conformance fixture `choice-into-jump`: an arm ending in `::jump`.
- `language/choices-and-hubs` (EN/KO): "`into=` writes first".

### 5.2 Blocking bridge results are definite assignments (#179)

- A **blocking bridge call** is a plugin directive call whose declaration has
  ≥1 `effects.writes` entry valued `fromBridgeResult`, and whose effective
  core `wait` is not `false`. Reason: the runtime applies the answer before
  the next command (`machine/plugin.rs:149-162`), and `validate.rs:325`
  treats exactly such a call as blocking. `wait` is the language's blocking
  key (`bridge-protocol.md:78-88`).
- Definite assignment (`defassign.rs:441`) adds each resolved result path of
  an unguarded blocking call to `available`/`writes` after the call. Paths
  are resolved with `permissions::resolve_path` (`fold.rs:1256`). Under
  `when=`, the writes enter only the discarded fork.
- The #179 scene checks clean. Removing an arm then reports
  `E-NONEXHAUSTIVE`. With `wait="false"` the read stays `E-MAYBE-UNSET`.
- `plugins/bridge` "Sync semantics" (EN/KO): result writes are assigned after
  the call. A fire-and-continue host option (a plugin `sync="false"`) MUST be
  written `wait="false"`. Lute does not read `sync`.

### 5.3 One presence guard for every `per:` member (#180)

**The guard.**
- `'<member>' in <family>`, where the family is a `per:` family and the
  member a string literal, is admitted (extending the exemption at
  `cel_resolve/state.rs:130`).
- It is a presence guard of `<family>.<member>`: `cel_paths::proved_if`
  (`cel_paths.rs:381`) proves it when the test is true, and its negation when
  false, exactly as for `has()`.
- A literal that is not a member gets the diagnostic a read of
  `<family>["<literal>"]` gets.
- Runtime and `lute trace` evaluate it as `has()` of the dotted member. A test
  traces a set member and an unset member.

**One presence formatter.** Every message that names a presence test goes
through one function, `presence_test(path, negated)`. It returns:
- `has(<path>)` / `!has(<path>)` when every segment after the root is a CEL
  identifier;
- `'<m>' in <family>` / `!('<m>' in <family>)` when the last segment is a
  `per:` member that is not an identifier;
- for any other path with a non-identifier segment (not a family member),
  no guard spelling exists, so the message omits the guard advice and names
  only the `after:`/`default:` remedies.

**Sites.**
- `envelope.rs:578,586,611` (`E-STATE-MAYBE-UNAVAILABLE`).
- `reachability/diagnostics.rs:313-319` (`unset_literal_message`). Its
  subject comes normalized from `select_path` (`decide.rs:1287-1322`); for
  #180's family it renders `!('look-around' in user.stepRank)`.
- `cast/presence.rs:479` (`!isSet(s)` rendering). It goes through the
  formatter wherever its text reaches a message.
- `cel_resolve/state.rs:155` (entity-indexed `E-UNDECLARED`): adds ``, or `'<member>' in {path}` to test whether a member is set``.
- `profile.rs:332` (`isset_hint`): already names accepted forms; text
  unchanged.
- `has(<family>["<m>"])` stays `E-CEL-PARSE`. The message gains the hint
  ``— `has()` takes a field; for a member that is not an identifier write `'<m>' in <family>` ``.

**Tests.** Each form in #180, plus the negative `== 'unset'` case. Every hint
text is fed back into `check` and MUST be accepted.

## 6. Connectivity and constraints

### 6.1 Start cycles and unavoidable deadlocks (#181)

On 0.48.1 a synthesized `start`/`accept` edge is added only if it closes no
cycle (`graph_assembly.rs:225-240`). The closing edge is silently dropped.

**Graph.** Every `start` anchor edge enters `edges` and `edge_kinds`, so
`lute scenario` draws every edge.

**Anchors keep their AND/OR structure** (`graph_sources.rs:27-43`,
`graph_assembly.rs:398-429`). Each top-level `&&` conjunct of a `start` is
one anchor, and must hold. An anchor's sources are alternatives: one
suffices.

**Deadlock** is the least fixed point of *can-start*:
1. Every node that is not a quest-with-anchors is decided by the existing
   reachability analysis. Scenes, beats and entries are routable unless they
   are unreachable or on an `after` cycle. An unanchored quest can start.
2. A quest can start when **every** anchor has **some** source that can
   start (a quest), or is routable (another node).
3. Iterate from "nothing can start" until stable.

A quest that can never start while being on a cycle of anchor edges is
**deadlocked**.

**Diagnostic.** Each deadlocked quest Q whose anchors do not read Q itself
(that case is §6.2) is **`E-QUEST-START-CYCLE`** (new), error, project-wide,
at Q's `start`. There is one per strongly connected set, reported at its
least quest. The path is the shortest anchor cycle through it, rendered like
`E-CONN-CYCLE`:

> quest start cycle: quest(cycA) -> quest(cycB) -> quest(cycA) — each `start` waits for the next and no source outside the cycle starts any of them; start one of them from something outside the cycle, or grant it with `accept="external"`

**Not a deadlock.** A cycle with an external entry: A starts when B is
active; B starts when A is active **or** `visited("entry")`; scene `entry` is
routable. B can start, so A can start: no diagnostic. Both edges are still
drawn, and the nodes are layered after `entry` where Kahn's order allows.
Otherwise they are listed unlayered as today.

**Output.**
- Graph text: deadlocked quests are printed in a line
  `(unlayered -- part of a start cycle, E-QUEST-START-CYCLE): …`.
  JSON/DOT carry `startCycle`.
- `reach` for a deadlocked quest, or one downstream only through deadlocked
  sources, is `Unknown — this quest's `start` waits on a start cycle
  (E-QUEST-START-CYCLE): <path>; it can never start under your declared
  routes. [unknown]`.
- An `after`-cycle's text is unchanged.

**Regressions.**
- The #181 two-node deadlock: error, both edges, the unlayered line, the reach
  reason.
- The externally entered cycle: no error, both edges drawn, `reach` not
  `Unknown` by reason of the cycle.

Accept anchors keep their 0.48.1 handling (§14).

### 6.2 A `start` that reads its own quest (#182)

- Any read of `quest.<own id>.*` in `start` is **`E-QUEST-START-SELF`**
  (new), error, per document, at `start`:

  > `start` of quest `locked` reads its own state (`quest.locked.state`), which has no value before the quest starts, so this condition can never start it as intended; a quest that only the host grants is written `accept="external"` without a `start`

- An anchoring self-read becomes a self-source. `graph_sources.rs:80` drops
  the `id != own` exclusion. In §6.1's fixed point a self-source never helps,
  so an anchor with only the self-source makes Q deadlocked. Q and its
  dependents are not `Reachable`. Reachability MUST NOT report `Reachable`
  for a quest that cannot start.
- A self-only deadlock is reported as `E-QUEST-START-SELF`, not as
  `E-QUEST-START-CYCLE`.

### 6.3 One reachability claim (#184)

- `lute_model::scenario::reach_claim(scenario, node) -> (verdict, evidence, reason)`
  moves from `cmd_scenario/reach.rs:54-157`. Both `scenario reach` and
  `constraints` (`constraints.rs:154`) use it.
- An unanchored quest is `reachable holds [proven]`, with reason
  `unanchored: available from the start of play`.

### 6.4 Verdict reasons and counterexamples (#184, #185)

- `ConstraintResult` (`constraints.rs:19`) gains `subject: String` and
  `reason: String`.
- `counterexamples` and `related` (`E-CONSTRAINT-VIOLATED`) are non-empty only
  on `violated`.
- `reason` is set on every verdict:
  - holds: the evidence, e.g. `connectivity proves reachable`;
  - unknown: e.g. `no play or test script was run (--all-scripts / --script)`,
    `2 script(s) ran; none completed quest `first``, or the reach-claim reason.
- `add_script_witnesses` (`cmd_constraints.rs:213`) reads `subject`.
- Text output prints `  reason: …` under `unknown`.
- Report `0.49.0.constraints`:

```json
{"command": "constraints", "schemaVersion": "0.49.0.constraints", "ok": true, "diagnostics": [],
 "constraints": [{"root": ".", "id": "first-reachable", "kind": "reachable", "subject": "quest:first",
   "verdict": "holds", "evidence": "proven", "reason": "unanchored: available from the start of play",
   "scope": null, "declaration": {…}, "witnesses": [], "counterexamples": [], "related": [], "declarationErrors": []}]}
```

- `E-CONSTRAINT-DECL` entries move from `constraints` (`cmd_constraints.rs:96`)
  to `diagnostics`.

### 6.5 `constraints` on an invalid manifest (#183)

- A root whose `lute.project.yaml` exists but does not load
  (`cmd_constraints.rs:86-88` skips it) MUST print the manifest diagnostics
  whole-project `check` prints and exit `1`.
- JSON: `ok: false`, `constraints: []`, the diagnostics in `diagnostics`
  (`path` = manifest).
- A declared constraint is never omitted without a diagnostic.

## 7. Project checks and tooling

### 7.1 Single-file check names the skipped class (#175)

- Document-mode `check <FILE>…` and the LSP add **`W-PROJECT-CHECK-SKIPPED`**
  (new, severity **info**), once per distinct quest id per document. It fires
  at the first read of `quest.<id>.*` whose id the document and its imports

### 9.2 Architecture

Rule (ADR D14, §9.9): project-wide information is built once per project. A
document holds only its own overlay.

The coding-rules note's prohibition on a consuming-tree Fold/HIR does not
cover this. Environment folding (`fold_env`) is environment construction, and
nothing here introduces a HIR.

**`ProjectBase`** (lute-check, `Arc`) is memoized in `InputCache` by
`(root, profile, plugins, permission profile, providers dir)`:

```rust
pub struct ProjectBase {
    pub snapshot: Arc<CapabilitySnapshot>,   // permissions / identity flags applied once
    pub providers: Arc<ProviderSet>,
    pub defaults: Arc<MetaDefaults>,
    pub plugin_origins: Arc<PluginOrigins>,
}
```

**`ProjectVocab`** (lute-check, `Arc`) is built once per `(ProjectBase,
(base dir, uses, extends))` and memoized in `ImportCache`. It holds:
- `imports: Arc<SchemaImports>` (diagnostics at `AT_PLACEHOLDER`);
- `domains`;
- `rel: Arc<RelVocab>`, with rule checks, stratification and guard expansion
  done;
- `state: BaseState` (imported decls, `per:` families §9.3, `prev.run`,
  clock decls, ranges and members, season mirrors, `domain_members`);
- base def tables with each def's state-read set and def-reference set;
- clock, terminal, seasons, declared cast, `kind_order`;
- `ir_state` (§9.4);
- **base summaries** (R5): the default-carrying paths, the engine-owned paths,
  and the domain names read, each aggregated once;
- `base_diags: Vec<(Stage, Diagnostic)>`.

**`CheckInput`**:

```rust
pub struct CheckInput {
    pub text: String, pub uri: String, pub mode: Mode,
    pub base: Arc<ProjectBase>,
    pub vocab: Arc<ProjectVocab>,
    pub components: Arc<ComponentSet>,
    pub import_diags: Vec<Diagnostic>,
    pub component_diags: Vec<Diagnostic>,
}
impl CheckInput { pub fn new(text, uri, mode, sources: InputSources) -> Self; }
```

**`DocOverlay`** (in `FoldedEnv`) holds only this document's data:
- its inline `entities`/`enums`/`relations`/`facts`/`rules`/`add`/`defs`/`state`;
- its implicit decls (branch/hub, quest/entry reserved paths, payload,
  `occasion.target`, plugin slots), plus `prev.run` of its own decls;
- its diagnostics;
- the set of **changed names**: domains/kinds whose members or labels it
  changes (inline `enums:`/`entities:`/`add:`), imported state paths whose
  decl or default it refines (`extends` refinement, `fold.rs:175-201`), and
  defs it declares.

**Lookup.** `Env.state` becomes `StateView { base, overlay }`:
- `get`/`contains`/`string_members`/`is_faulty`/`domain_members` look in the
  overlay, then the base;
- `iter()`/`range()` merge both in byte order, the overlay winning;
- `.decls` is no longer reachable from outside lute-check.

`Env.rel_vocab`/`Env.domains` are `Arc`s shared with the vocab when the
overlay changes no relational/domain/def name. Otherwise they are a merged
copy built by the 0.48.1 code (7 of 629 corpus documents).

**Invariant (byte identity).** `fold_env` returns exactly what 0.48.1
returned: the observable `FoldedEnv`, and both diagnostic streams in order.
Base stages splice their diagnostics at their 0.48.1 position, re-anchored to
`doc.meta.span`. A base result is reused only when **none of its inputs is in
the overlay's changed set**; otherwise that stage runs on overlay ∪ base for
this document:

| Stage | Inputs | Reused when | Else |
|---|---|---|---|
| `merge_domains`, `build_rel_vocab`, `check_rules`, stratification, `expand_rule_guards` | domains, kinds, relations, rules, defs | no changed domain/kind/relation/rule/def | 0.48.1 full merge |
| `resolve_domains`, `check_domain_types` (R1) | each state path's domain | the path's domain is unchanged | recompute `domain_members` and diagnostics for every base path whose domain is changed, plus all overlay paths |
| `check_value_prefix` | path set | base pairs always | pairs touching an overlay path via `range` |
| clock stage: decls, ranges, slot members, reserved decls (R2) | clock decls, the clock's state paths and their **effective** defaults, domains, invalid-state metadata | the document declares no clock, refines none of the clock's paths or defaults (incl. `extends` refinement), changes no domain they use, and adds no invalid row | re-run `check_clock` and the derived decls on effective state |
| seasons, `prev.run` | state decls | the path is not refined | per path |
| `settle_defs` on imported defs (R3) | def bodies, def→def references, state reads | the document declares **no inline def** and no state path any imported def reads | re-settle **all** imported defs for this document |
| `member_envs` | — | — | overlay deltas over shared `Arc`s |

R3 decision: re-settle all imported defs whenever inline defs exist, rather
than tracking a reverse dependency closure. Reason: `settle_defs` infers
iteratively over the merged table (`def_decl.rs:231-270`), so a closure
would duplicate its logic. Documents with inline defs are rare, and the
conservative rule is trivially equivalent.

**Equivalence tests** (reference path = forced full merge):
- the corpus;
- (R1) imported `person: [a]` + `run.person: { entity: person }` + inline
  `add: person [b]`;
- (R2) an `extends` default refinement of a clock day path, and an inline
  `clock:`;
- (R3) imported `inner: "1"`, `outer: "@inner"`, inline `inner` as a string;
- an inline enum overriding an imported one;
- the generator.

**Consumers that aggregate state** (R5):
- `envelope.rs:470-477`, `lute-model/src/scenario.rs:58-62`,
  `reconcile.rs:650-659` and `project_check/domains.rs:80-85` read the base
  summaries once per vocab identity and apply the overlay;
- `scenario.rs` stops cloning `RelVocab`;
- none of them iterates `StateView` over base families.

**Callers.** `fold_env(doc, input)` keeps its signature for `check_parsed`,
`lute-compile`, LSP, `lute-wasm` (base built by `CheckInput::new`), trace,
context, loc, scaffold and differential.

### 9.3 `per:` families without per-member materialization

- A `per: <kind>` family is stored once: `Family { path, kind, decl, per-member defaults }`.
- `get` splits off the member and checks it against the merged kinds (sub-kind
  members implied).
- `iter()` expands lazily in byte order. Fault diagnostics
  (`meta/diagnostics.rs:563`) are unchanged. `DeclOrigins.state` keeps family
  keys.
- Memory is O(families + members). Base summaries (§9.2) record families as
  families.

### 9.4 Shared IR state table

- `ExecutionIr.state` becomes `StateTable { base: Arc<BaseStateEntries>, own: Vec<StateEntry> }`.
- It serializes to the 0.48.1 array byte for byte. `iter()` serves in-memory
  readers.
- A document whose overlay changes a domain, kind or label that a base entry
  renders gets an `own`-only table.
- `member_domain` becomes `Arc<[String]>`.

### 9.6 One model per command, including witnesses (R4)

- A witness-bearing command (`constraints` with `--script`/`--all-scripts`,
  `context` with scripts) builds **one** model per root with
  `ModelOptions { mode: Ci, compile: true, … }`. The **selected model
  itself**, not only the memo, is threaded to every consumer that today
  builds its own:
  - the constraints evaluation;
  - `PlayProject::compile` (`cmd_constraints.rs:241,265`,
    `play/project.rs:139-145`);
  - `testcmd::Shared::for_tests` (`runner.rs:344-351`, today
    `Ci, compile:false`);
  - `reconciled_project_results_in` (`runner.rs:405-418`), together with the
    gate helper it calls (`lute-model/src/gate.rs:106-124`, today a second
    `compile:false` model);
  - `run_test_for_constraint` / `run_test_for_context` (`runner.rs:510-535`);
  - `cmd_context`'s witness route.
- **Analysis-only checks are kept.** Compilation appends compile-gate
  diagnostics and can flip `document.check.ok` (`project.rs:282-323`). Test
  witnesses read the reconciled checks and `model_doc.check`
  (`runner.rs:1157-1174`). So `ModelDocument` keeps the reconciled
  analysis-only `CheckResult` separately from the compile-gated one, and every
  consumer that read a `compile:false` model reads the analysis-only result.
- **Why the options do not change the report.** The constraints report does
  carry diagnostics. `E-CONSTRAINT-DECL` declaration errors are printed and
  set `failed` (`cmd_constraints.rs:89-104,141-155`), and are computed in
  `constraints.rs:68-79` from `validate_when` over `folded`. The argument that
  the switch is safe is about the inputs:
  - no checker code branches on `Mode::Author` vs `Mode::Ci` in what the
    constraints read (the implementer greps `Mode::` and records each branch;
    any branch reached by these inputs blocks the switch);
  - `folded`, the documents, the scenario and the objective slots are settled
    before compilation runs, and compilation does not mutate them.
- **Equality test, before the switch.** On the corpus and on the #183–#185
  fixtures, compare under both option sets: every `ConstraintResult` field
  (verdict, evidence, subject, reason, witnesses, counterexamples, related,
  declaration errors), the report's `diagnostics`, and, for runs with scripts,
  each executed witness outcome and refusal diagnostic for both
  `.play.yaml` and `.test.yaml`.
- `scenario` (`reach`/`envelope`/`knowledge`) and `impact --node` build one
  model.
- `ModelMemo::builds()` counts underlying `ProjectModel::build_*` calls.
- No cross-process cache and no partial analysis (ADR §6). A partial one-node
  query is an item for 0.51 or later, if §9.8 still calls for it.

### 9.8 Performance acceptance

`scripts/vocab-grid.py` drives the #173 generator. The generator is ported
into `lute-bench generate-vocab` and produces output identical to the issue's
`gen.py`. The script measures CPU and peak RSS of `lute` with `/usr/bin/time`
(`-l` on macOS, `-v` on Linux). `--gate` requires:

1. The marginal CPU per document, `(CPU(400 scenes) − CPU(100 scenes)) / 300`,
   at 4 800 slots ≤ **1.5×** the same at 150 slots. HEAD: 17×.
2. The marginal RSS per document at 4 800 slots ≤ **1.5×** the same at 150
   slots (HEAD 19×). Also, peak RSS(400 scenes, 4 800 slots) ≤ **2×** peak
   RSS(400 scenes, 150 slots) (HEAD 18×).
3. On 20 scenes + 400 quests at 2 400 slots, `scenario`,
   `scenario reach --node quest:q0200` and `constraints` each stay ≤ **1.1×**
   `check --project` in CPU and RSS.
4. `constraints --all-scripts` on a project with one `.play.yaml` and two
   `.test.yaml` witnesses performs one underlying `ProjectModel` build
   (`ModelMemo::builds() == 1`, a Rust test). Its executed witness outcomes
   and refusal diagnostics, for both script extensions, equal those of 0.48.1.

The gate is shown failing on 0.48.1 and runs in CI (`test.yml`). The benchmark
corpus gains a `vocab` tier (20 scenes + 200 quests, 2 400 slots, generated
in-process into `$TMPDIR`), in `bench-ab.py` and the A/B gate. A base without
the tier is skipped (`supports_tier`).
