# Lute 0.47.0 — Brinewake round 2

This is the normative 0.47.0 contract. The words **MUST**, **MUST NOT**,
**SHOULD** and **MAY** have their RFC 2119 meaning. Inputs are issues
#118–#129 from the second round of the Brinewake dogfood; conservative
choices are listed in the decision note ("Orchestrator choices") and
Appendix A.

## 1. Scope and version contract

Every public version axis is `0.47.0`: toolchain, `luteVersion`, `irVersion`,
`eventVersion`, `snapshotVersion`, the seven npm packages and the generated
contracts. The contract schemas move to the `0.47` line
(`schemas/lute-{ir,events,snapshot,player-bindings}-0.47.schema.json`), project
files use `bindingsVersion: "0.47"`, and the player's save and profile format
version is `"0.47"`.

| Axis | 0.47.0 contract |
|---|---|
| Language | No syntax change. A `<choice id="prompt">` in a branch or hub that has `prompt=` is `E-CHOICE-DUP` (§3.1). |
| IR | A branch (`choice` command) or hub with a prompt gains `promptLineId` and, when a locale bundle translates it, `promptTexts` (§3.1). The project index gains optional `contentLang` (§2.2). Records without a prompt, and indexes of projects without `defaults.contentLang`, are byte-identical apart from stamps. |
| Event / snapshot | Shapes unchanged; stamps and schema line only. |
| Bindings | `ui.title.text`, `background`/`music` optional (§4.1); `bindingsVersion` is checked and fixed (§4.2). |
| Runtime | Unchanged. |
| Player core | Locale follows the settings (§2.2), lineage across reloads (§2.3), no confirm leaving an ended run (§2.5). |
| player-web | Ending screens from the real view entry (§2.1), translated text (§2.2), CG layer (§2.4), title heading (§2.6). |
| CLI | `loc` exports/imports prompts and source hashes, `W-L10N-STALE` (§3); bindings version diagnostics and `lute fix` (§4.2); `patch` multi-edit fix and format guarantee (§5.1); `schema` describes inputs (§5.2); `diff git:` subtree (§5.3). |
| Docs | Patch request on the website (§5.2), cross-run model (§2.3), CG layer order (§2.4), tutorial (§7). |

## 2. Player and player-web

### 2.1 Ending screens read the view entry (#118)

`program.view(state).state[path]` is a runtime `Value` (`{ kind, value }`,
`Contract.WorldView.state: Record<string, Value>`), never a bare string.
player-web's ending resolver MUST type the view it reads as the runtime's
`WorldView` and select a screen only when the entry at `ui.ended.by` is
`{ kind: "str", value: <member> }` and `screens` maps `<member>`. Every other
entry (absent, another kind, an unmapped member) and a failing query show the
stock screen, as in 0.46.0 §5.4. The unit test that mocked a string entry is
replaced by tests over a real runtime view (§6).

### 2.2 Translated text follows the locale setting (#122)

- The project index gains optional `contentLang`: the manifest's
  `defaults.contentLang` (omitted when the manifest has none). The **source
  locale** of a loaded bundle is `index.contentLang`, else the `contentLang`
  of the first artifact (in `index.documents` order) whose meta declares one,
  else `"en"`. Its **compiled locales** are the keys of every
  `texts`/`promptTexts` map in its artifacts. The Settings model's `locales`
  MUST be the source locale followed by the compiled locales (sorted, without
  duplicates).
- A new profile starts with the source locale. A saved locale the bundle does
  not carry (e.g. a 0.46 profile's `"en"` for an `en-US` project) reads source
  text, and Settings shows the source locale selected.
- For the current `settings.locale`, every text surface reads the record's
  translation and falls back to the source text: the dialogue line
  (`texts[locale]`, `localeSegments[locale]`), the backlog, choice and hub
  option labels (`texts[locale]`) and branch/hub prompts
  (`promptTexts[locale]`, §3.1). Changing the locale (`setSettings`) applies
  to the next text shown and to the backlog when it is shown; it does not
  require a new game. Speaker names are not localized.
- Mechanism: the cue factory takes the locale per call —
  `fromOutput(output, readLines, locale)` and `choiceView(await, locale)`
  (custom factories and `cueFactory` wrappers receive it too); the director
  passes the current `settings.locale`. A backlog entry keeps the record's
  `texts` (and `localeSegments` when present) next to its source `text`; the
  saved backlog keeps them; the Backlog screen resolves the text for the
  current locale when shown.
- No `MountOptions` or `LutePlayer.make` option is added: the locale is a
  setting.

### 2.3 Lineage: a second play-through survives a reload (#121)

- The **lineage** is the runtime snapshot (`Session.save`) taken when the
  session presents an `ended` output. It holds the user tier (`user.*`,
  user-tier facts, `once: user` spends, read marks of entries) and the ended
  run's values that `newRun` turns into `prev.run.*`.
- The player MUST store the latest lineage in its profile store (the
  profile record gains an optional `lineage`), replacing the previous one,
  and write it immediately (not debounced like settings).
- `begin` (New game) MUST send `newRun` when the session's current state is
  at `ended` — including a session restored from an ended snapshot; it never
  presents `started` again for it.
- In a player started without `snapshot`/`session` (the default or a host
  `seed`), New game that cannot send `newRun` where the session waits (an
  untouched session, or a run abandoned through the menu) restores the
  profile's lineage, if any, instead of the start point, then sends `newRun`;
  the input log then starts with `{ snapshot: <lineage> }`. A host `seed` is
  not used on New game while a lineage exists. If the runtime refuses to
  restore the lineage, New game starts from the start point as without one
  and the lineage is dropped.
- `profileVersion` is `"0.47"`. A profile of an older version keeps its read
  marks and settings and has no lineage; it is never refused.
- The player docs (website `player/custom-hosts.md` EN/KO and
  `docs/player/architecture.md`) MUST describe this as the cross-run model:
  which tiers survive a reload and when the lineage is written and used.

### 2.4 CG above the stage (#127)

player-web's stage layers are, bottom to top: `background`, `camera`
(actors), `cg`, `video`, `dialogue`, `choice`, `overlay`, `transition`. A
`::cg` therefore covers the actors and stays under the dialogue window and
UI. The order is documented on the player-web page (website
`player/getting-started.md` EN/KO) and `docs/player/web-architecture.md`.

### 2.5 Leaving an ended run (#129)

`toTitle` while the flow is `ended` goes to the title without the
discard-progress confirm. The in-game menu (`overlay: menu`) and the `error`
flow keep their confirm.

### 2.6 Title heading (#120)

The title screen's heading is `ui.title.text` when bound (§4.1); otherwise
the title screen draws no heading. player-web never draws the literal
`"Lute"` as a game title.

## 3. Localization

### 3.1 Localizable prompts (#125, part)

- A branch or hub with `prompt=` gets the prompt lineId
  `{prefix}.{branchOrHubId}.prompt`, where `{prefix}` is the one its options'
  lineIds use (`{prefix}.{branchOrHubId}.{choiceId}`). The compiler writes it
  as `promptLineId` on the `choice`/`hub` command; `prompt` stays the source
  string.
- `lute loc export` emits a row `kind: "prompt"` per prompt (`lineId`, `key`
  `{branchOrHubId}.prompt`, `text`, `file`, `line`, `source`), in document
  order before the options of that branch or hub; `loc import` accepts it;
  `compile --locales` writes `promptTexts: { <locale>: <text> }` (omitted when
  empty) and reports `W-L10N-MISSING` for a missing prompt translation like
  for an option label.
- Because the prompt id and an option id share the namespace, a
  `<choice id="prompt">` inside a branch or hub that has `prompt=` is
  `E-CHOICE-DUP` ("choice id `prompt` is the lineId of this branch's prompt;
  rename the choice"); the code's registry summary covers both cases. Without
  `prompt=` the id stays legal.
- The IR schema's `cmdChoice`/`cmdHub` document both fields; the TS player
  reads `promptTexts` (§2.2).

### 3.2 Stale translations (#128)

- Every export row carries `sourceHash`: `"sha256:<hex>"` (lowercase hex) of
  the record's **plain** source text as the compiler emits it (UTF-8): a line's
  text with inline delimiters, attributes and escapes removed (`LineCmd.text`),
  an option's `text`, a prompt's `prompt`. Translators do not change it. In CSV
  it is the last column (after `sourceLine`).
- `lute loc import` stores it per entry and locale in the locale bundle. The
  bundle moves to `schemaVersion: 2`, always written by `loc import`:
  `{ schemaVersion, locales, entries: { lineId: { locale: text } },
  sourceHashes: { lineId: { locale: "sha256:…" } } }` in that key order;
  `sourceHashes` is always present and holds only the pairs whose row carried
  a hash (`{}` when none). A second import of the same rows is byte-identical.
  A `schemaVersion: 1` bundle is still read (no hashes, no stale check).
- `compile --locales` (single and `--all`) reports `W-L10N-STALE` for every
  merged `(lineId, locale)` whose stored hash differs from the hash of the
  record's current source text; the message names the lineId and the locale
  and says to re-export (`lute loc export`) and update the translation. The
  translation is still merged. The warning is deniable like every warning
  (`--deny W-L10N-STALE`, `--deny-warnings`).
- `lute loc` docs (website `tooling/cli.md`, `language/dialogue-and-cast.md`
  EN/KO) describe `sourceHash`, the bundle shape and the warning.

Not developed: per-document locale scope; `W-L10N-MISSING` stays project-wide.

## 4. Bindings

### 4.1 `ui.title.text` (#120)

`ui.title` gains optional `text` (a non-empty string): the game's name drawn as
the title heading (§2.6). `background` and `music` become optional (their
resolution rules are unchanged, 0.46 §3.1); `ui.title`, when written, MUST
have at least one of `text`, `background`, `music` (`E-BINDING-SHAPE`).
player-web draws no title backdrop / plays no title music when the key is
absent. The JSON schema and the generated TS `Bindings` type follow.

### 4.2 `bindingsVersion` (#119)

The rule follows `luteVersion` (0.41.1 #76). `bindingsVersion` is
`"MAJOR.MINOR"`; the **toolchain line** is the toolchain version's
`MAJOR.MINOR`.

- `check-project` reports `W-BINDINGS-VERSION-STALE` at the
  `bindingsVersion` value when it differs from the toolchain line: older —
  "update it to `"<line>"`" (`lute fix` does it); newer — "upgrade the
  toolchain; do not downgrade the stamp"; not `MAJOR.MINOR` — restamp advice.
- A section newer than the declared line is `E-BINDINGS-VERSION` at that key,
  naming the section and the line it needs (`` `ui.ended` needs
  bindingsVersion "0.46" or newer; this file declares "0.45" ``). The section
  lines: `vfx.<name>` with `effect: custom` — 0.41; `volumes` — 0.42;
  `ui.ended` — 0.46; `ui.title.text` — 0.47. Every other section is part of
  the 0.40 line. Not checked when the declared value is not `MAJOR.MINOR`.
- `lute fix` raises an older `MAJOR.MINOR` `bindingsVersion` in
  `player.bindings.yaml` to the toolchain line, byte-preserving the rest; a
  newer or malformed value is left alone.
- `player/bindings.md` (website EN/KO, `docs/player/bindings.md`) states the
  rule and the section table.

## 5. Tooling

### 5.1 `lute patch` with several edits in one file (#123)

- All edits of one file are resolved against the original text and applied in
  descending offset order; the touched regions handed to the formatter MUST be
  the edited spans in the written text (each region shifted by the net growth
  of the edits before it), and the formatter's output MUST be spliced back per
  region (not as one block by line number). Both 0.46 defects are fixed
  (`map_offset` inside an edit; the single-block line splice); the refusal
  below is a guard, not the fix.
- Before reporting `accepted`, every written `.lute` file whose text edits
  were region-formatted MUST satisfy: if its original bytes were `fmt --check`
  clean, the written bytes are clean; otherwise formatting the touched regions
  of the written bytes changes nothing. (`createFile` and YAML are formatted
  whole and always satisfy it.) A violation refuses the patch (nothing
  written) with `E-PATCH-FORMAT` naming the file, with the exit code of the
  other `E-PATCH-*` refusals.
- Regression: two `replaceNode` edits in one file (the second after a line
  that the first edit's growth would shift) leave the file `fmt --check`
  clean and change only the two nodes.

### 5.2 The patch request is documented (#124)

- `lute schema <command>` gains `inputs`: one entry per structured input,
  `{ argument, kind: "request", format: "json", fields, ops, preserve,
  nodeKinds }` for `patch`'s `PATCH`; an empty list for every other command.
  `fields`: `base`, `targets`, `edits`, `preserve` with `required` and
  `type`; `ops`: each edit op with its fields; `preserve`: each key with its
  type; `nodeKinds`: every node-key kind, with whether a patch may target it.
  A test MUST round-trip a request built from the description through the
  patch request parser, so the description cannot drift. The schema report's
  `schemaVersion` becomes `0.47.0.schema`.
- The website `tooling/ai-harness.md` (EN/KO) documents the request shape,
  the ops, `preserve` keys, the node-key kinds and where keys come from
  (`lute context --json` `affected[].key`); `tooling/cli.md` links it.

### 5.3 `lute diff git:<rev> <path>` compares the subtree (#126)

When the other side is a directory inside the current work tree, the git
side is materialized from that subtree only (`git -C <toplevel> archive <rev>
-- <its toplevel-relative path>`) and rooted at it, so both sides compare the
same project root. A symlink, submodule or special file outside it does not
matter; inside it it is still refused. Otherwise (the other side outside the
repository, or both sides `git:`) the cwd tree is archived as in 0.46.

## 6. Testing rule

Every player / player-web behaviour of this release is tested against real
runtime output — a compiled fixture project through `@lute-lang/runtime`, or
the player-web browser/e2e suite over a compiled bundle and the wasm runtime —
not a hand-written view or record. A test of a touched feature that mocks
runtime data is replaced. Browser/e2e assertions read what player-web drew
(Pixi display objects or pixels), not presenter models. Required: an ending
screen per member of the demo's multi-ending case (§2.1); a locale switch
mid-run and on a new game showing a named line, a choice and a prompt in
Korean (§2.2); run 1 finished, reload, New game shows a `prev.run`-gated line
and a `user.*` value from run 1 (§2.3); a CG covering an actor (screenshot,
§2.4); the ended screen's Back to title reaching the title with no confirm
(§2.5); the bound title text and no heading when unbound (§2.6).

## 7. Documentation

The `build-a-town-game` tutorial (EN/KO) drops its leftover "0.45 pattern"
wording and gains a second play-through step (`user.*`, `prev.run`, lineage
across reloads) and a localization step (`lute loc export/import`,
`compile --locales`, the Settings locale), over `docs/examples/quayside`.

## 8. Not developed

Per-document locale scope for partial translations (#125 second half). A
project display name (no manifest field exists; §2.6 draws no heading
instead). Out of scope: canon#70, #77, #78, C ABI, `--fields`, `--agent`,
patch batch input, per-report JSON Schema, dynamic bark line queries.

## Appendix A — decisions

See the decision note's "Orchestrator choices": source locale from
`contentLang`; lineage replaces a `seed`; prompt id `.prompt` with
`E-CHOICE-DUP`; per-locale source hashes and bundle v2; bindings section
table; no project display name; `E-PATCH-FORMAT` and the "clean if it was
clean" rule; `inputs` on every schema description.
