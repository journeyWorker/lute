# Lute 0.53.1 — patch: the npm launcher replaces itself

This is the normative 0.53.1 contract, a patch release on the 0.53 contract
line. The words **MUST**, **MUST NOT**, **SHOULD** and **MAY** have their RFC
2119 meanings. The input is
[PR #243](https://github.com/journeyWorker/lute/pull/243): the npm launcher
ran the native binary as a child process and kept a ~39 MB Node process
resident for the whole run, which for `lute-lsp` is the editor session.

## 1. Scope and version contract

The release changes the `@lute-lang/lute` launcher (`packages/cli`) only. It
MUST NOT change:

- syntax or static semantics: no diagnostic is added, removed or reworded;
- the execution IR, the Event or snapshot shapes, or their contents;
- the output, exit code or `--explain` text of any native command;
- the runtime or player packages, apart from version stamps.

The toolchain earns the release; every other axis is a content no-op, as in
0.49.1.

| Axis | 0.53.1 rule |
|---|---|
| Toolchain | The Cargo workspace, `lute version` and all seven npm packages stamp `0.53.1`. The launcher change of §2. |
| Language | `luteVersion` stamps become `0.53.1`; no syntax or semantic change. Language `0.53.1` is byte-for-byte `0.53.0` semantics. |
| IR | `irVersion` stamps become `0.53.1`; no field or meaning change. |
| Event/snapshot | Stamps become `0.53.1`; shapes and schema bodies unchanged. |
| Player bindings | `bindingsVersion` stays `"0.53"`; schema body and generated TypeScript unchanged. |
| Player | The save and profile format stays `"0.53"`. A bundle recompiled with 0.53.1 stamps gets a new project fingerprint (the snapshot hashes `irVersion`), as any recompile does. |
| Report ids | `0.48.0.check`, `0.48.0.schema`, `0.53.0.fix`, … keep their names: a report id names the release that introduced the report. |

The release MUST NOT alter the bodies of
`schemas/lute-{ir,events,snapshot,player-bindings}-0.53.schema.json`,
`packages/runtime/src/generated/**` or `packages/player/src/bindings/schema.ts`.
Engines and hosts gated on `0.53` need no gate change.

## 2. The launcher replaces itself with the native binary

The `lute` and `lute-lsp` entry points of `@lute-lang/lute` resolve the native
binary as before (workspace build, platform package, `LUTE_LAUNCHER_BINARY`
and the fork-bomb guard are unchanged). Then:

- On macOS and Linux, under Node 26.1 or newer or under Bun, the launcher
  MUST replace its own process with the binary through `process.execve`,
  passing the arguments and the environment unchanged. No Node process stays
  resident, the process id stays the one the caller started, and signals
  reach the binary directly. Node's `ExperimentalWarning` for `execve` MUST
  NOT reach stderr (an LSP server's stderr lands in the editor's log).
- On Windows, under Node older than 26.1 (where a failed `execve(2)` aborts
  the process instead of throwing, nodejs/node#62878), or when `execve`
  throws, the launcher MUST run the binary as a child process and exit with
  its exit status, as 0.53.0 did.

`packages/cli/test/launcher.test.ts` runs the built launcher under `node`
with stub binaries: `lute` and `lute-lsp` replace the launcher (the binary's
parent is the caller), stdin reaches `lute-lsp` with nothing written to
stderr, a binary the system cannot execute falls back to the child path
instead of aborting, and without `process.execve` the binary runs as a child
and keeps its exit status. The `launcher-typecheck` job of
`.github/workflows/test.yml` runs it under Node 26.

## 3. Breaking changes and migration

| Class (D6) | Change | Migration |
|---|---|---|
| Release | All axes `0.53.1`; schemas, `bindingsVersion` and the save format stay on `0.53`. | None. `lute fix` raises `luteVersion` stamps. |

There are no Syntax, Semantic, IR, Plugin, CLI-output or Player rows.
