# Lute Scenario DSL — 0.10.2: No Language Change

- **Version:** 0.10.2
- **Status:** Draft (**alignment-only** revision of 0.10.1)
- **Date:** 2026-08-12
- **Scope:** no grammar production, no static-semantic rule, no `decide()`
  (§5.1 R1–R5) change, no Closure change. Language 0.10.2 is **byte-for-byte
  0.10.1 semantics** (which was itself byte-for-byte 0.10.0) for every
  document. The single change on this axis is the version stamp:
  `LUTE_LANG_VERSION` advances from `"0.10.1"` to `"0.10.2"` in the release
  that aligns the toolchain and the IR at the same number. **Unlike 0.10.1,
  the IR axis is NOT a no-op this time** — see §2.

## 1. Why this file exists

Same reason as [`0.10.1.md`](0.10.1.md), which set the precedent this file
repeats: [`docs/versioning.md`](../../versioning.md) commits to re-aligning
every visible axis number on every release, and separately commits the
language axis's history to this stack. A language version with no entry here
is a hole a reader resolving `luteVersion: "0.10.2"` cannot see into — nothing
distinguishes "this revision changed nothing" from "the revision was never
written down." `0.7.0` and `0.10.1` both closed that hole for their own
release; this is the third.

## 2. What changes on the language axis — nothing; what changes on the IR axis — for real

`LUTE_LANG_VERSION` → `"0.10.2"`. Nothing else on this axis. Every diagnostic
code, grammar production, admission rule, vocabulary slot, and `decide()`
result is exactly as `0.10.1` (== `0.10.0`) defined it. Historical citations of
the form "dsl 0.10.0 §N" / "dsl 0.10.1 §N" continue to name the proposal that
defined the rule and are **not** rewritten.

**The IR axis is different from `0.10.1`'s story.** `0.10.1`'s IR advance was
shape-identical to `0.10.0` — this one is not. `SceneMeta`/`QuestMeta` (the
compiled artifact's `meta` envelope) gain a `plugin` field: a checker-validated,
plugin-owned top-level frontmatter key folded into the artifact, key → JSON
value, skipped entirely when a document authors none (plugin-system
[`0.0.4.md`](../plugin-system/0.0.4.md) §2). This is a **real, additive**
artifact-shape change, and the compiler and checker code that implement it
landed on `main` before this release commit — this file is the version-axis
record of that landing, not its specification (0.0.4 is).

**Still no engine-side edit required.** The runtime contract gates on
`irVersion` **major.minor**
([`docs/runtime/execution-model.md`](../../runtime/execution-model.md#version-negotiation)),
and `0.10.2` shares `0.10` with `0.10.0`/`0.10.1`, so an engine that already
accepts a `0.10.0`/`0.10.1` artifact accepts a `0.10.2` artifact with **no
edit** — the new field is purely additive and a permissive JSON reader ignores
an object key it does not ask for. `schemas/lute-ir-0.10.schema.json` is **not**
renamed and its `$id` does not move (the schema file tracks the gated
`major.minor`, per the same `0.7.0`-set precedent `0.10.1.md` §2 restates); it
DOES gain content this release — `sceneMeta`/`questMeta` each gain a `plugin`
property, so an engine validating strictly against that schema now admits the
new field instead of rejecting it under `additionalProperties: false`.

## 3. What the release does change

One item, entirely toolchain/IR, per [`docs/versioning.md`](../../versioning.md)'s
"which bump when" ("change the compiled artifact's shape → IR, and toolchain"):

- Plugin-owned, checker-validated frontmatter now reaches the compiled
  artifact (`meta.plugin`) instead of being discarded at compile time. See
  [`CHANGELOG.md`](../../../CHANGELOG.md) for the full entry and
  [`plugin-system/0.0.4.md`](../plugin-system/0.0.4.md) for the normative
  membership rule, the value-conversion path, and the defense-in-depth
  re-validation `lute-compile` performs regardless of which `CheckResult` gate
  produced the artifact.

Nothing else. No fix, no CLI flag, no new diagnostic on the language axis.

## 4. Stale-stamp remedy

Because the language version advances, a document carrying
`luteVersion: "0.10.1"` (or `"0.10.0"`) now lags `LUTE_LANG_VERSION` and fires
**`W-LUTE-VERSION-STALE`** (dsl 0.6.1 §3) — the stamp is still never validated
against capabilities (D13 stands; the warning is a freshness signal only). The
remedy is mechanical — restamp to `luteVersion: "0.10.2"` — and because
`0.10.2` is byte-for-byte `0.10.1`/`0.10.0` semantics, an already-clean
document restamped to `0.10.2` checks clean with no other edit.

## 5. Non-goals

- No grammar or semantic change, on the language axis.
- No new diagnostic code, checker- or compiler-side. `meta.plugin`'s
  membership rule reuses `E-FRONTMATTER-SCHEMA` (plugin-system 0.0.2 §3)
  verbatim — a value the checker already rejects still cannot reach the
  artifact.
- No change to the axis-independence policy, and no change to
  `capabilityVersion`: the plugin's declared frontmatter key/schema pair was
  already part of the capability snapshot hash (plugin-system 0.0.1 §6.8);
  only whether the compiler *acts* on that already-hashed declaration changed.
