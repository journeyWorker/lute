# Lute Scenario DSL — 0.13.0: Code Lock

- **Version:** 0.13.0
- **Status:** Draft
- **Date:** 2026-08-26
- **Scope:** the language axis gains ONE new universal frontmatter key,
  `codesLocked:`, and the §12 identity contract gains the tooling override it
  guards against: `lute tag --force`, a drafting-time renumber of every
  content line's `code`. No grammar production changes, no new directive, no
  new diagnostic code on the checker surface — `codesLocked` is a declaration
  the CHECKER admits and the TAG TOOL reads.
- **IR:** unaffected on both the shape and content axes — `codesLocked` never
  reaches the artifact (it is a source-side editing guard, not scene data),
  and a renumbered draft compiles through the same addressing pass as any
  other document. `capabilityVersion` is likewise unaffected: no `lute.core`
  export changes. Separately, this release relaxes the runtime
  version-negotiation gate to MAJOR-only — a runtime-contract change recorded
  in [`execution-model.md`](../../runtime/execution-model.md#version-negotiation)
  and the changelog, not a language change.
- **Companion (toolchain, same release):** the lint system — `lute lint`,
  `lute.lint.yaml`, and the plugin `lints` export
  ([`plugin-system/0.0.5.md`](../plugin-system/0.0.5.md)) — is advisory
  tooling with no language surface, recorded in the changelog rather than
  here.
- **Design record:**
  [`docs/superpowers/specs/2026-08-26-lute-lint-system-design.md`](../../superpowers/specs/2026-08-26-lute-lint-system-design.md)
  covers the release's lint half; this file is the design record for the
  language half, per the `0.12.0` precedent.

## 1. Motivation

§12's identity contract is assign-once: a content line's `code` is generated
once, persisted into source, and never recomputed, because everything
downstream — the `lineId` localization join (`loc export`/`import`,
`compile --locales`) and the `voiceKey` a voice pipeline attaches to — keys
on it. `lute tag` therefore back-fills only, stepping above the scope's
existing per-speaker maximum, and never touches an authored code.

That is exactly right after publication and mildly hostile before it. While
a scene is still being drafted, insertions, deletions, and reorderings leave
the back-filled sequence gappy and out of document order (`0050` before
`0010`, holes where cut lines used to be). Nothing is *wrong* — identity does
not require order — but authors read these codes constantly while writing,
and a clean monotone sequence is legibility the assign-once rule was never
meant to forbid. The rule exists to protect published identity; a draft has
none to protect.

`0.13.0` resolves the tension by naming the boundary instead of weakening
the rule: a document is renumberable until it declares it is not.

## 2. `codesLocked:` — a universal frontmatter key

`codesLocked:` joins the universal frontmatter key set (valid on every
document kind — scene, quest, schema, component; `lute-check`
`meta.rs::UNIVERSAL_KEYS`). Declaring it marks the document's codes as
published identity.

Interpretation is deliberately FAIL-CLOSED and total:

- key absent → unlocked;
- `codesLocked: false` (the YAML boolean, exactly) → unlocked;
- **any other value** — `true`, a string (`"no"`, `"yes"`), a number, a map —
  → locked.

A typo can therefore only ever over-protect. A guard whose misspelled value
silently unlocked a shipped episode would be worse than no guard; a guard
that over-triggers costs one frontmatter edit.

The key is a source-side declaration, not scene data: it does not fold into
state, does not reach the compiled artifact, and does not participate in any
capability or identity derivation. The checker's only obligation is
admission (it is not `E-META-UNKNOWN-KEY`); its only reader is tooling.

## 3. `lute tag --force` — the guarded renumber

`lute tag --force` rewrites EVERY content line's `code` in clean document
order: each identity scope (the scene; each `<quest>` — the same scopes
`lute tag` and `E-DUP-LINE-CODE` already use, dsl 0.2.0 §7) restarts a
per-speaker counter and assigns `0010`, `0020`, … step 10 — the same shape
the back-fill pass produces, so a force-renumbered document is
indistinguishable from one tagged fresh.

Rules, all inherited from the plain pass unless stated:

- **Locked documents refuse.** A `codesLocked:` declaration (per §2's
  fail-closed reading) exits 1 with the reason; nothing is rewritten.
- **Broken documents refuse.** Any Error-severity parse diagnostic exits 1;
  a possibly-corrupt node stream is never spliced.
- **Non-string codes are skipped.** A `code=@ref` is intentional identity
  outside the numeric sequence; it is left verbatim, consumes no counter
  slot, and is counted in the report.
- **Idempotent.** A second `--force` run is byte-identical and reports
  "codes already in order".
- **Plain `lute tag` is unchanged, and stays available under lock.**
  Back-filling a NEW line's code cannot sever any existing join — a fresh
  code keys a `lineId` no translation has ever seen — so the lock gates only
  the rewriting pass.

## 4. What this does NOT change

- §12's assign-once contract for published documents is strengthened, not
  relaxed: the normative statement becomes "never recomputed **once
  published**", and publication now has a machine-readable marker instead of
  a convention.
- `lineId`/`voiceKey` derivation, the addressing pass, `loc export/import`,
  and `compile --locales` are byte-for-byte unaffected. A document that
  never runs `--force` behaves identically to `0.12.0` in every tool.
- No migration: `0.12.0` documents are valid `0.13.0` documents unchanged
  (the new key is optional, and no existing key changed meaning).
