# Lute Scenario DSL — 0.23.0: Author overviews and time

- **Version:** 0.23.0
- **Status:** Released (0.23.0, 2026-09-25)
- **Date:** 2026-09-25
- **Scope:** what a writer needs to see and say once a story is selected by
  occasions rather than read top to bottom: overviews of who can say what
  when (a beat ladder, a calendar, a knowledge map), windows and missed
  events, composing a routine with an event, several beats in one file, cast
  and reward vocabularies, and a sharper condition decider.
- **Evidence:** dogfood triage T2-8, T2-11, T2-12, T2-13, T2-14, T1-17, T2-7
  (`prev`), T2-9 (`cast`), T3-13, T3-16, T3-18.
- **IR:** additive — `IndexBeat.when` / `title` and kind `bundle`,
  `ObjectiveEntry.by` / `target`, `BeatIr.also`, `HubCmd.prompt`, a new
  `beat` command (bundle beats in a lore artifact), `RewardEntry.credits`;
  capability snapshot: occasion `select: sequence`, `cast`,
  `rewardKinds.credits` (each counted only when declared). The schema moves
  to `schemas/lute-ir-0.23.schema.json`.

## 1. Overviews

- `IndexBeat` gains `when` (raw, expanded) and `title` (scene title / entry
  title).
- `lute beats <dir> [--occasion O]… [--target T]… [--json]` prints, per
  occasion and per target of a targeted occasion (untargeted beats appear in
  every target's ladder), the beats in selection order with priority,
  `once`, `also`, `after:`, `when`, title, and the `check-project` verdicts
  (unreachable, shadowed, tied, once-run-user). The project need not check
  clean.
- `lute calendar <dir> --axis <path>=<lo>..<hi> | <path>=<a>,<b>,… (repeatable,
  first axis slowest) [--occasion O]… [--target T]… [--script save.play.yaml]
  [--json | --csv]` evaluates, for every cell of the axes' product and every
  listed occasion/target column (default: all), play's own eligibility —
  the winner (or the offered / sequence list), `+N` shadowed eligible beats,
  `?` for an undecided cell — starting from the script's save (0.22.0 §3;
  its `steps:` are not played and may be omitted) with the quests settled
  per cell. Axis values are checked against the path's declared type.
  Beats never eligible in any cell are listed at the end with the reason.
  More than 10,000 cells is refused. Exit `0` ok, `1` the project does not
  compile, `2` usage error.
- `lute scenario <dir> knowledge [--for <node>] [--format json]` traces, for
  every beat/entry/objective whose condition queries a relation
  (`holds`/`count`/`validAt`), each queried atom through the rules (the
  head's variables bound per rule) to its producers: asserting documents,
  seed facts, reserved (the engine), or **no producer**. `--for` takes a
  scene key, an entry id, `<quest>.<objective>` or `quest:<id>` and suggests
  a near match on a miss.
- The `lute scenario` graph notes the `completed()`/`active()`/`visited()`
  references it does not draw because the referencing quest has no `after=`
  (the graph JSON gains `omitted`).

## 2. Windows and missed events

- `<objective by="<condition>">` — while the objective is not done, the first
  time `by` becomes true the objective **fails** and is never judged again (a
  required objective fails its quest: `failed` rewards, `questFailed`,
  cascade). `by` is a condition slot like `done` (its faults are the slot
  codes `E-UNDECLARED`, `E-MAYBE-UNSET`). `by` is judged at every lifecycle
  settle, `on=` or not, after `done`: an objective done in the same settle
  does not fail. The failure is lifecycle state, not a state path; `newRun`
  clears it for a run-tier quest.
- `<objective on="<occasion>" target="<target>">` — the objective is judged
  only when the occasion is raised for that target, checked like a beat
  target (`E-BEAT-ATTR`: dotted id, needs `on`, the occasion must take a
  target, inside its target domain).
- Tooling raises an occasion for a target as `<occasion>@<target>`: `lute
  trace` mocks `occasions: [talk@npc.maud]`, `lute run --occasion
  talk@npc.maud`; a `lute play` step judges objectives for its `target:`.

## 3. Composing occasions

- Occasion `select: sequence` — the engine presents **every** eligible beat
  in selection order (a routine followed by the day's event). The value
  changes the capability stamp only for snapshots that declare it.
- A scene or bundle beat MAY set `also: true`: on a `select: first`
  occasion, an eligible `also` beat is presented in addition to the winner,
  after it (a side remark that never replaces the main beat); it is
  presented even when no main beat is eligible. `also` is `E-BEAT-ATTR` when
  not a bool, on an entry, or set on a `select: all` / `sequence` occasion.
  `W-BEAT-SHADOWED` and `W-BEAT-PRIORITY-TIE` ignore `also` beats.
- For `sequence` and `also`, eligibility is decided once, when the occasion
  is raised; quests settle after each presentation, so a `by` deadline is
  judged between beats.
- `lute play` presents the whole list (`--json`: `presented`, then `then`),
  rejects `pick:` on a `sequence` occasion (usage error), and gains the step
  expectation `presented: [ids]`.

## 4. Beat bundles

A lore document MAY hold scene-like beats: `<beat id on target title when
priority once also>` blocks with a scene body (lines, branches, hubs, match,
directives). A bundle beat is a beat of the project in declaration order;
its canonical id is `<document id>.<beat id>`:

- the document MUST declare `id:`; the beat `id` is an identifier without
  `-` (`[A-Za-z][A-Za-z0-9_]*`) and unique in the document; a canonical id
  equal to a scene's id is `E-CONN-EPISODE-ID-DUP`. Shape faults are
  `E-BEAT-ATTR`; any other attribute is `E-UNKNOWN-ATTR`; `<beat>` in a
  scene document is rejected.
- `title` labels the beat in a `select: all` menu (§11); it is localized
  (`titleLineId` = `<canonical id>.title`).
- A bundle beat behaves like a scene beat: `once` defaults to `run` and is
  spent by presentation, presenting it marks the canonical id visited, and
  it is checked like one (`E-OCCASION-UNKNOWN`, `E-BEAT-UNREACHABLE`,
  `W-BEAT-SHADOWED`, `W-BEAT-PRIORITY-TIE`, `W-BEAT-ONCE-RUN-USER`). It has
  no `after:`; `visited('<doc>.<beat>')` reads it in any condition, and an
  `after:` clause cannot name it.
- IR: a `beat` command heads each beat's addressing unit in the lore
  artifact (units in source order; an entry's or beat's body segment runs to
  the next `entry` or `beat` record), and `project.index.json` beat rows gain
  kind `bundle`. Body `lineId`s are prefixed with the canonical id.
- `lute trace --beat <id>` and `lute run --beat <id>` present one bundle
  beat (an id that names none is `E-TRACE-BEAT` in trace, a usage error —
  exit 2 — in run).

`<hub prompt="…">` (in any scene body) attaches a prompt line shown with the
hub's options (IR `HubCmd.prompt`; an empty prompt is `E-BRANCH-PROMPT`).

## 5. Components with sentences

A component `string` param MAY be interpolated (`{{@p}}`); a literal
`::use` argument is substituted at expansion like other params (0.21.1), so
each call site ships its own sentence under its own component-scoped
`lineId`. Binding such a param to a `@def` reference is `E-REF-TYPE` at the
argument (followed through nested components).

## 6. Previous run

`prev.run.<path>` reads the value `run.<path>` had when the previous run
ended (reserved, read-only, `unset` before the first run ends). The checker
declares a mirror `prev.run.<p>` for every declared `run.<p>`, with the same
type and no default, so every read is maybe-unset and needs `isSet` or an
`unset` arm (`E-MAYBE-UNSET`). A content `::set` of it is
`E-QUEST-RESERVED-WRITE`; an author declaring `prev.*` gets
`E-STATE-NAMESPACE`. The mirror is not in the IR state table (artifacts are
unchanged). The engine snapshots it at run end; `lute play` does so at
`newRun`; play `state:` seeds and trace mocks may set it.

## 7. Cast

A plugin `cast` export (`cast/*.yaml`) or a schema document's `cast:` key
MAY declare `cast: { <id>: { name: "…" } }`. When a cast is declared, a
speaker id outside it (and not `narrator`) is `E-CAST-UNKNOWN` with a
did-you-mean, in scenes, quests, entries and bundle beats; without one,
speakers stay shape-only. A `cast:` key in a scene's frontmatter remains
`E-META-UNKNOWN-KEY`. A plugin cast counts in `capabilityVersion` only when
non-empty. `lute context` lists the cast; LSP speaker completion offers it.

## 8. Rewards that credit state

A `rewardKinds:` entry MAY declare `credits: <state path>`; the compiler
stamps it on each reward (`RewardEntry.credits`, omitted otherwise). `lute
run` / `lute play` then add a **scalar** reward amount to that path when
granted (a range amount is the engine's roll, 0.16.0 D-C), and a content
`::set` of that path in one of the same quest's `<on>` or objective bodies is
`W-REWARD-DOUBLE-CREDIT`.

## 9. The condition decider

`decide` treats a conjunction as a set of constraints per path: equalities,
disequalities, and numeric intervals. A path is a state path, `$`, a
component param, or a relational call (`holds(P)`, `visited(id)`,
`count(P)`) keyed by its text. A conjunction whose constraints on one path
are unsatisfiable decides **false** (`run.n > 5 && run.n < 3`,
`run.slot == 'a' && run.slot == 'b'`, `x && !x`). A disjunction decides true
when its cases cover the path's domain. A negated fact atom whose positive is
Must-true decides false; in the may set, a negated rule atom over a seed
that nothing retracts or displaces is false.

Soundness: `unset` counts as a value, and an ordering or bare boolean read
on `unset` is an error, neither true nor false, so every verdict is the
expression's actual value. `run.m > 5 && run.m < 3` therefore stays
undecided when `run.m` has no default, while `isSet(run.m) && …` decides
false. On an undeclared path only equality reasoning applies. Reasoning
inside a rule's `cel()` guard is out of scope (D-E). `E-BEAT-UNREACHABLE`,
`E-ENTRY-UNREACHABLE`, `E-ARM-DEAD`, `E-OBJECTIVE-UNSATISFIABLE`,
`W-BEAT-PRIORITY-TIE` and the compile-time fold all use it, so a project
that checked clean on 0.22 MAY now report contradictions it used to miss.

## 10. Work in progress

`lute check-project --wip` downgrades `E-ENTRY-UNREACHABLE`,
`E-BEAT-UNREACHABLE` and `E-OBJECTIVE-UNSATISFIABLE` caused by a relation
that has **no producer at all** to warnings (content not yet written). A
relation that has producers but can never match remains an error. A quest
dead only because of unwritten content still feeds connectivity, so a
downstream `E-CONN-UNREACHABLE` stays an error.

## 11. Interview menus

On `select: all`, index rows carry `title` (a scene's `title:`, an entry's
or bundle beat's `title=`), so an engine can label the menu; an entry beat
that is already read is marked `read: true` in the play transcript's
candidate list (`, read` in the human transcript).

## 13. Decisions

| # | Decision | Rationale |
| --- | --- | --- |
| **D-A** | the calendar is a tool over play, not a schedule file | the day-clock VN proved beats express every cell; what was missing was a way to see them |
| **D-B** | `by=` fails on the first true | a deadline is an event, and "first time true" is observable by the engine without a clock |
| **D-C** | `also` over multi-winner `select: first` | keeps "one main beat per occasion" explainable while letting a remark ride along |
| **D-D** | bundles live in lore documents | lore already groups many ids in one file with series and categories |
| **D-E** | interval reasoning only in conjunctions | enough for every false negative the dogfood found; full SMT is not warranted |
| **D-F** | bundle beats are records in the lore command stream (`beat` + body segment), not nested metadata | follows the entry pattern, so an engine walks one address space and localization keys stay per line |
| **D-G** | `prev.run` is a checker mirror, not an IR state row | existing artifacts stay byte-identical; the snapshot at run end is engine contract |
