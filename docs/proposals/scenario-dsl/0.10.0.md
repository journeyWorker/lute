## 1. Motivation

`0.8.0` was the adoption release: a real assessment against a real catalog,
producing a list, producing a spec. `0.10.0` has the same shape and a different
instrument. Anseo is not a catalog Lute was measured *against* — it is eighteen
documents written *in* Lute, on purpose, to find out what the language does
when someone means it.

The unifying finding was not a missing capability:

> The toolchain computes more than it will tell you, and occasionally tells you
> the opposite.

Every rule in this document is an instance. The checker resolves the declared
type of a `::set` target — to produce `E-INTO-VALUE` about a *different*
construct, in the same run, on the same path — and does not apply it to the
write itself (T3.2). The parser holds the per-tag permitted-attribute table —
`<otherwise>`'s empty set is enforced *from* it — and does not close the other
five (T8.2). The producibility fixpoint proves a relation dead and reports it
in `done=` as a project-wide error, in `start=` as nothing at all, and then
`scenario reach` prints **Reachable** for the silent one (T4.5, T9.6). The
injection reducer removes a character from the stage and consults that
knowledge one conjunct away, using absence as "nothing to reset" and never as
"the author staged something impossible" (T2.4).

And once — the case that gives the theme its second clause — the toolchain says
the opposite of what it knows. `W-INJECT-CONFLICT` fires on `anchor="center"`
where `center` is the declared default, and *only* there: writing a different
anchor is silent, writing none is silent. The one authored shape it complains
about is **agreement** (T5.8).

0.10.0 makes every diagnostic the toolchain already had the information to
emit, and retires the one it had no information for.

## 2. Scope — what counts as a language change

The release takes 26 of the backlog's 38 issues; the other 12 are deferred
`DESIGN` work (design doc, *Not in this release*). Of the 26, **thirteen** are
on the language axis and are specified here. The other thirteen are toolchain
work and belong in the CHANGELOG and the implementation plan. This section
states the boundary so it is auditable, because the boundary is a judgement and
a reader is entitled to disagree with it in a named place rather than by
inference.

### 2.1 The test

> Does this change **what a document is allowed to be**, or **what the checker
> emits about a legal one**?

Anything that answers yes to either half is language-axis and is in this
document. Anything that changes only *how a command renders*, *which flag it
accepts*, *what its `--help` claims*, or *what a non-normative tool artifact
contains* is toolchain and is not.

Two clarifications the test needs, both used below:

- **A manifest is language surface.** `lute.project.yaml` decides which
  documents resolve and what they resolve to; `identity:` is normative in
  `0.8.0 §9`. So is a `--mock` file: its four keys and its four `E-TRACE-MOCK-*`
  rules are normative in `0.4.0 §4.3`, which states that "state-by-typo MUST
  fail in mocks exactly as in documents". A `*.test.yaml` is **not** — no
  proposal in this series defines it.
- **A leg agreeing with a leg that already rejected the content is not a new
  rule.** If `check-project` already errors on a construct and a second command
  says `ok`, closing that gap changes what the toolchain *says*, not what the
  language *allows*.

### 2.2 In scope — six `LANG`, seven `LANG-SOFT`

  document or project can go red.
- **`LANG-SOFT`** — adds a warning, relaxes a rejection, or corrects a message.
  A currently-green document **cannot** go red.

## 3. `::set` is typed against the path it writes

**Was** (T3.2, reproduced at HEAD 2026-08-04). `run.shedPressure` is declared
`{ type: number, default: 0 }`. All three of these are `ok … (0 warning(s))` at
exit 0 under `--deny-warnings`, compile, and are carried through by `lute run`:

```lute
::set{run.shedPressure += "two"}                       # → final = 0
::set{run.shedPressure = true}                         # → final = true
::set{run.shedPressure += (run.shedPressure > 0) * 3}  # → final = 0
```

The declared `type:` binds `into=`/`value=` (`E-INTO-VALUE`: *"`value` is
required for `run.shedPressure` (only a `bool` path defaults to `true`)"*) and
binds nothing about `::set`. One construct away, holding the same answer,
resolved by the same function.

**Is.** For a write `::set{P op E}` whose target `P` resolves to a declared
type `T`, the expression `E` MUST produce a value of the **required type**. A
decidable mismatch is **`E-SET-TYPE`**.

### 3.1 The required type, per operator

The grammar's assignment operators are exactly four (`0.1.0 §7.3.3`:
`AssignOp ::= "=" | "+=" | "-=" | "*="`); there is no fifth.

| op | required type of `E` |
| -- | -------------------- |
| `=` | `T` |
| `+=`, `-=`, `*=` | `number` |

The compound operators already require `T` to be `number` —
**`E-SET-OP-TYPE`**, unchanged — so the two rows agree wherever both apply.
When `E-SET-OP-TYPE` fires, `E-SET-TYPE` MUST be suppressed for that write: the
target is wrong, and reporting the value against a type the target does not
have would send the author to the wrong end of the line.

### 3.2 The required type, per declared scalar type

Author `state:` is scalar (`0.8.0 §4`): `bool | number | string | enum`.

| `T` | required produced type | additional obligation |
| --- | ---------------------- | --------------------- |
| `bool` | `bool` | — |
| `number` | `number` | — |
| `string` | `string` | — |
| `enum: [m…]` | `string` | when `E` is a **string literal**, its value MUST be one of `m…`; otherwise `E-SET-TYPE`, carrying a did-you-mean over the declared members |

`enum` is a **distinct type from `string`** in the checker, not a refinement of
it, and the two rows above must not be read as making them interchangeable.
Two consequences are normative, both of them **D-M** applied to its own table:

- **An `enum` value satisfies a required `string`.** A right-hand side whose
  decided type is `enum: [m…]` — by §3.3 rule 2, a read of a path declared with
  an enum type — produces a `string` for the purpose of the `string` row.
  Deciding otherwise would make `::set{run.note = run.suspectFocus}` an
  `E-SET-TYPE` on a write that is correct.
- **An `enum: [a…]` → `enum: [b…]` write with `a… ≠ b…` is undecidable unless
  the right-hand side is a literal.** The checker cannot know which member the
  source path holds at that point, so it cannot know whether that member is in
  `b…`; the write is accepted with no diagnostic. When `E` **is** a string
  literal the enum row above applies unchanged, because then the member is in
  hand. Copying one enum-typed path into another — including into itself — is
  therefore never reported, which is the ordinary write **D-M** exists to
  protect.

The enum member rule is the T5.4 case the backlog re-verifies:
`::set{run.ending = "shed-with-modle"}` against
`{ enum: [bridge-reached, shed-with-module] }` MUST exit 1 with the suggestion
the path table already computes for `E-UNDECLARED`.

`narrativeTime` is not an author-declarable state type (`0.8.0 §5`), so a
right-hand side that produces it is `E-SET-TYPE` against every legal `T`. By
§3.3 rule 4 that is `now()` and nothing else. **A read of a reserved quest path
such as `quest.<id>.activatedAt` is not decided by any §3.3 rule** — rule 2
covers a path declared in `state:`, and a reserved quest path is not one — so
it is undecidable and passes. §3.3 is closed by construction, and this section
MUST NOT assert a diagnostic §3.3 cannot derive.

**A non-scalar declared type is outside this section's domain.** §14 records
that the author-`state:` guard rejects `list`/`record`/`map` and
`narrativeTime` but **falls through** for `domain`, `providerRef`, `slotId`,
`assetKind` and `enumFromOption` — five real declarable types that `0.8.0 §4`'s
scalar union does not admit and that the table above therefore has no row for.
A `::set` whose target resolves to one of those five has **no required type
under §3** and draws no `E-SET-TYPE`, whatever `E` produces. Closing that
fall-through is the gap §14 names; it is a question about what an author may
*declare*, and answering it in a typing table would be answering it in the
wrong place.

### 3.3 What the checker MUST decide

`E-SET-TYPE` is a **proof obligation on the checker, never a guess** (**D-M**).
The checker decides an expression's produced type by these rules and no others;
an expression it cannot decide is **accepted, with no diagnostic**.

The tree these rules run over is **`CelSlot.ast`** (`lute-syntax`'s
`ast::CelSlot`) — the `cel_parser::ast::Expr` handle that
**`lute_cel::parse_slot`** fills for every CEL slot in a document, a `::set`'s
included. It is **not** `lute-compile`'s `ExprNode`, and naming it matters
because `ExprNode` is the one an implementer is most likely to reach for: it is
the crate's portable, serialized expression AST, it carries **no**
`holds`/`count`/`now` node at all, and an unknown call there lowers to `None`
while a `None` child poisons its parent. Implemented over `ExprNode`, rule 4 is
silently unimplementable and rule 3 is lost for every expression containing a
fact query — two rules under-implemented with no failure to show for it. The
rules below are stated over `CelSlot.ast` and MUST be implemented there.

1. A literal. `true`/`false` → `bool`; a numeric literal → `number`; a quoted
   string → `string`.
2. A read of a declared state path → that path's declared type.
3. A comparison (`==`, `!=`, `<`, `<=`, `>`, `>=`, `in`) or a logical operator
   (`&&`, `||`, `!`) → `bool`.
4. `isSet(p)`, `has(p)`, `holds(q)` → `bool`. `count(q)` → `number`. `now()` →
   `narrativeTime`.
5. `-`, `*`, `/` → `number`, and **any operand whose type is decidable and is
   not `number` makes the whole expression ill-typed**, reported as
   `E-SET-TYPE` naming that operand.
6. `+` → `number` when both operands are decidable and both `number`; `string`
   when both are decidable and both `string`; `E-SET-TYPE` when both are
   decidable and they disagree; undecidable otherwise.
7. A conditional `c ? a : b` → the common type of `a` and `b` when both are
   decidable and equal; undecidable otherwise.
8. A whole `@ref` occupying the entire right-hand side → its declared produced
   type. This slot already carries an expected type, so a mismatch here is the
   pre-existing **`E-REF-TYPE`**; `E-SET-TYPE` MUST be suppressed for it. No
   construct grows a second name for one fault.

Rule 5 is what decides T3.2's third probe:
`(run.shedPressure > 0)` is `bool` by rule 3, `bool * 3` is ill-typed by rule 5,
and the write is `E-SET-TYPE` naming the comparison.

Every other form — an arithmetic expression over an undecidable operand, a
`@ref` embedded in a compound expression, a list literal — is **undecidable**
and passes. The decidable set MAY only grow in a later release. It MUST never
be widened by inference that can be wrong: a false `E-SET-TYPE` on a correct
counter is strictly worse than the silence this section removes, because the
author's only remedy would be to stop declaring the type.

### 3.4 Message

`E-SET-TYPE` names the path, its declared type, and the type it decided for the
expression:

```
error [E-SET-TYPE] `::set` writes a `string` into `run.shedPressure`, declared
`number` (dsl 0.10.0 §3)
```

Anchored at the right-hand side's own span, not the directive's — the target is
correct and the author is looking for the value.

## 4. Every attribute surface is closed

**Was** (T8.2). `<choice id="…" label="…" goto="anseo.s01ep08">` is
`ok … (0 warning(s))`, exit 0, and `grep -c goto` on the artifact is `0`. Three
routing declarations, discarded in silence. It is the whole logic-tag family:
five of six constructs accept and drop any invented attribute, and the sixth —
`<otherwise>`, the one whose permitted set is **empty** — is the one that
enforces. Directives and content lines are closed and enforced, each with its
own message. Three attribute surfaces in one language, two of them enforced.

And one of the attributes silently eaten is `as=`, removed from `<choice>` in
`0.1.0`, whose sibling `persist` — removed in `0.6.0` — draws a bespoke
`E-PERSIST-REMOVED` with a column-exact span and a migration instruction, three
lines away. With `as=` in place of `into=`, a document compiles to **no `set`
record at all**, at exit 0, on a file `lute check` calls `ok`.

**Is**, per **D-J**. Closure is a **checker** rule with a fixed per-tag table,
modelled on the content-line surface — logic tags are core grammar and, unlike
directives, are not plugin-extensible, so the table is a constant and not a
capability lookup. It emits **`E-UNKNOWN-ATTR`**, the code the other two
surfaces already raise, at the offending attribute's own span, once per
attribute. A bespoke code would defeat the point: the surface becomes uniform,
or #6 was not worth doing.

The table is enumerated from the **AST and its readers**, not from `0.1.0
§7.3`'s prose, because the prose and the parser do not agree about where an
attribute lives:

| construct | required | permitted | removed, told by a dedicated code |
| --------- | -------- | --------- | --------------------------------- |
| `<branch>` | `id` | — | — |
| `<choice>` **under `<branch>`** | `id`, `label` | `when`, `into`, `value` | `as` → `E-AS-REMOVED`; `persist` → `E-PERSIST-REMOVED` |
| `<choice>` **under `<hub>`** | `id`, `label` | `when`, `into`, `value`, `once`, `exit` | `as` → `E-AS-REMOVED`; `persist` → `E-PERSIST-REMOVED` |
| `<match>` | `on` | — | — |
| `<when>` | at least one of `is` / `test` | the other | — |
| `<otherwise>` | — | — | — |
| `<hub>` | `id` | — | — |

Four shapes the table MUST account for, all of them AST facts rather than
prose facts:

- `<hub>` has **no `id` field**. Its `id=` survives in the residual attribute
  list and the checker reads it from there, so `id` MUST be in the permitted
  set or the closure rejects every hub in existence.
- `once` and `exit` are **bare flags**, not `key="value"` pairs. They are
  attributes for this rule's purposes and are matched by key alone.
- `<match>`, `<when>` and `<otherwise>` **discard** residual attributes at
  parse today. The parser MUST retain them: a checker rule over attributes the
  checker never receives is not a rule. This is **D-J**'s precondition, not a
  separate change.
- **The fourth column is not a permitted set, and the closure rule skips it.**
  `as` and `persist` on a `<choice>` are errors — that is the whole point of
  §4 — but they are errors *already told by their own code*. The closure rule
  MUST NOT **also** raise `E-UNKNOWN-ATTR` on a key a dedicated removal code
  reports; each is reported once, by that code. The checker already holds this
  invariant for `persist`, deliberately: the attribute is recognised at its own
  site so that it is *"never reported as unknown/extra"* and
  `E-PERSIST-REMOVED` stays *"the sole report for it"*
  (`lute-check/src/check.rs:2564-2565`, `:2571-2572`). A table built without
  this column breaks that invariant on the exact attribute this section uses to
  argue that `as` and `persist` should be told the same way.

Normative points:

- **The two `<choice>` positions have different permitted sets** (**D-L**).
  `once` and `exit` are hub-choice flags — `0.1.0 §7.3`'s grammar attaches them
  to `HubChoice` and to nothing else, and the hub reducer is their only reader.
  `once` or `exit` on a `<choice>` under a `<branch>` is `E-UNKNOWN-ATTR`.
  Enforcing one merged set would leave a branch choice carrying `exit` silent,
  which is the defect this section closes wearing a smaller hat.
- **`<otherwise>` joins the table as the empty set**, and the parser's
  attribute arm is **deleted**. An attribute on `<otherwise>` is now
  `E-UNKNOWN-ATTR` like every other logic tag, not `E-LOGIC-CONTENT`. This is a
  visible message change on the one construct that already enforced, and it is
  the right trade: `E-LOGIC-CONTENT` has four emission sites in
  `lute-syntax/src/parser/blocks.rs` and only one is about attributes —
  `:178`, `:309` and `:378` are body-shape rules about children, and the
  attribute arm is at **`:426`** (**D-J**'s rationale cites `:425`, the
  `self.emit_o(` line one above; the code constant is on `:426`). Leaving
  `<otherwise>` behind would preserve exactly the
  overloading #6 exists to remove. `E-LOGIC-CONTENT` survives, unchanged, for
  its **three body-shape** rules — a `<branch>` body admitting only `<choice>`
  children, a `<hub>` body the same, a `<match>` body admitting only `<when>`
  and `<otherwise>`. Those belong in the parser and stay there.
- **`as=` on a `<choice>`, in either position, is `E-AS-REMOVED`.** This
  answers **D-J**'s first follow-on, and it takes the bespoke-code arm rather
  than the did-you-mean arm. `E-UNKNOWN-ATTR` would state something false: the
  attribute is not unknown, it was **renamed** in `0.1.0`, the rename has a
  documented migration, and `lute fix` already performs it. Its sibling
  `persist` — removed one release later — has had a dedicated code, a
  column-exact span, and a migration instruction since `0.6.0`; two removals of
  two attributes from one construct should not be told two different ways
  because one of them was noticed earlier. `E-AS-REMOVED` mirrors
  `E-PERSIST-REMOVED` in **severity, layer, span behaviour and kind** — an
  error on the logic layer, anchored column-exact at the attribute's own key,
  carrying a migration instruction and a `"migrate"` fixit. **The edit
  differs, and the implementation MUST NOT be shared.**
  `E-PERSIST-REMOVED`'s fixit is a *deletion*, widened by `widen_attr_delete`
  (`lute-check/src/check.rs:2762-2766`) to swallow one adjacent separating
  space so no double space is left behind; `as` needs a two-byte-to-four-byte
  *key replacement* with no widening at all, and reusing the deletion helper
  produces wrong output. Note also that `lute fix` does not read
  `Diagnostic.fixits`: the LSP fixit and `lute fix`'s own `as` → `into` edit
  are two independent implementations that MUST stay byte-identical, which is
  the hazard `check.rs:2758-2759` already records for `persist`. The uniformity
  **D-J** asks for is about the *unknown-attribute* rule, and `as=` is not an
  unknown attribute.
- **Content lines and directives are unchanged.** They were already closed —
  content lines against a fixed constant, directives against the capability
  schema, both raising `E-UNKNOWN-ATTR`. What changes is that the language has
  one answer instead of two, which is the whole of #6.

**Deliberately still open, and named rather than quietly left:** `<quest>`,
`<objective>`, `<on>` and `<track>`. They are not logic tags, they are not in
`0.1.0 §7.3`'s table, and they are not in the issue this section implements.
`<quest after=…>` in particular is *parsed and consumed* with no normative
statement anywhere in this series — closing its set means writing that
statement first. Filed, not smuggled.

## 5. A gate that can never open is an error

**Was** (T4.5, T9.6, both re-probed at HEAD on the finished corpus). A `done`
predicate over a relation nothing in the project can ever assert is a hard,
project-wide `E-OBJECTIVE-UNSATISFIABLE` naming the relation and the reason.
The **same predicate** in the slot that decides whether the quest ever
*starts* emits nothing:

```console
$ # done="holds(sealed(toma))"  — sealed is declared and asserted nowhere
docs/examples/anseo/quests/hold-the-spine.lute:32:1: error [E-OBJECTIVE-UNSATISFIABLE] …
failed: docs/examples/anseo (18 file(s), 1 project-wide error(s), 13 project-wide warning(s))

$ # start="holds(sealed(toma))" — the same predicate, one attribute over
ok: docs/examples/anseo (18 file(s), 12 project-wide warning(s))
```

Note the count, and note that it **drops**: the committed, working
`start="holds(can_halt(toma))"` yields one `W-UNPROVEN-RELATIONAL`, and the
gate that can never open yields none. The only project-wide number an author
watches goes *down* when the quest dies. `scenario reach` then prints
`verdict: Reachable` for it — while for the scalar-dead `start="false"` it
correctly reads the lifecycle and prints `Unreachable`.

T9.6 is the same hole on the other axis: two required objectives with disjoint
solution sets (`done="run.shedPressure >= 99"` and `done="run.shedPressure <= 0"`)
draw nothing, while `done="false"` beside them is an error.

### 5.1 The dead `start=` — one missing branch, no new diagnostic code

The producibility fixpoint (`0.6.1 §2`) already runs over `<quest start|fail>`;
that is what emits `W-UNPROVEN-RELATIONAL` there. It has no *not*-producible
branch. It gains one:

> A `<quest start>` predicate that decides **false** once every fact query over
> a never-producible relation is substituted, where that substitution is
> **load-bearing** for the false result, is **`E-QUEST-UNREACHABLE`** — the
> existing dead-`start` cause of the existing code (`0.4.0 §5.3` rule 2, D21),
> naming the relation and carrying the verbatim "under your declared routes"
> hedge that `E-OBJECTIVE-UNSATISFIABLE`'s relational cause already carries.

Three rules bound it, and each removes a false positive:

- **Load-bearing only.** A `start` that was already false before substitution
  (`start="false"`) is the pre-existing scalar cause and MUST NOT be
  double-reported.
- **`start=` only, never `fail=`** (**D-N**). A `fail` predicate gated on a
  never-producible relation means the quest can never *fail*. That is not a
  defect and MUST NOT fire; the analysis is symmetric and the verdict is not.
  `fail` keeps `W-UNPROVEN-RELATIONAL` for the producible case, unchanged.
- **Producible is producible.** `start="holds(found(toma))"` MUST NOT error on
  the finished Anseo corpus, because `found` *is* asserted
  (`scenes/stowaway.lute:19`). A false positive on this layer is worse than the
  silence: it is the layer the release exists to defend.

`scenario reach` needs a second wire, and the reason is a channel mismatch this
section originally got wrong. An earlier draft said it *"reads
`E-QUEST-UNREACHABLE` through `unreachable_quest_ids`, so wiring the branch is
what makes it stop printing `Reachable`"*. **False, and verified false by
building it:** `unreachable_quest_ids` scans the **per-file** `check()` results,
while the dead-`start` analysis lives in the **project-wide**
`scan_objective_liveness`, whose output goes to the CLI's `project_diags` and
never reaches `file_results`. With only §5.1's branch wired, `check-project`
correctly reported the new error at `quest.span` and `scenario reach` still
printed `verdict: Reachable`.

The fix follows the module's own stated discipline — this cause is consumed as
**structured boolean data**, never by re-inspecting an emitted diagnostic's code
or message text. So `producible` exposes `dead_start_quests`, the boolean twin
of the diagnostic computed by the **same** `dead_guard`, so the two cannot
disagree; the connectivity fixpoint accumulates it and subtracts it from the
`dead_required_objective_quests` difference, which routes it to the existing
`E-QUEST-UNREACHABLE` verdict branch rather than the `E-OBJECTIVE-UNSATISFIABLE`
one tested before it. The verdict *text* for the lifecycle cause did already
exist; what did not exist was a path from this analysis to it.

### 5.2 Contradictory objectives — `E-OBJECTIVE-CONTRADICTION`

Per **D-G**, the supported domain is **scalar comparisons between a declared
path and a literal**, and nothing wider. General range analysis over arbitrary
CEL is a different feature with a different cost.

An objective's `done` predicate is **in domain** when it is, in its entirety,
a single comparison

```
<declared scalar state path>  <op>  <literal>
```

with `<op>` one of `==`, `!=`, `<`, `<=`, `>`, `>=`, and the literal
well-typed for the path's declared type. An `&&`, an `||`, a `!`, a fact query,
a `@ref`, a second path, or anything else puts the predicate **out of domain**,
and an out-of-domain predicate participates in no pair.

> Two **required** (`!optional`) objectives of the same `<quest>`, whose `done`
> predicates are both in domain and name the **same** path, whose solution sets
> over that path's declared type do not intersect, are
> **`E-OBJECTIVE-CONTRADICTION`**.

Solution sets are computed over the declared type's domain: an interval over
`number`, the finite member set for `enum` and `bool`, and equality/inequality
only for `string`. **The `number` domain is the reals, not the integers** — a
literal is an `f64` and the language has no integer scalar type. `run.x > 1`
and `run.x < 2` therefore **intersect**, and that pair is not a contradiction;
reading it as disjoint would produce a false `E-OBJECTIVE-CONTRADICTION` on a
legal pair, which is the one outcome §5.2 may not produce. Reported **once per
pair**, anchored at the second objective, naming both objective ids and the
path.

The quest consequence follows `0.4.0 §8.2` rule C4 verbatim (**D-O**): a
contradictory required pair means the quest can never complete, and that rides
as a **note on this diagnostic**, never as a second `E-QUEST-UNREACHABLE`. It
reuses `REQUIRED_QUEST_NOTE` unchanged, so the consequence reads identically
whichever cause found it. An **optional** objective never participates: the
quest can still complete without it, and a pair including one is not a
contradiction about the quest.

Neither objective is individually dead, so neither draws
`E-OBJECTIVE-UNSATISFIABLE`, and the two codes MUST NOT both fire for one pair.

## 6. `defaults:` in `lute.project.yaml`

Per **D-F** this is new manifest grammar with inheritance and override
semantics, and it changes which documents are accepted. It gets the most
careful text in this release because it is the only change here that adds a
surface rather than closing one.

**Was** (T7.12, T9.5). Across the eight scenes T7.12 measured: 48 frontmatter
key lines, **18 distinct** — 30 byte-identical duplicates — and only `episode:`
and `after:` carrying per-file information. Frontmatter is 18% of the corpus's
scene lines. Across five quests: 20 key lines, **8 distinct**, one of four keys
carrying per-file information. Both composition mechanisms the language
documents (`uses:`, `extends:`) operate on **schema** files, not on document
meta. And the manifest that *consumes* `character:` and `season:` — through
`identity:`'s `{prefix}` — cannot supply them.

`profile:` already falls back to the project's `defaultProfile`. The idea of a
project-level default exists and is applied to exactly one key.

**Is.**

```yaml
# lute.project.yaml
defaultProfile: core
defaults:
  kind: scene
  character: anseo
  season: 1
  uses: [world.schema.yaml, vocabulary.schema.yaml]
```

### 6.1 Which keys may be defaulted

The defaultable set is **closed** (**D-P**). A key outside it is
**`E-DEFAULTS-KEY`** at project load, with a did-you-mean over the set.

| defaultable | not defaultable | why not |
| ----------- | --------------- | ------- |
| `kind`, `character`, `season`, `episode`, `pov`, `luteVersion`, `contentLang`, `uses`, `extends`, `components` | `episodeId` | derived identity. A defaulted `episodeId` gives every scene under the root the same `{prefix}`, i.e. a silent `lineId` collision across the whole project |
| | `mode` | **inert.** `mode:` is a legal core frontmatter key that nothing reads — the analysis mode comes from the check invocation, never from the document. A defaultable key that changes nothing is a trap in a block whose entire purpose is to change many documents at once, so it is excluded (**D-P**) rather than shipped as a no-op an author will reasonably expect to work |
| | `title`, `after` | per-document content and per-document routing. A project-wide `after` wires every scene to one prerequisite |
| | `enums`, `state`, `entities`, `relations`, `facts`, `rules`, `defs` | schema declarations, which **already have** a composition mechanism: `uses:`/`extends:` (`0.1.0 §9.2`). Hoist them into a schema and default `uses:`. A second route to one job is what `0.9.0 §7` refused for vocabulary and this refuses for the rest |
| | `profile`, `plugins` | already project-level, via `defaultProfile` and `profiles.<name>.plugins`. Defaulting them again would make the activation order (`plugin 0.0.1 §11.1`) depend on two manifest keys |
| | `component`, `params` | component identity, per file, and discarded at import anyway (`0.9.0 §6.1`) |

`episode:` is defaultable although T7.12 measured it as the one scene key that
always varies. Forbidding a key nobody will default needs a reason and there
is not one; a root that does default it and does not override it lands in the
duplicate-identity rules of §6.4.

Three of the defaultable keys — `uses`, `extends`, `components` — hold
**paths**, and a path in a manifest is not a path in a document.

> **A path resolves relative to the file that contains it** (**D-Y**). An
> authored `uses:` resolves against the **document's** parent directory, as it
> does today. A path supplied by `defaults:` resolves against the **manifest's**
> directory, because that is the file it is written in.

This is not a detail. Documents under one root sit at different depths —
`scenes/`, `quests/`, a nested subdirectory — so a manifest default resolved
document-relative would be correct only when every consumer happens to share a
depth, and would break when a single file moved. A default that fragile is
worse than the boilerplate §6 exists to delete.

Implementations MUST canonicalise `defaults:` paths **at manifest load**
(**D-Z**), not by threading provenance through the import resolver. Two
consequences follow. A bad path fails **once, at the manifest, naming the
`defaults:` key** — never once per inheriting document. And a canonical path is
absolute and machine-specific: it MUST NOT reach any serialised surface — not
the capability snapshot, not `capabilityVersion`, not a stamp, not a compiled
artifact, not `lute context --json`. An absolute path in a stamp means two
developers on one commit compute different versions and the drift guard fires
on nothing. Pre-resolution is for resolution only; anything that renders or
hashes keeps the **authored** string.

### 6.2 Inheritance and override

Resolution is **per key, whole-value** (**D-P**):

> For each key in the governing manifest's `defaults:`, if the document's own
> frontmatter contains that key **at all**, the document's value is used
> **entire**. Otherwise the default's value is used **entire**.

- **No merging of any kind.** No deep merge of mappings, no concatenation of
  sequences. A document with `uses: [wake.schema.yaml]` under a root defaulting
  `uses: [world.schema.yaml, vocabulary.schema.yaml]` resolves to
  `[wake.schema.yaml]` — not to three imports. `defaults:` states this rule
  **directly** rather than inheriting it from `defaultProfile`: that fallback
  proves scalar `Some`-over-fallback only, and a present YAML null there is
  indistinguishable from an absent key, so it demonstrates nothing about list
  or map values (**D-P**, corrected). The rule is stated on its own merit — it
  is the only one under which a reader can tell what a document imports by
  reading the document. Concatenation would make an import list depend on a
  file the document does not name.
- **Present-but-empty counts as present.** `uses: []` in a document means *no
  imports*, not *inherit*. A null value (`uses:` with nothing after it) is
  likewise present. There is no "unset me" spelling and none is added: a
  document that wants nothing writes the empty form.
- **Applied before every other frontmatter rule.** The resolved frontmatter —
  authored keys plus defaults — is what per-kind legality, required-key
  checking, type checking, and identity rendering all see. A document that
  omits `character:` under a root that defaults it is complete, not
  `E-META-MISSING`.
- **A defaulted value is validated exactly as an authored one.** No new code:
  an ill-typed or illegal default draws the same diagnostic an authored one
  would (`E-UNKNOWN-KIND`, `E-FRONTMATTER-SCHEMA`, …). The author edits the
  manifest, so the diagnostic points at the **manifest**, names the offending
  `defaults:` key in its message, and names a document it was applied to.
  It does **not** anchor at the key's line and column: a manifest diagnostic
  is a spanless `ResolveDiag`, and spanned YAML parsing is not in scope for
  this release (**D-Z**, and the same retreat §8 makes for mocks under
  **D-AB**). The limitation is documented, not engineered around.

### 6.3 Per-kind legality, and mixed roots

A default whose key is **not legal on a document's resolved kind is not applied
to that document, and that is not an error.** `character:` is scene-only; a
quest under a root defaulting `character:` simply does not receive it and does
not draw `E-META-UNKNOWN-KEY`. Without this rule `defaults:` would be unusable
in any root holding more than one kind of document — which is every real root.

The same rule covers component files: a component import's legal keys are
`component:`, `params:`, and the universal set, so a default of `kind:` or
`character:` never reaches one. `uses:` would reach one and is then discarded
at import exactly as an authored `uses:` is (`0.9.0 §6.1`) — the scoping limit
that release named is unchanged, and `defaults:` is not a way around it.

`kind:` deserves its own sentence because it is required and has no default
today: defaulting it is legal, and a root of scenes may write `kind: scene`
once. A document whose kind differs overrides it, and `E-KIND-MISSING` now
means "neither the document nor the manifest says".

### 6.4 Interaction with `identity:`

`identity:`'s `{prefix}` derives from `character`, `season` and `episode` (or a
non-empty `episodeId`). Defaults are resolved **before** identity rendering, so
a defaulted `character:` participates in `{prefix}` identically to an authored
one — which is #34's own motivation: the manifest that consumes these keys can
now supply them.

No new rule is needed for the collision case. A root that defaults `episode:`
and holds two scenes that do not override it produces two documents with the
same `{prefix}`; the resulting duplicate `lineId`s are caught by the existing
identity and duplicate-code rules, at the documents, exactly as they are when
two authors type the same `episode:` by hand. `defaults:` makes that mistake
easier to make in one place and no harder to find.

### 6.5 Scope

`defaults:` is **per project root**, like every other manifest key and like
`0.9.0 §3`'s vocabulary declaration. The governing manifest's `defaults:`
applies whole; a nested root's `defaults:` **replaces** an outer root's
entirely rather than extending it. There is no inheritance across roots and no
`extends:` between manifests. Combined with §6.2's whole-value rule, that gives
exactly one place to look for any resolved key: the document, then the
governing manifest, then nothing.

## 7. Nested manifests are validated by every command that walks them

**Was** (T1.10). `check-project /tmp/nest` fails the whole build over an
illegal `identity:` template in an **inner** manifest two directories down;
`compile --all --project /tmp/nest` exits 0 over the same tree, never opens
that file, and prefixes every `lineId` — including the nested project's — with
the outer template. One command refuses to proceed over a manifest the other
never reads, while the site states the opposite guarantee: *"what checks clean
is exactly what compiles"*.

**Is**, per **D-D** — `compile` aligns to `check`, never the reverse:

- **Every command that walks a directory tree of documents MUST validate every
  `lute.project.yaml` it encounters under that tree**, and MUST fail on an
  invalid one. `E-IDENTITY-TEMPLATE` and every other project-load diagnostic is
  reachable from `compile` and `compile --all` on exactly the manifests
  `check-project` already reaches.
- **Which manifest *governs* is unchanged.** Validating a nested manifest does
  not make it govern: under `compile --project <dir>` the invoked root still
  supplies identity and capability for every document. This is deliberate and
  is the backlog's own boundary — "nearest manifest wins" for `compile` is a
  different change with different consequences and is not made here.
- **A manifest diagnostic MUST carry the manifest's path.** Today the outer
  run's failure line is byte-identical to the inner run's, carries no path, and
  is preceded by no `ok:` lines. An author is told a manifest is broken and
  left to find out which.
- **A nested manifest that is present and inert draws `W-PROJECT-INERT`** —
  but only when it would have mattered (**D-S**):

  > `W-PROJECT-INERT` fires for a `lute.project.yaml` under the invoked root
  > that does not govern, **and** that would have resolved a different
  > capability snapshot, different `identity:` templates, or a different
  > `defaults:` block than the invoked root's.

  Narrowing it this way is what makes it a signal, and **all three** disjuncts
  have to be evaluated. The three are not arbitrary: §6.5 says a document
  resolves exactly these things through its governing manifest — "the
  document, then the governing manifest, then nothing" — so they are the
  complete set of ways an inert manifest can change an outcome.
  Measured at HEAD over `docs/examples`'s six nested manifests, by resolving
  each root and comparing its `capabilityVersion` against the outer root's:
  three resolve **identically** (`anseo/`, `episodes/`, `investigation/`) and
  three do **not** (`showcase/`, `plugindef-project/`, `idola-project/` — each
  declares a `pluginsDir` and activates a plugin the outer root's `core`
  profile does not). The identity disjunct excludes `anseo/` on its own terms,
  since its two templates are the defaults verbatim, and **no manifest in the
  corpus declares a `defaults:` block at all**, so the third disjunct changes
  the corpus count by zero. The narrowing takes six candidates to **three**,
  and §13.4 measures what those three cost. The warning exists for the case
  T1.10 measured: an inner `identity:` block that is quietly not applied, on a
  project whose entire localization pipeline is keyed on `lineId`. The
  `defaults:` disjunct is the same failure with a sharper edge — two roots
  supplying different `season:`/`character:` defaults rewrite every `lineId`
  in the inner subtree while **both** `check-project` and `compile --all`
  stay at exit 0.

## 8. Scaffolded artifacts are checked

**Was** (T1.9). `lute init` emits `mocks/playthrough.yaml`. Task 1 replaced
`world.schema.yaml` and deleted `scenes/opening.lute`, and `check-project`
stayed `ok`, exit 0, with a mock in the tree naming a state path that no longer
exists and a scene file that no longer exists. At HEAD that run is
`ok: docs/examples/anseo (18 file(s), 13 project-wide warning(s))` — the same
baseline §13 opens with — and **not one of those 13 is about the mock**; they
are `W-UNPROVEN-RELATIONAL` on the quest gates. The mock contributes nothing to
the count and never has, which is the finding. The rule *is* implemented and
stated forcefully — `E-TRACE-MOCK-UNDECLARED`, *"state-by-typo MUST fail in
mocks exactly as in documents"* (`0.4.0 §4.3`) — but only fires when a human
runs `trace` with the right two arguments. When it does fire, its position is
`scenes/wake.lute:0:0`: a source diagnostic against a file that is not at
fault, at an impossible position, for a defect in `mocks/playthrough.yaml`.

**Is**, per **D-E** — an error, behind a checker pass:

- **The mock grammar gains a required `file:`** (**D-AC**), naming the document
  the mock previews:

  ```yaml
  file: ../scenes/cryobank.lute
  state:
    run.shedPressure: 1
  ```

  `file:` resolves **relative to the mock that contains it** — D-Y's rule for
  documents and `*.test.yaml`'s rule for tests, unchanged. The key is not new
  grammar invented here: a `*.test.yaml` goes through the same
  `parse_mock_yaml` and has carried a **required** `file:` since `0.4.0`, used
  by every test in the corpus. Because the mock grammar is open, `file:` is
  already legal in a `mocks/*.yaml` today and simply does nothing. This section
  gives it its meaning there rather than minting a second spelling of one
  concept, in one format family, read by one function, with a different base
  directory.

  Three rules, and no fourth:

  - A mock with **no** `file:` is **`E-MOCK-SUBJECT`**.
  - A `file:` naming a path that does not exist is **`E-MOCK-SUBJECT`**.
  - `lute trace <doc> --mock m.yaml` supplies the subject on the command line
    and **that wins**. A `file:` in the mock that names a different document is
    **`E-MOCK-SUBJECT`**: the two ways of saying what a mock is for must not be
    able to disagree in silence.

  **Required, not optional, and that is what makes the section
  implementable.** `validate` is document-scoped by its signature
  (`lute-trace/src/mock.rs:712`); there is no union `FoldedEnv` type and no
  union document to validate a subject-less mock against. An optional `file:`
  would have left the *majority* branch — every mock in the corpus lacks the
  key today — specified against machinery that does not exist, and that branch
  would have been the one carrying this section's headline red. With `file:`
  required there is exactly one mode: resolve the subject, fold that document's
  schema, validate against it. It is also what makes **D-E**'s "a mock naming a
  deleted scene" checkable at all — the Anseo mock names `scenes/opening.lute`
  **in a YAML comment**, and a comment is not language surface.

  The upgrade cost is stated rather than hidden. Because the grammar is open, a
  pre-`0.10.0` binary **silently ignores** `file:` — and `file:` is precisely
  the key that decides which schema a mock validates against. An author who
  adds it early gets no signal that it did nothing, then gets a required-key
  error from the new binary on every mock that lacks it. This is the trap
  **D-Q** records for `defaults:`, in the same release, on the same ground.

- **`check-project` MUST validate every `mocks/*.yaml` under the root** against
  the schema resolved for that mock's `file:` subject, using the rules
  `0.4.0 §4.3` already states: `E-TRACE-MOCK-UNDECLARED`, `E-TRACE-MOCK-TYPE`,
  `E-TRACE-MOCK-FACT`, and the **structural** half of `E-TRACE-CHOICE`.
  `E-MOCK-SUBJECT` is the one new code; the pass is the one new mechanism.

  **The glob is `mocks/*.yaml` and nothing else, and that boundary is chosen,
  not incidental.** Two neighbouring file sets look like they belong and do
  not. A `*.test.yaml` already carries a **required** `file:` read by the same
  parser and is already validated when `lute test` runs it, so sweeping it here
  would be a second enforcement of a rule that has an owner. A
  `conformance/*/mock.yaml` is a fixture whose whole purpose is to pin
  behaviour, including behaviour this pass would call wrong. Appendix C's
  "`conformance/`: zero fixtures affected" is therefore a **consequence of this
  boundary**, not an independent measurement, and is written there as such.

  Two mechanical prerequisites the pass needs and does not have. `lute-trace`
  does not export `E-TRACE-MOCK-PARSE` (`lib.rs:49-52` exports the other six);
  a pass outside that crate cannot name the code, so it MUST be added to the
  `pub use`. And a malformed mock exits **2** under `lute trace` — an input
  error about the file the author named on the command line — while under
  `check-project` it is one project error among many and exits **1**. Both are
  right for their command; the spec states them so the difference is a decision
  on the record rather than a surprise in a test.

  **`E-MOCK-SUBJECT` suppresses the other four for that file**, and this is
  forced rather than chosen: with no resolvable subject there is no resolved
  schema and no parsed document, so there is nothing for the remaining rules to
  decide. A subject-less mock is reported **once**. The author supplies
  `file:`, the schema becomes knowable, and whatever else is wrong is caught on
  the next run — which is how the Anseo mock's `run.greeted` surfaces
  (**D-AC**).

- **`E-TRACE-CHOICE` is two rules under one name, and this pass owns exactly
  one of them.**

  - The **structural** half — a `choose:` naming a branch/hub id, or a choice
    id beneath it, that is absent from the subject document — is a pure id
    lookup over the parsed document (`lute-trace/src/mock.rs:618-642`). It is
    statically decidable, and it is what this pass runs.
  - The **walk** half — a forced choice whose `when=` guard decides false *at
    its presentation point* (`lute-trace/src/walk.rs:594-604`) — is
    **explicitly out of the pass** and entirely unchanged. It depends on
    in-flow writes the walk has not applied yet, which is why the pre-walk
    validator deliberately does not evaluate guards (`mock.rs:6-12`), and no
    static pass can deliver it. It already anchors at the `<choice>` the
    diagnostic is *about*, and it **keeps that anchor**. Nothing in this
    section moves a correctly anchored document diagnostic into a YAML file.

- **A mock diagnostic anchors at the mock file and names the offending key in
  its message** (**D-AB**) — not at the key's own line and column. Three layers
  stand in the way and this release budgets none of them: `parse_mock_yaml`
  deserializes into `serde_yaml::Value` (`mock.rs:166`), which retains no
  position for a key or a scalar; every mock entry carries the hardcoded
  all-zeros `synthetic_span()` (`mock.rs:71-79`); `MockSet`'s `facts`,
  `choose`, `events` and `accepts` have no span slot to fill even if it did;
  and `Diagnostic` has **no file field** (`lute-core-span/src/lib.rs:113-141`),
  so fixing the first two would put a correct position in the wrong file.
  Spanned YAML parsing is not in scope for five diagnostics, exactly as
  **D-Z** put it out of scope for one at `E-DEFAULTS-KEY`; the limitation is
  documented, not engineered around. What the author gets:

  ```
  docs/examples/anseo/mocks/playthrough.yaml: error [E-TRACE-MOCK-UNDECLARED]
  `run.greeted` is not declared in the schema resolved for `../scenes/wake.lute`
  ```

  Right file, offending key named, impossible position gone. The column is
  future work and it is **one** change — spanned YAML at the parse site plus a
  file field on `Diagnostic` — rather than five.

**This reddens all three `mocks/*.yaml` in `docs/examples`, and that is
correct.** All three predate the key and none carries it, so all three draw
`E-MOCK-SUBJECT` on the first run. `anseo/mocks/playthrough.yaml` then draws a
**second** red once its `file:` is supplied: `run.greeted` is undeclared in the
schema the subject resolves. Its subject scene was deleted nine tasks ago and
it has been green for the entire exercise; finding T1.9 exists precisely
because nothing said so. The two `investigation/mocks/*.yaml` have nothing
further wrong — they seed declared paths and force real choice ids — so one red
each and one line each is the whole of it. Making `file:` required is a grammar
change and it reddens every mock written before it; there are three. §13.5
measures it. The corpus must not ship the defect the release is fixing.

**Not here:** T10.4's README half. `lute init` writing a "Next steps" block
hard-coded to `scenes/opening.lute` is a generator defect with a generator fix
("do not write the section at all"), and it changes no document, grammar, or
diagnostic. It ships with the toolchain work — as does teaching `lute init`'s
scaffolded mock to carry `file:`, which is the generator side of this key and
is now mandatory rather than merely tidy.

## 9. A component check does not contradict itself

**Was** (T6.3, T6.7, T9.12). The two check legs split caller-awareness from
span-precision and neither has both.

```console
$ lute check components/interject.component.lute --project …
ok: …/interject.component.lute (0 warning(s))     # exit 0
```

— on a component that cannot work with **any** of its callers, because a
standalone check resolves against the component's own `uses:`, the one
vocabulary that never applies at runtime (`0.9.0 §6.1`). `check-project` catches
the fault and reports it **once per caller, at line 1 of the wrong file**: N
identical `E-BAD-ENUM`s at `1:1` in the N files that are correct, while the one
file to edit reports `ok`. The position exists — the same run prints
`reader.component.lute:9:54` for an `E-COMPONENT-STATE`. And `lute trace` on the
component refuses with *"run `lute check` first"* — advice that cannot be
followed, because `lute check` on that exact file says `ok`.

**Is.** Four rules. None of them makes any content newly illegal; every fault
below is already an error under `check-project`.

1. **A component-body diagnostic carries the component-internal position.** It
   is still *reported at the caller* with the component prefix — `0.9.0 §5`
   settled that, and for the injection case it is the honest anchor because the
   verdict depends on state inherited there. What is added is the position
   *inside* the component (`…/interject.component.lute:10:34`) as a secondary
   location. `0.9.0 §6.2` named the collapse to the importing document's
   frontmatter span as a known limitation; this narrows it.
2. **Identical caller reports roll up.** One diagnostic per *problem*, not per
   caller, with the remaining callers summarised (`(+6 more callers)`). Eleven
   modules must not produce eleven identical messages.
3. **`E-COMPONENT-PARSE` fires on the standalone leg**, and **suppresses the
   `E-UNDECLARED-REF` it causes.** A malformed `params:` means the param is
   never registered, so the body's `@ref` resolves against nothing; reporting
   only the consequence sends the author to `defs:` for a param they declared
   four lines up.
4. **A standalone component check with at least one caller in the resolved
   project MUST run the caller-resolved check** and report every diagnostic
   that holds at **every** call site, anchored inside the component. A
   diagnostic holding at only some call sites is caller-specific and stays with
   `check-project`, where the caller is visible.

   **With no caller in scope** — no project resolved, or no document in the
   project imports this component — the check MUST NOT report a bare `ok`. It
   reports **`W-COMPONENT-UNVERIFIED`** (**D-W**), stating that the verdict
   covers the component's own frontmatter and body against the component's own
   imports, that those imports are discarded at `::use`, and that
   `check-project` is the deciding leg.

Rule 4 is what makes T9.12's advice followable: `lute trace` on a component and
`lute check` on the same file stop disagreeing, because the check no longer
claims a verdict it did not compute.

## 10. Timeline time is integer milliseconds

**Was** (T7.2). `::vfx{… at="0.8" duration="0.4"}` followed by
`::vfx{… at="1.2"}` → `E-CLIP-OVERLAP: clip at 1.2 overlaps another clip in
track '#vfx'`. Both normative sources make the hand-off legal and agree — §11.4
says a clip whose start *precedes* the previous resolved end is the error, and
`1.2` does not precede `1.2`. **The comparison is not the bug**: the checker
tests `at < o_end && o_at < end`, a correct symmetric half-open intersection.
The bug is the right-hand side. `0.8 + 0.4` in IEEE-754 is
`1.2000000000000002`, so the hand-off lands one ULP inside the previous clip.
`0.5 + 0.25 → 0.75` passes; `0.1 + 0.2` and `0.2 + 0.4` do not. The same leak is
printed at the author by `E-TIMELINE-DURATION`: *"below the max resolved clip
end 1.2000000000000002"*.

**Is**, per **D-H** — integer milliseconds, not an epsilon. An epsilon replaces
one false positive with an unpredictable class of them; milliseconds remove the
class.

### 10.1 The authorable syntax

The authorable time-valued attributes are exactly three, plus the timeline's
own: clip `at`, cross-cutting `duration`, cross-cutting `delay`, and
`<timeline duration>`. (`wait` is a boolean policy, `::bg{time}` is a
categorical label, and `::vfx{transition}` is an identifier; none is a time
magnitude. `after`, `now()` and `quest.<id>.activatedAt` are narrative time, a
different clock, untouched.)

Each is authored as it always has been: **a decimal number of seconds**, with
at most **three** fractional digits.

```lute
::vfx{type="shed" at="0.8" duration="0.4"}
::vfx{type="pressure-drop" transition="cut" at="1.2"}
```

A value carrying more than three fractional digits is **`E-TIME-RESOLUTION`**,
an error naming the resolution limit. There is no rounding: a timeline the
author cannot see the difference in is a timeline whose diagnostics they cannot
predict, and `1.2000001` — the epsilon superstition T7.2 measured an author
acquiring — must be rejected rather than quietly honoured.

### 10.2 The conversion

> A time value's canonical representation is a **non-negative integer number of
> milliseconds**, obtained from the authored decimal **by shifting the decimal
> point three places** — never by multiplying a binary floating-point value.

`0.35` is `350`. `0.8` is `800`. `1.2` is `1200`. Exactly, for every value the
grammar admits, with no rounding step to specify and no representation error to
inherit. Performing the conversion on the parsed `f64` would reintroduce the
class this section removes at the one point it is easiest to overlook.

All cursor arithmetic — a clip's resolved end, an omitted `at` continuing from
the previous clip, the maximum resolved end across tracks, and the barrier —
is integer addition and integer comparison in this domain. `E-CLIP-OVERLAP` and
`E-TIMELINE-DURATION` compare integers and MUST print the authored decimal, not
a reconstructed float.

**Resolution limit: 1 ms.** Two clips whose starts differ by less than a
millisecond are the same instant, and `E-WRITE-CONFLICT`'s "same instant"
(`0.1.0 §11.4`) is defined at that granularity.

A value that does not parse as a decimal number at all keeps its current
behaviour (a clip `at` is treated as absent; a `duration` resolves to zero).
That is pre-existing, it is not what #26 is about, and it is recorded as
underspecified rather than changed here — see §14.

### 10.3 The artifact keeps seconds

**D-T.** `Stamp.at`, `Stamp.duration`, `Stamp.delay` and the barrier's `at`
remain JSON **numbers in seconds**, emitted as milliseconds divided by 1000.

An engine never performs cursor arithmetic — the compiler resolves every clip's
absolute `at` before lowering — so exactness is a compile-time property and
paying for it at the boundary buys nothing. Changing these fields to
milliseconds under the same names and the same JSON type would be the worst
available break: an engine reading `at` as seconds would place every effect a
thousand times late with nothing to detect it, and renaming them is an IR delta
far larger than **D-I** sanctions.

The consequence is a **value** change, not a shape change: a clip whose `at` is
cursor-derived now emits `1.2` where the accumulated float previously emitted
`1.2000000000000002`. That is a correction and it is expected.

## 11. Warnings the checker could already compute

### 11.1 `W-DOMAIN-UNREAD` — a declared domain nothing reads

**Was** (T5.3). Declare `enums: reason: [...]` and it appears in
`projectEnums (8)` beside the seven enforced slots, with no mark distinguishing
it, and ships into the compiled artifact's `enums` array — the array documented
as making the artifact *"self-describing about the vocabulary it was compiled
against"*. It enforces nothing. `enums: sausage: [a, b]` behaves identically.
An author who declares a vocabulary for `::end{reason}` and sees it on two
surfaces has every reason to believe their ending ids are typed.

**Is.** A declared domain that **no active construct reads** is
**`W-DOMAIN-UNREAD`**. The checker already computes the reading set — it is
exactly what produces `E-DOMAIN-UNKNOWN` (`0.9.0 §3`) — so this is the same
question asked in the other direction.

The reading set is the set of domain-typed attribute slots in the **resolved
capability snapshot**, not a fixed list: a plugin directive declaring
`{ domain: reason }` makes `reason` read, and the warning stops.

**`W-DOMAIN-UNREAD` is project-wide only** (**D-V**). It is emitted by
`check-project`, computed over every document under the root, and a
single-document `lute check` never emits it. A domain declared in a shared
schema is read by *some* document, and warning on the scene that happens not to
read it would be a false positive on the most common layout there is.

### 11.2 `W-EXIT-INERT` and `W-STAGE-ABSENT` — stage state the reducer holds

**Was** (T2.1, T2.4). *An exit written where the departure happens is inert:*
`@vesna{code="0030" emotion="hollowed" action="go-under"}:` — `action` is a
documented content-line attribute and `go-under` is a declared member of the
`action` domain's `exits:`. `ok` at every gate including `--deny-warnings`; the
artifact keeps `"action":"go-under"` on the line and emits **no** `exit`. *A
character exits, keeps speaking, and exits again:* a scene doing exactly that is
`ok … (0 warning(s))` under `--deny-warnings` and compiles to **two**
`exit: true` records with a line between them. The checker removes the character
on the first exit and then consults that knowledge one conjunct away, in
`auto-pose-reset`'s guard, using absence as "nothing to reset" and never as "the
author staged something impossible".

**Is**, two warnings (**D-X**), both against the injection reducer's threaded
stage state — the same state `0.9.0 §5` already folds over component bodies.
The severity tier is settled by precedent: this is the *"this staging attribute
is not doing what you think it is doing"* class.

- **`W-EXIT-INERT`** — a content-line `action=` whose value is a member of the
  resolved `action` domain's `exits:`. The attribute is honoured as an action
  and does **not** remove the character from the stage; the two-event form
  (`@vesna{…}:` then `::auto{character="vesna" action="go-under"}`) is what
  does, and the message names it. The resolved domain is demonstrably in hand
  at that site, since `E-BAD-ENUM` enumerates its members on that exact
  attribute.

  **Its discharge path is stated, not implied** (**D-AD**). §12.3 removes a
  warning for having no expressible remedy, and a warning this document adds
  must not carry the same defect. There is no `--allow` and no in-source
  acknowledgement — `0.6.1 §6` is untouched — so the remedy is in the content
  or in the vocabulary, and there are exactly two:

  1. **Write the two-event form.** If the character does leave, say so where it
     happens: keep the line, and follow it with
     `::auto{character="…" action="<exit member>"}`. The warning is discharged
     and the artifact gains the `exit` record the author believed they already
     had.
  2. **Stop declaring that member an exit.** If the value is a *pose* — the
     character sinking while still speaking — then it is not an exit, and the
     project's `action` domain should not list it under `exits:`. Removed from
     `exits:`, it becomes an ordinary action member: legal on a content line,
     warning-free, everywhere in the project.

  The warning stands, and the second remedy is why. If a project declares
  `go-under` an exit, then in that project `go-under` **means** exit, and a
  pose sharing the name is ambiguous by construction — the ambiguity lives in
  the vocabulary, which is where it is fixed. The message MUST name **both**
  remedies. A warning whose remedy exists but is undocumented is
  `W-UNPROVEN-RELATIONAL` again by another route.
- **`W-STAGE-ABSENT`** — a staging event for a character the threaded stage
  state records as **not on stage**, in two positions:
  1. a spoken content line whose speaker was removed by a declared exit earlier
     in the walk, with no intervening show;
  2. an `::auto` whose `action` is a declared exit member, for a character
     already off stage.

  It fires **only after an explicit declared exit** and only until a re-show. A
  character who simply has not been shown yet is put on stage by their first
  line, as today; that is not the finding and MUST NOT warn.

## 12. Relaxations and corrections

### 12.1 A parse failure inside `::set` names `::set`'s empty attribute surface

**Was** (T3.6). `::set{run.shedPressure += 3 when="run.shedPressure > 0"}` →
`error [E-CEL-PARSE] '=' assigns; comparison is '==' — did you mean
'3 when=="run.shedPressure > 0"'?`. The `when=` was swallowed into the CEL
expression, so the parser offered the fix it offers for `if (x = 1)`. Apply the
suggestion verbatim and the next run rejects it:
`error [E-CEL-PARSE] not a valid condition expression`. The real problem is
that `::set` has no attribute surface at all: its grammar is
`Set ::= "::set{" Path WS AssignOp WS CelExpr "}"` (`0.1.0 §7.3.3`) and
everything after the operator is expression text.

**Is.** A CEL parse failure **inside a `::set` body** MUST say so — *"`::set`
takes no attributes; guard a write with `<match>`/`<when>`"* — and MUST
suppress the `==` suggestion there. Same code, same severity; a suggestion that
does not parse is worse than none, because did-you-mean is usually excellent
here and following it is reasonable.

### 12.2 `&&` narrowing runs in every CEL slot

**Was** (T5.6). `fail="isSet(run.ending) && run.ending == 'shed-with-module'"`
on a quest → `E-MAYBE-UNSET: state path 'run.ending' may be read before it is
set (no default, no dominating '::set', no guard)` — with a guard five
characters to its left. The same expression on a scene content line's `when=` is
`ok`. `isSet(run.ending)` alone in an objective's `done=` is `ok`.
Intra-expression `&&` short-circuit narrowing **is** implemented; the quest
predicate slot does not run it.

**Is.** The definite-assignment reader's intra-expression narrowing applies in
**every** CEL slot the language has. `<quest start>`, `<quest fail>`,
`<objective done>` and `<objective when>` are no longer exempt. `isSet(p) && …`
is `ok` in all of them, and an unguarded read is still `E-MAYBE-UNSET` in all
of them. This is a relaxation: it can only turn a red document green.

Separately, and a message correction rather than a rule change (#17):
`E-MAYBE-UNSET` on `quest.<id>.state` describes a definite-assignment problem
the author cannot fix, because the path is engine-populated and not
author-writable. It MUST instead name the two forms that work — read
`quest.<id>.objectives.<oid>.done`, or gate with `after="completed(…)"`.

### 12.3 `W-INJECT-CONFLICT` is removed

**Was** (T5.8).
`::auto{character="vesna" anchor="center" action="brace"}`, where the `anchor`
slot is `{ members: [port, center, starboard], default: center }` →
`warning [W-INJECT-CONFLICT] 'vesna' is shown with an explicit anchor="center"
that 'auto-anchor-on-show' would otherwise inject`. The message is accurate and
the mechanism is right, but the only authored shape it fires on is
**agreement**: a *different* explicit anchor is honoured silently, and no
anchor at all is silent. `port`, which most Anseo scenes write explicitly, is
fine.

The cost is not cosmetic. There is no suppression — `lute check` has `--deny`
and `--deny-warnings` and **no `--allow`**, and no in-source acknowledgement.
A project on `--deny-warnings` in CI, which the toolchain's own docs encourage,
cannot express "centre, on purpose" at all.

**Is** — the code is **removed**, not narrowed (**D-U**).

`auto-anchor-on-show` is the only injection rule that can produce it, and
equality with the declared default is its only emission condition. Adding "and
the values differ" to that condition makes it unsatisfiable, so narrowing and
removing are the same change described two ways, and a code with no reachable
trigger is precisely the kind of thing this release exists to stop shipping.
`0.9.0 §5`'s widening of it over component bodies is thereby moot.

**What is lost, stated plainly** (**D-AA**). `W-INJECT-CONFLICT` is the only
record anywhere in the toolchain that the author wrote what a rule would have
injected, and removing it **drops that information**. There is no other
surface. An earlier draft of this section claimed an `injected: false`
provenance entry retained the fact in the resolved view; **there is no such
entry**. Every `Provenance` the injector constructs is `injected: true`, the
conflict arm emits a diagnostic and no `InjectedCommand` at all, and the doc
comment that says otherwise (`lute-compile/src/inject.rs:107-108`) is design
intent that was never implemented — it is corrected in the same change, because
it is what produced the claim. Building the entry instead was considered and
rejected: `inject_cmd` turns **every** `InjectedCommand` into a `sprite` record
in the artifact, so an `injected: false` record would plant a spurious anchor
command beside the author's own — an IR consequence **D-I** does not sanction,
and one that would need the compile layer to filter on a field no consumer
reads. Appendix B records the IR follow-on.

Removal is still right — a code whose only trigger is agreement with the
declared default is exactly what this release exists to stop shipping — but it
is a **straight loss**, not a migration to another surface, and this document
says so rather than sending the next reader looking for something they will not
find.

One thing it is **not**: `0.6.1 §6`'s refusal of an `--allow` flag is
untouched. This section removes a warning that was wrong; it does not reopen
suppression.

Consequence for the corpus: `check-project docs/examples` drops from **4**
`W-INJECT-CONFLICT` to **0** (`anseo/scenes/bridge.lute:11`,
`anseo/scenes/spine-b.lute:44`, `bianca-s01ep02.lute:52`,
`idola-project/date-minigame.lute:38`, all verified at HEAD). Two of those are
documented as deliberate in `docs/examples/anseo/README.md:98-110` — items 1
and 2 of that file's "wrong on purpose" list. Those entries and their finding
cross-references must be deleted in the same change, or the example documents a
warning it no longer emits; and the list's opening count at `README.md:94-96`
(*"Five things …"*) must be corrected with them. §13.5 states what it becomes
once §8 takes item 4 as well.

### 12.4 A component param may use the long form

**Was** (T6.6). The accepted param grammar is exactly two forms —
`pressure: string` and `pressure: { enum: [steady, rising] }`.
`pressure: { type: string }` is
`E-COMPONENT-PARSE: … each entry must be 'name: <type>' (dsl §13)`. The long
form is how `state:` entries are written, how `defs:` entries are written, and
how the `anchor` domain is written in Anseo's own vocabulary — and
`components-and-extends.md` says component params are *"typed exactly like a
def param"*.

**Is.** `{ type: X }` is accepted as a synonym for `X`, for every type spelling
`X` the shared `Type` deserializer admits. The wrapper takes **no other key**:
`{ type: string, default: "steady" }` and `{ enum: [...], default: … }` remain
`E-COMPONENT-PARSE`. Param **defaults** are not added — the issue explicitly
does not ask for them, and a default would need a rule for how it interacts
with `E-COMPONENT-ARG`, which is a separate design.

`E-COMPONENT-ARG` on an omitted argument is unchanged, at the `::use` line and
column.

## 13. Migration

Six changes are `LANG`. Five of them can redden existing content; `defaults:`
(§6) is pure addition and cannot. Corpus impact below was **measured**, not
assumed, against `docs/examples` (18 Anseo documents, six nested example
projects, and the root-level example scenes), the six `conformance/`
mini-projects, and `crates/lute-compile/tests/fixtures/`, on
`feat/lute-0.10.0` at HEAD.

Baseline: `lute check-project docs/examples/anseo` →
`ok … (18 file(s), 13 project-wide warning(s))`, exit 0.

### 13.1 `E-SET-TYPE` (§3)

**What an author sees.** At the right-hand side's own span:

```
error [E-SET-TYPE] `::set` writes a `string` into `run.shedPressure`, declared
`number` (dsl 0.10.0 §3)
```

**What they do.** Write a value of the declared type, or change the
declaration. Every report is a write the runtime was already discarding: T3.2
measured `+= "two"` on a `number` producing `final run.shedPressure = 0`, and
`= true` producing a boolean in a path the schema declares numeric.

**Corpus: clean.** All 37 `::set` directives enumerated — 35 in
`docs/examples`, 2 in `conformance`, 0 in `crates/lute-compile/tests/fixtures`.
Every right-hand side is a bare literal (`1`, `2`, `300`, `true`,
`"halsinDead"`, `"blake"`) and every one is well-typed against its
declaration. The one enum write, `run.suspectFocus = "blake"` at
`investigation/scenes/interview.lute:30` and `:35`, names a declared member of
`{ enum: [blake, cass, dana] }`. No right-hand side in the corpus is even
undecidable, let alone wrong.

### 13.2 Closed attribute surfaces (§4)

**What an author sees.** `error [E-UNKNOWN-ATTR]` at the offending attribute's
own column, or `error [E-AS-REMOVED]` with a migration instruction.

**What they do.** Delete the attribute — it was being discarded — or, for
`as=`, run `lute fix`, which performs the `as` → `into` rename and thereby
restores the `set` record the document was silently losing.

**Corpus: clean.** Attribute census over every `<branch>`, `<choice>`,
`<match>`, `<when>`, `<otherwise>` and `<hub>` in `docs/examples` and

cannot be miscounted as attributes:

```
branch{id}  choice{id,label,when,into,value,once,exit}  match{on}
when{is,test}  otherwise{}  hub{id}
```

Every name is in its construct's permitted set. Zero `as=`; zero `goto=` — the
one `goto` hit in the corpus is explanatory prose at
`anseo/scenes/spine-b.lute:101`, not a tag. And **D-L**'s per-position rule
reddens nothing: all three `once` and all three `exit` sit on hub choices —
`investigation/scenes/interview.lute:38,41` under the `<hub>` at `:27`,

### 13.3 Dead gates and contradictory objectives (§5)

**What an author sees.** `error [E-QUEST-UNREACHABLE]` naming the relation and
the declared routes, or `error [E-OBJECTIVE-CONTRADICTION]` naming both
objective ids and the path.

**What they do.** Make the relation producible — assert it in a scene or seed
it in `facts:` — or fix the gate. For a contradiction, one of the two
objectives is wrong; the diagnostic names both because it cannot know which.

**Corpus: clean.** **24** gates across the six Anseo quests, enumerated
tag-anchored: 6 `<quest start=>`, 2 `<quest fail=>`, 16 `<objective done=>`
(27 if the 3 `<objective when=>` visibility guards are counted, which §5 does

recording because it will recur: a scanner that matches `start=` in text rather
than inside a parsed tag picks up
`hold-the-spine.lute:26`, where the string appears **inside a prose comment**
explaining the quest. Two independent recounts hit the same trap from opposite
sides before the tag-anchored number settled. All
four declared relations are producible: `awake` from the `facts:` seed
(`world.schema.yaml:16`) and three asserts, `knows` and `found` from asserts

`can_halt(C) :- awake(C), knows(C, shed_sequence)` over producible premises.
No quest has two required objectives whose `done=` are in-domain scalar

The backlog's regression guard holds: `start="holds(found(toma))"` must **not**

### 13.4 Nested manifests (§7)

**What an author sees.** A manifest error from a command that used to exit 0 —
now carrying the manifest's own path, which it did not before — or
`warning [W-PROJECT-INERT]` naming a nested manifest that does not govern.

**What they do.** Fix the manifest, or invoke the inner root directly.

**Corpus: clean, and both of D-S's disjuncts were measured.** Seven manifests:
`docs/examples/lute.project.yaml` and six descendants (`anseo/`, `episodes/`,
`investigation/`, `showcase/`, `plugindef-project/`, `idola-project/`); none is
nested below another descendant. All seven load without error, so validating
them adds nothing.

*The identity disjunct.* Only `anseo/` declares `identity:`, and both its
templates are the defaults verbatim, so it would resolve identically and
`W-PROJECT-INERT` stays silent there.

*The capability disjunct*, measured at HEAD against the outer root's
`0678492f…`. **D-S compares what each MANIFEST resolves, not what its documents
resolve, and those are different numbers** — a document may declare its own
`profile:` and even a scene-local `plugins:` block, which move the hash without
the manifest saying anything. The probe is therefore a profile-less,
plugin-less scratch document under each root; measuring a real document instead
reports the document's activation and answers a question D-S never asked:

| nested manifest | `capabilityVersion` | differs? |
| --------------- | ------------------- | -------- |
| `anseo/` | `0678492f…` | no |
| `episodes/` | `0678492f…` | no |
| `investigation/` | `0678492f…` | no |
| `showcase/` | `2a5eaaeb…` | **yes** — `pluginsDir`, `catalogDir`, activates `showcase.pack` |
| `plugindef-project/` | `1235ef58…` | **yes** — `pluginsDir`, activates `demo.defs` |
| `idola-project/` | `c7fa83a9…` | **yes** — `pluginsDir`, activates `idola.minigame` with options |

An earlier draft of this table gave `d91cefe6…` for `idola-project/`. That is

`profile: date-minigame` *and* a scene-local `plugins: { idola.minigame: … }`
block — not what its manifest resolves. The conclusion is unchanged (three of
six differ), but the wrong basis would have produced a wrong test: an
implementation that compares document-resolved snapshots reports

So **three** of the six trip **D-S**, not one. The narrowing still earns its
keep — six candidates to three — but the "five of them meaningless" arithmetic
in its rationale row was wrong, and Appendix D now says three.

*What those three cost: nothing green.* `W-PROJECT-INERT` fires only where a
nested manifest **does not govern**, and under `check-project` the nearest

`ok: docs/examples (47 file(s), 18 project-wide warning(s))` at exit 0, with

- `showcase/`'s three documents declare `profile: showcase` and

  profiles, not just `showcase`, at exit 1.
- `plugindef-project/plugin-def.lute` declares no `profile:` and is green under

Nothing in CI compiles from the outer root — both workflows run
`check-project docs/examples` and `lute test docs/examples`. So
`W-PROJECT-INERT` reddens no green target in this corpus and adds no warning to
any invocation CI performs.

### 13.5 Scaffolded mocks (§8) — the reds

**What an author sees.** Anchored at the mock file, naming the offending key
in the message (**D-AB**), never at a line and column. First run:

```
docs/examples/anseo/mocks/playthrough.yaml: error [E-MOCK-SUBJECT] mock
```

### 13.6 Timeline resolution (§10)

**What an author sees.** `error [E-TIME-RESOLUTION]` on a time value finer than
a millisecond.

**What they do.** Round it to a millisecond — and, more usefully, delete the
workaround it was part of.

**Corpus: clean, and it greens a workaround.** All 43 `at`/`duration` values in
the corpus carry at most **two** fractional digits (`.3`, `.35`, `.75`, `1.8`,
…); none exceeds three, so `E-TIME-RESOLUTION` fires nowhere. Twenty-seven of
the 43 are not exactly representable in binary and are today at the mercy of
cursor accumulation. One is a measured casualty: `anseo/scenes/spine-a.lute:37`
carries `duration="0.35"`, a silent substitution for the `0.4` the author
wanted, made to dodge `E-CLIP-OVERLAP` at the `1.2` hand-off on `:38`.
Restoring `duration="0.4"` MUST check clean, and that is this section's
acceptance test.

None can redden a green document, by construction (**D-K**). Of the three that
could change a green project's *output*, two do and the third was measured to
add nothing:

- §12.3 removes 4 `W-INJECT-CONFLICT` from `check-project docs/examples`

- §11.2 adds none: the corpus has no content-line `action=` naming an exit
  member, and no post-exit line or double exit.
- §11.1 adds none, and this was **measured, not inferred from silence**.
  `docs/examples` declares exactly seven domains anywhere in the tree —
  `action`, `anchor`, `emotion`, `mood`, `musicAction`, `vfxType`, `volume`

**Order of work for a 0.9.0-clean project:**

1. **Run `lute fix`** before anything else. It performs the `as` → `into`
   rename §4 now diagnoses, and it is the one migration in this release with a
   mechanical fix.
2. **Read the `E-SET-TYPE` reports as bugs, not as noise.** Every one is a
   write the runtime was already evaluating to nothing.
3. **Fix the mocks.** Add the now-required `file:`, resolved against the mock
   itself, and seed declared paths.
4. **Delete the epsilons.** Any `1.2000001` written to dodge `E-CLIP-OVERLAP`

5. **Hoist frontmatter, if you want to.** `defaults:` is optional and nothing
   requires it.
6. **Restamp.** A document stamped `luteVersion: "0.9.0"` fires the pre-existing

## 14. Non-goals — explicitly rejected

Recorded so they are not re-proposed.

- **Inferring the type of an arbitrary CEL expression.** §3.3 fixes a decidable
  set and accepts everything outside it. A checker that guesses produces false
  `E-SET-TYPE`s on correct counters, whose only remedy is to stop declaring the
  type — strictly worse than the silence being removed.
- **Closing `<quest>`/`<objective>`/`<on>`/`<track>`'s attribute sets.** Not in
  the issue, and `<quest after=…>` has no normative statement to close against.
  §4 names it.
- **General range analysis over CEL for contradictory objectives.** **D-G**
  fixes the domain at path-vs-literal scalar comparisons, which is exactly what
  T9.6 demonstrated. Anything wider is a different feature with a different
  cost.
- **"Nearest manifest wins" for `compile`.** §7 makes the two commands agree
  about *validity* without changing which manifest *governs*. Changing
  governance is a separate change with separate consequences, and the backlog
  rules it out by name.
- **Merging `defaults:` into document frontmatter.** §6.2 is whole-value
  override per key. Deep merge or list concatenation would make a document's
  import list depend on a file the document does not name.
- **Defaulting schema keys.** `enums:`, `state:`, `relations:` and their
  siblings compose through `uses:`/`extends:` already. A second route to one
  job is what `0.9.0 §7` refused.
- **Milliseconds in the artifact.** §10.3. Same field names and same JSON type
  with a 1000× different meaning is the worst available break; renaming them is
  a larger IR delta than **D-I** sanctions.
- **An epsilon tolerance on the clip interval test.** **D-H**. It replaces one
  false positive with an unpredictable class of them.
- **An `--allow` flag or an in-source warning acknowledgement.** `0.6.1 §6`
  refuses it on purpose. §12.3 removes a warning that was wrong rather than
  adding a way to silence warnings that are right.
- **Component param defaults.** §12.4 adds the type synonym only. A default
  needs a rule for its interaction with `E-COMPONENT-ARG`.
- **`W-FACT-UNREACHABLE`** — producibility at ground-fact rather than relation
  granularity (T8.8). It is the one genuinely new analysis the #12 cluster
  proposed, and `T4.3` identifies relation granularity as today's deliberate
  boundary. Scoped separately.
- **A component-schema surface.** Still the right answer to `0.9.0 §6.1`, still
  a separate proposal. §9 makes the two check legs agree about the vocabulary
  that *is* in scope; it does not change what is in scope.

**Underspecified, found while writing, not changed here.** Recorded because an
implementer will hit them: a clip `at` whose value is an `@ref` rather than a
string literal is silently treated as absent; a `<timeline duration>` whose
text does not parse as a number silently resolves to `0.0`; and the author
`state:` guard rejects `list`/`record`/`map` and `narrativeTime` but falls
through for `domain`, `providerRef`, `slotId`, `assetKind` and
`enumFromOption`, which `0.8.0 §4`'s scalar union does not admit. None is in
the 26; each is a real gap. §3.2 states the consequence of the third for
`::set` rather than papering over it: a write into one of those five types has
no required type under §3 and draws no `E-SET-TYPE`.

### `--deny <CODE>` registration

`--deny <CODE>` accepts only a code listed in `DENIABLE_CODES`
(`crates/lute-cli/src/main.rs:505-558`), a hand-maintained sorted const that is
the toolchain's only registry of the codes `check`/`check-project` emit;
anything outside it is a clap **usage error**, exit 2, never a silent no-op.
**D-X**'s rationale depends on that list — *"`--deny <CODE>` must be able to
separate them"* — so maintaining it is part of this release, not a follow-up.

Measured at HEAD: the const holds **177** entries, sorted; it contains
`W-INJECT-CONFLICT`, none of this release's eleven new codes, and **no
`E-TRACE-*` entry at all**. Three edits follow:

1. **Add the eleven new codes** — `E-SET-TYPE`, `E-AS-REMOVED`,
   `E-OBJECTIVE-CONTRADICTION`, `E-DEFAULTS-KEY`, `E-MOCK-SUBJECT`,
   `E-TIME-RESOLUTION`, `W-PROJECT-INERT`, `W-DOMAIN-UNREAD`, `W-EXIT-INERT`,
   `W-STAGE-ABSENT`, `W-COMPONENT-UNVERIFIED`.
2. **Add the four `E-TRACE-*` codes §8's pass now emits** —
   `E-TRACE-MOCK-UNDECLARED`, `E-TRACE-MOCK-TYPE`, `E-TRACE-MOCK-FACT`,
   `E-TRACE-CHOICE`. This is not housekeeping. They are absent today because
   they live in `lute-trace`, a crate `check` never surfaced; §8 makes
   `check-project` surface them, so without this edit `check-project` emits
   four codes that `--deny` rejects as unknown. The
   `every_check_emitted_code_is_deniable` guard rescans the crates whose
   diagnostics `check` surfaces, so **its scan set MUST be widened to include
   `lute-trace`'s mock module** — otherwise the gap ships with no test to
   catch it. That guard is a `#[cfg(test)]` unit test **inside
   `crates/lute-cli/src/main.rs` (`:3997`)**, not in `crates/lute-cli/tests/deny.rs`:
   `deny.rs` exists and contains no such test. The misdirection is the code's
   own — `main.rs:500`'s doc comment names `tests/deny.rs` — and it has now
   misled two independent readers, so **the same task fixes that comment**.
3. **Remove `W-INJECT-CONFLICT`** (§12.3). A superset is harmless — denying a
   code `check` never emits merely protects nothing — so this one is optional
   for correctness and required for honesty: the const is the registry, and the
   code no longer exists.

Net: 177 − 1 + 15 = **191**.

## Appendix B — IR delta (0.9.0 → 0.10.0)

The IR moves on its own merit this time, and the shape changes (**D-I**).

| change | shape | owner |
| ------ | ----- | ----- |
| `Provenance.reason` → **`Provenance.explanation`** | field rename on the injection provenance stamp. The new name is chosen, not incidental: `end.reason` is an **opaque author token a host dispatches on**, while this field is **human-readable English the compiler wrote** (*"pre-loading `vesna`'s first emotion `level` seen ahead of the entrance"*). `explanation` cannot be mistaken for a dispatch key and reads correctly beside `by`: `{ injected: true, by: "auto-pose-reset", explanation: "…" }`. The Rust field, the serialized key, and every golden move together | backlog #36, **D-I**, name settled by **D-AE** — a toolchain item, recorded here because it is the IR delta |
| `Provenance.injected` becomes **constant-`true`** | no shape change: the field is retained and still serialized on every injected record, but with `W-INJECT-CONFLICT` gone (§12.3, **D-AA**) nothing can construct a `false`. Removing the field is an IR break and is deferred to a future cycle; a consumer MUST NOT read a `true` as distinguishing anything | §12.3, **D-AA** |
| clip `at` / `duration` / `delay` and the barrier `at` | **value** change, not shape: still JSON numbers in seconds, now milliseconds ÷ 1000, so a cursor-derived `1.2` stops emitting `1.2000000000000002` | §10.3, **D-T** |
| `enums` array content | a domain a project declares and nothing reads still reaches the artifact; §11.1 warns about it, and does not remove it | §11.1 |

No command `kind` is added, renamed, or removed. `Stamp`'s timing fields keep
their names, their JSON type, and their unit. `sprite.exit`, `shots`, `texts`,
`labels` and the `0.8.0` additions are untouched.

The JSON schema becomes `schemas/lute-ir-0.10.schema.json`. Per the runtime
contract an engine refuses an artifact from a newer `irVersion` major.minor, so
an engine implementing IR `0.9` rejects `0.10.0` artifacts until it accepts
`0.10`; the rename is the only edit it needs.

`capabilityVersion` changes: `W-INJECT-CONFLICT` leaves the code set and eleven
codes join it. `DENIABLE_CODES` moves with it — see Appendix A's
`--deny <CODE>` registration.
