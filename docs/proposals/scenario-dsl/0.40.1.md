# Lute 0.40.1 — runtime condition queries

This specification adds two read-only queries to the runtime contract so a
host can ask the runtime — not a private re-implementation of its evaluator —
whether a condition holds: `evaluate` of an IR expression and `def` of a
project def by name. To make `def` answerable, `project.index.json` carries the
project's parameterless defs. Nothing else changes.

The words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Scope and version contract

| Axis | Change in 0.40.1 |
|---|---|
| Language | none. A 0.40.0 document has the same semantics. |
| IR | `project.index.json` MAY carry `defs` (§3); artifacts are unchanged. Additive under the 0.40 line: `schemas/lute-ir-0.40.schema.json` gains `projectIndex.defs`; engines keep gating on `irVersion` `0.40`. |
| Event | the `evaluate` and `def` queries (§2), the `Evaluation` definition, the rejection `E-RUNTIME-EVAL`. `schemas/lute-events-0.40.schema.json` is regenerated from Rust; inputs, outputs, events and snapshots are unchanged. |
| npm | `@lute-lang/runtime` `Program.evaluate` / `Program.def`, `Errors.EvaluationError`, `Errors.QueryRejection`. |
| CLI | `lute compile --all` writes `defs` into the index (§3); no other output changes. |

Out of scope: defs taking params (a host calls them by evaluating an
expression it builds), evaluating CEL text (a host passes the lowered `expr`
the IR already carries), and any write through a query.

## 2. `evaluate(state, expr)`

1. `expr` is an IR `exprNode` (`lute-ir-0.40` `$defs.exprNode`): the `expr`
   of any `{cel, expr}` slot the IR carries — a beat's `when.expr`, a quest
   objective's `visibleWhen.expr`, a def's `expr` from §3.
2. The runtime MUST evaluate it over the state exactly as a walk evaluates a
   guard: the effective state (written, seeded, then declared default), the
   fact store with derivation under the run's `derive` mode (`holds`, `count`,
   `countDistinct`), `visited(...)`, the reserved clock and quest paths, and
   `now()` from the clock. An `occasion.target` read outside a raise is
   unknown. A state suspended at an await is evaluated over its world before
   the awaited input, as `view` is.
3. The result is an `Evaluation` `{ value: Value, unresolved?: string[] }`.
   `value` is `bool`, `int`, `double`, `str` or `unknown`; for `unknown`,
   `unresolved` lists one reason per distinct unresolved read (an unset state
   path, an undetermined derived fact, `validAt(...)`), and it is omitted for
   a decided value.
4. `value` MUST NOT be `error`. An expression that evaluates to an error
   (division by zero, `int()` of a non-number, a type mismatch) is the
   rejection `E-RUNTIME-EVAL`, whose message names the expression and the
   error.
5. `expr` MUST be exactly an `exprNode`, checked recursively before anything
   is evaluated: every node carries one variant's keys and no other key, each
   field of its schema type (`args` and `list` arrays, `int` within `±2^53`),
   and `op` in its arity's set. Anything else — including a non-JSON string
   at the binding — is `E-RUNTIME-INPUT`.
6. The query MUST NOT change the state; the same state answers the same way
   any number of times.

## 3. `def(state, name)` and the index's `defs`

1. `lute compile --all` writes `project.index.json` `defs`: an object keyed by
   def name, each value a `celSlot` `{ cel, expr, authored? }` — the body
   `@def`-expanded (as a seam condition is) and lowered; `authored` is the
   unexpanded body when it differs.
2. The defs a document sees are its plugins' `defs:`, then its `uses:`
   schema imports over them (the checker's precedence). A document's own
   frontmatter defs are local to it and are not exported. The index carries
   the union over the project's documents, except:
   - a def that takes `params` (it is no condition on its own);
   - a def whose body does not expand or lower (the checker reports it);
   - a def two documents see with different bodies (their `uses:` differ,
     so the name names no one condition). Bodies are compared as lowered
     `expr`: the same condition spelled differently (`@base` in one document,
     written out in another) is one def, exported with the `cel` and
     `authored` of the first such document in source-path order.
   The object is name-sorted and omitted when empty.
3. `def(state, name)` MUST evaluate the def's slot as §2 does and return the
   same `Evaluation` or `E-RUNTIME-EVAL`. A `name` the index does not carry
   (unknown, parameterised, ambiguous) is `E-RUNTIME-INPUT`.

## 4. Bindings

- Rust: `Runtime::evaluate(&State, &serde_json::Value) -> Result<Evaluation, Rejected>`,
  `Runtime::def(&State, &str) -> Result<Evaluation, Rejected>`.
- WASM: `Program.evaluate(state, exprJson)` and `Program.def(state, name)`
  return a `QueryResult` `{ ok, value?, rejected? }` of `Evaluation` /
  `Rejected` JSON.
- `@lute-lang/runtime`: `Program.evaluate(state, expr: Json)` and
  `Program.def(state, name)` are `Effect<Evaluation, QueryRejection>`, where
  `QueryRejection` is `InvalidInput` (`E-RUNTIME-INPUT`) or `EvaluationError`
  (`E-RUNTIME-EVAL`). `E-RUNTIME-EVAL` is not a `RuntimeRejection`: no
  `step` or `begin` returns it.

## 5. Tests

- Rust: an `exprNode` decodes only when every node is one; `evaluate` of
  bool/int expressions, `holds`/`count`, `visited`, an unknown with its
  reason, an evaluation error; `def` of a def (including one that `@def`s
  another), of a parameterised def and an unknown name.
- CLI: `crates/lute-cli/tests/runtime_evaluate.rs` over the fixture
  `crates/lute-runtime-wasm/tests/fixtures/evaluate`, compiled by
  `lute compile --all`.
- WASM and TypeScript: the same fixture through `Program.evaluate` /
  `Program.def`, values and both typed rejections.
