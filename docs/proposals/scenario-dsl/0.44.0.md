# Lute 0.44.0 — player hosting recipes, terminal writes, staging-note closure

This is the normative 0.44.0 contract. The words **MUST**, **MUST NOT**,
**SHOULD** and **MAY** have their RFC 2119 meaning. Conservative choices are
listed in Appendix A; evidence is in the decision note.

## 1. Scope and version contract

Every public version axis is `0.44.0`: toolchain, `luteVersion`, `irVersion`,
`eventVersion`, `snapshotVersion`, the seven npm packages and the generated
contracts. The contract schemas move to the `0.44` line
(`schemas/lute-{ir,events,snapshot,player-bindings}-0.44.schema.json`; bodies
change only in `$id`, title and version stamps) and project files use
`bindingsVersion: "0.44"`. The player's save and profile format version
follows the line (`"0.44"`).

| Axis | 0.44.0 contract |
|---|---|
| Language / IR / Event / snapshot / bindings | Shapes unchanged; stamps and schema line only. |
| Runtime | One refusal message changes (§3.2); codes, classes and acceptance rules are unchanged. |
| Player packages | No API change; documentation (§2). |
| CLI | Unchanged apart from the stamp. |

## 2. Player hosting recipes (#94, #95, #96)

The player's consumer documentation — `packages/player/README.md`,
`docs/player/architecture.md`, and the website `player/custom-hosts.md` in
English and Korean — MUST contain, consistently:

1. **Composing `Director.make` directly.** A code example passing `bundle`
   (required), `host` with `plugin`, and a `cueFactory` wrapper together, with
   the rule that `host.plugin` reaches the default cue factory, a wrapper
   receives that default, and a pre-composed factory must come from
   `Cues.make` for `host.plugin` to be merged (otherwise `Director.make`
   dies).
2. **`LutePlayer.make` over an external runtime session.** An end-to-end
   example: obtain the bundle (`BundleSource.value(bundle)`, or `directory`/
   `url`), build the runtime session (`Session.layer({ seed })` or
   `({ snapshot })` over `LuteRuntime`, the `BundleSource` and an `InputLog`),
   and call `LutePlayer.make({ session, … })` providing the **same**
   `BundleSource` and a `KeyValueStore`; the in-memory store (`Stores.memory`)
   and a persistent one (`BrowserKeyValueStore.layerLocalStorage` in a
   browser; a host-supplied store elsewhere) are both shown or named, and the
   requirements of each `make` overload are stated.
3. **Runtime snapshot versus player save.** A table contrasting
   `Contract.Snapshot` (runtime state; produced by runtime `Session.save`,
   consumed by `Session.restore` and `LutePlayer.make({ snapshot })`) with
   `SaveRuntime` (`{ snapshot, log, backlog }`; produced by the player handle's
   `snapshot`, consumed by its `restore` and stored in save slots), and the
   checkpoint/restore pattern: `handle.snapshot` to checkpoint;
   `handle.restore(save)` on a running player; for a fresh player, start from
   `save.snapshot`, leave `boot`, then `restore(save)` to bring back the log
   and backlog.

The fresh-player restore sequence MUST be exercised by a player test.

## 3. Host writes that accompany an ending (#97)

### 3.1 Rule

When the runtime answers `ended`, it accepts only `newRun` or an `outsideRun`
raise. A host write that belongs to the ending run (ending metadata, scores)
therefore MUST be carried as `writes` on the input that causes the terminal
transition, when that input carries writes — `raiseOccasion`, `advanceClock`,
`bridgeResult` or `hostWrite` — whose writes are applied before the
transition. `choose`, `timeout` and `worldEvent` carry no writes; an ending
they cause records such state in the story (a `::set` in the branch) or in a
`hostWrite` sent before them. `newRun`'s writes seed the run it starts (the
ended run's `run.*` values are then readable as `prev.run.*`); they do not
write into the ended run. This release adds no input and no new place for a
write. The event contract and the player's `send` documentation MUST state
this rule.

### 3.2 Refusal message

A `hostWrite` received at `ended` MUST still be refused with `E-RUNTIME-BUSY`
(class `RuntimeBusy` in TypeScript) and MUST NOT change the snapshot; its
message MUST name the rule:

> the runtime has ended; only newRun or an outsideRun raise is accepted — a
> write that belongs to the ending rides as `writes` on the input that ends
> the run

Every other input refused at `ended` keeps its current message.

## 4. Staging-note closure

1. `lower:`'s closed grammar is enforced since 0.24.0; this release changes
   nothing there.
2. The stage reducer keeps dispatching on the core `::bg` and `::clear`
   directives. The plugin lowering documentation (website
   `plugins/manifests.md` EN/KO) MUST state that a plugin directive lowered
   to a `bg` record changes the background only — characters on stage are not
   auto-hidden and their pose bookkeeping carries over — so an author exits
   characters (or uses `::clear`) explicitly before a plugin scene change.
3. `docs/superpowers/notes/2026-08-10-staging-tag-dispatch.md` is marked
   `Superseded` with an addendum pointing to the 0.44 decision note.

## 5. Out of scope

Stage reducer dispatch on the lowered record kind (first 0.45 candidate),
`--fields` projection, an `--agent` profile, batch `patch` input, per-report
JSON Schema documents, C ABI, concurrent presentations.

## 6. Breaking changes and migration

| CHANGELOG class | Change | Migration |
|---|---|---|
| Release | All axes and packages stamp `0.44.0`; schemas move to the `0.44` line; `bindingsVersion: "0.44"`; save/profile format `"0.44"`. | Widen version gates to 0.44; update `bindingsVersion`. |
| Runtime | `hostWrite` at `ended`: same code, a message that names the rule. | None (codes are the contract). |
