# Lute Scenario DSL — 0.12.0: Forward Jump

- **Version:** 0.12.0
- **Status:** Draft
- **Date:** 2026-08-19
- **Scope:** the language axis gains ONE new control-flow primitive family: a
  position label (`::mark{id}` / a content line's `id=`) and a forward jump
  to it (`::next{to [when]}`, unconditional or CEL-guarded). Two new core
  directives, one new content-line attribute, four new diagnostic codes, no
  new IR command kind — the jump reuses the SAME `JumpCmd` a branch/match
  converge already emits.
- **IR:** `irVersion` is unaffected on the SHAPE axis — `kind: "jump"` and
  `kind: "match"` already exist and are unchanged; this release is purely
  additive at the DOCUMENT level, not the wire level. `capabilityVersion`
  moves (it is a content hash of the directive table, §6) — that is an
  automatic, unauthored consequence of declaring `mark`/`next`, not a
  reviewable IR decision.
- **Design record:** none published separately; this file is the design
  record, following the `0.8.0`/`0.10.0` precedent of a single combined
  motivation + spec document for a release with no prior backlog entry to
  cite.

## 1. Motivation

Every existing control-flow construct in the language is STRUCTURED: a
`<branch>`/`<hub>`/`<match>` forks and converges, a `::use` inlines, an
`::end` terminates. None of them can express "resume reading somewhere else
already written" — the one shape narrative branching structures reach for
constantly: two choices that diverge for a beat and then share the same
scene, or a gated aside that either detours through a whole shot or
rejoins immediately after itself. Authoring that today means literally
duplicating the shared content into every arm, because there is no way to
name a point in the document and jump to it.

`::mark{id}` names a point. `::next{to}` jumps to one, forward only. That is
the entire feature: a label and a goto, scoped tightly enough that it adds
no new reasoning burden to `check`, `compile`, or `trace` — each of those
already own the machinery this reuses (converge labels, the gated-line
guard desugar, the walk's own document order).

## 2. Grammar (no production change)

Both `::mark{…}` and `::next{…}` parse through the EXISTING generic
`Directive ::= "::" Ident Attrs?` production (dsl 0.2.2 §7.2) — the same
shape `::end{reason}` already has. `lute-syntax` gains exactly one
targeted addition, scoped to a single tag:

> `::next{to="…" [when="…"]}`'s `when` is extracted into a typed `CelSlot`
> the SAME way `Line.when`/`Choice.when` are (`take_cel`, `parser.rs`),
> stored on a new `Directive.when: Option<CelSlot>` field. Every OTHER
> directive's parse is byte-identical: the field is `None` unless
> `tag == "next"`.

`id=`/`to=` are ordinary string attrs, requiring no parser change at all — a
content line's attribute scanner has no key whitelist (that lives in the
checker, §3), and `::mark`'s `id`/`::next`'s `to` are just two more manifest-
declared string attrs on a generic directive, exactly like `::end`'s
`reason`.

```
::mark{id="checkpoint"}
@narrator{id="afterCheckpoint"}: text
::next{to="checkpoint"}
::next{to="checkpoint" when="run.blessed"}
```

## 3. Labels — one document-wide namespace

Two DISTINCT syntactic forms bind to the SAME namespace:

1. `::mark{id="x"}` — a pure position anchor. It emits no record; the label
   resolves to whatever record comes immediately after it in document order
   (mirrors an anonymous branch/match converge label,
   `lute-compile::cfg::Emitter::bind`), or, trailing past the last record of
   its enclosing shot/quest unit, that unit's one-past-end converge address
   (the SAME synthetic address a branch converge at shot-end already
   produces) — which the runtime's sorted-next-addr fallback resolves onto
   the FOLLOWING unit's first record. This is how "join a later shot"
   actually works: no special case, the existing converge/resolve machinery
   already does it.
2. A content line's `id="x"` attr — the label names that LINE's own record.

Both forms share ONE table, spanning the WHOLE document (every shot, every
quest — not reset per shot the way `lute-compile`'s internal numeric
converge labels are). A repeated `id` — `::mark`/`::mark`, `::mark`/line,
or line/line — is `E-MARK-DUP`, regardless of which two forms collide.

`id=` is line-scoped: `lute-check::content_line::KNOWN_ATTRS` admits it, but
(unlike every other member of that list) it is never a `LineCmd` field — it
is consumed purely by the addressing pass (§5) and never serialized.

## 4. `::next` — unconditional and guarded

`::next{to="x"}` is an unconditional forward jump: the walk continues at
`x`'s resolved address, and nothing else in the SAME straight-line body
after it can ever run — `W-CODE-AFTER-NEXT` flags it, mirroring
`W-CODE-AFTER-END` (dsl 0.8.0) verbatim, including its per-body scoping (a
`::next` inside one `<choice>` says nothing about a sibling choice or
content after the enclosing `<branch>`).

`::next{to="x" when="COND"}` is GUARDED: `COND` decides at the jump's own
position, exactly like a gated content line's `when=` (dsl 0.4.0 §7.2) —
`true` jumps, `false` falls through to the next node, `unknown` is
authoring-tool-dependent (the same K3 treatment every other guard gets).
Because a guarded `::next` has a fall-through, `W-CODE-AFTER-NEXT` does NOT
fire after it — content after a guarded jump is reachable on the `false`
arm.

### 4.1 Diagnostics

| Code | Severity | Fires when |
|---|---|---|
| `E-MARK-DUP` | Error | a label id (`::mark`/line `id=`) is declared more than once anywhere in the document |
| `E-NEXT-UNDEFINED` | Error | `::next{to}` names no label anywhere in the document |
| `E-NEXT-BACKWARD` | Error | `::next{to}` names a label at or before its own document position — jumps are FORWARD ONLY (§7) |
| `W-CODE-AFTER-NEXT` | Warning | an unconditional `::next` is followed by more content in the same straight-line body |

`to`/`id` missing entirely is the EXISTING generic `E-MISSING-ATTR` (both
attrs are manifest-declared `required: true`, §6) — no new code needed. A
malformed `when=` CEL expression is the EXISTING `E-CEL-PARSE`/profile
family, reached through the identical `check_cel_slot` call a gated line's
`when=` reaches (dsl 0.4.0 §7.2's own validation path) — again no new code.

## 5. Lowering — `::mark` emits nothing, `::next` reuses `JumpCmd`

`::mark{id}` lowers to NOTHING: `lower_directive`'s `mark` arm returns
`None`, exactly like the `__component-begin`/`-end` normalization
sentinels. Its label is bound during the stage walk
(`stage::walk_seq`/`walk_quest`'s own `mark` interception, BEFORE the
generic `Node::Directive` dispatch reaches `lower_directive` at all) via a
NEW `Emitter::bind_named(String)` — a NAMED sibling of the existing
`Emitter::bind(Label)` used for anonymous converge labels. A content line's
`id=` binds the same way, at the exact point its OWN `LineCmd` is about to
be pushed (after any preceding injected sprite record, so the label never
resolves to an unrelated `::auto`-injected anchor/preload instead of the
authored line).

An UNGUARDED `::next{to}` lowers straight to `Command::Jump(JumpCmd{ target:
… })` — the SAME command kind a branch/hub/match converge already emits;
`compile-IR`'s command vocabulary gains no new `kind`. The target starts as
a NAMED placeholder distinct from the existing anonymous `"@<n>"` symbol
scheme (so the two never collide), resolved by a document-wide pass in
`address::assign_addresses` — built BEFORE any shot is consumed, so a
`::next` authored in shot 1 can target a label in shot 4 (§3's whole point).

A GUARDED `::next{to when}` is desugared, in `normalize` (before staging,
the SAME pass position the gated-line sugar already runs at), into the
IDENTICAL canonical one-arm `<match>` a gated line desugars to (dsl 0.4.0
§7.2's `synth_when_match`, mirrored verbatim as `synth_when_next_match`):
the guard becomes the match subject, one `When test="$"` arm wraps the now-
unconditional `::next`, and an empty `<otherwise>` is the implicit
fall-through. `stage::walk_match`'s existing two-arm lowering handles both
outcomes with zero new lowering code — the SAME machine a gated line's
guard already goes through.

## 6. Manifest — `mark`/`next` join the `lute.core` directive table

Declared in `lute.core`'s `directives/staging.yaml`, admitted at the exact
same place `::end` is:

```yaml
- name: mark
  attrs:
    - { name: id, required: true, type: string }
  lower: { kind: builtin, name: mark }
- name: next
  attrs:
    - { name: to, required: true, type: string }
    - { name: when, required: false, type: string }
  lower: { kind: builtin, name: next }
```

Neither carries a `semantics:` flag — `terminatesWalk` (the one flag
`::end` declares) does not fit: an unguarded `::next` DOES always divert
the walk, but that fact is dispatched by TAG in `lower_directive`/
`check_code_after_next`, the same way `::end`'s own `terminatesWalk`
declares-but-does-not-drive dispatch (dsl 0.8.0's own precedent, restated
in `SEMANTICS_VOCAB`'s doc comment). `capabilityVersion` is a content hash
over the whole directive table (`snapshot::capability_version`), so
declaring these two moves it automatically — no manual bump, no reviewable
decision on this axis.

## 7. Why forward-only

A `::next` may target only a label that is STRICTLY LATER in document
order (`E-NEXT-BACKWARD` otherwise). This is not an arbitrary restriction:
`lute-trace`'s walk (dsl 0.4.0 §4) is a bounded, terminating, structured
recursion over the document tree, and every reachability/definite-
assignment pass in `lute-check` relies on the same DAG shape — a body's
successors are always STRUCTURALLY later than the body itself, never a
cycle back through already-analyzed content. Admitting a backward jump
would turn the walk into a graph with cycles, which:

- breaks `lute-trace`'s termination guarantee (dsl 0.4.0 §4.2's D1
  quarantine: a bounded, terminating preview, never a loop);
- breaks `check_definite_assignment`'s forward-only fixed-point (dsl §9.4's
  lattice walk assumes a DAG — a backward edge would need real loop-
  fixpoint iteration this pass was never designed for); and
- breaks the addressing invariant "lexicographic addr order == execution
  order" (dsl 0.8.0 adoption G2) for anything downstream that sorts by
  `addr` expecting a single forward pass.

Forward-only keeps the walk's DAG property intact by construction: a
`::next` is, structurally, exactly one more kind of converge edge — the
SAME shape a branch/match/hub convergence already contributes to the
command graph, just author-named instead of compiler-synthesized.

## 8. Non-goals

- No LSP go-to-definition for `::next{to=}` in this release. The existing
  `nav.rs` local-span-lookup pattern (`scene.choices.<id>` → the owning
  `<branch>`'s span) is the closest precedent, but wiring a document-wide
  label index into the LSP's incremental model is deferred — toolchain
  work, not a language-axis blocker.
- No backward jump, no jump INTO a different document, no label declared
  inside a `<timeline>` clip (`::mark`/`::next` are explicitly rejected
  there — a `<track>` body admits only staging directives and `::set`, dsl
  §7.4, mirroring `::end`'s own timeline-clip rejection).
- No new `Command` kind, no IR shape change, no schema file move (§ir note
  above).
