# Lute Scenario DSL — 0.10.1: No Language Change

- **Version:** 0.10.1
- **Status:** Draft (**alignment-only** revision of 0.10.0)
- **Date:** 2026-08-10
- **Scope:** no grammar production, no static-semantic rule, no IR shape, no
  `decide()` (§5.1 R1–R5) change, no Closure change. Language 0.10.1 is
  **byte-for-byte 0.10.0 semantics** for every document. The single change on
  this axis is the version stamp: `LUTE_LANG_VERSION` advances from `"0.10.0"`
  to `"0.10.1"` in the release that aligns the toolchain and the IR at the same
  number.

## 1. Why this file exists

This revision changes nothing an author writes. It is written down anyway,
because [`docs/versioning.md`](../../versioning.md) makes two commitments that
would otherwise contradict each other:

> Every release re-aligns every visible axis number to that release's number.

and

> **Language** … History is the versioned spec stack under
> [`docs/proposals/scenario-dsl/`](.).

Together they mean a language version with no entry in this stack is a hole:
a reader who resolves `luteVersion: "0.10.1"` against the stack finds nothing,
and cannot distinguish "this revision changed nothing" from "the revision was
never written down". `0.7.0` set the precedent for closing that hole — it, too,
was an alignment-only revision, and it says so in the same words. This is the
second.

## 2. What changes on the language axis

`LUTE_LANG_VERSION` → `"0.10.1"`. Nothing else. Every diagnostic code, grammar
production, admission rule, vocabulary slot, and `decide()` result is exactly as
`0.10.0` defined it. Historical citations of the form "dsl 0.10.0 §N" continue
to name the proposal that defined the rule and are **not** rewritten.

The IR advances to `0.10.1` under the same alignment rule and is likewise
shape-identical. `schemas/lute-ir-0.10.schema.json` is **not** renamed and its
`$id` does not move: the runtime contract gates on `major.minor`
([`docs/runtime/execution-model.md`](../../runtime/execution-model.md#version-negotiation)),
`0.10.1` and `0.10.0` share theirs, and a consuming engine that accepts one
accepts the other with no edit. This is the first release where the alignment
rule moves a number that the schema filename deliberately does not follow —
`0.7.0` renamed its schema because its minor moved.

## 3. What the release does change

The two fixes `0.10.1` carries are **toolchain**, per
[`docs/versioning.md`](../../versioning.md)'s "which bump when": both are cases
of a validator accepting an input it was specified to reject, or a command
resolving less context than its siblings.

- `lute test` resolves a governing project through `--project`, exactly as
  `check`, `compile` and `trace` already do. Before this, the subcommand had no
  such flag and passed `None` unconditionally, so a document that reaches its
  schema through a manifest's `defaults: uses:` or its directives through a
  `profile:` could not be tested at all.
- An `assetKind` **segment** declared `{ domain: … }` — or any other `Type`
  outside the closed production the plugin spec gives a segment position — is
  rejected at plugin load instead of being accepted and enforcing nothing.

Neither touches this stack. See [`CHANGELOG.md`](../../../CHANGELOG.md) for the
full entries and
[`plugin-system/0.0.1.md` §7](../plugin-system/0.0.1.md) for the segment
production the second one enforces.

## 4. Stale-stamp remedy

Because the language version advances, a document carrying
`luteVersion: "0.10.0"` now lags `LUTE_LANG_VERSION` and fires
**`W-LUTE-VERSION-STALE`** (dsl 0.6.1 §3). The stamp is still never validated
against capabilities (D13 stands); the warning is a freshness signal only. The
remedy is mechanical — restamp to `luteVersion: "0.10.1"` — and because
`0.10.1` is byte-for-byte `0.10.0` semantics, a `0.10.0`-clean document
restamped to `0.10.1` checks clean with no other edit.

## 5. Non-goals

- No grammar, semantic, or IR shape change.
- No new diagnostic code on the language axis and none removed. The release does
  add one **plugin-load** code, `E-PLUGIN-ASSET-SEGMENT-TYPE`; it fires on a
  plugin package, never on a `.lute` document, which is why it is a toolchain
  entry and not a language one.
- No change to the axis-independence policy. The axes MAY drift when an axis
  genuinely does not change; this release re-aligns the visible numbers so a
  single release presents a single number, and this file is where a reader
  learns that the language axis did not earn its move.
