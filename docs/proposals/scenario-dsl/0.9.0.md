# Lute Scenario DSL — 0.9.0: Vocabulary Ownership

- **Version:** 0.9.0
- **Status:** Draft
- **Date:** 2026-07-30
- **Scope:** the compiler declares content-vocabulary **slots** and ships **no
  members**; every member comes from a document's own inline `enums:`, a project
  schema's `enums:`, or a plugin's `enums` export. Adds the `enums:` long form
  (`members` / `default` / `exits`) and four validation codes; makes an
  undeclared slot an error; deletes the hardcoded exit heuristic and the
  hardcoded default anchor; and closes five
  validation bypasses that let an imported component body skip whole-document
  checks the same content gets at scene level.
- **IR schema unchanged at `0.8.0`.** No artifact field is added, renamed, or
  moved. This is the one thing the release refuses to trade.
- **Companion:** [`plugin-system/0.0.3.md`](../plugin-system/0.0.3.md) — the
  `enums` export long form, the `lute.core` empty `enums`, and the closed
  `semantics` vocabulary shrinking from twelve flags to ten.
- **Design record:**
  [`2026-07-29-lute-vocabulary-ownership-design.md`](../../superpowers/specs/2026-07-29-lute-vocabulary-ownership-design.md).
  Its decision labels (D-A … D-F) are cited by the diagnostics this release
  emits, so they are quoted here rather than renumbered.

## 1. Motivation

Lute ships as a general authoring toolchain; any one game is a consumer. A
concrete list of emotions inside the compiler is therefore a **category error**,
not merely an inconvenience — the whole premise of the language is that
vocabulary is declared data.

Until 0.9.0 the six baseline vocabularies (`emotion`, `mood`, `vfxType`,
`anchor`, `volume`, `musicAction`) shipped as closed members inside the
built-in `lute.core` plugin, and **no route could extend or replace them**: a
project schema declaring `emotion:` got `E-DOMAIN-DUP` and had its members
dropped; a project's own capability plugin exporting `emotion` failed whole-
project resolution with `E-PLUGIN-DUP-ACROSS`; and `lute.core` cannot be
deactivated. The data-catalog foundation design had already classified
`emotion`/`mood`/`vfxType` as project-definable — the implementation simply did
not follow its own classification.

Measured against one real catalog: 20.7% of 30,861 authored `emotion` values
were unrepresentable (its authors say `furious`, the core said `angry`), and
`action` — 9,880 values across 53 distinct ids — received **zero** validation,
because the checker skipped the attribute entirely when nothing declared the
domain. A typo like `step-foward` shipped silently.

0.9.0 removes the special case in both directions: the members become yours,
and using a slot you have not declared is an error.

## 2. The core declares slots, never members

`lute.core`'s `enums.yaml` is **empty**. Seven names survive as *types on
attributes*, with no member list anywhere in the binary:

| Slot | Bound at | Type in 0.9.0 |
| ---- | -------- | ------------- |
| `emotion` | content line `emotion=` | `{ domain: emotion }` |
| `action` | content line `action=`, `::auto{action}` | `{ domain: action }` |
| `anchor` | `::auto{anchor}` | `{ domain: anchor }` |
| `mood` | `::music{mood}` | `{ domain: mood }` |
| `volume` | `::music{volume}` | `{ domain: volume }` |
| `musicAction` | `::music{action}` | `{ domain: musicAction }` |
| `vfxType` | `::vfx{type}` | `{ domain: vfxType }` |

Two of those types are new: `::auto{action}` and `::music{mood}` were free
`string`s, which is why the `mood` domain had been declared-but-inert since it
shipped, and why `action` went unchecked. They are domain-typed now so the slot
is actually checkable.

**Not vocabulary, and untouched.** `::cut{action}` and `::video{action}` remain
`{ enum: [show, hide] }` declared inline on the directive — a genuine two-member
pairing the engine dispatches on, not a shared vocabulary. The delivery flags
`{mono}`/`{os}`/`{vo}`, the `narrator` speaker name, and the `::end` tag are
grammar, not vocabulary.

Because the core declares no members, **there is nothing to override**: no
`overrides:` protocol, no "baseline plugin" concept, no override-conflict
diagnostics. `E-DOMAIN-DUP` is unchanged for genuine peer collisions and simply
stops firing for these seven names.

**The attribute name stays the language's.** `emotion=` is still a content-line
grammar slot lowering to a top-level IR field; only the members it resolves
against moved. The record shape is untouched:

```jsonc
// unchanged, guaranteed by this release
{ "role":"dialogue", "text":"Mr. Fixer!", "emotion":"delighted", "variant":1 }
```

## 3. Declaring a vocabulary

A declaration is an `enums:` block, and there are **three** routes to one:

1. **Inline** — in the using document's own frontmatter. `enums:` is a universal
   frontmatter key, so any document (scene, quest, schema) may declare the
   vocabulary it uses right where it uses it. This is the only route available to
   a single-file author and to the playground, which checks one in-memory
   document and can resolve no import.
2. **Imported** — in a project schema reached through `uses:`/`extends:`
   (dsl §9.2). The route a multi-document project should prefer: declare once at
   the root, let every document reach the same members.
3. **Plugin** — in a plugin's `enums` export (plugin 0.0.3 §2). The route an
   engine or genre pack uses to ship a vocabulary to every project that
   activates it; unlike the other two it surfaces on the capability snapshot
   (`lute context --json`'s `enums`, and therefore `capabilityVersion`).

All three go through the same parser and the same validator.

```yaml
enums:
  # Shorthand: a bare sequence IS `{ members: [...] }`.
  emotion: [neutral, content, delighted, shy, surprised, sad]

  # Long form: the two slots whose members carry semantics the compiler reads.
  anchor:
    members: [left, center, right]
    default: center
  action:
    members: [fade-in-up, sway, lean, nod, step-forward, fade-out, hide]
    exits:   [fade-out, hide]
```

Normative rules:

- A bare sequence is shorthand for `{ members: [...] }`. Every pre-0.9.0
  `enums.yaml` and project schema keeps parsing byte-for-byte.
- The long form's keys are `members` (required), `default`, and `exits`.
- **A declaration of `action` MUST supply `exits:`**, and **a declaration of
  `anchor` MUST supply `default:`** — the two places the compiler branches on
  *which member* it is. Omission is an error, never a fallback: a silent
  fallback to a `fade-out*` name prefix is exactly the hidden coupling this
  release removes. The language owns the knowledge that these two slots need
  member semantics; it does not know which members satisfy them.
- For the other five slots `exits:`/`default:` are meaningless and **rejected**,
  so a typo cannot hide in an ignored key.
- `default:` and every `exits:` entry MUST be a declared member.
- **Using a domain slot that no source declares is `E-DOMAIN-UNKNOWN`** — an
  error, not a warning. A slot whose members nobody wrote down cannot be
  checked, and silently not checking is the failure mode this release exists to
  remove. `action` no longer has the guard clause that made it the exception.
  The message names all three routes:

  ```
  error [E-DOMAIN-UNKNOWN] `mood` is not a declared domain — declare its
  members in an `enums:` block in this document's own frontmatter, in a project
  schema reached through `uses:`, or in a plugin's `enums` export before using
  `mood` (dsl 0.9.0 D-C)
  ```

Declaration is **per project root**. A root is a directory with a
`lute.project.yaml`; a sibling root's declaration never reaches into it.

**Precedence**, when more than one route declares the same slot within one root:

| clash | verdict |
| ----- | ------- |
| a project declaration (inline *or* imported) vs the plugin/core vocabulary | `E-DOMAIN-DUP` — the plugin/core entry wins, the project entry is dropped and reported. Pick one route per slot |
| inline vs imported | the **inline** declaration wins, and it MUST re-declare a **superset** of the imported members; a non-superset re-declaration is `E-EXTENDS-RELATION-SIG` (the decision-D5 add-by-re-listing rule, the document being depth 0 to any import's depth ≥ 1). **Never** `E-DOMAIN-DUP` — that code is reserved for clashes involving a plugin |

**Scope limit on the inline route.** It declares a vocabulary for the document
that carries it, and a component body does not carry its own: a component's
`uses:` is discarded at parse and its body resolves vocabulary against the
**importing** document. So a component declaring a domain only *it* names passes
standalone and is `E-DOMAIN-UNKNOWN` through a scene that does not declare or
import the same vocabulary. See §6.1.

`lute init` scaffolds a starter vocabulary covering all seven slots, and
`lute doctor <dir>` reports which slots a root has declared, with the member
semantics inline:

```
vocabulary slots declared: emotion, action (exits: fade-out/hide), anchor (default: center), mood, volume, musicAction, vfxType
```

That is the whole answer to "every project uses something different": the
**template** is opinionated, the **tool** is not. An author edits a file they
own instead of repudiating members compiled into the binary.

## 4. Member semantics replace two hardcoded rules

Both deletions are behaviour-preserving for a project that declares the
equivalent members, and both were gated on a table test proving the new reading
reproduces the old verdict over the full fixture corpus before either copy was
removed.

| Was | Is |
| --- | -- |
| exit detection by name: `fade-out*` \| `exit*` \| `hide`, in **two** hand-synced copies (`lute-check`'s reducer and `lute-compile`'s lowerer, the second commented *"mirrors … byte-for-byte"*) | membership in the resolved domain's `exits:`, read once from the merged domain map both crates already hold |
| `DEFAULT_ANCHOR = "center"` compiled into the checker | the resolved `anchor` domain's `default:` |

After this release **production code branches on zero domain members.** The
surviving member literals in the tree are inside `mod tests` (the equivalence
closure that gated the deletion) and one historical doc comment.

An authored exit is now visible end to end: a member listed in `exits:` lowers
to a `sprite` record carrying `exit: true` and drops the character from the
stage. `crates/lute-compile/tests/snapshots/e2e__bianca_s01ep02.snap` pins one.

## 5. A component is checked the same way through `::use` as standalone

This is a behaviour change an author can observe, and it is the reason 0.9.0's
headline invariant holds at all.

`check()` runs eighteen diagnostic-producing stages over the whole document.
**Five of them were root-only** and never ran over an imported component body,
so the same content checked *clean* inside a component and *dirty* at scene
level — the toolchain contradicting itself about one file depending on how you
reached it. All five now run over component bodies.

| Stage | What escaped through a `::use` | Measured before the fix |
| ----- | ------------------------------ | ----------------------- |
| content-line attributes | every content-line attr rule: `E-DOMAIN-UNKNOWN`, `E-BAD-ENUM`, `E-UNKNOWN-ATTR`, and the delivery rules (`E-DELIVERY-NARRATOR`, `E-DELIVERY-CONFLICT`) | three lines yielding **5 errors** at scene level yielded **0** in a component, exit 0 — and `lute compile` also exited 0 with the undeclared value `emotion: "TOTALLY-UNDECLARED"` **in the artifact** |
| duplicate line codes | `E-DUP-LINE-CODE` | a duplicate `(speaker, code)` pair reached the artifact as a duplicated `lineId`; it now errors and no artifact is emitted |
| reachability | `E-ARM-DEAD`, `W-CODE-AFTER-END` | `lute check react.lute` → `E-ARM-DEAD` exit 1; the same line at scene level → `E-ARM-DEAD` exit 1; `lute check s.lute` (a `::use` of `react.lute`) → **ok, exit 0** |
| admission of unwalked content | `E-GRAMMAR-NOT-ADMITTED` | a component's top-level `<quest>` was never walked at all: `E-GRAMMAR-NOT-ADMITTED` standalone, **silent** via `::use`, and compiling it emitted **zero** records — the whole `<quest>` was silently dropped, so a `::set{run.gold = 1}` smuggled inside it never ran and never reported |
| injection folding | `W-INJECT-CONFLICT` | reported by **no tool**: scene level warned, standalone warned, via `::use` gave nothing |

Normative statement: **content the component walker does not process is an
error, never a silent drop.** No new component-kind admission table was
invented and no existing §6 admission rule changed; the unwalked-content case
reuses `E-GRAMMAR-NOT-ADMITTED`.

Two properties of the fix worth relying on:

- An imported diagnostic anchors at the **`::use` site** with a component
  prefix naming the component and its file. For the injection case that is the
  honest anchor, because the conflict depends on the stage state inherited
  there: `check()` folds the `::use` *in position*, with the inherited stage
  state, which is the same context the compiler folds the inlined body in.
- The unwalked-content pass is guarded at **compile time**, not by vigilance: it
  opens with an exhaustive `let Document { meta, title, shots, quests, span }`
  with no `..`, so adding a field to `Document` fails to compile until the
  author decides how the component walker treats it. Current verdicts: `meta`
  processed, `shots` walked, `quests` **reported** (a component body has no
  quest-walking semantics, so a top-level `<quest>` is diagnosed rather than
  dropped — the case this release closed), `title` exempt (structurally
  populatable but inert across the whole toolchain, so flagging it would invent
  the mirror-image divergence; pinned by a test), `span` not applicable.

**Migration.** A component body that used to check clean may now report. Every
such report is a real defect that was already reaching the artifact or being
silently dropped; the fix is the same one the scene-level form always needed.

## 6. Known limitations

Stated so a component author is not surprised. Neither is a regression
introduced by this release, and neither is presented as fixed.

### 6.1 A component body resolves vocabulary against the **importing** document

A component's own `uses:` is discarded when the component is imported: the
resolved `ComponentDef` carries only `params`, `body`, and `src`. So the
vocabulary a component body checks against is the **importing document's**, not
its own — and that holds for **both** project-side routes. Neither the
component's `uses:` nor an inline `enums:` block in the component's own
frontmatter is in scope once the body is folded into an importing document.

The consequence, measured:

```
lute check c.component.lute      # its own uses:/inline enums: → ok, exit 0
lute check s.lute                # components: [c.component.lute], no vocabulary
                                 # → error E-DOMAIN-UNKNOWN, exit 1
```

A component naming a domain that only *it* declares therefore passes standalone
and fails through a `::use` from a scene that does not import the same
vocabulary. **Consumers own the vocabulary imports.** The practical rule: keep
the vocabulary declaration at the project root and let both the scene and the
component reach the same one, which is what `docs/examples` does.

This is a *scoping* limitation, not the checking divergence §5 closed: every
rule now runs on both routes, and both routes agree about the vocabulary that
is actually in scope. **Named future direction:** a *component schema* surface,
in which a component declares its own imports and `::use` carries them into the
expansion (with a rule for what happens when the two disagree). That is a
distinct design with its own compatibility questions and is filed separately
rather than smuggled into a vocabulary release.

### 6.2 Dead-arm suppression over component bodies is coarse

The C4 rule that suppresses `W-OVERLAP-ARMS` when an `E-ARM-DEAD` covers the
same construct matches by **span overlap**, and every component-body diagnostic
collapses to the importing document's frontmatter span. So one component's
`E-ARM-DEAD` suppresses `W-OVERLAP-ARMS` from *every* component body of that
document. Pre-existing (reproducible with an `E-ARM-DEAD` source older than
§5's reachability fix) and widened in reach by making reachability run over
bodies at all. A correct fix needs an origin discriminator the flat diagnostic
list does not carry.

### 6.3 One precision boundary the checker keeps

`lute compile` folds the *expanded* tree, so it can observe an injection
conflict that only exists once a `@param` is bound. `check()` does not expand,
so it is blind to that case — **identically** standalone and via `::use`, so no
route disagrees with another. Closing it would mean duplicating the compiler's
expansion inside the checker: a second resolution path, which the architecture
forbids.

## 7. Non-goals — explicitly rejected

Recorded so they are not re-proposed:

- **Splitting `lute.core`** into a language core plus an overridable genre
  plugin. Its only justification was conceptual purity, and with directive
  override out of scope it produces no observable difference while touching four
  crates.
- **An `overrides:` protocol.** Strictly more machinery than emptying the core,
  to reach a weaker place where the core still ships an arbitrary vocabulary
  every consumer must explicitly repudiate.
- **Moving `emotion`/`action`/`variant`/`dialogMotion` into `stampAttrs`.** More
  uniform, and the mechanism admits it, but a `stampAttrs` key lowers into the
  record's `stamp` instead of a named IR field — an IR break for every engine,
  bought for purity.
- **Driving reducer dispatch from `semantics` flags.** The reducer keeps
  matching on the directive tag. `mutatesScene` is declared on both `::bg` and
  `::music`, so branching on it would make `::music` clear the stage.
- **Member patterns** (`pose-*`). The language has no matching facility, and
  adding one to every domain declaration for a handful of values is
  unwarranted; enumerate instead.
- **A component-schema surface.** See §6.1 — a real gap, deliberately a separate
  proposal.

## Appendix A — Diagnostic codes

Added:

| code | severity | § |
| ---- | -------- | - |
| `E-ENUM-MISSING-SEMANTICS` | error | §3 — `action` declared without `exits:`, or `anchor` without `default:` |
| `E-ENUM-UNEXPECTED-SEMANTICS` | error | §3 — `exits:`/`default:` on a slot with no such semantics |
| `E-ENUM-DEFAULT-NOT-MEMBER` | error | §3 — `default:` is not one of `members:` |
| `E-ENUM-EXITS-NOT-MEMBER` | error | §3 — an `exits:` entry is not one of `members:` |

Reused with a widened surface — same code, same severity, now reachable where
it previously was not:

| code | § | widening |
| ---- | - | -------- |
| `E-DOMAIN-UNKNOWN` | §3 | fires for `action` (its skip-when-undeclared guard is gone) and for any of the seven slots a project has not declared; message reworded to name all three declaration routes — inline, imported, plugin |
| `E-BAD-ENUM`, `E-UNKNOWN-ATTR`, `E-DELIVERY-NARRATOR`, `E-DELIVERY-CONFLICT` | §5 | now reported on content lines inside an imported component body |
| `E-DUP-LINE-CODE` | §5 | now reported across an imported component body |
| `E-ARM-DEAD`, `W-CODE-AFTER-END` | §5 | reachability now runs over component bodies |
| `E-GRAMMAR-NOT-ADMITTED` | §5 | now reported for a component's top-level content the walker does not process |
| `W-INJECT-CONFLICT` | §5 | now reported for a conflict inside a component body, anchored at the `::use` site |

Removed: none. `E-DOMAIN-DUP` and `E-PLUGIN-DUP-ACROSS` are unchanged and
simply stop firing for the seven slot names.

## Appendix B — IR delta (0.8.0 → 0.9.0)

**None.** `irVersion` stays `"0.8.0"`; the JSON schema stays
`schemas/lute-ir-0.8.schema.json`. No field is added, renamed, or moved.

Two **artifact-content** changes are expected and are not schema changes:

| change | why |
| ------ | --- |
| the `enums` array becomes populated for a project that declares a vocabulary inline or in an imported project schema | the declaration is now project data, so it flows through the folded relational vocabulary into the artifact exactly as `entities:`/`relations:` already did — and a document's OWN inline `enums:` reaches it by the same path an imported one does. Previously the vocabulary lived in the capability snapshot, which is never serialized per artifact. The artifact simply becomes self-describing about the vocabulary it was compiled against. A vocabulary supplied by a **plugin** `enums` export does **not** appear here — it is part of the capability surface, and shows up in `capabilityVersion` and `lute context --json`'s `enums` instead |
| `capabilityVersion` changes | the core's `enums`/`domains` are empty and two attribute types changed. Stamped and expected (plugin §13) |

An engine that ignores `enums` is unaffected. `exits:`/`default:` are **not**
serialized into the artifact: the compiler has already resolved them into
`sprite.exit` and the emitted anchor, so the engine needs no member semantics at
runtime.

## Appendix C — Version stamp and migration

`LUTE_LANG_VERSION` advances to `"0.9.0"`. **`LUTE_IR_VERSION` stays
`"0.8.0"`** — the axes are independent (`docs/versioning.md`) and this release
genuinely does not change the IR.

A document stamped `luteVersion: "0.8.0"` fires the pre-existing
`W-LUTE-VERSION-STALE`; the remedy is to restamp.

Migration for a 0.8.0-clean project, in order:

1. **Declare your vocabulary.** Pick one of the three routes of §3: add an
   `enums:` block to a schema the documents already import (the route to prefer
   for a multi-document project), add one to a document's own frontmatter (the
   route for a single file or the playground, which can resolve no import), or
   export `enums` from your own capability plugin. `lute init` scaffolds a
   starter vocabulary; `lute doctor <dir>` tells you which slots a root has
   declared, and `lute check` names all three routes on the first undeclared
   use.
2. **Spell out the member semantics.** `action` needs `exits:`; `anchor` needs
   `default:`. Copy the members your project actually uses — including the ones
   the old core rejected.
3. **Fix what the component bodies were hiding.** Anything §5 now reports inside
   a component was already reaching the artifact, or already being silently
   dropped.

| Axis | Effect |
| ---- | ------ |
| **IR schema** | unchanged (`0.8.0`) |
| **Artifact content** | changes deliberately; see Appendix B |
| **`capabilityVersion`** | changes |
| **Documents** | breaking: a document using any of the seven slots needs its project to declare that domain |
| **Plugins** | break only if one declares `isStateful`/`cancelsPrevious` (plugin 0.0.3 §4); none shipped |
| **`lute.project.yaml`** | no new keys |
| **`conformance/`** | zero fixtures affected — no conformance source uses any of the seven slots |
