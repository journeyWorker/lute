# Lute 0.41.0 — dogfood fixes

This specification is the normative 0.41.0 contract. It fixes the 24 issues
filed while moving lute-town (a Phaser 3 game) onto `@lute-lang/runtime` and
`@lute-lang/player` (#43–#66), as decided in the decision note above, and it
absorbs the unreleased 0.40.1 work (`evaluate` / `def` condition queries,
index `defs`, strict `exprNode` input), which is never released on its own:
`docs/proposals/scenario-dsl/0.40.1.md` is folded into §4.3 and §5.1 and is
deleted in the release.

Clean cutover (ADR D6): breaking contract changes land without aliases or
compatibility windows; every consumer in this repository (CLI, corpus,
conformance, `@lute-lang/runtime`, `@lute-lang/player`,
`@lute-lang/player-web`, the demo) migrates in the release. ADR D13 holds:
the runtime stays parser-free and returns effects as data.

The words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119. Where the
decision note leaves a detail open this document decides it; each such point
is marked **spec decision** with a one-line reason and is collected in
Appendix A.

## 3. Language, checker and CLI

### 3.1 Renamed domains and `lute fix` (#43)

1. `lute_check::renames` gains one table of renamed domains,
   `RENAMED_DOMAINS: &[RenamedDomain]`, `RenamedDomain { old, new, since }`,
   beside `RENAMED_DIRECTIVES` / `RENAMED_DIRECTIVE_ATTRS`. 0.41 ships one row:
   `musicAction` → `musicPlayback`, since `0.37.0`. The table is the only
   source for both the fix (2) and the diagnostic (3).
2. `lute fix` (file or directory; the existing traversal already visits
   `.yaml` / `.yml`) rewrites, in project (`lute.project.yaml`), schema and
   plugin YAML:
   - a mapping key `<old>:` directly under a top-level `enums:` or
     `entities:` block → `<new>:`;
   - the scalar of a `domain:` type reference (`type: { domain: <old> }`,
     and the same inside `params:`, `attrs:`, `result:`, `payload:` and
     state-shape `fields:`) → `<new>`.
   The rewrite splices spans in place exactly like the existing YAML CEL
   rewriter (`rewrite_yaml_cel`): comments, key order, quoting and layout
   are preserved; nothing is re-serialized. It is idempotent: a second run
   changes nothing. Where the same mapping already declares `<new>:`, the
   key is left unchanged and `lute fix` prints to stderr
   `lute fix: <file>:<line>: kept \`<old>:\` — \`<new>:\` is already declared`
   (**spec decision**: renaming would create a duplicate key). Each rename
   counts as one fix in the existing `applied N fix(es) in M of K file(s)`
   line.
3. Every `E-DOMAIN-UNKNOWN` whose unknown name is a table `new` and whose
   project (the document's folded vocabulary) declares the matching `old`
   appends to its message:
   `` — this project declares `musicAction`, renamed `musicPlayback` in 0.37.0; run `lute fix` ``.
   The code and severity are unchanged.

### 3.2 `type: number` and declaration cascades (#44)

1. **`E-TYPE-NUMBER`** (new, error) replaces the `type: number` message the
   checker and loader report today under other codes (`E-STATE-DECL`, def
   errors, plugin load errors, occasion payload errors). It fires at the
   YAML position of every `type: number` — state rows, def result types and
   `params:`, component `params:`, directive `attrs:`, bridge `result:`
   fields, occasion `payload:` fields, plugin state-shape `fields:`.
   Message: `` `type: number` is no longer a numeric type — choose `type: int` for whole numbers or `type: double` for fractional values ``.
2. When every literal value the checker sees for the declaration is
   integral, the message appends
   `` ; every value it takes here is whole (<values>), so `int` fits ``.
   The values considered are the declaration's own `default:`, and for a
   state row every literal `::set` / `::set{… += N}` of that path in the
   project; `<values>` lists at most three, then `…`. No values seen: no
   suggestion. There is no `lute fix` rule: the choice is semantic.
3. **No cascade.** A declaration that fails to parse but whose name is
   recoverable stays in the environment, marked **invalid**:
   - it reports its own error(s) only;
   - it takes part in name resolution, so nothing downstream reports it as
     unknown (no `E-CLOCK-DECL` for a `clock:` naming an invalid state row,
     no `E-UNKNOWN-DIRECTIVE` for a directive whose declaration is invalid,
     no type or membership diagnostic against its unparsed type);
   - a plugin package whose exports contain invalid entries still loads:
     each export entry is decoded on its own, valid entries are assembled,
     invalid ones are kept by name as invalid. A plugin whose `plugin.yaml`
     itself fails still fails to load; the document's unknown directive
     tags are then attributed to that plugin (below) instead of one
     `E-UNKNOWN-DIRECTIVE` per use.
4. **`W-DEPENDS-ON-INVALID`** (new, severity `info`): at most one per
   invalid declaration (or failed plugin), anchored at its first suppressed
   dependant in source order:
   `` `<dependant>` depends on `<declaration>`, which is invalid (<code> at <file>:<line>); it is not checked until that declaration is fixed (<n> more dependant(s)) ``
   (the parenthesis is omitted when `n` is 0). The existing `faulty` /
   `clock_rejected` suppression of `StateSchema` is the mechanism for state
   rows; it is extended to every declaration kind above.

### 3.3 Summary counts (#47)

Summaries count `info` diagnostics separately and never as warnings:

- `lute check` (each file): `ok: <path> (W warning(s)[, I info])` /
  `failed: <path> (E error(s), W warning(s)[, I info])`.
- `lute check-project`: `ok: <dir> (F file(s), W project-wide warning(s)[, I project-wide info])` /
  `failed: <dir> (F file(s), E project-wide error(s), W project-wide warning(s)[, I project-wide info])`.

`[, I …]` is printed only when `I > 0`; `hint` diagnostics are not counted; a
`--deny`-promoted diagnostic counts as an error only (unchanged). **Spec
decision**: the existing shape and words are kept and the info count is
appended only when non-zero, so every summary of a run without info
diagnostics stays byte-identical (docs, tests). `lute lint` is unchanged.

### 3.4 `W-OBJECTIVE-STRANDED` (#48)

The lint (`check-project`) keeps its candidate search (completion beats by
`on=`, `visited(…)` in `done`, `::set` of a path `done` reads) and its
window rule, and gains two exemptions:

1. **Re-arm**: not reported when the objective's own quest re-arms —
   `tier="run"`, `tier="season:<name>"`, or a non-empty `rearm=`.
2. **Outside evidence**: not reported when any completion beat lives in a
   document other than the objective's own document. (**Spec decision**:
   the decision's "a beat outside the objective's document can complete
   it" is applied as stated; the pass does not model the positions another
   document's raises reach.)

With (1) the run-tier `info` branch disappears: the diagnostic is always a
warning. Its message states its evidence level (D9):

`` required objective `<id>` can only be completed by beats of this document whose clock windows close at <position>; it has no `until=` or `by=` — add `until=` or `by=` so a missed window fails it (evidence: bounded — declared clock windows of this document's beats, no path search) (dsl 0.31.0 §3) ``

The diagnostic's JSON `evidence` stays `Bounded { scope: "declared clock
windows; no path search" }`. `project_objective_slot_results` (the
projection project constraints consume) is unchanged (**spec decision**:
constraints are author-declared invariants with their own evidence; the
decision narrows the lint only).

### 3.5 Host defs: `host: true` (#49)

1. A def declared in a project schema file (`defs:` of a schema reached
   through `uses:`) or in a plugin's `defs:` export MAY carry `host: true`.
   The key is boolean; `host: false` is the same as absent.
2. A `host: true` def is exempt from `W-DEF-UNUSED`.
3. A `host: true` def the index exports carries `"host": true` in index
   `defs` (§4.3).
4. A document's own frontmatter defs keep the closed key set
   (`type`, `params`, `cel`): `host:` there is the existing unknown-key
   error, with the hint `a frontmatter def is local to its document — declare
   a host def in a project schema file` (**spec decision**: frontmatter defs
   are never exported, so no host can read them).
5. The editor schemas `schemas/lute.schema.json` (schema `defs`) and
   `schemas/lute.plugin.json` (plugin `defs`) gain the `host` property.

### 3.6 `lute expr` (#56)

```console
lute expr <CEL> [--project <dir>] [--json]
```

Lowers a host condition to an IR `exprNode` against a project, with checker
diagnostics, so a host passes the result to `Program.evaluate` (§5.1). The
runtime stays parser-free (D13): hosts lower at build time.

1. `--project` defaults to `.`; the directory MUST contain
   `lute.project.yaml` (else usage error, exit 2).
2. The expression is checked as the `when:` of a scene document at the
   project root whose frontmatter declares nothing but `uses:` of every
   schema file the project's documents import and the project's plugin set,
   with the index `defs` (§4.3, parameterised defs included) as its def
   table. Expected type: `bool`. (**Spec decision**: a host evaluates
   against the bundle, whose vocabulary is the union the index carries.)
3. Diagnostics are the checker's existing codes (`E-CEL-PARSE`,
   `E-CEL-PROFILE`, `E-CEL-TYPE`, unknown path / relation / def, …), with
   spans in the expression text (line 1, columns from 1). An expression
   that checks but does not lower (`lower_expr` → `None`) is
   `E-CEL-PROFILE`.
4. Human output: on success one line on stdout, the canonical JSON of the
   `exprNode`; warnings on stderr in the standard rendering; exit 0. On
   error: diagnostics on stderr, nothing on stdout, exit 1.
5. `--json`: stdout carries exactly one object:

   ```json
   {"ok": true, "cel": "run.gold >= 3", "authored": "@atLeast(3)", "expr": {"op": ">=", "l": {"path": "run.gold"}, "r": {"int": 3}}, "diagnostics": []}
   ```

   `cel` is the `@def`-expanded text, `authored` the input when expansion
   changed it (omitted otherwise) — the index's `celSlot` fields — and
   `diagnostics` the `lute check --json` diagnostic objects. On error:
   `{"ok": false, "diagnostics": [...]}`, exit 1.
6. Registered in the CLI `Command` enum and the website CLI reference.

## 4. IR 0.41 and `project.index.json`

`LUTE_IR_VERSION` and the runtime's `IR_VERSION` are `0.41.0`; the IR schema
is `schemas/lute-ir-0.41.schema.json` (renamed from 0.40 in the release).

### 4.1 Typed `bridgeResults` (#45)

`ProjectIndex.bridge_results` becomes `BTreeMap<String, BTreeMap<String,
Type>>`: each field carries the capability's declared result type in the
same serialized form as `occasions[*].payload` (`lute_manifest::types::Type`:
`"bool"`, `"int"`, `"double"`, `"string"`, `{"enum": [...]}`,
`{"domain": "<name>"}`, `{"entity": "<kind>"}`, …).

```json
"bridgeResults": {"battle": {"outcome": {"enum": ["win", "lose"]}, "hpFloor": "int"}}
```

The coarse `"number"` / `"string"` mapping (`crates/lute-cli/src/bundle.rs`)
and its twin in `BridgeReads::with_result_types` are deleted; both read the
declared `Type`.

### 4.2 Enum labels (#46)

`enumEntry` (artifact `enums` rows and index `enums` rows — one row type)
gains `labels: { member: text }`, the long-form `labels:` of the merged
`enums:` declaration, omitted when none is declared, exactly as
`entityKindEntry.labels`:

```json
{"name": "slot", "members": ["morning", "noon", "night"], "labels": {"morning": "아침", "noon": "낮", "night": "밤"}}
```

(**Spec decision**: one row type for artifact and index; entity labels set
the precedent.) The checker's merged vocabulary (`RelVocab`) carries enum
labels to the compiler.

### 4.3 Index `defs` and the `param` node (0.40.1 §3; #49, #56)

1. `lute compile --all` writes `project.index.json` `defs`: an object keyed
   by def name, name-sorted, omitted when empty. Each value is an
   **`indexDef`**:

   ```json
   "defs": {
     "atLeast": {"cel": "run.gold >= n", "expr": {"op": ">=", "l": {"path": "run.gold"}, "r": {"param": "n"}}, "params": [{"name": "n", "type": "int"}]},
     "marketOpen": {"cel": "run.slot != 'night'", "expr": {"op": "!=", "l": {"path": "run.slot"}, "r": {"string": "night"}}, "host": true}
   }
   ```

   `cel` is the body `@def`-expanded (as a seam condition is), `authored`
   the unexpanded body when it differs (omitted otherwise), `expr` the
   lowered body, `params` the declared parameters in declaration order
   (omitted when none), `host: true` per §3.5 (omitted otherwise).
2. The defs a document sees are its plugins' `defs:`, then its `uses:`
   schema imports over them (the checker's precedence). A document's own
   frontmatter defs are local to it and are not exported. The index carries
   the union over the project's documents, except:
   - a def whose body does not expand or lower (the checker reports it);
   - a def with a parameter whose type is not a scalar
     (`bool`/`int`/`double`/`string`/`enum`/`domain`/`entity`)
     (**spec decision**: a host cannot pass a list, record or map
     argument);
   - a def two documents see with different bodies or parameter lists
     (their `uses:` differ, so the name names no one condition). Bodies are
     compared as lowered `expr` plus `params`: the same condition spelled
     differently is one def, exported with the `cel`/`authored` of the first
     such document in source-path order.
3. **`{"param": "<name>"}`** is a new `exprNode` variant. In an exported
   def's body, an identifier that names one of the def's parameters lowers
   to it (after `@def` expansion, which substitutes the arguments of nested
   `@other(p)` calls textually, so their `p` is the outer parameter too).
   A `param` node appears only in index `defs` rows whose def declares that
   parameter: the compiler never emits one in an artifact, and the runtime
   rejects one anywhere else (§5.1).

### 4.4 Generated index schemas (#57)

1. Every index type in `lute_ir::index` (`ProjectIndex`, `IndexDocument`,
   `IndexEntry`, `IndexBeat` including `advances`, `IndexOccasion`,
   `StateDomain`, the new `IndexDef`) and every type they embed derive
   `schemars::JsonSchema` under the `json-schema` feature;
   `lute_manifest::types::Type` gets a hand-written impl matching its
   serde form.
2. `lute-contract-schema` owns the index `$defs` of
   `schemas/lute-ir-0.41.schema.json`: `projectIndex`, `indexDocument`,
   `indexEntry`, `indexBeat`, `indexOccasion`, `indexStateDomain`,
   `indexDef`, `fieldType`. It replaces exactly those keys and leaves every
   other key of the file (hand-written command and artifact definitions)
   byte-identical. Shapes the hand-written part already defines
   (`exprNode`, `celSlot`, `clockDecl`, `entityKindEntry`, `enumEntry`,
   `relationEntry`, `seedFactEntry`, `ruleEntry`, `prereqEdgeEntry`,
   `targetKind`, `forKind`, …) are referenced with `$ref: "#/$defs/<name>"`
   (`schemars(schema_with = …)`), never redefined. (**Spec decision**: one
   definition per shape, the `Ir` namespace unchanged, and the existing
   `git diff --exit-code schemas/` drift check covers it.)
3. `bun run contract:gen` then emits typed `Ir.projectIndex`,
   `Ir.indexBeat` (with `advances`), `Ir.indexOccasion` (`select`,
   `target`, `judge`, `payload`, `outsideRun`), `Ir.indexStateDomain`
   (`kind`, `members`), `Ir.indexDef`, `Ir.fieldType`; `Bundle.index` in
   `@lute-lang/runtime` is typed `Ir.projectIndex`.

No other IR field changes. Engines widen their IR gate to `0.41`.

## 5. Runtime and the Event contract 0.41

`EVENT_VERSION`, `eventVersion` and `snapshotVersion` are `0.41.0`. The Rust
contract types stay the single definition; `lute-events-0.41.schema.json`,
`lute-snapshot-0.41.schema.json` and `Contract.ts` are regenerated.

### 5.1 Condition queries: `evaluate` and `def` (0.40.1 §2–§3; #56)

`evaluate(state, expr)`:

1. `expr` is an IR `exprNode`: the `expr` of any `{cel, expr}` slot the IR
   carries (a beat's `when.expr`, an objective's `visibleWhen.expr`), or the
   output of `lute expr` (§3.6).
2. The runtime MUST evaluate it over the state exactly as a walk evaluates a
   guard: the effective state (written, seeded, then declared default), the
   fact store with derivation under the run's `derive` mode (`holds`,
   `count`, `countDistinct`), `visited(...)`, the reserved clock and quest
   paths, and `now()` from the clock. An `occasion.target` read outside a
   raise is unknown. A state suspended at an await is evaluated over its
   world before the awaited input, as `view` is.
3. The result is an **`Evaluation`** `{ value: Value, unresolved?: string[] }`:
   `value` is `bool`, `int`, `double`, `str` or `unknown`; for `unknown`,
   `unresolved` lists one reason per distinct unresolved read (an unset state
   path, an undetermined derived fact, `validAt(...)`); it is omitted for a
   decided value.
4. `value` MUST NOT be `error`: an expression that evaluates to an error
   (division by zero, `int()` of a non-number, a type mismatch) is the
   rejection **`E-RUNTIME-EVAL`**, whose message names the expression and
   the error.
5. `expr` MUST be exactly an `exprNode`, checked recursively before anything
   is evaluated: every node carries one variant's keys and no other key,
   each field of its schema type (`args` and `list` arrays, `int` within
   `±2^53`), `op` in its arity's set. A `param` node is not admitted here.
   Anything else — including a non-JSON string at the binding — is
   `E-RUNTIME-INPUT`.
6. The query MUST NOT change the state.

`def(state, name, args?)`:

7. Evaluates the index def `name` (§4.3) as `evaluate` does, binding each
   `param` node to the positional argument of the same index in `args`.
8. `args` is an array of JSON scalars, one per declared parameter
   (absent = `[]`). Arity mismatch, or an argument that does not fit its
   parameter type, is `E-RUNTIME-INPUT`: `int` takes a JSON integer within
   `±2^53`; `double` a number; `bool` a boolean; `string` a string; `enum` a
   string member; `domain` / `entity` a string, checked against the index
   `enums` / `entities` members when the kind is closed.
9. A `name` the index does not carry (unknown, ambiguous, frontmatter, not
   exportable) is `E-RUNTIME-INPUT`. Evaluation errors are `E-RUNTIME-EVAL`.

`E-RUNTIME-EVAL` is not a `RuntimeRejection`: no `step` or `begin` returns it.

### 5.2 Gate refusal and the `gate` query (#51)

1. A `raiseOccasion` the engine would not make — its `raisedWhen` is false,
   or `terminal` holds and the occasion is not `outsideRun` — is
   **rejected** with `E-OCCASION-GATE`: `step` returns the state unchanged
   (the input's own `writes` and payload included) and a `Rejected`
   `{ "code": "E-OCCASION-GATE", "message": <refusal> }`. The input is not
   logged. It never halts. The gate is judged after the input's `writes`
   and payload are applied (dsl 0.27.0 §4, unchanged), on the state they
   produce.
   ```json
   {"code": "E-OCCASION-GATE", "message": "step 0: E-OCCASION-GATE: the engine raises `talk` for `npc.tilly` only when `presentHere(tilly)` (its `raisedWhen`), which is false here — make it hold first (an `engine:` write, an earlier step), or drop the step"}
   ```
   The message is the refusal text `lute play` prints (event contract:
   messages keep play's refusal text). (**Spec decision**: a raise refused
   because the game is over is the same refusal class and code, and the
   player now sends raises at `ended` (§7.3).)
2. An **undecided** gate (`raisedWhen` or `terminal` reads a value no input
   defines) stays the `incomplete` halt it is today (**spec decision**: the
   decision covers a false gate; an undecided one is the same class as every
   other incomplete halt, and `gate` reports it beforehand).
3. Clock-cascade raises (`dayEnd`, `dayStart`, `slot`) keep their rule: a
   closed seam raises nothing and the clock still moves (dsl 0.27.0 §4).
4. `lute play` (human and `--json`) and `lute test` are unchanged — same
   text, exit 1. `lute play --events` prints
   `{"input": …, "rejected": {"code": "E-OCCASION-GATE", …}}` instead of an
   output with a `halted` await, exit 1 (unchanged).
5. **`gate(state, occasion, target?)`** returns a **`Gate`**
   `{ open: bool, unresolved?: string[] }`: whether a `raiseOccasion` of
   `occasion` (for `target`) with no writes would pass the seam now.
   `open: false` without `unresolved` is decided closed: the occasion's
   `raisedWhen` is false, or `terminal` holds **and the occasion is not
   `outsideRun`** — the raise rule of rule 1 exactly (an `outsideRun`
   occasion is open at `ended` when its own `raisedWhen` holds or it has
   none); with `unresolved` it is undecided, one reason per
   unresolved read. `target` is mapped through the occasion's target domain
   as a raise maps it. An occasion the bundle does not declare is
   `E-RUNTIME-INPUT`. The query reads the state as `view` does and changes
   nothing.
   ```json
   {"open": false}
   {"open": false, "unresolved": ["<one reason per unresolved read, as Evaluation.unresolved>"]}
   ```
6. `Candidate` gains no gate field: the gate is per occasion, not per beat.

### 5.3 `bridgeResult.writes`; blocking calls (#52)

1. `bridgeResult` gains optional `writes`, the `WritesInput` of `hostWrite`
   (`state`, `facts`, `retract`, `accept`):
   ```json
   {"type": "bridgeResult", "request": 4, "fields": {"depth": 3}, "writes": {"state": [{"path": "user.wellDepth", "value": 3}], "facts": ["pulled(rope)"]}}
   ```
   The input keeps `fields` for the answered values (**spec decision**:
   decision #54 renames the await's schema only; inputs and logs keep their
   key).
2. `writes` are resolved when the input arrives, exactly as `hostWrite`
   resolves them; a write that does not resolve, or a write to the clock's
   `day` / `slot` path (**spec decision**: the clock cannot move inside a
   walk), is `E-RUNTIME-INPUT` with the state unchanged.
3. On resumption they are applied at the call, after the call's declared
   effects (writes, then retracts, then asserts) and before the walk
   continues: `state`, then `facts`, then `retract`, then `accept`. Each is
   recorded like the call's own effect records, with `"effectOf": <tag>`
   and `"by": "host"`; an `accept` is activated at the next quest settle, as
   `hostWrite`'s is. Later lines, guards and calls of the same presentation
   read them.
4. The answer — fields and writes — is part of the continuation's answer
   list: deterministic replay re-applies it, and a snapshot of a suspended
   state serializes it (`continuation.answers[*].writes`).
5. **Blocking** is the existing rule (dsl 0.25.0 §7): a plugin call
   suspends with `awaitBridge` iff it has `bridgeResult` effects whose
   landing paths content reads. A host action whose effect later lines of
   the same presentation must see is declared as such a bridge; its answer
   carries the values and, now, `writes`. **Non-blocking plugin records are
   write-free**: a host cannot write in answer to them; it writes with
   `hostWrite` at the next `idle`, or the call is declared a bridge. The
   event contract states this. (**Spec decision**: the decision adds no
   new declaration key; the bridge declaration is the blocking
   declaration.)
6. `lute play` scripts gain no answer-writes surface (out of scope).

### 5.4 Clock ordering (#53)

The event contract specifies these orders; the runtime implements them.

**`advanceClock { by, writes?, pick? }`**:

1. Resolve `by`, `writes`, `pick` (malformed: `E-RUNTIME-INPUT`, nothing
   applied).
2. Apply `writes` (`state`, `facts`, `retract`, `accept`) and settle the
   quests, as `hostWrite` does. **Changed:** in 0.40 they landed after the
   move's raises.
3. If `terminal` now holds the input ends here: no clock movement, await
   `ended` (**spec decision**: the terminal rule — the clock does not move
   on after the game is over — as `hostWrite` would end).
4. Move the clock. For each midnight crossed: walk to the day's last slot
   (an `advance: day` stays where it stands), settling at every position
   passed; raise `dayEnd`; move to the next day's first slot, settling;
   raise `dayStart`. Then walk to the destination, settling at every
   position passed. On a finite clock whose destination lies past its end:
   stop at the last position, end the clock, raise the last `dayEnd`.
5. At the destination: settle, then raise the clock's `slot` occasion with
   `pick` (not when the clock ended).
6. Emit `clock { from, to }`. It follows every event of steps 2–5,
   unchanged (**spec decision**: a host acts only after the step returns, so
   moving the summary earlier gives it nothing to act on).

Every raise is a presentation (`presentation` … `presentationEnd`); a closed
seam raises nothing (§5.2 rule 3).

**Beat `advances:`**: after the beat's walk ends — its `presentationEnd`
already emitted — the runtime performs the same movement as steps 4–5 with
no writes and no pick (raises nest inside the current input), then emits
`clock { from, to }`. Nesting is bounded (`E-ADVANCE-CASCADE`).

**`raiseAtStart: true`**: the runtime raises nothing at `begin` or
`newRun`. The declaration states that the host raises, at the run's first
position, `dayStart` and then the slot occasion, as two ordinary
`raiseOccasion` inputs, in that order; the checker models those raises
(`W-BEAT-UNRAISED`).

**`lute play`**: an `advance:` step's `engine:` writes follow rule 2 (the
step and the input share `run_advance`): they land before the clock moves,
so the new day's raises read them. Documents and scripts that relied on the
0.40 order put those writes in a following `engine:` step.

Hosts SHOULD express clock-boundary rules in the story — derived rules, a
guarded `dayStart` beat — rather than between a move and its raises; no new
await is added.

### 5.5 `awaitBridge.attrs` / `results`; plugin record `attrs` (#54, #45, #62)

```json
{"type": "awaitBridge", "request": 4, "tag": "battle", "document": "day3.lute", "position": "2.5", "attrs": {"foe": "kato", "mode": "ambush"}, "results": {"outcome": {"enum": ["win", "lose"]}, "hpFloor": "int"}}
```

1. **`attrs`** (always present, `{}` when none): the call's attributes as the
   runtime executes it — the IR command's `fields` (typed JSON values) with
   `occasion.target` bound to the raise's member. The compiler makes
   `fields` complete: every authored attribute (an `@ref` value is already
   folded to its constant at compile time — a state-dependent one is
   `E-ATTR-DEF-DYNAMIC`, so `fields` never carries CEL text), plus every
   omitted attribute whose directive declaration has a `default`, typed as
   an authored value of that type (assembly refuses a `default` that is not
   a value of its `type`, `E-PLUGIN-INVALID-DIRECTIVE`; an integer defaulting
   a `double` reads as a double; the checker judges the default at each call
   that omits the attribute exactly as it judges an authored value, in that
   document's resolved vocabulary — so an `enumFromOption`, `providerRef`,
   `domain`, `entity` or `assetKind` default outside it is, e.g., `E-BAD-ENUM`
   at the call, its message naming the declared default). `fields` excludes the attributes the
   record's stamp carries instead: the timing attributes `wait`, `duration`
   and `delay` (in `timing`), and a plugin cross-cutting `stampAttrs`
   attribute the directive does not declare itself (a top-level key of the
   record beside `timing`). The runtime reads no directive declarations; it
   ships `fields` as they are.
2. **`results`** replaces `fields`: each result field content reads (the
   same set as before) mapped to its declared type from index
   `bridgeResults` (§4.1). A `bridgeResult` answer is validated against
   these types (`E-RUNTIME-BRIDGE-SHAPE`): `int` an integer, `double` a
   number, `bool` a boolean, `string` a string, `enum` a member string,
   `domain` / `entity` a string.
3. Every `plugin` execution record (runtime `record` events and `lute run
   --json`) carries the same `attrs` object, after `tag`:
   ```json
   {"position": "2.3", "kind": "plugin", "tag": "give", "attrs": {"item": "rope", "to": "edda"}, "external": true, "unresolvedEffects": []}
   ```

### 7.1 Start options and handle (#55)

export type LutePlayerStart =
  | { readonly seed?: Contract.Seed; readonly snapshot?: never; readonly session?: never }
  | { readonly snapshot: Contract.Snapshot; readonly seed?: never; readonly session?: never }
  | { readonly session: Runtime.Session.SessionShape; readonly seed?: never; readonly snapshot?: never }

### 7.2 `DirectorHandle.send` at `idle` (#58)

```ts
export interface DirectorHandle {
  readonly actions: (action: PlayerAction) => Effect.Effect<void>
  readonly view: SubscriptionRef.SubscriptionRef<PlayerView>
  readonly send: (input: Contract.Input) => Effect.Effect<void, Errors.RuntimeRejection | Errors.InputLogError | DirectorBusy>
  readonly restore: (save: SaveRuntime) => Effect.Effect<void, SaveIncompatible | Errors.RuntimeRejection | Errors.InputLogError | DirectorBusy>  // §7.4
  readonly shutdown: Effect.Effect<void>
}
export class DirectorBusy extends Schema.TaggedError<DirectorBusy>()("DirectorBusy", { flow: Schema.String, story: Schema.String }) {}
```

1. `send(input)` is accepted while no batch runs and the story waits at
   `idle` or `ended`; otherwise it fails with `DirectorBusy` and changes
   nothing. The runtime decides acceptance: a rejection fails `send` with the
   typed `RuntimeRejection`, the director stays at the same await (an idle
   menu stays shown). An accepted input's output plays as a batch, as an
   idle-menu pick does; `send` completes when the runtime accepted the input
   (the batch has started), not when the batch ends (**spec decision**: a
   handler that sends must not wait on its own presentation).
2. `PlayerAction` gains `{ type: "send"; input: Contract.Input }`, the same
   operation from a presenter widget or input map; a refusal is logged and
   changes nothing.
3. `PlayerHost.idle` stays the automatic path, but the director runs it on a
   fiber of its own instead of inside its command loop; a `send` (or any
   input that leaves `idle`) interrupts a pending `idle`. (**Spec
   decision**: a host `idle` that waits for the game must not block
   actions and `send` — the deadlock of #58.)

### 7.3 Continuing at `ended`; `begin` (#59)

1. At story `ended`, `send` (and the `send` action) accepts every input the
   runtime accepts there — `newRun` and `outsideRun` raises; an accepted
   input moves the flow from `ended` back to `playing` and plays its batch.
   `toTitle` / `confirm` keep working.
2. `PlayerSession.begin` returns the runtime session's `started` output only
   while the session has accepted no input since it was built (or restored).
   Afterwards `begin` (title → new game) sends `newRun`, then the bound
   `flow.newGame` raise when there is one, and returns their output (events
   concatenated in order, the last await). A session waiting where the
   runtime refuses `newRun` (halted, a choice, a bridge) is first restored to
   the snapshot the player session captured when it was built (**spec
   decision**: title → new game is reachable from any wait, not only a
   halt). On the first `begin` with `flow.newGame` bound, `started`'s events
   precede the raise's events.
   (**Spec decision**: a new game keeps `user.*` progress per the event
   contract — endings and unlocks live in `user.*` — and `started` belongs to
   the lineage's start only.) The unused `begin(flow)` parameter is removed:
   `begin: Effect<Output, …>`.

### 7.4 `DirectorHandle.restore` (#60)

`restore(save)` is accepted in every flow state except `boot`
(`DirectorBusy` there):

1. interrupt the running batch, the countdown and the auto timer; hide the
   choice UI and any overlay;
2. `PlayerSession.restore(save)` — runtime snapshot, input log, backlog;
   rollback history cleared (as a load);
3. stores: the read marks this director added at input points later than
   `save.log.length` are removed from the profile's read history, and when
   autosave is enabled the `auto` slot is rewritten from the restored point
   (**spec decision**: the stores must not keep the abandoned presentation —
   the #60 symptom — and the director journals the marks it adds per input
   point);
4. ensure the stage's files, `presenter.restore(point.stage)`, restart the
   stage music (§7.7);
5. re-present the restored await (`load.done`): a choice shows its menu, a
   bridge calls its handler, `idle` runs the idle flow, `ended` shows the
   ending. The machine accepts `load.done` from `ended` and `halted`.

### 7.5 Presenter-paced lines (#61)

1. `linePacing: "presenter"` (on `LutePlayer.make` and the director): the
   presenter types, pages and takes the confirm itself. `Presenter.showLine`
   completes only when the reader released the line; the director treats its
   completion as the release. In this mode `advance` never reveals or
   releases a line, and the director runs no auto timer for lines (the
   presenter reads `PlayerView.mode`). `showLine(line, "skip")` still
   completes at once; read-only skip still stops at an unread line.
2. Default mode (`"director"`): `Presenter` MAY declare
   `readonly confirmsLines?: boolean`. When `true`, an `advance` that arrives
   while the line is `typing` is buffered and applied as the release when
   `line.shown` arrives, instead of being consumed as `reveal`. Without the
   flag, behaviour is 0.40's.

### 7.6 Plugin host hooks; one cue per event (#62)

```ts
export interface PluginCall {
  readonly tag: string
  readonly attrs: BridgeAwait["attrs"]      // the generated JSON object type of §5.5
  readonly document: string
  readonly position: string
}
export interface PlayerHost {
  readonly bridge?: Readonly<Record<string, (request: BridgeAwait) => Effect.Effect<BridgeAnswer>>>  // §7.10
  readonly plugin?: Readonly<Record<string, (call: PluginCall) => Effect.Effect<void>>>
  readonly idle?: (await_: Await) => Effect.Effect<Input | undefined>
}
```

1. A `plugin` record whose tag has a `plugin` handler becomes a **waiting
   cue**: the scheduler runs the handler at the record's place in the batch
   and continues when it completes; in skip mode it runs too (a game action
   is not presentation). Without a handler the record stays a bookkeeping
   cue. A record carrying `answered` (a call the host answered through
   `awaitBridge`) is never handed to `plugin`.
2. `PluginCall` is built from the record (`tag`, `attrs` §5.5) and its
   event's `document`.
3. `CueFactory.fromOutput` returns exactly one cue per output event, in event
   order; this is normative in `docs/player/architecture.md` (a host MAY
   wrap the factory relying on it).

### 7.7 Music and vfx (#63)

Music cues read `playback`, `volume`, `stop`, `mood`, `assetId`:

| Record | Audio |
|---|---|
| `stop: true`, or `playback` `stop` | stop, fade `duration ?? 0` |
| `playback` `fadeOut` | stop, fade `duration ?? 1` s |
| `playback` `start` | play the resolved file from its start (`restart: true`), fade-in `duration ?? 0` |
| any other `playback`, or none | play the resolved file (`change`): crossfade `duration ?? 0`; the file already playing only changes volume |

`volume` is parsed as a number and clamped to `[0, 1]`; absent or not
finite → `1`. `AudioPlay` gains `readonly restart: boolean`; `AudioPort.play`
of the music file already playing without `restart` changes its volume
(fading over `fade`) without restarting. After a load, rollback or
`restore`, the stage's music is silent when the stage has no music or its
`playback` is `stop` / `fadeOut`. (**Spec decision**: the four names are the
player's playback vocabulary; reading `stop`/`fadeOut` from the stage keeps
a restore consistent with what the record did even when the project
declares no `stops:`.)

Vfx: `player.bindings.yaml` `vfx` entries MAY be
`{ effect: custom, name?: string, duration?: number }`; `name` defaults to the
binding key. `custom` is admitted only under `vfx:` (`E-BINDING-EFFECT`
elsewhere, unchanged code) (**spec decision**: transitions, actions and
camera moves keep their closed catalogue). Rust: the `vfx` map takes a
`VfxSpec` (catalogue `EffectSpec` or the custom shape); the bindings schema
and `packages/player/src/bindings/schema.ts` are regenerated.

```yaml
vfx:
  flash: { effect: flash, color: "#fff", duration: 0.3 }
  lanterns: { effect: custom }
  tideRise: { effect: custom, name: tide-rise, duration: 2 }
```

`StageCue.Vfx` keeps its shape, `{ _tag: "Vfx"; effect: EffectSpec; duration: number | undefined }`,
and the port `EffectSpec` (`packages/player/src/ports/index.ts`, hand-written,
not generated) gains `readonly name?: string`, present exactly when
`effect` is `"custom"`. One shape everywhere:

- a custom binding (the generated bindings decoder's
  `{ effect: "custom", name?, duration? }` variant in
  `packages/player/src/bindings/schema.ts`) gives
  `effect: { effect: "custom", name: <name ?? binding key>, params: {} }`,
  its `duration` going to the cue's `duration` as for every effect;
- a catalogue binding gives its effect (`{ effect: "flash", params: {…} }`,
  no `name`);
- a vfx `type` with no binding gives
  `effect: { effect: "custom", name: <type>, params: {} }`
  (`W-BINDING-MISSING` already reports it at check time)
  (**spec decision**: the presenter decides; silently mapping to `none` was
  the bug).

A presenter branches on `cue.effect.effect === "custom"` and reads
`cue.effect.name`.

## Appendix A — spec decisions

| § | Decision | Reason |
|---|---|---|
| 3.1 | a mapping that already declares the new domain keeps the old key; `lute fix` prints a note | renaming would duplicate a key |
| 3.2 | new code `E-TYPE-NUMBER` replaces the message under several codes; new `W-DEPENDS-ON-INVALID` (info); "values seen" = own `default:` and literal writes of a state path | one code names the choice wherever it occurs; the decision's "note" needs a code (only `E-`/`W-` prefixes exist); those literals are what the checker already sees |
| 3.3 | keep the summary shape, append `, I info` only when non-zero | byte identity for every run without info |
| 3.4 | "beat outside the document" exempts as stated; constraint projection unchanged | the pass does not model other documents' raise positions; constraints keep their own evidence |
| 3.5 | `host:` refused on frontmatter defs | frontmatter defs are never exported |
| 3.6 | `lute expr` checks as a root scene `when:` over every imported schema, the plugin set and the index defs | hosts evaluate against the bundle's union vocabulary |
| 4.2 | enum labels on the shared `enumEntry` (artifact and index) | one row type; entity precedent |
| 4.3 | defs with non-scalar params are not exported; ambiguity compares params too | a host cannot pass them; params are part of the def |
| 4.4 | generator owns the index `$defs` inside the IR schema and `$ref`s hand-written shapes | one definition per shape; existing drift check |
| 5.2 | terminal-closed raises are rejected too (non-`outsideRun` occasions only, in the raise rule and in `gate` alike); undecided gates still halt `incomplete` | same refusal class / same class as other incomplete halts, reported by `gate` |
| 5.3 | input keeps `fields`; clock-path writes refused; records carry `effectOf` + `by: "host"`; blocking = existing bridge rule | decision renames the await only; the clock cannot move in a walk; one record shape; no new declaration key |
| 5.4 | terminal after the writes stops the move; `clock` event stays last | the terminal rule; a host acts only after the step |
| 6.2 | handles record their fingerprint; mismatch is a defect | makes the documented contract checkable |
| 7.2 | `send` completes when the input is accepted; host `idle` runs on its own fiber | handlers must not wait on their own presentation; removes the #58 deadlock |
| 7.3 | later `begin` = `newRun` (+ `flow.newGame`); a wait that refuses `newRun` (halted, choice, bridge) → restore the start snapshot; first `begin` puts `started` before the `flow.newGame` raise | `user.*` progress survives a new game; `started` is the lineage start; title → new game works from any wait |
| 7.4 | `restore` unmarks read lines added after the save and rewrites `auto` | the stores must not keep the abandoned presentation |
| 7.7 | stage `playback` `stop`/`fadeOut` silences on restore; `custom` only under `vfx`; one `EffectSpec` shape (`{ effect: "custom", name, params }`) for custom and unbound vfx; `AudioPlay.restart` | restore matches the record; other catalogues stay closed; one shape for presenters, which decide; `start` vs `change` needs it |
| 9 | the CLI is not packed | the launcher needs a platform binary package |
