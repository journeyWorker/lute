# Lute 0.43.0 — agent-facing CLI contract

This is the normative 0.43.0 contract. It is a clean cutover: every caller in
this repository — tests, conformance fixtures, scripts, CI and documentation —
migrates together, and no compatibility alias is kept for a replaced JSON
shape or crate name.

The words **MUST**, **MUST NOT**, **SHOULD** and **MAY** have their RFC 2119
meaning. Choices taken where the owner asked for the conservative option are
listed in Appendix A with their reasons; the decision note carries the
evidence.

## 1. Scope and version contract

Every public version axis is `0.43.0`: toolchain, `luteVersion`, `irVersion`,
`eventVersion`, `snapshotVersion`, the seven npm packages, and the generated
contracts. The contract schemas move to the `0.43` line
(`schemas/lute-{ir,events,snapshot,player-bindings}-0.43.schema.json`) and
project files use `bindingsVersion: "0.43"`.

| Axis | 0.43.0 contract |
|---|---|
| Language | Unchanged except the stamp. |
| IR / Event / snapshot | Shapes unchanged; the schema files are renamed to the `0.43` line and differ from the 0.42 files only in their `$id`, title and version stamps. |
| Player bindings | Shape unchanged; `bindingsVersion: "0.43"`. |
| CLI | Common JSON envelope (§3), JSON error envelope (§4), `lute schema` (§5), local telemetry (§6). |
| Rust dependencies | `serde_yaml` is replaced by `yaml_serde` (§2). |
| npm | All seven packages publish `0.43.0` in lockstep; no TypeScript API change. |

## 2. YAML library (#88)

Every crate that parses or writes YAML MUST use `yaml_serde` (`0.10.x`); the
workspace MUST NOT depend on `serde_yaml` directly or under an alias. Code,
comments and documentation name the crate as `yaml_serde`. Behaviour MUST NOT
change: every CLI snapshot output is byte-identical apart from the 0.43 stamp
and the changes §3–§6 specify. `lute-runtime`'s direct dependencies are
unchanged.

## 3. Command identity and the common JSON envelope (#89)

### 3.1 Command id

A command's **id** is its subcommand path as typed, joined by single spaces:
`check`, `check-project`, `scenario`, `scenario reach`, `loc report`,
`catalog refresh`. Flags and arguments never change the id. A command whose
bare form is a view of its own keeps its name for that view: `lute scenario
--format json` is `scenario`, while `lute scenario reach …` is `scenario reach`
(likewise `scenario envelope`, `scenario knowledge`). The id is the
`command` value of §3.2 and §4, the path accepted by `lute schema` (§5) and
the `command` recorded by telemetry (§6).

### 3.2 Envelope

In JSON mode every **report** listed in §3.3 MUST be printed as one JSON
object that contains:

| Key | Value |
|---|---|
| `command` | the command id (§3.1) |
| `schemaVersion` | the report's shape version (§3.3) |
| `ok` | `true` exactly when the process exits `0` |

plus the report's own fields at the top level, unchanged in name and content
except where §3.3 says otherwise. No report field may be named `command`,
`schemaVersion` or `ok` with a different meaning. Key order is not part of
the contract (the CLI's JSON objects are emitted with sorted keys).

### 3.3 Reports and their versions

A `schemaVersion` is `<release>.<name>`. Reports whose payload is unchanged
since an earlier versioned release keep that version.

### 3.4 Documents that are not reports

These outputs are artifacts or engine contracts and MUST NOT be enveloped or
otherwise changed by this release: the execution IR `compile` writes (and
`compile --all`'s output directory with `project.index.json`); `compile-stream`'s
NDJSON; `run --json` (the reference transcript the conformance corpus pins);
`play --events` (the Event stream); `loc export` rows; and `version --json`
(`{toolchain, language, ir}`).

## 4. JSON error envelope (#90)

### 4.1 JSON mode

A run is in **JSON mode** when its arguments before any `--` contain `--json`,
or `--format json` / `--format=json`, or the command is `schema`. An implicit
default format (e.g. `loc export`'s) is not JSON mode. JSON mode is decided
from the arguments themselves, so it applies to usage errors that occur
before the command line parses.

### 4.2 Envelope

In JSON mode, a run that fails because the invocation is invalid, a path
cannot be read or written, or an input file is not valid for the command
MUST print to stdout exactly one object:

```json
{
  "command": "check",
  "schemaVersion": "0.43.0.error",
  "ok": false,
  "error": {"code": "E-CLI-IO", "message": "cannot read nope.lute: no such file or directory", "path": "nope.lute"}
}
```

* `command` is the id (§3.1), or `null` when the arguments name no command.
* `error.code` is one of §4.3; `error.message` is the human message, which
  stays on stderr unchanged.
* `error.path` is present when one file or directory is at fault (as given on
  the command line or as the command names it).
* For `E-CLI-USAGE`, `error.argument` names the offending argument and
  `error.hint` carries the parser's suggestion when one exists (`lute check
  --json --deny-warning x.lute` → `argument: "--deny-warning"`, `hint:
  "--deny-warnings"`). A misspelt `--json` itself is not JSON mode, so it
  is reported on stderr only.
* The exit code is unchanged (`2`). No report document is printed in
  addition.

`compile-stream` and `play --events` keep their stream protocols and MUST NOT
print the error envelope. `patch` keeps its own refusal documents (§3.3): the
error envelope applies to `patch` only where it prints no JSON document today
(usage errors, an unreadable patch file). A request for help or the version (`--help`,
`--version`) is not an error.

### 4.3 Codes

The codes are registered diagnostics (explainable with `lute --explain` and
listed in the diagnostics reference):

| Code | Meaning |
|---|---|
| `E-CLI-USAGE` | The command line is invalid: unknown command or argument, missing required argument, invalid value or combination. |
| `E-CLI-IO` | A path named by the command cannot be read or written. |
| `E-CLI-INPUT` | An input file was read but is not valid for the command: malformed JSON or YAML, the wrong kind of document, or an unsupported version. |

## 5. `lute schema` (#91)

`lute schema [COMMAND]...` prints the CLI's command tree as the `schema`
report (§3). It reads no project or input file — its answer depends only on
its arguments and the CLI itself. (Telemetry, §6, still records the
invocation.)

* With no path, the report has `commands`: one entry per top-level command
  `{id, summary, hasSubcommands}`, in help order.
* With a path naming a command, the report has `id`, `summary`, `arguments`,
  `options`, `subcommands` and `outputs`:
  * `arguments` (positionals, in order) and `options` entries carry `name`
    (`--json` for options, the value name for positionals), `required`,
    `repeatable`, `takesValue`, and when applicable `short`, `valueName`,
    `possibleValues`, `default`, and `help` (one line).
  * `subcommands`: `{id, summary}` for each.
  * `outputs`: one entry per machine-readable output `{flag, kind,
    schemaVersion}`, where `flag` is the flag(s) selecting it (or `null` when
    the output is unconditional), `kind` is `report`, `artifact` or `stream`,
    and `schemaVersion` is §3.3's value for a report, else `null`. A command
    without a machine-readable output has an empty list.
* Hidden arguments and the generated `--help`/`--version` options are
  omitted. `summary` is the one-sentence summary `lute --help` shows.
* An unknown path is `E-CLI-USAGE` with `argument` set to the unknown
  segment.

The argument data MUST be derived from the same command definition the parser
uses, and `outputs` from the same table the envelope uses, so neither can
drift from the CLI.

## 6. Local telemetry (#92)

### 6.1 Record

Unless disabled (§6.3), every invocation of `lute` appends one line to
`telemetry.jsonl` in the state directory (§6.2):

```json
{"v":1,"ts":1760400000000,"lute":"0.43.0","command":"check","json":true,"exit":0,"durationMs":12}
```

`ts` is milliseconds since the Unix epoch at completion, `lute` the toolchain
version, `command` the id (§3.1) or `null`, `json` whether the run was in JSON
mode (§4.1), `exit` the process exit code, and `durationMs` the wall time.
The record MUST NOT contain anything else: no argument or flag values, paths,
file contents, output, or environment.

### 6.2 Location

The state directory is `$XDG_STATE_HOME/lute` when `XDG_STATE_HOME` is an
absolute path, else `$HOME/.local/state/lute` (Linux, macOS and other Unix),
and `%LOCALAPPDATA%\lute` on Windows. When no such base exists, nothing is
recorded.

### 6.3 Opt-out

Telemetry is disabled when `LUTE_TELEMETRY` is `0`, `false`, `off` or `no`
(case-insensitive), or when `DO_NOT_TRACK` is set to a value other than empty
or `0`.

### 6.4 Guarantees

* The CLI MUST NOT send telemetry anywhere; no network code is involved.
* Recording MUST NOT change stdout, stderr or the exit code; every failure to
  record is silent.
* Each record is written with one append-mode write of the whole line, so
  concurrent invocations never interleave within a line.
* When the file has reached 1 MiB it is renamed to `telemetry.jsonl.1`
  (replacing any previous one) before the next line is appended. Telemetry
  is best-effort: no lock is taken (a lock could stall the command), so under
  concurrent invocations a record may land in the rotated file or be lost,
  and the active file may exceed 1 MiB by the concurrent writers' lines.

### 6.5 Doctor

`lute doctor` reports a `telemetry` check: when enabled, its detail is the
file path; when disabled, it names the variable that disabled it. The check
never fails.

## 7. Breaking changes and migration

| CHANGELOG class | Breaking change | Migration |
|---|---|---|
| CLI | Every `--json` report gains `command`, `schemaVersion`, `ok`; `constraints`, `trace` refusals and `compile` refusals are objects instead of arrays. | Read the array from `constraints` / `diagnostics`; use `ok` instead of per-command success fields where convenient. |
| CLI | `patch --json` is `0.43.0.patch`: `ok` is `true` only on exit `0`; whether the patch was accepted is the new `accepted` field (an accepted patch with semantic changes exits `1`, `ok: false`, `accepted: true`). | Read `accepted` where `ok` was read. |
| CLI | In JSON mode, usage/I/O/input failures print an error envelope on stdout. | Parse stdout in JSON mode even when the exit code is `2`. |
| Diagnostics | New codes `E-CLI-USAGE`, `E-CLI-IO`, `E-CLI-INPUT`. | None. |
| Tooling | Local telemetry is on by default. | Set `LUTE_TELEMETRY=0` (or `DO_NOT_TRACK=1`) to disable. |
| Release | All axes and packages stamp `0.43.0`; schemas move to the `0.43` line; `bindingsVersion: "0.43"`. | Widen version gates to 0.43; update `bindingsVersion`. |

## 8. Tests and CLI identity

Rust tests MUST cover: the envelope keys and `ok`/exit agreement for every
report in §3.3; each former array report's new field; artifacts in §3.4
byte-identical; JSON-mode detection (`--json`, `--format json`, `schema`,
argv before `--`); each error code with `path`/`argument`/`hint`; streams
never printing the envelope; `lute schema` top-level and nested output,
unknown path, and agreement with the parser (every visible argument
appears); telemetry record fields, opt-out variables, location resolution,
rotation, silence on an unwritable directory, and no record content beyond
§6.1.

The CLI snapshot delta against 0.42.1 is limited to: the 0.43 stamps, the
envelope keys and the three former arrays, the `schema` line in `lute
--help`, the doctor `telemetry` check, and error envelopes on stdout for
JSON-mode failure cases. Conformance fixtures change only where they pin a
report (§3.3) or a stamp.

## 9. Documentation and release

English and Korean CLI documentation describe the envelope, the error
envelope and its codes, `lute schema`, and telemetry (with the opt-out), and
every documented JSON example shows the 0.43 shape. The CHANGELOG `[0.43.0]`
section carries every row of §7. `docs/versioning.md` gains the 0.43.0
paragraph.

## Appendix A — decisions

| § | Decision | Rationale |
|---|---|---|
| 3.1 | Ids are subcommand paths as typed. | One name across envelope, schema and telemetry; pasteable. |
| 3.2 | Flat envelope, no `data` wrapper. | Least churn; payload fields stay where consumers read them. |
| 3.2 | `ok` ⇔ exit `0`. | One rule without per-command knowledge. |
| 3.3 | Keep `0.36.0.*` versions for unchanged payloads; new ones are `0.43.0.<name>`. | Reuse the existing convention. |
| 3.4 | Artifacts and engine contracts are not enveloped. | Their consumers are engines, the conformance corpus and the playground. |
| 4.2 | Envelope on stdout, human message kept on stderr, exit code kept. | stdout is the agent contract; nothing human-facing is removed. |
| 4.2 | No `retryable`/`request_id`. | A local deterministic toolchain has neither. |
| 4.3 | Three registered codes. | Covers every exit-2 path; one code space. |
| 5 | No per-report JSON Schema documents. | Out of scope for this release. |
| 6 | Default on, local only, minimal record, silent failure, 1 MiB rotation. | Owner decision plus the report's minimum. |
| 3.3, 4.2 | `patch` keeps its refusal documents; the error envelope covers only what prints no JSON today. | `patch`'s refusals are an existing versioned contract with their own codes. |
| 3.3 | `patch`'s old `ok` becomes `accepted`; the version moves to `0.43.0.patch`. | One `ok` rule for every report; a field whose meaning changes gets a new name and the payload a new version. |
| 6.4 | Best-effort telemetry without a lock. | Never block or slow the command for telemetry. |
