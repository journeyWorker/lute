# Lute 0.48.1 — fix patch

This is the normative 0.48.1 contract, a patch release on the 0.48 contract
line. The words **MUST**, **MUST NOT**, **SHOULD** and **MAY** have their RFC
2119 meanings. Inputs are issues #145 and #142, both pre-existing defects
(same on 0.48.0), and #143, a repository hygiene fix.

## 1. Scope and version contract

The toolchain, language, IR, Event/snapshot stamps, player packages and
launcher packages read `0.48.1`. Schema filenames and bodies stay on the
`0.48` line. The Rust change is in `lute-cli` (`play`); the TypeScript change
is in `@lute-lang/player-web` (and a doc comment in `@lute-lang/player`).

| Axis | 0.48.1 rule |
|---|---|
| Toolchain | Cargo workspace, `lute version` and all seven npm packages stamp `0.48.1`. |
| Language | `luteVersion` stamps become `0.48.1`; no syntax or semantic change. |
| IR | `irVersion` stamps become `0.48.1`; no field or meaning change. |
| Event/snapshot | Stamps become `0.48.1`; shapes and schema bodies unchanged. |
| Player bindings | `bindingsVersion` stays `"0.48"`; schema body and generated TypeScript unchanged. |
| Player | Save/profile format stays `"0.48"`. While audio is locked every `play` returns at once and starts on unlock (§3). |
| Report ids | `0.48.0.check`, `0.48.0.schema`, `0.48.0.tag`, … keep their names: a report id names the release that introduced the report. |

The release MUST NOT alter the bodies of
`schemas/lute-{ir,events,snapshot,player-bindings}-0.48.schema.json`,
`packages/runtime/src/generated/**` or `packages/player/src/bindings/schema.ts`.
Every command output captured by `scripts/cli-snapshot.py` MUST be identical
to 0.48.0 after version-stamp normalization, except the witness change of §2.

## 2. A play that completes a quest is a witness (#145)

`constraints --all-scripts` / `--script` and `context --script` record a
witness from each play and test script they run. Before 0.48.1 the
completed-quest set of a *play* run was empty, so a `completable` constraint
whose only witness was a `*.play.yaml` that completes the quest stayed
`unknown`; a test trace already supplied it from its final `quests` map.

- The completed-quest set of a play run MUST be built from the play
  transcript's settled quest transitions — records
  `{"kind":"quest","quest":<id>,"state":"complete"}` — as it is from a test
  trace's final `quests` map (`{<id>: "complete"}`).
- Regression test (`lute-cli`): a quest-completing `*.play.yaml` under
  `plays/` makes a `completable` constraint `holds [witnessed]` through
  `constraints --all-scripts`; on 0.48.0 it is `unknown`.

## 3. A host-driven batch never hangs on locked audio (#142)

`PixiAudio` held every `play` until Web Audio was unlocked by a user gesture
(0.47.2 §3 made a restore not wait for music). A batch driven through the host
API (`mountPlayer(...).act({ type: "newGame" })`, no gesture) that reached a
music cue, or an sfx/voice cue with `wait`, still waited for a sound that could
not start, so the batch never settled.

- While audio is locked, `PixiAudio.play` MUST return at once on every channel;
  the sound starts when audio unlocks, on a fiber owned by the mount scope
  (`PixiAudioOptions.scope`; closing the mount interrupts it; without a scope
  the fiber is detached). No new host API.
- A play is **pending** until it starts. A `stop` of a channel supersedes every
  pending play of that channel; a music `play` also supersedes every earlier
  pending music play (0.47.2 §3). A superseded play never starts. While audio
  stays locked only the latest music request survives and starts at unlock.
- An unlocked `play` is unchanged (it waits for finite sounds to end).
- `AudioPort` docs (`@lute-lang/player`): while the platform cannot start sound
  yet, `play` SHOULD return at once and start the sound when it can.
- Browser test (player-web, over a compiled bundle, no mock):
  `mountPlayer(...).act({ type: "newGame" })` with no gesture reaches a
  stage-music save point and settles; a later gesture starts the music. Unit
  (`PixiAudio`): a locked `play` returns at once and starts on unlock; a
  channel `stop` cancels its pending plays.

## 4. Repository hygiene (#143)

`packages/player-web/test-results/.last-run.json` and `title.png` are removed
from the index; the directory is already ignored and nothing reads them. The
player-web e2e server honours an explicit `LUTE_BIN` instead of overriding it
with `target/release/lute` or `target/debug/lute`.

## 5. Testing

Each fix has a regression test that fails on 0.48.0. Player / player-web
behaviour is tested against real runtime output (compiled fixtures, the
browser suite over compiled bundles), never a hand-written view or record.

## 6. Out of scope

#139 (a literal `{` directly before a marker); everything else.

## 7. Breaking changes and migration

| Class | Change | Migration |
|---|---|---|
| CLI | A quest-completing play now witnesses `constraints` / `context`. | None. |
| player-web | While audio is locked every `play` returns at once and starts on unlock; `stop` supersedes the channel's pending plays. | A custom `AudioPort` SHOULD do the same while it cannot start sound. |
| Release | All axes `0.48.1`; schemas, `bindingsVersion` and save format stay on `0.48`. | None. |
