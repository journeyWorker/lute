# Lute Scenario DSL — 0.20.0: Fact envelopes (knowledge analysis)

- **Version:** 0.20.0
- **Status:** Draft
- **Date:** 2026-09-24
- **Scope:** static semantics only. `check-project` computes, for every
  relational query (`holds(…)`, `count(…)`) in every guard slot, whether the
  queried facts are **impossible**, **guaranteed**, or **possible** at that
  point, from two sets: the project-wide **may** set (argument-level: every
  ground fact any seed, assert, rule, or engine relation can produce) and the
  path-sensitive **must** set (facts true on every route to the slot, within a
  document and across the `after:` graph). The verdict feeds the existing
  decision procedure, so dead guards surface through the codes each slot
  already has; two new diagnostics cover the rest; `W-UNPROVEN-RELATIONAL` is
  removed. No grammar change.
- **IR:** no change; restamps to 0.20.0.

## 1. Motivation

An author who writes a line that presumes knowledge guards it:

```lute
@eris{when="holds(knows(player, project_lumen))"}: ...So you read the log.
```

That is the right tool — and until now the checker never looked at it. A
relational query was always *undecided*: `producible.rs` asked only whether a
relation **name** is asserted somewhere, and only for quest `start`/`fail`,
objective `done`, and entry `when`. A line guard on a fact nobody ever
asserts — a typo'd argument, a scene that was cut, a lore entry that was
never written — checked clean. `W-UNPROVEN-RELATIONAL` then marked every
other relational gate as "not proven", which is noise on exactly the guards
that are fine.

Everything Lute analyzes is finite: closed entity members, declared
relations, a total Datalog, non-Turing content, and engine inputs confined
to declared domains. So each query has a decidable answer among three:
**impossible** (no route produces the fact), **guaranteed** (every route
reaching the slot has it), or **possible** (both outcomes are reachable, or
the analysis cannot separate them). 0.20.0 computes the two sets that decide
it.

## 2. Facts and patterns

A **ground fact** is a relation applied to members of its argument domains
(`knows(vesna, manifest)`). The universe is finite: the product of each
relation's closed domains. A relation with an `open:` (engine-minted) entity
argument has an **unbounded** universe; it is represented symbolically and
never enters the must set (§4).

A **query pattern** is the atom inside `holds(…)` / `count(…)`, with `_`
wildcards. `holds(P)` is true iff some live fact matches `P`; `count(P)`
counts them.

## 3. The may set (project-wide, argument-level)

`May` over-approximates every ground fact that can be live at any point of any
run. It is the least fixpoint of:

1. every seed in `facts:`;
2. the fact of every `::assert` anywhere in the project root — scenes,
   quests (`<on>` / `<objective>` bodies), and lore entries — whose document
   is not proven unreachable (the `live_assert_relations` discipline);
3. **reserved** relations: every fact in their universe (the engine may
   populate any of them);
4. **derived** relations: the facts their rules produce over `May`, reading
   every negated atom `not R(…)` as satisfiable and a rule-body CEL guard as
   satisfiable unless it decides false (both over-approximate).

`May` is flow-insensitive: it does not know *when* a fact appears, only that
some route can produce it.

## 4. The must set (path-sensitive)

`Must(p)` under-approximates the facts live on **every** route reaching program
point `p`.

**Stability.** Only **monotone** facts can be guaranteed across time the
author does not control. A ground fact is monotone iff no `::retract` pattern
anywhere in the project matches it, no other assert shares its `key:` tuple
with a different value, and its relation is neither reserved nor unbounded.
Facts of `tier: scene` relations never cross a document boundary.

**Within a document** (a forward must-dataflow over the node stream, the
fork/join shape of definite assignment, `defassign.rs`):

- `::assert{F}` adds `F` and removes facts it invalidates through `key:`;
  `::retract{P}` removes every fact matching `P`.
- Forks (`<branch>`, `<match>`, `<hub>`, guarded lines) walk each arm; joins
  **intersect**. A `<hub>` body may run zero or more times.
- A guard is an **assumption** inside its region: within
  `<when test="holds(F)">`, a choice `when="holds(F)"`, or a line
  `when="holds(F)"`, a ground `F` is in `Must`.
- Derived facts are recomputed over `Must` at each query (positive atoms from
  `Must`; a negated atom only when its fact is outside `May`).

**Entry points.**

- A **scene** starts from `Must_in`: the seeds, plus every monotone fact
  guaranteed by its `after:` formula — `visited(A)` contributes
  `Must_out(A)`; `a && b` unions; `a || b` intersects; `completed(q)` /
  `active(q)` contribute nothing. Propagation follows the `after:` graph with
  the memoized structural recursion of the scalar envelope (`envelope.rs`); a
  cycle or an unresolved node contributes nothing.
- A **quest body** (`<on>`, `<objective>`) and a **lore entry body** run at
  engine-chosen times: they start from the monotone seeds plus their own
  guard assumptions (`start` / `done` / `when`).
- Asserts in quest and entry bodies contribute to `May` everywhere and to
  `Must` only inside their own bodies. Their retracts make the matched facts
  non-monotone.

## 5. Verdicts

For a query at slot `s`:

| Query | impossible | guaranteed | otherwise |
| --- | --- | --- | --- |
| `holds(P)` | no fact in `May` matches `P` | some fact in `Must(s)` matches `P` | possible |
| `count(P) ⋈ n` | decided over the interval `[|Must(s) ∩ P|, |May ∩ P|]` | ← same | possible |

The verdict is substituted into the existing decision procedure (`decide`,
dsl 0.4.0 §5.1; previously its R5 firewall left every relational gate
undecided), so every slot that already reports a provably dead or always-true
condition now does so for relational ones too:

- a `<when test>` or `<choice when>` that decides false → `E-ARM-DEAD`;
- an objective `done` → `E-OBJECTIVE-UNSATISFIABLE`, a quest `start` / `fail`
  → `E-QUEST-UNREACHABLE`, a hidden objective → `W-OBJECTIVE-HIDDEN`;
- a content line's `when=` or a lore entry's `when` that decides false →
  **`E-GUARD-DEAD`** (new: these slots had no dead-code diagnostic);
- a relational query that is **guaranteed** inside a guard — a line
  `when=`, a `<choice when>`, a `<when test>`, or an entry `when` →
  **`W-FACT-GUARANTEED`** (new): the condition is redundant, the fact is
  already established on every route (the message names where). Quest
  `start` / `fail` and objective `done` are predicates, not guards, and are
  not flagged.

Messages name the fact and the reason: *"no seed, assert, rule, or engine
relation produces `knows(toma, heading)`"*, or *"`knows(vesna, manifest)` is
asserted on every route to here (scenes/archive.lute:21)"*.

A **possible** verdict is silent: it is the normal case for a guard, and
exactly what a guard is for. **`W-UNPROVEN-RELATIONAL` is removed** — the
second removal in the series after `W-INJECT-CONFLICT` (0.10.0); `--deny
W-UNPROVEN-RELATIONAL` handling follows that precedent.

## 6. Where it runs

The analysis needs the whole project, so it runs in `check-project` (and in
any surface that already resolves a project root the way `check-project`
does). Single-file `lute check` keeps today's behavior for relational queries
— undecided — because an assert in a sibling document is invisible to it.

`lute scenario` gains the per-node fact envelope beside the scalar one: the
guaranteed facts at each scene entry, so an author can see why a guard is
judged guaranteed.

## 7. Diagnostics

| Code | Grade | Status |
| --- | --- | --- |
| `E-GUARD-DEAD` | error | new — a line `when=` or entry `when` that provably never holds (§5) |
| `W-FACT-GUARANTEED` | warning | new — a relational guard that provably always holds (§5) |
| `E-ARM-DEAD`, `E-OBJECTIVE-UNSATISFIABLE`, `E-QUEST-UNREACHABLE`, `W-OBJECTIVE-HIDDEN` | — | extended — now decided for relational conditions (§5) |
| `W-UNPROVEN-RELATIONAL` | warning | **removed** (§5) |

## 8. Compatibility

- No grammar or IR change. Every document that checked clean under 0.19.0
  still parses and compiles identically.
- `check-project` may report new errors on guards that could never hold —
  those guards were already dead at runtime; the diagnostic is new, the bug
  is not — and new warnings on redundant relational guards.
- `W-UNPROVEN-RELATIONAL` disappears from output.

## 9. Decisions

| # | Decision | Rationale |
| --- | --- | --- |
| **D-A** | two sets (may, must) rather than exact model checking | sound in both directions (impossible and guaranteed are proofs), linear-ish in project size, and the shape the scalar envelope already uses; exhaustive state enumeration is decidable but explodes combinatorially, and SMT would add a solver for no verdict the sets can't give |
| **D-B** | `May` is flow-insensitive, `Must` is path-sensitive | the valuable proofs are "never" (a global question) and "always here" (a path question); a flow-sensitive may set would only sharpen *possible*, which is silent anyway |
| **D-C** | only monotone facts cross time the author doesn't control | a retract or key-invalidation anywhere — in a later scene, a quest handler, a lore entry read at any moment — could break a guarantee; restricting cross-boundary must to monotone facts keeps it sound without modeling engine timing |
| **D-D** | guards are assumptions | a region guarded by `holds(F)` has `F` by construction; without this, nested guards on the same fact would all be "possible" and redundancy could never be shown |
| **D-E** | dead relational guards reuse each slot's existing code | an arm dead because of a fact is as dead as one dead because of an enum typo; one code per slot keeps `--deny` configs and author mental models stable |
| **D-F** | remove `W-UNPROVEN-RELATIONAL` | its premise — relational gates are unanalyzable — no longer holds; its remaining content ("possible") is the normal, correct state of a guard |
| **D-G** | project-level only | per-file checking cannot see sibling asserts; claiming "never asserted" from one file would be false |
