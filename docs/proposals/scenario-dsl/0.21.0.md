# Lute Scenario DSL — 0.21.0: Beats and occasions

- **Version:** 0.21.0
- **Status:** Draft
- **Date:** 2026-09-24
- **Scope:** story selection without a clock. A project declares
  **occasions** — engine moments at which a story beat may be chosen (a hub
  visit, entering a room, talking to an NPC, a new day, the start of a run).
  A scene or lore entry becomes a **beat** by naming the occasion it answers,
  a `when` condition over any state, fact, or quest, a `priority`, and a
  repetition policy. The engine raises occasions; Lute defines which beats
  are eligible and which one wins. `schedule.yaml` and its clock/lane model
  are **removed**; `lute play` is rebuilt on occasions and now drives quest
  lifecycles.
- **IR:** additive — `SceneMeta.beat`, `EntryCmd.on` / `priority`,
  `ProjectIndex.beats`, plugin-exported `occasions`.

## 1. Motivation

The 0.11.0 schedule layer modelled one kind of game: a visual novel on a day
clock. Everything was a placement at a tick on a lane. Most narrative games do
not advance by clock:

| Game | What advances the story | When a beat is chosen |
| --- | --- | --- |
| *Hades* | runs, relationships, events witnessed | at a hub visit, each NPC offers the highest-priority line whose requirements hold |
| *Undertale* | area, kill count, route flags | entering a room, ending a fight |
| messenger fiction | real time | a notification |
| *Outer Wilds* | what the player knows | examining a place |
| day-clock VN | day and time of day | a time-of-day change |

The common shape: **at some moment, pick one of the story pieces whose
conditions hold.** Time is one input to those conditions, not the frame.

An audit of the schedule layer found the rest: quest progress could not gate
placements (`completed()`/`active()` always evaluated against an empty set), a
placement's order was a second source of truth beside `after:`, recurring
events were forbidden (`E-SCHED-EVENT-DUP`), pacing opinions were always-on
diagnostics, and player-chosen order, windows, deadlines, and weekday
variation were inexpressible. No project uses `schedule.yaml`; 0.21.0 removes
it rather than migrating it.

## 2. Occasions

An **occasion** is engine vocabulary: a named moment the engine raises. A
plugin manifest MAY export `occasions:`:

```yaml
occasions:
  hubVisit:   { select: first }
  talk:       { select: first, target: true }
  roomEnter:  { select: first, target: true }
  dayStart:   { select: first }
  inbox:      { select: all }
```

- `select: first` (default) — the engine presents the single winning beat.
- `select: all` — the engine offers every eligible beat, in selection order,
  and the player picks (an area map, a message inbox, quest givers in any
  order).
- `target: true` — the occasion is raised **for** something
  (`talk` → `npc.vesna`); a beat may restrict itself to one target.

The export folds into the capability snapshot as a guarded, sorted section
(the `rewardKinds` precedent, 0.16.0 D-E): a project without it keeps its
`capabilityVersion`. When no resolved plugin declares occasions, occasion
names are **shape-only** (any identifier is accepted); when any do, an
undeclared occasion is `E-OCCASION-UNKNOWN`, and a `target` on an occasion
declared without `target: true` is `E-BEAT-ATTR`.

## 3. Beats

### 3.1 Scene beats (frontmatter)

```yaml
---
kind: scene
id: hades.achilles.run12
on: talk
target: npc.achilles
when: 'user.runs >= 10 && holds(knows(zagreus, patroclus_name))'
priority: 50
once: user
---
```

| Key | Meaning |
| --- | --- |
| `on` | the occasion this scene answers; makes the scene a beat |
| `target` | optional; only when the occasion is raised for this target (dotted id, the `<entry target>` shape) |
| `when` | optional CEL condition — state (`run` / `user` / `app`), `quest.*`, `entry.*.read`, and fact queries; the scene's own `scene.*` state does not exist yet and is rejected |
| `priority` | optional integer, default `0`; higher wins |
| `once` | `run` (default: once per run), `user` (once ever), or `false` (repeatable) |

`after:` keeps its meaning — the structural prerequisite over
`visited` / `completed` / `active` that connectivity analyzes — and a beat is
eligible only when both `after:` and `when` hold. `when`, `target`,
`priority`, and `once` without `on` are `E-BEAT-ATTR`: a scene that answers no
occasion is reached by explicit flow, as before.

### 3.2 Entry beats

A lore entry answers an occasion with `on=` and `priority=` beside its
existing `when` and `target`:

```lute
<entry id="achillesBark3" on="talk" target="npc.achilles" category="bark" priority="10" when="user.runs >= 3">
  @achilles: Back again, lad.
</entry>
```

Entries have no `once`: re-presentation is their nature (0.19.0 §6). An entry
that should be heard once guards on its own `entry.<id>.read`.

## 4. Selection (engine contract)

When the engine raises occasion `O` (optionally for target `T`), the
**candidates** are the beats with `on: O` whose `target` is absent or equal to
`T`. A candidate is **eligible** when its `after:` and `when` hold and its
`once` policy is not spent (`run`: not yet presented this run; `user`: never
presented). Eligible beats are ordered by **priority descending, then
`ProjectIndex.beats` order**. `select: first` presents the first;
`select: all` offers the list. No eligible beat means the occasion passes with
no story — the engine's default behavior applies.

Normative text: [`docs/runtime/beats-and-occasions.md`](../../runtime/beats-and-occasions.md).
Presenting a scene beat runs the scene; presenting an entry beat follows the
entry rules (0.19.0 §6).

## 5. Static checks

- `E-BEAT-ATTR` — shape: non-identifier `on`, malformed `target`, non-integer
  `priority`, `once` outside `run` / `user` / `false`, beat keys without
  `on`, `target` on a non-targeted occasion.
- `E-OCCASION-UNKNOWN` — `on` names an occasion no resolved plugin declares
  (only when some plugin declares occasions).
- `E-BEAT-UNREACHABLE` — a beat whose `when` provably never holds
  (single-file for scalar-decidable conditions; `check-project` for fact
  conditions via the 0.20.0 fact envelope), mirroring `E-ENTRY-UNREACHABLE`.
- `W-BEAT-SHADOWED` (`check-project`) — a `select: first` beat that can
  never win: an earlier-ordered beat on the same occasion and target has a
  condition that is always true and a repetition policy that is never spent
  (`once: false`), so it wins every time.
- `when` joins the CEL-slot registry (profile, definite assignment,
  unset-sentinel rules) like a quest `start`.

## 6. `lute play`

`lute play <dir> --script <play.yaml>` walks a playthrough as a sequence of
**raised occasions**:

```yaml
state: { user.runs: 9 }
steps:
  - occasion: hubVisit
  - occasion: talk
    target: npc.achilles
  - occasion: inbox
    pick: messageFromMeg      # select: all → the beat the player takes
choose:
  achilles.run12.gift: accept # ordinary branch decisions, as in trace mocks
```

For each step it computes the eligible beats, presents the winner (or `pick`),
runs it with the reference runner, and then **advances every quest lifecycle**
exactly as `lute run` does for a quest artifact — so `when` conditions over
`quest.*` and `after: completed(…)` see real progress. The transcript names
every step, the candidate list with each beat's verdict, and the winner.
`--json` emits the same. An empty or unknown step is a usage error; a `pick`
that is not eligible is an error.

## 7. Removals

- `schedule.yaml`, its loader and route-space sweep, the clock / lane /
  placement model, and every `E-SCHED-*` / `W-SCHED-*` diagnostic.
- `lute play`'s schedule-driven mode (§6 replaces it).
- `docs/schedule-and-play.md` and the website's schedule pages.

## 7a. Quests meet scenes and occasions

The quest audit (haven drive test T9.4, T9.5, T4.7) ranked five frictions.
With occasions in place, four close with small additions and one with a
report fix.

### 7a.1 `visited()` in conditions

`visited('<scene id>')` — until now legal only inside `after:` — becomes a
Lute-CEL function in **every condition slot** (quest `start` / `done` /
`fail`, objective `done` / `fail`, beat `when`, entry `when`, content-line and
branch `when=`). It is true once the scene has been presented in this save
(the tier `after:` already uses; `newRun` does not clear it). An id that names
no scene in the project is `E-CONN-UNKNOWN-NODE` at `check-project`, as in
`after:`. A scene can now advance a quest by being played, without relaying a
flag:

```lute
<objective id="heardVesna" title="Hear Vesna out" done="visited('haven.s01ep04')"/>
```

### 7a.2 Objectives evaluated at an occasion

`<objective on="<occasion>">` evaluates that objective's `done` / `fail` **only
when the occasion is raised** while the quest is active — the missing
end-of-run check point. Without `on`, an objective is evaluated continuously,
as before.

```lute
<objective id="lowPressure" title="Keep the shed calm" on="runEnd" done="run.shedPressure < 2"/>
```

The occasion is checked against the vocabulary exactly as a beat's `on`
(`E-OCCASION-UNKNOWN`, shape-only when undeclared); `on` that is not an
identifier is `E-BEAT-ATTR`. `lute trace` / `lute run` raise occasions for a
quest walk with the mock key `occasions: [runEnd]` (or `--occasion runEnd`,
repeatable), applied in order after the walk settles; `lute play` evaluates
them on every step that raises the occasion — an occasion referenced only by
an objective is a legal step.

### 7a.3 `::accept` from a scene

`::accept{quest="<id>"}` declares that the player accepts an accept-driven
quest at this point (in a choice branch, typically). It is the scene-side form
of the engine's "accept quest" action and of `lute trace --accept`. The target
MUST be an accept-driven quest (no `start`) in the project: otherwise
`E-ACCEPT-TARGET` at `check-project` (a missing or non-identifier `quest` is
`E-ACCEPT-TARGET` per file). IR: command `{"op": "accept", "quest": "<id>"}`;
the engine activates the quest if it is `unset`, and ignores it otherwise.

### 7a.4 Quest outcomes in scenario tests

`lute test` gains `expect.quests: {<questId>: unset | active | complete |
failed}`, asserted against the lifecycle the trace ran — no side-effect
`::set` needed to observe completion.

### 7a.5 Bare quests in `lute scenario`

A quest without `after=` is no longer silently absent from the project
report: `lute scenario` lists it as **unanchored** (available from the start of
play; the connectivity layer holds no prerequisites for it), and
`scenario reach` reports it so instead of an unresolvable node.

## 8. IR delta

| Field | Change |
| --- | --- |
| `SceneMeta.beat` | NEW, omitted for non-beat scenes: `{on, target?, when?: CelPair, priority, once}` — `once` is `"run"`, `"user"`, or `"none"` (source `once: false`) |
| `EntryCmd.on` / `EntryCmd.priority` | NEW, omitted when not authored |
| `ProjectIndex.beats` | NEW, omitted when empty: `{id, kind: "scene" \| "entry", document, on, target?, priority, once?}` in selection-tiebreak order (document order within the project) |
| `Objective.on` | NEW, omitted when not authored (§7a.2) |
| `accept` command | NEW: `{op: "accept", quest}` (§7a.3) |
| CEL `visited(id)` | NEW call in condition expressions, encoded like `holds` (§7a.1) |

`LUTE_LANG_VERSION` / `LUTE_IR_VERSION` → `0.21.0`; the schema renames to
`lute-ir-0.21.schema.json`. Scene and lore artifacts without beats are
byte-identical apart from version strings.

## 10. Decisions

| # | Decision | Rationale |
| --- | --- | --- |
| **D-A** | selection is keyed by occasions, not time | time is one progress axis among many (runs, areas, knowledge); a clock-first model forces every other game into fake ticks |
| **D-B** | occasions are engine vocabulary, shape-only until declared | the moments a game raises are the engine's design; the `rewardKinds` pattern lets authors start before a plugin exists and get checking once one does |
| **D-C** | priority then declaration order | the Hades model: deterministic, explainable, and overridable by the engine; weighted randomness and cooldowns are engine policy |
| **D-D** | `select: all` covers player-chosen order | an inbox, a map, or quest givers "in any order" are occasions whose eligible set is offered, not a separate ordering model |
| **D-E** | `after:` stays structural; `when` carries state | connectivity and the fact envelope analyze `after:` as a graph; state conditions belong in a CEL slot the checker already analyzes, which is what `after:`'s ban on state reads was forcing authors to relay through flags |
| **D-F** | `once` defaults to `run` | a story beat that repeats every time its occasion fires is the exception (barks are entries); `user` covers "once ever" without a flag |
| **D-G** | remove `schedule.yaml` instead of migrating | it has no users; a day-clock VN is a `dayStart`/`timeChange` occasion plus `when` over `run.day`, so the new model covers its one use case |
| **D-H** | `lute play` drives quest lifecycles | the schedule-era player never advanced quests, which is why quest-gated beats could not be exercised; a reference player that ignores quests cannot validate a quest-structured story |
| **D-I** | one word `on` for every occasion binding | a beat answers an occasion and an objective is judged at one; the same key and vocabulary check keep the model one concept |
| **D-J** | `visited()` in every condition slot | the scene→quest channel was a flag relay; `after:` already tracks presentation, so exposing it to CEL costs the engine nothing new |
