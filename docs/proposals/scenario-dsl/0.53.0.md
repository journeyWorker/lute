# Lute 0.53.0 — dogfood round 3

This is the normative 0.53.0 contract. The words **MUST**, **MUST NOT**,
**SHOULD** and **MAY** have their RFC 2119 meanings.

The release resolves the eight issues of dogfood round 3 (porting a large
existing VN / live-game content set): #224, #225, #226, #227, #228, #229,
#230, #231. The headline is #228: `lute lint` rebuilt the project for every
document. The audit that #228 required found the same defect in five more
commands; all of them are fixed here (§3). The decisions, the measurements
and the per-command audit are in
[`2026-10-28-lute-0.53-decisions.md`](../../superpowers/notes/2026-10-28-lute-0.53-decisions.md);
where this spec departs from an issue's suggestion or an owner default, the
note gives the evidence and Appendix B lists every decision. The rule
throughout is conservative: the smallest surface, one spelling per concept,
static analysis kept sound, refuse rather than guess, and the runtime and the
checker agree.

The base is `main` at **v0.52.0** (`596d19c5`). Code anchors are cited at
`596d19c5`; Appendix A lists them by symbol.

Implementation plan:
[`2026-10-28-lute-0.53.0-dogfood-r3.md`](../../superpowers/plans/2026-10-28-lute-0.53.0-dogfood-r3.md).

## 1. Scope and version contract

This is a minor release. Every public version axis is `0.53.0`: toolchain,
`luteVersion` (`LUTE_LANG_VERSION`), `irVersion`, `eventVersion`,
`snapshotVersion` and the seven npm packages. The contract schemas move to the
`0.53` line (`schemas/lute-{ir,events,snapshot,player-bindings}-0.53.schema.json`)
with no shape change. `bindingsVersion` and the player save/profile format
become `"0.53"`. This follows the 0.52.0 §1 precedent.

| Axis | 0.53.0 contract |
|---|---|
| Language | **Looser:** a bounded loop may span the top-level `##` sections of a document (§9). **Stricter:** a misspelled reference in a field of a `record`-typed (or `map`/nested `list`) plugin frontmatter value is an error (§6). |
| Static semantics | An `accept="external"` quest keeps the host as an accept source; an in-script accept deadlock is `E-QUEST-START-CYCLE` (§7). |
| IR | **Unchanged.** Schemas renamed `-0.53`. |
| Semantics (D5) | **No new id.** The runtime does not change. |
| Event / snapshot | **Unchanged.** Schemas renamed `-0.53`. |
| Plugin manifests | Unchanged. |
| Lint | `pair` rules take `scope: document` (§5). `lute lint` builds the project input layer once per root (§3.2). |
| CLI | `lute fix` keeps plugin stamps, names its rules and reports kept sites; report `0.53.0.fix` (§4). Every multi-document command shares the project input layer (§3). |
| Runtime / player | Unchanged. |
| `capabilitySnapshot` | **Unchanged.** |
| Report ids | `fix` moves to `0.53.0.fix` (§4.3). Every other report id is unchanged. |

Outside the deltas listed in §15, every output captured by
`scripts/cli-snapshot.py` MUST be byte-identical to 0.52.0 after version-stamp
normalization. Compare with `--strict` against 0.52.0. The plan's first slice
extends the snapshot to the commands §3 changes (§3.7) before the baseline is
captured, so their outputs are compared too.

## 2. Shared rules

The 0.52.0 §2 rules apply unchanged: a regression test that fails on the base
for every behaviour change (the issue reproductions first); one diagnostic
shape (registered in `crates/lute-cli/src/codes/registry.rs` and
`crates/lute-check/src/evidence.rs`, blessed with `LUTE_BLESS_DIAGNOSTICS=1`,
website EN + KO); **no hint recommends a spelling the checker rejects**; no
silent drop; byte stability for projects that use none of the changed
constructs (except §15); documentation in the same change; and
`docs/design/rust-coding-rules.md` for new Rust code. In particular:

- **Newtypes and enums, not strings:** `FixRule` (one variant per `lute fix`
  migration, §4.3), `FixKept` (why a site was not rewritten), `PairScope::Document`
  (§5), `FrontmatterPath` (a field path inside a frontmatter value, §6),
  `AcceptSource::Host` or an equivalent flag on the accept anchor (§7.1),
  `Region` (a loop region's node slices, §9.3).
- **One function per rule.** Whether an attribute is an old spelling is one
  function the checker and `lute fix` call (§4.1). Where a frontmatter type
  holds references is one walk that the reference check and
  `W-DOMAIN-UNREAD` share (§6). A loop region is computed by one function
  every flow walk calls (§9.3).
- **Project data is built once (ADR D14, extended by this release).** A
  command that reads two or more documents of a project builds the project
  input layer once per root and holds per document only its overlay (§3).
- **No HIR, no Fold, no synthesized nodes** (rules §7). **No new semantic
  id**: the runtime does not change.

## 3. Project data built once per command (#228 and the audit)

### 3.1 The input layer and the defect

`lute_load::InputCache` (`lute-load/src/cache.rs`) memoizes, per run, each
root's manifest (`project`), its capability base (`base`: snapshot,
providers, defaults, plugin origins), each `(dir, uses, extends)` import
graph as a `ProjectVocab` (`imports.vocab`, with every fold stage that reads
only the imports), and each component set (`imports.resolve_components`).
`assemble_input_with_mode` (`lute-load/src/input.rs:176-264`) builds one
document's `CheckInput` from them: the document's text plus `Arc`s to the
shared values. This is the layer `ProjectModel::build_impl` assembles every
document through (`lute-model/src/project.rs:172-193`), and it is what
whole-project `check` shares since 0.49 (#173, ADR D14).

`lute_load::build_input` (`input.rs:59-73`) creates a **fresh**
`InputCache::default()` on every call. A command that calls it once per
document rebuilds the project base and vocabulary for every document: its
marginal cost per document grows with the project vocabulary. The decision
note measures every call site on the #173 grid and gives each a verdict.
This section fixes every one whose verdict is "fix".

**Rule.** A command that reads two or more documents MUST assemble them
through **one** `InputCache` for the whole run (it keys every root
internally), or through one `ProjectModel` per root obtained from one
`ModelMemo`. It MUST NOT call `build_input` (fresh cache) per document, and
it MUST NOT build a checked `ProjectModel` to read a manifest field: the
manifest is `InputCache::project(root)` (or `lute_load::manifest_context`
where the snapshot is needed without documents). `build_input` stays for
single-document commands.

### 3.2 `lute lint`

`lint_target` (`lute-cli/src/lint.rs:258-443`), per root:

1. **One cache.** `run_lint` creates one `InputCache` for the run and passes
   it to every `lint_target` call; every root's base and vocabulary are built
   once.
2. **The manifest from the cache.** `project_for_root` (`lint.rs:203-236`)
   reads `cache.project(root)` instead of `ProjectModel::build_single_root`.
   A manifest that does not load — an error or absent — keeps today's text
   and exit, `lute: cannot load project manifest {path}` (exit 2): the model
   turned a load error into an absent manifest (`project.rs:173-178`), so
   that is the message 0.52 printed. The model's other failure,
   `lute: cannot load project {root}: {error}`, was a walk error inside the
   model build; lint has already walked the files (`lint.rs:296-302`, which
   reports a walk error itself), so that path goes with the model. Its other
   cause, an unreadable document inside the root, is now reported by
   `build_lint_input` as the file's own I/O error (exit 2 either way; the
   only wording change of §3, listed in §13).
3. **One assembly, one parse.** `build_lint_input` (`lint.rs:162-201`) calls
   `assemble_input_with_mode(&cache, file, text, providers, Some(root), None,
   Mode::Ci)` and uses the parsed document it returns, after
   `apply_quest_tier_default` and `apply_chapters` exactly as today
   (`lint.rs:180-185`); it no longer parses the text a second time. A file
   that cannot be read keeps its exit-2 envelope.
4. **No `BuiltInput` kept.** For each document the build keeps only the
   `LintDocInput` and a `NameInputs` value — the `CheckInput` (text plus
   shared `Arc`s), the `TypedMeta` and the `use_speaker_lines` table that
   `display_name_dups` reads. `display_name_dups` (`lint.rs:498-539`) reads
   the cast origins by reference from `input.imports().rel.origins.cast`
   (no `clone()` per document, `lint.rs:511`). The cast table
   (`declared_cast`) stays per document, as whole-project `check` computes
   it (`reconcile.rs:388`).
5. **No `ProjectModel`.** Lint reads no check result (decision note,
   "Decisions changed" item 1).
6. **Rules that are off cost nothing per document.** With no active rule
   the engine returns before any per-document work (`engine.rs:119-122`,
   unchanged); with some, it computes the tables the rule targets read.
   `W-DISPLAY-NAME-DUP` always runs, as today.
7. Output is byte-identical: the same diagnostics, order, paths, exit codes
   and `--json` envelope for every project and every `--config`.

`BuiltInput` itself stops copying manifest data into each document
(`input.rs:196-261`): `defaults` is removed (every caller reads
`input.defaults()`, the shared base's value — the same `MetaDefaults`), and
`identity`, `identity_rename_decls` and `identity_rename_diags` are shared
(`Arc`) from the cached manifest. Every caller is migrated (clean cutover).

### 3.6 Cost gate: `vocab-grid.py` tiers

`scripts/vocab-grid.py` (the 0.49 #173 gate, `test.yml`) gains **tiers**.
The existing items are tier `check`. Each new tier measures one command on
the same four cells (100 and 400 scenes at 150 and 4 800 slots), with the
same method (minimum of `--runs` runs; marginal = (400 − 100) / 300), and
every command MUST exit 0 on the generated projects. `gate` runs every tier;
`--tier NAME` (repeatable) selects tiers; `grid` prints every tier's table.

| Tier | Command on project `P` | Items |
|---|---|---|
| `check` | `check --project P` | 0.49 items 1–3 unchanged (marginal CPU and RSS ≤ 1.5× from 150 to 4 800 slots; peak RSS ≤ 2×; `scenario`, `scenario reach`, `constraints` ≤ 1.1× `check`). |
| `endings` | `scenario reach --endings --project P` on the item-3 project (20 scenes + 400 quests, 2 400 slots) | ≤ 1.1× `check --project` in CPU and in RSS, as 0.49's item 3. |
| `lint` | `lint P` and `lint P --config <every rule off>` | L1: marginal CPU per document at 4 800 slots ≤ 1.5× the same at 150 (each config). L2: marginal RSS per document likewise ≤ 1.5×. L3: rules off, marginal CPU per document at 4 800 slots ≤ 1.0× `check`'s at 4 800. L4: default rules, ≤ 1.25× `check`'s. L5: peak RSS of 400 scenes at 4 800 slots ≤ 1.25× `check`'s (default rules). |
| `files` | `check <every scene file> --project P` | F1: marginal CPU ≤ 1.5× from 150 to 4 800 slots. F2: marginal CPU at 4 800 ≤ 1.5× `check`'s. |
| `loc` | `loc export --project P -o <tmp>`, `loc report --project P` | F1 and F2, each command. |
| `doctor` | `doctor --project P` | F1 and F2. |
| `fix` | `fix --check P` | F1 and F2. |

**Where the bounds come from** (decision note, measured on v0.52.0): `check`
costs 0.57/0.67 ms per document at 150/4 800 slots. The lint engine alone
costs about 0.1 ms per document, and an assembly through a shared cache
0.13–0.20 ms (the `tag` row), so a fixed `lint` is predicted at about
0.3–0.4 ms per document, 0.5–0.6× `check`. L3–L5 allow about 2× that
prediction and still fail today's lint (27× growth, 45 ms per document).
F2's 1.5× allows the commands that do more per document than `check`'s
per-document share (`loc` normalizes, `check <files>` runs the whole
per-file check). The growth items reuse 0.49's 1.5×. The implementing slices
record their measured values; the bounds are not loosened without the owner.

**#228's own reproduction** is also an acceptance test (plan, slice L1): the
issue's `gen.py`/`bench.py` (large vocabulary: 20 kinds × 200 members,
100 `per:` paths; 200/400/800 documents) where `lint p --config off.yaml`
has user time and peak RSS at most `check --project p`'s at every size.

## 4. `lute fix` and plugin stamps (#224)

### 4.1 One predicate for an old attribute spelling

`renames.rs` replaces `renamed_directive_attr(tag, key)` (`:176-181`) by

```rust
/// The current name of `key` on `::tag` when `key` is a renamed core
/// attribute (dsl 0.37.0 §4) AND the snapshot does not admit `key` on
/// `::tag` — neither the directive's own attribute nor a stamp on its
/// surface (plugin §14.1, 0.50.0 §3.4). `None` otherwise.
pub fn renamed_attr(tag: &str, key: &str, snapshot: &CapabilitySnapshot) -> Option<&'static str>
```

Every caller uses it, so the checker and the codemod make one decision:

- `directives.rs:382-386` (an omitted attribute's `default:` is judged only
  when the attribute is absent) and `:411-423` (a required attribute written
  under its old name): with a stamp `action` declared on `::cg`, `action` is
  not `display`, so `display`'s declared default is judged and `display`
  counts as absent.
- `renames::attr_diag` (`:204-215`, `E-RENAMED-ATTR`), reached after the stamp
  lookup (`directives.rs:284-295`) — unchanged behaviour, one predicate.
- `fix.rs:402-406` (rule 8, also under an old tag), and the hint of
  `renamed_directive_diag` (`renames.rs:184-200`, "its `action=` is now
  `display=`"), which judges the attribute on the new tag's surface.

### 4.2 `lute fix` reads each document's snapshot

`fix_document` (`fix.rs:99`) takes the document's `CapabilitySnapshot`
(`Option<&CapabilitySnapshot>`; `None` when it did not resolve). `run_fix`
(`rewrite.rs:586-651`) obtains it:

- for a `.lute` file under a manifest, from the `ProjectModel` of its root
  that the 0.42 volume migration already builds (`project_has_old_volume`,
  `rewrite.rs:1404-1422`). Both read one model per root from one
  `ModelMemo` for the run (§3.1): `document.input.snapshot()`;
- for a `.lute` file under no manifest, from `build_input_with` over one
  `InputCache` for the run (the core snapshot plus the document's own
  `plugins:`);
- `None` when the model or the assembly reports a resolution error for the
  document (`resolve_error`).

With a snapshot, rule 8 renames only where `renamed_attr` says so. With
`None`, rule 8 renames nothing in that document; every other rule runs.
Each site rule 8 does not rewrite because of the snapshot is a **kept**
site, printed on stderr in both modes:

> ``lute fix: scenes/intro.lute:9:31: kept `action` on `::cg` — the active profile declares it as a stamp attribute; the 0.37 rename to `display` does not apply``

> ``lute fix: scenes/intro.lute:9:31: kept `action` on `::cg` — the document's capability snapshot did not resolve, so `lute fix` cannot tell a stamp from the 0.37 spelling; run `lute check` and fix the project first``

The issue's project then fixes only the manifest's `luteVersion`
(`applied 1 fix(es) in 1 of 5 file(s)`) and checks clean afterwards.

### 4.3 The rule list in the report

`FixRule` (in `lute-check`, re-exported for the CLI) has one variant per
migration `lute fix` applies, with a stable kebab-case id and a one-line
description. The slice enumerates them from the code (the phases of
`fix_document`, `fix.rs:99-329`, and `fix_file`, `rewrite.rs:675-729`); at
least: `line-sigil` (`:line[…]` and every `:`-led content line → `@`),
`choice-into` (`as` → `into`), `choice-persist` (`persist="run"` with
`into`), `shot-heading` (`## Shot N.` prefix), `when-is` (`<when test>` →
`is`), `delivery` (content-line `delivery` → flag), `renamed-tag` (0.37
directive tags), `renamed-attr` (0.37 directive attributes),
`renamed-tag-attr` (0.37 `<choice label>`, `<match on>`), `line-id-label`
(content-line `id` → `::label`), `cel-0.32` (0.31 fact-query calls),
`domain-rename` (0.41 domains), `lute-version` (`luteVersion` stamps),
`bindings-version` (`bindingsVersion`), `volume` (0.42 members). `FixResult`
counts edits per `FixRule`.

- **Human output.** A changed file's line names its rules in `FixRule`
  order: `lute: ./scenes/intro.lute: would apply 3 fix(es): renamed-attr 3`
  (`applied` without `--check`). A file with nothing to fix and the summary
  line are unchanged. Kept sites print as §4.2.
- **`--json`** (`schemaVersion` **`0.53.0.fix`**, `envelope.rs:50`): each
  `files[]` entry gains `rules: [{ "rule": <id>, "fixes": <n> }]` (empty
  when nothing applies) and `kept: [{ "line", "column", "rule", "reason" }]`
  (`reason`: `stamp` or `unresolved`). Existing keys are unchanged.
- **`--help`** (`lute fix`) lists every `FixRule` description, the 0.37
  directive attribute renames included, and says that a key the active
  profile declares as a stamp is kept. A unit test asserts that the help
  text names every `FixRule`.

## 5. `pair` lints: `scope: document` (#225)

`PairScope` (`lute-manifest/src/lint.rs:125-135`) gains **`Document`**
(`scope: document`): one slot for the whole document, every row of every
section and top-level declaration, at every depth, in document order — the
`section` walk without the reset at each section.

- `lute-lint/src/pair.rs`: `Frame::Document`; `PairRule::parse` maps
  `PairScope::Document` to it; `PairFault`'s unit is `document`
  ("— opened here, with no close in this document", "— a close with no open
  pair in this document").
- `lute-lint/src/nodes.rs:556-610` (`walk_nodes_with`): the visitor gets
  `document_start()` before the first section and `document_end()` after the
  declarations, so a `Document` frame spans both. Body and section frames
  are unchanged.
- Cost: one slot push and pop per document; `pair_slots` counts them. The
  0.51 `pair` axes of `lute-bench lint-nodes` are unchanged.
- `node` rules get no scope (decision note, departures item 4).
- Docs: `tooling/linting` lists the third scope with the issue's example.

**Tests.** The issue's `skip.lute` with `scope: document` lints clean
(failing before: `E-LINT-CONFIG unknown variant`); an unbalanced open across
sections reports "no close in this document"; `body` and `section` outputs
unchanged.

## 6. References inside structured plugin frontmatter (#226)

### 6.1 One walk

`frontmatter_ref` (`lute-check/src/meta/frontmatter.rs:859-887`) is replaced
by a recursive walk over the key's declared `Type` and the authored YAML
value:

- a reference type (`Entity`, `Domain`, `EnumFromOption`, `ProviderRef`,
  `AssetKind`) with a string value yields one reference;
- `List(t)`: each item, at its index;
- `Record(fields)`: each authored field present in the declaration, by name;
- `Map { key, value }`: each key (against `key`) and each value (against
  `value`);
- any other type yields nothing. A value whose shape does not match is
  `E-FRONTMATTER-SCHEMA`'s (unchanged) and yields nothing.

Each reference carries a `FrontmatterPath` (the key and its field names and
indices). `check_frontmatter_refs` (`:893-933`) checks each with
`check_attr_value`, owner `frontmatter`, at the key's span, and the attribute
name rendered from the path: `` `mirra` is not a member of entity kind
`person` (field `partner` of `talk` of `frontmatter`) — did you mean `mira`? ``
(a list item: ``item 2 of `guests` ``; nested: ``field `b` of item 1 of
`a` ``). A top-level or list value keeps today's text
(``attribute `lead` of `frontmatter` ``).

### 6.2 `W-DOMAIN-UNREAD` counts frontmatter types

`domain_reading_set` (`project_check/domains.rs:23-57`) adds, for every
`snapshot.frontmatter` key type, the names `collect_domain_names` finds
(`:128-145`, which already recurses into `List`, `Record` and `Map`). The
warning's message lists the new source ("… no plugin frontmatter key is typed
by it …").

### 6.3 Tests

The issue project: `talk.partner: mirra` is `E-BAD-ENUM` with the
did-you-mean and the field path (failing before); `W-DOMAIN-UNREAD` on
`person` is gone (failing before). A `providerRef` field, a `list` of
records, a `map` keyed by entity, and a record field of a non-reference type
(no reference) each have a test.

## 7. Quest grants and accept cycles (#227)

### 7.1 The host is an accept source of an `accept="external"` quest

`quest_anchors` (`connectivity/graph_assembly.rs:434-464`) builds an accept
anchor from the in-script accept sources (`::accept`, reward `accepts`). For
an `accept="external"` quest the anchor also holds the **host** as a source:
it holds from the start of play. Every consumer of anchors treats it so:

- **Reachability** (`reachability.rs:271-288`): the anchor is `Reachable`.
  The issue's `letter` is `Reachable`, and so is `intro` through it.
- **Can-start** (`start_cycles.rs`): the anchor can always start (§7.2).
- **`lute scenario reach` text**: the anchor line lists the host first:
  `[accept] the host (accept="external") | quest(intro)`; JSON adds
  `"host": true` on that anchor. A quest with no in-script accept source
  stays absent (unanchored), as today.
- The `[accept]` graph edges are unchanged: drawn where they close no cycle
  (`graph_assembly.rs:268-295`), so `impact` and envelopes keep them.

### 7.2 In-script accept deadlocks are start cycles

`gates()` (`start_cycles.rs:16-22`) also counts an `Accept` anchor as gating,
**unless** it holds the host. The 0.49.0 §6.1 fixed point is unchanged
otherwise: a quest can start when every gating anchor has some source that
can start. So a cycle of `start` and in-script accept anchors that no source
outside enters is **`E-QUEST-START-CYCLE`** (error, project-wide), one per
strongly connected set, at the least quest's `start` — or at its `id`
attribute when the quest has no `start` (an accept-driven quest). The path
names each edge kind:

> `` quest start cycle: quest(intro) -[start]-> quest(letter) -[accept]-> quest(intro) — each waits for the next (a `start` for its condition, an accept for the `::accept` or reward that grants it) and no source outside the cycle starts any of them; start one of them from something outside the cycle, or let the host grant one with `accept="external"` ``

`reach` for such a quest is the 0.49 start-cycle `Unknown` with this path.
The graph prints the deadlocked quests on the "part of a start cycle" line,
as for a `start` cycle. Rationale: decision note, departures items 6–8.

### 7.3 A gated grant is written with `follows=`

`accept="external"` with `start` stays refused (decision note, "Decisions
changed" item 2). The spelling that keeps the condition visible to analysis
and to the host is `follows=` (a quest's prerequisite formula,
`quest-lifecycle.md` §Cross-document reachability), on an `accept="external"`
quest or on a quest a reward accepts. Messages:

- `E-ATTR-TYPE` on the pair (`logic_attrs.rs:684-687`):
  `` `<quest id="letter">` carries both `accept="external"` and `start`: an externally accepted quest activates when the host grants it, never by a `start` condition; drop `start`, and write the scenes and quests it waits for as `follows="…"` (for example `follows="completed('intro')"`), which analysis and the host read ``
- `E-QUEST-START-SELF` (`match_check/records.rs:398`): after "… is written
  `accept="external"` without a `start`" add "; the other conditions it
  waits for, if they name scenes or quests, go into `follows="…"`".
- `E-ACCEPT-TARGET` for an accepted quest with `start` (`accept.rs:344`):
  after "only an accept-driven quest (no `start`) can be accepted" add
  "; drop its `start` and keep the scenes and quests it waits for as
  `follows="…"`".

Each message's suggested spelling is verified to check clean (§2).

## 9. Bounded loops across sections (#231)

### 9.1 What a section is

A `##` section is presentation and identity metadata: the heading, the
optional `{#id}` in the artifact's descriptive `sections` table, and the
first segment of the build-local `position`. It is not a runtime range, a
resume point, a host entry or a jump target (decision note, "#231: what a
section is at runtime"). The runtime runs a scene's sections as one range.

### 9.2 Rule

The top-level sections of a document are **one loop scope**, as they are one
range (0.52.0 §5.1, `BodyRange::TopLevel`). A bounded `::jump{to max}` may
loop back to a label in an earlier section; the region is every node from
the head label to the jump, across the sections between. Every other rule
applies unchanged: `E-JUMP-INTO-LOOP` (an entry other than the head),
`E-JUMP-LOOP-CROSS`, nesting, `E-JUMP-INTO-BODY`, and `E-JUMP-LOOP-SCOPE` for
a loop that leaves a hub option, `<return>`, `<on>`, `<objective>`, entry or
beat body. `::end` inside a region stays legal, as within one section today.

In `next_labels.rs`, the scope chain treats `BodyKind::Section` bodies as one
top-level body for the loop rule, so `E-JUMP-LOOP-SCOPE` never names a
section; `leave_message`'s `Section` arm (`:243`) is removed and the
registry summary (`registry.rs:714-718`) drops "or a section". `LoopTable`
regions (`first..=last` positions) need no change.

### 9.3 The flow walks

`loop_walk::region_len` (`loop_walk.rs:200-208`) becomes `loop_walk::region`,
returning a `Region<'d>`: the node slices from the head to the last node that
holds a back edge — the rest of the head's body, and, at the top level of a
document, the bodies of the following sections up to the one that holds the
last back edge (its prefix through that node). Each walk visits the parts in
order where it visited the one slice:

- `defassign.rs:618-658` (`label`, `head`), `fact_must.rs:1057`,
  `inject.rs:647` (the stage fold; the compiler's `walk_*` read its head
  state, `stage.rs`), `cast/presence/walk.rs:319` (`kill_writes`).
- Each walk's top-level iteration over `doc.sections` (`fact_must.rs:775-777`,
  `cast/presence/mod.rs:170-176`, the scene branch of the checker's walk
  `check/pipeline.rs:443-447`, and the stage fold's) gives the walk the
  following sections while it walks a section at depth 0, so `region` can
  see them. Nested bodies are unchanged.
- The final pass is the ordinary walk, which already continues across
  sections, so diagnostics are reported once.
- `LoopWalkStats` counts the probe nodes of every part.
  `lute-bench flow-loops` gains a `sections` shape (a loop whose region spans
  k sections), with work asserted linear like the 0.51 region axis.

The compiler and runtime need no change: positions are ordered across
sections and the runtime's `loop_table` works on record indices.

### 9.4 `E-JUMP-INTO-LOOP`: the one-option hint

When the entering forward jump is the last node of a `<choice>` body (a
`<branch>` option) and no other jump targets its label, the message adds:

> `` — `blockA` is reached only from option `a` of `<branch id="pick">`: move the block into that option's body ``

The suggested move is verified to check clean in the test.
