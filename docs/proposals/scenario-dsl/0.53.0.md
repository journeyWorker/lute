# Lute 0.53.0 — dogfood round 3

This is the normative 0.53.0 contract. The words **MUST**, **MUST NOT**,
**SHOULD** and **MAY** have their RFC 2119 meanings.

The release resolves the eight issues of dogfood round 3 (porting a large
existing VN / live-game content set): #224, #225, #226, #227, #228, #229,
#230, #231. The headline is #228: `lute lint` rebuilt the project for every
document. The audit that #228 required found the same defect in five more
commands; all of them are fixed here (§3). The decisions, the measurements
and the per-command audit are in
[`2026-10-28-lute-0.53-decisions.md`](../../superpowers/notes/2026-10-28-lute-0.53-decisions.md);
where this spec departs from an issue's suggestion or an owner default, the
note gives the evidence and Appendix B lists every decision. The rule
throughout is conservative: the smallest surface, one spelling per concept,
static analysis kept sound, refuse rather than guess, and the runtime and the
checker agree.

The base is `main` at **v0.52.0** (`596d19c5`). Code anchors are cited at
`596d19c5`; Appendix A lists them by symbol.

Implementation plan:
[`2026-10-28-lute-0.53.0-dogfood-r3.md`](../../superpowers/plans/2026-10-28-lute-0.53.0-dogfood-r3.md).

## 1. Scope and version contract

This is a minor release. Every public version axis is `0.53.0`: toolchain,
`luteVersion` (`LUTE_LANG_VERSION`), `irVersion`, `eventVersion`,
`snapshotVersion` and the seven npm packages. The contract schemas move to the
`0.53` line (`schemas/lute-{ir,events,snapshot,player-bindings}-0.53.schema.json`)
with no shape change. `bindingsVersion` and the player save/profile format
become `"0.53"`. This follows the 0.52.0 §1 precedent.

| Axis | 0.53.0 contract |
|---|---|
| Language | **Looser:** a bounded loop may span the top-level `##` sections of a document (§9). **Stricter:** a misspelled reference in a field of a `record`-typed (or `map`/nested `list`) plugin frontmatter value is an error (§6). |
| Static semantics | In-script accepts are routes regardless of `follows`; an `accept="external"` quest has a host route (open, or once `follows` holds as host policy); reach repeats over undrawn accept edges; an in-script accept deadlock is `E-QUEST-START-CYCLE` (§7). |
| IR | **Unchanged.** Schemas renamed `-0.53`. |
| Semantics (D5) | **No new id.** The runtime does not change. |
| Event / snapshot | **Unchanged.** Schemas renamed `-0.53`. |
| Plugin manifests | Unchanged. |
| Lint | `pair` rules take `scope: document` (§5). `lute lint` builds the project input layer once per root (§3.2). |
| CLI | `lute fix` keeps plugin stamps, names its rules and reports kept sites; report `0.53.0.fix` (§4). Every multi-document command shares the project input layer (§3); `lint` reads only its operands and `catalog refresh`/`doctor` read `catalogDir` from the manifest (§3.9). |
| Editors (LSP) | One input cache per project root across requests, validated on every request against its recorded filesystem dependencies (lookups, listings, files; metadata tuple then content), with bounded retention (§3.5). |
| Runtime / player | Unchanged. |
| `capabilitySnapshot` | **Unchanged.** |
| Report ids | `fix` moves to `0.53.0.fix` (§4.3). Every other report id is unchanged. |

Outside the deltas listed in §15, every output captured by
`scripts/cli-snapshot.py` MUST be byte-identical to 0.52.0 after version-stamp
normalization. Compare with `--strict` against 0.52.0. The plan's first slice
extends the snapshot to the commands §3 changes (§3.8) before the baseline is

## 2. Shared rules

The 0.52.0 §2 rules apply unchanged: a regression test that fails on the base
for every behaviour change (the issue reproductions first); one diagnostic
shape (registered in `crates/lute-cli/src/codes/registry.rs` and
`crates/lute-check/src/evidence.rs`, blessed with `LUTE_BLESS_DIAGNOSTICS=1`,
website EN + KO); **no hint recommends a spelling the checker rejects**; no
silent drop; byte stability for projects that use none of the changed
constructs (except §15); documentation in the same change; and
`docs/design/rust-coding-rules.md` for new Rust code. In particular:

- **Newtypes and enums, not strings:** `FixRule` (one variant per `lute fix`
  migration, §4.3), `FixKept` (why a site was not rewritten), `PairScope::Document`
  (§5), `FrontmatterPath` (a field path inside a frontmatter value, §6),
  `HostGate` (`Always` or `Follows(formula)`, the host route of an
  accept anchor, §7.1), `Region` (a loop region's node slices, §9.3),
  `ProjectInputs` and `Fingerprint` (the LSP's per-root cache, §3.5).
- **One function per rule.** Whether an attribute is an old spelling is one
  function the checker and `lute fix` call (§4.1). Where a frontmatter type
  holds references is one walk that the reference check and
  `W-DOMAIN-UNREAD` share (§6). A loop region is computed by one function
  every flow walk calls, the compiler's stage walk included (§9.3).
- **Project data is built once (ADR D14, extended by this release).** A
  command that reads two or more documents of a project builds the project
  input layer once per cache key and holds per document only its overlay;
  the LSP keeps it across requests (§3).
- **No HIR, no Fold, no synthesized nodes** (rules §7). **No new semantic
  id**: the runtime does not change.

## 3. Project data built once per command (#228 and the audit)

### 3.1 The input layer and the defect

`lute_load::InputCache` (`lute-load/src/cache.rs:37-130`) memoizes, per run,
each root's manifest (`project`), the provider sets, the capability
snapshots, the plugin origins and the resolved bases (`base`: snapshot,
providers, defaults, plugin origins), each `(dir, uses, extends)` import
graph as a `ProjectVocab` (`imports.vocab`, with every fold stage that reads
only the imports), and each component set (`imports.resolve_components`).
`assemble_input_with_mode` (`lute-load/src/input.rs:176-264`) builds one
document's `CheckInput` from them: the document's text plus `Arc`s to the
shared values. This is the layer `ProjectModel::build_impl` assembles every
document through (`lute-model/src/project.rs:172-193`), and it is what
whole-project `check` shares since 0.49 (#173, ADR D14).

`lute_load::build_input` (`input.rs:59-73`) creates a **fresh**
`InputCache::default()` on every call. A command that calls it once per
document rebuilds the project base and vocabulary for every document: its
marginal cost per document grows with the project vocabulary. The decision
note measures every call site on the #173 grid and gives each a verdict.
This section fixes every one whose verdict is "fix".

**Rule.** A command that reads two or more documents MUST assemble them
through **one** `InputCache` for the whole run (it keys every root
internally), or through one `ProjectModel` per root obtained from one
`ModelMemo`. It MUST NOT call `build_input` (fresh cache) per document, and
it MUST NOT build a checked `ProjectModel` to read a manifest field: the
manifest is `InputCache::project(root)` (or `lute_load::manifest_context` /
`lute_manifest::project::load_project` where no cache exists). `build_input`
stays for single-document commands. A long-lived process (the LSP) keeps
one cache per root across requests with exact invalidation (§3.5).

**"Once" means once per cache key, not once per root.** The cache keys a
base by root, providers directory, resolution profile, the document's
`plugins:` and the permission profile (`BaseKey`, `SnapshotKey`); documents
of one root that select different profiles or plugins MUST keep distinct
entries, exactly as today. The tests and counters below count builds per
key: one build per distinct key, never one per document.

**What stays per document.** The overlay (text, parsed document, `TypedMeta`,
import diagnostics anchored at the document) and, as today, the
`declared_cast` table `W-DISPLAY-NAME-DUP` reads (`reconcile.rs:388`, a
clone of the cast per document). That clone is pre-existing in `check` and
is sized by the cast, not by the state vocabulary the gate grows; 0.53 does
not change it and does not claim it is shared.

### 3.2 `lute lint`

`lint_target` (`lute-cli/src/lint.rs:258-443`), per root:

1. **One cache.** `run_lint` creates one `InputCache` for the run and passes
   it to every `lint_target` call; every base and vocabulary key is built
   once.
2. **The manifest from the cache.** `project_for_root` (`lint.rs:203-236`)
   reads `cache.project(root)` instead of `ProjectModel::build_single_root`.
   A manifest that does not load — an error or absent — keeps today's text
   and exit, `lute: cannot load project manifest {path}` (exit 2): the model
   turned a load error into an absent manifest (`project.rs:173-178`), so
   that is the message 0.52 printed.
3. **Only the operands are read.** The model build read **every** document
   of the root (`project.rs:155-185`), so on 0.52 `lute lint good.lute`
   failed (exit 2, `lute: cannot load project {root}: …`) when an unrelated
   sibling `bad.lute` of the same root was unreadable (invalid UTF-8, no
   permission). 0.53 reads only the operands, the manifest, the plugins, the
   providers and the imports they reach: that lint succeeds, and an
   unreadable **operand** is reported by `build_lint_input` as its own I/O
   error (exit 2). This is an intentional correction (§3.9).
4. **One assembly, one parse.** `build_lint_input` (`lint.rs:162-201`) calls
   `assemble_input_with_mode(&cache, file, text, providers, Some(root), None,
   Mode::Ci)` and uses the parsed document it returns, after
   `apply_quest_tier_default` and `apply_chapters` exactly as today
   (`lint.rs:180-185`); it no longer parses the text a second time.
5. **No `BuiltInput` kept.** For each document the build keeps only the
   `LintDocInput` and a `NameInputs` value — the `CheckInput` (text plus
   shared `Arc`s), the `TypedMeta` and the `use_speaker_lines` table that
   `display_name_dups` reads. `display_name_dups` (`lint.rs:498-539`) reads
   the cast origins by reference from `input.imports().rel.origins.cast`
   (no `clone()` per document, `lint.rs:511`). The `declared_cast` table
   stays per document (§3.1).
6. **No `ProjectModel`.** Lint reads no check result (decision note,
   "Decisions changed" item 1).
7. **Rules that are off cost nothing per document.** With no active rule
   the engine returns before any per-document work (`engine.rs:119-122`,
   unchanged); with some, it computes the tables the rule targets read.
   `W-DISPLAY-NAME-DUP` always runs, as today.
8. On every project whose documents are all readable, the output is
   byte-identical: the same diagnostics, order, paths, exit codes and
   `--json` envelope for every `--config` (the §3.8 snapshot commands).

`BuiltInput` itself stops copying manifest data into each document
(`input.rs:196-261`): `defaults` is removed (every caller reads
`input.defaults()`, the shared base's value — the same `MetaDefaults`), and
`identity`, `identity_rename_decls` and `identity_rename_diags` are shared
(`Arc`) from the cached manifest. Every caller is migrated (clean cutover).

### 3.5 The LSP: one input cache per root across requests

**Measured cause** (decision note): every request (`analyze` on open and
on change, `analyze_declaration`, the document queries) creates a fresh
`InputCache` (`lute-lsp/src/backend/{analysis.rs:46,document.rs:42,declaration.rs:62}`),
so every keystroke folds the whole project base and vocabulary again: about
40 ms CPU per request at 4 800 slots against ~0 at 150 (proxy: a
single-file `check`, which does the same assembly).

**Rule.** The `Backend` (`backend/mod.rs:43`) holds a `ProjectInputs`
table: per project root (and one entry for documents under no root), an
`Arc<InputCache>` and the **dependency record** of everything that cache
observed on disk. A request reuses the entry when every dependency still
validates (below), else replaces it with a fresh cache. The analyzed
document's own text is never cached: it comes from the request, as today.
The project root itself is found per request (`find_project_root`, an
upward walk), so creating or removing a `lute.project.yaml` between a
document and its root selects another entry without any cache involvement.

**Dependencies, not just files read.** The cache records, at each site
where it consults the filesystem, a `Dependency` (one enum; the record is
`InputCache::dependencies()`):

- **`Lookup { path, outcome }`** — every lexical path the cache resolves,
  as authored and joined (before canonicalization), with its outcome:
  `Missing`, `Resolved { target, fingerprint }` (the canonical target and
  the target file's fingerprint), or `Error(kind)`. Sites: every `uses:`
  and `extends:` reference (`schema_import.rs:1420-1440`; a failed
  `canonicalize` is today `E-USES-NOT-FOUND`, and is now recorded as
  `Missing`), every `components:` reference, the manifest's
  `pluginsDir`/`catalogDir`/`defaults: uses:` entries that name a path, and
  the manifest file itself. Validation re-resolves the path: a created
  missing file, a deleted file, and a **retargeted symlink** (anywhere on the
  path; the canonical target changes) all fail validation.
- **`Listing { dir, filter, entries }`** — every directory enumeration that
  decides which files exist, with the filter it applied and the sorted
  matching entry names: the manifest's `defaults:` glob expansion
  (`lute-manifest/src/project.rs:1140-1203`, `read_dir` `:1187`), the
  provider catalog directory (`provider.rs:79`), the plugins directory and
  each plugin's export directories (`lute-load/src/cache.rs:286`, `:295`;
  `lute-manifest/src/loader.rs:1639`, `:2222`). Validation re-lists: an
  added or removed matching file fails it; a non-matching file does not.
- **`File { path, fingerprint }`** — every file whose bytes the cache read
  and that no `Lookup` above already covers (plugin files found by a
  listing, provider catalog files, schemas reached through a listing).

The recording is done by the functions that touch the filesystem (each
takes a `&DependencySink`; the CLI passes a no-op sink, so CLI cost and
output are unchanged).

**Fingerprint.** On Unix `(length, mtime, ctime, inode, device)` from one
`stat`; on Windows `(length, last-write time, file index, volume serial)`.
`ctime` cannot be set by `touch` or by editors, and a replace-by-rename
changes the inode/file index. Only when the tuple differs from the recorded
one is the file hashed (SHA-256; `sha2` is already a dependency of
`lute-manifest` and `lute-model`): an equal hash keeps the cache (and
updates the recorded tuple), a different hash fails validation. Validating
an entry costs one `stat` per `File`/`Lookup` target and one `read_dir` per
`Listing` per request.

**The remaining limit, stated plainly:** an edit that preserves every field
of the tuple — possible only by tampering with file-system metadata (e.g.
setting the clock back and rewriting in place so `ctime` lands on its old value) — is not
detected by request-time validation. A server restart, or a
`didChangeWatchedFiles`/`didSave` notification for that path (which forces a
content comparison, below), revalidates it. Nothing else is claimed.

**Notifications mark for revalidation; they never drop by themselves.**

1. **Every request** validates the entry's dependencies before use (the
   guarantee, also for clients without file watching).
2. **`workspace/didChangeWatchedFiles`** (new handler): the server registers
   watchers (dynamic registration when the client supports it) for
   `**/lute.project.yaml`, `**/*.{yaml,yml,json}` and `**/*.lute`. A
   notified path is marked **dirty** in every entry whose record names it
   (as a file, a lookup path or target, or inside a listed directory). The
   next validation of a dirty dependency compares **content** (re-resolve,
   re-list, hash) regardless of the fingerprint tuple; an unchanged touch
   therefore keeps the cache, in this path exactly as in the request path.
3. **`textDocument/didSave`** of a recorded input marks it dirty the same
   way.
4. **`didChange` of an open input document** does not invalidate: the LSP
   reads schemas, plugins and components from **disk**, not from open
   buffers, on 0.52 as on 0.53 (only the analyzed document's text comes
   from the buffer, `analysis.rs:50-58`; `did_change`,
   `requests.rs:314-326`, stores only that text); an unsaved schema edit is
   therefore not an input until it is saved, exactly as today. Reading
   inputs from buffers is not in 0.53 (§16).

**Bounded retention: the dependency closure of retained configurations.**
Keys come from document frontmatter (profile, `plugins:`, `uses:`,
`extends:`), so unsaved edits create new keys, and evicting only the
top-level memos would not release what they share: `InputCache` and
`ImportCache` hold several independently owning maps. The persistent cache
therefore retains exactly the **dependency closure** of its retained
configurations and reclaims everything else.

- **Configuration.** A document's configuration is the tuple of keys its
  last analysis used: snapshot key `(root, profile, plugins)`
  (`cache.rs:43-49`, `:78-92`), base key, import key `(directory, uses,
  extends)`, vocabulary key, component-set key.
- **Retained configurations** = the **live** ones (used by at least one
  open document, tracked per URI in `ProjectInputs`) plus at most **N = 4**
  **superseded** ones (no open document uses them any more, because its
  frontmatter changed or it closed), in LRU order. Four covers flipping
  between a few profiles or `uses:` lists while editing without rebuilding.
- **Every owning memo** records, per entry, the entries it was built from
  (its children) and the dependency records it observed: `InputCache`'s
  `projects` (loaded manifests), `providers`, `snapshots`, `plugin_origins`
  and `bases` (`lute-load/src/cache.rs:43-50`); `ImportCache`'s `imports`
  (per import key), `vocabs`, `components` (component sets) and `files`
  (parsed imported files) (`schema_import.rs:321-328`, `:350-355`,
  `:505-518`).
  Dependency records (`Lookup`, `Listing`, `File`) are owned by the entry
  whose build observed them, not by a flat list.
- **Reclamation** is a mark-and-sweep after each request (under the entry
  lock): mark every memo entry reachable from a retained configuration's
  keys or from a key **pinned by an in-flight request** (a request pins its
  configuration's keys for its duration; an `Arc` it holds keeps the value
  alive regardless); sweep every unmarked entry from **every** owning memo
  (`Memo` gains `remove`, `schema_import.rs:404-435`), with its dependency
  records. Parsed files are kept exactly while some retained configuration
  reaches them — no fixed file limit.
- **Validation** (above) walks only the records of retained entries, so an
  obsolete lookup (a missing import of a superseded `uses:`) is neither
  kept nor revalidated once swept.
- **`didClose`** (`requests.rs:328`) moves the document's configuration to
  the superseded LRU (if no other open document uses it); when the last
  open document of a root closes, the root's entry is dropped entirely.
- A cached failure (an invalid profile name, a missing plugin, a missing
  import) is a value under its key, retained and reclaimed the same way.

So an entry holds the closure of at most (live configurations + 4), in
every memo and in its dependency records, whatever the number of edits; the
sweep costs O(retained entries) per request.

**Profiles.** A document that selects another profile or `plugins:` gets its
own snapshot and base, built once and reused while live or within the LRU.

**Tests.** (1) Twenty requests on one document of a generated project build
one base (`InputCache` counter) — failing before (twenty). (2) An edited
schema (a new enum member the document uses) is picked up on the next
request: the `E-BAD-ENUM` disappears — without a watcher notification. (3)
The same for a plugin directive file and for the manifest's
`defaults: uses:`. (4) **Creating a missing import**: a document whose
`uses:` names an absent file reports `E-USES-NOT-FOUND`; after the file is
created the next request is clean. (5) **Adding a glob or catalog match**: a
new schema matching a `defaults:` glob, and a new provider file in the
catalog directory, are each picked up on the next request; a non-matching
new file keeps the cache. (6) **Retargeting an imported symlink** (Unix):
`uses: [link.yaml]` with `link.yaml → a.yaml`, then `→ b.yaml`: the next
request reads `b.yaml`. (7) A touched but unchanged schema keeps the cache
(counter unchanged), both without and with a `didChangeWatchedFiles` /
`didSave` for it. (8) **Equal-length edit with mtime restored** (Unix):
rewrite a schema with different bytes of the same length, then restore its
mtime with `touch -d`: detected through `ctime`, the next request reads the
new bytes. (9) Two profiles in one root keep two bases. (10) A
`didChangeWatchedFiles` for a changed recorded path invalidates; for an
unrelated path does nothing. (11) **Configuration churn**: one open document
whose frontmatter cycles (unsaved) through 20 configurations mixing
distinct `plugins:` maps, `uses:` lists of existing imports, and `uses:`
lists naming distinct **missing** imports. After every step the test
inspects **every owning memo** — `projects`, `providers`, `snapshots`,
`plugin_origins`, `bases` (`InputCache`), `imports`, `vocabs`,
`components`, `files` (`ImportCache`) — and the total
dependency-record count: each equals the closure of live + the last 4
configurations (computed independently by the test), so none grows past
the fifth step; returning to one of the last four reuses it (build
counters unchanged), returning to the sixth-last rebuilds it. An in-flight
request pinning a superseded configuration (the test holds its pin across
a sweep) keeps its entries until it ends. (12) **Document close**: open
three documents with distinct profiles, close two: their configurations
move to the LRU and their exclusive entries stay within the closure bound;
close all: the entry is dropped.

**Measurement and gate.** `lute-bench lsp-requests <project> --doc <file>
--requests N` drives the backend's analysis function (the pure part of
`analyze`, factored so the bench and the backend call the same code) and
prints the median warm request time, the base and vocabulary build counts
and its peak RSS; `--fresh` creates a cache per request, reproducing 0.52
for the before/after table; `--churn K` cycles the document's frontmatter
through K configurations and prints the retained entry count per memo and
the dependency-record count. The
`vocab-grid.py` tier `lsp` (§3.7) runs it.

### 3.7 Cost gate: `vocab-grid.py` tiers

`scripts/vocab-grid.py` (the 0.49 #173 gate, `test.yml`) gains **tiers**.
The existing items are tier `check`. Each new tier measures its command on
the same four cells (100 and 400 scenes at 150 and 4 800 slots), with the
same method, and every command MUST exit 0 on the generated projects.
`gate` runs every tier; `--tier NAME` (repeatable) selects tiers; `grid`
prints every tier's table.

**Method** (amended 2026-10-28 after review, for shared-machine noise):
`--runs` **interleaved rounds** (default 7 for `gate`), each running every
command once on every cell; a cell's CPU is the **median** over the rounds,
its peak RSS the minimum; marginal = (400 − 100) / 300. A **CPU slope item**
(0.49 item 1, L1, L3, L4, F1, F2) passes when measured ≤ max(bound ×
reference, reference + 0.10 ms/doc): at about 0.1 ms/doc a slope is a 30 ms
difference of two cells, so a ratio alone judges noise, while the allowance
keeps real per-document growth failing (0.52.0's lint and streaming slopes
were 28–58×). A reference slope that is not positive gives no verdict: its
command is remeasured over a doubled interval (800, then 1 600 scenes), and
a reference still not positive is a measurement error (exit 2). The other
items keep their ratios; the counters stay exact.

**Every tier asserts CPU and memory.** Two memory criteria, chosen per
command by what its memory does, plus a deterministic counter:

- **Retaining commands** (they hold every document until the end: `check`,
  `lint`): marginal RSS per document at 4 800 slots ≤ 1.5× the same at 150,
  as 0.49's item 2.
- **Streaming commands** (they drop each document: `check <files>`, `loc`,
  `doctor`, `fix`): their marginal RSS is about 0 (0.001–0.005 MB per
  document, decision note), so a ratio of two near-zero numbers is noise.
  Instead: **M1** peak RSS(400 scenes, 4 800 slots) ≤ 1.5× peak RSS(400
  scenes, 150 slots) — a per-document copy of vocabulary-sized data that
  the command kept would grow with slots; **M2** peak RSS(400 scenes,
  4 800 slots) ≤ 1.25× `check --project`'s at the same cell.
- **Work counter** (every tier): with `LUTE_STATS=input-cache` in the
  environment, `lute` prints one stderr line at exit,
  `lute: stats: input-cache bases=<n> vocabs=<n> assemblies=<n>`, counted
  over the run's caches (a model's included). The expected `bases` and
  `vocabs` are **derived per fixture from its distinct memo keys**, never
  a fixed number: a base per distinct (profile, `plugins:`, providers,
  permissions) among the documents the command reads, a vocabulary per
  distinct (directory, `uses:`, `extends:`, base) — the vocabulary key
  includes the document's directory (`lute-load/src/input.rs:233-237`,
  `schema_import.rs:351-369`). The generator's scene grid: 1 base, 1
  vocabulary (one `scenes/` directory, no `uses:`); the item-3/`endings`
  fixture (scenes and quests in two directories,
  `lute-bench/src/vocab.rs:128-137`): 1 base, **2** vocabularies.
  `vocab-grid.py` computes the expectation from the fixture it generated
  (directories × frontmatter configurations it wrote) and asserts the
  counter equals it **and is the same at 100 and 400 documents** (no
  growth with document count). The variable is for tooling only
  (documented in `tooling/cli`; never set by the snapshot).

## 7. Quest grants and accept cycles (#227)

### 7.1 The routes into an accept-driven quest

An accept-driven quest (no `start`) activates when it is accepted
(`machine/quest.rs:459-482`). There are two kinds of accept, and they differ
in who decides:

- **In-script accepts** — a `::accept` and a reward kind's
  `effects.accepts` — call `accept_quest` directly (`commands.rs:50-62`,
  `quest.rs:1079-1080`); the quest activates at the next lifecycle round,
  **whatever its `follows=` says**. `follows` is not loaded into the
  runtime's quest declaration at all: the compiler writes it only into
  `prereqEdges` (`lute-compile/src/lib.rs:1363-1369`).
- **The host's grant** of an `accept="external"` quest (the board, the menu,
  the server). The host owns that grant and its policy (ADR D1). A
  `follows=` on such a quest is the **declared condition under which the
  host grants it**: Lute carries it to the host in `prereqEdges` and
  analysis reads it as host policy. Lute does not enforce it, in 0.53 as
  before; 0.53 adds no runtime gate.

**Anchors.** `quest_anchors` (`connectivity/graph_assembly.rs:434-464`)
today skips every synthesized anchor of a quest that declares `follows`
(`decls.with_after`, `:442`), so a reward-accepted quest with `follows`
was analysed as if `follows` gated it. 0.53 builds, for every accept-driven
quest, its **accept anchor** whether or not it declares `follows`:

- the anchor's sources are the in-script accept sources (any-of), each an
  unconditional route;
- for an `accept="external"` quest the anchor also holds the **host
  route**: `HostGate::Always` without `follows`, `HostGate::Follows(formula)`
  with a valid one, `HostGate::Unreadable` with a malformed one (the route's
  verdict is `Unknown`: its condition cannot be read);
- **The authored `follows` formula is kept separately from the activation
  route state.** Today a quest node's `prereq` holds `PrereqState::Valid`
  from `follows` and is then **replaced** by `PrereqState::Anchored` when
  anchors are synthesized (`graph_assembly.rs:108-158`), and the edge loop
  reads only `Valid` (`:228-244`); so moving anchors onto quests with
  `follows` would silently drop their edges. 0.53 gives `GraphNode` a
  separate field `follows: FollowsDecl` — the authored declaration, a
  three-state enum `Absent` / `Malformed(code)` / `Valid(PrereqFormula)`,
  set from the attribute whatever the activation state (`Malformed` carries
  the code already reported, `E-CONN-PROFILE`) — next to `prereq`
  (activation: `Absent`/`Valid`/`Invalid`/`Anchored`). The two are
  independent: an anchored quest keeps its `Malformed` or `Valid`
  declaration. The edge loop emits `follows`'s atom edges from a `Valid`
  declaration for **every** quest that declares it — external, non-external reward-accepted, or `start`-driven — exactly
  the edges 0.52 drew, without treating it as a gate. Only the host route
  reads it as a condition. Start and subquest anchors keep the 0.52 skip for
  quests with `follows`.
- **Every authored-metadata reader reads `GraphNode::follows`; every
  activation reader keeps reading `prereq`.** Metadata readers (they report
  what the author declared): the edge loop (`graph_assembly.rs:228-244`);
  `omitted_refs` (`graph_sources.rs:212-236`, lifecycle references to
  declared quests absent from the graph); `lute scenario`'s JSON `prereq`
  (`scenario_fmt.rs:89-100`: the formula text for `Valid`, the existing
  marker `"(malformed — E-CONN-PROFILE)"` for `Malformed`, `null` only for
  `Absent` — beside any accept anchor); `lute scenario reach`'s structure and referenced list
  (`cmd_scenario/reach.rs:136-159`, `:198-212`; `PrereqState::referenced`,
  `graph_nodes.rs:487-497`). Activation readers (they answer what is
  guaranteed or routable): reachability (`reachability.rs:196`, `:258-259`),
  the entry envelope (`envelope.rs:356-371`) and must-facts
  (`fact_must.rs:216`) — they keep `prereq`, so an anchored quest's
  `follows` never becomes an entry guarantee or a route. For an anchored
  quest that declares `follows`, `reach` prints the declaration first,
  marked as metadata — `` follows: completed("intro") (declared ordering; not an activation route) ``,
  or for a malformed one the existing reach marker
  `` follows: (malformed — E-CONN-PROFILE) (declared ordering; not an activation route) `` —
  then the anchor lines; the referenced list is the union of the formula's
  atoms and the anchor sources. A quest without `follows` and every quest
  that is not anchored print exactly as in 0.52.

An accept-driven quest **without** `accept="external"` that declares
`follows`: its routes are its in-script sources only; its `follows` stays
ordering metadata (edges, `prereqEdges`) and is no route. (No corpus quest
has this shape: every corpus quest with `follows` has a `start`.)

**Reachability** (`reachability.rs:245-290`): the accept anchor is the OR

### 7.2 Reach over undrawn accept edges

`check_reachability` evaluates nodes once in topological order and repeats
only when a graph back edge or an undrawn **raise** source exists
(`reachability.rs:161-189`, `has_undrawn_raise_source` `:225-243`). An
accept edge that would close a cycle is not drawn, so its source can be
evaluated after the quest it anchors: with reward-accepting quests `a` and
`b` where only `a` is external, the graph may draw `b → a` and omit

kind `Accept` or `Raises` (and every undrawn atom of a host `follows`): the

update monotone, so it terminates). Both placements of the host in a
mutual-accept cycle reach both quests; `constraints` gets the same verdicts.

### 7.3 In-script accept deadlocks are start cycles

`gates()` (`start_cycles.rs:16-22`) also counts an `Accept` anchor as gating.
In the 0.49.0 §6.1 fixed point, an accept anchor can start when one of its
in-script sources can start, or when it has a host route — always with
`HostGate::Always`, and when the `follows` formula's atoms can start with
`HostGate::Follows`. So a cycle of `start` and in-script accept anchors that
no source outside enters, and no host route opens, is
**`E-QUEST-START-CYCLE`** (error, project-wide), one per strongly connected
set, at the least quest's `start` — or at its `id` attribute when the quest
has no `start` (an accept-driven quest). The path names each edge kind:

> `` quest start cycle: quest(intro) -[start]-> quest(letter) -[accept]-> quest(intro) — each waits for the next (a `start` for its condition, an accept for the `::accept` or reward that grants it) and no source outside the cycle starts any of them; start one of them from something outside the cycle, or let the host grant one with `accept="external"` ``

`reach` for such a quest is the 0.49 start-cycle `Unknown` with this path.
The graph prints the deadlocked quests on the "part of a start cycle" line,
as for a `start` cycle. Rationale: decision note, departures items 6–8.

### 7.4 A host-gated grant is written `accept="external" follows="…"`

`accept="external"` with `start` stays refused (decision note, "Decisions
changed" item 2). A quest the host grants once a condition holds is written

- `E-QUEST-START-SELF` (`match_check/records.rs:398`): after "… is written
  `accept="external"` without a `start`" add "; if the host grants it only

  after "only an accept-driven quest (no `start`) can be accepted" add

## 8. A marker that opens on a literal brace (#229)

In every `{{…}}` grammar (line text and translations, and every
label-grammar value: choice and hub labels, prompts, directive `text`
attributes), a marker whose expression text begins with `{` opened at a
literal brace. The checker reports **`E-INTERP-BRACE`** there instead of
`E-CEL-PROFILE`: in `interp_grammar_diag` (`check/interp.rs:210-265`), an
expression `raw` that starts with `{` gets code `E-INTERP-BRACE` and layer
`Content`.

**The intended marker** strips the **whole** leading run: `raw` =
`{`×n + `expr`, n ≥ 1, `expr` not starting with `{`; the intended marker
is `{{expr}}` preceded by n literal braces. (`{{{run.a}}`: n = 1,
`expr` = `run.a`; `{{{{run.a}}`: n = 2.)

**The message** names the two spellings for n literal braces, built by one
function `interp_brace_message(n, marker)` in `lute-syntax`
(`parser/line.rs:413-420` today takes only the marker; the #139 parser site
calls it with its own odd run length, so both sites share it):

1. a character between the braces and the marker: the n braces spelled as
   literals, then a space, then the marker — `{ {{run.a}}` for n = 1,
   `\{{ {{run.a}}` for n = 2 (`\{{` is a literal `{{` in line text,
   0.47.1 §3, and in the label grammar, 0.52.0 §3.2), and in general
   `\{{` for each pair plus `{` for an odd remainder;
2. the braces from a string state path: `{{run.lbrace}}` repeated n times
   before the marker, with `run.lbrace` declared
   `{ type: string, default: "{" }`.

> `` a literal `{` directly before `{{run.a}}` cannot be told apart from the marker in compiled text (lute 0.47.1 §3): put a character between them (`{ {{run.a}}`), or show the brace from a string state path (`{{run.lbrace}}{{run.a}}`, with `run.lbrace` declared `{ type: string, default: "{" }`) ``

For n = 2 the message says "literal `{{`" and shows `\{{ {{run.a}}` and
`{{run.lbrace}}{{run.lbrace}}{{run.a}}`. One diagnostic per marker: the
`E-CEL-PROFILE` it replaces is not emitted. No expression starting with `{`
was ever valid, so only the code and text of an existing error change.
`E-INTERP-BRACE`'s registry summary names the second site.

**As implemented (B).** The rule reads the marker's exact interior
(`Interp::source`), not the trimmed referent `raw`: a space after the `{{`
(`{{ {run.a}}`) is a marker the author opened, so it stays `E-CEL-PROFILE`,
and the marker named keeps everything after the run as written, spacing
and a format hint included (`{{{{{ run.a:ordinal }}` names
`{{ run.a:ordinal }}`, n = 3). A run with nothing after it (`{{{}}`) meant
no marker and stays `E-CEL-PROFILE`. The check is

checker's two interpolation walks (`check_interps`: scene lines, choice and

diagnostic, not two. The #139 site now names its whole run: its own repro

### 8.1 A translation shows its source's markers (#241)

Found while implementing B (Main's decision, 2026-10-28: folded into 0.53,
its own commit). A translation entered through a locale bundle was merged
verbatim whatever its `{{…}}` markers: `compile --locale-bundle` accepted
`S {{{run.a}} E` and `S {{run.zzz + 1}} E` for the source `S {{run.a}} E`
(exit 0, `texts.ko` as written), and the runtime, which renders a
translation's marker with the value its source gave the marker of the same
trimmed interior (`substitute_by_marker`), shows any other marker verbatim.
A silently wrong output; the 0.37 modifier parity (`E-L10N-MODIFIERS`) is the
precedent.

**Rule.** Every translated text — a line's (its plain derivation), an
option label's, a prompt's, a directive `text` attribute's — shows its
source's markers:

1. Each marker parses under the source rules (lute 0.47.1 §3): a `{{` has
   its `}}` (else `E-INTERP-UNTERMINATED: …`), and no marker opens on a
   literal brace run (else the §8 `E-INTERP-BRACE` message, n-specific).
   A translated text is read by exactly the grammar of its source surface:
   in an option or hub label, a prompt or a directive `text` attribute (the
   label grammar) a `{{` with no `}}` is literal text, as it is in such a
   source, so only a line refuses it, and only real markers are compared
   in part 2 (`loc import` reads a row's grammar from its `kind`; a CSV
   without `kind` reads as the label grammar). A line translation's
   inline-markup errors (the #139 run included) stay `E-L10N-MODIFIERS`,
   judged first.
2. The markers are the source text's: each source marker as often as the
   source shows it, in any order, compared by the trimmed interior (the
   runtime's identity: spacing is free, a format hint is part of the
   marker). The message lists what is missing and what is extra.

Any other translation is **`E-L10N-MARKERS`** (new, error, layer
`Content`, class `SourceError`) and is not merged, which fails the build as
`E-L10N-MODIFIERS` does (`compile <file> --locale-bundle` and `compile

> `` `ko` text for `s.narrator_0010` is not merged: its markers differ from the source's (missing `{{run.a}}`; extra `{{run.zzz}}`): a translation shows each `{{…}}` marker of its source as often as the source does, in any order ``

> `` `ko` text for `s.narrator_0010` is not merged: its markers do not parse (E-INTERP-BRACE: a literal `{` directly before `{{run.a}}` cannot be told apart from …) ``

**Where translations enter.** `compile --locale-bundle` (single file and

## 9. Bounded loops across sections (#231)

### 9.1 What a section is

A `##` section is presentation and identity metadata: the heading, the
optional `{#id}` in the artifact's descriptive `sections` table, and the
first segment of the build-local `position`. It is not a runtime range, a
resume point, a host entry or a jump target (decision note, "#231: what a
section is at runtime"). The runtime runs a scene's sections as one range.

### 9.2 Rule

The top-level sections of a document are **one loop scope**, as they are one
range (0.52.0 §5.1, `BodyRange::TopLevel`). A bounded `::jump{to max}` may
loop back to a label in an earlier section; the region is every node from
the head label to the jump, across the sections between. Every other rule
applies unchanged: `E-JUMP-INTO-LOOP` (an entry other than the head),
`E-JUMP-LOOP-CROSS`, nesting, `E-JUMP-INTO-BODY`, and `E-JUMP-LOOP-SCOPE` for
a loop that leaves a hub option, `<return>`, `<on>`, `<objective>`, entry or
beat body. `::end` inside a region stays legal, as within one section today.

In `next_labels.rs`, the scope chain treats `BodyKind::Section` bodies as one
top-level body for the loop rule, so `E-JUMP-LOOP-SCOPE` never names a
section; `leave_message`'s `Section` arm (`:243`) is removed and the
registry summary (`registry.rs:714-718`) drops "or a section". `LoopTable`
regions (`first..=last` positions) need no change.

### 9.3 The flow walks

`loop_walk::region_len` (`loop_walk.rs:200-208`) becomes `loop_walk::region`,
returning a `Region<'d>`: the node slices from the head through the **last**
node that holds a back edge to the head, searched across every slice the
region may cover — the rest of the head's body and, at the top level of a
document, the bodies of **all** following sections. A back edge in the
head's own section does not stop the search: several bounded jumps may
loop to one head (equal-head regions pass the crossing check,
`next_labels.rs:835-853`; the runtime keeps every such jump under the head,
`machine/mod.rs:449-453`), and when an earlier one's bound is exhausted,
execution reaches the later sections. The region ends at the section and
node of the last back edge (its prefix through that node). Each walk visits
the parts in order where it visited the one slice.

**The checker's walks:** `defassign.rs:618-658` (`label`, `head`),
`fact_must.rs:1057`, `inject.rs:647` (the checker's stage fold),
`cast/presence/walk.rs:319` (`kill_writes`).

**The compiler's own stage walk.** The compiler does not read a checker
head-state table: it builds its own `StageFlow` with
`WalkKind::StageCompile` (`lute-compile/src/stage.rs:60-82`), walks each
section separately (`lute-compile/src/lib.rs:561-565`, `walk_seq` per
`doc.sections` entry) and hands only the current section's remainder to
`cx.stage.label` (`bind_label`, `stage.rs:234-243`). Its head state decides
injections such as `PosReset` (`inject.rs:1338-1353`), so a blind compiler
walk changes **emitted commands**. 0.53 changes it in the same way: the
per-section loop in `lib.rs` gives the walk the following sections, and
`bind_label` passes `region`'s parts to `StageFlow::label`.

**Top-level hand-off** (every walk above): while a walk walks
`doc.sections[i].body` at depth 0 it holds `&doc.sections[i + 1..]` (in the
compiler, the remaining shots of the loop at `lib.rs:561`); inside nested
bodies the following sections are empty. Each walk's top-level iteration
is changed: `fact_must.rs:775-777`, `cast/presence/mod.rs:170-176`, the
scene branch of the checker's walk (`check/pipeline.rs:443-447`), the
checker's stage fold, `defassign`'s, and the compiler's `lib.rs:561-565`.

- The final pass is the ordinary walk, which already continues across
  sections, so diagnostics are reported once.
- `LoopWalkStats` counts the probe nodes of every part, for both
  `WalkKind::Stage` and `WalkKind::StageCompile`.
  `lute-bench flow-loops` gains a `sections` shape (a loop whose region spans
  k sections, and a variant with a second back edge in the head's section),
  with work asserted linear like the 0.51 region axis.

The runtime needs no change: positions are ordered across sections and its
`loop_table` works on record indices.

### 9.4 `E-JUMP-INTO-LOOP`: the one-option hint

When the entering forward jump is the last node of a `<choice>` body (a
`<branch>` option) and no other jump targets its label, the message adds:

> `` — `blockA` is reached only from option `a` of `<branch id="pick">`: move the block into that option's body ``

The suggested move is verified to check clean in the test.
