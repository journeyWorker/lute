# Lute Scenario DSL — 0.27.0: One runtime, seasons, templates

- **Version:** 0.27.0
- **Date:** 2026-09-27
- **Scope:** a large minor. It unifies the two document runtimes (the play
  runner and the trace walker), closes every round-5 finding
  (`lute-dogfood/round5/TRIAGE.md`: T1-1…T1-11, T2-1…T2-13, T3-1…T3-25,
  D-1…D-15), and adds the model areas round 5 asked for: occasion-bound
  members, engine gates and terminal states, finite clocks, seasons and quest
  rearm, beat templates, labels, plurals and linear chapters.
- **IR:** additive — occasion `payload`, `raisedWhen`, project `terminal`,
  clock `last`, `BeatIr.once` `week` / `season:<name>`, `QuestCmd.rearm`,
  season declarations, entity-kind `labels`, directive `effects.asserts`,
  placeholder format `plural`.

## 1. One runtime (T1-3, T1-5, T1-7, T1-9, T1-11)

`lute play` (crates/lute-cli runner.rs/play.rs) and `lute trace` / `lute
test` (crates/lute-trace walk.rs) are two implementations of the same
document semantics; every round since 0.23 found them disagreeing.

- Document execution (lines, guards, `::set` / `::assert` / `::retract`,
  directive effects, bridges, derivation and exclusivity, interpolation and
  formats, `occasion.target` binding, `once` spending, quest settling and
  lifecycle handlers) lives in **one walker** parameterized by a driver:
  - the *play* driver picks one choice per decision, answers bridges from the
    script, and knows every value;
  - the *trace* driver enumerates or mocks decisions, answers from mocks, and
    may hold unknown values (tri-state), reporting what an unknown blocks.
- Where the drivers genuinely differ (decision policy, unknown handling,
  output), the difference is a driver hook, never a second copy of the
  semantics.
- A **differential test** runs every scene of `docs/examples`, the
  conformance corpus and the test fixtures through both drivers with fully
  concrete inputs and requires identical transcript, state, facts and quest
  states. It runs in `cargo test`.
- Output formats (play transcript, trace report, JSON) are unchanged unless a
  finding fixes them.

## 2. The checker says no (T1-1, T1-2, T1-4, T1-5a, T1-6, T1-8, T1-10, T3-15)

- `::set{ path <op> expr }` without an assignment operator is `E-SET-SHAPE`
  naming `=` / `+=` / `-=`.
- A state path typed `{ domain: K }` (enum or entity kind) is checked against
  K's members everywhere a literal meets it (`::set`, `==`/`!=`/`in`, `into=`
  values, `<when is>`), and `<match>` over it is exhaustive over K.
- A directive `effects.writes` value shape is validated at plugin load
  (`{ fromAttr }` is legal where documented and applied; an unknown shape is
  `E-PLUGIN-PARSE`).
- `<match on="@def">` whose def is a fact query is `E-MATCH-RELATION-SUBJECT`,
  as the inline form is.
- `per: K` covers members added through `subsetOf:` children.
- `lute scenario knowledge` reasons with the checker's rule instantiation.
- A param `default: "@def"` is judged for definite assignment at each `::use`.
- An entity kind rejects unknown keys (`E-ENTITY-KIND-SHAPE`, did-you-mean).

## 3. Members bound by occasions (T2-1, T2-2, T2-10)

- Inside a `target="kind:K"` beat, `occasion.target` is a typed ground term:
  it may appear as a fact-query argument (`holds(owned(occasion.target))`)
  and as a `per:` family index (`user.bond[occasion.target]`). The checker
  instantiates the guard per member; the runtime substitutes the raised
  member.
- `for="kind:K"` on a beat of an untargeted `select: sequence` occasion
  presents the beat once per member whose instantiated `when` holds, in
  member order, binding `occasion.target`.
- A rule variable bound by a positive atom may be compared with a
  domain-typed state path (`cel("run.stalker == S")`); it is instantiated per
  member like `per:` indexing.
- An occasion MAY declare a typed payload, `summon: { target: …, payload: {
  copies: number } }`, read as `occasion.payload.copies`; play steps give it
  (`payload: { copies: 2 }`), trace/test mock it.

## 4. The engine seam (T2-3, T2-4, T2-5, T2-11)

- **Gates:** an occasion MAY declare `raisedWhen: "<condition>"` (may read
  `occasion.target`). The checker conjoins it into every beat of that
  occasion (reachability, `W-RELATION-UNREAD` counts it as a read; a beat it
  makes unreachable ties with nothing), `lute beats` marks targets whose gate
  can never hold, and `lute play` refuses a step raising the occasion while
  the gate is false (`E-OCCASION-GATE`); a clock raise whose gate is false
  is not made, and the step notes it.
- **Terminal state:** a schema MAY declare `terminal: "<condition>"` (several
  schemas' conditions are joined by `||`). The manifest does not: `defaults.uses`
  already makes one schema project-wide, so a second declaration site would
  only be a second place to look. Once it holds, no occasion is raised: play
  ends with `end: terminal` (`--json`: `"end": "terminal"`), the checker
  treats beats as unreachable under it, and an `occasion:` or `advance:` step
  after it is a usage error (`E-OCCASION-GATE`) until a `newRun`.
- **Finite clock:** `clock: { last: { day: 1, slot: h05 } }` (or `days: N`).
  The clock raises the last `dayEnd` and stops; a later `advance:` is a usage
  error; `when`s requiring a later position are unreachable.
- **Directive facts:** a directive MAY declare `effects: { asserts:
  ["holding(@item)"], retracts: [...] }`; play, trace and test apply them and
  `lute scenario --facts` draws them. A lore entry may use a directive whose
  only effects are declared writes/asserts (first-read rule applies). An
  `occasion:` step may carry `engine:` writes (applied before the raise).
  `by: { fromAttr }` is accepted in `effects.writes`.

## 5. Cadence: weeks, seasons, rearm (T2-6, T2-7, T3-25)

- `once: week` is legal when the clock declares `week:`; a beat is spendable
  again when `clock.weekday` returns to `week.first`.
- **Quest rearm:** `<quest … rearm="<condition>">` returns the quest to
  `unset` (objectives cleared, `failedBy` cleared) when the condition goes
  from false to true; a rearmed quest can be accepted/started again.
- **Seasons:** a schema MAY declare
  `seasons: { harvest: { live: "@harvestLive" } }`. Each season is a state
  tier: paths `season.<name>.<field>` (declared under `state:` like others),
  `once: season:<name>`, quests with `tier="season:<name>"`. When `live` goes
  false→true, the season's state resets to defaults, its `once` spends and
  season-tier quests reset, and `prev.season.<name>.*` holds the last window's
  final values. Seasons overlap freely. The artifact carries the season
  declarations so the engine resets from the same source.
- **Spent by result:** a beat MAY declare `spentBy: "<condition>"` instead of
  `once`: it stays eligible until the condition holds (a retryable puzzle).

## 6. Beat templates (T2-9)

A component MAY declare a beat header template in its frontmatter:

```yaml
component: bondStory
params: { hero: { entity: hero }, rank: { enum: [r1, r2, r3] }, prev: { type: string, default: "" } }
beat:
  on: bondStory
  target: "hero.@hero"
  once: user
  when: "holds(bondRank(@hero, @rank))"
  after: "@prev"        # omitted when empty
```

`<beat use="bondStory" id="ariaR2" hero="aria" rank="r2" prev="bonds.aria.ariaR1">body</beat>`
in a bundle document derives the beat's `on`/`target`/`once`/`when`/`after`/
`priority` from the template; attributes written on the `<beat>` override the
template. The template's body (if any) runs first, then the use's body;
`::body` in the template body places the use's body explicitly. Params are
checked like `::use` args. A template with no body and a body-less use make a
one-line beat (`<beat use="trainer" id="r3Joey" who="joey"/>`).

## 7. Text

- Entity kinds MAY declare `labels: { member: "display text" }`; `{{…}}` of
  a kind-typed value (`occasion.target`, `{ domain: K }` paths, component args)
  renders the label; a cast `name:` wins for cast ids (T2-8).
- `{{n:plural(lantern|lanterns)}}` carries the forms in the IR placeholder;
  the engine localizes; play/trace render English (T2-12).

## 8. Linear chapters (T2-13, D-1)

`lute.project.yaml` MAY declare
`sequence: { occasion: chapter, scenes: [prologue, counter, kitchen] }`
deriving `on: chapter`, `after: visited(previous)` and descending priority
for the listed scenes (explicit keys on a scene still win). The novice guide
teaches it first.

## 12. Decisions

| # | Decision | Rationale |
| --- | --- | --- |
| **D-A** | one walker with drivers, not shared helpers | every divergence came from a second copy of a rule; helpers leave the copies' glue |
| **D-B** | differential test in `cargo test` | the next divergence fails CI, not a dogfood round |
| **D-C** | `occasion.target` is instantiated per member | the checker already draws per-member ladders; the runtime substitutes one value |
| **D-D** | seasons are named tiers declared by a live condition | one source for the dates; overlap and reruns fall out; the engine resets from the artifact |
| **D-E** | beat templates are components with a `beat:` header | one reuse mechanism; params, checks and `@@who` already exist |
| **D-F** | `raisedWhen`/`terminal` are declarations the engine honours | Lute declares when; the engine executes — the checker can then reason about gates |
