# Lute Scenario DSL — 0.14.0: Subquests

- **Version:** 0.14.0
- **Status:** Draft
- **Date:** 2026-08-31
- **Scope:** the language axis gains ONE new attribute on an existing
  element — `<objective quest="childId"/>` — making a child quest's
  completion a parent objective, plus the derived failure semantics in both
  directions and the activation refinement the reference implies. Four new
  diagnostic codes (`E-OBJECTIVE-QUEST-DONE`, `E-QUEST-REF-UNKNOWN`,
  `E-QUEST-MULTI-PARENT`, `E-QUEST-TREE-CYCLE`) and one propagation rule
  onto the existing `E-OBJECTIVE-UNSATISFIABLE`. No grammar production
  changes — `quest=` is an attribute on the existing `<objective>` form, and
  a tag with all its attributes still sits on one physical line.
- **IR:** additive-only. `ObjectiveEntry` gains `quest` (the referenced
  child id), omitted when unauthored, so non-subquest artifacts are
  byte-identical; the objective's `done` and the parent's `fail` carry
  compiler-synthesized predicates (§3). `capabilityVersion` is unaffected:
  no `lute.core` export changes.
- **Design record:**
  [`docs/superpowers/specs/2026-08-31-lute-subquest-design.md`](../../superpowers/specs/2026-08-31-lute-subquest-design.md).

## 1. Motivation

Quest hierarchies were expressible before this release only by hand: a
parent objective reading `quest.<child>.state == 'complete'`, a child
gating itself with `after="active('parent')"`, and failure propagation
copy-pasted as CEL on every member. Nothing *named* the relationship, so
the checker could not catch an orphaned or doubly-claimed child, an engine
could not derive a journal tree, and the soft-lock where a failed required
child leaves its parent forever `active` was silent.

`0.14.0` names the edge once — on the parent, at the objective that owns
it — and derives everything else.

## 2. `<objective quest=…>` — the subquest reference

`quest=` names a child quest by id. It is **mutually exclusive** with a
non-empty `done=` (`E-OBJECTIVE-QUEST-DONE`); exactly one of the two
carries an objective's completion source. Every other objective attribute
admits alongside it — `when=` still gates visibility only, `optional`
still excludes the objective from derived completion, `title=` and a body
behave as before (the body plays exactly once, when the objective first
becomes `done`, i.e. when the child completes).

The child is an ordinary `<quest>`, in the same document or another. Ids
stay flat and project-unique; the tree is derived from references, never
from id structure.

The project-wide reference shape is a **tree, not a DAG**: at most one
parent per quest (`E-QUEST-MULTI-PARENT`), no cycles
(`E-QUEST-TREE-CYCLE`; a self-reference is a length-1 cycle, caught at
`check` when parent and child share a document), depth unbounded. An id no
project quest defines is `E-QUEST-REF-UNKNOWN` — same-document references
resolve at `check`, cross-document resolution belongs to `check-project`,
matching how `after` targets already split.

## 3. Derived semantics

Synthesis happens where the compiling document has the information; an
engine rule covers only what it cannot (a child does not know its parent).

- **Completion (synthesized).** The objective's `done` becomes
  `quest.<child>.state == 'complete'`. Derived parent completion ("all
  non-`optional` objectives `done`") is unchanged.
- **Upward failure (synthesized).** The parent's effective `fail` becomes
  the disjunction of the authored predicate (if any, parenthesized) and one
  `quest.<c>.state == 'failed'` test per **required** child, document
  order. An `optional` child's failure contributes nothing. `fail` before
  derived completion (§6.3 precedence) is unchanged.
- **Downward failure (engine rule).** When a quest transitions to a
  terminal state (`failed` or `complete`), every child still `active`
  transitions to `failed` and fires its own `questFailed` handlers,
  recursively. A required child cannot be `active` when its parent
  completes, so the `complete` arm only ever fails running optionals.
  Recorded normatively in
  [`quest-lifecycle.md`](../../runtime/quest-lifecycle.md).
- **Activation (engine rule).** A referenced child with no `start`
  activates when its parent activates — replacing the walk-start /
  accept-driven default for referenced quests only. A referenced child's
  `start` predicate is evaluated only while its parent is `active`. An
  unreferenced quest keeps `0.13.0` semantics exactly.

A required subquest objective whose child is `E-QUEST-UNREACHABLE`
propagates `E-OBJECTIVE-UNSATISFIABLE` onto the referencing objective
(project-level).

## 4. What this does NOT change

- The lifecycle enum is untouched: `unset` → `active` → `complete` |
  `failed`. A fifth `abandoned` state was considered and rejected — the
  downward cascade reuses `failed` (design record §2.3).
- `quest.<id>.state` / `quest.<id>.activatedAt` reservation, monotonic
  objective completion, `<on>` semantics, and hub/timeline exclusion from
  quest documents are byte-for-byte `0.13.0`.
- No migration: `0.13.0` documents are valid `0.14.0` documents unchanged
  (the new attribute is optional, and no existing attribute changed
  meaning). A document that never authors `quest=` compiles to a
  byte-identical artifact.
