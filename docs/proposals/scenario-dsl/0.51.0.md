# Lute 0.51.0 — flow and text

This is the normative 0.51.0 contract. The words **MUST**, **MUST NOT**,
**SHOULD** and **MAY** have their RFC 2119 meanings.

The inputs are the dogfood issues #159, #165, #170, #172 (the `pair` half) and
#176 (the authoring half, decided but not developed), each with a 0.48.1 reproduction from a large real
port. The options and recommendations are in
[`docs/design/0.50-extensibility-options.md`](../../design/0.50-extensibility-options.md)
(§3, §6, §7, §8, §9, §10, §12), and the decisions are in
[`2026-10-26-lute-0.51-decisions.md`](../../superpowers/notes/2026-10-26-lute-0.51-decisions.md).
Where this spec departs from a recommendation, the decision note gives the
evidence, and Appendix B lists every decision.

The release adds one kind of control flow that every analysis can see (a
bounded backward jump), one host contract the scenario graph can see (a
declared occasion raise), one localized attribute type and one lint target.
There is no new keyword and no new element. The new surface is one core
directive attribute (`::jump{max}`), two plugin manifest keys
(`effects.raises` on directives and reward kinds; `raisedBy` on occasions),
one attribute type (`text`) and one lint target (`pair`). #176 is not developed
(§7). The release is a clean cutover (ADR D6).

The base is `main` at **v0.50.0** (`9ccd2fa9`). Code anchors are cited at
`9ccd2fa9`; Appendix A lists them. The spec was first drafted before 0.50.0 was
implemented; the decision note's "Reconciled with 0.50.0" section lists every
change made when it was checked against the released code.

Implementation plan:
[`2026-10-26-lute-0.51.0-flow-and-text.md`](../../superpowers/plans/2026-10-26-lute-0.51.0-flow-and-text.md).

## 1. Scope and version contract

This is a minor release. Every public version axis is `0.51.0`: toolchain,
`luteVersion` (`LUTE_LANG_VERSION`), `irVersion`, `eventVersion`,
`snapshotVersion`, and the seven npm packages. The contract schemas move to the
`0.51` line (`schemas/lute-{ir,events,snapshot,player-bindings}-0.51.schema.json`).
`bindingsVersion` and the player save/profile format become `"0.51"`. The
player save also changes shape: it carries the pending declared-raise queue
(§4.6). The Rust runtime `Snapshot` keeps its shape. This follows the 0.50.0
§1 precedent.

| Axis | 0.51.0 contract |

## 2. Shared rules

The 0.50.0 §2 rules apply unchanged: a regression test that fails on the base
for every behaviour change (the issue reproductions first); one diagnostic shape
(registered in `crates/lute-cli/src/codes/registry.rs` and
`crates/lute-check/src/evidence.rs`, blessed with `LUTE_BLESS_DIAGNOSTICS=1`,
website EN + KO); **no hint recommends a spelling the checker rejects**; no
silent drop; byte stability for projects without the new keys (except §13);
documentation in the same change; and `docs/design/rust-coding-rules.md` for new
Rust code. In particular:

- **Newtypes and enums, not strings:** `JumpMax` (a `u8` in 1..=99),
  `LoopRegion`, `LoopTable`, `RaiseDecl`, `RaiseTarget`, `RaisedBy`,
  `LocalizedText`, `TextAttr`, `PairSpec`, `PairScope`, `PairFault`.
- **No HIR, no Fold, no synthesized nodes (rules §7).** A loop is a table
  computed from the AST once per document (§3.2), and every walk consults it. A
  raise is a table resolved once per project pass (D14), read by each consumer
  beside its existing walk. Like 0.50's `GrantTable` (`crates/lute-check/src/reward_effects.rs:347-380`),
  it resolves each document's rewards against that document's own
  `ProjectDoc::reward_kinds`.
- **One join.** Every flow walk joins at a label through one helper per walk
  kind (§3.4), never through a second ad-hoc rule.
- **Counted work.** The loop-head fixed point (§3.4) and the `pair` lint (§6.2)
  count their work the way 0.50's node walk does (`NodeWalkStats::work`,
  `crates/lute-lint/src/nodes.rs:38-91`): deterministic counters, asserted in
  CI on generated inputs, with growth ratios recorded in the plan log.
- **Project diagnostic levels (0.50.0 §6).** The new warnings
  (`W-OCCASION-NEVER-RAISED`, and the new sites of `W-LINE-CODE-UNTAGGED`,
  `W-STAGE-ABSENT`) can be re-levelled in `lute.project.yaml` `diagnostics:`
  like every `W-*` code (`codes::tests::every_registry_warning_can_be_levelled`).
  Simulating commands (`test`, `play`, `calendar`) apply no project levels
  (0.50 Option A).

## 3. Bounded backward jump (#159)

### 3.1 Syntax and the `max` attribute

`::jump` may target an **earlier** `::label` when it carries `max`, the number
of times the jump may be taken. After `max` takes, the jump is not taken and
control falls through to the next node.

```lute
::label{name="attempt"}
::minigame{level="2"}                     # a blocking bridge call that writes run.won
<match subject="run.won">
  <when is="false">
    @mira: Again!
    ::jump{to="attempt" max="2"}
  </when>
</match>
@theo: That's enough for today.
```

- `lute.core`'s `jump` declaration
  (`crates/lute-manifest/assets/lute.core/directives/staging.yaml:83-87`) gains
  `{ name: max, required: false, type: int }`. It is the only declaration site.
  The LSP, `lute context` and the attribute checker read it from there. This
  changes `capabilitySnapshot` for every artifact once (§13 class 4).
- **`max` is a literal integer in 1..=99.** A non-integer value is the existing
  `E-ATTR-TYPE` (the declared `int`). An `@ref` value, `0`, a negative value or
  a value above 99 is **`E-JUMP-MAX`** (new): `` `max` on `::jump` is the most
  times it may be taken: a literal integer from 1 to 99 (a loop bound is static,
  so it cannot be `@ref`) ``.
- **A backward jump without `max`** stays `E-JUMP-BACKWARD`. The message gains
  the new spelling: `` … `::jump` only jumps forward unless it carries `max`:
  `::jump{to="again" max="3"}` repeats at most 3 times; to offer choices again,
  use a `<hub>` (it asks until an `exit` choice is taken) ``.
- **`max` on a forward jump** is `E-JUMP-MAX` too: `` `max` bounds a backward
  jump; `::jump{to="later"}` already goes forward, so `max` means nothing here —
  remove it ``.
- `when=` and `max` combine: the jump is taken while `when` holds and takes
  remain. A guarded jump keeps its 0.12.0 lowering (a one-arm `<match>` around
  the `jump`, `crates/lute-compile/src/normalize.rs:582-605`).
- `max` is not a stamp carrier: `::jump` stays in `UNSTAMPED_DIRECTIVES`
  (`crates/lute-manifest/src/core.rs:79`), so a 0.50 `stampAttrs` entry with
  `on: [jump]` stays `E-PLUGIN-STAMP-SURFACE` (`SurfaceError::Unstamped`,
  `stamps.rs:51-53`). `StampSurface::own_attrs` (`stamps.rs:145-152`) reads the
  jump's declared attributes, so it lists `max` with no code change.

### 3.2 Loop regions and structural rules

Positions are the document-order counter of the label pass
(`crates/lute-check/src/next_labels.rs`, `walk` `:130-180`), which agrees
with compiled address order. The counter is depth-first and ticks at every
node: labels and jumps when recorded, every line, ordinary directive, `::set`,
`::assert`, `::retract` and `<timeline>` (`:142-152`), and every `<branch>`,
`<hub>`, `<match>`, `<on>` and `<objective>` before its bodies are walked
(`:153-180`). (The module comment, `:9-17`, still says only label and jump
sites tick; it is stale and S1 corrects it.) For a bounded jump **J** at
position *j* that targets label **L** at position *l* < *j*, the **region** of
J is every node at a position in [*l*, *j*]: L, J and every node that order
visits between them. L is the region's **head**.

The label pass builds a `LoopTable` once per document: every bounded jump with
its head, its region and its enclosing regions. It is computed beside the
existing label table in `check_next_labels` (`next_labels.rs:194`) and handed to
the flow walks the way `next_targets` is (`:322`). The rules:

| Rule | Code | Message shape |
|---|---|---|
| **Scope.** L is in J's own body or in a body that encloses J, and every body between them is a `<choice>` body of a `<branch>` or a `<match>` arm body. The chain may not leave a hub option body, a hub `<return>` body, an `<on>` or `<objective>` body, a quest, an entry, a beat or a section. **The region contains no `<on>` or `<objective>`**: a quest body's top level admits `::label`/`::jump` beside them (`crates/lute-check/src/admission.rs:22-24`), but each is a separate runtime range and carries 0.50's grant points (§3.4). | **`E-JUMP-LOOP-SCOPE`** (new) | `` `::jump{to="attempt" max=…}` loops back to a label outside the `<hub>` option it is in; a loop stays inside one option body — put `::label{name="attempt"}` inside it, or use the hub itself to repeat `` (the boundary is named: hub option, hub `<return>`, `<on>`, `<objective>`, quest, entry, beat, or section `## …`; for a region that contains an `<on>`/`<objective>`: `` … loops back over `<objective id="o">`, which runs on its own; put the loop inside the objective's body or before it ``) |
| **No entry into a region.** A forward jump whose source is outside a region and whose label is strictly inside it (after its head). | **`E-JUMP-INTO-LOOP`** (new) | `` `::jump{to="mid"}` enters the loop of `::jump{to="attempt" max=…}` (line N) after its head `attempt`; a loop is entered only at its head — jump to `attempt` instead `` |
| **Nest, never cross.** Two regions either nest or are disjoint. Regions [*l₁*, *j₁*] and [*l₂*, *j₂*] cross when *l₁* < *l₂* ≤ *j₁* < *j₂*. Regions with the same head nest. | **`E-JUMP-LOOP-CROSS`** (new), at the later jump | `` the loop `attempt` … (line N) and the loop `retry` … (line M) overlap without nesting; close the inner loop before the outer one jumps back `` |

- Two or more bounded jumps MAY share a head. Each has its own counter and its
  own region.
- A jump from inside a region to a label after the region (an exit) and a
  forward jump from before the region to the head are legal.
- A bounded jump inside a component body is checked in the component's own
  document. After expansion every instance has its own command positions and so
  its own counters (§3.7).
- These rules make every loop reducible and well-nested, so each flow walk
  can treat a head as one join point (§3.4).

### 3.3 Meaning

- **Counter.** Each bounded jump has a counter, local to one walk (one
  presentation; one quest handler or objective segment; one entry or beat
  body), starting at 0.
- **Take.** When control reaches J (and its `when` holds, if any): if the
  counter is below `max`, it is incremented and control moves to the head;
  otherwise control falls through to the node after J.
- **Reset.** J's counter returns to 0 whenever control arrives at its head from
  **outside J's region**: by falling through into the label, by a forward
  jump, or by a bounded jump that is not inside J's region. A take of J itself,
  or of another bounded jump inside J's region, does not reset it.
- **Termination.** Between two consecutive bounded takes, control moves only
  forward, so it is bounded by the walk's length. A region's counter is reset
  only when its head is entered from outside, so by induction over the nesting
  (innermost first) a region of nesting depth *d* is traversed at most
  Π(max_k + 1) times, the product over its enclosing jumps. Every walk ends
  without player cooperation. The landing page's "total" claim stands.
- A jump with `max` that is never reached, or a `when` that never holds, is not
  an error (the existing `E-ARM-DEAD` rule applies to a provably false `when`).

### 3.4 Flow analyses: one label join, a fixed point at each head

**Rule.** Every analysis that threads a state through a body in document order
MUST compute the state at a `::label` as the **join** of the fall-through state
and the state of every jump that reaches the label, and MUST compute the state
at a loop head as the fixed point reached by starting from the entry state and
joining the back-edge states of the region, walked from the head, until the
head is stable. For a Must lattice (meet as join) this is the greatest fixed
point below the entry state, as for `fact_must`'s hub
(`crates/lute-check/src/fact_must.rs:1363-1392`, convergence test `same`,
`:318`). Each walk:

- treats a jump by its kind: an **unguarded jump without `max`** sends its state
  to the label and leaves no fall-through (bottom, the identity of the join, as
  `fact_must` already does, `:1232-1235`); a **guarded** jump sends a copy with
  its guard assumed and falls through (`:1225-1231`); a **bounded** jump (with
  or without `when`) sends a copy and falls through, because its exhaustion
  falls through (§3.3);
- iterates the region until its head state is stable (a **probe pass**),
  then walks the region once more from the stable head state and reports
  from that pass only. A probe pass routes control exactly as the final pass
  does: it keeps a **fresh probe-local pending map** for the labels inside the
  region, so a jump inside the region (forward to a later label in it, or an
  exit) carries its state there, an unguarded jump still leaves no
  fall-through, and every back edge's state is accumulated into the next head
  state. A nested head runs its own probes with their own probe-local maps
  inside each probe pass of its enclosing head. What a probe pass may **not**
  do is publish: no diagnostics, verdicts, recorded slots or emitted records,
  and no update of the outer (enclosing walk's or final pass's) pending map —
  an exit jump's state reaches the outer map only from the final pass. The
  probe-local map is discarded at the end of each probe pass. (Publishing a
  probe's pending states would be harmless: the iterates descend and every
  transfer is monotone, so a probe's state on a route contains the final
  pass's on the same route, and meeting it in changes nothing. It is
  forbidden for clarity, not for soundness.);
- bounds the iterations per head by its lattice's height (stated per walk
  below) and, should a head not stabilize within the bound, widens it to the
  walk's conservative top. A unit test reaches the bound with a generated chain
  of facts or characters;
- **counts its work** in a `LoopWalkStats { heads, probe_passes, probe_nodes }`
  per walk kind, the 0.50 `NodeWalkStats` approach: deterministic counters,
  asserted on generated documents (the plan's cost gate). A nested head is
  iterated inside each probe pass of its enclosing head, so the probe work of a
  head at nesting depth *d* is bounded by the product of the per-head bounds of
  its enclosing heads times its region size, the same shape as the runtime
  bound Π(max + 1) (§3.3).

### 3.7 Runtime, replay and trace

- **Counters.** `Machine` keeps `loop_counts: BTreeMap<usize, u8>`, keyed by the
  jump's command index, for one walk. The `"jump"` arm
  (`crates/lute-runtime/src/machine/mod.rs:776-783`) reads `max`. A `jump`
  without `max` behaves as in 0.50.
- **Reset by position.** The region of a bounded jump at index *j* with target
  index *t* < *j* is [*t*, *j*] in the flat command stream. On every transfer of
  control from index *p* to index *t* (fall-through, any jump, a choice or
  match transfer, or the first command of a range), the machine resets the
  counter of every bounded jump whose target is *t* and whose region does not
  contain *p* (or when there is no *p* in this range). This is §3.3's rule on
  the flat stream; §3.2's scope rule keeps a region inside one range.
- **Runaway guard.** `run_range`'s step guard (`mod.rs:712-735`, limit `:718`) counts steps
  since the range started or since the last taken bounded backward jump,
  whichever is later. Between two takes the walk is acyclic, so a defect cycle
  still trips it.
- **Replay and saves: no shape change.** A suspended input is resumed by
  replaying it from its pre-input world with the answers already given
  (`runtime.rs:1-5`, `Continuation`, `:495-506`). Counters are walk-local and
  rebuilt by that replay, exactly as a hub's `presentation` is
  (`machine/menu.rs:529-603`). The Rust `Snapshot` (`runtime.rs:335-349`) keeps its
  shape; its version string moves to `0.51` with every axis. (The player save
  changes shape for a different reason: the pending declared raises, §4.6.)
- **Menus in a loop.** A `<branch>` reached again in a later iteration is a new
  `awaitChoice` with a new `request`; its `presentation` stays `0` (its 0.49
  meaning). Scripted `choose:` lists for a branch are consumed one decision per
  presentation (`ScriptedChoices::pick`, `crates/lute-runtime/src/driver.rs:330-380`), so
  `choose: { retry: [yes, yes, no] }` drives three iterations. A `<hub>` inside a
  loop starts each visit at presentation 0, and its scripted list is per visit,
  as in 0.49. The play and test docs say so.
- **Trace.** The driver's `jump` observation (`mod.rs:779-780`) gains the take
  number and `max` (`{ "kind": "jump", "position", "taken": n, "max": m }`) and
  an exhausted observation (`{ "kind": "jump", "position", "exhausted": true }`).
  `lute trace` (`crates/lute-trace/src/trace/driver_records.rs:223`) prints
  `jump → attempt (again 1/2)` and `jump → attempt not taken (2/2 used)`. This is
  explanation, not a static claim (the D1 quarantine).
- **Player:** none. `jump` is a bookkeeping cue (`packages/player/src/cues/index.ts:412`).
- **Conformance:** a new fixture `conformance/bounded-jump` covers: a retry loop
  exhausted (`max` takes, then fall-through); a loop left early by its guard;
  nested loops where the inner counter resets on each outer iteration; two
  bounded jumps sharing a head (no mutual reset); a `<branch>` inside a loop
  driven by a three-decision script; a `<hub>` inside a loop; a loop inside a
  hub option body; and a save at a choice await in the second iteration,
  restored and resumed to the same transcript. It runs in the Go + JS harness.

## 4. Declared occasion raises (#170)

### 4.1 Manifest

A directive's `effects:` and a reward kind's `effects:` (0.50.0 §5.1) MAY declare
the occasions the **host** raises in answer to the call or the grant:

```yaml
# plugins/acme.stage/occasions/o.yaml
occasions:
  cutscene: { select: first, target: { prefix: scene, entity: cutsceneId }, raisedBy: declared }
# plugins/acme.stage/directives/d.yaml
directives:
  - name: playScene
    attrs:
      - { name: scene, required: true, type: { entity: cutsceneId } }
    effects:
      raises: [{ occasion: cutscene, target: "@scene" }]
# plugins/acme.stage/rewardkinds/r.yaml
rewardKinds:
  CUTSCENE: { target: { entity: cutsceneId, required: true }, effects: { raises: [{ occasion: cutscene, target: "@target" }] } }
```

```lute
--- # scenes/chapter2.lute
kind: scene
id: chapter2
on: cutscene
target: scene.chapter2
---
```

- **`effects.raises`**: a non-empty list of `RaiseDecl { occasion, target? }`,
  `deny_unknown_fields`. `DirectiveEffects` (`crates/lute-manifest/src/schema/directives.rs:57-69`)
  and the 0.50 `RewardEffects` (`schema/vocabulary.rs:201-210`, read through
  the closed `RawRewardEffects`, `:212-239`) gain `raises: Vec<RaiseDecl>`.
  Each `Debug` (hand-written: `DirectiveEffects` `:85-98`, `RewardEffects`
  `vocabulary.rs:259-274`, which `RewardKindDecl`'s `Debug`, `:454-468`, prints
  inside `effects`) prints `raises` only when non-empty, so every existing
  manifest keeps its `capabilitySnapshot`.
- **`target`** is one of:
  - absent: only for an occasion declared without a target (`target:` absent or `false`);
  - `@<attr>` on a directive (a declared attribute of the directive), or
    `@target` on a reward kind (the reward's `target=`);
  - a literal target, written whole (`scene.chapter2`), as a beat writes it.
- **`raisedBy`** (`OccasionBody` `schema/occasions.rs:23-56`, `OccasionDecl` `:108-141`):
  optional, one value `declared`; a `RaisedBy` enum, default `Any` (today's
  meaning). With `declared`, the host raises the occasion only where a
  declared `raises` says so (§4.4). The hand-written `OccasionDecl` `Debug`
  (`:144-170`) prints it only when `declared`.
- `schemas/lute.plugin.json`: `effects.raises` on directives and reward kinds;
  `raisedBy` on occasions.
- `raises` is admitted beside `writes`/`asserts`/`retracts` (directives) and
  `asserts`/`retracts`/`accepts` (reward kinds). A reward kind's `effects: {}`
  stays `E-PLUGIN-PARSE` (0.50.0 §5.1, `RewardEffects::try_from`,
  `vocabulary.rs:223-239`); its "declares no effect" message lists `raises:`
  among the keys, and `effects: { raises: [...] }` alone is a valid block.
  `DirectiveEffects::is_empty` (`directives.rs:72-75`) counts `raises`.
  `RewardEffects::reads_target` (`vocabulary.rs:251-256`) counts a raise whose
  target is `@target`, so 0.50's forbidden-target check
  (`validate_reward_effects`, `validate.rs:545-590`) covers raises with no
  second rule.

### 4.2 Load and assembly rules

At **load** (`E-PLUGIN-PARSE`, at the entry): `raises: []`; an entry that is not
a mapping with `occasion` and optional `target`; a `target` that is neither
`@<name>` nor a dotted target; on a directive, `@<name>` naming no declared
attribute of the directive; on a reward kind, any `@<name>` other than
`@target`, or `@target` on a kind with `target: { forbidden: true }`; an unknown
`raisedBy` value.

A directive whose lowering has no carrier for raises — any `lower:` (a staging
record or a builtin) — cannot declare `effects.raises`:
**`E-PLUGIN-INVALID-DIRECTIVE`** (existing code, new cause, at the `raises`
key): `` directive `::playVideo` lowers to the `video` record, which carries no effects (only a `plugin` record does), so its `effects.raises` could never reach the host — drop `lower:` so the call stays a `plugin` record, or raise the occasion from a passthrough directive ``.
This is the boundary `validate.rs:599-602` already documents for `effects.writes`
on record lowerings (`lower.rs:452-469` returns the record before any effect is
assembled). Staging records are not extended.

At **assembly** (occasions may come from another plugin, so this is where they
are known; 0.50 `E-PLUGIN-STAMP-SURFACE` precedent), **`E-PLUGIN-RAISES`** (new,
error, plugin assembly). A refused entry is dropped and its siblings land:

| Fault | Message shape |
|---|---|
| the occasion is not in the snapshot | `` directive `::playScene` (`acme.stage`) raises occasion `cutscne`, which no active plugin declares — did you mean `cutscene`? `` (a plugin raising another plugin's occasion lists it in `depends:`; the message says so when the occasion exists in an installed but inactive plugin) |
| a `target` on an untargeted occasion, or none on a targeted one | `` … raises `cutscene` without a target, but `cutscene` is raised for a target (`scene.<cutsceneId>`) — add `target: "@<attr>"` `` |
| for a domain occasion `{ prefix, entity }`, an `@attr` whose declared type is not `{ entity: <entity> }` (on a reward kind: whose `target:` contract is not `{ entity: <entity> }`) | `` … raises `cutscene` for `@scene`, which is typed `string`; the target of `cutscene` is a `cutsceneId` member, so type the attribute `{ entity: cutsceneId }` `` |
| a literal target outside the occasion's domain shape (`<prefix>.<member>`; `members:` when listed) | `` … raises `cutscene` for `room.office`, but its targets are `scene.<cutsceneId>` `` |

### 4.3 Checks per call and per grant

`E-RAISES-TARGET` (new, error) is reported by the project pass
(`check --project`, beside `check_project_accepts` in the project-pass list of
`crates/lute-model/src/reconcile.rs:326-328`), at the call's attribute
value for an `@attr` target, at the directive head for a literal, and at the
reward's `target=` (or `kind=`). For each **resolved** target (the attribute's
literal value, the reward's quoted `target=`, or the literal):

- A domain target `<prefix>.<value>` whose value is not a member of the
  project's kind (or of the occasion's `members:`) is `E-RAISES-TARGET` with a
  did-you-mean. (An `@attr` value outside the kind is already `E-ATTR-TYPE`/the
  entity check at the attribute; this case is the `members:` subset.)
- A target that **no** scene or beat answers (no document with `on:` that
  occasion and that target or no `target:`) is `E-RAISES-TARGET`:
  `` `::playScene{scene="chaptr2"}` raises `cutscene` for `scene.chaptr2`, but no scene or beat answers it — did you mean `scene.chapter2`? ``
- **Target resolution** (one rule, used by the project raise table, these
  checks, lowering and the runtime): the call's authored value of the
  attribute; else the attribute's declared `default:`; else the target is
  **unbound**. Only an unbound target suppresses the raise, with no extra
  diagnostic (the directive fact-effect rule: `call_facts`, used by lowering at
  `lower.rs:510-515`, binds through `attr_term`,
  `directive_facts.rs:40-46,140-163`; `required` already reports). A defaulted
  target is a static target: it is judged above, draws its edge and is written
  to the IR. For a reward, the value is the reward's quoted `target=`, bound
  the way 0.50 binds `@target` for `accepts` (`reward_effects::target_accepts`,
  `reward_effects.rs:184`); a reward kind has no target default.
- An `@def` attribute value must fold to a constant, as every attribute value
  must (`def_inline.rs:8-12`, `E-ATTR-DEF-DYNAMIC`; `fold_attr_refs`,
  `expand.rs:340-350`), so it is a static target. A call inside a component body
  is resolved at each `::use` with the use's arguments bound, as `lute-compile`'s
  expansion binds them (`component_effects::use_args_for`/`bind_attrs`,
  `component_effects.rs:113,168`); a `@def` argument folds to a constant there
  too (`def_inline.rs:11-12`). The **only** dynamic target is a value that reads
  `occasion.target` (a call in a beat). It is not judged here; in the graph it
  stands for every answerer of the occasion (§4.5), and the runtime binds it.

### 4.4 Meaning (the host contract)

Lute does not execute a raise: raising occasions is a host duty (D13). A
declared raise is a promise about what the host does:

- **Directive.** After the presentation that ran the call ends
  (`presentationEnd`), the host raises each listed occasion for its resolved
  target, in record order and list order, as a `raiseOccasion` input once the
  runtime is idle.
- **Reward.** After settling the grant (the output that carries the `grant`
  record has been applied), the host raises each listed occasion the same way.
- A raise refused by the occasion's gate (`raisedWhen`, the `gate` query) is
  the host's to report; Lute treats a declared raise as *possible*, never as
  guaranteed. This is the 0.50 soundness bar for reward effects (0.50.0 §5.4:
  reward asserts are possible only): a declared raise adds no fact, write or
  Must claim anywhere, and every static analysis that reads it reads it as a
  may-edge (§4.5, "Soundness").
- A raised occasion declared `judge: before` defers lifecycle handlers as any
  raise of it does; 0.50's #203 rule already applies to every handler,
  whatever raises the occasion (`Root::outlasts_deferral`,
  `fact_must.rs:628`), so a declared raise adds no case to it.
- **`raisedBy: declared`**: the host raises the occasion only through declared
  raises. Without it (the default), the host may raise the occasion at any time
  as before, and a declared raise of it is recorded in the artifact and
  checked (§4.3), but adds no graph edge. An occasion the project clock raises
  (the clock's `raise:` map, `RaiseRule::of`,
  `crates/lute-check/src/clock_positions.rs:776-807`) is raised outside any
  declared raise, so for it `raisedBy: declared` draws no anchor and
  `W-OCCASION-NEVER-RAISED` stays silent (§4.5); `plugins/manifests` says so.
- **Clock analyses count declared raises** (Review051b F3). A declared raise of
  a clock-mapped occasion may deliver it at any clock position, not only where
  the clock's `raise:` map schedules it. `RaiseModel` (`clock_positions.rs:896-992`)
  decides where an occasion is raised (`open`, `:972-981`) and its consumers
  claim absence from that: `unraised` (`:989-1047`), `check_project_unraised`
  (`W-BEAT-UNRAISED`, "never plays", `:1067-1110`) and `chapter_window`
  (`W-CHAPTER-STALL` windows, `:1122-1181`). Conservatively, a `RaiseModel`
  built for an answerer that some declared raise **reaches** treats the
  occasion as raised at every position (`rule` `None`, so `open` holds
  everywhere). "Reaches" is the raise table's one answerer rule (§4.5,
  `RaiseTable::reaches`), the same one anchors, `W-OCCASION-NEVER-RAISED` and
  `E-RAISES-TARGET`'s "no answerer" use: the raise names the answerer's `on:`
  occasion, and the occasion is untargeted, or the answerer declares no
  `target:` (it answers every target of a targeted occasion), or the raise's
  target is `occasion.target`, or its static target equals the answerer's
  `target:` (Review051b F3a).

  `rule` `None` removes only **schedule-only** impossibility claims: that no
  scheduled raise meets the `when` (`unraised` returns `None` at `:990`, so
  `W-BEAT-UNRAISED` does not fire). It does not remove a genuine `when`-window
  failure: `chapter_window` still evaluates the scenes' guards against every
  position (`:1145-1181`; with `rule` `None` a raise may come again at the
  position the scene before played, `later` at `:1157`), so a chain whose next
  scene's `when` has expired by every position after the previous scene can
  still be reported (Review051b F3b). The raise table is passed to these
  passes; answerers no declared raise reaches are judged as in 0.50.
- **Player bindings.** The reference player's `bindings.flow.idle` and `flow.newGame` raises
  (`packages/player/src/session/index.ts:24-50,244-246`) are host
  configuration: a host that raises a `raisedBy: declared` occasion from them
  breaks its own declaration, and `player/bindings` says so.

### 4.5 Graph and reachability

- **Raise sources.** A project-pass table (D14; §2) lists every declared raise
  with its source node, exactly the sources `accept_sources` admits for an
  accept (`crates/lute-check/src/connectivity/graph_sources.rs:103-177`): the
  scene whose shots contain the call, the lore bundle beat whose body contains
  it, or the quest whose body contains it or that grants the reward. Reward
  grant sites are enumerated **once per reward** by a new
  `reward_effects::reward_grant_sites(quest, kinds)` (Review051b F2): one site
  per `<reward>` whose kind declares `effects` (raises included), with 0.50's
  grant point and outcome rules (objective rewards at their objective's
  completion, quest-level rewards at completion, `outcome="failed"` at
  failure) and each document's own vocabulary (`ProjectDoc::reward_kinds`).
  `quest_grants` (`reward_effects.rs:225-263`) cannot serve: it emits one
  `GrantEffect` per resolved fact or accept effect (`Effect`, `:78-85`), so a
  raises-only reward yields nothing and a mixed reward yields several items.
  `quest_grants` is rebuilt on `reward_grant_sites`, so both share the grant-point
  rules. A call in a lore
  entry's body is a raise (it counts for `E-RAISES-TARGET` and
  `W-OCCASION-NEVER-RAISED`) but anchors nothing, as an entry's `::accept`
  anchors nothing (`graph_sources.rs:109-110`). A call inside a component body
  counts at each `::use` site (§4.3); `accept::walk` does not enter components
  (`accept.rs:388-422`), so the raise table walks a `::use`'s component body
  itself, with its arguments bound.
- **Anchors.** A scene or bundle beat node that answers a `raisedBy: declared`
  occasion, declares no `after:`, and has at least one raise source that is a
  graph node gets `PrereqState::Anchored` (`graph_nodes.rs:448-465`) with one
  `Anchor { kind: EdgeKind::Raises, from: <every source of a raise that
  reaches the node, by `RaiseTable::reaches` (§4.4): a matching static target,
  an `occasion.target` target, or any target when the node declares no
  `target:`> }`. The anchors are set
  after the quest anchors (`graph_assembly.rs:133-148`) and before the pass that
  makes every anchor source a node (`:149-183`), so a quest that raises becomes
  a node there. A node that declares `after:` keeps `after:` as its declared
  route, and no `[raises]` edge is drawn to it (the quest rule:
  `QuestDecls::with_after`, `graph_assembly.rs:409-412`). Scenes and beats are
  anchored for the first time; the `PrereqState::Anchored` doc
  (`graph_nodes.rs:458-463`) and the unanchored-`when` list
  (`when_visited_unanchored`, `identity.rs:210-249`, which reads only `Absent`
  nodes) are updated to say so.
- **Reachability** (`connectivity/reachability.rs:249-266`): as for every
  anchor, `Unreachable` reads `Unknown`. A declared raise is a host promise,
  not a proof.
- **Soundness: no Must or guaranteed claim rests on a raise.** An anchored
  node's facts and writes start where an entry node's do, so a raiser's
  writes and asserts never reach the answerer as guaranteed:
  - fact Must: a scene's `Must_in` adds `after:` facts only for
    `PrereqState::Valid` (`fact_must.rs:217-222`); an anchored scene starts
    from the seeds;
  - scalar envelope: `PrereqState::Anchored` starts from the entry floor
    (`envelope.rs:356-363`), as for an accepted quest;
  - start gating: raise anchors do not gate a start and do not join start-cycle
    detection (`start_cycles.rs:20-22` gates `Start` and `Subquest` only);
  - cast presence's `occasions_before` (`cast/facts.rs:52-65`) may follow
    `[raises]` edges: an edge there only **adds** `W-CAST-ABSENT` may-warnings
    (`reconcile_presence`, `cast/presence/mod.rs:281-300`), never removes one,
    and the answerer of a `raisedBy: declared` occasion does follow its raiser.
    `Accept` stays excluded there, as in 0.50;
  - the scenario node envelope's writer provenance (Review051b F4):
    `ancestors_of` (`crates/lute-cli/src/cmd_scenario/node_envelope.rs:16-41`)
    walks every ordering edge to find the writers whose writes are "provably
    before" the node, and `writers_of`/`print_path_set_with_writers`
    (`:62-92,99-146`) list them as upstream; every other writer is "not provably
    before this node". A raise anchor's sources are alternatives (one of them
    ran), so the walk does **not** cross an edge whose only kind is `Raises`;
    a raiser's write is listed as "not provably before this node". An edge that
    also carries another kind is crossed as before.
  A test per bullet (§4.7) shows that an unconditional `::set`/`::assert` in a
  raiser is neither in the answerer's envelope `G` nor Must in it.
- **Edges.** `EdgeKind::Raises` (`graph_nodes.rs:503-540`, token `raises`) is
  appended last, so the derived order of existing kinds, and the `kinds` lists
  of every existing edge, stay as they are. It is drawn `source -> answerer` by

## 5. Localizable directive text (#165)

### 5.1 Manifest: `type: text`

```yaml
directives:
  - name: banner
    attrs:
      - { name: title,    required: true, type: text }
      - { name: subtitle, type: text }
      - { name: style,    type: { enum: [toast, card] } }
```

- `lute_manifest::types::Type` (`types.rs:11-41`) gains `Text`, spelled `text`.
  It prints only where declared, so no existing `capabilitySnapshot` moves.
- **Admitted only** as the type of a directive attribute (`attrs:`) of a
  directive that compiles to a `plugin` record: no `lower:` of any kind and no
  `bridge:`. Load faults (`E-PLUGIN-PARSE`, at the attribute):
  - `text` on a directive with `lower:` (a staging record, a builtin) or with
    `bridge:`: `` `title` of `::banner` is `text`, but `::banner` lowers to the `actor` record, which carries no localized text — declare it `string`, or drop `lower:` so the call stays a `plugin` record ``;
  - `text` with `default:` (an untranslatable source);
  - `text` anywhere else the type grammar is read — a stamp (`stampAttrs`,
    refused at assembly beside 0.49's structured-type refusal,
    `assemble.rs:571-585`), plugin `options:`, an occasion `payload:`,
    reward-kind `attrs:`, bridge results, `{ list: text }` — each place's
    existing invalid-type diagnostic, naming the one place `text` is admitted.
    A 0.50 host token (`hostTokens:`) cannot be `text` already: its type is
    `string`, `int` or an enum (`HostTokenType`, `schema/host_tokens.rs`);
  - a directive with a `text` attribute that also declares an attribute named
    `code` (`code` is the identity attribute of such a directive, §5.3).
- **Stamps (0.50.0 §3.2).** A stamp scoped with `on: [banner]` and named `code`
  is shadowed by that core attribute: `E-PLUGIN-RESERVED-STAMP-ATTR`. The
  mechanism is 0.50's: `StampSurface::own_attrs` for a `Directive(tag)` surface
  (`stamps.rs:145-152`) lists the directive's declared attributes and gains
  `code` when one of them is `text`, so `merge_stamp_attr`'s shadow check
  (`assemble.rs:887-898`) reports it with no new rule. A cross-cutting stamp
  (no `on:`) named `code` keeps applying to other directives; on a directive
  with a `text` attribute the core `code` is matched first, as a line's own
  `code` is (`LINE_ATTRS`, `core.rs:88-99`).

### 5.2 Authoring and checking

```lute
::banner{code="0010" title="Welcome to the hall, {{userName}}" style="card"}
```

- A `text` value is a quoted string in the **choice-label grammar**: `{{…}}`
  interpolations of state paths, `@def`s and host tokens (0.50.0 §4: the core
  `userName` and each plugin's `hostTokens:`) with their modifiers, and `\{{`
  for a literal brace (`scan_label_interps`,
  `crates/lute-syntax/src/ast.rs:837`; host tokens classified by
  `classify_interp`, `:738`). Inline markup is not parsed, as in a label. Each
  interpolation is checked as a label's is (definite assignment
  `check_label_reads`, `defassign.rs:953`; modifier typing; a declared host
  token's hints typed by its declaration; `E-CEL-PROFILE` for an undeclared
  token, naming the declared ones). (S6: a quoted attribute value cannot
  spell `\{{` today — `E-STRING-ESCAPE` — in a choice label either; #211. The
  whole-project quest-reference pass does not yet read `text` values; #212.)
- A 0.50 `node` lint row of such a directive (`node.attrs`, read with
  `lute_syntax::authored_attrs`) shows the value as written, markers and
  escapes undecoded, and `code` like any attribute.
- An `@ref` value (`title=@greeting`) is `E-ATTR-TYPE`: `` `title` of `::banner` is localizable `text`, written as a quoted string; a `@def` value has no translation of its own ``.
- **`code=`** is admitted on a directive with at least one `text` attribute, as
  on a content line: a string, trimmed. On any other directive `code` stays
  `E-UNKNOWN-ATTR`.

### 5.3 Identity

- **`lineId`** of a `text` attribute is `{prefix}~{tag}~{code}~{attr}`, e.g.
  `intro~banner~0010~title`. It does **not** go through the `lineId` template.
  `prefix` is the line prefix of the enclosing identity scope, component
  instance segments included, exactly as for a line (`address.rs:254-370`).
  Position is never identity (D8).
- **Why ids do not collide.** `~` is the directive-text separator. A choice or
  prompt id is `{prefix}.{groupId}.{optionId|prompt}` (`address.rs:348-367`)
  over identifiers and the document prefix; a line id is the `lineId` template
  over that prefix, a speaker identifier and a code. 0.51 keeps `~` out of the
  parts it controls:
  - a `lineId` template whose literal text contains `~` is
    `E-IDENTITY-TEMPLATE` (new cause; `validate_template`, `project.rs:906-937`): `` identity template `lineId` contains `~`, which is reserved for directive text identities ``;
  - a `code` (on a line or a directive) containing `~` is
    **`E-LINE-CODE-RESERVED`** (new): `` `code="a~1"` contains `~`, which is reserved for directive text identities ``.
    `lute tag` never writes one, and the corpus has none (all corpus codes are
    numeric; re-checked at `9ccd2fa9`, `plugin-surfaces` included).

  The prefix is not fully closed: a scene without an authored `id:` takes the
  prefix `{character}.{episodeId}`, and a legacy `episodeId` is free text that
  can contain `~` (`canonical_episode_id`, `crates/lute-check/src/meta/kind.rs:409-444`). The
  separator therefore does not prove distinctness by itself; the final
  uniqueness check below governs that case (and every custom-template case).
- **Final uniqueness, every kind.** As a backstop for every shape (custom
  templates without `{prefix}` included), the project pass checks that the
  final `lineId`s of every line, option, prompt and directive text in the
  project are distinct: **`E-LINE-ID-DUP`** (new, error, project-wide, at the
  second unit, `related` the first): `` lineId `intro.mira_0010` of this line is also the lineId of the line at scenes/intro2.lute:8 — a lineId keys one translation `` (the same invariant `lute loc import` relies on when it rejects duplicate rows, `loc.rs:1176-1184`). Units expanded from one component at several `::use` sites are distinct by their instance segment under a template with `{prefix}`; a unit expanded from a component is reported in the component's file, at its line (S6 review).
- **Codes.** `assign_identity_scope` (`address.rs:298`) keeps per-scope counters
  per directive tag, in a keyspace separate from speakers (a `DirectiveTag`
  owner, never a speaker string). An untagged directive gets the next code (max
  authored + 10, `{:04}`), as a line does, numbered in **source order** — the
  order `lute tag` writes them in — even where a `<timeline>` plays its clips
  in another (S6). A component's calls are numbered over the whole component
  source before a `::use`'s arguments fold a `<match>` away, as its lines are
  (S6 review), and a `{{@param}}` in a component's `text` attribute binds at
  expansion as in a content line. A directive's code reaches the
  artifact only inside `localized.<attr>.lineId`: `code` is never written to
  `fields` **or** `stamps` (Review051b F5). Lowering decides "the directive's
  own attribute" in one predicate, `declares_attr` (`lower.rs:752-758`), which
  feeds both the stamp extraction (`plugin_stamps`, called at `:291-293`; it
  skips owned keys, `:803-805`, and otherwise serializes any applicable stamp,
  a cross-cutting `code` included, `:806-808`) and the passthrough fields loop
  (`:473-487`). It becomes an ownership predicate that also answers `true` for
  the implicit identity `code` of a directive with a `text` attribute, so
  `plugin_stamps` never lifts a `code` stamp there; the fields loop skips
  `code` explicitly (it is owned but is no field). Elsewhere — lines, and
  directives without a `text` attribute — a `code` stamp is serialized as in
  0.50. `PluginCmd` gains no serialized `code` field (the authored code rides a
  `#[serde(skip)]` field from lowering to addressing).
- `lute tag` (`crates/lute-check/src/tag.rs`, `tag_document` `:27`,
  `retag_document` `:294`) writes `code="…"` into every untagged directive that
  has a `text` attribute, with the same back-fill order the compiler uses (a
  test asserts both agree). `codes_locked` (`:462`) applies. It finds the
  directive head's attributes with 0.50's `lute_syntax::authored_attrs`
  (`crates/lute-syntax/src/parser/attrs.rs:413`), the parser's own scanner,
  rather than a second scan. A component the project's documents use is
  tagged under its users' snapshots (an imported body is checked and lowered
  under its host's); users that disagree on whether a called directive has
  `text` attributes refuse the component: **`E-COMPONENT-TEXT-DIRECTIVE`**
  (new, `lute tag`, at the call, a use of each kind related) (S6 review).
- **`E-DUP-LINE-CODE`** (existing, `match_check/line_codes.rs`) gains the site
  "two `::banner` calls in one scope share `code`"; message: `` `::banner` calls at lines N and M share `code="0010"`; a (directive, code) pair is the localization identity of its `text` attributes ``.
- **`W-LINE-CODE-UNTAGGED`** (with `identity.requireStable`) applies to such a
  directive without `code`.

## 6. Lint `target: pair` (#172)

### 6.1 Declaration

```yaml
lints:
  - id: group-balanced
    target: pair
    open:   'node.tag == "group" && "mode" in node.attrs && node.attrs["mode"] == "begin"'
    close:  'node.tag == "group" && "mode" in node.attrs && node.attrs["mode"] == "end"'
    inside: 'node.kind == "line" || node.tag in ["actor", "sfx"]'   # optional
    scope: body                                                    # body (default) | section
    level: error
    message: "::group begin/end"
```

- `lute_manifest::lint::LintTarget` (`lint.rs:82-92`, which 0.50 extended with
  `Node`) gains `Pair`. A rule's body
  becomes an enum: `Predicate { when }` for every other target and
  `Pair(PairSpec { open, close, inside: Option, scope: PairScope })` for `pair`.
  The `LintRuleDecl` (`lint.rs:42-75`, today a flat `when: String`, `:56`) loader enforces the shape: on `pair`, `open`
  and `close` are required and `when` is refused; on every other target,
  `open`/`close`/`inside`/`scope` are refused. A fault is `E-PLUGIN-PARSE` in a
  plugin's `lints:` and `E-LINT-CONFIG` in `lute.lint.yaml` `custom:`.
- `open`, `close` and `inside` are lint-CEL predicates over the 0.50 `node` row
  (0.50.0 §8.1; `NodeRow`, `crates/lute-lint/src/nodes.rs:103-160`: `kind`,
  `tag`, `speaker`, `attrs` as authored, `index`, `first`, `last`, `depth`,
  `prev`, `next`, `parent`, `preceding`, `section`), with the `scene` and
  `options` bindings and the 0.50 string members. Missing keys keep CEL
  semantics (`E-LINT-EXPR`); the recipes guard every index (0.50.0 §8.1).

### 6.2 Evaluation

- **Scope `body`**: each body's direct children, in order (the rows' siblings).
  **Scope `section`**: every row of one section or declaration in document
  order, at every depth (the unit that resets `node.preceding`, 0.50.0 §8.1).
  `section` is document order, not paths: an `open` in one `<choice>` and a
  `close` in its sibling pair up.
- For each scope, one pass with one open slot:
  - a row for which `close` holds while a pair is open closes it (a row that
    satisfies both `open` and `close` is a close while a pair is open, an open
    otherwise);
  - a row for which `open` holds while a pair is open is a **nested open**; the
    outer pair stays open;
  - a row for which `close` holds with no pair open is an **unopened close**;
  - with `inside`, every row strictly between an open and its close (scope
    `body`: siblings only, not their descendants) for which `inside` is false is
    an **inside fault**;
  - at the end of the scope, an open pair is an **unclosed open**.
- **Findings** carry the rule's code and level, anchor at the offending row's
  span, and append a fixed `PairFault` phrase to the rendered `message`:
  - unclosed: `` — opened here, with no close in this body `` (`section` scope: `in this section`);
  - unopened: `` — a close with no open pair in this body ``;
  - nested: `` — opened again while the pair from line N is still open ``;
  - inside: `` — not allowed inside the pair opened at line N ``.

  `related` names the open row for nested and inside faults.
- **Where it runs.** `pair` rules are evaluated in the 0.50 **node walk**
  (`walk_nodes`, `nodes.rs:492`, driven by `evaluate_node_rules`,
  `crates/lute-lint/src/rules.rs:549`), not the metrics walk: 0.50 moved node
  rows into their own walk after the metric tables because a row binds `scene`
  (`nodes.rs:26-27`; 0.50 plan log, S7). The engine runs that walk when a
  `node` **or** `pair` rule is active (`engine.rs:160-168` selects `node` rules
  today). Each rule is evaluated at its row while the row's view is valid; no
  row is stored or copied. A `body`-scope rule keeps one open slot per body
  frame (pushed and popped with the walk's `preceding` frames), a
  `section`-scope rule one slot per section or top-level declaration (the
  walk's scope reset, `nodes.rs:557-605`). The first `E-LINT-EXPR` stops that
  rule for the document, as for a `node` rule (`rules.rs:546`).
- **Cost** (0.50.0 §8.1 "Cost" approach; Review051b F6). **What is linear:**
  the pair state machine's own overhead — at a fixed number of rules, each row
  costs at most three predicate invocations per `pair` rule and O(1) slot
  work. **What is not claimed linear:** the work a predicate does. A predicate
  is a lint-CEL expression and may read variable-size data at every row, for
  example `size()` of a long string (it counts characters, `eval.rs:359-365`)
  or attributes of `node.preceding` entries (`nodes.rs:193-208`); an
  N-character value read at N later rows costs N² characters, which is the
  rule's choice, as a whole-map read of `preceding` is in 0.50. The counters
  say which is which:
  - `NodeWalkStats` (`nodes.rs:38-91`) gains `pair_evals`, an **invocation
    counter** (predicate calls, not their cost), and `pair_slots` (slot
    opens, closes and frame pushes);
  - predicate processing is counted by the existing work counter, which
    today counts rows, head bytes, attributes, modeled map steps and copied
    values but not string processing. It gains `eval_chars`: the characters
    the evaluator scans in a string operation (`size(string)`, `startsWith`,
    `endsWith`, `contains`, string `==`/`!=`), for `node` and `pair` rules
    alike;
  - `work()` adds `pair_slots` and `eval_chars` (`pair_evals` is reported, not
    summed: its cost is in the others). 0.50's components keep their values,
    so `work() − eval_chars − pair_slots` reproduces 0.50's logged grid.

  `lute-bench lint-nodes` (`crates/lute-bench/src/lint_nodes.rs`) gains a
  `pair` axis: N ∈ {5 000, 10 000, 20 000} rows with alternating begin/end
  markers at D = 3, each doubling ≤ 2.3× in work and in time; D ∈ {2, 8, 32} at
  N = 10 000, 2→32 ≤ 2×; and a **payload axis**: a predicate reading
  `size(node.attrs["text"])` over attribute values of P ∈ {16, 256, 4 096}
  characters at N = 10 000: `eval_chars` equals the characters the predicate
  scans exactly, and total work grows no faster than the N × P ratio (≤ 1.15×
  it) — the gate shows the cost is counted, not that it is absent.
  The work counts are the CI test; the times are recorded in the plan log.
