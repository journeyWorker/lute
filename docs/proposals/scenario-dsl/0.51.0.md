# Lute 0.51.0 — flow and text

This is the normative 0.51.0 contract. The words **MUST**, **MUST NOT**,
**SHOULD** and **MAY** have their RFC 2119 meanings.

The inputs are the dogfood issues #159, #165, #170, #172 (the `pair` half) and
#176 (the authoring half), each with a 0.48.1 reproduction from a large real
port. The options and recommendations are in
[`docs/design/0.50-extensibility-options.md`](../../design/0.50-extensibility-options.md)
(§3, §6, §7, §8, §9, §10, §12), and the decisions are in
[`2026-10-26-lute-0.51-decisions.md`](../../superpowers/notes/2026-10-26-lute-0.51-decisions.md).
Where this spec departs from a recommendation, the decision note gives the
evidence, and Appendix B lists every decision.

The release adds one kind of control flow that every analysis can see (a
bounded backward jump), one host contract the scenario graph can see (a
declared occasion raise), one localized attribute type and one lint target.
There is no new keyword and no new element. The new surface is one core
directive attribute (`::jump{max}`), two plugin manifest keys
(`effects.raises` on directives and reward kinds; `raisedBy` on occasions),
one attribute type (`text`) and one lint target (`pair`). #176 is not developed
(§7). The release is a clean cutover (ADR D6).

The base is `origin/main` after **v0.50.0**. Code anchors are cited at
`f34f141f` (v0.49.0) plus the changes the 0.50.0 spec describes; Appendix A
lists them, and the plan's bootstrap re-locates each one by symbol.

Implementation plan:
[`2026-10-26-lute-0.51.0-flow-and-text.md`](../../superpowers/plans/2026-10-26-lute-0.51.0-flow-and-text.md).

## 1. Scope and version contract

This is a minor release. Every public version axis is `0.51.0`: toolchain,
`luteVersion` (`LUTE_LANG_VERSION`), `irVersion`, `eventVersion`,
`snapshotVersion`, and the seven npm packages. The contract schemas move to the
`0.51` line (`schemas/lute-{ir,events,snapshot,player-bindings}-0.51.schema.json`).
`bindingsVersion` and the player save/profile format become `"0.51"`. This
follows the 0.50.0 §1 precedent.

| Axis | 0.51.0 contract |
|---|---|
| Language | **Looser.** `::jump` may target an earlier `::label` when it carries `max` (§3). A directive attribute may be typed `text`, and such a directive takes `code=` (§5). |
| Static semantics | Every flow analysis joins the states of all jumps that reach a label, forward and backward, and iterates a loop head to a fixed point (§3.4). This fixes two forward-jump gaps (§3.4, "Fixed"). |
| IR | `jump.max` (§3.6). `plugin` records gain `raises` and `localized`; `RewardEntry` gains `raises` (§4.6, §5.4). Schema `-0.51`. |

| Event / snapshot | **No schema shape change.** The untyped `record` payload of a `plugin` record gains `raises` and `localized`; a `grant` record gains `raises` (§4.6, §5.6). The `Snapshot` shape is unchanged: loop counters are rebuilt by replay (§3.7). Schemas renamed `-0.51`. |
| Plugin manifests | Directive and reward-kind `effects.raises`; occasion `raisedBy: declared` (§4.1); attribute type `text` (§5.1). |

| `capabilitySnapshot` | **Changes once for every artifact**, because the core `::jump` declares `max` (§3.1; class 4 of §13). Otherwise each new key folds into the hash only when used (§4.1, §5.1). |
| Report ids | Unchanged. |

Outside the deltas listed in §13, every output captured by
`scripts/cli-snapshot.py` MUST be byte-identical to 0.50.0 after version-stamp

## 2. Shared rules

The 0.50.0 §2 rules apply unchanged: a regression test that fails on the base
for every behaviour change (the issue reproductions first); one diagnostic shape
(registered in `crates/lute-cli/src/codes/registry.rs` and
`crates/lute-check/src/evidence.rs`, blessed with `LUTE_BLESS_DIAGNOSTICS=1`,
website EN + KO); **no hint recommends a spelling the checker rejects**; no
silent drop; byte stability for projects without the new keys (except §13);
documentation in the same change; and `docs/design/rust-coding-rules.md` for new
Rust code. In particular:

- **Newtypes and enums, not strings:** `JumpMax` (a `u8` in 1..=99),
  `LoopRegion`, `LoopTable`, `RaiseDecl`, `RaiseTarget`, `RaisedBy`,
  `LocalizedText`, `TextAttr`, `PairSpec`, `PairScope`, `PairFault`.
- **No HIR, no Fold, no synthesized nodes (rules §7).** A loop is a table
  computed from the AST once per document (§3.2), and every walk consults it. A
  raise is a table resolved once per project root (D14), read by each consumer
  beside its existing walk.
- **One join.** Every flow walk joins at a label through one helper per walk
  kind (§3.4), never through a second ad-hoc rule.

## 3. Bounded backward jump (#159)

### 3.1 Syntax and the `max` attribute

`::jump` may target an **earlier** `::label` when it carries `max`, the number
of times the jump may be taken. After `max` takes, the jump is not taken and
control falls through to the next node.

```lute
::label{name="attempt"}
::minigame{level="2"}                     # a blocking bridge call that writes run.won
<match subject="run.won">
  <when is="false">
    @mira: Again!
    ::jump{to="attempt" max="2"}
  </when>
</match>
@theo: That's enough for today.
```

- `lute.core`'s `jump` declaration
  (`crates/lute-manifest/assets/lute.core/directives/staging.yaml:83-87`) gains
  `{ name: max, required: false, type: int }`. It is the only declaration site.
  The LSP, `lute context` and the attribute checker read it from there. This
  changes `capabilitySnapshot` for every artifact once (§13 class 4).
- **`max` is a literal integer in 1..=99.** A non-integer value is the existing
  `E-ATTR-TYPE` (the declared `int`). An `@ref` value, `0`, a negative value or
  a value above 99 is **`E-JUMP-MAX`** (new): `` `max` on `::jump` is the most
  times it may be taken: a literal integer from 1 to 99 (a loop bound is static,
  so it cannot be `@ref`) ``.
- **A backward jump without `max`** stays `E-JUMP-BACKWARD`. The message gains
  the new spelling: `` … `::jump` only jumps forward unless it carries `max`:
  `::jump{to="again" max="3"}` repeats at most 3 times; to offer choices again,
  use a `<hub>` (it asks until an `exit` choice is taken) ``.
- **`max` on a forward jump** is `E-JUMP-MAX` too: `` `max` bounds a backward
  jump; `::jump{to="later"}` already goes forward, so `max` means nothing here —
  remove it ``.
- `when=` and `max` combine: the jump is taken while `when` holds and takes
  remain. A guarded jump keeps its 0.12.0 lowering (a one-arm `<match>` around
  the `jump`, `crates/lute-compile/src/normalize.rs:572-594`).
- `max` is not a stamp carrier: `::jump` stays in `UNSTAMPED_DIRECTIVES`.

### 3.2 Loop regions and structural rules

Positions are the document-order counter of the label pass
(`crates/lute-check/src/next_labels.rs:9-17`, `walk` `:130-180`), which agrees
with compiled address order. For a bounded jump **J** at position *j* that
targets label **L** at position *l* < *j*, the **region** of J is every node at
a position in [*l*, *j*]. L is the region's **head**.

The label pass builds a `LoopTable` once per document: every bounded jump with
its head, its region and its enclosing regions. It is computed beside the
existing label table in `check_next_labels` (`next_labels.rs:194`) and handed to
the flow walks the way `next_targets` is (`:322`). The rules:

| Rule | Code | Message shape |
|---|---|---|
| **Scope.** L is in J's own body or in a body that encloses J, and every body between them is a `<choice>` body of a `<branch>` or a `<match>` arm body. The chain may not leave a hub option body, a hub `<return>` body, an `<on>` or `<objective>` body, a quest, an entry, a beat or a section. | **`E-JUMP-LOOP-SCOPE`** (new) | `` `::jump{to="attempt" max=…}` loops back to a label outside the `<hub>` option it is in; a loop stays inside one option body — put `::label{name="attempt"}` inside it, or use the hub itself to repeat `` (the boundary is named: hub option, hub `<return>`, `<on>`, `<objective>`, quest, entry, beat, or section `## …`) |
| **No entry into a region.** A forward jump whose source is outside a region and whose label is strictly inside it (after its head). | **`E-JUMP-INTO-LOOP`** (new) | `` `::jump{to="mid"}` enters the loop of `::jump{to="attempt" max=…}` (line N) after its head `attempt`; a loop is entered only at its head — jump to `attempt` instead `` |
| **Nest, never cross.** Two regions either nest or are disjoint. Regions [*l₁*, *j₁*] and [*l₂*, *j₂*] cross when *l₁* < *l₂* ≤ *j₁* < *j₂*. Regions with the same head nest. | **`E-JUMP-LOOP-CROSS`** (new), at the later jump | `` the loop `attempt` … (line N) and the loop `retry` … (line M) overlap without nesting; close the inner loop before the outer one jumps back `` |

- Two or more bounded jumps MAY share a head. Each has its own counter and its
  own region.
- A jump from inside a region to a label after the region (an exit) and a
  forward jump from before the region to the head are legal.
- A bounded jump inside a component body is checked in the component's own
  document. After expansion every instance has its own command positions and so
  its own counters (§3.7).
- These rules make every loop reducible and well-nested, so each flow walk
  can treat a head as one join point (§3.4).

### 3.3 Meaning

- **Counter.** Each bounded jump has a counter, local to one walk (one
  presentation; one quest handler or objective segment; one entry or beat
  body), starting at 0.
- **Take.** When control reaches J (and its `when` holds, if any): if the
  counter is below `max`, it is incremented and control moves to the head;
  otherwise control falls through to the node after J.
- **Reset.** J's counter returns to 0 whenever control arrives at its head from
  **outside J's region**: by falling through into the label, by a forward
  jump, or by a bounded jump that is not inside J's region. A take of J itself,
  or of another bounded jump inside J's region, does not reset it.
- **Termination.** Between two consecutive bounded takes, control moves only
  forward, so it is bounded by the walk's length. A region's counter is reset
  only when its head is entered from outside, so by induction over the nesting
  (innermost first) a region of nesting depth *d* is traversed at most
  Π(max_k + 1) times, the product over its enclosing jumps. Every walk ends
  without player cooperation. The landing page's "total" claim stands.
- A jump with `max` that is never reached, or a `when` that never holds, is not
  an error (the existing `E-ARM-DEAD` rule applies to a provably false `when`).

### 3.4 Flow analyses: one label join, a fixed point at each head

**Rule.** Every analysis that threads a state through a body in document order
MUST compute the state at a `::label` as the **join** of the fall-through state
and the state of every jump that reaches the label, and MUST compute the state
at a loop head as the least fixed point of
`head = join(entry, back-edge states of the region walked from head)`. Each
walk:

- iterates the region until its head state is stable, with **no diagnostics,
  verdicts or emitted records during the iterations**, then walks the region
  once more from the stable head state and reports from that pass only;
- bounds the iterations by its lattice's height and, should a head not
  stabilize within the bound, widens it to the walk's conservative top (stated
  below). A unit test reaches the bound with a generated chain of facts or
  characters.

| Walk | Today (`f34f141f`) | 0.51 |
|---|---|---|
| Relational facts, must/may (`crates/lute-check/src/fact_must.rs`): `E-ARM-DEAD`, `W-FACT-GUARANTEED`, `E-FACT-EXCLUSIVE`, `E-QUEST-UNREACHABLE` inputs, completion states | joins forward jumps at labels (`label`/`jump`, `:868-885`; `pending`) | Loop heads: `head = meet(entry, back edges)` iterated (Must only shrinks; finite). Guards inside a region are `record`ed only in the final pass, so no verdict rests on an early iteration's Must set. Top: the empty Must set. |
| Definite assignment (`crates/lute-check/src/defassign.rs:407-481`): `E-MAYBE-UNSET`, choice `into`/`scene.choices` records | **no join**: a `::label` is a no-op, so a jump that skips a write is unseen (decision note item 4) | A `pending` map per label (as `fact_must.rs`): at a jump, record `available`; at a label, intersect. Loop heads: `head = intersect(entry, back edges)`, iterated; assignments only grow along a path, so it is stable after one pass, which the test asserts. Top: the empty set. |
| Stage state, checker (`crates/lute-check/src/check/injections.rs:19-65`, `inject.rs`): `W-STAGE-ABSENT`, implicit-read diagnostics | **no join** (same) | Pending states joined with `StageState::join` (`inject.rs:341`) at each label. Loop heads iterated. Top: `on_stage` empty, every character seen in the document in `maybe_on_stage`, `exited` the union seen, `bg`/`music` `None`. |
| Stage state, compiler (`crates/lute-compile/src/stage.rs:48-110`, `walk_seq`): injected records | **no join** (same) | The compile walk binds the same head and label states. The head state comes from one shared function in `lute-check` (the checker fold, run without emission), so the checker and the compiler cannot disagree; the compile walk emits once, from the stable state. A test compares both on every conformance and example document with a jump. |
| Cast presence (`crates/lute-check/src/cast/presence/walk.rs`): `W-CAST-ABSENT` | a jump target kills the live guards of the enclosing regions (`label`, `:236-244`) | A loop head is a jump target, so that rule applies. In addition, at a loop head the walk applies `kill_writes` to the region (`:276`), the treatment a `<hub>` gets for its bodies. |
| Dead code (`crates/lute-check/src/reachability/diagnostics.rs:311`): `W-CODE-AFTER-JUMP` | an unguarded `::jump` ends the straight-line body | A bounded jump does not: its exhaustion falls through. Only an unguarded jump without `max` ends the body. |

- **Fixed: forward jumps.** The defassign and stage rows fix two gaps that
  0.49.0 and 0.50.0 have for forward jumps (decision note item 4). Both

- The slice greps every consumer of `LABEL_DIRECTIVE`, `JUMP_DIRECTIVE`,

  `crates/lute-trace` and `crates/lute-lsp`, and records each as "joins at

### 3.6 IR and semantics

- `JumpCmd` (`crates/lute-compile/src/ir.rs`, lowered at `lower.rs:408-411`)
  gains `max: Option<u8>`, `skip_serializing_if = "Option::is_none"`. Its
  `target` is the position of the first record after the label, as for a forward
  jump (`address.rs:147`, the document-wide named-label resolution). A jump
  without `max` is byte-identical to 0.50.
- **New semantic id `lute.core.boundedJump/1`** (module `core`, behaviour
  `"bounded backward jumps"`). `semantics::collect` adds it with provenance
  `bounded jump` when any `jump` command has `max`. An engine that ignores `max`
  either loops without bound or never loops, so the field changes meaning (D5).
  `REGISTRY` goes from 16 (after 0.50) to 17 entries, and `FIELD_TABLE` gains
  `max`. The id lists in `crates/lute-cli/tests/engine_negotiation.rs`,
  `docs/design/modules.md` and `tooling/runtime-contract` gain it.
- Schema `schemas/lute-ir-0.51.schema.json`: the `jump` command gains
  `"max": { "type": "integer", "minimum": 1, "maximum": 99 }`.

### 3.7 Runtime, replay and trace

- **Counters.** `Machine` keeps `loop_counts: BTreeMap<usize, u8>`, keyed by the
  jump's command index, for one walk. The `"jump"` arm
  (`crates/lute-runtime/src/machine/mod.rs:733-740`) reads `max`. A `jump`
  without `max` behaves as in 0.50.
- **Reset by position.** The region of a bounded jump at index *j* with target
  index *t* < *j* is [*t*, *j*] in the flat command stream. On every transfer of
  control from index *p* to index *t* (fall-through, any jump, a choice or
  match transfer, or the first command of a range), the machine resets the
  counter of every bounded jump whose target is *t* and whose region does not
  contain *p* (or when there is no *p* in this range). This is §3.3's rule on
  the flat stream; §3.2's scope rule keeps a region inside one range.
- **Runaway guard.** `run_range`'s step guard (`mod.rs:675-680`) counts steps
  since the range started or since the last taken bounded backward jump,
  whichever is later. Between two takes the walk is acyclic, so a defect cycle
  still trips it.
- **Replay and saves: no shape change.** A suspended input is resumed by
  replaying it from its pre-input world with the answers already given
  (`runtime.rs:1-5`, `Continuation`, `:495-506`). Counters are walk-local and
  rebuilt by that replay, exactly as a hub's `presentation` is
  (`machine/menu.rs:532`). The `Snapshot` (`runtime.rs:337-349`) and the player
  save keep their shapes. Their version strings move to `0.51` with every axis.
- **Menus in a loop.** A `<branch>` reached again in a later iteration is a new
  `awaitChoice` with a new `request`; its `presentation` stays `0` (its 0.49
  meaning). Scripted `choose:` lists for a branch are consumed one decision per
  presentation (`crates/lute-runtime/src/driver.rs:346-377`), so
  `choose: { retry: [yes, yes, no] }` drives three iterations. A `<hub>` inside a
  loop starts each visit at presentation 0, and its scripted list is per visit,
  as in 0.49. The play and test docs say so.
- **Trace.** The driver's `jump` observation (`mod.rs:736-737`) gains the take
  number and `max` (`{ "kind": "jump", "position", "taken": n, "max": m }`) and
  an exhausted observation (`{ "kind": "jump", "position", "exhausted": true }`).
  `lute trace` (`crates/lute-trace/src/trace/driver_records.rs:214-222`) prints
  `jump → attempt (again 1/2)` and `jump → attempt not taken (2/2 used)`. This is
  explanation, not a static claim (the D1 quarantine).
- **Player:** none. `jump` is a bookkeeping cue (`packages/player/src/cues/index.ts:403`).
- **Conformance:** a new fixture `conformance/bounded-jump` covers: a retry loop
  exhausted (`max` takes, then fall-through); a loop left early by its guard;
  nested loops where the inner counter resets on each outer iteration; two
  bounded jumps sharing a head (no mutual reset); a `<branch>` inside a loop
  driven by a three-decision script; a `<hub>` inside a loop; a loop inside a
  hub option body; and a save at a choice await in the second iteration,
  restored and resumed to the same transcript. It runs in the Go + JS harness.

## 4. Declared occasion raises (#170)

### 4.1 Manifest

A directive's `effects:` and a reward kind's `effects:` (0.50.0 §5.1) MAY declare
the occasions the **host** raises in answer to the call or the grant:

```yaml
# plugins/acme.stage/occasions/o.yaml
occasions:
  cutscene: { select: first, target: { prefix: scene, entity: cutsceneId }, raisedBy: declared }
# plugins/acme.stage/directives/d.yaml
directives:
  - name: playScene
    attrs:
      - { name: scene, required: true, type: { entity: cutsceneId } }
    effects:
      raises: [{ occasion: cutscene, target: "@scene" }]
# plugins/acme.stage/rewardkinds/r.yaml
rewardKinds:
  CUTSCENE: { target: { entity: cutsceneId, required: true }, effects: { raises: [{ occasion: cutscene, target: "@target" }] } }
```

```lute
--- # scenes/chapter2.lute
kind: scene
id: chapter2
on: cutscene
target: scene.chapter2
---
```

- **`effects.raises`**: a non-empty list of `RaiseDecl { occasion, target? }`,
  `deny_unknown_fields`. `DirectiveEffects` (`crates/lute-manifest/src/schema/directives.rs:57-69`)
  and the 0.50 `RewardEffects` gain `raises: Vec<RaiseDecl>`. Each `Debug` (hand-written,
  `:83-97` and the 0.50 `RewardKindDecl` `Debug`) prints `raises` only when
  non-empty, so every existing manifest keeps its `capabilitySnapshot`.
- **`target`** is one of:
  - absent: only for an occasion declared without a target (`target:` absent or `false`);
  - `@<attr>` on a directive (a declared attribute of the directive), or
    `@target` on a reward kind (the reward's `target=`);
  - a literal target, written whole (`scene.chapter2`), as a beat writes it.
- **`raisedBy`** (`OccasionBody`/`OccasionDecl`, `schema/occasions.rs:23-50,108-`):
  optional, one value `declared`; a `RaisedBy` enum, default `Any` (today's
  meaning). With `declared`, the host raises the occasion only where a
  declared `raises` says so (§4.4). The hand-written `OccasionDecl` `Debug`
  prints it only when `declared`.
- `schemas/lute.plugin.json`: `effects.raises` on directives and reward kinds;
  `raisedBy` on occasions.
- `raises` is admitted beside `writes`/`asserts`/`retracts` (directives) and
  `asserts`/`retracts`/`accepts` (reward kinds). An `effects: {}` stays
  `E-PLUGIN-PARSE` (0.50.0 §5.1).

### 4.2 Load and assembly rules

At **load** (`E-PLUGIN-PARSE`, at the entry): `raises: []`; an entry that is not
a mapping with `occasion` and optional `target`; a `target` that is neither
`@<name>` nor a dotted target; on a directive, `@<name>` naming no declared
attribute of the directive; on a reward kind, any `@<name>` other than
`@target`, or `@target` on a kind with `target: { forbidden: true }`; an unknown
`raisedBy` value.

At **assembly** (occasions may come from another plugin, so this is where they
are known; 0.50 `E-PLUGIN-STAMP-SURFACE` precedent), **`E-PLUGIN-RAISES`** (new,
error, plugin assembly). A refused entry is dropped and its siblings land:

| Fault | Message shape |
|---|---|
| the occasion is not in the snapshot | `` directive `::playScene` (`acme.stage`) raises occasion `cutscne`, which no active plugin declares — did you mean `cutscene`? `` (a plugin raising another plugin's occasion lists it in `depends:`; the message says so when the occasion exists in an installed but inactive plugin) |
| a `target` on an untargeted occasion, or none on a targeted one | `` … raises `cutscene` without a target, but `cutscene` is raised for a target (`scene.<cutsceneId>`) — add `target: "@<attr>"` `` |
| for a domain occasion `{ prefix, entity }`, an `@attr` whose declared type is not `{ entity: <entity> }` (on a reward kind: whose `target:` contract is not `{ entity: <entity> }`) | `` … raises `cutscene` for `@scene`, which is typed `string`; the target of `cutscene` is a `cutsceneId` member, so type the attribute `{ entity: cutsceneId }` `` |
| a literal target outside the occasion's domain shape (`<prefix>.<member>`; `members:` when listed) | `` … raises `cutscene` for `room.office`, but its targets are `scene.<cutsceneId>` `` |

### 4.3 Checks per call and per grant

`E-RAISES-TARGET` (new, error) is reported by the project pass
(`check --project`, beside `check_project_accepts`), at the call's attribute
value for an `@attr` target, at the directive head for a literal, and at the
reward's `target=` (or `kind=`). For each **resolved** target (the attribute's
literal value, the reward's quoted `target=`, or the literal):

- A domain target `<prefix>.<value>` whose value is not a member of the
  project's kind (or of the occasion's `members:`) is `E-RAISES-TARGET` with a
  did-you-mean. (An `@attr` value outside the kind is already `E-ATTR-TYPE`/the
  entity check at the attribute; this case is the `members:` subset.)
- A target that **no** scene or beat answers (no document with `on:` that
  occasion and that target or no `target:`) is `E-RAISES-TARGET`:
  `` `::playScene{scene="chaptr2"}` raises `cutscene` for `scene.chaptr2`, but no scene or beat answers it — did you mean `scene.chapter2`? ``
- A target that is not static (an `@def` that does not fold to a literal, or a
  value reading `occasion.target`) is not judged here. In the graph it stands
  for every answerer of the occasion (§4.5).
- An unbound `@attr`/`@target` (the attribute or `target=` omitted): no raise
  and no extra diagnostic (the directive effect rule, `lower.rs:483-486`;
  `required` already reports).

### 4.4 Meaning (the host contract)

Lute does not execute a raise: raising occasions is a host duty (D13). A
declared raise is a promise about what the host does:

- **Directive.** After the presentation that ran the call ends
  (`presentationEnd`), the host raises each listed occasion for its resolved
  target, in record order and list order, as a `raiseOccasion` input once the
  runtime is idle.
- **Reward.** After settling the grant (the output that carries the `grant`
  record has been applied), the host raises each listed occasion the same way.
- A raise refused by the occasion's gate (`raisedWhen`, the `gate` query) is
  the host's to report; Lute treats a declared raise as *possible*, never as
  guaranteed.
- **`raisedBy: declared`**: the host raises the occasion only through declared
  raises. Without it (the default), the host may raise the occasion at any time
  as before, and a declared raise of it is recorded in the artifact and
  checked (§4.3), but adds no graph edge.

### 4.5 Graph and reachability

- **Raise sources.** A project-root table (D14), built once, lists every
  declared raise with its source node: the scene, bundle beat, entry or quest
  whose body contains the call (components counted at their `::use` sites, as
  `accept_sources` does), or the quest that grants the reward. It mirrors
  `accept_sources` (`crates/lute-check/src/connectivity/graph_assembly.rs`).
- **Anchors.** A scene or bundle beat node that answers a `raisedBy: declared`
  occasion and declares no `after:` gets `PrereqState::Anchored`
  (`graph_nodes.rs:448-465`) with one `Anchor { kind: EdgeKind::Raises, from:
  <every source raising that occasion for its target, or with a non-static
  target> }`. A node that declares `after:` keeps `after:` as its declared route,
  and no `[raises]` edge is drawn to it (the quest rule, `graph_assembly.rs:404-406`).
- **Reachability** (`connectivity/reachability.rs:249-266`): as for every
  anchor, `Unreachable` reads `Unknown`. A declared raise is a host promise,
  not a proof.
- **Edges.** `EdgeKind::Raises` (`graph_nodes.rs:504-540`, token `raises`) is
  drawn `source -> answerer`. An edge that would close a cycle is not drawn (the
  `[accept]` rule, `graph_assembly.rs:243-246`), so a scene that raises its own
  occasion again is never `E-CONN-CYCLE`. Raise anchors do not gate a start and
  do not join start-cycle detection (`start_cycles.rs`, unchanged).
- **CLI.** `lute scenario` text: `scene(intro) -> scene(chapter2) [raises]`;
  `--json`: `"kinds": ["raises"]`; dot: a solid edge labelled `raises`.
  `lute scenario reach` and `lute impact` follow the edge with no other change.
  The `scenario` node envelope names the raise
  (`` raised by `::playScene` in scene `intro` ``).
- **`W-OCCASION-NEVER-RAISED`** (new, warning, project-wide), the analogue of
  `W-QUEST-NEVER-ACCEPTED` (`accept.rs:234-264`): for each document answering a
  `raisedBy: declared` occasion (for a target) that no declared raise names
  (statically for that target, or with a non-static target), at the document's
  `on:`:
  `` scene `chapter2` answers `cutscene` for `scene.chapter2`, which `acme.stage` declares `raisedBy: declared`, but no `effects.raises` in the project raises it — add a `raises` entry to the directive or reward kind that leads here, or drop `raisedBy: declared` if the host raises `cutscene` on its own ``.
  A `lute play`/`lute test` step that raises the occasion is no source (a test
  proves a test, not the game; the dsl 0.25.0 D-C rule).

## 5. Localizable directive text (#165)

### 5.1 Manifest: `type: text`

```yaml
directives:
  - name: banner
    attrs:
      - { name: title,    required: true, type: text }
      - { name: subtitle, type: text }
      - { name: style,    type: { enum: [toast, card] } }
```

- `lute_manifest::types::Type` (`types.rs:11-36`) gains `Text`, spelled `text`.
  It prints only where declared, so no existing `capabilitySnapshot` moves.
- **Admitted only** as the type of a directive attribute (`attrs:`) of a
  directive that compiles to a `plugin` record: no `lower:` of any kind and no
  `bridge:`. Load faults (`E-PLUGIN-PARSE`, at the attribute):
  - `text` on a directive with `lower:` (a staging record, a builtin) or with
    `bridge:`: `` `title` of `::banner` is `text`, but `::banner` lowers to the `actor` record, which carries no localized text — declare it `string`, or drop `lower:` so the call stays a `plugin` record ``;
  - `text` with `default:` (an untranslatable source);
  - `text` anywhere else the type grammar is read — a stamp (`stampAttrs`),
    plugin `options:`, an occasion `payload:`, reward-kind `attrs:`, bridge
    results, `{ list: text }` — each place's existing invalid-type diagnostic,
    naming the one place `text` is admitted;
  - a directive with a `text` attribute that also declares an attribute named
    `code` (`code` is the identity attribute of such a directive, §5.3).
- A scoped stamp (0.50.0 §3.2) named `code` on a directive with a `text`
  attribute is shadowed by that core attribute: `E-PLUGIN-RESERVED-STAMP-ATTR`.

### 5.2 Authoring and checking

```lute
::banner{code="0010" title="Welcome to the hall, {{playerName}}" style="card"}
```

- A `text` value is a quoted string in the **choice-label grammar**: `{{…}}`
  interpolations of state paths, `@def`s and host tokens (0.50.0 §4) with their
  modifiers, and `\{{` for a literal brace (`scan_label_interps`,
  `crates/lute-syntax/src/ast.rs:830`). Inline markup is not parsed, as in a
  label. Each interpolation is checked as a label's is (definite assignment
  `check_label_reads`, `defassign.rs:952`; modifier typing; `E-CEL-PROFILE` for
  an undeclared token).
- An `@ref` value (`title=@greeting`) is `E-ATTR-TYPE`: `` `title` of `::banner` is localizable `text`, written as a quoted string; a `@def` value has no translation of its own ``.
- **`code=`** is admitted on a directive with at least one `text` attribute, as
  on a content line: a string, trimmed. On any other directive `code` stays
  `E-UNKNOWN-ATTR`.

### 5.3 Identity

- **`lineId`** of a `text` attribute is
  `render_line_id(prefix, tag, code) + "." + attr`
  (`IdentityTemplates`, `crates/lute-manifest/src/project.rs:804-827`): with the
  default template `{prefix}.{tag}_{code}.{attr}`, e.g. `intro.banner_0010.title`.
  `prefix` is the line prefix of the enclosing identity scope, component
  instance segments included, exactly as for a line (`address.rs:297-369`).
  The `.attr` suffix keeps it apart from any line id. Position is never
  identity (D8).
- **Codes.** `assign_identity_scope` (`address.rs:297`) keeps per-scope counters
  per directive tag, in a keyspace separate from speakers (a `DirectiveTag`
  owner, never a speaker string). An untagged directive gets the next code (max
  authored + 10, `{:04}`), as a line does. A directive's code reaches the
  artifact only inside `localized.<attr>.lineId`: `code` is never written to
  `fields` (the rule that keeps stamps out of `fields`, `lower.rs:453`), and
  `PluginCmd` gains no serialized `code` field (the authored code rides a
  `#[serde(skip)]` field from lowering to addressing).
- `lute tag` (`crates/lute-check/src/tag.rs`, `tag_document` `:27`,
  `retag_document` `:294`) writes `code="…"` into every untagged directive that
  has a `text` attribute, with the same back-fill order the compiler uses (a
  test asserts both agree). `codes_locked` (`:462`) applies.
- **`E-DUP-LINE-CODE`** (existing, `match_check/line_codes.rs`) gains the site
  "two `::banner` calls in one scope share `code`"; message: `` `::banner` calls at lines N and M share `code="0010"`; a (directive, code) pair is the localization identity of its `text` attributes ``.
- **`W-LINE-CODE-UNTAGGED`** (with `identity.requireStable`) applies to such a
  directive without `code`.

### 5.4 IR

- `PluginCmd` gains
  `localized: BTreeMap<String, LocalizedText>`, `skip_serializing_if =
  "BTreeMap::is_empty"`, keyed by attribute name, with

## 6. Lint `target: pair` (#172)

### 6.1 Declaration

```yaml
lints:
  - id: group-balanced
    target: pair
    open:   'node.tag == "group" && "mode" in node.attrs && node.attrs["mode"] == "begin"'
    close:  'node.tag == "group" && "mode" in node.attrs && node.attrs["mode"] == "end"'
    inside: 'node.kind == "line" || node.tag in ["actor", "sfx"]'   # optional
    scope: body                                                    # body (default) | section
    level: error
    message: "::group begin/end"
```

- `lute_manifest::lint::LintTarget` (`lint.rs:81`) gains `Pair`. A rule's body
  becomes an enum: `Predicate { when }` for every other target and
  `Pair(PairSpec { open, close, inside: Option, scope: PairScope })` for `pair`.
  The `LintRuleDecl` (`lint.rs:42`) loader enforces the shape: on `pair`, `open`
  and `close` are required and `when` is refused; on every other target,
  `open`/`close`/`inside`/`scope` are refused. A fault is `E-PLUGIN-PARSE` in a
  plugin's `lints:` and `E-LINT-CONFIG` in `lute.lint.yaml` `custom:`.
- `open`, `close` and `inside` are lint-CEL predicates over the 0.50 `node` row
  (0.50.0 §8.1), with the `scene` and `options` bindings and the 0.50 string
  members. Missing keys keep CEL semantics (`E-LINT-EXPR`); the recipes guard
  every index (0.50.0 §8.1).

### 6.2 Evaluation

- **Scope `body`**: each body's direct children, in order (the rows' siblings).
  **Scope `section`**: every row of one section or declaration in document
  order, at every depth (the unit that resets `node.preceding`, 0.50.0 §8.1).
  `section` is document order, not paths: an `open` in one `<choice>` and a
  `close` in its sibling pair up.
- For each scope, one pass with one open slot:
  - a row for which `close` holds while a pair is open closes it (a row that
    satisfies both `open` and `close` is a close while a pair is open, an open
    otherwise);
  - a row for which `open` holds while a pair is open is a **nested open**; the
    outer pair stays open;
  - a row for which `close` holds with no pair open is an **unopened close**;
  - with `inside`, every row strictly between an open and its close (scope
    `body`: siblings only, not their descendants) for which `inside` is false is
    an **inside fault**;
  - at the end of the scope, an open pair is an **unclosed open**.
- **Findings** carry the rule's code and level, anchor at the offending row's
  span, and append a fixed `PairFault` phrase to the rendered `message`:
  - unclosed: `` — opened here, with no close in this body `` (`section` scope: `in this section`);
  - unopened: `` — a close with no open pair in this body ``;
  - nested: `` — opened again while the pair from line N is still open ``;
  - inside: `` — not allowed inside the pair opened at line N ``.

  `related` names the open row for nested and inside faults.
- The pass is linear in the rows and evaluated in the 0.50 metrics walk while
  the scope view is valid (0.50.0 §8.1 "Cost"); no row is copied.
