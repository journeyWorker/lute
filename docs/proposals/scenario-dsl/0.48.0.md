# Lute 0.48.0 — CLI grammar cutover

This is the normative 0.48.0 contract. The words **MUST**, **MUST NOT**,
**SHOULD** and **MAY** have their RFC 2119 meanings. It applies
[`docs/design/cli-grammar.md`](../../design/cli-grammar.md) (the grammar) to
every `lute` command in one release, following the 0.47.2 → 0.48 mapping and
the orchestrator choices in the
[decision note](../../superpowers/notes/2026-10-19-lute-0.48-decisions.md).
It is a clean cutover (ADR D6): every caller in this repository — tests,
conformance harnesses, scripts, CI, examples and documentation in English and
Korean — migrates in the same change, and no alias is kept.

## 1. Scope and version contract

Every public version axis is `0.48.0`: toolchain, `luteVersion`, `irVersion`,
`eventVersion`, `snapshotVersion`, the seven npm packages and the generated
contracts. The contract schemas move to the `0.48` line
(`schemas/lute-{ir,events,snapshot,player-bindings}-0.48.schema.json`),
`bindingsVersion` and the player save/profile format to `"0.48"`.

| Axis | 0.48.0 contract |
|---|---|
| Language | No syntax or semantic change. |
| IR / Event / snapshot | Shapes unchanged; schema files renamed to the `0.48` line (stamps and `$id` only). Description text that names a command (`compile --all`, `check-project`) uses the 0.48 spelling. |
| Player bindings | Shape unchanged; `bindingsVersion: "0.48"`. |
| CLI | The grammar (§2–§8): one command per action, `--project` everywhere, one option name per concept, `--json` on every reporting command, `tag --renumber` previews, removed spellings answer with the replacement, a CI test over `lute schema`. |
| npm | Seven packages publish `0.48.0` in lockstep; no TypeScript API change. Package scripts that run `lute` use the 0.48 spelling. |

Behaviour other than the command line MUST NOT change: for every command line
the 0.47.2 → 0.48 mapping (§5) translates, the output is byte-identical to
0.47.2 after stamp normalization except for the classes §10 lists.

## 2. Shared rules

### 2.1 The project

- Every command that works on a project takes it as `--project <DIR>` and
  only that way; no command takes the project as an operand or under another
  name.
- **Discovery.** When `--project` is absent the project is the nearest
  ancestor directory containing `lute.project.yaml`, starting at the
  directory of each file operand for `check`, `compile`, `context` and
  `trace` (per file), else at the current directory. The discovered
  directory is used exactly as if it had been passed with `--project`
  (in particular `compile <FILE>` and `trace <FILE>` gate on the reconciled
  project verdict and `trace` uses the project's single-root producer set,
  as an explicit `--project` did in 0.47.2). The stderr note `lute: note:
  using project <DIR> (nearest lute.project.yaml); pass --project to choose
  another` is kept for the file commands that printed it, once per distinct
  project.
- **The project directory as walk root.** For every command that 0.47.2 gave a
  directory operand, `--project <DIR>` (explicit or discovered) means exactly
  what that operand meant: the walk root, with each document (or script)
  resolving against its nearest project at or below `<DIR>` — nested projects
  keep their own documents, and a directory without `lute.project.yaml` is a
  workspace whose documents resolve against their own projects, else
  core-only. Old `cmd <DIR>` ≡ new `cmd --project <DIR>`. Discovery itself
  only ever yields a directory with a manifest.
- **None found.** With no `--project` and no ancestor manifest, a command that
  needs a project (whole-project `check`, `compile` without a document,
  `impact`, `constraints`, `patch`, `play`, `test`, `loc export`, `loc
  report`, `scenario` and its subcommands, `beats`, `calendar`, `lore`,
  `refs`, `expr`) MUST fail with `E-CLI-USAGE`, `argument: "--project"`,
  message `lute <command>: no lute.project.yaml at or above <dir> — pass the
  project directory with --project <DIR>`. `check <FILE>…`, `compile
  <FILE>`, `context`, `trace`, `lint`, `fmt`, `fix`, `tag`, `new` and
  `doctor` keep their 0.47.2 behaviour without a project.
- `init [<DIR>]` is the exception: its operand is the directory to create
  (default `.`).

### 2.2 Shared option groups

Options for one concept MUST be declared once, as a `clap` `Args` struct
flattened into each command that takes them (one help text, one value name).
The project options are three single-option structs, so a command takes
exactly the ones that can change its result:

| Group | Options | Commands |
|---|---|---|
| Project | `--project <DIR>` | every command that works on a project (§2.1) |
| Providers | `--providers <DIR>` | `check`, `compile`, `context`, `trace`, `expr`, `lint`, `impact`, `constraints`, `patch`, `play`, `test`, `scenario` (global), `beats`, `calendar`, and `catalog refresh` (the directory it refreshes, §3.12) |
| Permission profile | `--permission-profile <NAME>` | `check`, `compile`, `context`, `trace`, `expr`, `patch`, `play`, `test`, `calendar` |
| Diagnostic gate | `--deny <CODE>` (repeatable), `--deny-warnings` | `check`, `compile` (not with `--stream`), `lint` (its own code parser; same names and value name), `trace`, `expr`, `play`, `test`, `calendar` |
| JSON | `--json` | every command that reports a result (§4), except `schema` (always JSON) and `loc export` (an artifact writer, §3.15) |

The commands column is the expected outcome of one rule: a command takes
`--providers` / `--permission-profile` exactly when the option can change its
result, shown by a test that fails without the threading (a profile ceiling
violation refusing with exit `1`, a provider id resolving). Options are
threaded into the project model the command builds (`ModelOptions`,
`build_input`, `apply_patch`, the project gate) where 0.47.2 passed `None`.
An implementer who cannot show an effect for a listed command drops the
option there and records it in the decision note; the commands table
(`docs/design/cli-commands.tsv`, §6) is the result. `--deny*` promotes
diagnostics of the verdict the command exits on: `trace` its check gate
(refusal, exit `1`), `expr` the lowering diagnostics, `play` and `calendar`
the project compile gate, `test` every check verdict a test consults (each
traced document's check and each play's compile gate), so a denied warning
fails that test.

These are amendments to grammar §6 (one project group split into three
single-option structs; `loc export` exempt from `--json`); R3 writes them
into the grammar.

### 2.3 Output

Text is the default everywhere; JSON is produced only with `--json` (§1.1 of
the grammar). No output depends on whether a stream is a terminal or on an
environment variable. With `--json` a command prints exactly one JSON
document on stdout (the 0.43 report envelope, or the 0.43 error envelope on a
usage/I/O/input failure); messages that 0.47.2 printed on stdout move to
stderr in JSON mode. JSON mode (0.43.0 §4.1) is `--json` before `--`, or the
`schema` command; `--format json` no longer exists.

### 2.4 Value placeholders

Every option and operand value name is from grammar §5 (which this release
extends, see the decision note). clap's derived names (`MAX_ITEMS`,
`NODE_ID`, `PATHS`) MUST NOT appear.

## 3. Commands

Synopses below are normative. `[location]` is `--project <DIR>` alone,
`[project]` is `--project <DIR>` plus the providers / permission-profile
options §2.2 gives the command, `[gate]` is
`--deny <CODE>`… `--deny-warnings`. In a synopsis `<OCCASION>[@<TARGET>]`
and `<BRANCH>=<CHOICE>[,<CHOICE>…]` describe the accepted value; the clap
value names are `OCCASION` and `BRANCH=CHOICE`. An option not mentioned
keeps its 0.47.2 spelling, meaning and help.

### 3.1 `check [<FILE>]… [project] [--engine <FILE>] [--wip] [gate] [--json]`

One command for both scopes (grammar §1.3).

- **Documents.** With one or more `<FILE>` operands each document is checked
  exactly as 0.47.2 `check <FILE>` checked it (the same per-document
  analysis; `.yaml`/`.yml` schema operands as before), resolved in its
  project (`--project`, else discovery from that file's directory, per
  file). The help and docs MUST say that relational guard decisions (dead
  guards over relations, `W-WIP`) need the whole-project mode. A directory
  operand is `E-CLI-USAGE` naming `--project` (`lute check: <DIR> is a
  directory — check the whole project with lute check --project <DIR>`). An
  unreadable operand ends the run with exit `2` and the `E-CLI-IO` envelope
  (no report), as 0.47.2 `check` did; operands before it may already have
  printed their text lines.
- **Whole project.** With no operand, every document of the project (§2.1)
  plus the project-wide checks — exactly what 0.47.2 `check-project <DIR>`
  did for the same directory, including nested projects grouped by their own
  manifests. `--wip` is valid only here; with document operands it is
  `E-CLI-USAGE` (`argument: "--wip"`).
- **Text.** Document mode prints each document as 0.47.2 `check` did, in
  operand order. Whole-project mode prints what 0.47.2 `check-project`
  printed.
- **Exit.** `0` clean, `1` any error (or `--deny` promotion), `2`
  usage/I/O — as before in both modes.
- **Report** `0.48.0.check` (both modes), schema
  `schemas/lute-check-report-0.48.schema.json`:

```json
{
  "command": "check",
  "schemaVersion": "0.48.0.check",
  "ok": true,
  "files": [
    {"path": "scenes/a.lute", "ok": true, "diagnostics": [], "resolved": {"commands_preview": [], "injections": [], "timeline_tables": []}}
  ],
  "project_diagnostics": []
}
```

  `files[]` has one entry per document checked, in the order checked; each
  entry is the 0.47.2 `check-project` file entry (`path` as given or walked,
  `ok` after `--deny`, the `CheckResult` `diagnostics` and `resolved`, which
  is `null` for a schema operand). `project_diagnostics` (each a diagnostic
  plus `path`) is present exactly when the whole project ran, in the 0.47.2
  order. `ok` follows 0.43 §3.2. Runs that 0.47.2 ended with exit `1` and no
  JSON MUST print this report in JSON mode: an invalid manifest in
  whole-project mode gives `files: []` and the manifest diagnostics in
  `project_diagnostics` (with `path` = the manifest); a plugin/profile
  resolve error for a document gives that document's entry with `ok: false`
  and the resolve diagnostics in its `diagnostics`. The report schema MUST be
  checked against real `lute check --json` output of both modes in CI.

### 3.2 `compile [<FILE>] [project] [-o, --output <PATH>] [--locale-bundle <FILE>] [gate] [--json] [--stream]`

- `compile <FILE>` compiles one document to stdout or `-o <FILE>`, as 0.47.2.
- `compile` with no document operand compiles every document of the project
  (§2.1) into `-o <DIR>` plus `project.index.json` — what 0.47.2 `compile
  --all <DIR> -o <DIR>` did. `-o` is required (`E-CLI-USAGE`, `argument:
  "--output"`).
- `--locale-bundle <FILE>` is 0.47.2's `--locales`.
- `compile --stream <FILE>` is 0.47.2's `compile-stream <FILE>`: body text
  from stdin against the prefix, the same NDJSON on stdout, no envelope.
  `--stream` together with `-o`, `--locale-bundle`, `--json`, `--deny`,
  `--deny-warnings`, or without a document is `E-CLI-USAGE` naming the
  conflicting option.
- `lute schema compile` lists the outputs `artifact` (no flag), `report`
  (`--json`, `0.43.0.compile`) and `stream` (`--stream`).

### 3.3 `impact --node <NODE> [project] [--json]`

0.47.2 `impact <DIR> <TARGET>`; `<NODE>` is the target key as before.

### 3.4 `constraints [project] [--script <FILE>]… [--all-scripts] [--json]`

`--all-scripts` is 0.47.2's `--run` (execute every `*.play.yaml` and
`*.test.yaml` of the project for witnesses); `--script <FILE>` (repeatable)
executes only the named scripts — a directory selects every script under
it. The two are exclusive (`E-CLI-USAGE`).

### 3.5 `lint [<PATH>] [project] [gate] [--config <FILE>] [--json]`

As 0.47.2 without `--project`. With `--project <P>`: no `<PATH>` means `<P>`;
each document resolves against its nearest project at or below `<P>` (`<P>`
is the walk floor, as for every directory command); each root's
`lute.lint.yaml` applies unless `--config` names one.

### 3.6 `expr <EXPR> [project] [gate] [--json]`

As 0.47.2 with the operand named `<EXPR>`; `--project` defaults to discovery
from the current directory (0.47.2: the current directory itself).

### 3.6a `patch <FILE> [project] [--dry-run] [--json]`

0.47.2 `patch <DIR> <PATCH>`: the operand is the patch request; the project
is `--project` or discovery from the current directory. Providers and the
permission profile reach `apply_patch` (`lute-model`), which 0.47.2 built
with default options. Two operands are `E-CLI-USAGE` naming `--project`.

### 3.7 `tag [<PATH>]… [--renumber [--commit]] [--check] [--json]`

- Default (no `--renumber`): back-fill missing codes and instance keys, as
  0.47.2 `tag`, writing files.
- `--renumber`: the dangerous mode (grammar §1.2). With `--commit` it is
  exactly 0.47.2's `--force` (including, for a `codesLocked:` document, the
  refusal of the code renumber with exit `1` while missing component
  instance keys are still added). Without `--commit` it MUST write nothing and
  print what `--commit` would do — one line per changed code `<path>:<line>:
  <old or (none)> -> <new>`, one line per file that would get instance keys,
  each refusal as 0.47.2 printed it — then `lute: would renumber <N> line(s)
  in <M> of <T> file(s); pass --commit to apply`; exit `0`, or `1` when a
  file is refused (as `--commit` would).
- `--check`: write nothing; exit `1` when the selected mode would change any
  file, else `0` (a refusal is still `1`). `--commit` without `--renumber`, or
  with `--check`, is `E-CLI-USAGE`.
- Report `0.48.0.tag`: `{mode: "tag"|"renumber", applied, files: [{path,
  changed, lines, instances, refused?, renumbered?: [{line, from, to}]}]}` —
  `applied` is `true` only when files were written; `lines` the number of
  codes added or renumbered, `instances` the number of instance keys added;
  `refused` the refusal message; `renumbered` only in renumber mode, `from`
  `null` for a line without a code. The per-line data comes from
  `lute_check::tag` (R3 extends `RetagOutcome`).

### 3.8 `fix [<PATH>]… [--check] [--json]`

As 0.47.2 (`.lute` and project/schema/plugin YAML, directories recursive).
`--check` writes nothing and exits `1` when any fix applies. Report
`0.48.0.fix`: `{applied, files: [{path, changed, fixes}]}`, `fixes` the
count 0.47.2 printed.

### 3.9 `context <FILE> [project] [--node <NODE> | --at <FILE>:<LINE>:<COLUMN>] [--max-items <N>] [--script <FILE>]… [--all-scripts] [--json]`

`--node` is 0.47.2's `--target` (report `0.36.0.context`, output flag
`--json --node`); `--script` (repeatable) is `--run` — a file, or a
directory selecting every script under it, as before; `--all-scripts`
executes every play/test script of the project. `--script` and
`--all-scripts` are exclusive (`E-CLI-USAGE`).

### 3.10 `fmt [<PATH>]… [--check] [--json]`

Report `0.48.0.fmt`: `{applied, files: [{path, changed}]}` over every
selected file.

### 3.11 `trace <FILE> [project] [gate] … [--choice <BRANCH>=<CHOICE>[,<CHOICE>…]] [--accepted-quest <QUEST>] [--occasion <OCCASION>[@<TARGET>]] [--fact <ATOM>] [--entry <ID> | --beat <ID>] [--json]`

`--choice` is `--choose`, `--accepted-quest` is `--accept`; values and
meaning unchanged. The permission profile is threaded (0.47.2 passed none).
The hidden `--target` refusal is removed with `--on` (§5).

### 3.12 `catalog refresh [location] [--providers <DIR>] [--json]`

`--providers <DIR>` is the snapshot directory to refresh (0.47.2's operand),
default the project's `catalogDir` (default `catalog/`); the project
(`--project` or discovery) stamps them — inside a project the stamp is now
the project's multi-plugin version where 0.47.2 without `--project` stamped
the core baseline. With neither a project nor `--providers`: `E-CLI-USAGE`
naming `--providers`. Report `0.48.0.catalog-refresh`: `{providers,
capabilitySnapshot, refreshed: [path], skipped: [{path, reason}]}`.

### 3.13 `init [<DIR>] [--template <NAME>] [--json]` and `new`

- `init` defaults to `.`. It MUST refuse (exit `2`, nothing written) when
  any file it would write already exists, naming it (0.47.2 refused only an
  existing `lute.project.yaml`). Its "Next steps" and generated README use
  0.48 command lines. Report `0.48.0.init`: `{dir, template, files: [path]}`.
- `new scene <NAME> [location] [--occasion <OCCASION>] [--target <TARGET>]
  [--json]`, `new quest <NAME> [location] [--start] [--json]`, `new lore
  <NAME> [location] [--json]`, `new schema <NAME> [location] [--json]`.
  The project is `--project` or discovery from the current directory; an
  explicit `--project` that is inside a project but not its root keeps the
  0.47.2 refusal (naming `--project`). Report `0.48.0.new`: `{kind, id,
  path}`.

### 3.14 `doctor [location] [--strict] [--json]`, `run`, `play`, `test`

- `doctor`: the project replaces the directory operand; with none found it
  reports the missing manifest as before; the document scan walks the
  project directory.
- `run <FILE> [--engine <FILE>] [--mock <FILE>] [--occasion
  <OCCASION>[@<TARGET>]] [--entry <ID> | --beat <ID>] [--conditions-output
  <FILE>] [--json]`: `--occasion` accepts the same value grammar as
  `trace` (a targeted raise); `--conditions-output` is `--dump-conditions`.
- `play [project] --script <FILE> [--engine <FILE>] [--events | --json]
  [--no-derive] [--derivation <ATOM>]… [--ir] [--quiet]
  [--conditions-output <FILE>] [gate]`: `--derivation` is play's
  `--explain`.
- `test [<PATH>]… [project] [--coverage] [--no-derive] [gate] [--json]`:
  operands select test/play scripts — a script file, or a directory walked
  for `*.test.yaml` and expectation `*.play.yaml`; no operand walks the
  project directory (grammar §1.3). Each script resolves against its nearest
  project at or below the project directory (§2.1) — 0.47.2's resolution
  without `--project`; 0.47.2's forced single-root resolution under an
  explicit `--project` is gone. Coverage is over the project directory.

### 3.15 `loc`, `lore`, `refs`, `scenario`, `beats`, `calendar`

- `loc export [location] [--format <FORMAT>] [-o, --output <PATH>]`:
  `--format csv` selects CSV, JSON is the default; `--format json` is
  `E-CLI-USAGE` (omit it). `loc import <FILE>… [-o, --output <PATH>]
  [--json]`: report `0.48.0.loc-import` `{output, locales, lines, skipped,
  diagnostics: [{path, code, message}]}`; `--json` requires `--output`.
  `loc report [location] [--json]`.
- `lore [location] [--json]`, `refs [location] [--attr <DIRECTIVE>.<ATTR>]
  [--reward <KIND>] [--json]`.
- `scenario [project] [--format <FORMAT>] [--json] [--facts]`, `scenario
  reach [--node <NODE> | --endings[=<OCCASION>]]`, `scenario envelope --node
  <NODE>`, `scenario knowledge [--node <NODE>]`. `--format` is `text` or
  `dot`; `--json` replaces `--format json` with the same reports and
  versions (`0.43.0.scenario*`). `--json` with `--format` is `E-CLI-USAGE`.
- `beats [project] [--occasion <OCCASION>]… [--target <TARGET>]… [--expand]
  [--json]`.
- `calendar [project] [gate] [--axis <AXIS>=<VALUES>]… [--occasion
  <OCCASION>]… [--occasion-axes <OCCASION>=<AXES>]… [--relation
  <RELATION>]… [--target <TARGET>]… [--script <FILE> [--until <STEP>]]
  [--where <EXPR>] [--format <FORMAT>] [--json]`: `--relation` is
  `--facts`; `--format csv` is `--csv` (`text` default); `--occasion-axes
  O=<AXES>` is 0.47.2's `--occasion O@<AXES>` with `<AXES>` unchanged (it
  selects `O`); naming the same occasion in `--occasion` and
  `--occasion-axes`, or twice in `--occasion-axes`, is `E-CLI-USAGE`;
  `--json` with `--format` is `E-CLI-USAGE`.

### 3.16 Unchanged

`diff <BEFORE> <AFTER> [--json]`, `version [--json]`, `schema
[<COMMAND>]…`, `lute --explain <CODE>`.

## 4. Reports

The outputs table (`envelope.rs`, read by `lute schema`) MUST list every
machine-readable output with its version: the 0.47.2 rows with
`check-project` and `compile-stream` removed, `check` → `0.48.0.check`,
`compile` gains the `--stream` stream, `context`'s node report is selected
by `--json --node`, `scenario*` reports by `--json`, `loc export`'s artifact
has no flag (JSON) and `--format csv`, and the new rows `tag` `0.48.0.tag`,
`fix` `0.48.0.fix`, `fmt` `0.48.0.fmt`, `catalog refresh`
`0.48.0.catalog-refresh`, `init` `0.48.0.init`, `new scene`, `new quest`,
`new lore`, `new schema` `0.48.0.new`, `loc import` `0.48.0.loc-import`.
Every other report keeps its version. `schema` moves to `0.48.0.schema`: an
option whose value is optional (`--endings[=<OCCASION>]`) carries
`valueOptional: true`, which the §6 arity rule reads. The mapping's "no `--json`" row lists `compile-stream`; the
stream folds into `compile --stream`, where `--json` is a conflict (§3.2).

## 5. Removed spellings

Each removed spelling MUST be `E-CLI-USAGE` (exit `2`; the error envelope in
JSON mode with `argument` = the removed spelling and `hint` = the
replacement) whose message names the replacement and, where the rest of the
command line allows, the full rewritten command
(`lute check-project docs/x` → ``lute check-project is now `lute check
--project docs/x` ``). This holds for one minor release (grammar §7). A
removed command is not a command: its error envelope has `command: null`
and telemetry records no command id for it (`envelope::command_id_in`,
`telemetry.rs`).

| Removed | Replacement |
|---|---|
| command `check-project [<DIR>]` | `check --project <DIR>` |
| command `compile-stream <FILE>` | `compile --stream <FILE>` |
| `compile --all` | `compile --project <DIR> -o <DIR>` (no document) |
| `--out` (`compile`, `loc export`, `loc import`) | `-o, --output` |
| `compile --locales` | `--locale-bundle` |
| a project directory operand (`impact`, `constraints`, `patch <DIR> <PATCH>`, `doctor`, `play`, `test`, `loc export`, `loc report`, `beats`, `calendar`, `scenario`, `lore`, `refs`) and `check <DIR>` | `--project <DIR>` |
| `catalog refresh <DIR>` | `--providers <DIR>` |
| `new <KIND> <NAME> --dir <DIR>` | `--project <DIR>` (`new <kind> <NAME>` itself still parses: the kinds are subcommands) |
| `impact <DIR> <TARGET>` | `--project <DIR> --node <TARGET>` |
| `context --target`, `--run` | `--node`, `--script` |
| `constraints --run` | `--all-scripts` |
| `scenario reach <NODE>`, `scenario envelope <NODE>`, `scenario knowledge --for` | `--node <NODE>` |
| `scenario --format json` | `--json` |
| `play --explain`, `--dump-conditions` | `--derivation`, `--conditions-output` |
| `run --dump-conditions` | `--conditions-output` |
| `trace --choose`, `--accept` | `--choice`, `--accepted-quest` |
| `calendar --facts`, `--csv`, `--occasion O@<AXES>` | `--relation`, `--format csv`, `--occasion-axes O=<AXES>` |
| `loc export --format json` | (omit: JSON is the default) |
| `tag --force` | `--renumber --commit` |

The hidden `--on` refusals of `trace`, `beats`, `calendar` and `new`, and
`trace`'s hidden `--target` refusal, are removed (plain unknown-argument
errors; grammar §7).

## 6. Enforcement

`crates/lute-cli/tests/cli_grammar_048.rs` walks `lute schema` (every command
and subcommand) and MUST fail when:

1. an option name is not lowercase kebab-case;
2. one option name has two value names, or two arities, across commands
   (arity: `takesValue`, and whether the value is optional);
3. an option is missing from `docs/design/cli-vocabulary.tsv` (option, value
   name or `-`, concept), or a vocabulary row is unused;
4. a placeholder token (the uppercase words of a value name) is outside
   grammar §5;
5. a valued option's name is a denylisted verb (`choose`, `accept`, `run`,
   `explain` below the top level, `dump-*`, `out`);
6. a command's options differ from its row in `docs/design/cli-commands.tsv`
   (command id → `--project` yes/no, `--providers` yes/no,
   `--permission-profile` yes/no, `--json` yes/exempt, gate yes/no), or a
   command is missing from that file or a row is unused;
7. a short alias other than `-o` (and clap's `-h`/`-V`) exists.

The checks run over a directory of `lute schema` dumps when

## 9. Breaking changes and migration

The removed spellings of §5, plus:

| Class | Change | Migration |
|---|---|---|
| Project discovery | Without `--project`, a command uses the nearest `lute.project.yaml` above the file operand (or the current directory) exactly as if it had been passed: `compile <FILE>` and `trace <FILE>` inside a project now use the project verdict (in the 0.47.2 corpus three documents a single-file check refused with `E-MAYBE-UNSET` now compile, and their trace exits `3` instead of `1`); `expr` discovers upward; directory commands need a project or `--project`; `new`, `test` and `doctor` run from a project subfolder act on the whole project (0.47.2 `new` refused there); `catalog refresh` inside a project stamps the project's version. | Pass `--project` explicitly where another project is meant. |
