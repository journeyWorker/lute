# Lute 0.40.0 — runtime R3

This specification is the normative 0.40.0 contract for phase R3 of ADR D13.
It makes the **stage** (background, actors on stage, music, shown CG/video)
runtime state carried in snapshots; makes **timed choice** a language and
runtime rule (the author names the option a timeout takes, the runtime takes
a `timeout` input); adds a project **bindings** file that maps the project's
staging vocabulary to concrete assets, checked by `lute check-project`; and
ships a real web visual-novel **player**: `@lute-lang/player` (presenter-free
core: Effect 4, XState v6, a cue scheduler, saves, read history, backlog,
auto/skip, rollback) and `@lute-lang/player-web` (PixiJS 8 renderer, Web
Audio, screens, input), plus a playable demo game.

The words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

## 1. Scope and version contract

All visible version axes are `0.40.0` (`docs/versioning.md` alignment rule):
toolchain, language, IR, Event, and the npm packages, released in lockstep
(`@lute-lang/lute`, the platform packages, `@lute-lang/runtime`, and the new
`@lute-lang/player` and `@lute-lang/player-web`).

| Axis | Change in 0.40.0 |
|---|---|
| Language | `<branch default="…">` names the option a timeout takes; `timeout` and `default` require each other (§2.1). `musicPlayback` domains gain `stops:` (§2.2). |
| IR | `ChoiceCmd.default` (present iff `timeout`), `MusicCmd.stop` (§3). `schemas/lute-ir-0.40.schema.json`. |
| Event | runtime stage in the snapshot and the `stage` query (§4.1–4.2); `timeout` input (§4.3); `awaitChoice.menu.timeout` / `default` populated (§4.4); `E-RUNTIME-TIMEOUT`. Schemas `lute-events-0.40` / `lute-snapshot-0.40`, generated from Rust as in 0.39. |
| Project files | optional `player.bindings.yaml` with a generated schema `schemas/lute-player-bindings-0.40.schema.json`, validated by `lute check-project` (§5). |
| CLI | byte-identical to v0.39.0 except stamps and the deliberate changes of §12. |
| npm | new `@lute-lang/player`, `@lute-lang/player-web` (§6–§8); `@lute-lang/runtime` gains `stage` and the `timeout` input. |

Out of scope: concurrent presentations (owner 2026-10-11: after R3); the C ABI;
3D / engine presenters (hosts build them against the same core); a timed
`<hub>` (a hub has no timeout, unchanged since 0.11.1); snapshot migration
across content versions.

## 2. Language

### 2.1 Timed choice: `default`

`<branch>` gains `default="<choice id>"`, naming the option a timeout takes:

```lute
<branch id="door" prompt="Open it?" timeout="10" default="wait">
  <choice id="open" text="Open the door">…</choice>
  <choice id="wait" text="Wait">…</choice>
</branch>
```

1. `timeout` and `default` MUST appear together. `timeout` without `default`,
   or `default` without `timeout`, is `E-BRANCH-DEFAULT`. (0.11.1 left expiry to
   the engine; from 0.40 a timed branch always names its outcome.)
2. `default` MUST name a `<choice id>` that is a direct option of this branch
   (`E-BRANCH-DEFAULT`, with a did-you-mean over the branch's option ids).
3. The named option MUST NOT carry `when` (`E-BRANCH-DEFAULT`): it is always
   open, so a timeout always has an outcome.
4. `timeout` keeps its 0.11.1 rule (positive whole seconds, `E-BRANCH-TIMEOUT`).
   `<hub>` still admits neither `timeout` nor `default` (`E-UNKNOWN-ATTR`).

All four `E-BRANCH-DEFAULT` cases are errors with distinct messages. The
checker's closed `<branch>` attribute set gains `default`, and
`E-BRANCH-DEFAULT` is registered in the diagnostics catalogue
(`lute --explain E-BRANCH-DEFAULT`). The LSP offers the branch's option ids
when completing `default`.

### 2.2 `musicPlayback` stops

The long form of the reserved `musicPlayback` domain gains `stops:`, a list of
its members that end the current music:

```yaml
enums:
  musicPlayback: {members: [start, change, stop, fadeOut], stops: [stop, fadeOut]}
```

`stops` is admitted only on `musicPlayback`: elsewhere it is
`E-ENUM-UNEXPECTED-SEMANTICS`, as `exits` off `action`; an entry that is not a
member is `E-ENUM-STOPS-NOT-MEMBER` (new, beside `E-ENUM-EXITS-NOT-MEMBER`).
Unlike `action.exits`, `stops` is optional: no `E-ENUM-MISSING-SEMANTICS`. A
`::music{playback=…}` whose value is a `stops` member lowers with
`stop: true` (§3). A project that declares no `stops` never stops music in the
runtime stage.

## 3. IR 0.40

- `ChoiceCmd` gains `default: string` — the option id of §2.1 — emitted iff
  `timeout` is emitted.
- `MusicCmd` gains `stop: true`, emitted iff the playback member is a
  `stops` member (§2.2); omitted otherwise.
- No other field changes. `schemas/lute-ir-0.40.schema.json` is the 0.39
  schema with these two fields; engines gate on `irVersion` `0.40`.

## 4. Runtime and the Event contract 0.40

`EVENT_VERSION`, `eventVersion` and `snapshotVersion` are `0.40.0`. The
contract types stay the single definition in Rust; the schemas and the
TypeScript `Contract` module are regenerated (0.39 §3).

### 4.1 Stage

The runtime world carries a **stage**, serialized in every snapshot
(`world.stage`):

```text
Stage {
  bg:     { location?, time?, assetId? } | null
  music:  { playback?, mood?, volume?, assetId? } | null
  actors: [ { character, anchor?, emotion?, costume? } ]   // entry order
  cg:     { assetId, layout? } | null
  video:  { assetId } | null
}
```

The runtime applies every staging record it executes, in command order,
including compiler-injected records, before the record is emitted:

| Record | Effect on the stage |
|---|---|
| `bg` | `bg` := the record's `location` / `time` / `assetId` (absent members absent) |
| `music` with `stop: true` | `music` := `null` |
| `music` otherwise | `music` := the record's `playback` / `mood` / `volume` / `assetId` |
| `actor` with `exit: true` | the actor with that `character` leaves `actors` |
| `actor` otherwise | upsert by `character`: a new actor is appended; present `anchor` / `emotion` / `costume` replace the actor's; `action`, `posReset`, `preload` change nothing persistent |
| `cg` `display: show` / `hide` | `cg` := `{assetId, layout}` / `null` |
| `video` `display: show` / `hide` | `video` := `{assetId}` / `null` |
| `sfx`, `vfx`, `camera`, `sequence`, `barrier` | none (one-shot cues; camera is not persisted, as since 0.37) |

**Presentation start resets the stage** to empty (all `null`, no actors) for
every beat kind — scene, entry (lore) and bundle beat: the compiler analyses
every presented body against an empty stage (`StageState::default()` for a
scene, an entry body and a bundle-beat body; `crates/lute-compile/src/
stage.rs`, `lib.rs`), so its injected show/hide records assume one. Bodies
that run without a presentation of their own — quest objective bodies and
`<on>` reactions, which the compiler also analyses from an empty stage —
apply their records to the current stage without a reset (an injected show
of an actor already on stage is an upsert). A presentation's end leaves its
final stage in place until the next presentation starts; a snapshot taken at
`idle` carries it.

Timeline records are applied in command order (their compiled order), not at
their timeline time; the stage after a batch is the state the batch's last
cue leaves.

### 4.2 The `stage` query

`Runtime::stage(&state) -> Stage` returns the stage of a state; the wasm
binding gains `Program.stage(state): string` (canonical JSON, 0.39 §4) and
`@lute-lang/runtime`'s `Program.stage(state): Effect<Stage>`. `Session`'s
`SessionState` gains `stage`. A player restores its presenter from this
query after a load or rollback; it never re-derives the stage from records.

### 4.3 The `timeout` input

```json
{"type": "timeout", "request": 3}
```

1. Accepted only while the await is `awaitChoice` whose menu carries
   `timeout` (a timed branch); `request` MUST equal the await's request
   (`E-RUNTIME-REQUEST`). On any other await it is rejected with the new
   **`E-RUNTIME-TIMEOUT`** ("the pending await is not a timed choice"),
   leaving the state unchanged.
2. Its effect and output are exactly those of `choose` with the menu's
   `default` option: the same events, the same next await, the same state.
   Inside the runtime the suspended walk's answer list (the deterministic
   replay continuation, 0.38 §8) records it as the choice of the `default`
   option, so resumption, snapshots and `restore` need no new answer kind.
3. The input log keeps it as `timeout` (what the player sent); replaying a
   log containing `timeout` reproduces the outputs; the CLI's `--events`
   stream prints it as given.
4. Wall-clock time never enters the runtime: the player measures the timeout
   and sends `timeout`.

### 4.4 `awaitChoice` menu fields

`menu.timeout` (integer seconds) and `menu.default` (option id) carry the
command's `timeout` / `default` when present and are omitted otherwise. (In
0.38–0.39 `menu.timeout` existed in the schema but was never populated; it
becomes an integer.)

### 4.5 Rejections

`E-RUNTIME-TIMEOUT` joins `RuntimeRejection` in Rust and as the typed error
`TimeoutUnavailable` in `@lute-lang/runtime`.

## 5. Bindings: `player.bindings.yaml`

A project MAY place `player.bindings.yaml` beside `lute.project.yaml`. It maps
the project's staging vocabulary and assets to files and named player
effects. The Rust types in `lute-manifest` (`bindings` module) are the single
definition: `schemas/lute-player-bindings-0.40.schema.json` is generated from
them (schemars, as for the contract), and `@lute-lang/player`'s Effect
Schema for bindings is generated from that schema (the 0.39 codegen).

```yaml
bindingsVersion: "0.40"
canvas: { width: 1920, height: 1080 }
assets:                      # assetId → file, for every assetId= in the project
  theme: audio/theme.ogg
  door: cg/door.png
backgrounds:                 # bg location → image; optional per-time variants
  foyer: { image: bg/foyer.png, times: { night: bg/foyer-night.png } }
characters:                  # cast id → sprites; optional name colour and voice
  guide:
    sprite: { default: char/guide.png, emotions: { happy: char/guide-happy.png } }
    costumes: { coat: { default: char/guide-coat.png } }
    nameColor: "#e0c080"
anchors: { default: { x: 0.5 }, left: { x: 0.25 }, right: { x: 0.75 } }
actions: { enter: { effect: fadeIn, duration: 0.4 }, leave: { effect: fadeOut, duration: 0.4 }, hop: { effect: hop } }
transitions: { fade: { effect: fade, duration: 0.6 } }
framing: { closeUp: { zoom: 1.35 }, wide: { zoom: 1.0 } }
cameraMove: { shake: { effect: shake, duration: 0.5, strength: 12 } }
cgLayouts: { full: { fit: cover }, inset: { fit: contain, scale: 0.6 } }
textStyles: { emphasis: { fontWeight: bold }, whisper: { alpha: 0.6, scale: 0.9 } }
vfx: { flash: { effect: flash, color: "#ffffff", duration: 0.3 } }
music: { moods: { calm: audio/calm.ogg } }
sfx: { door: audio/door.ogg }
sequences: { doorOpens: { video: video/door-opens.mp4 } }
voice: { pattern: "voice/{voiceKey}.ogg" }
ui: { font: "Noto Sans KR", title: { background: bg/title.png, music: theme } }
flow: { newGame: { occasion: start }, idle: { menu: [ { label: "Foyer", occasion: visit, target: place.foyer } ] } }
```

Keys and values (all sections optional):

- **Domain-keyed sections** — keys MUST be members of the project's declared
  reserved staging domains (`docs/handbook/staging.md`): `anchors`
  (`anchor`), `actions` (`action`), `transitions` (`transition`), `framing`
  (`framing`), `cameraMove` (`cameraMove`), `cgLayouts` (`cgLayout`),
  `textStyles` (`textStyle`), `sequences` (`sequence`), sprite `emotions`
  (`emotion`), `costumes` (`costume`). A non-member key is `E-BINDING-KEY`
  (did-you-mean); a declared member with no binding is `W-BINDING-MISSING`
  (the player falls back to a neutral effect / no sprite change).
- **Cast-keyed section** — `characters` keys MUST be cast ids
  (`E-BINDING-KEY`); a cast member that appears on stage (`::actor`) with no
  binding is `W-BINDING-MISSING`.
- **Usage-keyed sections** — `assets` (keys are `assetId` values),
  `backgrounds` (bg `location` values; `times` keys are bg `time` values),
  `music.moods` (`mood` values), `sfx` (`sound` values) and `vfx` (`type`
  values) are not domains: their source of truth is the values the compiled
  project uses. A used value with no binding is `W-BINDING-MISSING`; a key
  no document uses is `W-BINDING-UNUSED`.
- **Files** are paths relative to `assetsBase` (default `assets/` beside the
  bindings file); a missing file is `E-BINDING-FILE`.
- **Effects** name the player's effect catalogue (§7.4); an unknown effect or
  a parameter it does not take is `E-BINDING-EFFECT`.
- **Flow** names occasions (`E-BINDING-KEY` if undeclared) and targets in the
  occasion's target domain (`E-BINDING-KEY`).
- A malformed file is `E-BINDING-SHAPE`, anchored at the YAML position as
  manifest errors are.

**Loading and checking.** `lute check-project` discovers `player.bindings.yaml`
in the project root (beside `lute.project.yaml`) after it has compiled the
project, and validates it against the project's merged domains, cast and the
compiled documents' staging values; with no file there are no checks.
Single-file `lute check`, `lute compile` and the runtime never read it, and it
is not part of the project fingerprint (it changes no execution). The
diagnostics are registered in the catalogue, anchored at the bindings file's
line and column, and appear in `check-project --json` like any project
diagnostic. The schema is generated by `lute-contract-schema` (which gains the
bindings types from `lute-manifest`, feature `json-schema`), and the
generated-schemas CI step covers it.

## 6. `@lute-lang/player` — player core

The core knows no renderer. It drives a `@lute-lang/runtime` session, paces
its output, and talks to a **presenter** and **audio** through ports. It is
Effect 4 for services, resources, time and I/O, and XState v6 for the
interaction state of the player. Exact pins: `effect@4.0.2`,
`xstate@6.0.0-alpha.65`, `@xstate/effect@0.1.0-alpha.7`.

### 6.1 Ownership

| Concern | Owner |
|---|---|
| story outcome, world, stage, timed-choice outcome, input log | runtime (`@lute-lang/runtime` session) |
| what the player is doing now (reading, typing, waiting, choosing, auto, skip, which screen) | the **progression statechart** (XState) |
| when cues start and finish | the **cue scheduler** (Effect fibers on `Clock`) |
| how cues look and sound | presenter / audio ports (player-web) |
| saves, read history, settings | player stores (Lute-owned formats, §6.7) |

XState snapshots MUST NOT be persisted (owner rule): a save holds a runtime
snapshot plus player data; on load the statechart starts fresh from that
domain state.

### 6.2 Cues — the command pattern

Every runtime record a player acts on decodes (via the generated contract)
into a **cue**: an immutable command object with the record, its `timing`,
and an `execute` that returns an `Effect` completing when the cue's effect
finished. Cue types: `LineCue`, `BgCue`, `ActorCue`, `MusicCue`, `SfxCue`,
`VfxCue`, `CameraCue`, `CgCue`, `VideoCue`, `SequenceCue`, `BarrierCue`, and
`ChoiceRecordCue` / `StateCue` / `PluginCue` (bookkeeping: backlog, no
presentation). Commands are dispatched through a registry keyed by
`family`/`kind`; a record kind the registry does not know is a defect
(contract drift). Every cue supports `execute` (normal), `complete` (jump
to its end state immediately — skip and fast-forward) and `describe` (backlog
and debugging). Presentation events (`presentation`, `presentationEnd`,
`quest`, `clock`) become session cues the host can observe.

### 6.3 The cue scheduler

The scheduler runs one output batch's cues in order on Effect fibers against
`Clock` (so `TestClock` drives tests):

1. A cue without timeline placement starts when the previous blocking cue
   finished. `timing.delay` delays its start. `timing.duration` is handed to
   the presenter as the effect's length. With `timing.wait: true` the next cue
   waits for its completion; without it the cue runs concurrently and the
   scheduler moves on. `sequence` blocks by default (0.37).
2. **Lines always block** until the progression statechart releases them
   (§6.4); voice and typewriter run inside the line cue.
3. **Timelines:** records sharing a `timeline` ordinal form one timeline; each
   clip starts at `at` seconds after the timeline started (plus its `delay`);
   the `barrier` with that ordinal completes when every clip of the timeline
   finished, and blocks (`docs/runtime/timeline-semantics.md`).
4. Before a batch ends the scheduler joins every still-running non-blocking
   cue whose effect is part of the stage (actor, bg, cg, video, music
   transitions) so the stage is settled at an await; one-shot cues (sfx, vfx,
   camera) MAY continue.
5. **Skip / fast-forward**: every cue is `complete`d instead of `execute`d;
   timeline order is kept; nothing waits on the clock.
6. A batch is interruptible: load, rollback or quitting interrupts its fibers;
   the presenter then `restore`s the target stage.

### 6.4 The progression statechart

One XState v6 machine (`playerMachine`) with parallel regions:

- **flow**: `boot → title → loading → playing → ended`, plus `error`.
  `loading` preloads the assets the next batch references (§7.5).
- **story** (inside `playing`): `running` (the scheduler plays a batch) →
  `line` (`typing → shown`) → … → at the batch's await: `choice` (`open`,
  timed: `countdown`), `bridge` (waiting for the host's answer), `idle`
  (flow occasion menu or host raise), `ended`, `halted` (error screen).
- **mode**: `normal | auto | skip`. Auto advances a shown line after the
  configured delay plus the line's voice; skip completes cues while the line
  is read (setting: read-only or all) and stops at choices, at an unread line
  in read-only mode, and at awaits that need the host.
- **overlay**: `none | backlog | menu | saveLoad | settings | confirm`; an
  overlay pauses `story` timers (typewriter, auto, the choice countdown).

Player **actions** (the input vocabulary; §7.6 maps devices to them):
`advance`, `toggleAuto`, `toggleSkip`, `rollback`, `openBacklog`,
`openMenu`, `quickSave`, `quickLoad`, `hideUI`, `choose(optionId)`,
`close`. Actions are the only way input reaches the machine.

Timed choice: entering `choice` on a menu with `timeout` starts a countdown
(paused by overlays); on expiry the player sends the runtime `timeout`
(§4.3) — never a `choose` of its own picking. Choosing earlier sends `choose`.

### 6.5 Backlog, read history, rollback

- **Backlog**: every shown line (speaker display name, text in the current
  locale, `voiceKey`, `lineId`), bounded (setting, default 200), restored
  from saves; a backlog entry MAY replay its voice.
- **Read history**: the set of `lineId`s shown, per project fingerprint, kept
  in the profile (§6.7); it drives read-only skip and the read colour of
  lines.
- **Rollback**: the player keeps the runtime state of each of the last N
  input points (states are immutable, 0.38); `rollback` returns to the
  previous input point, restores the presenter from `stage` (§4.2) and the
  backlog to that point, and re-presents the await. Rolling back past a
  choice lets the reader choose again; the input log is truncated to that
  point.

### 6.6 Bridges and occasions (the host seam)

- `awaitBridge`: the player calls the host's handler for the bridge `tag`
  (`PlayerHost.bridge(tag, request) → Effect<fields>`); with no handler the
  player shows the halted screen naming the tag.
- `idle`: the player follows `bindings.flow.idle`: a `menu` of occasions the
  reader picks (a world map, a day planner), or `raise` (one occasion raised
  automatically); the host MAY override with `PlayerHost.idle`.
- New game raises `bindings.flow.newGame` after `begin`.

### 6.7 Stores and formats

All player formats are versioned JSON with Effect Schemas in
`@lute-lang/player`; persistence goes through Effect's `KeyValueStore`
(browser: IndexedDB-backed, localStorage fallback).

- **Save** `{saveVersion: "0.40", project: <fingerprint>, savedAt, label,
  runtime: <Snapshot 0.40>, log: <inputs since begin>, backlog: [...],
  thumbnail?: <PNG data URL>}` — the stage comes from the snapshot.
  Loading a save of another project fingerprint is refused with the 0.38
  snapshot rule; loading reproduces the stage, backlog and await.
- **Profile** `{profileVersion: "0.40", project, readLines: [lineId…],
  settings}` — settings: text speed, auto delay, skip mode (read/all),
  volumes (master/music/sfx/voice), locale, window opacity.
- Slots: quick save, autosave (at each choice), and numbered slots (default
  24).

### 6.8 Services (Effect)

`LutePlayer` (the facade the host mounts), `PlayerSession` (runtime session
+ log + rollback history), `CueScheduler`, `Presenter` (port), `AudioPort`
(port), `AssetLoader` (port), `SaveStore`, `ProfileStore`, `Bindings`
(decoded bindings), `InputActions` (stream of player actions), `PlayerClock`
(Clock). Expected failures are tagged errors (`BindingsInvalid`,
`AssetMissing`, `SaveIncompatible`, `BridgeUnhandled`, …); contract drift and
broken invariants are defects.

## 7. `@lute-lang/player-web` — PixiJS presenter and the browser app

Exact pins: `pixi.js@8.22.0`, `@pixi/sound@6.0.1`; renderer `webgl`.

### 7.1 Structure

The Pixi `Application` is a scoped resource (init on acquire, `destroy` on
release). The scene graph has fixed layers: `background`, `cg`, `actors`
(inside a `camera` container that framing/moves transform), `video`,
`dialogue`, `choice`, `overlay` (screens), `transition` (full-screen fades).
The canvas letterboxes `bindings.canvas` into its element and scales on
resize.

### 7.2 Entities and behaviours

Every stage object (background, each actor, CG, video, dialogue window) is an
**entity** with a set of **behaviours** — small update objects (`Tween`,
`Fade`, `Crossfade`, `Shake`, `Hop`, `Typewriter`, `Countdown`, …) the
presenter's ticker system advances each frame and removes when finished. A
cue's `execute` attaches behaviours and completes when they finish; its
`complete` snaps them to their end. Entities are created/updated from cues
and rebuilt wholesale by `restore(stage)`.

### 7.3 Text

The dialogue window shows the speaker's display name (cast `name`, the
binding's `nameColor`), the line text in the current locale (`texts` /
`localeSegments` when present), segments with their `styles` mapped through
`textStyles` bindings, per-segment `rate` and `pause`, and a typewriter by
grapheme cluster (text speed setting; `advance` while typing completes the
line). Lines already read are tinted when read-colouring is on.

### 7.4 Effect catalogue

Named effects bindings refer to: transitions `fade`, `dissolve`,
`wipeLeft`, `wipeRight`, `wipeUp`, `wipeDown`, `slideLeft`, `slideRight`,
`cut`; actor actions `fadeIn`, `fadeOut`, `slideIn`, `slideOut`, `hop`,
`shake`, `none`; camera `zoom` (framing), `pan`, `shake`; vfx `flash`,
`shake`, `blur`, `tint`. Each effect declares its parameters (durations,
strengths, colours) in the bindings schema; an absent binding plays a neutral
default (`cut` / `none`).

### 7.5 Assets

`AssetLoader` builds a Pixi `Assets` manifest from the bindings; before a
batch plays, the player loads every asset it references (backgrounds,
sprites for actor emotion/costume, CG, audio, voice) and shows the loading
screen when that takes longer than 150 ms; assets of the previous
presentation unload when a presentation ends.

### 7.6 Input

Keyboard (Enter/Space/click: advance; Ctrl: skip while held; A: auto;
Escape/right-click: menu; mouse wheel up / PageUp: backlog; F5/F9: quick
save/load; H: hide UI; digits: choose), pointer and touch (tap: advance;
long press: menu; swipe up: backlog) and gamepad (A: advance; B: menu; Y:
backlog; RB: skip) map to the player actions of §6.4. The mapping is a
configurable table.

### 7.7 Audio

`AudioPort` via `@pixi/sound`: channels `music` (crossfade on change, fade on
`stop`), `sfx`, `voice` (stopped on advance; auto waits for it); volumes from
settings; a `wait: true` music/sfx cue completes when the sound (or its
fade) ends. Browser autoplay rules: audio starts after the first user gesture
(the title screen).

### 7.8 Screens and the host API

Screens: **title** (new game, continue, load, settings), **game**,
**backlog**, **save/load** (slots with thumbnails), **settings**,
**confirm**. Theme from `bindings.ui`.

```ts
const player = yield* LuteWeb.mount(element, {
  bundle: "/game/bundle/", wasm: "/lute/lute_runtime_wasm_bg.wasm",
  bindings: "/game/player.bindings.yaml", host: { bridge: { minigame: … } },
})
```

`mount` returns a scoped handle (`unmount` releases the renderer, audio and
fibers); a plain-Promise wrapper `mountPlayer(element, options)` exists for
non-Effect hosts and is the only Promise API.

## 8. Demo game

`examples/player-demo/` is a small complete project (title, three scenes,
an occasion menu, a hub, a timed branch with `default`, actors with emotions
and costumes, CG, music, sfx, a timeline, a sequence, a save-worthy quest)
with generated placeholder assets (committed, small: SVG/PNG backgrounds and
sprites drawn by a script, synthesized short audio) and a
`player.bindings.yaml` that `lute check-project` passes with no warnings.
`packages/player-web` serves it in dev (`bun run demo`).

## 9. Tests

- **Runtime (Rust):** stage reduction per record kind and presentation reset;
  stage survives snapshot/restore; `timeout` input acceptance, rejection
  (`E-RUNTIME-TIMEOUT`, `E-RUNTIME-REQUEST`) and equivalence with
  `choose(default)`; menu `timeout`/`default` populated.
- **Conformance:** new session cases `timed-choice` (seed → awaitChoice →

## 11. Performance

Stage reduction is O(records) with no allocation for one-shot cues; the A/B
benchmark gate (15 samples, 1.10) MUST pass against v0.39.0. The player's
frame loop allocates nothing per frame in steady state (behaviours are
pooled); a batch of 200 records schedules in under 2 ms (measured in the
browser test).

## 12. CLI and byte identity

Every CLI output is byte-identical to v0.39.0 except: version stamps; IR
artifacts of projects that author `default` / `stops` (none in the
repository today); `--events` streams whose menus are timed (none today);
snapshots, which gain `world.stage`. `lute play` scripts MAY answer a timed
branch with a timeout: `choose: { door: { timeout: true } }` sends the
`timeout` input; `lute test` reads the same.
